# 犬猫マイクロチップ登録（試作）

環境省 自然環境局 総務課 動物愛護管理室の「[要件定義書](https://www.env.go.jp/content/900517405.pdf)」（令和 3 年 4 月。指定登録機関 Web システムの要件）が定義する業務を、YDE のワークスペースとして再現する試作です。
プログラムは書かず、情報の形（型・番号・参照・状態の流れ）と操作（登録・所有者変更・届出・検索・通知）を YAML で定義し、架空のデータで動かします。
`samples/todos-sysdev` の前提「要件定義は業務モデルそのもの」と同じ立場で、要件定義書の業務を、動く業務モデルとして書き直したものです。

2 つの層があります。

- **動く業務モデル**（`.yde/` と `registry/`）: 型、状態の流れ、操作、検査、一覧、ダッシュボード、レポート。画面でも CLI でも、同じ名前の操作で業務を進められます。
- **業務の記述**（`spec/`）: 要件定義書の業務一覧・利用者区分・帳票・API・業務フローを写した文書。どの業務をどの操作・ビュー・レポートで再現したかを参照でつなぎ、再現していない部分を「足りないこと」に書きます。

データはすべて架空です。人名・団体名・住所（番地は X-X-X）・電話番号（中央は 0000）・メールアドレス（example.* のドメイン）・自治体（都道府県コード 98・99 は実在しません）・マイクロチップ番号（先頭 999）は、実在のものと関係ありません。

## 再現した範囲

要件定義書の業務一覧（表 6）は 27 業務です。

| 再現の状態 | 件数 | 業務 |
|---|---|---|
| 再現 | 22 | 登録・所有者変更・情報変更・死亡届・再交付（単体と紙運用）、飼養管理検索、ワンストップ情報照会、逸走情報検索（紙運用を含む）、アカウントの登録・更新・削除、トレーサビリティ照会、ヘルプデスク、コールセンター、マスタ設定 |
| 一部 | 5 | 一括の登録・所有者変更・情報変更（外のスクリプト）、ワンストップ通知・飼養管理通知（外のスクリプトと、手で送るメール） |

表 6 に無く、業務フローとユースケース図にある 3 つ（所有者別検索＝再現、手数料支払＝一部、ログイン＝対象外）も記述しています。
業務ごとの対応は、ダッシュボード「要件定義書との対応」か `spec/businesses.yaml` にあります。

再現していないのは、Web システムとしての手段です。

| 要件 | このワークスペースでの扱い |
|---|---|
| ログイン、利用者区分ごとの閲覧制限 | ありません。利用者区分ごとにダッシュボードを分け、「自分」（所有者・自治体）を入力で選んで絞ります。見せ方で、権限ではありません |
| 決済（クレジットカード・コンビニ払い） | システムの外です。確かめた入金を、操作「手数料の支払を記録する」で記録します |
| メール（登録証明書の送付・完了連絡・通知） | 送りません。登録証明書と通知の文面をレポートで作ります |
| 個別 Web と共通 DB の分離、API | 1 つのワークスペースにまとめています。API 一覧（別紙 4）は、同じ働きをする操作・前提・ビューに対応付けています（`spec/apis.yaml`） |
| 一括（CSV）と結果 CSV | 外のスクリプト `scripts/bulk.py` が、操作を 1 行ずつ呼びます |
| 日次バッチ | 外のスクリプト `scripts/daily-batch.py` を、OS のスケジューラから動かします |
| PDF・Word の帳票、申請書の様式 | 登録証明書は HTML です（ブラウザの印刷で PDF にします）。申請書の様式は、要件定義書に示されていないので作っていません |
| 規模（年 57 万件の登録）、非機能要件 | 対象外です。架空データは数十件です |

## 状態の流れ

| 対象 | 流れ |
|---|---|
| 申請・届出 | 受付（支払待ち）→ 支払済み → 完了。手数料の要る手続（新規登録・所有者変更・再交付）は受付から、届出（情報変更・死亡届）は受け付けた時点で完了です |
| マイクロチップ登録 | 新規登録の手続が完了するとでき（登録済み）、死亡届で死亡になります |
| アカウント | 有効 → 削除済み |
| 問い合わせ | 未回答 → 回答済み → 完了。電話の問い合わせは、回答済みから始まります |

## 操作

| 操作 | アクション ID | 受け手 | 内容と前提 |
|---|---|---|---|
| 所有者情報を登録する | `register-owner` | なし | 所有者を作ります。番号は採番します |
| マイクロチップ情報登録を申請する | `apply-registration` | なし | 新規登録の申請を受け付けます。同じ番号の登録や、手続の途中の申請があれば断ります（二重登録の確認） |
| 所有者変更登録を申請する | `apply-transfer` | マイクロチップ登録 | 新しい所有者の申請を受け付けます。変更キーが合い、いまの所有者と違い、手続の途中の申請が無いことが前提です |
| 登録証明書の再交付を申請する | `apply-reissue` | マイクロチップ登録 | 変更キーか、所有者の登録した電話番号で本人確認をします |
| 手数料の支払を記録する | `record-payment` | 申請・届出 | 支払待ちの申請に支払を記録します。支払額が料金と同じことが前提です |
| 手続を完了する | `complete-application` | 申請・届出 | 支払済みの申請を完了にし、登録へ反映します（新規登録は登録を作り、所有者変更は所有者と所在地を変え、どれも新しい変更キーを発行します） |
| 情報変更を届け出る | `report-change` | マイクロチップ登録 | 犬猫の名前・毛色・所在地と、所有者の連絡先を変えます。変えたい項目だけを入れます |
| 死亡を届け出る | `report-death` | マイクロチップ登録 | 登録を死亡にします |
| アカウントを登録する・情報を更新する・削除する | `register-account`・`update-account`・`delete-account` | なし・アカウント | 行政と指定登録機関のアカウントを扱います |
| 問い合わせを受け付ける・回答する・完了にする | `receive-inquiry`・`answer-inquiry`・`close-inquiry` | なし・問い合わせ | ヘルプデスクの問い合わせを進めます |
| 電話の問い合わせを記録する | `record-call` | なし | コールセンターの応対を、内容と回答ごと記録します |

- 状態を変える操作は、どの状態からできるか・移り先・状態の履歴の行を、状態の流れから決めます。
- オンラインの申請と紙の申請は同じ操作で、経路の値で区別します。紙の申請では、入力した担当者を入れます。
- 変更キーは、登録・所有者変更・再交付が完了するたびに変わります（`CK-` と申請番号の数字。実システムは推測できない値を発行します）。

## 検査

| 検査 | 中身 |
|---|---|
| 状態と記録の整合 | 死亡の登録には死亡日がある、完了した申請には完了日がある、支払済み・完了の申請には支払がある、届出には料金と支払が無い、など |
| 手続種別ごとの内容 | 新規登録には登録の申請内容、所有者変更には旧所有者、死亡届には死亡日、通知の対象になる手続には手続の時点の所在地がある |
| 日付の順 | 生年月日 ≤ 装着日 ≤ 登録日、受付日 ≤ 完了日、オンラインの申請は受付日 ≤ 支払日 |
| 参照を辿る検査 | 支払額は料金の手数料と同じ、料金は手続種別と経路に合う、母親はメスで同じ種別で子より先に生まれている、1 つの登録に手続の途中の申請は 1 件まで |
| 関係の多重度 | 登録は所有者と所在地の自治体を 1 件ずつ、申請は申請者を 1 件、母親の関係は循環しない |
| 業務の記述 | 再現・一部とした業務には対応する操作・ビュー・レポート・スクリプトがある、一部・対象外には足りないことが書いてある、業務には業務フローがある、システム利用の工程には対応か理由がある、ダッシュボードは利用者区分か業務に対応付いている |

## 試す

作業用にこのディレクトリをコピーし、YDE で開いてください（操作は原本を書き換えます）。「指定登録機関（登録業務）」から始まります。

1. 上部の「業務の流れ」で、受付（支払待ち）4・支払済み 2・完了 40 を確かめます。線「手数料の支払を記録する 4/4」を押すと、支払待ちの申請が並びます。
   APP-000042（わらびの新規登録）で操作を始め、支払額に `300` を入れて確認します。`200` を入れると「支払額が、申請の手数料（料金一覧）と違います」と止まります。
2. 線「手続を完了する」から、支払済みにした申請を完了します。差分に、マイクロチップ登録 `MC-999000000000044` の作成（所有者・所在地・変更キー `CK-000042`・状態の履歴）と、申請の完了が入っています。
   `Ctrl+Z` 1 回で、作った登録ごと戻ります。
3. 「すべての登録」で `MC-999000000000003`（だいふく）を開き、「この対象の操作」から「所有者変更登録を申請する」を選びます。新しい所有者 `OWN-0006`、変更キー `CK-000003`、所在地の自治体 `LG-991037` を入れます。
   変更キーを違う値にすると「変更キーが違います」、新しい所有者をいまの所有者 `OWN-0001` にすると理由つきで止まります。
   申請 → 支払の記録 → 手続の完了と進めると、登録の所有者と変更キーが変わります。古い変更キーでは、次の手続ができません。
4. 同じ登録で「死亡を届け出る」を適用すると、登録が死亡になり、届出（完了）ができます。死亡にした登録では、所有者変更・情報変更・再交付が理由つきで無効になります。
5. ダッシュボードを「基礎自治体（ワンストップ情報）」に切り替え、自治体に「あおば市」、完了日（から）に `2026-04-01` を入れます。あおば市へ通知する犬の手続だけが並びます。
   情報種別が所有者変更の行は、所有者が手続の時点の申請者（新しい所有者）になっています。
6. 「都道府県等（飼養管理・検索）」の「基準超過の疑い（仮の基準）」に、さくら（2018 年生まれ）の子が並びます。所有者の氏名・名称に `ペット` と入れると、所有者別検索がペットショップの犬猫に絞られます。
7. 「警察（逸走情報検索）」でマイクロチップ番号に `MC-999000000000012` を入れると、すずと、いまの所有者の連絡先が出ます。
8. 「ヘルプデスク・コールセンター」の業務の流れで、未回答の INQ-0003 に回答し、完了にします。マイクロチップ番号に `MC-999000000000004` を入れると、「トレーサビリティ照会」に あずきの登録・所有者変更 2 回・情報変更が並びます。
9. 台帳の「ビュー」で「マイクロチップ登録証明書」を選び、番号に `MC-999000000000004` を入れて「作る」を押します。手続を完了したあとで作り直すと、変更キーが変わっています。
10. 「要件定義書との対応」で、業務一覧の再現の状態と足りないことを確かめます。台帳の「フロー」タブで「業務フロー図」を選び、文書に `BF-01` を選ぶと、登録のスイムレーンの図が出ます。
    箱を選ぶと、右に工程の詳細（対応する操作かビュー）が出ます。

見てほしい点は、業務の流れと「この対象の操作」で業務を迷わず進められるか、前提で止まったときの文面で直し方が分かるか、利用者区分ごとのダッシュボードの入力（自分を選ぶ）が業務の入口として成り立つか、要件定義書との対応が「どこまで再現したか」の説明として読めるか、です。

## 動かし方

リポジトリの根で実行します（Windows は `yde.cmd`、Python は `py -3`）。

```bash
./yde validate labs/microchip-registry                                   # 検証（配布時はエラー 0・警告 0）
./yde behavior-scenarios labs/microchip-registry labs/microchip-registry/scenarios/lifecycles.yaml   # 業務シナリオ 15 件（宣言した 15 の遷移をすべて通る）
```

## 決めていること

- **申請・届出を独立させます。** 手数料の支払待ちを状態として持てます。新規登録は、手続が完了するまでマイクロチップ登録の文書を作らず、申請が内容を預かります（要件の「登録することが確定したデータを共通 DB へ格納する」に当たります）。
- **ワンストップ通知と飼養管理基準超過の判定は、書き込まずに導きます。** 業務フローの「ワンストップ通知登録」「飼養管理基準超過判定・通知登録」は、申請・届出と登録からビューで求めます。
- **申請・届出に、手続の時点の所在地を残します。** ワンストップ情報の通知先は、いまの所在地ではなく、手続の時点の所在地です。所有者は、手続の時点の申請者です。
- **紙運用は別の操作にしません。** 業務フローでは担当者が同じ入力をするだけなので、経路の値と担当者で区別します。紙の申請は先に支払うので、支払日が受付日より前でもかまいません。
- **利用者区分は、ダッシュボードで分けます。** 権限ではありません。「自分」は入力で選びます。
- **変更キーは、申請番号から決まる値で代用します。** 秘匿性は再現しません。前提で照合し、手続のたびに変えるところだけを再現します。
- **決済・メール・ログインは扱いません。** 決済は確かめた入金の記録、メールはレポートの文面、ログインは対象外です。入金は外で起きる事実として、Event の種類（`payment-settled`）だけ宣言しています。
- **マイクロチップ番号の ID は「MC-」を付けます。** 数字だけの値は YAML が数として読むためです。
- **料金と飼養管理の基準は仮です。** 料金の額と、基準超過の判定条件は要件定義書に無いので、仮の値（出産時に母親が 6 歳を超える）を置いています。

## 要件定義書を写して気づいたこと

業務を動く形にすると、要件定義書に書かれていない決まりが見えます。

- **支払われない申請の扱いが無い。** 支払待ちのまま残る申請の取り下げや期限がありません。ここでは取り下げの操作を作らず、「支払待ちが 14 日以上」の区画で気づけるようにしました。
- **業務一覧（表 6）とユースケース図・業務フローが合わない。** 所有者別検索は、ユースケース図と業務フローにあり、業務一覧にありません。
- **飼養管理基準の超過の判定条件が無い。** 共通 DB が判定するとあるだけで、条件と、判定に使う項目（母親・出産回数・交配時の年齢）の登録の仕方がありません。
- **手続の途中の重なりの扱いが無い。** 同じ犬猫に、所有者変更の申請中に死亡届や再交付が来たときの決まりがありません。ここでは、手続の途中の申請がある登録には、次の手続を受け付けません。
- **情報変更で通知先が変わるときの扱いが無い。** 所在地が別の市区町村へ変わる情報変更を、前の市区町村へも通知するかが書かれていません。ここでは、変更後の所在地へ通知します。

## 残り

- ローカル接続の業務 Web での確認（利用者区分ごとに、接続者へ操作を許可して使う）は試していません。
- 画面での確認は、この試作を作った環境（Linux のコンテナ）ではできていません。定義・データ・操作・ビュー・レポート・業務フロー図の表示モデルは、CLI で確かめています。
- 業務フローの工程は、レポートと skill を参照で指せません（定義の索引に載らないため）。登録証明書やマスタの取り込みの工程は、備考の文字で対応を書いています。
