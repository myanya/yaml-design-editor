# エージェント向け作業ガイド

このワークスペースは、TODO Webアプリの設計体系を YAML Design Editor 向けに作成する実験場です。
目的・前提・配置・記述例は [README.md](README.md)、各文書の項目は [.yde/schemas](.yde/schemas) を参照してください。
リポジトリ共通の作業規約は [CLAUDE.md](../../CLAUDE.md) に従います。

## ドメインを起点とする設計

- 複数利用者・メールアドレスとパスワードによる認証・利用者間で共有しない方針は確認済みです。
- 利用者・認証、TODO管理、分類・タグ管理を別のドメインとして扱います。
- ドメイン一覧がドメインのID・タイトル・概要・種別を定義し、同じIDのドメイン定義書で詳細化します。
- ドメインの種別はDDDのサブドメイン分類（`core`・`supporting`・`generic`）を使い、事業上の役割に基づいて一覧側で管理します。
- `21_domains` のドメイン定義書を、各種定義・設計書の導出元とします。1文書でサブドメイン相当の対象範囲を扱います。
- 管理対象のエンティティはドメイン定義書の `entities`、提供操作は `operations` に定義します。
- エンティティのID・名称・意味、提供操作のID・目的・業務上の契約は定義元で管理します。
- `33_entities` はドメイン内のエンティティと同じIDを使い、論理属性・型・制約を詳細化します。新しい定義出現にはしません。
- 画面・API基本設計・サービスには `domain_operations` で提供操作への参照を記述し、導出の根拠を辿れるようにします。
- 新しい管理対象や提供操作が必要なら、まずドメイン定義書に追加し、それを根拠に後続設計を更新します。
- ドメインの変更時は、同一IDの詳細化文書と被参照先を確認します。名称・説明・対応一覧を両側に複製しません。
- 未決事項は `notes` に明記し、技術選定や業務ルールを決定済みとして補いません。
- ドメイン定義書の情報項目・入力と論理エンティティの属性には、`data_type` で業務データ型一覧の `DT-*` を参照させます。
- 操作の結果は `result` に直接定義します。`kind` で単独の値・複合値・戻り値なしを区別し、戻り値がある場合は `multiple` と `required` を明記します。
- 結果の複合値は `attributes` に返却属性を列挙します。単独の値と各返却属性の `data_type` は値型一覧を参照し、モデル型で結果全体を包みません。
- 結果全体の `name`・`description` は設けません。名称・意味は各返却属性に記述し、結果全体への補足は `constraints` に記述します。
- 結果は成功時の返却情報を表します。失敗の条件は `errors` に記述し、返却項目の変更と表記の変更を区別します。
- 型の制約・選択肢・構成項目は個別の型定義書に記述します。必須・複数値の指定と、その場所に固有の条件は型を使う側で記述します。
- 所有者や参照先の存在などの業務条件はドメイン側に置き、通信形式・言語の型・DBの物理型は後続設計で対応付けます。

## 配置と記述

- README.md と AGENTS.md は `sysdev-todo` 直下、本ツールの設定・スキーマは `.yde` に置きます。
- 各設計文書は一覧と個別設計書に分けます。一覧にID・タイトル・概要・種別・設計状態を置き、個別側に同じIDと詳細・未決事項を記述します。
- 一覧のタイトル・概要・種別などを個別設計書に複製しません。
- ドメインは `21_domains/domain-list.yaml` と `21_domains/<ID>.yaml` に配置します。
- 業務データ型のうち、単独の値を表す値型は `22_valuetypes/value-type-list.yaml` と `22_valuetypes/DT-*.yaml` に配置します。
- 複合情報を表すモデル型は `23_modeltypes/model-type-list.yaml` と `23_modeltypes/DT-*.yaml` に配置します。
- `23_modeltypes` の位置付けは検討中です。既存定義と入力側の参照を保持し、操作の結果との同期やモデル型の整理は別途検討します。
- 両方の型で `DT-*` を使い、IDはワークスペース全体で一意にします。モデル型の構成項目から値型や他のモデル型を参照できます。
- 他の設計文書を作成するときも、既存のスキーマのひな型を一覧と個別設計書の分担に合わせて整えてから記述します。
- 一覧と個別のスキーマのmatchを重複させず、同一IDの定義出現と詳細化出現を使い分けます。
- 記述は日本語、キーとIDはスキーマに従い、UTF-8・LF・YAMLのインデント2スペースを使います。
- 操作名は「何をどうするか」が自然に伝わる日本語にします。説明文でも助詞や動詞を省きすぎず、操作の対象と条件を明確にします。
- 設計体系を変更するときは、関連するスキーマ・参照範囲・関係レジストリ・READMEを整合させます。
- 自動生成・自動同期の定義はまだありません。後続設計は導出元を読んで具体化し、参照を残します。

## 確認

リポジトリルートからREADME記載のCLI検証を実行し、定義エラー・IDの重複・未解決参照を確認します。
スキーマ変更時は、ドメイン内のエンティティ・提供操作と後続設計を含む仮文書で参照解決を確認します。
検証用の仮文書は `scratchpad` などの一時領域に置き、設計の原本へ混ぜません。
