# RPG Maker MZ データベースの計画

目的: RPG Maker MZ（以下 MZ）のデータベースを YDE のワークスペースで再現する。YAML を原本にして MZ の JSON を書き出し、実際の MZ で動かして確かめる。既存の MZ プロジェクトの JSON も取り込めるようにする。
本体側の汎用の JSON の取り込みと書き出しは [ROADMAP P50](../../docs/ROADMAP.md) で進める。この文書は案で、順番と着手はオーナーが決める。大きさの目安は、小＝半日以内・中＝1 日・大＝数日。

## 決まったこと（2026-11-02 オーナー）

- 検証のために、書き出したデータを実際の MZ に戻して動かす。既存の MZ の JSON を取り込めるようにもする。そのために、汎用の JSON の取り込みと書き出しを本体で開発する（P50）。
- 変換は、まず往復を成立させ、分かったことを宣言型の定義へ寄せる。
- 項目名は MZ のままにし、ラベルを日本語にする。
- データの題材は現代ホラーの探偵もので、名前も文章も架空のオリジナルにする。
- 画像・音・動画・フォントなどのアセットは取り込まない（公開リポジトリに載せない）。フリーの素材はオーナーが後で探す。
  - 2026-11-02 オーナーが、4 人のアクターのための AI 生成のオリジナルの素材（顔・歩行・装備のアイコン）を用意して「取り込んで」と指示した。MZ でそのまま使う形のものだけを `img/` に置いた（原画は置かない）。MZ の既定の素材は今までどおり取り込まない。
- 形の照合には、オーナーが手元に作った MZ の新規プロジェクト（リポジトリの外）を使う。
- P50 は MZ に依存しない汎用の機能として、P49 より先に v0.2.x の中で作る。ワークスペースの外への書き出しは、実行のときに人が選んだ場所だけ。

## 本体の準備（P50。2026-11-02 完了）

- JSON を木のまま取り込む（`input.tree`）・木を組み立てて書き出す（export の `build`・番号の位置・既存の object への書き込み・要素ごとに 1 行の書式）・書き出し先を実行のときに選ぶ（画面の「出力先を選ぶ…」・CLI の `--out`）・書く前の差分（`--dry-run`）・ID から番号を取り出す値の式 `extract`。
- 新規プロジェクトの JSON 14 ファイルを恒等の定義で YAML に取り込んで書き出すと、全ファイルがバイト単位で元と一致した。MZ の項目の形の変換（接頭辞・能力値の名前・成長表）は、段階 2・3 で rpmz の定義に書く。
- これで変換のスクリプトは要らなくなった（正解は MZ の元の JSON）。
- data フォルダの一式は、書き出しの定義を束ねる `include` で 1 回で書く。上書きは一括で確認し、控えは取らない（オーナー 2026-11-02）。書き出す前に MZ でプロジェクトを閉じる（開いたままだと、MZ が手元の古いデータで上書き保存することがある）。

## 全体方針

1. **原本は YAML、MZ の JSON は書き出した派生物**。既存プロジェクトの JSON は、移行のときに取り込む。
2. **YDE が持つのはデータベースのデータまで**。マップ・コモンイベント・アニメーション・タイルセット・システム設定の大半は MZ が持つ。YDE は参照先として番号と名前だけを読む。YDE が持つファイルを MZ で編集したら、書き出す前に取り込み直す。
3. **MZ の項目名と値をそのまま使い、変えるのは次の 4 点だけ**。区分の番号（`scope: 1` など）は MZ の数のまま持ち、画面では「敵単体」のような日本語のラベルで見せる。
   - ID と参照に種類の接頭辞を付ける。番号は MZ の位置のまま（`SKL-0010`＝スキルの 10 番。タイプは `ELM-02` のように 2 桁）。
   - 能力値の 8 個の並びに名前を付ける（`params: { atk: 10 }`）。職業の成長表はレベルを行にした表にする。
   - 先頭の `null` と空き枠は持たない（書き出すときに埋める）。
   - 「-1＝通常攻撃」は特別な ID（`ELM-NORMAL` など）を一覧に置いて表し、「0＝なし」は項目を書かないことで表す（下の「段階 1 で決めたこと」）。
4. **1 件を 1 ファイルにする**（`db/skills/SKL-0010.yaml`）。タイプのような小さな一覧だけは 1 ファイルにまとめる。
5. **素材の無い画像の欄は空にしておく**。MZ は名前が空の画像を読まないので、画像も音も無いままテストプレイできる（エンジンの `ImageManager.loadBitmap` で確かめた）。素材があるアクターの画像は、ワークスペースの中の場所で書く（段階 3）。
6. **本体を直すのは、ここで必要が確かめられたものだけ**。足りない語彙は P50 か BACKLOG に登録し、着手は個別に判断する。

## 実物で確かめたこと（段階 0。2026-11-02）

新規プロジェクトの `data/*.json` の形（キー・型・値の範囲・書式）を要約した。中身の文章は読み出していない。

- **書式**: 一覧のファイルは `[` の次に `null,`、要素を 1 行に 1 つ並べ、最後は `]` で末尾に改行が無い。System.json は全体が 1 行（`editor.jsonFormatLevel: 1`）。差分を小さくするには、この書式で書き出す必要がある。
- **キーの順**: アルファベット順ではない（アクターは `faceName` の次が `traits`、その後に `initialLevel`。System.json は新しい版で足されたキーが末尾に並ぶ）。書き出しはひな型の順に出し、System.json は元のキーの順を保つ必要がある。
- **省略されるキー**: ステートの `releaseByDamage` は 30 件中 8 件にしか無い。無い値は書かない（`null` を書かない）。
- **数**: 特徴の `value` などは整数と小数が混ざる（`1` と `0.95`）。整数は整数のまま書く。
- **配列の中の null**: System.json の `terms.commands` に `null` が 2 つある。保つ必要がある。
- **職業の成長表**: 8 能力 × 100（0〜99 レベル）。0 レベル目の値はばらばらで、エンジンは使わない（レベルは 1 から）。
- **System.json のタイプ**: 属性・スキルタイプ・武器タイプ・防具タイプ・装備タイプ・スイッチ・変数は、先頭が空文字の文字列の配列。武器タイプの数と `attackMotions` の数がそろう（どちらも 13）。
- **エンジンの約束**: ステート 1 は戦闘不能、スキル 2 は防御、スキル 1 は既定の攻撃（特徴で変えられる）。初期パーティ（`partyMembers`）は無いアクターを飛ばすので、架空のアクターに合わせないとパーティが空になる。
- **件数**: スキル 235・防具 100・武器 50・アイテム 30・ステート 30・職業 8・アクター 8・敵キャラ 5・敵グループ 5。タイルセットは 1 件に 8192 個の数を持つ。

```
    types.yaml       # タイプ（属性・スキルタイプ・武器タイプ・防具タイプ・装備タイプ）
    system.yaml      # 初期パーティ・戦闘テスト・エンジンの約束
    specials.yaml    # 特別な値（ELM-NORMAL・ANI-NORMAL・STA-NORMAL）
    refs/            # MZ が持つものの番号と名前（animations.yaml・switches.yaml。要るときに common-events.yaml・variables.yaml）

```

## 段階 1 で決めたこと（2026-11-02。見直しはオーナーの判断）

- **特別な値**: 一覧 `db/specials.yaml` に `ELM-NORMAL`・`ANI-NORMAL`・`STA-NORMAL` を置き、MZ が許す項目の参照の型だけが選べる（ダメージの属性・使用時のアニメーション・ステート付加）。ほかの項目では検査で誤り。書き出しで -1 か 0 にする。
- **「なし」（MZ の 0）**: 項目を書かない。アクターの初期装備の空の欄は `~`（空の欄は検査で誤りにならないことを確かめた）。
- **エンジンの約束**: `db/system.yaml` の `engine` に、ステート 1・スキル 1・スキル 2 を番号を固定した参照で書く。無ければ参照の切れとして誤りになる（書き出しはしない）。
- **敵グループのバトルイベント**: `pages` は型を決めずに持つ（取り込んだまま）。無ければ書き出しで空のページを 1 つ置く。
- **ドロップアイテム**: 使う枠だけを書き、4 つ以上は誤り。書き出しで 3 つの枠に埋める。
- **特徴と使用効果の値**: `dataId` と値（`value`・`value1`・`value2`）を種類ごとの項目にする。倍率・確率は % で見せ、ターン数・回数は数のまま（オーナーの試用で「0.5 のまま」と指摘されて直した）。MZ が使わない値（例 スキルタイプ追加の `value`）は項目にせず、取り込んだときだけそのまま持つ（`unknownFields: allow`。MZ は 0 か 1 をまちまちに持つため）。
- **特徴・使用効果・行動パターン・ドロップの並び**: 表ではなく縦の並び（`display: list`）にする。表では種類で変わる項目が列に出ないため（オーナー「種類はどれですか？」）。本体も、種類で項目が変わる並びを自動では表にせず、要約に選択肢の名前と参照先の名前を出すように直した（UX-233・UX-234）。
- **職業の成長**: レベル 1 とレベル 99 の値から、曲線（L1 ＋（L99 − L1）×（(L − 1) ÷ 98）^1.15）で作った。0 レベル目は持たない（エンジンが使わない）。
- **成長曲線の図（段階 4 の先取り）**: 99 行の表は「直感的でない」（オーナー）ため、職業の文書ビュー `.yde/views/class-doc.yaml` で、開いた文書の `params` を折れ線にする。本体に「文書ビューの区画にその場のチャート（`rows`）」を足した（UX-235）。
- **検査を誤りの例で確かめた**: 写しに 8 種の誤り（種類の違う dataId・計算式なし・ドロップ 4 つ・許されない特別な値・ステート 1 の欠落・成長 98 行・初期レベル超過・無い武器）を入れ、すべて指摘された。

## 段階 2 で分かったこと（2026-11-02）

- **取り込みの定義**: `.yde/skills/import-*.yaml` の 14 個。MZ の新規プロジェクトの JSON（System・Actors・Classes・Skills・Items・Weapons・Armors・Enemies・Troops・States・Animations・CommonEvents）を、リポジトリの外の空の写しに取り込んだ（476 文書）。既定のデータはリポジトリに入れていない。
- **検証**: 誤り 0・警告 0。区分・数の範囲・参照（属性・ステート・スキル・タイプ・装備）・職業の成長表（99 行）は、すべて既定のデータに収まった。
- **空きの番号**: 既定のデータには、名前の無い項目（スキル 86・防具 14・武器 10・アイテム 7・ステート 3、アニメーションとコモンイベントに 4）がある。区切りや未使用の番号で、MZ では配列の中に既定の値のまま並ぶ。番号を保つため取り込み、名前（と、空きの武器が持たない武器タイプ）を必須から外した。
- **MZ が使わない値**: 攻撃時属性の `value: 0` などは、決めたとおり取り込んだまま持つ（`unknownFields: allow`）。
- **初期装備の欄の種類**は並びの位置で決めた（1 番目が武器・ほかは防具）。二刀流のアクターは扱っていない（既定のデータには無い）。
- **職業の成長表**: 能力値ごとの 100 個の並び × 8 を、本体に足した `$zip`（並んだ配列を同じ番号で 1 行に）でレベルの行にする（オーナーが案 A を選んだ）。武器タイプの攻撃モーションも同じ書き方で、名前の並びと並べて読む。
- **0 レベル目は持たない**（オーナー）。エンジンは使わない。段階 3 の往復では、職業の 0 レベル目の値だけが元の JSON と違ってよい。
- **まだ書けないこと**（本体の BACKLOG）: スキルタイプの魔法スキル（番号の一覧 `magicSkills` に自分の番号があるか。UX-239）。特徴などの規則を 9 つの定義に写した（UX-237）。null の出し方は回り道をした（UX-238）。

## 段階 3 で分かったこと（2026-11-02）

- **書き出しの定義**: `.yde/skills/export-*.yaml` の 10 個と、束ねる `export-all`。配列は MZ と同じ書式（先頭の `null`・1 行に 1 要素・末尾に改行なし）で、System.json は既存のファイルにタイプ・初期パーティ・戦闘テストだけを書き込む（`mode: merge`）。魔法スキル・スイッチ・変数の名前は MZ の値のまま（書き込まない）。
- **往復**: 新規プロジェクトの JSON を取り込んで書き出すと、Actors・Skills・Items・Weapons・Armors・Troops・System はバイト単位で一致した。Enemies と States は値が同じでキーの並びだけが違い、Classes は 0 レベル目の値だけが違う（1 レベル目の値を書く。既定のデータの 0 レベル目は職業ごとに 3 通りあり、決まった値ではない）。
- **キーの並び**: MZ は読んだときの並びのまま保存するので、既定のデータでもステートは 4 通り、敵キャラの行動パターンは 2 通りの並びが混ざる。書き出しは、いちばん多い並びに合わせた。ゲームの動きには関係しないが、差分には出る（本体の BACKLOG UX-240）。
- **素材**: アクターの画像の欄を、名前の文字からワークスペースの中の場所（file 型）にした。フォームで画像が見え、書き出しでは名前に戻す。無い画像は警告（`.yde/workspace.yaml` の `files.missing: warning`。既定のデータを取り込むと、MZ にだけある画像を指す 24 件が警告になる）。装備のアイコンは、YDE で見るための `iconImage` を足した（書き出さない）。
- **架空のデータの書き出し**: 新規プロジェクトの data の写しへ `export-all` で書き、アクターの画像の名前・特別な値（-1）・成長表の 100 個の並び・System.json のほかの設定が保たれることを確かめた。

## 段階 4 で分かったこと（2026-11-02）
