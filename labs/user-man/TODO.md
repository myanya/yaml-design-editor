## 進め方と更新ルール

1. セッション開始時は、本書の「再開位置」と対象項目の関連ルールを読む。
2. 一覧は未解決の論点を管理する台帳として使う。仕様書の具体化に必要な項目を選び、着手時に状態を「検討中」にする。番号順の全項目の解決を、他の仕様書の作成に先行させない。
3. 確認はチャットで関連する質問をなるべくまとめて行い、未確認の一般的な機能を確定仕様として補わない。
4. 合意した内容を対応するYAMLへ反映し、一覧の「反映先・完了根拠」に実際のファイルへのリンクとRULE／RITMのIDを記録する。
5. YAML・スキーマ変更時は、[検証手順](OPERATIONS.md#cliによる検証)に従って確認し、結果を記録する。
6. セッション終了前、話題の切り替え時、回答の仕様反映後に、一覧と「再開位置」を更新する。

「再開位置」には、途中で決まったが未反映の内容、残る論点、次に確認する内容を具体的に残します。
仕様へ反映した決定の全文は本書に重複させず、原本への参照に置き換えます。
選択肢を提示しただけ、回答が得られていない、または検証が未実施の場合は、その事実を明記します。

| 状態 | 意味 |
|---|---|
| 未着手 | 追加検討事項の抽出のみ完了 |
| 検討中 | 利用者への確認や仕様の整理を進めている |
| 反映待ち | 合意済みだが仕様への反映または検証が残っている |
| 保留 | 理由・依存先・再開条件を記録して後回しにしている |
| 完了 | 合意内容を仕様へ反映し、必要な確認を終えている |

提供しないと決めた項目も、対象外の合意を仕様に反映して完了にできます。
完了はこの検討の完了を意味し、詳細設計・実装・試験の完了を意味しません。
完了後も一覧のID・状態・原本への参照は残し、長い検討経緯を残す必要があれば記録文書へ分離します。
IDは並べ替えても維持し、分割・追加する項目には新しいIDを付けます。

## 検討内容

### 検討-001 ユーザのライフサイクル

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[認証・セッション](10_specs/20_rules/RULE-0007-認証・セッション管理方式.yaml)、[パスワード](10_specs/20_rules/RULE-0014-パスワードに関する方針.yaml)

- [x] 管理者・担当者による登録、本人の新規登録なし、予約による特定日からの利用と「利用開始前」の事前登録を定める。
- [x] 状態を「利用開始前」「初期設定中」「利用中」「一時停止」「利用停止」「削除済み」とし、理由を管理して人事情報は持たない方針を定める。
- [x] 利用の許可と初期設定完了の両方を利用開始条件とする。
- [x] 初期設定未完了から再設定URL経由で再開し、自動取消・削除は行わず、管理者等向け画面で状態を表示する方針を定める。
- [x] 誤登録等の取消は通常の削除操作で行い、理由で取消を識別する方針を定める。
- [x] 「利用開始前」は事前登録中とし、再設定URL経由を含めて本人が初期設定を開始できないことを定める。
- [x] 「利用開始前」→「初期設定中」は管理者等の操作・予約、「初期設定中」→「利用中」は本人の初期設定完了によるものと定める。
- [x] 初期設定はパスワードと必要な多要素認証の設定までとし、会社・組織が登録済みの本人情報の入力は求めないことを定める。
- [x] 登録時のロール付与を任意とし、初期設定案内の契機と実送信の遅延を定め、[登録から利用開始の草案](10_specs/40_business_flows/BZFL-0001-ユーザ登録から利用開始.yaml)へ展開する（RITM-0206・0207）。
- [x] 一時停止と利用停止を運用上の意図で区別し、どちらも管理者等の操作・予約で再開でき、自動解除はしない方針を定める。
- [x] 各状態から論理削除でき、1か月経過後の次の月次バッチで物理削除する方針を定める。
- [x] 再開時は同じユーザと設定を引き継ぎ、削除済みからの復活はシステム管理者による直接DB操作の特殊な運用対処だけとする。
- [x] ロール別・操作別のテナント設定、管理者・担当者とも許可する既定値、ユーザの状態の変更権限、本人の状態変更禁止を定める。
- [x] 停止中の情報保持・変更と初期設定・パスワード設定、削除時のURL無効化、状態変更時の再ログインを定める。
- [x] 状態変更の予約、停止したユーザを対象とする情報変更、予約の登録者と実行権限者の停止の違いを定める。
- [x] 利用状態はユーザ単位で1つとし、本務・兼務ごとの利用状態を設けないこと、本務は異動で変更し兼務は解除できることを定める。
- [x] 理由は選択式と「その他」の自由記述とし、一時停止・利用停止・再開・削除で必須とする。
- [x] 選択肢はテナント・操作ごとに設定し、既定値を設けず、未設定なら自由記述のみとする。
- [x] テナント全体の担当者は、[操作権限](10_specs/20_rules/RULE-0005-管理者・担当者ごとの操作権限の違い.yaml)のRITM-0188に専用ロールとして定め、概要にも反映する。
- [x] 削除済みユーザの参照機能は提供せず、障害対応時にデータベースを直接確認する運用のみとする。
- [x] 削除済みの変更対象・実行権限者に関わる予約は実行エラー、登録者だけが削除済みなら別の実行権限者で実行可能とする。
- [x] 「利用開始前」では一時停止・利用停止を行わず、利用開始の操作をせずに保持するか、不要なら削除する。
- [ ] 「初期設定中」での停止可否と、初期設定完了前に停止した場合の再開先を具体化する。

### 検討-002 テナントの開設・停止・廃止

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[テナント分離](10_specs/20_rules/RULE-0002-テナント分離の原則.yaml)、[アーキテクチャ](10_specs/20_rules/RULE-0006-アーキテクチャ基本方針.yaml)

- [x] 利用側からAPI・サービスクラスで呼ぶ開設と、システム管理者が本機能を操作する開設の両方を提供する。
- [x] 本機能による開設では、管理対象機能向けのテナント作成と、注入された利用側コンポーネント経由の登録処理を連携できるようにする。
- [x] 利用側固有の情報表示・選択などの開設画面の拡張は提供しないことを定め、[テナント管理の草案](10_specs/30_subdomains/SDOM-0003-テナント管理.yaml)へ展開する。

- [ ] 停止中に許可する操作と、既存セッション・予約便・各種ジョブの扱いを決める。
- [ ] 廃止・再開の可否と、データ・ログの保管、廃止後の取得主体を決める。

- [ ] 組織の親変更、統合・分割、空のグループの可否を決める。
- [ ] 循環・最大階層超過の検査と、管理範囲が変わるユーザへの影響を整理する。
- [ ] 所属ユーザ、子組織、グループからの参照、ロール、予約が残る場合の削除条件を決める。

### 検討-006 ロール・権限そのものの管理

関連：[操作権限](10_specs/20_rules/RULE-0005-管理者・担当者ごとの操作権限の違い.yaml)、[認可](10_specs/20_rules/RULE-0008-認可方式.yaml)、[機能・権限マスタとロール管理](10_specs/20_rules/RULE-0018-機能・権限マスタとロール管理.yaml)

- [x] ユーザ管理も権限管理の対象となる一機能とし、他機能にも共通する権限管理を定める。
- [x] 機能・権限にID・表示名・説明を持たせ、権限マスタで機能ごとの権限一覧を管理する。
- [x] 開発者による定義に加え、テナント側でも機能・権限を追加・管理できること、機能に紐づく権限の追加・削除を提供することを定める。
- [x] テナント・機能ごとの独自ロール追加、権限設定の変更、初期ロールの位置付けを定める。
- [x] 機能の管理者ロールに権限設定を委譲し、委譲された管理者がその機能のロール等を作成・管理する方針を定める。
- [x] 利用側が機能IDに関するユーザのロールと、権限識別ID・権限値を取得して制御する責務を定める。
- [x] テナント全体のロールはユーザ・テナント・機能につき1つとし、テナント管理者は機能別ロールとは別に扱う。
- [x] 全機能共通の実行範囲の基準を原則として定め、全域管理の特例・システム管理者の除外を明記する（RITM-0203〜0205）。
- [x] テナント全域管理は組織・グループによる共通化と、組織権限をチェックしない特別な実装の両方を許容する（RITM-0204）。
- [x] ユーザ登録時のロール付与を任意とし、未指定で登録後もロール変更で設定できることを定める（RITM-0206）。
- [x] 登録時の指定ロール付与とユーザ登録を一体として成立させ、付与失敗時は登録も成立させない（RITM-0209、USCS-0001、DOPR-0005）。
- [x] テナントユーザ管理者の識別名をtenant-user-adminに変更する。
- [x] [権限管理](10_specs/30_subdomains/SDOM-0001-権限管理.yaml)と[ユーザ管理](10_specs/30_subdomains/SDOM-0002-ユーザ管理.yaml)のサブドメイン草案へ展開する。
- [x] 機能・権限マスタは各テナントに初期登録し、以後はテナントごとに独立して管理する方針を定める（RITM-0196）。
- [x] 管理者・担当者の名称や区分ではなく、設定された管理・付与の権限によって操作を制御し、名称が管理者でも操作できないロールを許容する（RITM-0197）。
- [x] RULE-0005の任命・付与・個人情報閲覧権限の設定条件を、初期ロールの設定と実際の権限による判定に整合させる。
- [ ] 機能登録時の管理者ロール自動作成案の採否を決める。
- [ ] 権限値の型・許容値・未設定時の扱いと、機能ID・権限識別IDの一意性・変更条件を詳細化する。
- [ ] 初期ロールの変更可能範囲の詳細と、ロールの削除条件を決める。
- [ ] 組織・グループで設定可能なロールと、各ロールで設定可能な権限の管理方法を決める。
- [ ] 付与権限の具体的な表現と、付与済みロールの内容変更にも必要となる制約を決める。
- [ ] 利用中のロール・権限・機能の廃止条件と、付与先や予約への影響を決める。

### 検討-008 システム管理者の権限境界

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[テナント分離](10_specs/20_rules/RULE-0002-テナント分離の原則.yaml)

- [x] テナント外のシステム管理者は組織・グループの原則の対象外とし、システム管理用の組織・グループを不要とする（RITM-0205）。
- [ ] テナント内のユーザ情報・設定・履歴を参照／変更できる範囲を決める。
- [ ] システム管理者の登録・任命・解除、ログイン方法、認証設定を決める。
- [ ] システム管理者自身の復旧方法と、テナントに属さない操作の監査先を決める。
- [ ] システム管理者とシステム運用者が同じ主体か、別の役割かを決める。

削除済みユーザの復活の提供範囲は、[ライフサイクル](10_specs/20_rules/RULE-0017-ユーザのライフサイクル.yaml)のRITM-0174で確定しています。
直接DB操作による特殊な復旧の実施記録と監査の扱いは、この項目で具体化します。

- [ ] 状態変更による再ログインと、権限変更の猶予設定・停止時の次回アクセスでの利用拒否の適用関係を具体化する。

### 検討-010 複数の管理経路を組み合わせた権限判定

- [ ] 操作の許可と対象範囲を同じ権限の根拠で満たす条件を決める。

- [ ] 複数の根拠で許可される場合の監査記録と、重複警告の対象条件を具体化する。

ENTY-0001だけを採番し、所属は関連、利用状態は値オブジェクトの草案としています。独立IDの要否と集約境界はまだ確定していません。
停止・再開の遷移表は未網羅です。初期設定中の停止可否・初期設定完了前の再開先は検討-001で具体化します。
所属先の重複の扱いは検討-004、削除済みデータを含む識別子の一意制約範囲は検討-017で扱い、草案の記述から未回答の条件を補いません。
詳細ユースケースと操作の具体化した約束には項目単位の参照を付けています。既存のほかの記述は具体化時にそろえ、全仕様書の移行完了とは扱いません。

## 文書体系の未決事項

文書形式に関する未決事項を管理します。採用済みの内容は共通記述規約または各種類の作成ガイドに反映します。

- [ ] 概要の文書の種類・分割構成とIDの要否・体系を決める。
- [x] モデル・操作はサブドメイン内で定義し、USCSに主担当サブドメインと具体化する操作を指定する。
- [ ] ルールの親子関係・個別ルール単位の関係のYAML表現と必須条件を具体化する。
- [ ] 親子・導出以外のルール間の関係の要否と表現方法を決める。
- [ ] サブドメイン・業務フローの草案形式を確認し、詳細ユースケース以降の一覧・個別文書の項目分担と一覧ファイル名を決める。
- [ ] サブドメイン内のモデル・操作と、画面・API等の後続の詳細定義との対応方法を決める。
- [x] 詳細ユースケースの一覧・個別文書と、各条件・手順・結果のRITM参照を持つ草案形式を具体化する。
- [x] 業務フローの手順・分岐からUSCSへ参照し、詳細側は逆参照で対応する業務フローを表示する。
- [x] エンティティ定義はサブドメイン内に置き、ENTY-0001から採番する。
- [ ] 画面・API定義の番号帯とディレクトリ構成を決める。
- [ ] 未採番の定義の採番開始値、欠番・廃止した番号、名称変更時のファイル名の扱いを決める。

## 文書への展開

横断的な決定は `20_rules` に反映し、必要に応じて既存ルールを補足するか新しいトピックとして分けます。
登録・異動・停止・復旧などの流れは、文書形式を利用者と確認しながら `40_business_flows` と `50_usecases` へ展開します。
登録から利用開始はBZFL-0001とUSCS-0001〜0005の草案を作成済みです。未確定の中断・失敗経路を、モデルと往復して具体化します。
モデルはサブドメイン内で育てます。画面・APIや後続工程の文書は、検討TODOを理由に先回りして作成しません。
ワークフロー／承認フロー、外部認証基盤との連携など、既存の対象外方針を暗黙に変更しません。
