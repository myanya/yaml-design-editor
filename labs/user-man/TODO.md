## 仕様書作成に先行する確認範囲

以下の検討順序は利用者と合意済みです。各項目に記載した未確定の業務仕様への合意を意味しません。
まず文書の骨格を左右する前提だけを確認し、各検討項目の細部は対応する仕様書を具体化する際に扱います。

| 具体化する対象 | 関連する検討項目 | 先に確認する範囲 |
|---|---|---|
| ロール・権限の概念と付与関係 | 検討-006 | 管理者・担当者の権限区分とテナント・機能別ロールの対応、テナント全体のロールの付与単位、機能・権限・ロールを定義する主体 |
| サブドメインの責務とシステムの境界 | 検討-021、002・003・008の一部 | 既存の提供機能を前提に、テナント開設・組織管理・権限定義などを本システムの機能、利用側の機能、運用作業のどこで担い、誰が行うか |
| 登録から利用開始までの業務の区切り | 検討-001・005・006・019の一部 | ユーザ登録と利用ロール付与の関係、初期設定用URLを案内する契機。事前登録・利用開始の操作・本人の初期設定という確定済みの流れは再確認しない |

一括登録・初期移行（検討-020）は、その経路を業務フローの対象に含める際に提供範囲を確認します。
入力項目の全制約、停止・復旧等の例外、権限変更の猶予、予約の競合・再実行、通知失敗、物理削除の詳細は、最初の概要草案の作成条件にしません。
サブドメインと業務フローは最初の具体例に合わせた草案形式を仕様書READMEに記載済みです。詳細ユースケースの文書項目と参照方法は、最初の具体例に合わせて最小限を決めます。

## 進め方と更新ルール

1. セッション開始時は、本書の「再開位置」と対象項目の関連ルールを読む。
2. 一覧は未解決の論点を管理する台帳として使う。仕様書の具体化に必要な項目を選び、着手時に状態を「検討中」にする。番号順の全項目の解決を、他の仕様書の作成に先行させない。
3. 確認はチャットで関連する質問をなるべくまとめて行い、未確認の一般的な機能を確定仕様として補わない。
4. 合意した内容を対応するYAMLへ反映し、一覧の「反映先・完了根拠」に実際のファイルへのリンクとRULE／RITMのIDを記録する。
5. YAML・スキーマ変更時は、[検証手順](README.md#開き方と検証)に従って確認し、結果を記録する。
6. セッション終了前、話題の切り替え時、回答の仕様反映後に、一覧と「再開位置」を更新する。

「再開位置」には、途中で決まったが未反映の内容、残る論点、次に確認する内容を具体的に残します。
仕様へ反映した決定の全文は本書に重複させず、原本への参照に置き換えます。
選択肢を提示しただけ、回答が得られていない、または検証が未実施の場合は、その事実を明記します。

| 状態 | 意味 |
|---|---|
| 未着手 | 追加検討事項の抽出のみ完了 |
| 検討中 | 利用者への確認や仕様の整理を進めている |
| 反映待ち | 合意済みだが仕様への反映または検証が残っている |
| 保留 | 理由・依存先・再開条件を記録して後回しにしている |
| 完了 | 合意内容を仕様へ反映し、必要な確認を終えている |

提供しないと決めた項目も、対象外の合意を仕様に反映して完了にできます。
完了はこの検討の完了を意味し、詳細設計・実装・試験の完了を意味しません。
完了後も一覧のID・状態・原本への参照は残し、長い検討経緯を残す必要があれば記録文書へ分離します。
IDは並べ替えても維持し、分割・追加する項目には新しいIDを付けます。

### 検討-001 ユーザのライフサイクル

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[認証・セッション](10_specs/20_rules/RULE-0007-認証・セッション管理方式.yaml)、[パスワード](10_specs/20_rules/RULE-0014-パスワードに関する方針.yaml)

- [x] 管理者・担当者による登録、本人の新規登録なし、予約による特定日からの利用と「利用開始前」の事前登録を定める。
- [x] 状態を「利用開始前」「初期設定中」「利用中」「一時停止」「利用停止」「削除済み」とし、理由を管理して人事情報は持たない方針を定める。
- [x] 利用の許可と初期設定完了の両方を利用開始条件とする。
- [x] 初期設定未完了から再設定URL経由で再開し、自動取消・削除は行わず、管理者等向け画面で状態を表示する方針を定める。
- [x] 誤登録等の取消は通常の削除操作で行い、理由で取消を識別する方針を定める。
- [x] 「利用開始前」は事前登録中とし、再設定URL経由を含めて本人が初期設定を開始できないことを定める。
- [x] 「利用開始前」→「初期設定中」は管理者等の操作・予約、「初期設定中」→「利用中」は本人の初期設定完了によるものと定める。
- [x] 初期設定はパスワードと必要な多要素認証の設定までとし、会社・組織が登録済みの本人情報の入力は求めないことを定める。
- [x] 登録時のロール付与を任意とし、初期設定案内の契機と実送信の遅延を定め、[登録から利用開始の草案](10_specs/40_business_flows/BZFL-0001-ユーザ登録から利用開始.yaml)へ展開する（RITM-0206・0207）。
- [x] 一時停止と利用停止を運用上の意図で区別し、どちらも管理者等の操作・予約で再開でき、自動解除はしない方針を定める。
- [x] 各状態から論理削除でき、1か月経過後の次の月次バッチで物理削除する方針を定める。
- [x] 再開時は同じユーザと設定を引き継ぎ、削除済みからの復活はシステム管理者による直接DB操作の特殊な運用対処だけとする。
- [x] ロール別・操作別のテナント設定、管理者・担当者とも許可する既定値、ユーザの状態の変更権限、本人の状態変更禁止を定める。
- [x] 停止中の情報保持・変更と初期設定・パスワード設定、削除時のURL無効化、状態変更時の再ログインを定める。
- [x] 状態変更の予約、停止したユーザを対象とする情報変更、予約の登録者と実行権限者の停止の違いを定める。
- [x] 利用状態はユーザ単位で1つとし、本務・兼務ごとの利用状態を設けないこと、本務は異動で変更し兼務は解除できることを定める。
- [x] 理由は選択式と「その他」の自由記述とし、一時停止・利用停止・再開・削除で必須とする。
- [x] 選択肢はテナント・操作ごとに設定し、既定値を設けず、未設定なら自由記述のみとする。
- [x] テナント全体の担当者は、[操作権限](10_specs/20_rules/RULE-0005-管理者・担当者ごとの操作権限の違い.yaml)のRITM-0188に専用ロールとして定め、概要にも反映する。
- [x] 削除済みユーザの参照機能は提供せず、障害対応時にデータベースを直接確認する運用のみとする。
- [x] 削除済みの変更対象・実行権限者に関わる予約は実行エラー、登録者だけが削除済みなら別の実行権限者で実行可能とする。
- [x] 「利用開始前」では一時停止・利用停止を行わず、利用開始の操作をせずに保持するか、不要なら削除する。
- [ ] 「初期設定中」での停止可否と、初期設定完了前に停止した場合の再開先を具体化する。

## 文書への展開

横断的な決定は `20_rules` に反映し、必要に応じて既存ルールを補足するか新しいトピックとして分けます。
登録・異動・停止・復旧などの流れは、文書形式を利用者と確認しながら `40_business_flows` と `50_usecases` へ展開します。

画面・API・エンティティ定義や後続工程の文書は、検討TODOを理由に先回りして作成しません。
