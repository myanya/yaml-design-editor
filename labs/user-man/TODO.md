# ユーザ管理仕様の検討TODO

ユーザ管理機能の開発に向けた追加検討事項と、セッションをまたぐ進捗を管理する台帳です。
ここに挙げた項目は検討候補であり、機能の提供や仕様を確定したものではありません。
確定仕様の原本は `10_specs/` のYAMLに置き、文書構成・命名・ID体系は [仕様書の作成方針](10_specs/README.md) に従います。

## 再開位置

- 作業中の項目：なし
- 次に扱う項目：検討-001「ユーザのライフサイクル」
- 次の一手：ユーザの登録から利用開始・停止・退職・削除までに必要な状態と、その区別をチャットで確認する。
- 回答済みで仕様に未反映の内容：なし
- 回答待ちの論点：なし（検討項目の整理まで完了）
- 保留・依存先：なし
- 直近の確認：既存の概要とRULE-0001〜0016を読み、追加検討事項を抽出済み。

## 進め方と更新ルール

1. セッション開始時は、本書の「再開位置」と対象項目の関連ルールを読む。
2. 原則として一覧の順に1項目ずつ扱い、着手時に状態を「検討中」にする。
3. 確認はチャットで行い、未確認の一般的な機能を確定仕様として補わない。
4. 合意した内容を対応するYAMLへ反映し、一覧の「反映先・完了根拠」に実際のファイルへのリンクとRULE／RITMのIDを記録する。
5. YAML・スキーマ変更時は、[検証手順](README.md#開き方と検証)に従って確認し、結果を記録する。
6. セッション終了前、話題の切り替え時、回答の仕様反映後に、一覧と「再開位置」を更新する。

「再開位置」には、途中で決まったが未反映の内容、残る論点、次に確認する内容を具体的に残します。
仕様へ反映した決定の全文は本書に重複させず、原本への参照に置き換えます。
選択肢を提示しただけ、回答が得られていない、または検証が未実施の場合は、その事実を明記します。

| 状態 | 意味 |
|---|---|
| 未着手 | 追加検討事項の抽出のみ完了 |
| 検討中 | 利用者への確認や仕様の整理を進めている |
| 反映待ち | 合意済みだが仕様への反映または検証が残っている |
| 保留 | 理由・依存先・再開条件を記録して後回しにしている |
| 完了 | 合意内容を仕様へ反映し、必要な確認を終えている |

提供しないと決めた項目も、対象外の合意を仕様に反映して完了にできます。
完了はこの検討の完了を意味し、詳細設計・実装・試験の完了を意味しません。
完了後も一覧のID・状態・原本への参照は残し、長い検討経緯を残す必要があれば記録文書へ分離します。
IDは並べ替えても維持し、分割・追加する項目には新しいIDを付けます。

### 検討-001 ユーザのライフサイクル

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[認証・セッション](10_specs/20_rules/RULE-0007-認証・セッション管理方式.yaml)、[パスワード](10_specs/20_rules/RULE-0014-パスワードに関する方針.yaml)

- [ ] 初期設定待ち・利用中・停止・退職・削除など、必要な状態と状態間の遷移条件を決める。
- [ ] 登録方法と実施者、利用開始条件、状態ごとに許可する操作を決める。
- [ ] 停止・退職・削除が所属、ロール、既存セッション、発行済みURL、予約に与える影響を決める。
- [ ] 復帰・再雇用時に同じユーザを復活させるか、新規登録するかを決める。

### 検討-002 テナントの開設・停止・廃止

関連：[所属](10_specs/20_rules/RULE-0001-テナント・組織への所属.yaml)、[テナント分離](10_specs/20_rules/RULE-0002-テナント分離の原則.yaml)、[アーキテクチャ](10_specs/20_rules/RULE-0006-アーキテクチャ基本方針.yaml)

- [ ] 停止中に許可する操作と、既存セッション・予約便・各種ジョブの扱いを決める。
- [ ] 廃止・再開の可否と、データ・ログの保管、廃止後の取得主体を決める。

- [ ] 循環・最大階層超過の検査と、管理範囲が変わるユーザへの影響を整理する。
- [ ] 所属ユーザ、子組織、グループからの参照、ロール、予約が残る場合の削除条件を決める。

- [ ] 強制ログアウトによる緊急対処と、管理者不在を防ぐ制約との関係を確認する。

### 検討-009 権限変更の猶予中の判定

- [ ] 猶予中の操作で参照するロール・権限定義・管理範囲の基準時点を決める。

- [ ] 権限変更が続いた場合の猶予期限と、利用停止・強制ログアウトなどとの優先関係を決める。
- [ ] 再ログイン要求が画面・API・処理中の操作に及ぼす扱いを決める。

### 検討-010 複数の管理経路を組み合わせた権限判定

関連：[操作権限](10_specs/20_rules/RULE-0005-管理者・担当者ごとの操作権限の違い.yaml)、[認可](10_specs/20_rules/RULE-0008-認可方式.yaml)のRITM-0057

- [ ] 操作の許可と対象範囲を同じ権限の根拠で満たす条件を決める。
- [ ] 営業部では編集可能、開発部では閲覧のみの場合に、開発部の編集をどう判定するか具体化する。
- [ ] 異動元・異動先に必要な権限を、組織ロールとグループロールの組み合わせで満たせるかを決める。
- [ ] 複数の根拠で許可される場合の監査記録と、重複警告の対象条件を具体化する。

### 検討-011 予約の一部失敗と業務上の整合性

関連：[変更予約](10_specs/20_rules/RULE-0010-変更の予約の考え方.yaml)のRITM-0083・0089・0092〜0098

- [ ] 一体として成功・失敗させる操作の単位を決める。
- [ ] 異動失敗後に所属ユーザが残る組織の削除など、先行処理の失敗が後続処理に与える影響を決める。
- [ ] 操作種別ごとの固定順序と同種操作内の順序、項目・操作の競合条件を具体化する。
- [ ] 予約後の即時変更、シミュレーション後の変更、本適用中のオンライン操作との競合を決める。
- [ ] 便開始時に固定する権限の範囲と、処理中に実行権限者が利用停止された場合の扱いを決める。
- [ ] 障害後の再開・二重適用防止と、締め切り後の取消・緊急対処の可否を決める。

- [ ] 利用開始後に変更できない設定と、変更前に整合性検査を必要とする設定を整理する。
- [ ] 設定同士の矛盾を検査する条件と、変更失敗時の扱いを決める。
- [ ] 設定変更の影響対象、履歴、通知、再ログイン要求の適用範囲をそろえる。

### 検討-019 通知の成立条件

関連：[通知方法](10_specs/20_rules/RULE-0015-ユーザ通知方法の方針.yaml)

- [ ] 通知対象イベントと、変更前・変更後の送信先の選択を決める。
- [ ] 予約登録時・適用時・部分失敗時の通知と、一括変更時の通知単位を決める。
- [ ] 初期設定・再設定・メール確認・MFA用メールの送信失敗時の対応を決める。
- [ ] 通知テンプレートの編集範囲、必須内容、言語別の未設定時の扱いを決める。
- [ ] お知らせの編集形式、掲載日時の境界、表示言語と管理権限を具体化する。

本人情報の変更通知を再送しない既存方針と、認証に必要なメールの失敗対応は区別します。

### 検討-020 一括操作・初期移行の要否

関連：[概要](10_specs/10_overview/overview.yaml)、[ログインID](10_specs/20_rules/RULE-0013-ユーザID（ログインID）方針.yaml)

- [ ] ユーザ・組織・ロールのCSV取込／出力、一括変更を提供するかを決める。
- [ ] 提供する場合の対象項目、実行権限、事前検査、部分成功、再取込時の扱いを決める。
- [ ] 既存システムからの移行範囲と、必須・一意制約を満たさないデータの扱いを決める。
- [ ] 移行したユーザの初回パスワード設定と、初回通知の運用を決める。

### 検討-021 利用側システムとの契約

関連：[アーキテクチャ](10_specs/20_rules/RULE-0006-アーキテクチャ基本方針.yaml)、[認証・セッション](10_specs/20_rules/RULE-0007-認証・セッション管理方式.yaml)

- [ ] 公開サービスとAPIの提供範囲、モジュール組み込みとマイクロサービスでの共通部分を決める。
- [ ] 利用者操作とサービス自身の操作の識別、テナント・ユーザ・認可情報の受け渡しを決める。
- [ ] セッション共有の前提、無効化・再ログイン要求を利用側へ反映する責務を決める。
- [ ] ユーザ・所属・権限の変更を利用側へ伝える必要性と、失敗・遅延時の扱いを決める。
- [ ] APIのエラー、互換性、バージョン更新とデータ構造更新の責務を決める。

### 検討-022 性能・障害・運用の成立条件

関連：[アーキテクチャ](10_specs/20_rules/RULE-0006-アーキテクチャ基本方針.yaml)、[変更予約](10_specs/20_rules/RULE-0010-変更の予約の考え方.yaml)、[ログ方針](10_specs/20_rules/RULE-0016-ログ方針.yaml)

- [ ] 想定テナント数・ユーザ数・同時利用数・予約件数と、一覧・検索・認可の応答時間を決める。
- [ ] 夜間処理の完了期限、処理が間に合わない場合の運用、テナント間の資源配分を決める。
- [ ] DB・Redis・メール・ログ保存先の障害時に、拒否・継続・再試行する操作を決める。
- [ ] 業務更新と監査記録、DBとファイルの保存結果が食い違った場合の扱いを決める。
- [ ] バックアップ・復旧範囲、許容する停止時間・データ損失、監視と運用者の対処を決める。
- [ ] パスワード・認証用秘密情報・通信の保護など、実装で満たす安全性の条件と責務を整理する。

### 検討-023 日時と同時更新の共通ルール

関連：[変更予約](10_specs/20_rules/RULE-0010-変更の予約の考え方.yaml)、[監査ログ](10_specs/20_rules/RULE-0009-監査ログと保管期間.yaml)、[ログ方針](10_specs/20_rules/RULE-0016-ログ方針.yaml)

- [ ] 基準タイムゾーン、日時の保存・表示、業務日と暦日の対応を決める。
- [ ] 「1か月」「1年」などの期間計算と、期限ちょうどの判定を決める。
- [ ] 管理者同士・本人と管理者・APIと画面の同時更新時の競合検出と利用者への案内を決める。
- [ ] 再送・二重クリックでの重複処理と、処理途中で権限・状態が変わった場合の確認時点を決める。

## 文書への展開

横断的な決定は `20_rules` に反映し、必要に応じて既存ルールを補足するか新しいトピックとして分けます。
登録・異動・退職・復旧などの流れは、文書形式を利用者と決めたうえで `40_business_flows` と `50_usecases` へ展開します。
画面・API・エンティティ定義や後続工程の文書は、検討TODOを理由に先回りして作成しません。
ワークフロー／承認フロー、外部認証基盤との連携など、既存の対象外方針を暗黙に変更しません。
