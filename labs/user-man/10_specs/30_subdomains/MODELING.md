# サブドメイン内のモデル定義と根拠参照

サブドメイン詳細の `concepts` と `operations` を原本として、業務概念からモデルを具体化します。
モデルと操作の所属サブドメインは原本の包含関係から導出します。
共通のID・参照方針は [共通記述規約](../WRITING.md)、操作・検証は [操作・検証ガイド](../../OPERATIONS.md) を参照してください。

## 概念からモデルへの具体化

| 項目 | 記述する内容 |
|---|---|
| `kind` | `concept`（概念）、`entity`（エンティティ）、`value_object`（値オブジェクト）、`relationship`（関連） |
| `id` | エンティティの場合の `ENTY-nnnn` |
| `name`・`description` | 名称と、このサブドメインでの意味 |
| `status` | 草案／確定 |
| `rule_refs` | 概念の意味の根拠 |
| `identity` | 同じ対象を識別する条件と、その根拠 |
| `attributes` | 主要属性の意味と根拠、属性ごとの `constraints` |
| `relationships` | 関連先の概念名・サブドメイン・多重度・根拠 |
| `constraints` | モデル全体が守る条件と根拠 |
| `transitions` | 状態遷移の前後・契機・根拠と、必要に応じた `conditions` |

種類の選択もモデル設計の判断です。独立して識別する必要がある対象をエンティティ候補とし、属性や関連を一律にエンティティ化しません。
値オブジェクトや関連は親の中で名前と項目位置により扱い、現段階では独立した文書IDを設けません。
概念の意味が異なる場合、同じ名称でも別のモデルとして記述します。

エンティティのIDは `concepts` の要素で定義し、その要素が名称と内容の原本になります。
エンティティ一覧はビューで導出し、名称・概要を別の一覧へ重複して入力しません。
将来個別文書へ分離する場合は、定義IDを維持して原本を移し、サブドメインから参照します。

関連の `multiplicity` は、当該モデル1件から見た関連先の件数です。逆方向を暗黙に同じ件数としません。
関連先が未採番の場合は `target_name` と `target_subdomain` を記録し、定義済みなら `target_model` も参照します。
未採番の概念を参照するためだけに、内容のないエンティティを作りません。

主要属性は業務上の意味と成立条件を記述します。DBカラム・物理型・索引・API入出力は後続設計で扱います。
状態遷移は具体化した範囲を記述し、記載のない遷移を「禁止」と解釈しません。未解決の条件と網羅範囲は [TODO](../../TODO.md) に残します。
集約の境界は操作前後の整合性と失敗時の扱いを検証して決め、同じ文書に書かれていることだけで一つの集約としません。

## 根拠を付ける粒度

各記述の `rule_refs` に、根拠となるRITMを直接参照します。
属性に複数の条件がある場合は、条件を分けてそれぞれに参照を付けます。

```yaml
attributes:
  - name: ユーザコード
    description: テナント側が採番する業務上の識別子。
    rule_refs: [RITM-0115]
    constraints:
      - name: 必須・一意性
        description: ログインIDの方式にかかわらず必須かつテナント内で一意とする。
        rule_refs: [RITM-0116]
      - name: 文字と長さ
        description: 3桁以上16桁以下の半角英数字とする。
        rule_refs: [RITM-0122]
```

この例では「必須・一意性」の根拠はRITM-0116であり、親属性のRITM-0115で代用しません。
モデルの識別条件・関連・状態遷移にも同じ粒度を適用します。一つの判断に複数のルールが必要なら、その項目に併記します。
RITMの本文は複製せず、対象のモデルに適用した条件を記述します。根拠がない業務判断を草案へ混ぜず、検討TODOに残します。

サブドメイン直下の `rule_refs` は、責務・境界等の全体説明の根拠です。
子項目の参照を集めた一覧として維持しません。同じルールを異なる判断に用いる場合、それぞれの判断に参照を記述します。
関係名 `grounded-in-rule` と参照元の項目位置により、ルール側から使用箇所を辿れます。

## 操作とモデルの対応

操作には一意のDOPR型 `id` と `rule_refs` を持たせ、`target_models` で定義済みのエンティティを参照できます。
具体化する条件は `conditions`、操作の結果は `effects` に分け、各項目に名称・内容・根拠を記述します。
業務活動の `operations` から操作を参照し、詳細ユースケースの `operations` で具体化する操作を指定します。
利用者の目的から複数活動を一つのユースケースにまとめられ、同じ操作を複数の業務フロー・ユースケースから利用できます。
処理の区切り・失敗時の扱い・他領域の操作との成立単位はユースケースで具体化します。

## YDEでの扱い

スキーマは [subdomain-detail.yaml](../../.yde/schemas/subdomain-detail.yaml)、
根拠付き記述の共通型は [domain-model-types.yaml](../../.yde/schemas/domain-model-types.yaml) で定義します。
エンティティは要素の `entity: {type: domain-entity, defines: true}` と `id` により索引へ登録されます。
IDを持たない概念・属性・制約は独立した業務エンティティにならず、参照元の項目位置で区別します。

- [業務エンティティ一覧](../../.yde/views/domain-entity-catalog.yaml)：名称・意味・所属・識別・属性・関連を一覧します。
- [サブドメインの操作と利用箇所](../../.yde/views/domain-operation-catalog.yaml)：全操作の所属と活動・ユースケースからの逆参照を一覧します。
- [個別ルールのモデル・操作への展開](../../.yde/views/domain-rule-usage.yaml)：RITMごとに参照元を表示します。

ビューのバックリンク列は参照元の要素を示します。細かな属性・制約の位置はエンティティページの関係パネルや参照検索で確認します。
参照のない行は、業務上不要であることや仕様の完成を意味しません。
