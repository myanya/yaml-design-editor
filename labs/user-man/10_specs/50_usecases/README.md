# 詳細ユースケース

業務フローを、実行主体とシステムの操作・応答・成立条件へ具体化します。
[一覧](0000-usecase-lists.yaml)にID・タイトル・概要を置き、同じIDの個別文書へ内容を記述します。
最初の対象は、ユーザ登録から利用開始までのUSCS-0001〜0005です。形式・内容は草案として育てます。

## 記述する項目

| 項目 | 内容 |
|---|---|
| `id`・`status` | USCSのIDと草案／確定 |
| `context` | 主に管理する一つのコンテキスト |
| `purpose` | 目的と、このユースケースで扱う範囲 |
| `actors` | 操作者・システム等の実行主体と役割 |
| `models` | 使用する概念の名前・所属・用途と、定義済みならエンティティへの参照 |
| `triggers` | 開始する契機 |
| `preconditions` | 開始に必要な条件 |
| `basic_flow` | 基本経路の手順と実施主体、条件・結果・連携先 |
| `alternatives` | 分岐条件、代替・例外の扱いとその結果 |
| `postconditions` | 成功時の事後条件を経路ごとに記述 |
| `guarantees` | 失敗・中断を含めて守る条件 |

役割・モデルの用途・開始契機・条件・各手順・結果の記述は、名称・内容・`rule_refs` を持つ項目とします。
一つの手順に複数の判断がある場合は `conditions` と `results` に分け、各項目に根拠のRITMを参照します。
代替・例外の `condition` と `outcomes` も個別の根拠を持ちます。
スキーマは [usecase-list.yaml](../../.yde/schemas/usecase-list.yaml) と [usecase-detail.yaml](../../.yde/schemas/usecase-detail.yaml) です。

## 業務フロー・モデル・境界との関係

業務フローの手順・分岐の `usecases` から、対応するUSCSへ参照します。
一つの手順から複数の詳細を参照でき、同じ詳細を複数の手順で利用できます。USCS側に同じ対応を重複入力せず、逆参照で表示します。
対応の関係名は `elaborates-with` です。

各USCSの `context` は一つですが、他コンテキストとのやり取りを手順に含められます。
相手側にも詳細ユースケースがある場合は、手順の `invokes` から参照します。
この参照は同期API、イベント、同一DBトランザクションなどの実装方式を指定しません。
利用開始の状態変更、案内メールの実送信、本人の設定完了は、それぞれの成立条件を持つ別の操作として扱います。

モデルの原本はサブドメイン内に置き、USCSにはこの操作でどう利用するかを記述します。
`models.entity` は定義済みのENTYを参照し、未採番の概念は名前と所属コンテキストで原本と対応付けます。
文書ID・実行時の内部ID・ロールの識別名を混同しません。

## 草案の範囲と未決事項

基本経路の手順だけを記述した時点で、全例外や再試行を定義済みとは扱いません。
未回答の業務判断を一般的な実装方法で補わず、未解決の条件と次の確認事項を [TODO](../../TODO.md) に記録します。
利用者向けのエラー文言、HTTPステータス、入力画面、永続化方式は対応する後続の設計で扱います。

例えば登録と指定ロール付与は、RITM-0209により一体として成立させます。
この約束を満たす方式は設計で検証し、コンテキストを統合する根拠や、ユーザとロールを同じ集約にする根拠にはしません。
初期設定用URLの発行・期限の起算はRITM-0210で定義済みですが、送信失敗時の再送とURLの再発行の関係は別に具体化します。

## 確認方法

[詳細ユースケース一覧ビュー](../../.yde/views/usecase-catalog.yaml)から、所属コンテキスト・使用モデル・対応する業務フローを確認できます。
ルール側からは[参照元一覧](../../.yde/views/domain-rule-usage.yaml)と参照検索で、条件・結果の項目位置へ辿れます。
具体的な手順は [操作・検証ガイド](../../OPERATIONS.md) に記載します。
