# 仕様書

ユーザ管理システムの仕様書を、このディレクトリにYAMLで作成します。
本書は、仕様書の構成・命名・ID体系・未決事項を管理します。
会社の設計体系と利用者の説明をもとに、各文書の項目と内容を具体化します。

仕様の原本は `10_specs/` のYAML文書に置きます。
スキーマはワークスペースのルートの `.yde/schemas/` に置き、フォーム編集と検証に使います。
スキーマがない文書も汎用ツリーとソースで編集できます。

## 仕様書の構成

仕様書は `10_specs/` 配下で管理します。各ディレクトリとYAML文書は内容の策定に合わせて作成します。
概要ユースケース（業務フロー）と詳細ユースケースは、別のディレクトリで管理します。

```text
10_specs/
├── 10_overview/       # システムの概要
├── 20_rules/          # ビジネス・システムのルール、アーキテクチャ方針など
├── 30_subdomains/     # 業務の問題領域と分類
├── 35_bounded_contexts/ # 用語・モデルの境界
├── 37_context_maps/   # コンテキスト間の連携
├── 40_business_flows/ # 概要ユースケース（業務フロー）
└── 50_usecases/       # 詳細ユースケース
```

画面定義・API定義・エンティティ定義は、この後に仕様を詳細化する対象です。
これらの番号帯とディレクトリ構成は未決定です。

### 概要

`10_overview/` では、システムの根幹となる次の内容を管理します。

- システム化の目的
- システムの概要
- システムのスコープ
- スコープ外

概要は種類ごとに1ファイルとし、一覧と詳細な個別ドキュメントには分けません。
現在は [overview.yaml](10_overview/overview.yaml) に大きな概要を記述します。追加する文書の種類と分割構成は未決定です。
対応するスキーマは [overview.yaml](../.yde/schemas/overview.yaml) です。
システム名と概要を必須とし、目的などの他の項目は具体化に合わせて追記できます。
提供機能一覧は、機能名と複数行の機能説明の組で記述します。
主要エンティティも、名称と複数行の説明の組で、概要段階での役割を記述します。
重要事項は見出しと内容の組を追加でき、細かな権限ルールは概要から段階的に詳細化します。

### ルール

`20_rules/` では、ビジネスルール・システムルール・アーキテクチャ方針などを管理します。
共通的な決定事項に加え、雑多な情報や考えを整理する場所としても使います。ルール自体はサブドメインに所属させません。
1トピックを1文書にまとめ、各文書に独立した `RULE-nnnn` のIDを付与します。
例えば、許容する組織構造や権限の種類をそれぞれ1トピックとして扱います。
本文は「見出し＋概要＋自由記述」を1組とし、全ての組に独立した `RITM-nnnn` のIDを必ず付与します。
既存の項目の分け方を保ち、説明や例を含めて機械的に採番します。参照しながら、項目の粒度に問題がないかを確認します。
決定理由は文書全体にまとめず、本文の各組に対応付けて記載します。

#### 一覧と詳細の分担

一覧にはID・タイトル・概要を持たせ、詳細文書には同じIDと、それ以外のドキュメントの中身を持たせます。
ID以外の内容は重複させず、タイトルと文書全体の概要は一覧だけで管理します。
本文の各組に記載する見出し・概要は、その部分の内容を説明するものです。

個別ルールの共通項目として、ルール区分、分類・タグ、ステータス、作成日、更新日を持たせます。
他ルールとの関係は、文書単位の関係と個別ルール単位の関係を区別して具体化します。
ルール区分はビジネス／システムに限定せず、スキーマ側で管理します。
本文と決定理由の入力形式は「ルールのYAML表現」に記載します。
共通項目は本文項目ごとに保持します。ルール区分・分類・ステータスの選択肢は、詳細文書のスキーマで管理します。

#### ルールのYAML表現

一覧は [0000-rule-lists.yaml](20_rules/0000-rule-lists.yaml) の `rules` 配列とし、各要素に `id`・`title`・`summary` を持たせます。
詳細文書はルートの `id` で対応付け、`sections` 配列に本文を記述します。
本文の各組は `id`（個別ルールID）・`title`（見出し）・`summary`（概要）・`content`（自由記述）・`decision_reason`（決定理由）で表します。
自由記述内の段落や箇条書きに追加のIDは付けず、`sections` の各要素を採番単位とします。
決定理由は対応する本文項目内だけに置き、ルートには置きません。

本文項目には次の管理情報を持たせます。

| キー | 項目 | 入力方針 |
|---|---|---|
| `rule_type` | ルール区分 | 性質を示す必須の単一選択 |
| `category` | 分類 | 主題を示す必須の単一選択 |
| `tags` | タグ | 横断検索用の補足キーワードを複数の自由入力で指定（空でも可） |
| `status` | ステータス | 本文の合意状態を示す必須の単一選択 |

区分・分類は文書単位で固定せず、個別ルールの内容に合わせます。タグは既存の表記を優先し、同じ意味の表記揺れを避けます。
回答済みの既存項目のステータスは「確定」とし、新規追加時の初期値は「草案」とします。
「確定」は本文に記した方針への合意を表し、詳細設計や実装の完了を意味しません。

`created_on`（作成日）と `updated_on`（更新日）は必須の日付項目とし、`YYYY-MM-DD` で記録します。
作成日は項目を追加したときに自動で入り、以後は保持します。更新日は、項目の内容が変わって保存されるたびに自動で当日の日付になります（スキーマの `auto: created` / `auto: updated`）。
外部エージェントなどがファイルを直接修正するときは、自動更新を通らないため、修正した個別ルールの更新日を当日に変更し、作成日は維持します。
あわせて `revision`（版）を持ち、内容が変わって保存されるたびに自動で +1 されます（画面では `rev-001` のように表示）。手で直すこともできますが、内容を変えて保存すると自動の値が優先されます。

対応するスキーマは [rule-list.yaml](../.yde/schemas/rule-list.yaml) と [rule-detail.yaml](../.yde/schemas/rule-detail.yaml) です。
一覧を定義出現、詳細文書を同じルールの詳細化出現として扱います。
個別ルールは `rule-item` の定義出現として索引に登録し、文書単位の `rule` と区別して参照できます。
現在のスキーマでは文書ID・個別ルールID・ルール区分・分類・ステータス・作成日・更新日・一覧のタイトルと概要・本文を必須とします。タグと決定理由は任意入力です。
導出元は `derived_from` にIDの配列で記録します。関係の定義は [rule-relations.yaml](../.yde/schemas/rule-relations.yaml) に置きます。
親子関係と個別ルール単位の関係のスキーマは、入力形式の具体化に合わせて追加します。

#### ルール間の関係

親子関係は、親ルールを分割・詳細化したものを子ルールとする関係です。
子は1つの親にのみ所属し、子側に親への参照を記録します。親側に子の一覧は持たせず、ツールでつながりを表示します。
子にも独立したIDを付与し、IDに階層は含めません。階層の深さによってIDが長くなることを避けます。

導出関係は、あるルールと別の要素を組み合わせた結果、新しいルールが導かれる関係です。
導出先のルールに複数の導出元への参照を記録できるようにします。逆方向の参照は重複して記録せず、ツールで表示します。
親子関係と導出関係は別の関係として管理します。

#### 具体化する順序

次の順にトピックを具体化します。この順序はルールIDの採番を意味しません。

1. テナント・組織への所属
2. 組織ツリーとグループの管理範囲
3. 組織・グループにおける管理対象ユーザ
4. 管理者・担当者ごとの操作権限の違い
5. アーキテクチャ基本方針
6. 認証・セッション管理方式
7. 認可方式
8. 監査ログと保管期間
9. 変更の予約の考え方
10. 画面デザイン方針
11. ID体系
12. ユーザID（ログインID）方針
13. パスワードに関する方針
14. ユーザ通知方法の方針
15. ログ方針

### サブドメイン

`30_subdomains/` では、業務の問題領域と、その戦略的な分類を定義します。
各サブドメインでは、扱うエンティティと可能な操作などの概要を定義し、その後の段階的詳細化に備えます。

詳細ユースケース・モデルの主な所属先は一つのコンテキストとし、サブドメインには業務上の対応を持たせます。
共通ルールは所属の対象外です。複数の境界を横断する業務フローは、詳細ユースケースと区別します。
所属を必須にするタイミングと、システム全体の概要における扱いは今後定めます。

#### 草案の形式

[サブドメイン一覧](30_subdomains/0000-subdomain-lists.yaml)と、同じIDの個別文書で管理します。
一覧にはID・タイトル・概要を置き、個別文書にタイトルと概要を重複させません。
権限管理・ユーザ管理・テナント管理・組織・グループ管理・ユーザ認証を草案として具体化しており、全体のサブドメイン分割を確定したものではありません。
文書項目も草案として具体例に合わせて見直し、未解決の論点は本文の質問欄にせず [TODO](../TODO.md) に置きます。

| 個別文書の項目 | 内容 |
|---|---|
| `id`・`status` | サブドメインIDと草案／確定の区別 |
| `classification`・`classification_reason` | 中核／支援／汎用の分類と、判断した事業・製品の立場および根拠。未検討時は未設定 |
| `responsibility` | 担当する責務 |
| `concepts` | 扱う概念の名称と説明 |
| `operations` | 操作の名称と概要 |
| `boundary` | 他の機能との分担 |
| `related_subdomains` | 関連するサブドメインへの参照 |
| `rule_refs` | 根拠とする個別ルールへの参照 |

概念と操作の一覧は概要段階の整理であり、エンティティ定義や詳細ユースケースの完成を意味しません。
`related_subdomains` は関連を表し、実装の依存方向を確定するものではありません。
スキーマは [subdomain-list.yaml](../.yde/schemas/subdomain-list.yaml) と [subdomain-detail.yaml](../.yde/schemas/subdomain-detail.yaml) です。

#### サブドメインの分類

分類は詳細文書にだけ保持し、一覧文書には重複させません。未設定は検討状態であり、第4の分類ではありません。

| 値 | 日本語ラベル | 判断の観点 |
|---|---|---|
| `core` | 中核サブドメイン | 事業・製品の価値や差別化の中心となる領域 |
| `supporting` | 支援サブドメイン | 中核を支えるために必要な、事業・製品固有の領域 |
| `generic` | 汎用サブドメイン | 広く共通する課題で、標準的な知識・解決方法を適用できる領域 |

重要度・開発規模・自作か外部製品かだけでは分類しません。認証のように重要な領域も、戦略上は汎用となり得ます。
参考：[SAPのDDD概念整理](https://github.com/SAP/curated-resources-for-domain-driven-design/blob/main/blog/0002-core-concepts.md)。
本ユーザ管理機能を提供する立場で、権限管理・ユーザ管理を中核、テナント管理・組織・グループ管理を支援、ユーザ認証を汎用として記録します。
組織・グループ管理は各機能の権限範囲を支える領域です。他機能の追加時にも利用しますが、権限範囲以外の用途への拡張は想定しません（RITM-0208）。
複数機能で共通利用することや、今後の拡張量だけで分類は決まりません。各文書に分類の根拠を記録します。
現時点では追加分類を要する対象はありません。技術基盤・外部システムなどは別の軸で管理し、三分類へ混在させません。

[サブドメイン分類一覧](../.yde/views/subdomain-catalog.yaml)は、一覧の名称と詳細の分類・根拠・状態・責務を同じIDで結合します。
台帳の「ビュー」から開き、分類セルを編集できます。分類の根拠は詳細文書で記入します。

### 境界づけられたコンテキスト

検討-024で文書構成・対応関係・ビューの方針を採用しました。個別の境界と連携内容は草案として具体化します。
サブドメインは業務の問題領域を分け、境界づけられたコンテキスト（bounded context）は、用語とモデルの意味を一貫させる範囲を定めます。
同じ「ユーザ」も、ユーザ管理では利用状態を持つ管理対象、認証では認証情報の主体、権限管理ではロールの付与先として捉えられます。
参考：[FowlerのBounded Context](https://www.martinfowler.com/bliki/BoundedContext.html)、[EvansのDDD Reference](https://www.domainlanguage.com/ddd/reference/)。

#### 文書構成

| 配置 | ID | 記述する内容 |
|---|---|---|
| `35_bounded_contexts/` | `BCTX-nnnn` | モデル・用語・責務の境界と、担当するサブドメイン |
| `37_context_maps/` | `CMAP-nnnn` | コンテキスト間の関係、情報の提供・利用、翻訳・連携の方針 |

各種類で一覧にID・タイトル・概要を置き、詳細は同じIDの文書に記述する既存の分担を踏襲します。
コンテキスト詳細の項目は、状態、目的、責務・対象外、主要概念・用語、情報の管理主体、公開する操作・情報、対応サブドメイン、根拠のルールです。
情報の管理主体は、例えば「利用状態はユーザ管理、認証情報はユーザ認証」のように、更新の責任と他の境界での参照を区別します。
具体的なAPIのパス・クラス・テーブル・トランザクション構成は後続設計へ渡し、仕様段階では約束する振る舞いまでを記述します。

最初の草案は、権限管理、ユーザ管理、テナント管理、組織・グループ管理、ユーザ認証です。
現在のサブドメイン名との対応は出発点であり、1対1を強制しません。特にユーザ管理と認証は、用語・状態遷移・変更責任を確認し、分離するか一つの境界内にまとめるかを判断します。
機能ID、組織・グループによる権限範囲、テナントのデータ分離、モジュール・サービスの配置とはそれぞれ異なる軸です。
境界を分けるだけではマイクロサービス化を決めません。利用側システムは外部境界として扱います。今回の草案は本機能内を対象とし、外部の具体的な境界・連携の追加は検討-021・024で扱います。

#### 二種類の関係と原本の置き方

サブドメインとコンテキストの対応は、コンテキスト詳細の `subdomains` にだけ記録し、サブドメイン側は逆参照で表示します。
一つの対応に担当範囲を記録できる属性付き参照を使います。次は書式例です。

```yaml
subdomains:
  - to: SDOM-0002
    responsibility: ユーザ情報と利用状態の管理
```

この参照に `covers-subdomain`（担当する業務領域）という関係を定義し、コンテキストからサブドメインへ辿れるようにします。
複数の対応を許し、分割時は各コンテキストの担当部分、統合時は複数領域をまとめる理由を記述します。対応の存在だけでは、その領域の全業務の網羅を意味しません。
単に別領域の情報を利用することは担当の対応に含めず、コンテキスト間の連携で記述します。

コンテキスト同士の関係はコンテキストマップを原本とし、両端の参照、関係の目的、提供・利用する情報、変更責任、モデルの翻訳、同期・遅延・失敗時の約束を持たせます。
DDDの関係パターンは、チーム間の協調関係と技術的な連携方式を分けます。例えばCustomer/Supplier、公開ホストサービス、公開言語、腐敗防止層は併用し得るため、単一の排他的な分類にしません。
上流・下流はモデル変更の影響や契約の主導関係で定め、API呼び出しやデータ転送の向きとは別に記録します。対等な協調関係も表せるようにします。
各CMAP文書は一つの境界間の連携を扱い、その集合をマップとして表示します。境界A・Bは情報の方向や上流下流を表しません。
草案ではユーザ管理と権限管理、組織・グループ管理と権限管理、ユーザ管理と認証の連携を記録しています。全連携の網羅を意味しません。
通信方式・チーム間の関係などの未決定項目は省略し、検討事項をTODOで管理します。

一覧は [コンテキスト](35_bounded_contexts/0000-bounded-context-lists.yaml)と[連携](37_context_maps/0000-context-map-lists.yaml)です。
スキーマは `.yde/schemas/` の `bounded-context-list.yaml`・`bounded-context-detail.yaml`、`context-map-list.yaml`・`context-map-detail.yaml` です。
関係は [domain-relations.yaml](../.yde/schemas/domain-relations.yaml) に定義します。CMAPからBCTXへの参照を `connects-context` として扱います。

#### 関係を一望するビュー

| ビュー | 行・列と確認できる内容 | 本ツールでの実現方法 |
|---|---|---|
| 対応一覧 | サブドメイン、分類、対応するコンテキスト、文書の状態 | サブドメインを全件並べ、コンテキストの逆参照列を加える。未対応の行も残す |
| 対応マトリクス | 行＝サブドメイン、列＝コンテキスト、セル＝対応件数 | グリッドの動的列 `each` と参照検索・件数。分類列を併置し、0は対応なし、1以上は対応あり |
| コンテキストマップ | 境界同士の関係、提供・利用、連携上の約束 | 関係の一覧ビューを原本から生成し、グラフレンズから関係先へ移動する |

対応マトリクスは全サブドメイン・全コンテキストを軸に取り、未対応も見落とさないようにします。対応セルから根拠の文書を辿り、担当範囲を確認します。
関係パターンや対応を図と文書へ二重入力せず、参照と属性から表示を導出します。
既存のグラフレンズは型・関係で絞った参照グラフを表示できますが、境界の囲みや任意のエッジ属性の常時表示まで保証しません。
マップを関係行として定義する場合、現在のグラフでは関係要素を経由する表示になり得ます。二つの境界を直接結ぶ専用図の必要性は、文書とビューの試作後に判断します。
実装時は [ビュー](../../../docs/manual/views.md) の既存のQuery・値の式・集計で構成し、新しい評価器は追加しません。

#### 所属と工程の管理単位

詳細ユースケース・モデルの主な所属先はコンテキストとし、サブドメインとは業務上の対応を持たせます。業務フローは複数の境界を横断できます。
設計以下の工程もコンテキストを主な管理単位とします。物理的な配置やデプロイ単位は後続設計で定めます。

### ユースケース

ユースケースには、次の2つの粒度があります。

| 種類 | 役割 | サブドメインとの関係 |
|---|---|---|
| 概要ユースケース（業務フロー） | `40_business_flows/` で業務全体の流れを記述 | 複数のサブドメインをまたぐ |
| 詳細ユースケース | `50_usecases/` でユーザとシステムとのインタラクションを具体化 | 主な所属先は1つのコンテキスト。サブドメインとは業務上の対応を持つ |

一般的なユースケース定義書の内容を記述し、粒度に応じてインタラクションを具体化します。
画面・API・エンティティの仕様を詳細化するための基礎とします。
業務フローは以下の草案形式で具体化します。詳細ユースケースの項目と、概要から詳細への対応方法は今後定めます。

業務全体の流れとコンテキスト内の振る舞いを分けると、それぞれの記載粒度と管理範囲を明確にできます。

#### 業務フローの草案形式

[業務フロー一覧](40_business_flows/0000-business-flow-lists.yaml)にID・タイトル・概要を置き、同じIDの個別文書に内容を記述します。
最初の具体例は、[ユーザ登録から利用開始](40_business_flows/BZFL-0001-ユーザ登録から利用開始.yaml)です。
形式と内容は草案として確認し、未解決の業務仕様は [TODO](../TODO.md) で管理します。

| 個別文書の項目 | 内容 |
|---|---|
| `id`・`status` | 業務フローIDと草案／確定の区別 |
| `purpose` | 対象とする業務と範囲 |
| `actors` | 関与する主体と役割 |
| `preconditions` | 開始に必要な条件 |
| `basic_flow` | 手順の配列。見出し、実行主体、内容、任意の状態変化、関与するサブドメイン、根拠の個別ルール |
| `variations` | 条件による分岐・例外と根拠の個別ルール |
| `outcome` | 業務の到達点 |
| `rule_refs` | 業務フロー全体の根拠となる個別ルールへの参照 |

手順内の `subdomains` は関与するサブドメインを、`rule_refs` は根拠を表し、業務フロー自体の所属は指定しません。
手順内の `contexts` は関与するコンテキストを表します。担当領域全体の対応から自動推測せず、その手順で関与する境界を指定します。
手順の配列順は業務の流れを表します。全手順を同期処理や単一トランザクションで実行する指定ではありません。
スキーマは [business-flow-list.yaml](../.yde/schemas/business-flow-list.yaml) と [business-flow-detail.yaml](../.yde/schemas/business-flow-detail.yaml) です。

## 文書の配置と命名

概要を除く各定義は、一覧と個別ドキュメントの構成を基本とします。

| 種類 | ファイル名 | 配置 |
|---|---|---|
| 一覧 | `0000-xxx-lists.yaml` | 定義の種類ごとのディレクトリ内 |
| 個別ドキュメント | `<ID>-<名称>.yaml` | 一覧と同じディレクトリ内 |

`xxx` は定義の種類を表す部分です。ルール一覧は `0000-rule-lists.yaml`、サブドメイン一覧の草案は `0000-subdomain-lists.yaml` とします。
業務フロー一覧の草案は `0000-business-flow-lists.yaml` とします。
コンテキスト一覧は `0000-bounded-context-lists.yaml`、連携一覧は `0000-context-map-lists.yaml` とします。
他の一覧の具体的な綴りは今後定めます。
例えばルールの個別ドキュメントは `20_rules/RULE-0001-<名称>.yaml` の形です（名称はプレースホルダー）。
個別ドキュメント用の別ディレクトリは設けません。
ルールの項目分担は「一覧と詳細の分担」、サブドメインと業務フローの草案はそれぞれの草案形式に従います。
その他の定義の項目分担と、同一IDによる対応付けの具体的なスキーマは今後定めます。
概要は例外として、`10_overview/` 内に種類ごとのファイルを置きます（現在は `overview.yaml`）。

## ID体系

| 定義の種類 | ID形式 |
|---|---|
| ルール | `RULE-nnnn` |
| 個別ルール（本文項目） | `RITM-nnnn` |
| サブドメイン | `SDOM-nnnn` |
| 境界づけられたコンテキスト | `BCTX-nnnn` |
| コンテキスト間の連携 | `CMAP-nnnn` |
| 概要ユースケース（業務フロー） | `BZFL-nnnn` |
| 詳細ユースケース | `USCS-nnnn` |
| 画面定義 | `SCRN-nnnn` |
| API定義 | `APID-nnnn` |
| エンティティ定義 | `ENTY-nnnn` |

`nnnn` は4桁の数字です。概要を含め、上表にない定義のID体系は未決定です。
ルールは `RULE-0001` から作成順に採番し、内容の順序と番号をそろえるために採番を止めません。
番号順の整備は、後でツールのリファクタリング機能を用いて行います。
個別ルールは文書をまたいで一意に採番し、文書IDや親子関係を番号に含めません。
初回は文書ID順・本文の記載順で `RITM-0001` から採番します。通常の並べ替えや文書間の移動ではIDを維持します。
サブドメインの草案は `SDOM-0001` から採番します。
業務フローの草案は `BZFL-0001` から採番します。
コンテキストと連携は、それぞれ `BCTX-0001`・`CMAP-0001` から採番します。
その他の定義の採番開始値、欠番・廃止した番号の扱い、名称変更時のファイル名の扱いは今後定めます。

## コンテキストと対応ビューの試し方

1. 台帳の「ビュー」で「サブドメイン分類一覧」を開き、分類・根拠と担当するコンテキストを確認します。
2. 「サブドメインとコンテキストの対応」で、全領域と全境界の対応件数を確認します。0は未対応、1以上は対応ありです。個別の担当範囲は分類一覧の逆参照から確認します。
3. 「コンテキスト一覧」で情報の管理責任と関与する連携を確認し、「コンテキスト間の連携一覧」で両端と受け渡す情報を確認します。
4. コンテキストのエンティティページからグラフレンズへ移動し、「担当する業務領域」「連携の当事者」の関係を辿ります。
5. BZFL-0001の各手順で、業務上の領域と、処理に関与するモデルの境界を区別できることを確認します。

## 業務フロー草案の試し方

1. YDEで `10_specs/40_business_flows/0000-business-flow-lists.yaml` を開き、登録から利用開始までの詳細へ移動します。
2. 基本フローで、実行主体・状態変化・サブドメイン・根拠のルールを順に確認します。
3. 登録時のロール指定が任意であり、登録後にも設定できることを確認します。
4. 「初期設定中」への遷移が案内の契機であり、予約バッチを優先して実際のメール送信を遅らせられることを確認します。
5. 参照先のサブドメインとルールをたどり、本人の初期設定や未完了からの再開について、根拠と業務手順が対応していることを確認します。

## サブドメイン草案の試し方

1. YDEで `10_specs/30_subdomains/0000-subdomain-lists.yaml` を開き、各サブドメインの詳細へ移動します。
2. 詳細が「草案」であることと、責務・概念・操作・他の機能との分担が読み分けられることを確認します。
3. 「根拠の個別ルール」からルール本文を参照し、ロールの定義・付与と、ユーザ自体の登録・利用状態の管理が区別できるかを確認します。
4. テナント管理では、利用側が開設処理を呼ぶ経路と、本機能から利用側コンポーネントを呼ぶ経路の責務が区別できるかを確認します。
5. 組織・グループ管理と権限管理の草案で、実行可能な操作を表す権限と、組織・グループの定義による実行範囲の関係を確認します。
6. テナント全域管理では組織権限をチェックしない実装も許容することと、システム管理者用の組織・グループが不要であることを確認します。
