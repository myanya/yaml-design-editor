# 業務フロー

業務フローは、業務の目的に向けて、誰が何を行い、どの結果を次へ引き渡すかを記述します。
利用者の判断・システムを使う活動・システムの自動処理を含めて、業務の開始から到達点までを扱います。

| 種類 | 役割 | サブドメインとの関係 |
|---|---|---|
| 業務フロー | `40_business_flows/` で主体の活動・判断・引き渡しを記述 | 必要に応じて複数のサブドメインをまたぐ |
| 詳細ユースケース | `50_usecases/` で主体がシステムを利用して目的を達成するための操作・応答・成立条件を具体化 | 主に管理する1つのサブドメインを指定し、他の境界との連携も含める |

業務フローは以下の草案形式で具体化します。詳細ユースケースの項目は [作成ガイド](../50_usecases/README.md) に従います。

## 作成順序と切り出し

1. 業務フローで目的・開始条件・関与者・活動・分岐・到達点を先に整理します。
2. 各活動のうち、システムを利用する部分と、業務上の判断や運用を区別します。
3. サブドメインのモデル・操作と照合し、各活動が利用する操作をDOPRで参照します。不足や粒度の違いはサブドメイン側と往復して整理します。
4. 主体の目的と結果を単位として詳細ユースケースを切り出し、業務フローから参照します。
5. 詳細ユースケースの条件・結果をモデルと操作に照合し、判明した不足を業務フロー・ルールへ戻します。

一つの活動を必ず一つのUSCSにするわけではありません。関連する活動を一つにまとめる場合や、同じUSCSを複数の活動から使う場合もあります。
「停止の種類を判断する」は業務上の活動であり、判断するだけで独立したシステム機能や承認機能を追加しません。
「停止を依頼する」からシステムが状態を変更して結果を返すまでを、一つのユースケースの候補として検討できます。
入力検査や状態反映などの内部処理は、まず対応するユースケースの手順として扱い、サブドメインの境界だけを理由に別USCSへ分割しません。
自動処理も業務フローに記述しますが、独立したUSCSとするかは、その開始契機・目的・結果から判断します。

業務フローを先に作る段階では `usecases` を省略できます。新しいUSCSは、元となる活動と目的・範囲を整理した後に作成します。

## 業務フローの草案形式

[業務フロー一覧](0000-business-flow-lists.yaml)にID・タイトル・概要を置き、同じIDの個別文書に内容を記述します。
最初の具体例は、[ユーザ登録から利用開始](BZFL-0001-ユーザ登録から利用開始.yaml)です。
[ユーザの停止と再開](BZFL-0002-ユーザの停止と再開.yaml)は、業務フローを先に記述し、USCSの切り出し前の状態を示します。
形式と内容は草案として確認し、未解決の業務仕様は [TODO](../../TODO.md) で管理します。

| 個別文書の項目 | 内容 |
|---|---|
| `id`・`status` | 業務フローIDと草案／確定の区別 |
| `purpose` | 対象とする業務と範囲 |
| `actors` | 主体ID・名称・役割 |
| `preconditions` | 開始に必要な条件 |
| `activities` | 主活動のID・区分・見出し・実施主体・内容・状態変化・関与する領域・利用操作・根拠・対応USCS |
| `supporting_activities` | 必須の順序に入らない任意活動と実施可能な状況 |
| `transitions` | 遷移ID・主活動へのfrom/to参照・進行条件と根拠 |
| `variations` | まだ活動・遷移へ展開していない予約・代替・例外の説明と根拠・対応USCS |
| `outcome` | 業務の到達点 |
| `rule_refs` | 業務フロー全体の根拠となる個別ルールへの参照 |

手順内の `subdomains` は関与するサブドメインを、`rule_refs` は根拠を表し、業務フロー自体の所属は指定しません。
新形式では進行順序をtransitionsで表します。活動の配列順から辺を補いません。同期処理・自動実行・単一トランザクションの指定でもありません。
手順・分岐の `usecases` は、その内容を具体化する詳細ユースケースを参照します。詳細側から見た対応は逆参照で表示します。
スキーマは [一覧](../../.yde/schemas/business-flow-list.yaml)・[詳細](../../.yde/schemas/business-flow-detail.yaml)・[主体／活動／遷移の型](../../.yde/schemas/business-flow-types.yaml)です。

## 活動と遷移の記述

- 主活動のkindはaction（活動）・decision（判断）・outcome（到達点）・handoff（引渡し）を使います。
- 主活動・任意活動のactorは、同じ文書のactorsで定義したBATRへの参照です。実在するユーザやロールのIDではありません。
- 遷移のfrom/toは、同じ文書のactivities内のBACTを指定します。任意活動を主経路の遷移へ混入させないよう検証します。
- conditionは、その遷移へ進む条件を記述します。適用処理から先へ進む辺では、適用が成立した経路であることを明示します。
- 活動と遷移のそれぞれにrule_refsを付けます。図に描けることを理由に、未確定の業務条件や失敗経路を補完しません。

BZFL-0002では、停止後の判断から再開・維持・削除への引き渡しへ分岐します。
停止中の情報更新・認証設定は任意活動として図示し、再開までの必須の辺に挟みません。
「維持」は今回の判断での到達点であり、後日の再開・削除を禁止する終端状態ではありません。
停止・再開の失敗経路や「初期設定中」からの停止条件は未確定で、成功扱いの遷移を追加しません。

## 表示と移行期間

[フロー図](../../.yde/views/business-flow-diagram.yaml)は既存の変換記法で主活動と任意活動を結合し、原本の遷移だけを辺にします。
[文書ビュー](../../.yde/views/business-flow-document.yaml)は目的・前提、図、編集用の活動・遷移、任意活動・補足を同じ文書内に表示します。
[業務活動と親フロー](../../.yde/views/business-activity-catalog.yaml)は包含関係から親を導出します。活動へ親フローIDを二重記入しません。
USCSへの逆参照は活動IDまたは旧形式のフローIDを表示し、RITMへの逆参照は根拠を用いる活動・遷移の位置へ辿れます。

BZFL-0001は移行中の旧形式basic_flowを使い、従来のフォームで表示します。主体にIDを付けていますが、既存の手順・USCS対応は維持します。
basic_flowとactivitiesはどちらか一方だけを持ち、欠落・併記・空配列・nullは拒否します。新形式のtransitionsは必須で、空配列は許容します。
新規作成は新形式を使います。フロー図と文書ビューのBZFL-0002限定globは暫定です。
BZFL-0001を移行した時点で両ビューのglobを外し、schemaIdで適用します。同時に旧形式の許容を外してactivitiesを必須にします。

共通の命名・ID・参照方針は [共通記述規約](../WRITING.md)、操作と確認は [操作・検証ガイド](../../OPERATIONS.md) を参照してください。

## 操作との対応

主活動・任意活動の `operations` から、サブドメイン内で定義したDOPRへ参照します。旧形式のbasic_flowでも同じ参照を使います。
活動は業務上の実施場面、操作は領域が提供する振る舞い、USCSは目的に沿った操作・応答と成立条件を記述します。
人の判断・停止の維持・削除運用への引き渡しには、実行しない操作を割り当てません。
例えば停止の依頼と適用は同じDOPR-0009を利用します。これらを一つのUSCSにまとめるかは、目的と結果から検討します。
一つの活動が複数操作を利用でき、同じ操作を複数の活動・USCSから利用できます。対応するUSCSが未検討の活動はusecasesを省略します。
活動のsubdomainsは関与する業務領域を表し、operationsは実際に利用する操作を表します。領域が関与するだけで操作の実施を推測しません。
