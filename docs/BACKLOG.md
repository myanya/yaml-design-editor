# 指摘台帳（BACKLOG）

UX試験・レビュー・開発中に見つかった「今のタスクとは本質が異なるが、気になるポイント」を**見つけた時点で**記録する台帳。対応するかどうか・いつやるかは後で個別に判断する（記録と対応判断を分離することで、脱線せずに指摘を失わない）。

**運用**:

- 気づいたら1行で登録する（完璧な分析は不要。技術メモは分かる範囲で）。登録の敷居を最低にする。
- 対応すると決めたら ROADMAP の項目（大きいもの）に起こすか、直接修正（小さいもの）する。解決したら状態を ✅ にし、対応先（ROADMAP ID・FEATURES ID）を記す。見送りは ❌ と理由。
- 複数の指摘が絡み合う横断課題は**テーマ（T-nn）**として「テーマ管理」節で独立管理する。束ねた指摘の対応先には T-nn を記し、材料（関連指摘・考えられる方策）をテーマへ蓄積して、機が熟したら ROADMAP へ起こす。
- 状態: 📋 未着手 / 💬 議論待ち / 🚧 対応中 / ✅ 解決 / ❌ 見送り

## テーマ管理（複数指摘が絡む横断課題）

単発の指摘として扱うと議論が分断される横断課題を、テーマ（T-nn）として独立管理する。対応判断は急がず、関連指摘と考えられる方策をここへ蓄積し、議論の機が熟したら ROADMAP へ起こす。

### T-01 エージェントフロー抜本検討 【保留——落ち着いてから議論を再開する】

S2第1回（2026-08-09）の総評「動きとしては正しいが、エージェントフローに関して抜本的な検討が必要」を受けたテーマ。個別修正で潰せる不具合ではなく、**いつ動くか・どう終わるか・どう振る舞うか・どう戻すか**の4論点が絡む設計課題として扱う。

- **束ねる指摘**: UX-46（挙動の不安定さ）・UX-48（リトライとコスト）・UX-49（承認待ち中の再発火）・UX-51（変更検知契機）・UX-56（状態管理・巻き戻し）
- **関連指摘**（テーマ外だが方向を揃える）: UX-08 / UX-11（Undoの単位）・UX-47（ゲート区分）・UX-54（部分適用）・UX-53（可観測性）

#### 論点1: いつ動くか（変更検知契機）— UX-51・UX-49

現状はファイルスタンプ差分＋デバウンスで、人間の保存タイミングの癖に依存する。途中保存で起動し、承認待ちがある対象にも再発火する。

考えられる方策（小→大）:

1. **トリガ条件の合成**: `trigger.condition: error-free` など「更新かつ検証OK」で発火する語彙（on-invalid の対）。中途半端な状態での起動を検証状態で弾く
2. **承認待ち対象の発火保留**: pending がある対象ファイルはトリガを保留し、採否決定後にまとめて1回発火（UX-49 の当たり。base 競合の構造的予防にもなる）
3. **編集セッションの区切り**: アイドル判定（一定時間の非操作）や、明示的な「区切り」操作（例:「レビューへ回す」ボタン＝人が引き金を引く半自動運用）。「保存＝作業中スナップショット」という人間のメンタルモデルに合わせる
4. **git 連携（コミット契機）**: コミットを「一通り編集が終わった」の宣言とみなす on-commit トリガ。変更差分も正確になり、論点4の基盤と共通化できる

#### 論点2: どう終わるか（提出ゲート・リトライ・コスト）— UX-48・UX-47

現状は error-free ゲート＋失敗フィードバック付きの単純再実行。既存エラーで恒久失敗し、ターン上限失敗もリトライして maxTurns×2 のコストになる。

考えられる方策:

1. **ゲート区分**: `no-new-errors`（実行開始時のベースライン検証との差分判定）。修正系＝error-free／点検系＝no-new-errors の使い分け（UX-47。単体先行可）
2. **失敗の分類とリトライ適格性**: 「リトライで直る見込みの失敗」と「直らない失敗」（ターン上限到達・権限不足・ゲートと権限の構造矛盾）をカーネルが区分し、後者は即終了して人間へ通知する
3. **ドラフト再開**: 上限到達時の未提出ドラフト保全（既存機構。手動実行ではレビューへ引き継げる）をリトライの開始点にし、毎回ゼロからやり直さない
4. **コスト予算**: リトライ・連鎖を横断する総トークン予算（アクティビティ単位／自動化エンジン単位）。上限は「実行回数」でなく「消費量」で管理する

#### 論点3: どう振る舞うか（エージェント挙動の安定化）— UX-46

現状はスコープ外パスへの書込試行の繰り返しや、変更なしで正常終了すべき場面での abort 選択など、終了様式の判断がモデル任せ。

考えられる方策:

1. **プロンプト規範化**: allowedPaths / allowedFiles のシステムプロンプトでの明示強化と、書込拒否時の誘導文言（「この範囲は読み取り専用。指摘は許可された場所へ」）
2. **終了プロトコルの構造化**: 「submit（変更あり）／点検完了・変更不要（正常終了）／abort（続行不能）」を明示的に区別したツール・引数にし、モデルの判断裁量を減らす（「変更なし＝abort」の誤選択を構造的に防ぐ）
3. **カーネル介入**: 同一パスへの書込拒否が繰り返されたらカーネルが介入する（許可パスの候補提示・早期終了）。リトライに入る前にターン内で軌道修正させる
4. **評価セットでの回帰固定**: `_evals` に「変更不要ケース」「スコープ外へ誘惑されるケース」のゴールデンを追加し、プロンプト・定義変更の回帰を測る（AG-20 の活用）

#### 論点4: どう戻すか（状態管理・巻き戻し）— UX-56・UX-08

現状は実行記録単位のバックアップ復元（CLI のみ）で、対象記録の特定が困難・後続適用と重なると全戻しになる。人間の Undo（文書単位・キーストローク単位＝UX-08/11）とも不連続。

考えられる方策（小→大）:

1. **導線改善**: 履歴・受信箱からの revert（実行記録の特定を不要にする）
2. **適用の系譜管理**: 変更セット適用の履歴（どのファイルのどのパスを・いつ・どの実行が変えたか）を持ち、後続と重ならない範囲の部分巻き戻しを可能にする
3. **git 連携**: 適用ごとに自動コミットし、巻き戻しを git revert 相当へ委譲する。コメント・スタイル保持（R8-01）はテキスト差分と相性が良く、論点1-4（コミット契機）と基盤を共有できる

#### 先行できる周辺改善（テーマの結論を待たない）

UX-45（自動実行対象の表示）・UX-50（競合破棄の区分）・UX-52（受信箱の日時）・UX-53（履歴⇔ログ紐付け）・UX-55（競合の事前検出）は独立に対応可能。UX-47（no-new-errors）も単体で先行できるが、論点2の失敗分類と方向を揃えて設計する。

### T-02 プラン／ワークフロー層（作業編成の一般化）【構想——T-01 と合流してから着手判断】

一括実行の検討（2026-08-09。Level 1〜3 の整理）で「大規模になるため特別扱いする」と決めたテーマ。foreach（ROADMAP R18-01 実装済み）が担う「同一アクティビティ×対象集合」を超えて、**複数アクティビティの順序・依存・分岐を宣言的に合成する**編成層（例 `_plans`: 「アクター全件 → ユースケース全件」の依存つき一括）を扱う。

- **束ねる指摘**: UX-60（本体）
- **関連**: UX-59（ゴール駆動 Level 2 = R18-02。編成層の手前で解けるものはそちらで解く）・T-01（契機・終わり方・巻き戻しの再設計と正面から絡む）
- **論点**:
  1. 既存 `chain`（成功/失敗/出力値分岐）との役割分担——chain の拡張で足りる範囲と、新定義種別が要る範囲の線引き
  2. 実行状態の永続化と再開（アプリ再起動をまたぐジョブ・失敗項目からの再開）
  3. 承認の束ね方（項目ごとの受信箱N件 vs ジョブ単位レビュー。UX-52/54/55 の受信箱改善と歩調を合わせる)
  4. ワークフローエンジンの再発明リスク——導入するなら本ツールの原則（原本主義・人間承認・直列実行）を壊さない最小語彙に絞る
- **運用**: 単発対応しない。T-01 の議論再開時に「編成層まで含めて」設計し、機が熟したら ROADMAP（R18-03）へ起こす。
