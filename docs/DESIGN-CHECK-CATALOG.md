# 設計チェックカタログ（R28-06）

設計情報（YAML文書群）に対して**どのような機械的チェックが可能か**のパターン台帳。
「AIが書き、機械が検証し、人間は差分を承認する」ループの検証部を設計するときの語彙集として使う。
各パターンは sysdev-template（会議室予約サンプル。gitignore 対象の実戦投入場）での実例IDを添える。
機構の詳細仕様は [README.md](../README.md)（利用者向けリファレンス）と [ARCHITECTURE.md](ARCHITECTURE.md) §4.30〜§4.32、
評価の意味論は [CORE-CALCULUS.md](CORE-CALCULUS.md) を参照。

## 0. 全チェック共通の性質

- **検証の乗る場所**: すべてのチェックは同じ検証器（Validator）で評価され、GUI検証タブ・CLI `validate`・
  エージェント提出ゲート・変更セット適用（`requireValid`）・準備完了レポート（`readiness`）に自動で乗る。
  チェックを1本書けば、人間の編集・AIの提出・一括適用のどこで壊しても同じ指摘が出る。
- **判定保留の哲学**（ARCHITECTURE §4.26）: 母集団外・材料が空・値未記入は**黙る**（違反にしない）。
  「書いていないこと」への催促は必須・カバレッジ・フェーズの担当で、規則系チェックは「書いてあるものの矛盾」を検出する。
- **Unknown 降格**（CORE-CALCULUS CALC-17）: 未解決参照で判定材料（解の候補）が失われたときは、
  「解の不足を理由とする違反」（exists 解なし・count 下限未達・到達不能・行き止まり）を黙らせる。
  原因は未解決参照のエラーとして別途報告されているため、沈黙が違反へ化けない。
- **フェーズゲート**: constraints / matrix / flow / coverage は `activeFrom:` で「このフェーズ到達後に判定を始める」
  と宣言できる（工程が進むまで催促しない）。

## 1. 記法・構造の規律（単文書で完結するチェック）

| 検証したいこと | 機構 | 書き方 |
|---|---|---|
| 必須項目の記入 | `required: true` | フィールド宣言 |
| 工程が進んだら必須になる項目 | `requiredFrom: フェーズ名` ＋ `phases:` | フェーズ累積必須（記入進捗は phaseProgress に出る） |
| 値の型・選択肢の統制 | `type:`（int / date / enum 等）・`values:` | enum の選択肢はリッチ形 `{value, label, description}` も可 |
| ID の命名規約 | `type: id` ＋ `idPattern:`（例 `"SCR-*"`） | 参照側にも `idPattern:` で受け入れ規約を書ける |
| 区分値によって変わる必須項目 | enum の `cases:` | 例: 由来が「論理項目由来」なら対応参照が必須・「技術項目」なら理由が必須（screen-design） |

## 2. トレーサビリティ（参照・関係・多重度）

関係の語彙と制約は**関係レジストリ**（`kind: relations` 文書）に一元宣言する。

| 検証したいこと | 機構 | テンプレ実例 |
|---|---|---|
| 参照先の実在（宙ぶらりん検出） | `type: ref`（未解決参照はエラー） | 全域 |
| 参照先の型・スキーマの統制 | ref の `scope:`／レジストリの `source:` `target:` | calls（画面→内部APIのみ） |
| 「全◯◯は△△から参照されること」（取りこぼし検出） | レジストリの `cardinality: {inMin: 1}` | groups（全UCはドメインに所属）・maps-type（全業務型はマッピング行を持つ） |
| 「◯◯は必ず根拠を持つこと」（出自の義務） | `cardinality: {outMin: 1}` | derived-from（画面・APIは導出元必須）・verifies |
| 二重対応の禁止 | `inMax: 1` / `outMax: 1` | maps-type（二重マッピング禁止）・viewpoint（項目は観点ちょうど1つ） |
| 未宣言の関係語彙・定義の重複の禁止 | `enforcement: {undeclaredRelation: error, definingUniqueness: error}` | sysdev-relations |
| 循環の禁止 | レジストリの `acyclic: true` | （テンプレ未使用。変更セット提出時も循環を拒否） |
| 詳細文書の存在（同一IDの詳細化） | スキーマの `coverage: - detailIn:` | 画面定義・画面設計書の存在（screen-list。作成スキャフォールドつき） |

## 3. パターン制約（constraints: グラフの経路パターン＋述語）

`match:`（node / edge の連鎖と束縛）で「起点エンティティごとの経路パターン」を宣言し、要求を1つ添える。

| 検証したいこと | 要求の書き方 | テンプレ実例 |
|---|---|---|
| 多段トレースの義務（経路の存在） | `expect: exists` | ti-covered（除外でないテスト項目は消化されること） |
| レイヤ規約・禁止経路 | `expect: absent` | screen-no-ext-api（画面は外部APIを直接呼ばない） |
| 解の件数の範囲 | `count: {min, max}` | proc-unit-min2（処理は単体テスト項目2件以上） |
| 条件付きの義務・免除 | 起点や途中の `where:`（equals / notEquals / exists） | br-unapproved-referenced（未承認BRの参照検出） |
| 2経路が同一ノードで合流すること（型不一致検出） | `node: {same: 束縛名}` | col-type-consistent（カラムの型 ≠ 実装属性の型を error） |
| 束縛間の値比較（大小・等値の整合） | `check: [{lte: [{of,path},{of,path}]}]`（lte/gte/lt/gt/eq/ne） | spi-length-within-dtype（入力制約が業務型の制約からはみ出さない）・dtype-bounds-ordered（同一束縛内の min≦max） |

原則: **値の一致で意味を推測しない**（ADR-0008）。「同じものを指しているか」は same（ノード同一性）で、
「値の大小・整合」だけを check で書く。

## 4. 網羅（matrix: 行×列の全組合せ）

「行の各エンティティ × 列の各エンティティ」の全セルに、両方を参照する**証人**が存在すること。

- 例: 処理 × 試験観点 → テスト項目（テスト項目一覧の機械的抽出規約。proc-viewpoint-matrix）
- あえて対象外にするセルは証人側に `excluded: true` の行を残す（**明示的除外**＝理由がデータに残る。TI-107）
- 不足セルは行の定義出現に列挙で報告される

## 5. 遷移・到達性（flow: エッジ集合の到達閉包）

エッジ文書の行（from 参照＋ to 参照）を有向グラフとみなし、経路の長さによらない到達性を検証する
（固定長パターンの constraints では書けない領分。R28-04）。

| 検証したいこと | 書き方 | テンプレ実例 |
|---|---|---|
| 到達不能ノードの検出 | `start: {relation: ...}`（開始ノードをデータで宣言） | screen-flow（全画面は開始画面から到達できること） |
| 行き止まりの検出 | 出エッジなし＝指摘。許容するノードは `terminal: {relation: ...}` で宣言 | 同上（完了画面などを終端に宣言） |
| 宣言外遷移の検出 | `usage: {from, to}`（使用エッジ ⊆ 宣言エッジを要求） | （テンプレ未使用。遷移の原本と利用側が分かれたら投入） |

**状態機械への一般化**: 状態をID化（エンティティ化。例 ST-RESERVED）して状態遷移表を ref で書けば、
同じ `flow:` 宣言が状態遷移の検証（未定義遷移・到達不能状態・吸収状態）になる。
enum の区分値のまま直接ノードにする形は、ID化パターンで足りないケースの需要が立つまで見送り（R28-07 の same と同じ筋）。

## 6. 導出値の整合（consistency）

文書内のID要素の宣言値が、参照先から導出される期待値と一致すること（例: 対応表の転記ミス検出）。
`consistency` は**組込みの定義体（YAML）が作る語彙**で、検証の前に「クエリ＋値の比較 `check`」の基本の検査へ展開される
（P29 Phase 6 第1段。ARCHITECTURE §4.36。展開結果は CLI `checks` で確認できる）。比べる相手の値が複数の文書に書かれていれば
すべて調べ、1つでも食い違えば指摘する（値の比較の共通規則）。指摘は値が書かれた場所に出て、
「導出規則へ／入力値へ／導出値を適用」の対応が付く。

## 6b. 自分の検査に名前を付ける（検査の定義と語彙の定義）

同じ形の検査を何度も書くとき・組込みに無い検査が欲しいときは、`functions`（関数のような定義）と
`vocabulary`（短く書くための語彙）で自分の検査を作る（README「検査の定義と語彙の定義」）。

| 目的 | 機構 |
|---|---|
| 同じ形の検査に名前を付けて使い回す | `functions` に定義し、`constraints` で `use` ＋ `with` |
| スキーマに短く書けるようにする | `vocabulary`（書ける場所 `in` と、どの定義をどの値で使うか `uses`） |
| 値を計算してから比べる | `check` の値の式（テンプレートの展開 `format`・辞書での置き換え `map`・最初に得られた値 `first`・決まった値 `value`） |
| どの文書に書かれた値を比べるかを指定する | 値の読み出しの `in: {schemaId, fileGlob}` |
| 指摘を値の場所に出し、直し方を示す | `reportAt`・`message`・`responses`（移動 `jump`・値の書き込み `apply`） |
| 展開された検査を確認する | CLI `checks <workspace> [schema-id] [--definitions]` |

組込みの語彙（`consistency`）も同じ仕組みで書かれており、組込みだけが使える特別な機能はない。
複雑なアルゴリズムが要る検査（例: 状態遷移への時相論理の適用）は、YAML で書こうとせず、コードの専用チェッカーとして実装する。

## 7. プロセスへの組み込み（ゲート・集計）

| 目的 | 機構 |
|---|---|
| 修正系エージェントの提出品質 | アクティビティ `gates.validation: error-free`（エラーが残る提出を拒否） |
| 点検系エージェントの提出品質 | `gates.validation: no-new-errors`（既存エラーは許容し、**増やした分だけ**拒否。R28-05b） |
| 一括適用の安全弁 | `apply --require-valid`（1件でもエラーなら何も書かない） |
| エンティティ単位の完了判定 | CLI `readiness`（全検証をエンティティに帰属させ、エラー0=準備完了。型／フェーズ別集計・`--pending` で未完了のみ） |
| 工程ごとの段階的な厳格化 | `phases:` ＋ 各チェックの `activeFrom:`（現フェーズに関係する指摘だけが出る） |

## 8. 正準の綴り（規範。R29-04）

同じ設計上の問いに複数の書き方を許すと、書き手が毎回悩み、数え方の差で答えまで揺れる。
以下を**正準（新規記述の規範）**とする（Core Calculus Phase 2 の決定 MP-01。2026-09-19）。

1. **1文書で書ける規律**はフィールド宣言（§1）で。書けないときだけ下へ進む。
2. **1ホップ・無条件・型全体に一律の多重度**（存在・件数の上下限）は関係レジストリの `cardinality`（§2）。
   数える単位は**参照の本数**（同じ相手への重複参照も数える＝リンク規律の検査）。
3. **条件付き（where）・多段・組の distinct が要る数え上げ**は constraints の `exists` / `count`（§3）。
   数える単位は**束縛タプルの distinct 件数**。値比較は `check`、宣言値=導出値は consistency（§6。中身は `check` へ展開される語彙）。
4. **同一IDの詳細化の存在**は coverage の `detailIn`（§2）。出現集合への集約であり、参照では書けない。
   （被参照数の要求＝旧 `requiredBy` は R29-01 で削除——上記 2 か 3 で書く。）
5. **全組合せの網羅**は matrix（§4）、**経路の長さによらない到達性**は flow（§5）。
6. チェックの粒度に迷ったら「違反メッセージを読んだ人が直す場所へ飛べるか」（relatedIds・報告先）で決める。
7. **表面語彙は増やさない**（語彙の予算。CONVENTIONS §9）: 新しい検証要求は、まず本書の正準の組合せで
   書けることを確認する。書けないときも新キーより既存キーの拡張を優先し、核にない演算へ名前を付けるとき
   （例: flow の到達閉包）だけ語彙を追加する——追加時は CORE-CALCULUS §20 のチェックリストを通し、
   計算体系の写像表（specs/20-semantics/calculus/feature-mapping.yaml）へ1行追加する。
