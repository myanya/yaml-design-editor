# 汎用フロービューの実装計画

## 位置付け

状態：初期範囲の実装・BZFL-0002移行・改名影響の開示が完了。利用者が最小例と実データの画面を確認済み。共通リファクタリングの既存不具合はBACKLOGで別管理する。
この文書は完了した計画の記録。現行機能の説明は [ビューの設計](../architecture/views.md)と[利用者ガイド](../manual/flow-views.md)を参照する。

目的は、YAMLの原本を図と詳細フォームから読み書きできること。
初期範囲は文書単位の有向フロー、任意レーン、分岐・合流・戻り線、参照移動、未保存編集への追随とする。
独立した `kind: flow` の定義を文書ビューからも参照し、同じ解決結果と描画部品を使う。
図上での接続編集、手動座標の保存、複数文書の横断表示、図の画像出力は後続候補とする。

## 定義とデータの境界

| 管理場所 | 担当する内容 |
|---|---|
| 原本YAML | 活動・状態・主体・遷移・条件・根拠への参照 |
| 利用者のスキーマ | 各項目の型、ID、参照、必須条件、業務上の種別 |
| ビュー定義 | 原本から表示モデルへの対応、図形、方向、詳細表示との組み合わせ |
| 一時的な画面状態 | 選択、拡大率、スクロール位置 |

活動の本文から遷移を推測せず、配列の隣同士を自動でつながない。
レーンは表示上の区分であり、実行権限・所属・同期処理・排他制御を意味しない。
ひし形や複数の矢印だけで、排他的分岐・並列実行・全到着待ちを判定しない。
そうした意味が必要なワークスペースでは、原本の種別・条件とスキーマの制約で表す。

## 表示モデル

変換結果は、`nodes`・`edges`・任意の `lanes` を持つ一時的なobjectとする。
これは変換の出力契約であり、描画部品へ渡す解決結果は次の3つに分ける。

| 解決結果 | 内容 |
|---|---|
| 表示データ | 描画できるノード・辺・レーンと、不完全な要素の表示情報 |
| 原本対応 | 出力位置に対応する文書ID・YPath、直接編集の可否 |
| 診断 | コード・重大度・メッセージ・出力位置・原本または定義の位置 |

診断対象はkeyだけで識別しない。key欠落・重複も扱えるよう出力位置を保持する。
変換不能なら表示データなしの全体診断を返す。描画部品は解決結果だけを読み、索引を独自に探索しない。
型・必須項目・列挙値は組込みの構造スキーマで検査する。keyの一意性・接続先との対応は解決側の別の検査とする。
構造検査の位置は来歴から原本へ対応付け、欠落値は元要素のdetail、原本がなければ定義の位置へ案内する。
構造が不完全でも保持できる要素は診断付きで表示し、未知のshapeをboxへ代替した事実も診断に残す。
`basic_flow`・`rule_refs`・特定のID接頭辞を本体へ固定しない。

| 場所 | 項目 | 契約 |
|---|---|---|
| `nodes[]` | `key` | 図内で一意の空でない文字列 |
| | `label` | ノードの短い見出し |
| | `shape` | `box`・`diamond`・`rounded`、省略時は `box` |
| | `lane` | レーンのkey、省略可 |
| | `detail` | 原本要素のコピーと、その出どころ |
| `edges[]` | `key` | 任意の安定した識別子 |
| | `from`・`to` | ノードのkey |
| | `label` | 遷移条件などの文字列、省略可 |
| | `detail` | 原本の遷移要素のコピーと、その出どころ |
| `lanes[]` | `key`・`label` | 図内で一意の区分値と見出し |

ノードのkeyは原本のIDを推奨する。原本でID・ref型を宣言すれば既存の索引・参照検査・改名を使える。
汎用ビュー自体はkeyを文字列として扱い、ローカルな文字列をYDEの論理IDとして索引へ追加しない。
配列番号を参照先の識別子にせず、原本座標は詳細への移動先として扱う。
エッジのkeyがなければ、その原本座標を一時的な画面上の識別に使う。
同じfrom/toの辺が複数あっても、条件・原本が異なる辺を統合しない。

レーンは `lanes` の配列順で並べる。所属レーンが未指定ならレーン外の領域に表示する。
複数主体の活動を複数ノードへ自動複製しない。主担当が未定ならレーン外へ置き、関与者を詳細で示す。
原本に複数の活動として記述された場合だけ、別のノードとして扱う。

## 原本座標と詳細フォーム

変換には既存の [Construct](../architecture/transform.md)を使用する。
各ノード・辺の `detail: {$copy: .}` が、原本の活動・遷移全体を指す。
`TransformResult.origins` の `nodes[i].detail` / `edges[i].detail` に記録された文書IDとYPathを、詳細フォームの対象にする。
タイトルの座標の親を推測したり、文書パスをビューに手入力したりしない。

`detail` の値は派生した読み取り用のコピーであり、編集する木ではない。
編集は出どころを使って文書キャッシュの原本を引き、既存の `FormCtx`・実効フィールド・Slot・`markEdited()` を使う。
認める編集対象は、原本の部分木を直接コピーした `detail` のみとする。
組み立てた値・定数・複数の出どころしかない値は読み取り表示と原本候補への移動にとどめる。
CLIにもdetailの原本座標と表示項目の来歴を開示する。

現行のTransformOriginはコピーと計算の区別を持たないため、座標があるだけで編集可能とはしない。
初期版で直接編集を許すのは、配列の `$each` の `$build` が通常のマップで、その直下のdetailがちょうど `{$copy: .}` である形だけ。
eachとcopyの `$of`・`$in`、`$when` による包み込み、子パスのcopy、規則経由・eachEntryは直接編集の対象外とする。
適格なeach同士を外側のconcatで結合する形は許可する。各要素の生成元と結合後の原本座標を照合する。
パース済みTemplateで適格性を確認し、対応する単一の原本座標が取得できた場合だけ詳細フォームで編集を許可する。
それ以外の定義は、変換結果を表示しても詳細欄からの編集は許可しない。
その場合も来歴から既存の原本フォームを開く操作は提供する。式の出力から原本への逆変換は行わない。

詳細の参照欄は既存フォームを使うため、USCS・RITM等の表示と移動をフロー側で再実装しない。
一意なkeyがある場合はビューID・対象文書ID・要素種別・keyで選択を保持し、最新の解決結果から座標を引き直す。
keyなしの辺は、文書とビュー定義のリビジョンが同じ間だけ原本座標で復元する。いずれかが変われば選択を解除する。
内容やハッシュによる同一性の推測はしない。keyが消えた場合・重複した場合も選択を解除する。
履歴へ上記の選択情報を追加し、復元条件を満たさなければ図だけへ戻る。セッションの再生成時もkeyなしの選択は失効させる。
keyなしの辺を編集すると選択が外れる制約があるため、今回の原本の遷移には安定した識別子を付ける。

## フロービューの記法案

以下の独立したflow定義は読取・コア解決に対応済み。現在の使い方は [フロービュー](../manual/flow-views.md)を参照する。
入力選択は既存の文書ビューと同じ `match` / `schemaId`（併記時はAND）を使う。
`projection` は既存のTransformDef形式で、初期範囲では開いた文書を入力とするため `from`・外部paramsを認めない。
`build`・`rules` は既存のパーサーと評価器をそのまま使い、専用のパス指定・穴埋め・条件言語を追加しない。
`projection.id` は変換の診断名で、ビューIDとは別の索引を作らない。

```yaml
id: business-flow-diagram
name: 業務フロー図
kind: flow
schemaId: business-flow-detail
match: 10_specs/40_business_flows/BZFL-0002-*.yaml
layout:
  direction: down
projection:
  id: business-flow-projection
  build:
    lanes:
      $each: actors
      $build:
        key: {$copy: id}
        label: {$copy: name}
    nodes:
      $concat:
        - $each: activities
          $build:
            key: {$copy: id}
            label:
              $format: '{category}：{title}'
              $with:
                category:
                  $map: {$copy: kind}
                  $using: {action: 活動, decision: 判断, outcome: 到達点, handoff: 引渡し}
            lane: {$copy: actor}
            shape:
              $map: {$copy: kind}
              $using: {action: box, decision: diamond, outcome: rounded, handoff: box}
            detail: {$copy: .}
        - $each: supporting_activities
          $build:
            key: {$copy: id}
            label: {$format: '任意：{title}'}
            lane: {$copy: actor}
            shape: box
            detail: {$copy: .}
    edges:
      $each: transitions
      $build:
        key: {$copy: id}
        from: {$copy: from}
        to: {$copy: to}
        label: {$copy: condition}
        detail: {$copy: .}
```

`layout.direction` は `down` / `right`、既定は `down`。
配列の順序は配置の同順位の候補を決める材料にだけ使い、辺の追加には使わない。
本例は未確定の原本項目 `activities` / `transitions` を使う適用案であり、現行BZFL文書にはそのまま適用できない。
任意活動もconcatでノード化するが、原本にない遷移は追加しない。接続のない任意活動は注記付きで表示する。
outcomeはroundedと「到達点」、handoffはboxと「引渡し」で区別し、色だけに依存しない。

文書埋め込みは実装済み。`fields`・`backlinks` に加えて `flow: {view: ビューID}` をセクションに指定できる。
1セクションは1種類だけを指定し、参照先をflow種別に限定するため、文書ビューの相互埋め込みによる循環は生じない。

```yaml
id: business-flow-document
name: 業務フローの確認
kind: document
schemaId: business-flow-detail
match: 10_specs/40_business_flows/BZFL-0002-*.yaml
sections:
  - label: 目的と前提
    fields: {include: [id, status, purpose, actors, preconditions]}
  - label: 業務の流れ
    flow: {view: business-flow-diagram}
  - label: 任意の関連活動と補足
    fields: {include: [supporting_activities, variations, outcome, rule_refs]}
```

埋め込みは現在の文書を渡し、別文書を暗黙に選ばない。
静的リントでは参照先の存在・flow種別・指定の構文までを検査し、glob同士の包含は判定しない。
現在の文書が参照先のmatchとschemaIdに適合するかは解決時に判定する。
不適合なら当該セクションに理由と定義への移動先を表示し、黙って空の図にしない。
台帳のビュー一覧から開く場合は適用対象文書を選ぶ。対象が複数でも最初の1件を勝手に選ばない。
文書内表示と拡大表示で選択を引き継ぎ、移動履歴はAppStateの既存経路へ接続する。

## BZFL-0002への適用案

対象原本は [ユーザの停止と再開](../../labs/user-man/10_specs/40_business_flows/BZFL-0002-ユーザの停止と再開.yaml)。
ここは原本を移行するための対応表であり、業務仕様の第二の原本ではない。
本体の記法とデータ構造を具体化する段階では、原本・スキーマ・既存ビューを変更しない。

### 原本の構造

| 項目 | 変更案 |
|---|---|
| `actors` | 既存の名称・説明を保持し、ID型の `id` を追加 |
| `activities` | 主経路と分岐の活動を格納し、`basic_flow` を置き換える |
| `supporting_activities` | 必須の順序を持たない、停止中の任意の活動を格納 |
| `transitions` | 遷移元・遷移先・条件・項目単位のRITM参照を格納 |
| `variations` | 予約や対象外条件など、まだ活動・遷移に展開していない説明を保持 |

活動には `id`・`kind`・`title`・`actor`・`content` と既存のstate_change・contexts・subdomains・rule_refs・usecasesを置く。
任意の活動には実施可能な状況を示す `condition` も置く。実施可能であることを、必ず実施することへ読み替えない。
活動IDは `BACT-nnnn`、主体IDは `BATR-nnnn`、遷移IDは `BTRN-nnnn` を採用し、[ID規約](../../labs/user-man/10_specs/WRITING.md)へ反映した。
各系列で文書間一意に採番し、親フローの番号や表示順をIDへ含めない。
主体をbusiness-actor型のID要素とし、両活動配列のactorをref型で宣言する。
主体の実在・型は既存の参照検査を使い、同じ文書のactorsに含まれることをcontainsとsameの検査で確認する。
遷移にもID型のidを付けてbusiness-transitionとして定義し、ビューの辺のkeyへ写す。
遷移のfrom/toは既存のref型を使い、対象は同じ文書のactivities内に定義された活動へ限定する検査を設ける。
この適用案では主活動と任意活動の型を区別し、任意活動を遷移の対象に含めない。表示対象と遷移の許容対象を分ける。
この母集団内の対応確認は既存のQuery・Predicateによる検査定義で表し、描画側だけで業務上の正しさを判定しない。

### 活動の対応

| 採用ID | 活動 | 移行前の原本との対応 |
|---|---|---|
| BACT-0001 | 停止の種類を判断 | 基本フローの状況確認・種類判断 |
| BACT-0002 | 理由を付けて停止を依頼 | 基本フローの停止依頼 |
| BACT-0003 | 停止を適用 | 基本フローの停止適用 |
| BACT-0004 | 停止後の扱いを判断 | 再開判断と、維持・削除の代替フロー |
| BACT-0005 | 理由を付けて再開を依頼 | 基本フローの再開依頼 |
| BACT-0006 | 再開を適用 | 基本フローの再開適用 |
| BACT-0007 | 再ログインして利用を再開 | 基本フローの再ログイン |
| BACT-0008 | 停止を維持 | 維持の代替フローの到達点 |
| BACT-0009 | 削除運用へ引き渡す | 削除の代替フロー |
| BACT-0010 | 必要なユーザ情報を更新 | 停止中の更新のうち管理者側の活動 |
| BACT-0011 | 許可された認証設定を行う | 停止中の更新のうち本人側の活動 |

BACT-0010・0011はsupporting_activitiesに置き、concatで図に表示するが、停止から再開までの必須の辺へ挟まない。
BACT-0004は人間の運用判断の整理であり、新しい承認機能・専用のシステム操作を追加する意味ではない。
BACT-0008は今回の判断で維持する到達点であり、後日の再開・削除を禁止する終端状態ではない。
継続中の運用を周期的な判断ループとして自動実行する意味の戻り線は追加しない。
BACT-0009では既存の削除条件を保持し、未検討の削除の詳細手順まで図を伸ばさない。

主経路は0001→0002→0003→0004、再開する場合は0004→0005→0006→0007とする案。
0004から「維持する」で0008、「削除する」で0009へ分岐する。
遷移は運用上の進行を表し、時間制限・自動開始・成功時の同期トランザクションを意味しない。
停止適用・再開適用から先へ進む辺は、当該適用が成立した経路であることを明記する。
失敗後の業務経路は未記述のまま残し、成功したことにして描かない。

予約、停止した登録者と実行権限者の違い、利用開始前の取扱いはvariationsへ保持する。
予約フローを展開する際は、即時フローと混ぜず別の開始条件・活動・遷移として整理する。
新しいUSCSの採番はこの構造整理に含めない。

### 既存参照への影響

活動にIDを付けると、YDEはその活動を参照の最内側の所有者として扱う。
現在の `elaborates-with` はsourceをbusiness-flowに限定しているため、IDの追加だけでは関係の型検査を壊す。
移行では活動要素にbusiness-activity型と定義出現を宣言し、関係レジストリのsourceへ活動型を加える。
まだIDを持たないvariationsからの既存参照も残るため、移行中はbusiness-flowを許容する。

現在のusecase-catalogの被参照列も、追加後は活動IDを表示する。
列名と案内を活動に合わせ、所属するフローは入れ子関係から辿れるようにする。
必要な親フローの表示は既存のcontainsクエリから導出し、各活動に同じ親IDを二重記入しない。
活動のRITM参照も、フロー全体からの参照と混同せず、元の活動へ着地することを確認する。

BZFL-0001も同じスキーマを使用するため、BZFL-0002の移行時にactivitiesを全件必須にはしない。
移行中はbasic_flowとactivitiesのどちらか一方だけが存在することを必須とし、両方・どちらもなしを拒否する。
存在検査だけでなく空配列・nullも拒否する。新形式はtransitionsを必須とするが、接続のない図の空の遷移配列は認める。
個別globはBZFL-0002で確認する間だけ使用する。BZFL-0001の移行後に両ビューの個別globを外し、schemaIdで共通適用する。
旧形式には移行中は既存フォームを適用する。全件移行後は旧形式の許容を外し、activitiesの必須条件へ一本化する。
スキーマ・関係定義・ビュー・作成ガイドに加え、WRITING.mdのID体系とOPERATIONS.mdの試し方も同じ移行単位に含める。

### 構造例

以下は分岐周辺だけを抜粋した変換入力例であり、移行後の完全なBZFL-0002ではない。
実際の移行では上の対応表に従い、既存の本文・領域・コンテキスト・根拠を保持する。
ACTOR-*・TRANS-*は検証例の識別子であり、本ワークスペースの採番規約を確定するものではない。

```yaml
id: BZFL-0002
actors:
  - {id: ACTOR-MANAGER, name: 管理者等}
  - {id: ACTOR-SYSTEM, name: 本システム}
  - {id: ACTOR-MEMBER, name: 対象ユーザ本人}
activities:
  - id: BACT-0003
    title: 停止を適用する
    kind: action
    actor: ACTOR-SYSTEM
    rule_refs: [RITM-0170, RITM-0175, RITM-0176]
  - id: BACT-0004
    title: 停止後の扱いを判断する
    kind: decision
    actor: ACTOR-MANAGER
    rule_refs: [RITM-0170]
  - id: BACT-0005
    title: 理由を付けて再開を依頼する
    kind: action
    actor: ACTOR-MANAGER
    rule_refs: [RITM-0170, RITM-0185]
  - id: BACT-0008
    title: 停止を維持する
    kind: outcome
    actor: ACTOR-MANAGER
    rule_refs: [RITM-0170]
  - id: BACT-0009
    title: 削除運用へ引き渡す
    kind: handoff
    actor: ACTOR-MANAGER
    rule_refs: [RITM-0170, RITM-0173, RITM-0175]
supporting_activities:
  - id: BACT-0010
    title: 必要なユーザ情報を更新する
    actor: ACTOR-MANAGER
    condition: 停止中に必要がある場合
    rule_refs: [RITM-0172]
  - id: BACT-0011
    title: 許可された認証設定を行う
    actor: ACTOR-MEMBER
    condition: 停止中に必要がある場合
    rule_refs: [RITM-0171]
transitions:
  - id: TRANS-STOP-APPLIED
    from: BACT-0003
    to: BACT-0004
    condition: 停止の適用が成立し、以後の運用で扱いを判断する
    rule_refs: [RITM-0170]
  - id: TRANS-RESUME
    from: BACT-0004
    to: BACT-0005
    condition: 再開すると判断した場合
```

## 配置と不完全なデータ

配置はComposeから切り出した純粋な関数にする。文字サイズを測った結果と表示モデルを入力し、ノード矩形・辺の経路を返す。
循環部分をまとめて段を割り当て、同順位は原本順とkeyで決める。戻り線・自己ループ・同じ両端の複数辺は別の経路を与える。
レーン内の重なりとラベルの占有領域を考慮し、描画しきれない場合もノード・辺を黙って間引かない。
文書内表示は高さを制限し、パン・ズームと拡大表示を提供する。ノード選択で図全体を再配置しない。

| 状態 | 表示と扱い |
|---|---|
| keyの重複 | 両方を区別して表示し、曖昧な接続先を選ばない |
| 未解決の参照 | 未接続の印と原本の参照位置を表示 |
| 存在するが図の対象外 | 対象外の接続先として示し、未解決と区別 |
| 必須の表示項目が欠落 | 元要素を消さず、不足項目と原本を示す |
| レーンが未解決 | レーン外に置き、指定値と不足を示す |
| 表示形状が未知 | boxで内容を表示し、未対応の指定を示す |
| 入力が不正で変換不能 | 図の代わりに診断と原本フォームへの入口を表示 |

表示対象外と未解決の区別は、from/toの原本座標とスキーマ・索引から行う。
単なる文字列keyで参照型の裏付けがない場合は「図内に接続先なし」とし、ワークスペースでの不存在と断定しない。
表示モデルの契約違反と、業務上の検証違反は区別する。描画できることを検証の充足とはしない。
変換は欠落した値を出力から落とすことがあるため、buildは元の各活動についてobjectとdetailを残す。
意図して絞った場合はその選択条件を開示し、除外ノードの前後に架空の辺を足さない。

## Core Calculusの確認

| 観点 | 本設計での対応 |
|---|---|
| 対象選択 | 初期版は文書の適用条件で1文書を渡し、文書内は既存のパスとeachで辿る |
| 値導出 | Copy・Map・Format等の既存Transform指示と共有の値評価を使用 |
| 条件判定 | 既存Predicateを使用 |
| 集合演算 | 初期の表示モデルでは集計を必要としない |
| 変更はRewrite → PatchOpに落とせるか | 解決・配置は原本への変更を生成しないため該当なし、詳細フォームは既存の編集経路を使用 |
| 新しい項の組み立て | Constructで行い、原本へ保存しない |
| 評価の重複 | 専用のQuery・式評価・参照解決を追加しない |
| 来歴 | TransformOriginを保持し、detailの直接コピーから編集対象を解決 |
| 決定性 | 同じ文書・定義・測定寸法から同じ配置を得る |
| Unknown・Conflict | 未解決・対象外・重複を区別し、空の結果や成功へ変換しない |
| 書き込み | 原本の既存フォーム経路を使用 |

追加する表示契約・配置計算は新しい図の表現であり、業務の実行エンジンではない。
新しい変換プリミティブが必要かは、下記の実データ検証をもとに判断する。
