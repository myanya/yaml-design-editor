### P14: ビュー機構の強化（文書ビュー・スキーマとビューの責務分離） ✅ 完了（2026-08）

狙い: スキーマは「データ契約（構造・意味・検証）」、ビューは「画面の合成（何を・どの順で・どんな派生情報とともに見せるか）」という責務分離を確立する。現状のビューは台帳スペース専用の横断グリッド1種類で、文書をフォームで開いたときの表示はスキーマだけが決めており、表示の要望（例: アクター定義書に「利用するユースケース」の被参照表を足す）がスキーマへの表示オプション追加圧力になっている（`role` / `display` / enum `options` と混入は既に始まっている）。本フェーズでビューに**文書ビュー**（`kind: document`: 文書単位の表示合成）を追加し、「内容はスキーマで検証し、表示はビューでコントロールする」を実現する。

方針（ARCHITECTURE §4.14 の不変条件は維持・拡張する）:

- **文書ビューがマッチしない文書は現行のスキーマ駆動フォーム**＝「今の表示は暗黙の既定ビュー」。ビューは足したい文書にだけ足す opt-in で、後方互換を壊さない。
- **表示決定の優先順位**: ①文書ビュー（画面の合成）＞②スキーマの固有表示ヒント（`role` / `display` / `label`＝要素の同一性に近い表示。`Display` の共有契約として存置）＞③予約語規約。既存ヒントの移設はせず、「今後、合成系のオプションはスキーマに足さない」を境界とする。
- **派生セクション（被参照表など）は読み取り専用＋原本座標へのジャンプ**。fields セクションの編集は既存の `FormCtx` / `Slot` 経路に委譲し、ビュー専用の書込経路を作らない。
- **人間とAIが同じ面を見る**: 文書ビューも `read_view` / CLI `view` で機械可読に解決できるようにする。

### P16: 値型と決定論的射影（値レベルの決定論的変換） 📋 構想

狙い: 段階的詳細化（概念データモデル→Javaエンティティ→テーブル定義など）には、機械的に置き換え可能な領域が一定数ある（例: 「ユーザ名: 4〜100文字の文字列」→ `String`＋`@Size(min=4, max=100)` → `varchar(100)`）。これをLLMではなく**宣言的・決定論的なルール**で導出し、導出元の変更が参照時に自動反映される状態を作る。アーキテクチャの先例は揃っている: 決定論的導出のパターンは派生スキーマ（R11-03: ロード時コンパイル・読み取り専用・`noteDiskChanges` での再導出）、参照時解決の器はビュー機構（ARCHITECTURE §4.14: データを持たない射影。バックリンク列＝派生表示列の先例）、写像語彙は `DeriveTypeRule` / skill列マッピング（path / map / default・`{パス}` プレースホルダ）。欠けているのは「値レベルの決定論的変換」の一級語彙と、導出の材料になる機械可読な制約の2点。

方針（検討済みの設計境界）:

- **導出結果は原則永続化しない**: 表示層の射影（計算列）とエクスポートで受ける。仮想派生文書（`derive:` の文書版）は、原本主義と索引・カタログの「ファイル実在」前提を崩すため採らない。
- **実体化する下流**（テーブル定義書のように手書き項目・意図的上書きが本質的にある文書）は「宣言値（原本）＞導出既定値」の**フィールド単位**合成とし、不一致はドリフト検証で可視化する（黙って書き換えない）。
- **変換は宣言に閉じる**: lookup（ref の前方トラバース）＋テンプレート（`{パス}` 置換）＋値辞書（map）＋default のみ。任意式・コード実行は導入しない（kind: run の明示許可制の境界を維持）。
- **命名変換（論理名→物理名）は計算しない**: 日本語→英語は決定論的でない（＝翻訳）ため、物理名は設計判断としてデータに書く（AI生成による一括起案は既存機能で可能）。

### P25: スキーマ・リファクタリング（スキーマ変更への既存文書の追随） ✅ 完了（2026-08-13）

狙い: スキーマ定義の変更（フィールド改名・移動・順序変更など）に、既存文書と周辺の消費者（ビュー・宣言）を**1つの変更セット**で追随させる。方式は「操作ベース」——スキーマ差分からの推測（改名と削除＋追加が判別不能）は採らず、明示的なリファクタリング操作が生成器（`Plan` = 変更セット＋警告＋サマリ）を通って既存の `Workspace.apply` で適用される。ID改名（EntityOps。R21-02）・ファイル移動（DocMove。R21-03）と同型で、**新しい書込経路は作らない**。`_schemas` はエージェント書込不可のため本機能は人間専用。

**設計上の決定（2026-08-13 方針承認時）**:

### P31: スキーマの値に式を書く（値の式を、検査の外でも使う） 🚧 着手（2026-09-23 オーナー決定「その方針で進める」＝判断点 E-01〜09 は推奨のとおり。R31-01〜03 と R31-05〔式を受け取る項目のメタ管理〕を実装・R31-04 は個別判断）

> **位置づけ（2026-09-23 オーナーの要望）**: スキーマでの値の表現に式を使えるようにする。応用の1つ目は、自動ファイル生成（詳細文書の作成）のファイル名に要素の項目の値を使えること——今は `{id}` しか書けず不便。式そのものは検査の `check` に書ける「値の式」（`schema/ValueExpr.kt`。P29 Phase 6・R29-11）が既にあるので、**新しい式言語を作らず、この値の式を検査の外（ひな型・表示・組み立て）でも使えるようにする**のが本節の中身。P30 の R30-01 ②（値の式をひな型の中で使う＝評価がクエリの評価器に閉じている点の解消）と R30-03（`{…}` の穴埋めの実装の整理）は、この土台と重なる。**各項目の着手は、オーナーの判断を待つ**（勝手に着手しない）。

**いまあるもの（2026-09-23 の調査）**:

- **値の式**（`ValueExpr`＝読み出し `{of, in, path}`・決まった値・`format`・`map`・`first`・`length` / `upper` / `lower` / `number`・四則演算・`refCount`・`occurrenceCount`・集計）は、検査の `check` の左右にだけ書ける。評価はクエリの評価器の中（`SemanticQuery.evalExpr`＝private。束縛の組と出現の割当てを前提）に閉じている。計算そのもの（`SemanticExpression`）は純粋な関数で、どこからでも呼べる。
- **文字の穴埋め `{パス}`** は `Projection.evaluate`（値の式の `format`・ビューの計算列・変換の `$format`・テンプレートの健全性が共有）。穴はいまの要素からの相対パスで、関数は書けない。
- **新しい文書のファイル名**は、どの経路でも `パターン.replace("{id}", id)` の1式（workspace-core の `DocumentScaffolds.scaffold`）。パターンの出どころは3つ——ビューの `detail.filePattern`／`newRow.filePattern`／詳細スキーマの `match` から機械的に導いた `{ディレクトリ}{id}.yaml`（`detailPatternFromMatch`。ディレクトリにワイルドカードの無い単純な glob だけ。`**` のスキーマでは「作成先を決められません」）。中身は必須項目の初期値（`SchemaScaffold.defaultTree`）＋ ID で、**元の要素からは ID しか流れない**。
- `{id}` の単純置換は5か所（`DocumentScaffolds`・`ViewDefinitions` の代表 ID の点検・`VirtualViews` の read_view の案内・root `Cli` の `detailCreatePath`・`ViewGridPane` の新規行ダイアログ）。そのほかの穴埋め（指摘の文面 `WorkspaceChecks.renderTemplate`・専用チェッカーの文面・派生スキーマ `SchemaDerivation`・エージェントの文脈 `resolveContextTemplate`・skill 取り込みの `Importer.resolveTargetFile`＝ファイル名に使えない文字を直す前例）を合わせて約10の実装がある。

**守ること（既存の方針から導かれる制約）**:

- 式は「値1つを計算する純粋な計算」（[CORE-CALCULUS.md](../CORE-CALCULUS.md) §7）。条件分岐・利用者が定義する関数・任意のコード・**非決定的な値（今日の日付・乱数・連番）は入れない**（連番は自動採番 `IdSuggest` の領分＝作成時の入力）。
- 語彙の予算（[CONVENTIONS.md](../CONVENTIONS.md) §9）: 新しい表面語彙より既存キーの拡張。書き方は検査の値の式と同じ（別の式言語・パイプ記法 `{name|lower}` のようなミニ言語を作らない）。
- 式を読むのは、ひな型（文書の作成）・表示・組み立てだけ。**検証・走査・検査は式を読まない**（`FieldHints` の規約と同じ線）。
- 置き場は semantic-core（yaml-core に足さない）。文書の作成は `AppState.createDocumentFile`（セッションの `CreateDocument`）とエージェントの `create_document`（ステージング）のまま——新しい書込経路を作らない。
- 穴埋めの実装を増やさない（減らす）。既存の挙動を変えるときは [INTENTIONAL-DIFFS.md](intentional-diffs.md) へ先に登録する。テンプレート・サンプルの検証出力は前後で完全に一致すること（式を書かなければ、今までどおり）。

**式の書き方（提案）**: 書き方は2つで、どちらも同じ評価器（値の式）に落ちる。

1. **短い書き方**＝`{パス}` を含む文字列。`{format: その文字列}` の省略形として読む。穴は**いまの要素**の値（相対パス。`{owner.name}` のように入れ子も可）で埋める。予約の名前は `{id}`（索引の ID）と `{title}`（表示の解決結果＝`role` ＞ 予約語。`schema/DisplayCore`）の2つで、要素の項目より先に解決する（今の `{id}` の意味を保つ）。
2. **完全な書き方**＝検査の値の式そのまま（`{format: …}`・`{map: …}`・`{first: […]}`・`{lower: …}` など）。`of` を省略すると「いまの要素」（変換の `$of` 省略と同じ流儀）。`format` に **`with:`（名前を付けた値）** を足し、穴に計算した値を差し込めるようにする（CORE-CALCULUS §7 の `Format(template, expr...)` の形。`with` は語彙の `use` ＋ `with` と同じ「渡す値」の言葉）。

**具体例**（[labs/sysdev-template](../../labs/sysdev-template) の画面一覧 → 画面設計書）:

入力（`30_basic-design/screen-list.yaml`。定義出現）:

```yaml
screens:
  - id: SCR-ROOM-LIST
    name: 空き状況照会画面
    domain: 予約
    derived_from: [UA-003]
```

定義①（`_schemas/screen-design.yaml`。短い書き方）:

```yaml
id: screen-design
match: 40_detail-design/screens/*.{yaml,yml}
filePattern: "40_detail-design/screens/{id}_{name}.yaml"
```

出力①: 検証パネルの「詳細文書を作成: SCR-ROOM-LIST（screen-design）」→ `40_detail-design/screens/SCR-ROOM-LIST_空き状況照会画面.yaml`（`name` が未記入なら「ファイル名の穴 {name} が埋まりません」で作成をエラーにする）。

定義②（完全な書き方。ドメインごとのディレクトリへ振り分け・辞書で英名に）:

```yaml
match: 40_detail-design/screens/**/*.{yaml,yml}
filePattern:
  format: "40_detail-design/screens/{dir}/{id}.yaml"
  with:
    dir: {map: {path: domain}, using: {予約: reservation, 会議室: room}}
```

出力②: `40_detail-design/screens/reservation/SCR-ROOM-LIST.yaml`（`match` が `**` でも作成先を決められる＝今の `detailPatternFromMatch` の制限が消える）。
