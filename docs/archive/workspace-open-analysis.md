# ワークスペースを開く処理の分析

2026-11-12、コミット `63b965b`（開く処理の時間の記録を足した版）で、冒険者ギルドの試作（`labs/adventurers-guild` の写し）を画面で開く処理を調べた。
製品コードは変えていない。一時の計数・計時は調査の後に外した。対策は案を比べただけで、採用は決めていない（devtrack のテーマ T-04）。

## 結論

1. 時間の大半は、初めて動くコードの暖まり（JIT のコンパイル前の実行・クラスの初期化）。同じ JVM で同じワークスペースを続けて開くと、クリックから最初の描画まで 2.79 → 1.04 → 0.77 秒、4.08 → 0.97 → 0.85 秒になった。
2. 暖まった後にも残る正味の仕事は、読み込み約 0.5 秒・画面の状態を戻す約 0.05 秒・ダッシュボードの組み立てと配置・描画で約 0.25 秒。
3. 同じ本文の解析・書き出し・読み直しが多い。最初の描画までに SnakeYAML に通す量は、全文書を 1 回ずつ解析する量の約 5 倍。冷えた JVM では余分な処理の 1 回が、暖まった後の約 3〜4 倍の時間になる。
4. 読み込みは 1 本のスレッドで順に進む。文書ごとの解析・書き出し・検証は互いに独立で、組込みスキーマの組み立てはワークスペースの本文に依存しない。
5. 画面のスレッドで、ビュー定義の読み直し（最初の描画までに 2 回）とダッシュボードの集計を行う（冷えた JVM で合わせて 0.4 秒前後）。
6. クラスの共有アーカイブ（AppCDS）は、この環境ではばらつきの中に収まり、効果を確かめられなかった。

## 測定の条件

- Linux（4 コア・15 GiB）・Xvfb の仮想画面・OpenJDK 21・既定の JVM 設定。配布物も JVM オプションを指定していない。
- ワークスペースは YAML 584 件。業務データ（`guild/`）499 件・約 175 KB、スキーマ 36 件・約 300 KB、ビュー定義 47 件・約 90 KB、シナリオ 1 件。
- 時間は `Timings`（`.yde/state/timings.log`・CLI の `--timings`）、JFR（profile 設定）、クラスの読み込みの記録（`-Xlog:class+load`）で測った。
  呼び出しの回数と呼び手は、一時の計数（`StackWalker` で呼び手を 3 段まで数える）で数えた。
- 起動の形は 2 つ。引数でワークスペースを渡す起動と、スタート画面を出して 8 秒後に開く起動（オーナーの使い方に近い）。
- 画面の部品の時間は、組み立ての中の処理を一時の計時で囲んで測った。OS のファイルキャッシュは消していない。
- 「時間の流れ」と「JVM の設定を変えた実験」は、呼び手を数える計数を入れたまま測った（その分だけ少し遅い）。「冷えた JVM と暖まった JVM」の最初の表は計数を切って測った。

## 処理の流れと依存

```
ファイルの一覧と本文 ─┬─ 文書の解析（全件） ─┬─ スキーマの割当 ─ 保存基準の書き出し ─ 構造の検証 ─ 意味の導出 ─ 索引
                      └─ スキーマ文書の解析 ─┘（導出スキーマの展開だけが文書の木を使う）
組込みスキーマ（構成だけに依存）─────────────┘
  → 切り替え（画面）→ 画面の状態を戻す（既定のダッシュボードを探すためのビュー定義の読み込み）
  → 組み立て（ビュー定義の読み込み → ダッシュボードの集計 → 業務の流れ）→ 配置と描画 → 図の配置（背景）
```

文書ごとの解析・書き出し・構造の検証は互いに独立している。組込みスキーマは本文の読み取りと並べられる。
スキーマ文書の解析が文書全体を待つのは、導出スキーマの展開のためだけ。

## 対策の案

比べただけで、どれも採用していない。見込みは上の測定からの概算で、測っていない。

| 案 | 内容 | 見込み | 気をつけること |
|---|---|---|---|
| A1 | 生の値への解析を 1 回にする（組み立てたノードから値を作る） | 定義の読み込みの解析が半分。冷えた読み込みで 0.15〜0.2 秒 | 数値のキー・日付など、`load` と同じ値になること |
| A2 | スキーマ文書の解析を 1 回にする（文書として読んだ木から生の値を作る） | A1 と合わせてスキーマ文書の解析の約 7 割 | 同上。スキーマ文書の読み取りの入口が増えないようにする |
| A3 | 組込みスキーマをプロセスで覚える（構成ごと） | 2 回目以降の開く処理で 0.04〜0.4 秒。初回は変わらない | 覚えを鍵（構成・拡張の種類）で分ける |
| A4 | ビュー定義をセッションの木から 1 回だけ組み立て、版ごとに画面で共有する | 開くときの画面のスレッドで 0.15〜0.2 秒。編集のたびの読み直しも減る | 未保存の編集を重ねた版と、ディスクの版を取り違えない |
| A5 | 保存基準の書き出しを、編集した文書だけにする | 冷えた読み込みで 0.15〜0.19 秒 | 読み込んだ木をその場で書き換えないこと（copy-on-write の規律）を前提にする |
| A6 | 構造の検証を、使うときに計算する | 冷えた読み込みで 0.28〜0.33 秒 | `requireValid`（全文書の誤りで適用を止める）の意味を保つ |
| A7 | 図の配置の 2 回目をなくす | 描画の後の CPU の取り合い 0.5 秒 | 原因を確かめてから |
| B1 | ダッシュボードの集計と業務の流れを背景で計算し、計算中の表示を出す | 最初の描画が 0.2〜0.35 秒早まる。中身が出るまでの時間は変わらない | 画面の購読の規律（版の鍵）を保つ |
| B2 | 既定のダッシュボード探しを読み込みの段（IO）で済ませる | 画面のスレッドで 0.1 秒前後 | A4 とまとめる |
| C1 | 組込みスキーマ・本文の解析・スキーマ文書の解析を並行にする | 冷えた読み込みで 0.3〜0.4 秒 | 誤りの並び・Map の順を入力の順に保つ |
| C2 | 文書ごとの解析・書き出し・構造の検証を並列にする | 冷えた読み込みで 0.2〜0.4 秒 | 同上。共有の lazy のスレッド安全 |
| D1 | 暖機: スタート画面の間に、組込みの見本を背景で読み込んで捨てる | 要実験（見本が小さいと JIT が十分に進まない） | 利用者のデータは読まない |
| D2 | 先読み: スタート画面の間に最近のワークスペースを読み込み、開くときに変わっていなければ使う | 当たれば読み込みが丸ごと消える。画面の組み立ては冷えたままなので、クリックから描画まで 1〜1.5 秒 | 所有権（いまは所有権を取ってから読む）・メモリ・選ばれなかったときの無駄 |
| E1 | AppCDS | この環境では確かめられなかった | — |
| E2 | C1 だけでコンパイルする | 0.2〜0.5 秒ほど速い可能性 | 長く使うときの速さが落ちる |
| E3 | JDK 25 の AOT キャッシュ（JEP 483・515） | 暖まりそのものを縮める仕組み。未検証（この環境では JDK 25 を取得できなかった） | ツールチェーンを 21 から 25 へ上げる判断と、Compose・Skiko の動作確認 |
| F | 読み込み中もワークスペースの枠を先に出し、進み具合を見せる | 体感だけ。合計は変わらない | — |

A1・A2・A5・A6 を重ねると、冷えた読み込み 1.6〜2.2 秒が 1.0〜1.3 秒になる見込み。A4・B1・B2 で画面のスレッドの 0.4 秒前後が 0.1 秒前後になる。
クリックから最初の描画まで 2.8〜4.1 秒が、2 秒前後になる見込み。D2 が当たれば 1〜1.5 秒になる。
D1・D2 は、引数で開く起動と、スタート画面にいる時間が短いときは効かない。画面の初回の組み立て（読み込みの後に初めて読むクラス約 1,800 個・初めて動く Compose のコード）は、どの案でも暖められない。

## 手元の端末での確かめ方

オーナーの端末（Windows）で何度か開き、`.yde/state/timings.log` の記録を比べる。
見出しの「JVM の起動から」で、アプリを起動して最初に開いた記録と、2 回目以降の記録を見分ける。
2026-11-03 の調査（[workspace-load-investigation.md](workspace-load-investigation.md)）では、Windows ではファイルの列挙と実パスの確認が重かった。「ファイルの一覧と本文の読み取り」の段がこの記録より大きければ、その経路をもう一度疑う。

## 追記: ファイルの段で決めたこと

2026-11-13、オーナーの判断で G1 を採り、G3 は採らないことにした。「対象の実パスは本文を読む直前に確かめる」決まりを守る。
G1 と G3 は、どの確認で守るかが逆向き（G1 は読む直前の確認、G3 は一覧のときのフォルダの確認）なので、G1 の後に G3 を足す道は取らない。

- 全読込で、リンクでない YAML の実パスは一覧では確かめず、読む直前の 1 回だけ確かめる。一覧で確かめるのは、フォルダ・リンクのファイル・Markdown だけ。
- 確認の回数は、この記録のワークスペースで 1,194 回（フォルダ 23・ファイル 587・読む直前 584）から 610 回（フォルダ 23・Markdown 3・読む直前 584）になった。
- 読む直前に確かめられない文書は、読まずに一覧から外して開く処理を続ける。これまでは、一覧の後に外へ差し替わった文書があると開く処理全体が失敗していた。
- Windows での効果は、オーナーの次の `timings.log`（ファイルの段の細かい区切りつき）で確かめる。
