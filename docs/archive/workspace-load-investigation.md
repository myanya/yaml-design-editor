# ワークスペース読込の性能調査

2026-11-03、コミット `0f60028` を対象に、ファイルが多いとき、特に `samples/orders` を開く待ち時間を調査した。製品コードの変更は行っていない。

## 結論

この Windows 環境では、繰り返すファイル列挙・本文読込と、それぞれに伴う実パス確認が主要な負担になっている。
`orders` の YAML は190件だが、カーネルの初期化だけでストアの列挙が2回、読出要求が387回ある。画面用の一覧・更新時刻の準備を含めると、ディレクトリ走査は6回になる。
画面の初期化後にも、監視の取りこぼしを防ぐ全件照合を画面の所有スレッドで実行しており、操作開始時の引っかかりを増やす。

読込時間には大きなばらつきがあった。遅い計測では `orders` の準備に約5〜7秒、後続の別 JVM では開く処理全体が約0.76〜0.85秒だった。
OS のキャッシュ・外部負荷・ファイル監視ソフト等の影響は分離していないため、どの環境でも一定の秒数かかるとは結論していない。一方、重複処理はコードと呼出回数の両方で確認できた。
内訳を再計測した際も、同一 JVM 内でカーネル読込が0.96 → 1.94 → 2.96秒、ストア列挙・読出しが0.49 → 1.47 → 2.58秒と変動した。「何度か開けば必ず速くなる」という性質も確認できていない。

## 測定条件

- Windows、リポジトリ内のサンプルを読取専用で使用、JDK 21、Gradle のテスト JVM のヒープ上限2GiB。
- Gradle 起動・コンパイル時間を除き、`System.nanoTime()` で処理本体だけを計測。
- `DocumentSession.prepareReload` → `WorkspaceSession.fork` → `activateWorkspace` を実行。Compose の描画・ダッシュボード集計・アプリ全体の起動時間は含まない。
- 最初の計測は JFR を併用して同じ JVM 内で4回ずつ実行。続いて JFR なしで内訳と読込直後の確認を測定。
- 「最初」は各テスト JVM での最初の呼出しであり、OS のファイルキャッシュを消した測定ではない。
- 一時的な計測コード・CSV・JFR・実行ログは `scratchpad/workspace-load/` で扱い、調査完了時に除去した。通常のソースセット・ビルド設定には追加していない。

## コード上の原因

### 実パス確認の反復

`WorkspacePaths.resolve` は呼出しごとにルートの `toRealPath()` と、対象または存在する親の `toRealPath()` を実行する。
`FileSystemDocumentStore` は列挙時の各ディレクトリ・YAMLと、本文を読むたびにこの確認を行う。`WorkspaceScan.walk` も同じ経路を使う。
ルートが同じでも毎回解決し直し、Windows のファイルシステム照会が積み上がる。
この境界確認とストアの列挙・読込への接続は、2026-10-15 のコミット `56993fd` で導入されていた。変更前後の比較測定は行っておらず、導入時の性能差までは確定していない。

### 一覧と本文の再取得

`WorkspaceReader.load` は一覧を取得して本文を読み、スキーマ本文をもう一度ストアから読む。
その後 `WorkspaceSession` の初期化が `refreshStoreTexts` で一覧と全本文を再取得する。
`Workspace.refresh` と `DocumentSession.prepareReload` はさらに、YAML・Markdown・台帳外YAML・更新時刻のために走査する。
レガシー構成では `WorkspaceReader.detectLayout` の構成判定にも列挙が必要となり、ストアの列挙は3回になる。

### 読込直後の画面スレッド上の照合

`DesktopRuntime.openWorkspace` の準備は IO スレッドで行われるが、`WorkspaceJobs` は監視登録後、所有スレッドに戻って `poll(null)` を実行する。
`AppState.noteFileEvents` → `DocumentSession.pollExternalChanges` は一覧と更新時刻を取り直し、変更時刻が同じでも `WorkspaceSession.externalChanges` で既知文書の本文を全件読む。
今回の速い状態でも約0.18〜0.21秒を要した。遅いファイルシステム状態での追加時間、実画面での停止時間は未測定。

### その他の負担

- `BuiltinSchemaResources.kernelSchemas` は開くたびに同梱の8スキーマを読み直してパースする。詳細計測の `orders` では最初が1.09秒、後続が0.09〜0.24秒だった。
- `WorkspaceReader.load` は全文書を YAML に再出力して保存基準を作る。`fork` も `dirtyDocuments` で全件を再出力するため、画面の所有スレッド側に件数比例の負担が残る。
- `DocumentSession.editorOnlyFilesOf` は `filter` の要素ごとに `cw.files.toSet()` を作るため、台帳宣言がある場合に二重ループ相当になる。単独の所要時間は未分離であり、今回の主因とは断定しない。

## 改善の優先順位

1. 読込時の一覧・本文・更新時刻を一度取得した結果から配る。保存基準用の再読込と画面用の再走査を減らし、同じ読取時点の内容を保つ。
2. ルート実パス等を一回の読込操作内で再利用する。対象の外部リンク拒否は維持し、書込時や別操作まで無期限に判定を使い回さない。
3. 監視開始直後の照合を IO 側で準備し、結果の採用を所有スレッドへ戻す。読込から監視開始までの変更を取りこぼさない設計は維持する。
4. 組込みスキーマの再利用、未変更文書の dirty 判定の再利用、台帳内ファイル集合の事前生成を検討する。

改善後の短縮量は未測定。安全な読込スナップショット、未保存編集、外部変更検出、リンク境界の意味を保った実装と回帰検証が必要。

## 検証

一時的な計測タスク4回、通常設定での `./gradlew test`、`scripts/docs-lint.sh`、差分の空白チェックが成功した。
文書チェックには既存の目安の指摘が98件あり、失敗は無かった。製品の挙動は変更していないため、機能索引・マニュアル・現行アーキテクチャの更新は不要と判断した。
