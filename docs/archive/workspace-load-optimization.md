# ワークスペース読込の最適化と再測定

2026-11-03、[読込の調査](workspace-load-investigation.md)（UX-244）に続き、ファイルアクセスの境界検査を保ちながら重複した処理を減らした。比較元はコミット `0f60028`、比較先は今回の変更をビルドしたもの。

## 結果

`orders` の読込準備の中央値は2.32秒から0.90秒へ、約61%短縮した。処理時間のばらつきは残っており、すべての起動で同じ秒数になるという結果ではない。

| 対象 | YAML件数 | 修正前の中央値 | 修正後の中央値 | 短縮率 | 中央値の対象回数（各版） |
|---|---:|---:|---:|---:|---:|
| samples/orders | 190 | 2,323.1ms | 900.6ms | 61.2% | 10回 |
| Bench.generate の合成データ | 1,035 | 46,310.9ms | 5,005.5ms | 89.2% | 3回 |

中央値は各 JVM の最初の回を除いたもの。合成データは修正前→修正後の1組だけで、順番を逆にした測定はしていないため参考値とする。対象は読込準備・編集用セッションの作成・採用であり、Compose の描画・ダッシュボードの集計・アプリの起動時間は含めない。

## 変更

- `FileSystemDocumentStore.capture` が YAML・Markdown・更新時刻を1回の走査で取得する。`Workspace` と `DocumentSession.prepareReload` はその一覧を使うため、`orders` の準備で6回あった走査が1回になった。
- YAML の本文は一度読み、パース・スキーマ構築・保存と外部変更の基準に共有する。調査時のカーネル初期化は190件にストア読出要求387回だったが、今回の全読込では190件の本文を各1回読む。これとは別に、アプリの構成判定は従来の境界確認のため構成ファイルを読む。
- `ReadBoundary` がルートの実パスを一回の読込操作内で共有する。個別の対象の実パス確認は続ける。
- 編集用セッションの `fork` と、監視登録直後の本文照合を IO スレッドで実行する。背景へ渡すのはパスと原文の写しで、可変のセッションや文書は共有しない。結果はワークスペースと世代が一致するときに所有スレッドで既存の取り込み経路へ渡す。
- 台帳外ファイルの抽出で、比較用の集合をファイルごとに作り直していた処理を一度にした。

本文と保存基準を共有することで、パース後・基準の再読込前に外部編集された場合も、画面の内容と異なる本文を保存基準にしてしまわない。一覧の分類・並び順、隠しファイルの扱いは従来の走査と比較して検証した。

## ファイルアクセスの安全性

- ルートの実パスを保持するのは一回の列挙・読込の間だけ。ストアに永続キャッシュを持たず、別の読込や書込・削除・移動では新たに境界を解決する。
- 列挙時に許可した対象でも、本文を読む直前に実パスを再解決する。存在しない書込先は既存の親まで確認し、領域外や壊れたリンクを拒否する規則を保つ。
- 親のジャンクションを内側から外側に差し替える場合と、読込途中にルート自体を外側のジャンクションに差し替える場合をテストした。開始時の境界外は拒否され、外部の目印ファイルが上書きされないことを確認した。
- 構成ファイルの外部リンクを拒否する入口、AI の書込先にリンクを許可しない条件、保存直前の内容照合は維持した。

検査と実アクセスの間を OS の単一操作として保証する仕組みを新設したものではない。変更したのは重複取得と共有する範囲であり、対象の検査結果を保存して後のアクセスを許可する方式にはしていない。

## 測定条件と内訳

- 同じ Windows 環境、Amazon Corretto JDK 21、ヒープ上限2GiB。同じ実行権限で、修正前後のアプリとコアの JAR を別々に固定して実行した。依存ライブラリは共通。
- `System.nanoTime()` で `DocumentSession.prepareReload` → `WorkspaceSession.fork` → `activateWorkspace` を計測。Gradle・コンパイル・Java のソース起動準備は計測外。JFR は併用せず、計測中にビルドやテストは走らせていない。
- `orders` は「修正前1・修正後1・修正後2・修正前2」の4プロセスで各6回。各プロセスの最初の1回を別記し、残り5回ずつを版ごとに合わせた。
- 合成データは `Bench.generate(path, 64)`（1,035 YAML・7,499行・4,237エンティティ）。同じ生成先を修正前後で各4回読み、最初の1回を別記した。
- OS のファイルキャッシュを消していない。OS・外部負荷・監視ソフト等の影響を分離していない。合成データは `orders` とディレクトリ構造も異なるため、件数だけの比較には使わない。

| 対象・版 | 各 JVM の最初の回 | 中央値に使った回の最小〜最大 |
|---|---:|---:|
| orders 修正前 | 1,694.3 / 1,769.3ms | 713.2〜6,711.0ms |
| orders 修正後 | 1,279.6 / 1,415.8ms | 257.5〜1,102.9ms |
| 合成データ 修正前 | 34,412.1ms | 12,125.2〜47,913.5ms |
| 合成データ 修正後 | 2,038.1ms | 1,037.5〜5,843.0ms |

読込直後の変更照合も別に測った。修正前は `pollExternalChanges(true)`、修正後は `prepareDiskCheck().changedFiles()` の処理時間で、実画面の停止時間ではない。

| 対象 | 修正前の中央値 | 修正後の中央値 |
|---|---:|---:|
| orders | 680.8ms | 664.7ms |
| 合成データ | 11,071.4ms | 4,154.1ms |

`orders` の照合自体の時間はほぼ変わらない。画面の所有スレッドから IO へ移したことがこの部分の改善であり、実画面の応答時間は今回測定していない。変更があれば取り込みは所有スレッドで行う。

## 回帰検証と残る範囲

`./gradlew test --no-daemon --console=plain` は全モジュールで成功した（8分17秒）。文書更新後の `DocReferencesTest` と `scripts/docs-lint.sh` も失敗なし（文書の目安の指摘は既存の98件）。

- `DocumentStoreTest`: 外部リンクの除外、親リンク・ルートの差し替え、対象外への書込拒否、YAML・Markdown・時刻の一覧。
- `SessionForkTest`: 各本文を一度だけ読み、読込途中に外部変更があってもパースと保存基準が一致すること。壊れた YAML の原文も保持し、競合時は外部の本文を上書きしないこと。
- `WorkspaceLoadingTest`: 従来の一覧・分類・並び順・時刻との一致、同時刻の上書きと作成・削除、背景用の原文がセッションの再読込で変わらないこと。
- `DesktopRuntimeTest`: 監視登録の間の同時刻上書き、未保存編集の保持と競合通知、切替と終了の所有関係。

組込みスキーマの構築や dirty 判定の再利用は変更していない。構成ファイルだけを同じ更新時刻で上書きした場合の既存の取り込み経路には別の懸念があり、追加調査を [指摘台帳](../BACKLOG.md) の UX-245 に記録した。

測定用コード・固定 JAR・合成データ・ログは `scratchpad/load-optimization/` で扱い、完了時に除去した。製品のソースセットとビルド設定には計測用コードを追加していない。
