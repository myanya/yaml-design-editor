2026-10-23。通常は約1,000ファイル、参考ソースを含む場合は約100,000ファイルを扱い、ファイル整理のたびにパス依存の定義を直す負担を減らすための変更。
利用者から、段階3まで中断せず開発・テスト・段階別コミットを行い、途中の判断は目的に沿って決めて報告する指示を受けた。

## 課題と採用した判断

| 課題 | 判断と理由 |
|---|---|
| 全ファイルを表示すると索引が肥大化する | 一覧を独立させ、必要な枝だけ読む。表示設定を変更しても台帳の対象は増やさない |
| 展開の覚えを共有設定へ書くか | 利用者の Preferences にワークスペース別で保存する。定義ファイルや Git の差分を増やさない |
| フォルダーの移動でパターンの意味が変わる | 全体移動は接頭辞を追随させ、一部移動は旧パターンと新しい対象の和を提案する。将来の対象範囲は差分で確認できるようにする |
| 書込権限や台帳範囲まで自動で広げてよいか | 通常の定義追随とは別に、明示チェックで採用する |
| 自由文やコードの import をどう直すか | 意味が分かる定義・型付き値・通常の Markdown リンクに絞る。未対応の言及は警告し、参考ソースを書き換えない |
| 外部変更を消してしまう可能性 | 計画前の原文照合と、適用・Undo/Redo 前の内容ハッシュを使い、競合を拒否する |
| 削除と履歴 | `.yde-trash` に退避し、セッションの単一履歴で戻す。再起動後も退避物は残すが履歴は永続化しない |
| 大量の参考ソースの本文検索 | 常設の本文索引を作らず都度検索する。範囲・読込量・件数・経過時間を制限し、途中結果と中止を提供する |
| 小ファイルでは容量上限だけでは時間を抑えられない | 既定30秒、120秒、時間制限なしを選べるようにした。上限時は一部の結果であると明示する |
| クラス名・メソッド名を扱いたい | 対応言語の宣言候補を読み、原文と切り離した新規 YAML に保存する。型解決・呼出関係は推測しない |

## 設計上の位置づけ

配置依存の修正は既存 Rewrite／Patch／Transaction に載せ、履歴は WorkspaceSession が所有する。一般ファイルの物理操作は ADR-0011 で拡張した。
一覧・検索はファイルシステムの射影。ソース構造の読取は外部入力から Term へのアダプタであり、既存 YAML の意味評価や Construct を重複実装しない。
構造情報の保存は既存の文書作成経路を通す。索引・検証に使う意味は、保存先のスキーマで利用者が定義する。

## 確認の範囲と制約

段階1と2でそれぞれ全テストとドキュメント検査を通してからコミットした。
段階3では移動の失敗復元・外部競合・一般ファイルの部分移動・複数削除・構造保存・本文検索の制限・ナビゲーションを自動テストで確認した。
最終の `build runCli --args=version` は成功。全1,294テストに失敗・エラー・スキップなし。docs-lint と git diff --check も通過した。
画面を実際に操作するテストは実施していない。今回の環境には Hot Reload の画面操作ツールが公開されていないため、操作手順を UX-SCENARIOS に残した。

ファイル操作中の例外は復元するが、電源断・強制終了を跨ぐ原子性は保証しない。構造抽出は軽量な宣言候補であり、言語構文の完全な解析ではない。
計測は一時領域の小さな Kotlin ファイルを対象とする。10万件の YAML を解析・検証する性能や、GUI の描画時間を示すものではない。

## 性能計測

Windows・JDK 21、100ファイルずつフォルダーを分けた一時領域で `fileTreeBenchmark` を実行した。単回の観測値であり、OSキャッシュ・ストレージ負荷に依存する。
同時に中断した旧計測の一時領域を整理していたため、通常の利用環境と同一のI/O条件ではない。

| 項目 | 1,000ファイル | 100,000ファイル |
|---|---:|---:|
| ルート直下の一覧取得 | 12 ms | 1 ms未満 |
| コアのワークスペース読込 | 612 ms | 3,010 ms |
| AppState のワークスペース読込 | 160 ms | 7,287 ms |
| 全体の名前検索 | 71 ms | 5,873 ms |
| 本文検索 | 25,826 ms・1,002件確認・完了 | 30,024 ms・1,014件確認・時間上限で一部の結果 |

コア読込の後に AppState を読んでいるため、1,000件側はウォームアップとキャッシュの影響を受けている。追加した構成YAMLと文書YAMLも本文検索の件数に含む。
全件本文検索の先行試行ではファイルを開くOS呼出しで長く待つことを確認し、中断した。時間上限を設け、検索範囲を狭めて使える設計を採用した。
初期実装の小ファイル読込では上限分のメモリ確保が発生する経路を改めた。ただし試行間の本文検索時間には大きな振れがあり、変更単体の速度向上率は断定しない。

## 試し方

1. アプリでワークスペースを開き、ファイルペインの「表示 → すべての形式」を有効にする。フォルダーを展開して再起動し、展開が戻ることを見る。
2. Ctrl／Shift で複数を選択して「移動」、またはフォルダーへドラッグする。「影響を確認」で match／fileGlob 等の差分を見て適用し、Ctrl+Z で配置と定義が一緒に戻ることを見る。
3. 「表示 → 本文を検索」で語を入れ、範囲・容量・時間を切り替える。結果から行へ移動し、中止や上限で一部の結果と分かるか確認する。
4. Kotlin・Java・Python・JavaScript／TypeScript のファイルを開き、「構造」で宣言へ移動する。「構造を保存…」で別 YAML を作成し、ソースの原文が変わっていないことを見る。

確認してほしい点は、整理の差分が判断しやすいか、複数選択とドラッグが自然か、検索を待つ間の表示が分かるか、構造候補の精度が資料閲覧に十分か。
