# ID とリンクの仕組み


## ID の索引化

ワークスペース内のYAMLをスキャンし、`id -> [(ファイル, パス, タイトル, schemaId, documentId)]` の索引を構築します。IDとして認識されるのは:

- スキーマで `type: id` と定義されたフィールドの値
- スキーマの有無に関わらず、キー名が **`id`** であるスカラー値（ネストした要素でも可）

同じIDは複数ドキュメントに定義できます。それらは段階的詳細化された同一論理要素の複数出現として索引化されます。同一ドキュメント内の重複だけが検証エラーです。ジャンプ時に複数出現がある場合は選択ダイアログを表示します。

スキーマの `id` は参照スコープに使う安定識別子、`name` は表示専用です。`id` を省略した場合はスキーマファイル名（拡張子なし）を使います。

ドキュメントIDは任意で次のように宣言できます。省略時はワークスペース相対パスを使います。

```yaml
_document:
  id: system-overview
  name: システム構想
  description: |
    システムの目的、利用者、主要な機能領域を定義する文書。
    後続の要求・設計文書が前提とする全体像を示す。
```

`name` は画面の文書ヘッダーに表示する任意の文書名です。省略時は従来どおりワークスペース相対パスを表示します。
`description` は、全文を読まずに文書の目的と内容を判断するための任意の概要です。フォーム先頭の「文書メタデータ」で文書名と概要を編集できます。これらは将来、LLMへ文書コンテキストを渡す際の要約情報としても利用できます。

## 表示解決（タイトル・要約の決まり方）

要素（IDを持つオブジェクトなど）を1行で見せる場面——畳み込みヘッダ・参照候補・バックリンク・ID横ぐしビュー・ビューグリッド・ID検索・エージェントの `related` 要約——は、すべて同じ**表示解決**の結果を使います（人間とAIが同じ要約を見ます）。タイトル・サブタイトルは次の優先順位で決まります。

1. **スキーマの `role` 指定**: `role: title` / `role: subtitle` を付けたフィールドの値（`$ref` 先の指定も合成され、library 共有にも乗ります）
2. **予約語**: タイトルは `title` → `name` → `label`、サブタイトルは `description` → `summary` の先勝ち
3. **id**: タイトルがなければ ID を表示
4. **キー数の要約**: どれもなければ「（n項目）」

つまり `name` や `title` という名前で項目を持つ文書はそのまま読みやすく表示され、独自の項目名（例 `件名`）をタイトルにしたい場合だけスキーマに `role: title` を1行足せば、参照候補から一覧・畳み込みヘッダまで**全画面に一括で**効きます。

補足:

- **タイトルの借用**: 要素自身にタイトルがなくても、同じ論理IDの他出現（定義側の文書）にタイトルがあれば画面上はそれを借りて表示します。id しか書かない写像行・詳細行の畳みヘッダでも「FLD-001 ユーザー名」のように読めます。
- **サブタイトルの併記**: 畳み込みヘッダは「ID タイトル — サブタイトル（n項目）」の形で、`role: subtitle`（または description / summary）も表示します。
- **親ノード情報**: エンティティページの各出現カードには、その出現がどの親要素（テーブル定義・一覧など）の配下にあるかが「親: …」として表示されます。

## 段階的詳細化の規約（1:1 の詳細化と 1:N の分裂）

工程をまたいで文書を詳細化していく運用では、次の2つの規約を使い分けます。

- **1:1 の詳細化 = 同一ID**: 同じ論理要素を別文書でさらに詳しく書くときは、**同じIDをそのまま使います**（例: 画面一覧の `SCR-LOGIN` と画面詳細文書の `SCR-LOGIN`）。出現はID横ぐしビュー・ビューグリッドで1行に結合され、詳細文書の存在は出現ベースのカバレッジルール（`detailIn`。[schema.md](schema.md)）で機械検証できます。
- **1:N の分裂 = 新しいID＋親への参照**: 1つの要素が複数の要素へ分かれて実装されるときは（例: データモデルの1エンティティ→単票・明細の2テーブル）、分裂先に**新しいID**を与え、`type: ref`（`relation` で種別を宣言。
例 `derives`）で**親へ逆リンク**します。親側のスキーマは被参照の制約（`constraints` の `dir: in` ＋ `expect: exists`、または関係レジストリの `cardinality: {inMin: 1}`）で「全エンティティが1つ以上のテーブルから実装されること」を検証でき、ビュー定義の**バックリンク列**（`backlinks`。
[views.md](views.md)）で親→分裂先の一覧を表示できます。

sample-workspace の `models/00-data-model.yaml`（エンティティ）と `tables/`（テーブル設計。`entity` 項目で親へ逆リンク）、ビュー定義 `_views/entity-tables.yaml` がこの規約の実例です。

スキーマに**エンティティ型宣言**（`entity:`。[checks.md](checks.md)）を書くと、どの出現がそのIDの「定義（誕生）」かを機械が知り、参照ジャンプ・タイトル解決が定義出現に安定します。定義出現の欠落・競合は検証が警告します。

## 参照候補の絞り込み

`type: ref` ではID体系と探索範囲を独立して指定できます。

```yaml
type: ref
idPatterns: ["ACTOR-*", "ROLE-*"]
scope:
  schemaIds: [system-concepts, actor-detail]
  documentIds: [system-overview]
```

`idPatterns`、`schemaIds`、`documentIds`の各配列内はOR、異なる条件間はANDです。IDパターンは大文字・小文字を区別します。参照の型（`type: 名前`。[schema.md](schema.md)「型の定義」）から引き継いだ `idPatterns` と、使う側に書いた `idPatterns` は重ね合わせになり、両方に合う ID だけが候補になります（`scope` は共通部分）。条件は候補表示だけでなく参照検証にも適用されます。ID自体が存在しても条件外なら検証エラーになります。条件を省略するとワークスペース全体が対象です。

## 参照（リンク）の認識

- スキーマで `type: ref` と定義された位置の値（配列要素含む）
- スキーマ外のキーに対する**命名規約ヒューリスティクス**:
  - キー名 `ref` または `*_ref` のスカラー値
  - キー名 `refs` / `*_refs` / `depends_on` / `relates_to` 配下のスカラー配列

## リンクの機能

- **ジャンプ**: ref フィールドの「→」ボタン（クリックで「定義へ移動（ファイル）／エンティティページで開く」を選択）、右パネル「関係」タブの参照クリックで定義元ファイルを開き、該当要素をハイライト表示＆自動スクロール
- **戻る・進む**: ジャンプやファイル切替のあと、ツールバーの「←」「→」ボタン（`Alt+←` / `Alt+→`）で移動前の位置へ戻る／やり直すことができます。文書はファイルとハイライト位置、ID横ぐしビュー・ビューグリッドから飛んだ場合はそのビューと選択中IDが復元されます。**レールでのスペース切替（編集・台帳・実行・設計）と台帳のタブ切替も履歴の対象**で、横ぐしビューでのID切替、ビューグリッドのビュー切替、検証パネルからのジャンプと同様に1段ずつ戻れます（同じ場所の再選択は積まれません。履歴は最大50件。ワークスペース切替でクリアされます）
- **補完**: ref フィールドのドロップダウンで、IDパターン、スコープ、入力文字列（ID・タイトル部分一致）により候補を選択
- **ID入力支援**: id フィールドのドロップダウンに「**採番**」（既存IDと `pattern` / entity 宣言から次の連番を提案。例 `TASK-003`）と既存IDの補完（選ぶと同一IDの出現＝別文書での詳細化・写像行の入力になる）が出ます
- **未解決検出**: 索引にも編集中ドキュメントにも存在しない ID への参照は、赤枠＋検証パネルにエラー表示
- **バックリンク**: 開いているファイルの ID を参照している箇所を「関係」タブの被参照に一覧表示。参照を書いた要素のID・タイトル（表示解決の結果）を主表示にし、クリックで参照元へジャンプ
- **出現**: 右パネル「出現」タブに、文書ルートIDと同じ論理IDの全出現（段階的詳細化の各文書）とカバレッジ充足を表示。「ID横ぐしビューで全出現を編集」で横ぐしビューへ展開
- **ID 検索**: 検索・コマンド（`Ctrl+K`）から ID・タイトルで横断検索してジャンプ

> **索引と「見たまま判定」**: 索引の正はディスク上のファイルで、ワークスペースを開く、再読込、保存、外部変更検出、一括編集のタイミングで更新されます。そのうえで**画面上の参照解決・被参照・カバレッジ・検証・ID検索は、未保存の編集を重ねたオーバーレイ索引（「見たまま判定」）で行われ、保存前でも追随します**。CLI・エージェントなどのヘッドレス経路はディスク索引基準のままです。
