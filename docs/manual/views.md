# ビュー


台帳スペース（レールの「台帳」）のタブから、次の横断ビューを利用できます。

- **一覧ビュー**: ID、タイトル、状態、担当、種別、ファイルを表形式で表示し、文字列・種別・状態で絞り込み
- **一括編集**: 選択した複数ファイルのルート直下のスカラー項目を確認後に一括更新。対象キーはワークスペースの文書に現れるルート直下のスカラーキーから選択（`id`・`_document` などの予約キーと、配列・オブジェクト値の項目は対象外）
- **グラフレンズ**: エンティティグラフ（解決済みの参照の両端）を力学配置で描画します。エンティティページの「グラフで見る」で**起点の近傍**（深さ1〜2。起点の解除・深さ切替可）に絞れ、エンティティ型・関係（relation）のチェックボックスで部分グラフを切り出せます。ノードは型で色分け（凡例つき）・エッジには関係レジストリの `label` が表示され、ノードやエッジ一覧をクリックするとそのエンティティのページへ移動します。ドラッグでパン・「＋／－」でズーム
- **エンティティページ**: 同一論理IDの全出現を**エンティティ全体像**（アスペクト合成。[checks.md](checks.md)「エンティティ型宣言」の `entity.aspect` / `owns`）として1画面に集約します。ヘッダにはID・エンティティ型・タイトルと**操作メニュー**（改名／別IDへ統合／削除。
全出現・全参照を書き換える変更セットのプレビュー→適用）、本文にはアスペクト見出しつきの所有フィールド（その場で編集できます。編集は通常のフォームと同じ経路＝未保存●表示・Undo・保存がそのまま効きます）、**関係パネル**（関係ラベルでグループ化した両方向の参照。
行クリックで相手エンティティのページへ・矢印で参照箇所へ）、カバレッジ充足を表示します。アスペクト宣言のないスキーマの出現も従来どおり出現フォームで編集でき、「出現別フォームで表示」トグルで従来表示に切り替えられます。ヘッダの「すべて保存」（未保存件数つき）で複数文書の編集をページを離れずに保存できます。
台帳スペースの「エンティティ」タブ、右ペイン（インスペクタ）の「出現」タブ、検索・コマンド、ID出現候補ダイアログから開けます
- **ビューグリッド**: `_views/*.yaml` に定義した「行（論理ID）×列（各文書の項目）」の宣言的ビューを、**編集可能な一覧**として表示（後述）
- **差分**: 文書の「差分」タブで、ディスク上の保存済み内容と編集中内容を左右比較。変更行では行内の変わった箇所を文字単位で強調表示
- **最近開いたファイル**: ツールバーの履歴アイコンから直近12ファイルを再度開く。履歴はワークスペース単位で保存
- **検索・コマンド**: `Ctrl+K` で開く統合パレット。ID・タイトルでのジャンプ、ファイル検索、**本文検索**（2文字以上で発動。キー・値への部分一致。未保存の編集も対象＝「見たまま」で検索し、ヒットのクリックで該当箇所へジャンプ）、台帳ビューの切替、実行／設計スペースの表示、保存、エンティティの改名（全出現・全参照の一括書き換え。プレビュー→適用）、ワークスペースの切替（履歴からの選択・ディレクトリ選択）をキーボード中心で実行

一括編集は対象に未保存文書が含まれる場合は実行されません。実行前には確認ダイアログを表示し、変更後は索引と画面を再読込します。

## ビューグリッドとビュー定義（`_views`）

段階的詳細化（同一IDを複数文書で詳細化する運用）では、「機能一覧」と「機能ごとの詳細文書」のように情報が複数ファイルへ分かれます。ビューグリッドは、`_views/*.yaml` の**宣言的なビュー定義**に従って、それらを1つの一覧に結合して表示・編集する機能です。台帳スペースの「ビュー」タブから開きます。

- **行** = `rows.idPattern` に一致する**論理ID**。同じIDの出現が複数文書にあれば1行に結合されます。または `rows.match`（**クエリ行**。後述）でパターン照合の束縛行を行にできます（`idPattern` とは併用不可）
- **列** = 「どの出現（`schemaId` / `fileGlob` で選択）の、要素からの相対パス（`path`）」。`editable: true` の列はグリッド上で直接編集できます（文字列・数値・enum・参照などのスカラー値。配列・オブジェクトはクリックで該当文書へジャンプ）
- セルの編集は**元の文書への通常の編集**そのものです（未保存●表示・Undo・`Ctrl+S`／すべて保存・差分がそのまま使えます）。ビュー自体はデータを持ちません
- **詳細列**: `detail` に一致する出現があればリンク、なければ「作成」ボタンで `filePattern` の位置に**詳細文書をスキャフォールド**します（スキーマの必須初期値＋行のIDを設定）。`filePattern` は値の式で、`{id}` のほか行の要素の値（`{name}` など）を穴に書けます（[schema.md](schema.md)「新しい文書の置き場所とひな型」。作り先のスキーマに `scaffold` があれば、中身も元の要素から埋まります）
- **新規行**: `newRow` を定義すると、グリッドから新しい行を作れます。2つのモードがあります（併用不可）
  - **配列モード**（`file` + `path`）: 一覧文書の配列へ新しい要素を追加します（IDを入力して保存するとグリッドの行になります）
  - **ファイルモード**（`filePattern`）: 一覧文書を持たず詳細文書だけでIDを運用するレイアウト向け。IDを入力すると `{id}` を置換したパスへ**詳細文書そのものをスキャフォールド**します（スキーマの必須初期値＋入力したIDを設定。ディスクへ書かれた時点で行が現れます。行がまだ無いので、書ける穴は `{id}` だけです）
- **バックリンク列**: 列に `path` の代わりに `backlinks` を書くと、行のIDへの**被参照**（参照元要素のID・タイトル）を一覧表示します。`relation`（参照の関係種別）と `schemaIds`（参照元スキーマ）で絞り込めます。1:N詳細化（[ids.md](ids.md)）の「親から見た分裂先の一覧」に使います。派生表示のため編集はできません（クリックで参照元へジャンプ）
- **定義参照列**: 列に `label`／`path` の代わりに `definition: モジュール#定義名` を書くと、スキーマの**名前付き定義**（[schema.md](schema.md)）のセル型フィールドが列に展開され、見出し・パスがスキーマから導出されます（ID型の項目は行のID列と重複するため除かれます）。`schemaId` を併記した場合は定義名だけでも書けます（例 `definition: screen`）。列の見出しをビューへ重複記載する必要がなくなり、スキーマの変更に自動で追随します。`editable: true` は展開された全列に適用されます
- **計算列**: 列に `path` の代わりに `computed` を書くと、他の出現に書かれた**テンプレート（元値）を参照時に評価した導出値**を表示します（読み取り専用の派生表示）。段階的詳細化で機械的に導出できる値（例: 値型の `maxLength` → `varchar(100)`）を、手で転記せずルールから表示するための機構です。導出元（テンプレート・入力値）を編集すると、**保存しなくても**評価値は自動で追随します（未保存のまま確認し、OKなら保存する流れで使えます）
  - `source`（必須）: 元値を読む対象IDの出現の選択（`schemaId`／`fileGlob`）。`path` でその要素からの相対パスを指定します
  - 元値の中の `{パス}` プレースホルダは「source の要素 → `values` で選んだ出現の要素 → `lookup` の起点要素」の順で解決されます（原本に書かれた値のみを参照する1段評価。解決できないものは `{...}` のまま表示されます）
  - `lookup`（任意）: 行の出現の参照フィールド（`via`）を1回だけ辿り、**参照先のID**を対象にします（例: 属性の値型参照を辿って型写像から導出）
  - `map`（評価後の値辞書）・`default`（元値が無いときの既定値）も指定できます
  - セルをクリックすると**導出の説明**（元値 → 評価結果）と行き先の選択が表示され、**導出規則**（テンプレート）と**各入力値**（プレースホルダを解決した値の位置）のどちらへもジャンプできます。値を変えたいときは規則か入力値を通常どおり編集します（`editable` とは併用できません）。エージェント（`read_view`）・CLI（`view` の `derivation` 節）にも同じ来歴が出ます
- **状態列**: カバレッジルール（[schema.md](schema.md)）の充足状況を行ごとに表示します

```yaml
# _views/screen-catalog.yaml
id: screen-catalog
name: 画面カタログ
rows:
  idPattern: "SCR-*"                  # このIDパターンが行になる
order:
  fileGlob: todos/10-screens-list.yaml  # 一覧文書での出現順に並べる（省略時はID順）
columns:
  - label: 画面名
    fileGlob: todos/10-screens-list.yaml  # 値を取る出現（schemaId でも指定可）
    path: name                            # 出現要素からの相対パス
    editable: true
  - label: エリア
    fileGlob: "todos/screens/*.yaml"
    path: areas                           # 複合値は要約表示＋ジャンプ
  - label: 実装テーブル
    backlinks:                            # バックリンク列: この画面IDを参照している要素を一覧表示
      relation: derives                   # 参照の関係種別で絞る（省略可）
      schemaIds: [table-design]           # 参照元文書のスキーマで絞る（省略可）
detail:
  fileGlob: "todos/screens/*.yaml"        # この条件に一致する出現を「詳細」と見なす
  filePattern: "todos/screens/{id}.yaml"  # 「作成」ボタンの作成先（{id} が行のIDに置換）
newRow:
  file: todos/10-screens-list.yaml        # 「新規行」の追加先（一覧文書の配列）
  path: screens
```

一覧文書を持たないレイアウト（1詳細文書＝1ID）では、`newRow` をファイルモードにします:

```yaml
# _views/actor-list.yaml — 詳細文書だけでIDを運用する場合
id: actor-list
name: アクター一覧
rows:
  idPattern: "ACT-*"
columns:
  - label: アクター名
    schemaId: actor
    path: name
newRow:
  filePattern: "00-requirements/011-{id}.yaml"  # 「新規行」でIDを入力すると詳細文書を直接作成
```

**クエリ行**（`rows.match`）: 行を「1つのID」ではなく、**グラフパターン照合の束縛行**（結合の組）にします。「画面→uses→ユースケース」のような**多段結合の組を1行に**でき、結合先の値もセルとして表示・編集できます:

```yaml
# _views/entity-table-matrix.yaml（sample-workspace に同梱の実例）
id: entity-table-matrix
name: エンティティ×テーブル（結合）
rows:
  match:                                   # node / edge の交互連鎖（node で始まり node で終わる）
    - node: { entity: entity-model, bind: ent }   # 起点集合（entity: 型 / schema: 出現スキーマ / id: IDパターン）
    - edge: { relation: derives, dir: in }        # dir: out（その要素が直接書いた参照を辿る。既定）/ in（被参照を辿る）。via（キー名・場所）でも絞れる。contains: true は入れ子の線
    - node: { entity: table-design, bind: tbl }   # bind した束縛が結果の列になる
  # rowKey: ent                            # 行キーの束縛（省略時は先頭の bind。詳細列・状態列・新規行はこのIDに効く）
  # where:                                 # プロパティ述語（equals / exists のみ。値はいずれかの出現の該当パス）
  #   - { of: tbl, path: status, equals: draft }
  # limit: 100                             # 行数上限（既定 100）
columns:
  - { label: エンティティ名, path: name }              # of 省略 = 行キー束縛（ent）の値
  - { label: テーブル名, of: tbl, path: title, editable: true }  # of: 束縛名 = 結合先の値をセル化（編集は原本へ）
  - { label: 状態, of: tbl, path: status, editable: true }
```

- 結合により**同じIDの行が複数現れる**ことがあります（例: 1エンティティ×2テーブル = 2行）。セルの編集は従来どおり各原本文書への通常編集です
- `also:`（`{from: 束縛名, steps: [...]}`）で束縛済みノードからもう1本の連鎖を足せます（1段のみ・内部結合）。`kind: document` のノード（文書そのもの）も扱えます
- 行の並びはクエリの決定的順序（束縛名の辞書順に並べた値のID昇順）で、`order` とは併用できません。CLI `query`（[cli.md](cli.md)）で同じパターンを試作できます

計算列の例（値型台帳の制約値で、型写像のテンプレートを評価して表示する）:

```yaml
# 行 = 属性ID（FLD-*）。属性の値型参照（type）を辿り、DDL型写像のテンプレートを評価する
columns:
  - label: DDL型（導出）
    computed:
      lookup: { schemaId: concepts, via: type }   # 行の出現の ref を1ホップ辿る（省略時は行のID自身）
      source: { schemaId: ddl-mapping }           # 元値（テンプレート）を読む出現
      path: to                                    # 例: varchar({maxLength})
      values:
        - schemaId: concepts                      # {maxLength} を値型定義の値で解決する
```

sample-workspace の `_views/field-traceability.yaml`（概念→実装→DDLの項目トレーサビリティ。手書きの宣言値と導出値を並置）と `_views/value-type-mappings.yaml` が実例です。

`_views` は予約ディレクトリで、組込みスキーマによりフォーム編集・検証できます。エージェントは同じビューを `read_view` ツールで参照でき（[ai.md](ai.md)）、CLI では `view` コマンドで解決できます（[cli.md](cli.md)）。

ビュー定義はロード時に**スキーマとの整合が検査されます**（リント）。存在しないスキーマIDへの参照、スキーマから解決できない列・セクションのパス、存在しない定義参照は「定義エラー」としてビューグリッドのバナー・`read_view`・CLI `view` の一覧に表示されます（指摘があってもビュー自体は従来どおり表示されます）。スキーマを変更したときに、それを参照しているビューが黙って壊れることを防ぎます。また、`_views` の定義文書を開いている間は**右ペインの検証タブにも同じ指摘が表示され**、編集中の内容で再判定されるため、保存する前に定義の誤りへ気づけます。

また、詳細文書をフォームで開くと、上部に**「他文書での定義」ストリップ**が表示され、同じIDの一覧側の情報（名前・種別など）を参照・ジャンプできます。一覧側にある情報を詳細文書へ重複記載する必要はありません。

## 文書ビュー（`kind: document`）— フォーム表示の合成

スキーマは「データの構造と検証」を、ビューは「画面の見せ方」を受け持ちます。**文書ビュー**は `_views` のビュー定義に `kind: document` を指定したもので、特定の文書をフォームで開いたときの表示を**セクションの並び**として合成します。「内容はスキーマでチェックし、表示はビューでコントロールする」ための機構です。

- **適用先**: `match`（ファイルglob）または `schemaId`（併記時は両方に一致）。マッチする文書ビューがない文書は、従来どおりスキーマ駆動フォームで表示されます（文書ビューは足したい文書にだけ足す上書きです）。複数の定義がマッチする場合は定義ファイル名順の先勝ちです
- **`sections`**: 上から順に描画されます。各セクションは次のどちらか一方を持ちます
  - **`fields`** — スキーマ駆動フォーム。`path` を省略すると文書全体、指定するとそのパスの項目だけを表示します。編集は通常のフォームと同じ（未保存●・Undo・保存がそのまま効きます）。`include: [キー...]`（列挙した順でそのキーだけを表示）／`exclude: [キー...]`（列挙したキーを除いて表示）で表示項目を選別でき、複数の fields セクションに分ければフォームをグループ分けできます。
`definition: モジュール#定義名` を添えると「このセクションはこの名前付き定義（[schema.md](schema.md)）の構造を表示している」という宣言になり、定義が存在しなければエラー、パス先のフィールドがその定義を参照しなくなればリントが指摘します（スキーマ変更への追随検出）
  - **`backlinks`** — 文書内のIDへの**被参照表**（読み取り専用）。`idPattern` で対象IDを絞り、`relation`・`schemaIds` で参照を絞り、`columns` で参照元要素の値を列表示できます。クリックで参照元へジャンプします
- **`attachments`（要素単位アタッチ）**: セクションが文書レベルの合成であるのに対し、アタッチは**フォーム中の要素の位置**へ被参照表を差し込みます。`at` に要素パスのパターン（YPath 構文＋`[*]`＝任意のインデックス。
例 `actors[*]`）を書くと、一致する各要素の展開フォーム内（配列要素・ネスト・テーブルの行展開すべて）に、**その要素のIDへの被参照**だけを絞った表が現れます。被参照の条件（`relation`・`schemaIds`・`columns`）はセクションの `backlinks` と同じ語彙です。
IDを持たない要素には差し込まれません

たとえば「アクター定義書に、そのアクターを利用するユースケースの一覧表を足したい」とき、スキーマにはアクター定義の本質だけを書き、被参照の表はビュー側に足します:

```yaml
# _views/actor-document.yaml
id: actor-document
name: アクター定義書
kind: document
match: "00-requirements/01-actors.yaml"   # schemaId: actors でも可
sections:
  - fields: {}                       # スキーマ駆動フォーム（従来表示そのもの）
  - label: 利用するユースケース
    backlinks:                       # 被参照表: この文書のアクターIDを参照している要素の一覧
      idPattern: "ACT-*"             # 文書内の対象ID（省略時は文書内の全ID）
      relation: uses                 # 参照の関係種別で絞る（省略可）
      schemaIds: [usecases]          # 参照元文書のスキーマで絞る（省略可）
      columns:                       # 参照元要素から表示する列（省略時はID・タイトルの要約のみ）
        - label: ユースケース名
          path: name
```

文書末尾の一覧表ではなく「各アクターの展開フォームの中に、そのアクターのユースケースだけを出したい」場合は、被参照表をアタッチとして書きます:

```yaml
sections:
  - fields: {}
attachments:
  - at: "actors[*]"                  # 各アクター要素の展開フォーム内に差し込む
    label: 利用するユースケース
    backlinks:
      relation: uses
      schemaIds: [usecases]
```

被参照は、画面上は未保存の編集を含む「見たまま」（オーバーレイ索引）、`read_view`・CLI はディスク索引に基づきます。文書ビューは台帳の文書のみが対象です（`ledger` 宣言時は台帳外に適用されません）。エージェントは `read_view` に `file` を渡して同じ被参照表を座標つきで読め、CLI では `view <view-id> [file]` で解決できます（適用対象が1文書だけなら `file` は省略可）。
