# ビュー

業務の件数から対象の詳細と操作へ進む画面は [ダッシュボード](dashboards.md) を参照してください。

文書をノード・辺へ射影する画面・CLI・文書内埋め込みは [フロービュー](flow-views.md)を参照してください。


台帳スペース（レールの「台帳」）のタブから、次の横断ビューを利用できます。

- **一覧ビュー**: ID、タイトル、状態、担当、種別、ファイルを表形式で表示し、文字列・種別・状態で絞り込み。チェックと ID の列は左に固定され、横にスクロールしても見えます
- **一括編集**: 選択した複数ファイルのルート直下のスカラー項目を確認後に一括更新。対象キーはワークスペースの文書に現れるルート直下のスカラーキーから選択（`id`・`_document` などの予約キーと、配列・オブジェクト値の項目は対象外）
- **グラフレンズ**: エンティティグラフを図にします。節点はチェックしたエンティティ型のエンティティ全部（ID 一覧から。参照を持たない節点も箱だけで出ます）、辺はその間の解決済みの参照です。
型と関係（relation）の絞り込みと辺の一覧は**右パネル**の「型」「関係」「辺」のタブにあり（型の色の凡例もここ。「すべて」「すべて隠す」で一括）、図の領域は画面いっぱいに使えます。右パネルを閉じているときは図の上の「型・関係・辺 ▶」で開けます。型を 1 つから始めて少しずつ足していくと、足した型との間の線が現れます。エンティティページの「グラフで見る」で**起点の近傍**（深さ1〜2。起点の解除・深さ切替可）に絞れます。
配置は 4 つから選べます: **放射**（起点を中心に、近い順に輪で並べる。起点があるときの既定）・**階層**（参照の向きに沿って上から下へ）・**応力**（つながりの近さを距離に映す。起点が無いときの既定。150 節点までで、超えると階層に代わります）・**力学**（軽い計算）。
ノードは ID とタイトルの箱で型ごとに色分け（凡例つき）、エッジは矢印に関係レジストリの `label` を添えます。同じ 2 点間に複数の関係があれば並べて描きます。ノードやエッジ一覧をクリックするとそのエンティティのページへ移動します。
**保有**（外側の要素の中に書かれた要素。[ids.md](ids.md)「保有と所属」）は**箱の入れ子**で描きます: 画面の箱の中に画面項目の箱が入ります。入れ子の箱は畳めます（見出しの左の「▸ 件数」を押す・右クリックの「中の箱を開く」。畳んだ箱の中の要素につながる線は箱に付きます）。既定では全部畳み、起点があればその外側の箱と起点だけを開きます。「開いた箱を戻す」で既定に戻ります。関係のチェックボックスには「（保有）」の印が付き、名前は項目の `relation` か、書いている項目のキー名です。隠すと入れ子が解け、子は外側の箱になります。
見え方は 2 つです。既定の**一体**は箱がエンティティで、同じ ID の出現を 1 つにまとめます。箱の中に入るのは定義出現の保有（誕生の場所）だけで、詳細化の出現の中に書かれた保有は親の側にひし形を付けた線で描きます。**「側面で分ける」**を入れると箱が出現になり、文書ごとの書かれ方（どの文書の中に何が書かれているか）をそのまま描きます。同じエンティティの箱は点線で結び、箱には側面の表示名（「〔基本〕」など。定義出現は「・定義」）を添えます。
箱をドラッグすると中の箱も一緒に動きます。起点の近傍は保有の入れ子も辿るので、画面を起点にすると画面項目が深さ 1 に出ます。
**段も 2 つ**です（ツールバーの「実体／型」）。既定の**実体**は箱がエンティティ、**型**にすると同じ画面が一段上がり、箱＝エンティティ型・線＝関係・入れ子＝保有の宣言の**スキーマの構造の図**になります。文書は読まず、スキーマ（`entity:`・object の `entity`・参照項目の `relation` / `scope` / `idPattern`）と関係レジストリだけから描くので、文書がまだ無いワークスペースでも見られます。
線の出どころは 2 つで、レジストリの宣言（`source` → `target`）と、スキーマの参照項目からの導出（参照を書く要素の型 → `scope.schemaIds` のスキーマに現れる型を `idPattern` で絞ったもの）を 1 本にまとめます。
相手の型を宣言した関係は宣言どおりに描き、スキーマの `scope` がそれより広いぶんは図に出しません（CLI `schema-graph` の `beyondDeclaration` で分かります）。
箱の添え書きはその型が現れるスキーマ、箱を押すとその型を定義するスキーマ文書が開きます。右クリックで、現れるスキーマを開く・**この型の実体を見る**（実体の段へ移り、その型だけを見せる）・起点にする、ができます。
型・関係の絞り込みと配置・PNG は実体の段と同じです。線にできなかった参照項目（型が決まらない・相手を絞っていない）は CLI `schema-graph` が理由つきで出します（[cli.md](cli.md)）。
**矢印の向き**は関係ごとに変えられます。`_views` にレンズの見え方の定義（`kind: lens`。後述）を置き、関係に `arrow: reverse` と書くと、その関係の矢印は相手から参照を書いた側へ（文字は `inverseLabel`）描かれます。子が親を「導出元」として参照する書き方でも、図では親から子へ「導出」の向きで読めます。表示だけの定義で、検証・クエリ・関係パネルの向きは変わりません。実体の段・型の段のどちらにも効き、右パネルの関係の一覧に「（矢印は逆向き）」と出ます。
配置はバックグラウンドで計算し、できあがると全体が収まるように表示します（「全体」で戻せます）。
  - **拡大縮小**: ホイールでカーソルの位置を中心に、「＋／－」で画面の中央を中心に拡大縮小します（縮小すると文字は省きます）。全体が画面に収まらないときは右下にミニマップが出て、押した場所を画面の中央にできます
  - **節点を動かす**: 箱をドラッグするとその位置に固定され、つながる辺は直線で引き直されます。配置を変えると固定は解けます（「動かした n 件を戻す」でも戻せます）
  - **ホバー**: 箱に重ねると、その節点と隣の節点・つながる辺だけが濃く、他は薄く表示されます
  - **右クリック**: 箱の上で、エンティティページを開く・起点にする・原本へ（定義の出現）・この型を隠す・動かした位置を戻す、を選べます
  - **PNG に保存**: 表示中の図（全体・等倍。長辺 8,000 px まで）を画像にして保存します。保存先は OS のダイアログで選び、file 型の項目から設計文書に貼れます
- **エンティティページ**: 同一論理IDの全出現を**エンティティ全体像**（アスペクト合成。[checks.md](checks.md)「エンティティ型宣言」の `entity.aspect` / `owns`）として1画面に集約します。ヘッダにはID・エンティティ型・タイトルと**操作メニュー**（改名／別IDへ統合／削除。
全出現・全参照を書き換える変更セットのプレビュー→適用）、本文にはアスペクト見出しつきの所有フィールド（その場で編集できます。編集は通常のフォームと同じ経路＝未保存●表示・Undo・保存がそのまま効きます）、**関係パネル**（関係ラベルでグループ化した両方向の参照。
行クリックで相手エンティティのページへ・矢印で参照箇所へ）、カバレッジ充足を表示します。アスペクト宣言のないスキーマの出現も従来どおり出現フォームで編集でき、「出現別フォームで表示」トグルで従来表示に切り替えられます。ヘッダの「すべて保存」（未保存件数つき）で複数文書の編集をページを離れずに保存できます。
台帳スペースの「エンティティ」タブ、右ペイン（インスペクタ）の「出現」タブ、検索・コマンド、ID出現候補ダイアログから開けます
- **ビューグリッド**: `_views/*.yaml` に定義した「行（論理ID）×列（各文書の項目）」の宣言的ビューを、**編集可能な一覧**として表示（後述）。ID 列と見出し行は固定され、列が多いクロス集計でも見えている列だけを組み立てるので軽く動きます
- **準備完了レポート**: 台帳の「準備」タブ。エンティティごとに指摘を帰属させ、エラー 0 を準備完了とみなします（CLI の `readiness` と同じ計算で、保存済みの内容で判定）。件数のタイル、型別・フェーズ別の積み上げ棒（準備完了／未完。棒に触れると値が出ます）、エンティティの表（未完だけ・文字で絞り込み。行クリックでエンティティページへ）が並びます
- **差分**: 文書の「差分」タブで、ディスク上の保存済み内容と編集中内容を左右比較。変更行では行内の変わった箇所を文字単位で強調表示
- **最近開いたファイル**: ツールバーの履歴アイコンから直近12ファイルを再度開く。履歴はワークスペース単位で保存
- **検索・コマンド**: `Ctrl+K` で開く統合パレット。ID・タイトルでのジャンプ、ファイル検索、**本文検索**（2文字以上で発動。キー・値への部分一致。未保存の編集も対象＝「見たまま」で検索し、ヒットのクリックで該当箇所へジャンプ）、台帳ビューの切替、実行／設計スペースの表示、保存、エンティティの改名（全出現・全参照の一括書き換え。プレビュー→適用）、ワークスペースの切替（履歴からの選択・ディレクトリ選択）をキーボード中心で実行

一括編集は対象に未保存文書が含まれる場合は実行されません。実行前には確認ダイアログを表示し、変更後は索引と画面を再読込します。

## ビューグリッドとビュー定義（`_views`）

段階的詳細化（同一IDを複数文書で詳細化する運用）では、「機能一覧」と「機能ごとの詳細文書」のように情報が複数ファイルへ分かれます。ビューグリッドは、`_views/*.yaml` の**宣言的なビュー定義**に従って、それらを1つの一覧に結合して表示・編集する機能です。台帳スペースの「ビュー」タブから開きます。

- **行** = `rows.idPattern` に一致する**論理ID**。同じIDの出現が複数文書にあれば1行に結合されます。または `rows.match`（**クエリ行**。後述）でパターン照合の束縛行を行にできます（`idPattern` とは併用不可）
- **列** = 「どの出現（`schemaId` / `fileGlob` で選択）の、要素からの相対パス（`path`）」。`editable: true` の列はグリッド上で直接編集できます（文字列・数値・enum・参照などのスカラー値。配列・オブジェクトはクリックで該当文書へジャンプ）
- セルの編集は**元の文書への通常の編集**そのものです（未保存●表示・Undo・`Ctrl+S`／すべて保存・差分がそのまま使えます）。ビュー自体はデータを持ちません
- **詳細列**: `detail` に一致する出現があればリンク、なければ「作成」ボタンで `filePattern` の位置に**詳細文書をスキャフォールド**します（スキーマの必須初期値＋行のIDを設定）。`filePattern` は値の式で、`{id}` のほか行の要素の値（`{name}` など）を穴に書けます（[schema.md](schema.md)「新しい文書の置き場所とひな型」。作り先のスキーマに `scaffold` があれば、中身も元の要素から埋まります）
- **新規行**: `newRow` を定義すると、グリッドから新しい行を作れます。2つのモードがあります（併用不可）
  - **配列モード**（`file` + `path`）: 一覧文書の配列へ新しい要素を追加します（IDを入力して保存するとグリッドの行になります）
  - **ファイルモード**（`filePattern`）: 一覧文書を持たず詳細文書だけでIDを運用するレイアウト向け。IDを入力すると `{id}` を置換したパスへ**詳細文書そのものをスキャフォールド**します（スキーマの必須初期値＋入力したIDを設定。ディスクへ書かれた時点で行が現れます。行がまだ無いので、書ける穴は `{id}` だけです）
- **バックリンク列**: 列に `path` の代わりに `backlinks` を書くと、行のIDへの**被参照**（参照元要素のID・タイトル）を一覧表示します。`relation`（参照の関係種別）と `schemaIds`（参照元スキーマ）で絞り込めます。1:N詳細化（[ids.md](ids.md)）の「親から見た分裂先の一覧」に使います。派生表示のため編集はできません（クリックで参照元へジャンプ）
- **定義参照列**: 列に `label`／`path` の代わりに `definition: モジュール#定義名` を書くと、スキーマの**名前付き定義**（[schema.md](schema.md)）のセル型フィールドが列に展開され、見出し・パスがスキーマから導出されます（ID型の項目は行のID列と重複するため除かれます）。`schemaId` を併記した場合は定義名だけでも書けます（例 `definition: screen`）。列の見出しをビューへ重複記載する必要がなくなり、スキーマの変更に自動で追随します。`editable: true` は展開された全列に適用されます
- **値の式の列**: 列に `path` の代わりに `value` を書くと、行の要素の値から**値の式**（[schema.md](schema.md)「新しい文書の置き場所とひな型」の `filePattern` と同じ書き方）で計算した値を表示します（読み取り専用の派生表示）。行の要素は `schemaId`／`fileGlob` で選んだ出現で、未保存の編集にも追随します
  - 短い書き方: `value: "{name}（{status}）"`（穴は行の要素の値。`{id}` は行のID・`{title}` は表示の解決結果）
  - 完全な書き方: `value: {max: {path: "comments[*].date"}}`（配列の各要素の `date` の最大）。読み出しは項をそのまま返し、パスの `[*]` は合う場所の値を並べた配列になります。`sum` / `min` / `max` / `count` は配列を受け取る関数です。`count` は配列の件数、`length` は文字数です。日付の項目から年月を出すなら `{yearMonth: {path: orderedAt}}`（`2026-10`）、年・月・日の数なら `{year: …}` / `{month: …}` / `{day: …}` です
  - `min` / `max` の比べ方は読んだ項目の型で決まります（`date` の項目なら日付・`int` なら数。表記から意味を決めません）。項目の型が分からない値を日付として比べるなら `type: date` を添えます
  - 値が得られないとき（配列が空・要素に値が書かれていない・日付として読めない値がある）はセルが空になり、クリックすると理由が出ます。既定値は `{first: [式, 値]}` で書きます
  - セルの座標は値の出どころ（最大・最小なら選ばれた要素）で、クリックのメニュー「元の値へ」でそこへジャンプできます。集計の材料（各要素の値と場所）も来歴として並びます
  - 参照を辿るには `via`: `{via: type, in: {schemaId: ddl-mapping}, path: to}` は、行の要素の `type` に書かれた参照を 1 段辿り、相手の写像行の `to` を読みます。`format` の入れ物（`scopes`）にも `via` を書けます。参照がちょうど 1 本のときだけ相手が決まり、無い・複数のときは理由つきで得られません。入れ物を書いても、最後にいつも行の要素が続きます
  - 集合から配列へは `all`: `{all: {match: [{node: {entity: category, bind: cat}}, {edge: {via: category, dir: in}}, {node: {entity: todo, bind: t}}], where: [{of: t, path: status, equals: OPEN}], of: t}}` は、
行の要素を起点にパターン照合（[checks.md](checks.md)「パターン制約」と同じ書き方）を評価し、`of` の束縛の要素を並べた配列にします。`path` を添えれば各要素の値の配列です（`in` で読む文書を選びます）。起点は行の要素（`from` に束縛名を書けばその束縛。クエリ行）で、先頭の `node` に合わなければ空です。
`{count: {all: ...}}` で件数、`{sum: {all: {..., path: amount}}}` で合計になり、セルのクリックで集めた要素へジャンプできます。`{each: 配列の式, value: 式}` は各要素をいまの要素として式を当てた配列です（例 `{sum: {each: {path: lines}, value: {multiply: [{path: price}, {path: qty}]}}}`）。`limit` は書けません
  - ビュー定義のリントは、式が読む項目がスキーマから解決できるか、`via` が参照型の項目か、集計に書いた `type` が項目の型と食い違っていないか（`date` の項目に `type: number`・文字の項目に `type: date`）を指摘します
  - 古い書き方 `computed`（`lookup` / `source` / `path` / `values` / `map` / `default`）は定義エラーになり、同じ意味の `value` の書き方が文面に出ます
- **行の並び**: `order` を省くと ID 順です。`order: { schemaId / fileGlob }` はその出現の文書内の順（一覧文書の並び）。`order: { path: date, direction: desc }` のように `path` を書くと、並び基準の出現（`schemaId` / `fileGlob`。省けばどの出現でも）の要素から読んだ**値の順**になります。
並べ方は項目の型で決まります（`int` / `number` は数の順・`date` / `time` / `datetime` は日付などの順・それ以外は文字の順）。`type: number | date | time | datetime` を書けば上書きできます。`direction: desc` で大きい順・新しい順。値の無い行はどちらの向きでも後ろ、同じ値は ID 順です（`samples/todos` の `todo-by-due.yaml`＝期限順が実例）
- **要素ごとに列を広げる**: 列に `label` / `path` の代わりに `each: { idPattern: "CAT-*", bind: cat }` と `value`（値の式）を書くと、`idPattern` に合う要素（費目など）ごとに 1 列ができます。見出しは要素のタイトル、並びは ID 順（`each.order: { schemaId / fileGlob }` でその出現の文書内の順）。
`value` の式の中では列の要素を `$cat`（`bind` の名前に `$`）で指せます。その文字だけの値が、列ごとにその要素の ID に置き換わります（例: 月の行から `all` で取引を集め、`edge: { via: category }` → `node: { id: $cat }` でその費目の取引に絞って `sum`。`where` の `equals: $cat` でも同じ）。
同じ表は[クロス集計](#クロス集計kind-matrix-行列のセルに集計)でも書けます。違いは、こちらが「ふつうの列の 1 つ」なので他の列と並べられ、合計の行や未分類の列は自分で書くことです
- **セルの表示**: 編集できない列のセルは、enum を「値（ラベル）」、参照を「ID（参照先の名前）」で併記します。編集できる参照のセルは、入力欄の下に参照先の名前を添えます。参照の配列の要約（「n 件: …」）でも各 ID に参照先の名前が付きます。値そのもの・CLI・エクスポートは変わりません
- **桁区切り**: 列に `display: grouped` を書くと、数のセルを桁区切り（45000 → 45,000）で見せます。`path` の列は、項目の側の `display: grouped`（[schema.md](schema.md)）でも同じに見えます。見せ方だけで、値・CLI `view`・エクスポートは変わりません。編集できる列は、編集中だけ元の表記に戻ります
- **表示の形**: 列に `format: "¥#,##0"`（数）や `format: "yyyy年M月d日"`（日付）を書くと、その形で見せます。`path` の列は項目の側の `format` でも同じに見え、値の式の列は値が数か日付として読めれば整形します。値は変わりません
- **状態列**: カバレッジルール（[schema.md](schema.md)）の充足状況を行ごとに表示します

```yaml
# _views/screen-catalog.yaml
id: screen-catalog
name: 画面カタログ
rows:
  idPattern: "SCR-*"                  # このIDパターンが行になる
order:
  fileGlob: todos/10-screens-list.yaml  # 一覧文書での出現順に並べる（省略時はID順）
  # path: date, direction: desc   # 値の順にするなら: 出現の要素の date（日付の項目なので日付として比べる）の新しい順
columns:
  - label: 画面名
    fileGlob: todos/10-screens-list.yaml  # 値を取る出現（schemaId でも指定可）
    path: name                            # 出現要素からの相対パス
    editable: true
  - label: エリア
    fileGlob: "todos/screens/*.yaml"
    path: areas                           # 複合値は要約表示＋ジャンプ
  - label: 実装テーブル
    backlinks:                            # バックリンク列: この画面IDを参照している要素を一覧表示
      relation: derives                   # 参照の関係種別で絞る（省略可）
      schemaIds: [table-design]           # 参照元文書のスキーマで絞る（省略可）
detail:
  fileGlob: "todos/screens/*.yaml"        # この条件に一致する出現を「詳細」と見なす
  filePattern: "todos/screens/{id}.yaml"  # 「作成」ボタンの作成先（{id} が行のIDに置換）
newRow:
  file: todos/10-screens-list.yaml        # 「新規行」の追加先（一覧文書の配列）
  path: screens
```

一覧文書を持たないレイアウト（1詳細文書＝1ID）では、`newRow` をファイルモードにします:

```yaml
# _views/actor-list.yaml — 詳細文書だけでIDを運用する場合
id: actor-list
name: アクター一覧
rows:
  idPattern: "ACT-*"
columns:
  - label: アクター名
    schemaId: actor
    path: name
newRow:
  filePattern: "00-requirements/011-{id}.yaml"  # 「新規行」でIDを入力すると詳細文書を直接作成
```

**クエリ行**（`rows.match`）: 行を「1つのID」ではなく、**グラフパターン照合の束縛行**（結合の組）にします。「画面→uses→ユースケース」のような**多段結合の組を1行に**でき、結合先の値もセルとして表示・編集できます:

```yaml
# _views/entity-table-matrix.yaml（sample-workspace に同梱の実例）
id: entity-table-matrix
name: エンティティ×テーブル（結合）
rows:
  match:                                   # node / edge の交互連鎖（node で始まり node で終わる）
    - node: { entity: entity-model, bind: ent }   # 起点集合（entity: 型 / schema: 出現スキーマ / id: IDパターン）
    - edge: { relation: derives, dir: in }        # dir: out（その要素が直接書いた参照を辿る。既定）/ in（被参照を辿る）。via（キー名・場所）でも絞れる。contains: true は入れ子の線
    - node: { entity: table-design, bind: tbl }   # bind した束縛が結果の列になる
  # rowKey: ent                            # 行キーの束縛（省略時は先頭の bind。詳細列・状態列・新規行はこのIDに効く）
  # where:                                 # プロパティ述語（equals / exists のみ。値はいずれかの出現の該当パス）
  #   - { of: tbl, path: status, equals: draft }
  # limit: 100                             # 行数上限（既定 100）
columns:
  - { label: エンティティ名, path: name }              # of 省略 = 行キー束縛（ent）の値
  - { label: テーブル名, of: tbl, path: title, editable: true }  # of: 束縛名 = 結合先の値をセル化（編集は原本へ）
  - { label: 状態, of: tbl, path: status, editable: true }
```

- 結合により**同じIDの行が複数現れる**ことがあります（例: 1エンティティ×2テーブル = 2行）。セルの編集は従来どおり各原本文書への通常編集です
- `also:`（`{from: 束縛名, steps: [...]}`）で束縛済みノードからもう1本の連鎖を足せます（1段のみ・内部結合）。`kind: document` のノード（文書そのもの）も扱えます
- 行の並びはクエリの決定的順序（束縛名の辞書順に並べた値のID昇順）で、`order` とは併用できません。CLI `query`（[cli.md](cli.md)）で同じパターンを試作できます

参照を辿る導出の例（値型台帳の制約値で、型写像のひな型を評価して表示する）:

```yaml
# 行 = 属性ID（FLD-*）。属性の値型参照（type）を辿り、DDL型写像のひな型を評価する
columns:
  - label: DDL型（導出）
    schemaId: concepts                                                 # 行の出現。ここに書かれた type を辿る
    value:
      format: { via: type, in: { schemaId: ddl-mapping }, path: to }  # 参照先の写像行のひな型（例 varchar({maxLength})）
      scopes:
        - { via: type, in: { schemaId: ddl-mapping } }                 # 穴は、まず写像行から
        - { via: type, in: { schemaId: concepts } }                    # 次に値型の定義から。最後に行の要素（暗黙）
```

セルの座標はひな型の場所で、クリックのメニュー「元の値へ」でそこへ、「入力値へ」で穴を埋めた値（`{maxLength}` の 100）へジャンプできます。

sample-workspace の `_views/field-traceability.yaml`（概念→実装→DDLの項目トレーサビリティ。手書きの宣言値と導出値を並置）と `_views/value-type-mappings.yaml` が実例です。

値の式の列の例（TODO 個票のコメントの日付から「最終更新日」を導く。配列の並び順によらず最新の日付が出て、最新のコメントを消せば残りの最新に変わります）:

```yaml
# 行 = TODO の ID。コメント（date と body の配列）の最新の日付を、手で転記せずに表示する
columns:
  - label: 最終更新日
    schemaId: todo-detail                                   # 値を読む出現（普通の列と同じ）
    value:
      first:
        - max: { path: "comments[*].date" }     # 各コメントの date の最大（date の項目なので日付として比べる）
        - 未更新                                            # コメントが無いときの表示
```

同じ式は検査の `check` にも書けます（[checks.md](checks.md)「パターン制約」の値の式）。一覧で見えている値と、検査が比べる値は常に一致します。

集合から配列へ落とす `all` の列の例（カテゴリ × ステータスの集計表。行＝カテゴリ、列＝状態ごとの TODO の件数。`samples/todos` の `category-status-matrix.yaml` が実例です）:

```yaml
# 行 = カテゴリの ID。行を起点に「このカテゴリを参照する TODO」を状態で絞って集め、件数にする
rows: { idPattern: "CAT-*" }
columns:
  - { label: カテゴリ名, schemaId: category-list, path: name }
  - label: 未着手
    schemaId: category-list
    value:
      count:                                              # 配列の件数
        all:                                              # 照合の解を配列にする
          of: t                                           # 集める対象
          match:
            - node: { entity: category, bind: cat }       # 起点（行の要素がこれに合うときだけ集める）
            - edge: { via: category, dir: in }            # カテゴリを参照している要素へ
            - node: { entity: todo, bind: t }
          where:
            - { of: t, path: status, equals: OPEN }       # 状態で絞る（個票の値）
  # 対応中・完了・中止は where の値を変えた同じ列。合計は where を書かない列。金額の合計なら sum に path: amount を添えた all
```

| カテゴリ名 | 未着手 | 対応中 | 完了 | 中止 | 合計 |
|---|---|---|---|---|---|
| 環境整備 | 1 | 0 | 1 | 1 | 3 |
| データ登録 | 0 | 1 | 2 | 0 | 3 |

セルのクリックで集めた TODO が並び、「入力値へ」で各 TODO の一覧の行へ移動できます。カテゴリを付けていない TODO はどの行にも数えられず、個票の無い TODO は状態の列に数えられません（合計にだけ入ります）。検査の中でも同じ `all` を書けるので（[checks.md](checks.md)「パターン制約」）、見えている件数と検査が数える件数は一致します。

`_views` は予約ディレクトリで、組込みスキーマによりフォーム編集・検証できます。エージェントは同じビューを `read_view` ツールで参照でき（[ai.md](ai.md)）、CLI では `view` コマンドで解決できます（[cli.md](cli.md)）。

ビュー定義はロード時に**スキーマとの整合が検査されます**（リント）。存在しないスキーマIDへの参照、スキーマから解決できない列・セクションのパス、存在しない定義参照は「定義エラー」としてビューグリッドのバナー・`read_view`・CLI `view` の一覧に表示されます（指摘があってもビュー自体は従来どおり表示されます）。スキーマを変更したときに、それを参照しているビューが黙って壊れることを防ぎます。また、`_views` の定義文書を開いている間は**右ペインの検証タブにも同じ指摘が表示され**、編集中の内容で再判定されるため、保存する前に定義の誤りへ気づけます。

また、詳細文書をフォームで開くと、上部に**「他文書での定義」ストリップ**が表示され、同じIDの一覧側の情報（名前・種別など）を参照・ジャンプできます。一覧側にある情報を詳細文書へ重複記載する必要はありません。

## クロス集計（`kind: matrix`）— 行×列のセルに集計

「月×費目の金額」「カテゴリ×状態の件数」のように、**両方の軸が動く表**を 1 つの定義で書けます。行は論理 ID（`rows.idPattern`）か要素ごとに計算した値（`rows.value`）、列は「セルに数える要素の参照先」「要素の値」「要素ごとに計算した値」から自動で広がり、合計の行と列が付きます。

```yaml
# _views/month-by-category.yaml
id: month-by-category
name: 月×費目
kind: matrix
rows: { idPattern: "M-*" }                      # 行の軸＝月
display: grouped                                # セルの数を桁区切りで見せる（省略可）
cells:
  match:                                        # 行の要素を起点に、セルに数える要素まで辿る（値の式の all と同じ書き方）
    - node: { entity: month, bind: m }
    - edge: { via: month, dir: in }
    - node: { entity: transaction, bind: tx }
  where: [ { of: tx, path: kind, equals: expense } ]   # 絞り込み（省略可。also も書けます）
  of: tx                                        # 数える要素
  columns: { via: category, idPattern: "CAT-*", order: { schemaId: categories } }   # 列の軸＝取引の費目（費目一覧の順）
  aggregate: sum                                # count（既定）/ sum / min / max
  path: amount                                  # sum / min / max で集計する値
```

- **列の軸**は 2 通りです。`columns: { via: 参照の項目, idPattern: "CAT-*" }` は、要素の参照先のエンティティが列になり、見出しはそのタイトル、並びは ID 順（`order: { schemaId / fileGlob }` でその出現の文書内の順）。`columns: { path: 値の項目, values: [ { value: income, label: 収入 }, expense ] }` は、要素の値が列になり、`values` の並びと見出しで出ます。
- **セル**は、行の要素から `match` で集めた要素のうち、その列に当たるもの（参照先がその列のエンティティ、または値がその列の値）を `aggregate` で畳んだ値です。値の式の列と同じ評価なので、セルをクリックすると集めた要素へ移動できます。
- **未分類の列**（既定の見出しは「（未分類）」）は、参照が無い・列の軸に無い値の要素です。`unclassified: 見出し` で名前を変え、`unclassified: false` で出しません（項目が必須なら不要です）。
- **合計**は列の右端「合計」（行の要素をすべて畳んだ値）と、最後の行「合計」（各列のセルを畳んだ値）です。`totals: false` で出しません。`count` / `sum` は足し、`min` / `max` はその順で選びます。
- 行の並びは `order`（[上](#ビューグリッドとビュー定義_views)の「行の並び」）で、CLI `view`・エクスポート・エージェントの `read_view` にも同じ表が出ます。`columns`・`detail`・`newRow` はこの種類では書けません。
- 同じ表を、ふつうのグリッドの「要素ごとに列を広げる」列（`each`）でも書けます。他の列と混ぜたいときはそちら、合計の行や未分類の列まで自動で欲しいときはこちらです。

**軸を値の式で広げる**（`rows.value` / `columns.value`）。月の文書を置かずに「受付日の年月ごと」の行を作る、のように、要素ごとに計算した値を軸にできます。`samples/orders` の `month-by-status.yaml` が実例です。

```yaml
# _views/month-by-status.yaml — 行＝注文受付日の年月、列＝注文状態、セル＝注文合計金額の合計
id: month-by-status
kind: matrix
rows: { value: { yearMonth: { path: orderedAt } } }   # 行の軸＝起点の要素ごとに計算した値（同じ値を 1 行に）
cells:
  match: [ { node: { entity: order, bind: o } } ]        # 起点＝注文（行が値の軸のときは、最初の node に合う要素すべてが起点）
  of: o
  columns: { path: status, values: [ { value: pending, label: 未処理 }, shipped, cancelled ] }
  aggregate: sum
  path: totalAmount
```

- `rows: { value: 式 }` は、照合の最初の `node` に合う要素ごとに式（[schema.md](schema.md)「値の式」と同じ書き方。`of` を省くとその要素）を計算し、同じ値の要素を 1 行にまとめます。行は値の順序の種類（数・日付・文字）で並び、`idPattern` や `order` とは一緒に書けません。値が得られない要素は「（未分類）」の行になります（`unclassified: false` なら出しません）。
- `columns: { value: 式 }` は、セルに数える要素（`of`）ごとに式を計算し、データに現れた値を列にします（`via` / `path` とは一緒に書けません）。注文ごとの行に月の列を広げる、のように使います。
- 列がデータから決まるので、画面のヘッダと書き出しの見出しは解決した行から取ります。セルの来歴（集めた要素）と合計の行・未分類の列は、ほかのクロス集計と同じです。
- 行が値の軸のとき、行は原本の出現を持ちません（ID を押しても対象のページは開きません）。原本へは、セルの来歴から辿ります。

## チャート（`kind: chart`）— 表を図に

グリッドかクロス集計を**元の表**にして、棒・積み上げ棒・折れ線・円を描きます。Excel で「表を作ってからグラフにする」のと同じで、行が横軸の項目、数の列が系列です。チャートはデータを持たず、集計は元の表がします。画面で描き、CLI `view` と `read_view` は項目×系列の数を返します。

```yaml
# _views/monthly-sales-chart.yaml
id: monthly-sales-chart
name: 月別売上
kind: chart
chart: stacked-bar                 # bar（棒）/ stacked-bar（積み上げ棒）/ line（折れ線）/ pie（円）
view: month-by-status              # 元の表（グリッドかクロス集計の ID）。行＝横軸の項目、列＝系列
y: { label: 売上高（円）, format: "#,##0" }   # 縦軸の見出しと値の形（省略可）
drill: below                       # 押したときの材料の一覧の出し方: popup（既定）/ below / right / none
# series: [未処理, 出荷済み]       # 系列にする列（省略すると数の列すべて。クロス集計なら合計と未分類の列は除く）
# x: 顧客名                         # 横軸の文字にする列（省略すると行のタイトルか ID）
```

- **系列**: `series` を省くと、数として読めるセルを持つ列がすべて系列になります。クロス集計の「合計」と「（未分類）」の列は既定で描かず、描くなら `series: [合計]` のように書きます（売上の推移を折れ線で、など）。
- **項目**: 元の表の行です（クロス集計の合計の行は除きます）。文字は行のタイトル（無ければ ID）で、`x` に列を書けばその列の値です。並びは元の表の行の順で、`order: { series: 列の見出し, direction: desc }` と書けば系列の値の多い順（`asc` で少ない順。`series` を省くと最初の系列。値の無い項目は後ろ）になります。顧客別の割合を多い順に、のように使います。
- **円**は最初の系列だけを描き、値の割合を扇形に、右の凡例に値と割合を出します。0 以下・読めない値は描きません。
- **置き場**は 3 つです。台帳の「ビュー」タブの一覧（表と同じ一覧から選びます。「元の表を開く」で元の表へ）、文書ビューの区画（`sections: [ { chart: { view: monthly-sales-chart } } ]`。フロー図の埋め込みと同じ）、ダッシュボードの区画（`view: monthly-sales-chart`。[dashboards.md](dashboards.md)）。
- 棒にマウスを載せると項目と系列ごとの値が出ます。値の形は `y.format`（DecimalFormat のパターン）で、省くと桁区切りです。
- **押すと材料が出ます**。棒・点・扇形を押すと、そのセル（項目×系列）の材料＝集めた要素（ID と名前・値）が並び、各要素の「詳細」（ダッシュボードなら業務詳細、台帳ならエンティティページ）か「原本」へ進めます。合計のような計算値でも、表のセルを押したときと同じ来歴が材料になります。項目そのものが実体（顧客など）なら、その詳細へも進めます。積み上げ棒は押した高さの系列、並べた棒は項目のすべての系列、折れ線はいちばん近い点、円は扇形か凡例の行です。
  出し方は `drill` で選びます: `popup`（押した場所に浮いた一覧。既定）、`below`（図の下に一覧）、`right`（図の右に一覧）、`none`（押せない）。
- 元の表が無い・`series` / `x` に書いた列が無い（列が宣言で決まるグリッドのとき）は定義エラーになります。クロス集計のように列がデータから決まる元の表では、無い列は描くときの注意に出ます。
- 書き出し（skill のエクスポート）の対象は元の表です。図そのものは書き出しません。

## レンズの見え方（`kind: lens`）— 矢印の向き

スキーマと関係レジストリは「データの契約」で、見え方は持ちません。グラフレンズの見え方のうちワークスペースで共有したい決まりは、`_views` に `kind: lens` の定義を置いて書きます（設計スペースの「ビュー」に並び、組込みスキーマのフォームで編集できます）。

```yaml
# _views/lens.yaml
id: lens
name: レンズの見え方
kind: lens
relations:                                # 関係ごとの見え方
  - { name: derived-from, arrow: reverse } # 矢印を相手から参照を書いた側へ（文字は inverseLabel）
```

- `relations[].name` は関係レジストリの関係名（か ref 項目の `relation`）。レジストリがあるときは、宣言の無い名前をビューの定義エラーとして指摘します。
- `arrow` は `forward`（既定。参照を書いた側から相手へ）か `reverse`。実体の段・型の段の両方に効きます。
- 表示だけの定義です。検証・クエリ（`dir`）・関係パネル・バックリンクの向きは変わりません。節点の選択（型・関係の絞り込み・起点・畳み）は画面の操作のままで、定義には書きません。
- 関係の改名（`rename-relation`）は、この定義の関係名を自動では書き換えず、計画の警告で場所を知らせます。

## 文書ビュー（`kind: document`）— フォーム表示の合成

スキーマは「データの構造と検証」を、ビューは「画面の見せ方」を受け持ちます。**文書ビュー**は `_views` のビュー定義に `kind: document` を指定したもので、特定の文書をフォームで開いたときの表示を**セクションの並び**として合成します。「内容はスキーマでチェックし、表示はビューでコントロールする」ための機構です。

- **適用先**: `match`（ファイルglob）または `schemaId`（併記時は両方に一致）。マッチする文書ビューがない文書は、従来どおりスキーマ駆動フォームで表示されます（文書ビューは足したい文書にだけ足す上書きです）。複数の定義がマッチする場合は定義ファイル名順の先勝ちです
- **`sections`**: 上から順に描画されます。各セクションは次のどちらか一方を持ちます
  - **`fields`** — スキーマ駆動フォーム。`path` を省略すると文書全体、指定するとそのパスの項目だけを表示します。編集は通常のフォームと同じ（未保存●・Undo・保存がそのまま効きます）。`include: [キー...]`（列挙した順でそのキーだけを表示）／`exclude: [キー...]`（列挙したキーを除いて表示）で表示項目を選別でき、複数の fields セクションに分ければフォームをグループ分けできます。
`definition: モジュール#定義名` を添えると「このセクションはこの名前付き定義（[schema.md](schema.md)）の構造を表示している」という宣言になり、定義が存在しなければエラー、パス先のフィールドがその定義を参照しなくなればリントが指摘します（スキーマ変更への追随検出）
  - **`backlinks`** — 文書内のIDへの**被参照表**（読み取り専用）。`idPattern` で対象IDを絞り、`relation`・`schemaIds` で参照を絞り、`columns` で参照元要素の値を列表示できます。クリックで参照元へジャンプします
- **`attachments`（要素単位アタッチ）**: セクションが文書レベルの合成であるのに対し、アタッチは**フォーム中の要素の位置**へ被参照表を差し込みます。`at` に要素パスのパターン（YPath 構文＋`[*]`＝任意のインデックス。
例 `actors[*]`）を書くと、一致する各要素の展開フォーム内（配列要素・ネスト・テーブルの行展開すべて）に、**その要素のIDへの被参照**だけを絞った表が現れます。被参照の条件（`relation`・`schemaIds`・`columns`）はセクションの `backlinks` と同じ語彙です。
IDを持たない要素には差し込まれません

たとえば「アクター定義書に、そのアクターを利用するユースケースの一覧表を足したい」とき、スキーマにはアクター定義の本質だけを書き、被参照の表はビュー側に足します:

```yaml
# _views/actor-document.yaml
id: actor-document
name: アクター定義書
kind: document
match: "00-requirements/01-actors.yaml"   # schemaId: actors でも可
sections:
  - fields: {}                       # スキーマ駆動フォーム（従来表示そのもの）
  - label: 利用するユースケース
    backlinks:                       # 被参照表: この文書のアクターIDを参照している要素の一覧
      idPattern: "ACT-*"             # 文書内の対象ID（省略時は文書内の全ID）
      relation: uses                 # 参照の関係種別で絞る（省略可）
      schemaIds: [usecases]          # 参照元文書のスキーマで絞る（省略可）
      columns:                       # 参照元要素から表示する列（省略時はID・タイトルの要約のみ）
        - label: ユースケース名
          path: name
```

文書末尾の一覧表ではなく「各アクターの展開フォームの中に、そのアクターのユースケースだけを出したい」場合は、被参照表をアタッチとして書きます:

```yaml
sections:
  - fields: {}
attachments:
  - at: "actors[*]"                  # 各アクター要素の展開フォーム内に差し込む
    label: 利用するユースケース
    backlinks:
      relation: uses
      schemaIds: [usecases]
```

被参照は、画面上は未保存の編集を含む「見たまま」（オーバーレイ索引）、`read_view`・CLI はディスク索引に基づきます。文書ビューは台帳の文書のみが対象です（`ledger` 宣言時は台帳外に適用されません）。エージェントは `read_view` に `file` を渡して同じ被参照表を座標つきで読め、CLI では `view <view-id> [file]` で解決できます（適用対象が1文書だけなら `file` は省略可）。
