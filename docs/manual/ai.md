# AI とエージェント

## AIによる作成支援

スキーマが適用された文書では、OpenAI / Anthropic（Claude）/ Azure OpenAI（AI Foundry）の API を使って内容のたたき台を生成できます。入口は次のとおりです。

- **フィールド単位**: フォームの各フィールドラベル横の ✨ アイコン
- **配列への候補追加**: 配列エディタの「AIで候補追加」（既存項目を残して追加／配列全体を置き換えを選択可能）
- **文書全体**: 文書ヘッダーの「文書操作」（⋯）→「AIで作成」（`_document` メタデータは保持されます）
- **出現単位**: エンティティページのアスペクトカード・出現カードのヘッダ ✨「この出現をAIで作成」。そのアスペクトが所有するフィールドだけを生成し、生成しなかったキー・スキーマ外のキー・ID はそのまま保持されます（キー単位のマージ適用）
- **新規作成のたたき台**: ファイルツリーの「YAML ファイルを作成」とビューグリッドの「新規行」ダイアログの「作成後にAIでたたき台を生成」チェックボックス、グリッドの詳細「作成」ボタン横の ✨。ファイルを作成して開いた直後に、その文書を対象としたAI生成ダイアログが続けて開きます。生成はキー単位のマージで、作成時に設定されたID・`_document` は変更されません（スキーマが適用されないファイルでは通常の作成のみ行われ、ステータスバーで案内されます）

フィールド単位と配列への候補追加は、編集スペースのフォームだけでなく、**エンティティページ（台帳の「エンティティ」タブ）のアスペクトカード・出現フォームなど、同じフォーム部品を使う画面ならどこからでも**使えます。生成の対象と適用先は常に「ボタンを押したフォームの文書」で、適用結果はその文書の未保存編集として入ります（Undo可・保存は手動）。

流れは「指示を入力 → 生成 → プレビューで現在値と比較 → 適用」です。

- 生成結果は、対象フィールドのスキーマから変換した JSON Schema による構造化出力（Structured Outputs）で受け取るため、型・enum・必須キーがスキーマに準拠します（`map` 型を含む場合のみ構造化出力を無効化し、プロンプト指示によるJSON生成にフォールバック）。
- `cases` を持つ enum を1つ含むオブジェクトは、enum 値ごとの分岐（`anyOf`）に変換され、選択値と追加フィールドの組み合わせもスキーマで保証されます（`cases` を持つ enum が同一オブジェクトに複数ある場合は全 case フィールドの和集合で受けます）。
- `ref` 型フィールドは、`idPatterns`・`scope` で絞り込んだワークスペース内の既存IDを enum 制約として渡すため、存在しないIDへの参照が生成されにくくなります（候補が200件を超える場合は制約を省略し、プロンプト内の一覧のみ）。
- プレビューは現在値とAI提案の行単位差分表示で、提案を適用した場合のスキーマ検証結果（エラー・警告数）も表示します。適用は Undo 可能で、自動保存はされません。
- 生成中は「生成を中止」でキャンセルできます。
- **参考文書**: 同じスキーマが適用される他の文書を「書き方・粒度の手本」として一緒に送信できます。既定では更新日時の新しい順に最大3件が自動選択され、ダイアログのチェックボックスで選び直せます（候補の表示は関連文書とあわせて20件まで。1件あたり2万文字・合計12万文字を超える分は省略）。参考文書に未保存の編集がある場合は編集中の内容が送信されます。
- **関連文書**: エンティティページから開いた場合は、そのエンティティの出現・参照先・参照元の文書が「関連文書」として候補に並び、既定でこちらから最大3件が自動選択されます。関連文書は書き方の手本ではなく**内容の文脈**（事実関係の参照元）としてAIに渡され、生成内容が既存の記述と整合しやすくなります。文字数の合計上限（12万文字）は関連文書→参考文書の順に消費されます。
- モデルに送信されるのは、指示、現在の文書、対象フィールドのスキーマ、選択した関連文書・参考文書、ワークスペース内の既存ID（最大500件）です。
- 生成はエージェント実行と同じカーネル上で「1ターンで提出する特殊アクティビティ」として実行され、実行記録が `_runs/` に他のアクティビティと同じ形式で残ります（アクティビティID: `ai-generate`。適用自体は従来どおりダイアログのプレビュー→編集中文書への反映で、自動保存されません）。
- 実行記録にはデバッグ用に、実際に送信したシステム指示・プロンプト全文・応答スキーマとモデルの生出力が `exchange` 節として残り、`usage` には実測のトークン数が入ります。生成に失敗した場合も実行記録は書かれ（解析できない応答は生の本文ごと記録）、エラー表示に記録ファイルのパスが示されます。

接続設定:

- **プロバイダ**: OpenAI / Anthropic / Azure をダイアログで切り替えます。選択は端末の設定（Preferences）に保存されます。
- **APIキー**: ダイアログで入力するか、環境変数（`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `AZURE_OPENAI_API_KEY`）を設定します。キーはメモリ上にのみ保持され、ディスクには保存されません。
- **モデル**: 既定は OpenAI が `gpt-5.1`、Anthropic が `claude-opus-4-8`。Azure は**デプロイメント名**を指定します。変更はプロバイダごとに端末の設定へ保存されます。Structured Outputs 対応モデルが必要です。
- **Azure OpenAI / AI Foundry**: 「接続の詳細設定」でエンドポイント（例 `https://<リソース名>.openai.azure.com`）と APIバージョン（空なら v1 サーフェス）を設定します（環境変数 `AZURE_OPENAI_ENDPOINT` / `AZURE_OPENAI_API_VERSION` でも可）。認証は `api-key` ヘッダで行われます。
- **OpenAI互換エンドポイント**: OpenAI 選択時にベースURLを上書きすると、ollama / vLLM 等の互換エンドポイントも利用できます（環境変数 `OPENAI_BASE_URL` でも可）。
- **プロキシ**: 既定はシステム設定に従います。「接続の詳細設定」でプロキシなし／手動（ホスト・ポート）へ切り替えられ、Basic 認証（ID・パスワード）も指定できます。パスワードはAPIキー同様メモリのみ保持です。エンドポイント・プロキシ設定はフィールド生成とエージェント実行の両方に共通で効きます。
- **レート制限時の自動リトライ**: API がレート制限（429）や一時的なサーバーエラーを返した場合、待機して自動で再送します（プロバイダ指定の待機時間を尊重、最大3回・1回あたり最大60秒）。一括実行などで制限に達しても、実行が途中で失敗しにくくなります。リトライ中は進捗表示が一時的に止まって見えることがあります。それでも失敗する場合は、時間を置くか一括実行の `limit` を下げてください。

## エージェントによるアクティビティ実行

定型化した仕事を「アクティビティ」として定義し、AIエージェントに委託できます。エージェントは探索（カタログ→骨子→本文）、複数文書への部分パッチ、横断検証を自律的に繰り返し、結果を**変更セット**として提出します。**原本は人間がレビューして採用するまで変更されません。**

### 定義の置き場所

| ディレクトリ | 内容 |
|---|---|
| `_agents/*.yaml` | エージェント定義: `id`・`persona`（性格・行動指針）・`rubric`（観点）・`model`（プロバイダ／モデルID）・`tools`（許可ツール分類） |
| `_activities/*.yaml` | アクティビティ定義: `id`・`agent`・`target.match`（対象glob）・`instruction`・`context.items`（コンテキストレシピ＝本書）・`allowedFiles`／`allowedPaths`（書込許可）・`actions`（[actions.md](actions.md)）・`limits`（上限）・`gates.validation`・`trigger`／`chain`／`retry`／`approval`（自動実行）・`foreach`（一括実行。本書）・`meta`（本書） |
| `_evals/*.yaml` | 評価セット定義: ゴールデン入力と期待結果によるアクティビティの回帰評価（本書） |
| `_skills/*.yaml` | skill定義: 宣言型のインポート・エクスポート（本書） |
| `_views/*.yaml` | ビュー定義: 行×列の横断一覧（[views.md](views.md)）。コンテキストレシピ（`context.items` の `kind: view`）でアクティビティの初期文脈にも開示できる |
| `_runs/` | 実行記録（自動生成＝ターン・ツール呼び出し・質問・採否・トークン使用量・評価レポート）。会話記録 `transcript` 節にモデルとの入出力が全文で残る（1件2万字で打切り・委譲先エージェントの内部会話は対象外）、コンテキスト会計の `context` 節には、毎ターン再送される固定部（システム指示・ツール定義・指示・カタログ・ビュー等）の区分別の文字数・概算トークンと、送信ごとの入力トークン実測が残り、「どの宣言がいくらトークンを払わせたか」を確認できる（`usage.cachedInputTokens` はキャッシュ読取の内数） |

どちらも組込みスキーマ付きのYAML文書なので、本ツールのフォーム編集・検証がそのまま使えます（独自スキーマを `_schemas` に置けば上書き可能）。定義例:

```yaml
# _activities/review-concepts.yaml
id: review-concepts
name: システム構想レビュー
agent: reviewer                          # _agents/reviewer.yaml
target: { match: "01_requirements/**/*.{yaml,yml}" }
instruction: |
  actors / capabilities をレビューし、指摘を各文書の review_comments 配列に追記してください。
allowedFiles: ["01_requirements/**"]     # 書込を許可する範囲（省略時は全ファイル）
allowedPaths: ["review_comments*"]       # 書込を許可するパス（省略時は全パス）
limits: { maxTurns: 16 }
gates: { validation: error-free }        # 検証エラーが残る提出は拒否。点検系には no-new-errors
                                         # （既存エラーは許容し、この実行で増えたエラーだけ拒否。同じエラーかどうかは「検査 × 対象の要素」で
                                         #  見分けるため、既存の不足を一部だけ直す提出も通る）・none も選べる
```

### コンテキストレシピ（初期文脈の設計）

エージェントの入力トークンの大半は「毎ターン再送される初期コンテキスト」です。何をどれだけ最初に開示するかは、アクティビティ定義の `context.items` で**利用者が設計**します（**無指定の既定は開示なし**。カタログも明示宣言制）。項目は宣言順に開示され、実行記録のコンテキスト会計（`_runs` の `context` 節・レビュー画面の内訳）で「どの宣言がいくら払わせたか」を確認しながらチューニングできます。

```yaml
context:
  items:
    - kind: catalog                # 文書カタログ（match で対象を絞る）
      match: "00-requirements/*"
    - kind: related                # 対象IDの出現・参照・被参照の軽量なまとめ（related ツールと同形式）
      id: "{target}"
      when: has-target             # 対象の指定がある実行だけ開示
    - kind: entity                 # 対象エンティティの全体像（read_entity ツールと同形式。related の上位互換）
      id: "{target}"
      when: has-target
    - kind: sample                 # 同スキーマの既存文書N件（記述粒度の手本）
      schema: usecase
      count: 1
    - kind: view                   # 横断グリッドの解決結果
      view: usecase-list
      rows: "{target}"             # 行IDのパターンで絞る（プレースホルダ可）
      columns: [機能名, 機能説明]    # 列ラベルで絞る（省略時は全列）
      budgetChars: 4000            # 超過は決定的に打切り
    - kind: doc                    # 指定文書の全文（path で一部だけも可）
      file: todos/10-screens-list.yaml
    - kind: phase                  # 対象文書のフェーズ状態（段階的詳細化）
    - kind: graph                  # ID関係グラフの経路トラバース（多段）
      start: "{target}"
      steps:
        - emit: summary                            # 起点自身（責務定義書内の機能ノード等）
        - { follow: out, via: actor, emit: full }  # actor 参照を辿ってアクター定義の全文まで
```

- **graph（経路トラバース）**: `steps` は連鎖で、各ステップは前ステップの到達ノードから辿ります（`follow: out`＝参照を辿る／`in`＝被参照を辿る。`relation`・`via`・`schema` で絞り込み、`emit` で開示粒度を選択、`limitPerHop` 既定10）。エージェントも同じ語彙の `traverse` ツールを実行中に使えます。レシピに固定する前に CLI `traverse` で試せます（[cli.md](cli.md)）
- **プレースホルダ**: `rows` / `file` / `path` / `id` / `start` には `{target}`（一括実行の対象ID等）・`{id}`・`{file}` などの対象値を書けます。値は `foreach`（本書）の各項目から供給され、解決できないプレースホルダが残る項目は開示されません（対象なしの実行で `{target}` 項目が黙って外れる、が意図した動きです）。
- **開示条件 `when`**: `always`（既定）／`has-target`（foreach の対象値または追加指示がある実行のみ）／`no-target`。「対象が指定された実行では全量ビューを載せない」を宣言で表現できます。
- **予算 `budgetChars`**: 項目ごとの文字数上限。超過は「…（予算 n 文字で打切り）」で決定的に切られます。全文系（doc / related / entity / sample）は無指定でも既定8,000字が掛かります。
- **旧語彙からの移行**: `context.include` / `context.views` は廃止されました（定義エラーになります）。`include: [catalog]` → `items: [{kind: catalog}]`、`views: [x]` → `items: [{kind: view, view: x}]` が等価な書き換えです。旧既定（カタログ自動開示）は引き継がれないため、カタログが必要なら明示してください。
- **prompt caching**: Anthropic 使用時は、システム指示・ツール定義・会話履歴の前方が自動でキャッシュされ（2ターン目以降はキャッシュ読取＝課金が大幅に下がる）、効果は実行記録の `usage.cachedInputTokens` で確認できます。

### プロバイダ・モデルの決まり方

実際に使われる接続先は **エージェント定義の `model:` が最優先**で、未指定の項目だけ「手動実行」タブの選択値で補われます。「AI接続」欄には常に**この実行で実際に使われる**プロバイダ・モデルが表示され、APIキーもそのプロバイダのものを入力します（例: エージェント定義が `provider: anthropic` を指定していれば、OpenAI を選んでいても Anthropic のキーが必要です）。

### 実行の流れ

1. レールの「実行」スペース →「手動実行」タブでアクティビティを選択（追加指示も可能）して「実行」
2. 実行中はターンごとの行動（探索・パッチ・検証）が流れ、エージェントからの**質問**には受信箱・実行タブのカードで回答できます（モーダルではないため、文書を確認しながら回答できます）。いつでもキャンセル可能。**実行中に他のスペースへ移動しても実行は継続**し、状態はステータスバーに表示されます
3. 終了すると**変更セットレビュー**画面になり、ファイル単位で採用／却下を選べます。採用の組み合わせを変えるたびに再検証され、参照整合の破れが警告されます
4. 「選択した変更を適用」で原本に書き込み（適用は Undo 不可ですが、適用前と同じ変更セットが `_runs/` の記録から辿れます）

### 安全性

- エージェントの読み書きはツール経由のみで、書込は `allowedFiles`／`allowedPaths` の範囲かつ予約ディレクトリ（`_schemas` `_agents` `_activities` `_evals` `_skills` `_views` `_runs`）以外に制限されます（定義ディレクトリはメタアクティビティ 本書 でのみ提案可能）
- 探索ツールにはビュー参照（`read_view`）が含まれ、複数文書に散らばる同一IDの情報を、原本上の座標（file / path）つきの一覧として取得できます。`rows`（行IDパターン）・`columns`（列ラベル）で必要な行・列だけに絞れます。文書ビュー（`kind: document`。[views.md](views.md)）は `file` で対象文書を指定して被参照表を取得できます（適用対象が1文書なら省略可）。コンテキストレシピ（`kind: view`。行・列の絞り込み可）で初期文脈として開示することもできます
- ID横断は2段構えです。`related` は隣接の軽量確認（主要フィールドの要約・フェーズ状態・参照・被参照・保有する要素と所属を1回で。被参照は既定20件打切り＝`limit` 引数で拡張）、**`read_entity`** は対象を深く理解するための**エンティティ全体像**（エンティティページのAI版。
アスペクト合成＝出現ごとの所有フィールドと原本座標（そのまま `apply_patch` の対象にできる）・両方向の関係ラベル・カバレッジ充足を1回で返す）です。`list_documents` のカタログにもフェーズ状態が付きます（`match` 引数で絞り込み可）。
コンテキストレシピ（`kind: phase` / `kind: entity`）で、フェーズ状態や対象エンティティの全体像を最初から初期文脈に含めることもできます
- **参照の名前解決**: `read_node`（およびレシピの `doc` 項目）の出力末尾には「参照の解決」——そのノード配下の参照IDを `ID = 名前 [定義元ファイル]` で列挙したフッタ——が付き、ビューのセルでも参照値は `ID（名前）` と注記されます。「ACT-001 が誰か」を確かめるためだけの追加読取りが不要になります（未解決IDは（未解決）と明示）
- 提出には検証ゲート（既定: エラー0）があり、変更が壊す参照（改名の未修正参照元など）はステージング外のファイルでも検出されます
- ターン数・トークン・時間の上限があり、上限到達時も作業は未提出ドラフトとして保全され、レビュー画面から引き継げます
- 文書の内容はエージェントへの指示として扱われません（データとして扱う規範をシステムプロンプトで明示）

### 自動実行（トリガ・連鎖・自動承認）

実行スペースの「自動化」タブで監視を有効化すると、アクティビティ定義の `trigger` に従って自動起動します。実行は常に1件ずつ（直列）で、キュー・履歴・ログを同じタブで確認でき、「停止」でいつでも全消去・中断できます。承認待ちの変更セットは**受信箱**に届き、レール・ステータスバーのバッジで気づけます。

```yaml
trigger: { type: on-change, match: "requirements/**", debounceSeconds: 30 }
# type: manual（既定）… 手動起動のみ
#       on-change      … 対象ファイルの更新後、debounceSeconds 静止してから起動
#       on-invalid     … 更新されたファイルに検証エラーがあるときだけ起動
#       schedule       … everyMinutes ごとに起動
chain:                       # 実行後に連鎖起動（循環・深さ5は自動停止）
  rules:                     # 出力値による分岐（上から評価し、最初に一致した then へ。省略可）
  - when: { outcome: success, noteContains: 重複 }   # 条件はAND: outcome（success/failure/any）/
    then: dedupe-issues                              # changedFiles（採用変更のglob）/ minChangedFiles / noteContains
  onSuccess: file-issues     # どのルールにも一致しないときのフォールバック
  onFailure: notify
retry: { maxAttempts: 2 }    # 失敗時、理由をフィードバックして再実行（同一失敗の繰り返しは打ち切り）
approval: auto               # 自動適用（下記の条件つき）。既定は human（承認待ち）
```

- **`approval: auto` の安全条件**: 提出ゲート通過＋書込スコープ内＋対象がエディタで**編集中でない**こと。条件を欠くと自動でも「承認待ち」に降格します。人間の編集と自動実行が衝突しない排他がこれに当たります。派生スキーマ（[schema.md](schema.md)）の**導出元文書**への変更を含む場合も、検証ルールが無人で変わることを防ぐため常に承認待ちへ降格します。
- **巻き戻し**: 自動適用は適用前の原文を実行記録（`_runs`）へバックアップし、`./gradlew runCli -q --args="revert <workspace> _runs/xxx.yaml"` で復元できます（適用後に更に変更されたファイルは競合として拒否。`--force` で上書き）。
- バックアップの保存に失敗した場合は適用を中止します。適用途中や完了記録の保存に失敗した場合は、原本と記録を確認してください。完了未確認のバックアップは通常の巻き戻しを拒否し、確認後に `--force` で復旧できます。
- **承認待ちの耐久性**: 変更セットは `_runs/xxx-changeset.yaml` にも保存されるため、アプリを閉じても後から `apply` コマンドで適用できます。
- **自己変更では再発火しない**: エージェントが適用した変更で自分の on-change が再度発火することはありません。
- **エージェント同士の相談**: エージェントは `delegate` ツールで別のエージェント（例: レビュー担当）へ読み取り専用の相談ができ、ドラフト（ステージング）を見せて所見を受け取れます。編集・提出は依頼元だけが行います。

CLIからも実行できます: 単発は `agent`、常駐監視は `watch`（`--once` で1回だけ判定・消化）。`./gradlew runCli -q --args="watch <workspace>"`（定義一覧は `activities`。APIキーは環境変数から）。

### 一括実行（foreach: 同一アクティビティの連続実行）

「1実行=1文書」のアクティビティを対象違いで連続実行し、複数の文書を一気に整備できます。アクティビティ定義に `foreach`（対象の列挙）を宣言すると、手動実行タブに「一括実行（対象を選択）」ボタンが現れます。押すと対象の一覧が**チェックボックス付き**で表示され（既定は全選択。全選択／全解除も可能）、選択した対象だけが1件=1実行として自動化キューへ投入されます（自動化タブで「自動実行」を有効にすると直列に消化。項目の失敗は後続の項目を塞ぎません）。

```yaml
foreach:
  source: view             # 列挙元: view / issues / search / files / ids / query
  view: usecase-list       # source: view … ビューの行を対象にする
  where: detail-missing    # detail-missing（詳細文書が未作成の行のみ。既定）/ all（全行）
  as: "対象: {id}"          # 1件ごとの追加指示テンプレート（{id} {title} {file} {path} {message} 等）
  limit: 10                # 1回の投入で展開する上限（既定 20）
# source: issues … 検証の指摘ごと（severity: error / warning、match で対象ファイルを絞る）
# source: search … 検索ヒットごと（text / pathGlob / refTo / unresolved / schemaIds / match）
# source: files  … match（glob）に一致する文書ごと
# source: ids    … idPattern（× schemaIds）に一致する論理IDごと
# source: query  … グラフパターン照合（ビューのクエリ行と同じ語彙）の束縛行ごと。
#   query: { match: [...], where: [...] } を宣言し、as やコンテキストレシピから
#   束縛名で値を参照できる（{scr}=そのID・{scr_file}=定義出現のファイル。{id} 等は先頭束縛）
```

- 対象の列挙は起動時に1回だけ・`limit` 件まで。**「次の対象選び」はLLMではなく機械が行い**、各実行には対象を明示した追加指示が注入されます（アクティビティ本体の指示・権限・ゲートはそのまま）。
- `trigger: manual` のアクティビティ専用です（トリガ・連鎖など自動起動からの展開は不可）。
- 承認は通常どおり働きます: `approval: human`（既定）では項目ごとに承認待ちが受信箱へ届きます。
- CLI では `agent <workspace> <activity> --foreach` が同じ列挙を直列に一括実行します。`--apply` 併用時は1件ごとに適用するため、後続の実行から先行の成果が見えます（省略時は変更セットの表示のみ）。

## 外部からの提出を受信箱で確認する

外部作業の提出記録は、実行スペースの「受信箱」→「外部からの提出」に表示されます。
現在は共通サービスと受信箱まで実装済みで、API・MCP・Web からの接続と権限登録はまだ公開していません。

1. 「内容と結果」で提出者・変更内容・状態を確認します。
2. 承認待ちなら「差分と検証を再確認」を押し、自動値を含む保存内容と検証結果を確認します。
3. 「承認して保存」で提出全体を確定します。検証エラー、未保存編集、競合、確認後の変更、接続者の権限失効があれば保存しません。
4. 「却下」は確認後に採否だけを記録し、原本を変更しません。「受信箱へ戻る」では承認待ちのまま残ります。

外部提出の承認はファイルに保存され、Undo には追加されません。変更対象の文書に触れる過去の履歴は戻せなくなります。
再起動後も提出と採否を読み直せますが、自動では承認・再実行しません。
「一部保存」「結果不明」は文書別の保存状態を確認してください。結果不明の照合を行う専用画面はまだありません。
内蔵エージェントの通常のレビューと検証設定は従来どおりです。

## 自己改善（メトリクス・評価セット・メタアクティビティ）

エージェント運用の品質を測定し、定義の改善をツール内で回すための機能群です。実行スペースの「計測・評価」タブで行います。

### 実行メトリクス

`_runs` の実行記録から、アクティビティ別に**提出率・採用率・却下ファイル率（部分採用で却下された割合＝人間による修正量の代理指標）・自動適用と巻き戻し・平均ターン・トークン**を集計します。実行のたびに追加の記録は不要で、過去の実行記録もそのまま集計対象です。CLI: `metrics <workspace> [--activity id]`。

### 評価セット（アクティビティの「テスト」）

`_evals/*.yaml` に**ゴールデン入力と期待結果**を定義すると、アクティビティを回帰評価できます。評価は**ワークスペースの一時コピー（サンドボックス）上で実行**されるため、原本は変更されません。レポートは `_runs/eval-*.yaml` に保存されます。

`setup.file` は通常の相対パスに限定します。絶対パス・親ディレクトリ参照・予約領域・隠し領域の指定は拒否します。コピー元の外部リンクも評価エラーとなります。

```yaml
# _evals/review-eval.yaml
id: review-eval
activity: review-concepts        # 評価対象のアクティビティ
variants:                        # 省略可: A/B比較（モデル・エージェント・追加指示・文脈レシピの差し替え）
- name: base
- name: strict
  instruction: 指摘は最大3件に絞ってください。
  # model: { provider: anthropic, id: claude-opus-4-8 } / agent: 別エージェントID も指定可
- name: lean-context             # 文脈レシピの差し替え（本書と同じ items 書式。空 = 開示なし）
  context:
    items:
      - kind: catalog
cases:
- id: vague-actor-is-flagged
  setup:                         # ゴールデン入力: サンドボックスへ上書き・作成するファイル
  - file: 01_requirements/01-system-concepts.yaml
    content: |
      （意図的に曖昧な定義を含むYAML全文）
  expect:                        # 宣言的な期待結果（すべて満たせば合格）
    status: submitted            # submitted（既定）/ aborted / limit / error / any
    errorFree: true              # 終了時点の検証エラー0
    changedFiles: ["01_requirements/**"]   # 各globに1件以上の変更が必要
    unchangedFiles: ["03_designs/**"]      # マッチする変更があれば不合格
    content:                     # 結果（ステージング）の内容チェック
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, exists: true }
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, contains: ACTOR-USER }
```

期待結果を「出力文字列の完全一致」ではなく構造条件で書くのは意図的な設計です。モデルの揺らぎに対して壊れにくく、**良い合格条件を書くこと自体が業務設計（ハーネスエンジニアリング）** になります。CLI: `eval <workspace> <eval-id>`（引数なしで一覧）。

レポート（`_runs/eval-*.yaml`）には変異別の合格率・ターン・トークン（キャッシュ読取の内数込み）とケース別のトークンが記録されます。variants の `context` 差し替えと組み合わせると、**コンテキストレシピの絞り方を「合格率×トークン」のデータで選べます**（絞りすぎると探索ターンが増えて逆にコストが増える、といったトレードオフの検出。本書）。

### メタアクティビティ（定義の改善提案）

アクティビティ定義に `meta: true` を付けると、そのエージェントは `_agents` / `_activities` / `_evals` / `_skills` / `_views` の**定義文書そのものへの変更を提案**できます（例: 実行記録の傾向を踏まえた指示の改善、評価ケースの追加、エクスポート列の追加）。安全のための制約:

- **承認は human 固定**。`meta: true` かつ `approval: auto` は定義エラーになります（エージェントが自分の権限・挙動を変える変更は必ず人間が承認）
- `_schemas` と `_runs` への書込は meta でも**常に不可**
- ステージされた定義が**実際にパース可能であること**が提出ゲートに加わります（壊れた定義は提出できず、自己修正ループに入る）

「メタアクティビティで改善案を提案 → 評価セットで変異比較 → レビューで採用」という改善サイクルがツール内で完結します。

## skill（インポート・エクスポート）

Excel・CSV等の現実の業務フォーマットと、YAML原本を接続する機能群です。設計スペースの「連携（skill）」から定義の一覧・作成と、取り込み・出力の実行を行います。変換は `_skills/*.yaml` に**宣言的に**定義します（例外は明示許可制のコード実行skill。後述）。

### インポート（表形式 → YAML原本）

xlsx / csv / json / markdown / docx（Word文書内の表）を、列マッピングでYAML文書群へ取り込みます。**取り込んだ時点からYAMLが原本**です。

```yaml
# _skills/import-issues.yaml
id: import-issues
kind: import
input: { format: xlsx, headerRow: 1 }        # xlsx / csv / json / markdown / docx
# docx は Word 文書内の表を読みます: input: { format: docx, table: 1 }（table = 何番目の表か。1始まり）
target: { file: "issues/{ID}.yaml" }         # {列名} が行の値で置換される（1行1文書）
mapping:
- { column: ID, path: id, required: true }
- { column: 件名, path: title, required: true }
- column: 状態
  path: status
  map: { 未着手: open, 対応中: in-progress, 完了: done }   # 値の変換辞書
- { column: 優先度, path: priority, type: int }            # 型変換（string/int/number/boolean/auto）
- { column: タグ, path: tags, split: "," }                 # 区切りで配列化
```

重要な性質:

- **既存文書はマップした項目だけ更新**されます（値が変わる場合のみ）。YAML側に追記した項目（レビューコメント等）は再インポートで消えません
- 適用前に**プレビュー**（作成／更新／変更なし／エラー）が出ます。適用は変更セット経由で、競合検出・検証ゲート・オール・オア・ナッシングが効きます
- エクスポートした帳票をそのまま再インポートすると**変更セットは空**になります（往復の無損失）

#### 行をひな型で組み立てて、配列へ追記する（`build`・`target.path`）

列の対応表で書けない取り込み（年月日が別の列・金額に `¥` と桁区切り・ID が無い・飛ばしたい行がある）は、`mapping` の代わりに **`build`**（[変換定義](views.md)と同じひな型）を書きます。CSV の各行は「見出し → セル」の項（object）になり、ひな型は見出しの名前でセルを読みます（空のセルは項目ごと無いので、`exists` の条件で見分けられます）。`target.path` を書くと、1 行 1 文書ではなく、文書の中の配列の末尾へ明細を足します。

```yaml
# _skills/import-bank.yaml —— 銀行の入出金明細の CSV を、月ごとの取引文書の配列へ
id: import-bank
kind: import
input: { format: csv, encoding: windows-31j }   # 文字コード（省略時 UTF-8）
target:
  file: { $format: "book/tx/{ym}.yaml", $with: { ym: { $date: { $copy: date }, $as: yyyy-MM } } }
  path: entries                                   # この配列の末尾へ追記
  id: { path: id, prefix: { $format: "TX-{ymd}-", $with: { ymd: { $date: { $copy: date }, $as: yyyyMMdd } } }, digits: 2 }
  key: [date, kind, amount, memo]                 # この項目が同じ明細が既にあれば取り込まない
build:
  $when: { path: 月, exists: true }               # 月が空の行（期首の残高行）は飛ばす
  $then:
    date: { $date: { $format: "{対象日（自）_年}-{月}-{日}" } }      # 2021-8-21 → 2021-08-21
    kind: { $first: [ { $when: { path: ご入金, exists: true }, $then: income }, expense ] }
    amount: { $number: { $first: [ { $copy: ご入金 }, { $copy: ご出金 } ] } }   # "¥10,000" → 10000
    memo: { $trim: { $copy: 摘要 } }              # 前後の空白を落とし、空なら書かない
```

- **`target` の式は、組み立てた明細を読みます**（`{$copy: date}` は上で組み立てた `date`）。`file` は文字列（`{項目}` が明細の値）でも、`$format` のひな型でも書けます。
- **採番（`target.id`）**: 組み立てた明細に `id` が無ければ、接頭辞（明細で埋めるひな型）＋連番を付けます。連番は、ワークスペースの既存 ID と取り込み先の配列から、同じ接頭辞の最大番号の次（`digits` 桁のゼロ埋め。既存が 99 なら 100）。同じ取り込みの中でも続き番号になります。
- **同じ明細の見分け（`target.key`）**: 配列への取り込みは**追記だけ**です。`key` の項目の値が同じ明細が既にあれば飛ばし（プレビューに「同じ明細 n 件を飛ばした」と出ます）、手で直した項目（費目など）を CSV の値で戻しません。同じ CSV を 2 回取り込んでも増えません。
- **見出しの行が無い CSV**: `input: { format: csv, columns: [日付, 摘要, 入金, 出金, 残高] }` のように列の名前の並びを書くと、1 行目からデータとして読みます。`mapping` の `column` や `build` の中のパスは、この名前で書きます。
- **飛ばす行**: `build` の `$when` に合わない行は取り込まず、プレビューに「条件に合わず飛ばした行」の数が出ます。ひな型が読む列がどれも見出しに無いときは誤り（文字コードや見出しの行の取り違え）として止まります。
- **値をそろえる指示**: `$date`（`2021/8/21`・`20210821`・`2021年8月21日` を `yyyy-MM-dd` に。`$as` で `yyyyMMdd`・`yyyy-MM` などの形）・`$number`（`¥` と桁区切りと全角、`▲` の負を許して数に。`$as` で `00` のような形の文字に）・`$trim`（前後の空白を落とし、続く空白を 1 つに。空なら「無い」）・`$format` の `$with`（計算した値を穴へ）・`$value`（値の式で計算する。例 `{$value: {multiply: [{path: 単価}, {path: 数量}]}}`）。ひな型の指示の一覧は [schema.md](schema.md)「新しい文書の置き場所とひな型」。
- `mapping` でも `target.path` は書けます（列の対応表で組み立てた明細を配列へ追記）。`target.id` と `target.key` は配列への取り込み（`target.path`）だけで使えます。
- 1 行 1 文書の取り込み（`target.path` なし）で、`build` が複数の行を同じ文書に**同じ内容**で組み立てたときは 1 つに畳みます（例: 明細の表の見出しの値から、期間の文書を 1 つ作る）。内容が違えば誤りです。

### エクスポート（YAML原本 → 派生成果物）

対象文書（glob）を行×列に展開し、xlsx / csv / markdown / json / html を再生成します（形式は出力ファイルの拡張子で決まります）。出力は**いつでも原本から作り直せる派生物**で、YAMLへの出力は定義段階で拒否されます。

```yaml
# _skills/export-issues.yaml
id: export-issues
kind: export
source: { match: "issues/**/*.{yaml,yml}" }  # rows: 配列パス を指定すると配列要素ごとに1行
output: { file: exports/issues.xlsx, sheet: 課題一覧 }
columns:
- { header: ID, path: id }
- { header: 件名, path: title }
- { header: タグ, path: tags, join: "," }
```

`source: { view: ビューID }` と書くと、`_views` のビュー定義（[views.md](views.md)）を行×列の源にして「ビューで見えている表をそのまま帳票へ」出力できます（このとき `match` / `rows` / `columns` は書けません。1列目は行のID、バックリンク列は参照元IDの列挙になります）。

```yaml
# _skills/export-board.yaml
id: export-board
kind: export
source: { view: screen-catalog }
output: { file: exports/screens.html }
```

### コード実行skill（kind: run・明示許可制）

宣言型では書けない変換・定型手順のために、任意のコマンドを実行する skill を定義できます。**サンドボックス外への作用**のため、次の明示許可制が機械的に強制されます。

```yaml
# _skills/normalize.yaml
id: normalize
name: 正規化スクリプト
kind: run
run:
  command: [python, scripts/normalize.py]   # コマンドと引数
  workdir: .                                # ワークスペース相対（既定 "."）
  timeoutSeconds: 120
  writes: ["work/**"]                       # ワークスペース内への書込を宣言するglob
```

- **実行前に人間がコマンド内容と権限を承認**します（GUIは連携画面の承認ダイアログ、CLIは `--yes` フラグ）。承認なしに実行される経路はありません
- 承認は「承認した時点の定義内容」に紐づき、**定義が変わると失効**します（承認後の定義すり替え防止）
- エージェント・自動実行（トリガ）からは起動できません。メタアクティビティによる定義の**提案**は可能ですが、実行は常に人間の承認が必要です
- 実行後にワークスペース内の変更を検出し、`writes` 宣言外の変更を**警告**、予約ディレクトリ（`_schemas` 等）の変更を**重大な逸脱**として報告します（事後検査であり書込は防げないため、事前承認が前提です）

### skill を含む出発点

テンプレート「課題管理」（`issues`）は、Excel の台帳を取り込み、YAML 原本で運用（棚卸しのアクティビティと評価つき）し、Excel 帳票を再出力する往復をそのまま体験できる雛形です。
展開は「新しいワークスペースを作る…」か CLI の `init`（[README.md「新しいワークスペースを作る」](README.md)・[cli.md](cli.md)）で行い、既存のファイルは上書きしません。
