# 設計の検証

スキーマに書く検査の語彙と、検証の見え方。基本の型や項目の書き方は [schema.md](schema.md)、ファイルの場所の検査は [files.md](files.md) を参照してください。

## エンティティ型宣言（`entity`: 出現の型と定義／詳細化の役割）

同一IDの複数文書出現（段階的詳細化。[ids.md](ids.md)）では、「どの出現がそのIDの**定義（誕生）**か」をこれまで機械が知りませんでした。スキーマのルートに `entity:` を宣言すると、この文書群の出現にエンティティ型と役割が付きます。

```yaml
# 単一型（この文書群の全IDが1つの型）
entity:
  type: screen          # エンティティ型名（ワークスペース内で一意にする運用）
  idPattern: "SCR-*"    # この型のID命名規約（省略可。逸脱は検証が警告する）
  defines: true         # この文書群の出現が「定義（誕生）」。省略時 false = 詳細化

# 複数型（idPattern か idType で判別。どちらも無い宣言は1つまで＝残り全部の受け皿）
entity:
  - { type: screen, idPattern: "SCR-*", defines: true }
  - { type: usecase, idType: ユースケースID, defines: true }   # ID の型（definitions の id を狭めた型。schema.md「型の定義」）の形式で判別

# アスペクト宣言（省略可）: この出現がエンティティのどの「側面」を所有するか
entity:
  type: screen
  idPattern: "SCR-*"
  aspect: design          # 側面名（省略時はスキーマID）。レジストリの entities 節で表示名・順序を宣言できる
  owns: [layout, memo]    # この出現が所有するフィールドの限定（省略時は宣言フィールド全部。id は常に対象外）
```

宣言の効果（宣言のないスキーマは従来どおり＝**非破壊**）:

- **ジャンプ・表示が定義出現に安定**: 同一IDの複数出現があるとき、参照ジャンプ・タイトル解決は定義出現（`defines: true` の文書群の出現）を優先します（従来は「パス順で最初の出現」）。
- **要素の形で決める書き方**: object の定義に `entity: { type: screen-item, defines: true }` と書けば、その形の要素がその型になります（[schema.md](schema.md)「オブジェクト型」）。
- **ID の決まりは 2 通り**: `idPattern`（glob）か `idType`（ID の型の名前。`画面ID: { type: id, pattern: "^SCR-\\d{3}$" }` のような定義。型の形式＝正規表現で判別し、ID の項目の `type: 画面ID` と同じ決まりを 1 か所に書けます）。両方書けば両方に合う ID がその型です。`idType` が未知の名前・id でない型なら定義エラーです。
- **エンティティ整合の検証（既定は警告）**: 定義出現がどこにもないID（浮遊詳細化）／定義出現が2文書以上にあるID（定義競合）／`idPattern` / `idType` に一致しないID（命名逸脱）／同一IDが異なる型で出現（型競合）を、各出現のID要素の座標つきで指摘します。定義出現の一意性（浮遊詳細化・定義競合）は、関係レジストリ文書の `enforcement: { definingUniqueness: error }` でエラーへ昇格できます（暗黙運用をやめる opt-in。後述）。
- **アスペクト（`aspect` / `owns`）＝エンティティ全体像の合成**: 各出現が「エンティティのどの側面（フィールド群）を所有するか」を宣言します。エンティティページ（[views.md](views.md)）・エージェントの `read_entity`（[ai.md](ai.md)）・CLI `entity show`（[cli.md](cli.md)）は、全出現を「定義出現 → レジストリのアスペクト宣言順」に並べ、所有フィールドを座標つきでマージした**エンティティ全体像**として表示します。
複数の出現が同じフィールドを所有していると検証が警告します（「同じ情報を重複記載しない」の機械化。誤検知を避けるため、双方に `entity` 宣言があり少なくとも一方が明示的な `owns` を持つ組だけを判定します）。
- sample-workspace の `_schemas/data-model.yaml`（`entity-model` 型）・`_schemas/table-design.yaml`（`table-design` 型）が実例です。

## 関係レジストリ（`kind: relations`: 関係語彙の宣言）

参照の関係種別（`type: ref` の `relation`）は自由な文字列です。`_schemas` に `kind: relations` の文書を置くと、ワークスペースの関係語彙を宣言できます（`kind: library` と同様、この文書自体はどの文書にもマッチしません）。

```yaml
# _schemas/relations.yaml
id: workspace-relations
kind: relations
enforcement:                    # 強制スイッチ（後述。省略可＝従来の lint のまま）
  undeclaredRelation: error
  definingUniqueness: error
entities:                       # エンティティ型のレジストリ宣言（省略可）: 型の表示名とアスペクト順序
  - type: table-design
    label: テーブル設計          # エンティティページ・レンズ・read_entity で使う表示名
    aspects:                    # 全体像の合成でのアスペクト（entity.aspect）の並び順と表示名
      - { name: design, label: テーブル設計 }
relations:
  - name: derives               # スキーマの ref フィールドの relation と一致させる
    label: 由来する              # 参照方向（この要素からの参照）の表示ラベル
    inverseLabel: 実装される     # 被参照方向（この要素への参照）の表示ラベル
    source: [table-design]      # 参照を書く側のエンティティ型（宣言すると対象型・出次多重度の検証が効く）
    target: [entity-model]      # 参照先のエンティティ型（宣言すると対象型・入次多重度の検証が効く）
    cardinality: { inMin: 1 }   # in / out の下限上限（source / target の型宣言がある側にだけ効く）
    acyclic: true               # 非循環の宣言（違反は常にエラー）
    level: warning              # 対象型・多重度の指摘の重大度（warning / error。既定 warning）
    description: 1:N 詳細化の逆リンク
```

- **逆方向ラベル表示**: バックリンクを表示する全ての面（右パネルの関係タブ・ID横ぐし・ビューのバックリンク列・文書ビュー・グラフ・エージェントの `related`）で、relation 名の代わりに `label`（参照方向）／`inverseLabel`（被参照方向）が表示されます。未宣言の relation は従来どおり名前のまま表示されます。
- **グラフ整合検証**: レジストリの宣言は検証の制約になります（検証パネル・CLI `validate`・変更セット適用・エージェントの提出ゲートに同じ判定が乗ります）。このうち**対象型と多重度は組込みの定義体**です（後述「検査の定義と語彙の定義」）——関係の宣言の `source` / `target` / `cardinality` という書き方は、検証の前に基本の検査（クエリ＋参照の本数の比較／型の否定＋参照の場所への指摘）へ展開され、スキーマの `constraints` と同じ規則で評価されます。
展開結果は CLI `checks <workspace> <レジストリのID>` で確認できます。多重度の指摘は他の検査と同じく、同じ ID が書かれた他の文書にも案内（警告級は情報・エラー級は同格のエラー）が出ます。
  - **対象型**: `source` / `target` を宣言した関係で、エッジ両端のエンティティ型が宣言と食い違う参照を、参照値の座標で指摘します（型宣言のないエンティティ・未解決参照には黙ります。参照を書いた要素は「その参照を含む、最も内側の ID を持つ要素」です）。
  - **多重度**: `cardinality` の `outMin` / `outMax` は「そのエンティティが書く参照の合計」（複数出現に分けて書いても合算）、`inMin` / `inMax` は「そのエンティティへの被参照数」を検査します。
判定対象は `source` / `target` の型宣言に一致する型つきエンティティだけです（「誰が満たすべきか」を推測しません）。座標は該当エンティティの定義出現です。被参照不足（`inMin`）の指摘は、クリックメニューに**「参照の追加先を開く: <文書>」**が出ます（追加先候補＝source 型を宣言するスキーマの文書のうち、対象IDのファイルと出現を共有するもの（同一IDの詳細化文書）か、台帳型スキーマの唯一の文書。
機械が選べない場合は出ません）。
  - **非循環**（これも組込みの定義体です——「その関係を何段でも辿って、自分自身へ戻る流れが無いこと」を、`edge` の `repeat` で書いています。循環の経路は、その参照から始まる最短の循環を示します）: `acyclic: true` の関係で循環ができると、「循環経路（A → B → A）」を添えて循環を構成する参照値の座標へ**常にエラー**が出ます。
- **強制スイッチ（`enforcement:`）**: ワークスペース単位の opt-in で破壊的な強制を有効化します。各キーは3値（未宣言＝従来のまま／`warning`／`error`）です。
  - `undeclaredRelation`: レジストリにない relation を使う参照を、文書側でも参照値の座標で指摘します（未宣言時はスキーマ読込エラー一覧の lint のみ）。
  - `definingUniqueness`: `error` で浮遊詳細化・定義競合をエラーへ昇格します（エンティティ宣言のあるスキーマで定義出現の一意性を強制＝「最初の出現＝定義」ヒューリスティクスの廃止）。
  - 同一キーを複数のレジストリ文書で宣言するとロードエラーです。
- **未宣言 relation の lint**: レジストリを1つでも置くと、スキーマの ref フィールドがレジストリにない relation を使っている場合にスキーマ読込エラー一覧へ警告が出ます（レジストリがなければ何も出ません）。
- **自動推測**: CLI `infer-relations <workspace>` が、索引の参照実績（relation・キー名・参照元／先のエンティティ型）からレジストリのドラフトを生成します（`--apply` で `_schemas/` へ保存。`inverseLabel` は TODO コメント付きなので実際の語彙に書き換えてください）。
- レジストリ文書には専用のメタスキーマ（`builtin-relations`）が適用され、フォーム編集・検証がそのまま使えます。

## 属性付き参照（`{to, 属性...}`: エッジへの注記）

参照そのものに小さな注記（例: アクター参照の「役割」）を付けたい場合、`type: ref` のフィールドに `fields:`（属性の型宣言）を書くと、オブジェクト形式が使えるようになります。

```yaml
# スキーマ
- key: actors
  type: array
  item:
    type: ref
    relation: uses
    fields:                 # エッジ属性の型宣言（これがある場合だけオブジェクト形式を許可）
      - key: role
        type: string

# データ（スカラー形式とオブジェクト形式を混在できる）
actors:
  - ACT-USER                # 従来どおりのスカラー参照
  - to: ACT-ADMIN           # 予約キー to = 参照値（ジャンプ・パッチの座標は to の値）
    role: 承認者             # 兄弟キー = エッジ属性
```

- 参照の解決・検証・ジャンプは `to` の値に対して従来の ref と同じに働きます。属性は object として検証されます（未宣言キーは `unknownFields` ポリシー）。
- バックリンク・`related` の表示には属性が「（role: 承認者）」の括弧注記で添えられます（値はIDのままです）。
- フォームでは参照行の下に属性行が表示され、スカラー形式の値には「属性を追加」でオブジェクト形式へ変換できます。
- **使い分けの規約**: エッジ属性は「それ自身がIDを持たない注記」です。属性の中に `ref` / `id` は書けません（メタスキーマ検証でエラー）。関係自体を他から参照したい・詳細化したい場合は、従来どおり **1:N 具体化**（関係を表す新しいIDを持つ要素＋逆リンク。[ids.md](ids.md) の規約）を使ってください。
- `fields` 宣言のない ref にオブジェクトが来た場合は従来どおり型不一致です（ヒューリスティクス検出のスキーマなし文書にも適用されません）。

## 文書参照（`target: document`: 文書そのものへの参照）

参照先が「要素（論理ID）」ではなく「文書そのもの」の場合、ref フィールドに `target: document` を宣言します（既定は `entity`。値の形から推測はしません）。

```yaml
- key: spec
  type: ref
  target: document    # 参照先は文書ノード（documentId）
```

- 参照値は **documentId**（文書ルートに `_document: { id: ... }` があればその値、なければワークスペース相対パス）です。
- 解決・検証は文書の名前空間に対して行われ、エンティティIDには混ざりません（未解決は台帳内でエラー・台帳外の文書では情報レベル）。
- フォームの候補は documentId＋文書名（`_document.name`）で提示され、ジャンプは参照先の文書を開きます。参照された文書側では右パネルの関係タブに「この文書への参照」が表示されます。
- `_document.id` を宣言した文書への参照は、ファイルを移動しても壊れません（パス参照は後述の移動機能が書き換えます）。

## パターン制約（`constraints`: グラフパターンの存在／不在／件数／値比較の検証）

カバレッジルール（被参照数）よりも複雑なトレーサビリティ要件——「このパターンが存在すること（`exists`）／しないこと（`absent`）／解の件数が範囲内であること（`count`）／解ごとに束縛間の値比較が成り立つこと（`check`）」——を、グラフパターン照合（ビューのクエリ行と同じ語彙）で宣言できます。カバレッジの一般形で、既存の `coverage` を置き換えるものではありません。

```yaml
# ユースケースのスキーマ: どの画面からも到達できない孤立ユースケースを検出する
constraints:
  - id: reachable
    description: いずれかの画面から利用されること
    match:
      - node: { entity: usecase, bind: uc }   # 起点束縛（先頭 node。kind: entity 限定）
      - edge: { relation: uses, dir: in }     # 被参照を1段辿る
      - node: { entity: screen }
    expect: exists                            # exists = 解が1つ以上 / absent = 解がない
    level: warning                            # warning（既定）/ error
    # activeFrom: 設計                        # このフェーズに達するまで判定保留（coverage と同じ）
    # where: [...] / also: {...} / limit: n   # クエリ行と同じ語彙が使える
  - id: tested-twice
    description: テスト項目が2件以上あること
    match:
      - node: { entity: usecase, bind: uc }
      - edge: { relation: verifies, dir: in }
      - node: { entity: test-item, bind: item }  # 数えたい対象に bind を書く
    count: { min: 2 }                            # 解（束縛の組）の件数範囲。expect と排他。max も指定可
```

```yaml
# 画面項目のスキーマ: 項目の最大文字数が、参照する業務データ型の最大桁を超えないこと
constraints:
  - id: length-within-dtype
    description: 画面項目の最大文字数は業務データ型の最大桁以内であること
    match:
      - node: { entity: screen-item, bind: si }
      - edge: { relation: dtype }
      - node: { entity: data-type, bind: dt }
    check:                                       # 解ごとの判定述語（expect / count と排他・複数書けばすべて成立が期待）
      - lte: [{ of: si, path: max_length }, { of: dt, path: max_digits }]
    level: error
```

- 判定は「**起点束縛に一致する各エンティティ**について、残りのパターンに解があるか（`expect`）／解が何件あるか（`count`）／解ごとに値比較が成り立つか（`check`）」。`count` の件数はクエリ結果の行と同じ同一性（`bind` した列の組の distinct）で数えます。指摘の座標は起点の**定義出現**（なければ先頭出現）で、その出現を持つ文書の検証にだけ現れます。
- **束縛間の値比較 `check`**: 項目は `{演算子: [左, 右]}`（例 `{lte: [{of: 束縛, path: 相対パス}, {of: 束縛, path: 相対パス}]}`。複数書けばすべて成立が期待）。演算子は下の「値の条件」の一式。
判定は解ごとに**出現の組**（同一IDの定義出現＋詳細化出現のどれから読むか）を走査し、**違反する組（反例）を1つでも発見したら違反**・値が読めない／順序比較で数値でない組しかなければ黙ります（判定保留）。1項目の中で同じ束縛を両辺に書いた場合は**同じ出現**から読みます（出現をまたいだ突合はしない）。
違反メッセージには反例の値の組（例 `si=SI-001（max_length: 20） > dt=DT-003（max_digits: 10）`）が列挙され、各IDへジャンプできます。
- `where` はノードを値で絞る条件で、1件につき条件を一つ書きます（複数の条件は `where` に並べる＝すべて満たすノードが対象）。
  `equals` / `notEquals`・`exists: true|false`（項目が書かれているか）・`empty: true|false`（`false` = 中身のある値がある／`true` = 書かれていないか、空文字・空の配列・空の object）と、下の「値の条件」（`oneOf` / `matches` / `startsWith` / `endsWith` / `contains` / `lt` / `lte` / `gt` / `gte`。
比べる相手は決まった値）。同じ ID が複数の文書に書かれているときは、**どれかの文書の値**が条件を満たせば成立します。`notEquals` は「値が1つ以上あり、どの出現の値も指定値でない」ときに成立します（例 `{of: br, path: status, notEquals: approved}` で「承認済み**以外**」を捕まえる。
値がなければ黙る）。
- **値の条件**（`check` と `where` が同じ演算子・同じ判定を共有します）: `eq` / `ne`（文字列として等しい・等しくない。`12` と `12.0` は別の値——数値として比べたいときは値の式 `number` を通す）・`lte` / `gte` / `lt` / `gt`（順序の大小。
**比べ方は値を読んだ項目の型で決まります**: `int` / `number` なら数、`date` / `time` / `datetime` なら日付・時刻・日時の値（`09:30` と `09:30:00` は同じ時刻）。項目の型が分からなければ数。その種類として読めなければ評価しません。
決まった値どうしを日付として比べるときだけ `{lte: [左, 右], type: date}` と添えます。例 `{lte: [{of: t, path: start}, {of: t, path: end}]}`＝開始日は終了日以前。`samples/todos` の `todo-detail.yaml` の「期限は作成日以降」が実例）・`oneOf`（選択肢のどれかと等しい。`check` では `{oneOf: [左, [選択肢, ...]]}`、`where` では `oneOf: [値, ...]`）・`matches`（正規表現の**全体**一致。
フィールドの `pattern` と同じ規則。決まった値で書いた正規表現が読めなければスキーマの読み込みエラー）・`startsWith` / `endsWith` / `contains`（前方・後方・部分の一致）。`where` では `eq` / `ne` の代わりに `equals` / `notEquals` を使います。
- **型の検査**: 同じ `where` と `check` を object の定義に書くと、その型の要素ごとに評価されます（`of` を省くとその要素。ID の無い要素にも書ける。[schema.md](schema.md)「オブジェクト型」）。
- **型の「または」と否定**: `node` の `entity` には型の並びを書けます（`entity: [usecase, batch]`＝どれか）。`node: { not: { entity: [...], schema: ..., id: ... } }` は、その絞り込みに**合わない**ノードだけを残します（型が宣言されていない要素は、型の否定では残しません＝判定保留）。
- **条件の否定と「または」**: `where` と `check` の各項目には、条件のほかに `{not: 条件}`（条件が成り立たない）と `{or: [条件, ...]}`（どれかが成り立つ）を書けます。入れ子は1段まで（`or` の中に書けるのは条件かその否定）・「かつ」は並べて書きます・`where` の `or` は同じ束縛（`of`）の条件どうしに限ります。
値が無くて判定できない条件は、否定しても判定できないままです（`where` では選ばれず、`check` では指摘しません）。`check` の `or` は、どれかが成り立てば成立・成り立つものがなく判定できない条件が残れば判定保留・すべて成り立たなければ指摘します。
- **参照の束縛と、参照の場所への指摘**: `edge` に `bind` を書くと、辿った**参照そのもの**（どの文書のどこに書かれた参照か）を束縛します。束縛した参照は解の同一性に加わり（同じ相手への参照が2本あれば2つの解）、`reportAt: { ref: 束縛名 }` で指摘を**その参照が書かれた場所**へ出せます（`expect: absent` か `check` と組み合わせ、見つかった解ごとに、その参照が書かれた文書の検証で報告します）。
- **参照を書いた要素と、入れ子の線（`contains`）**: 参照の線は、向きによらず「その参照を含む、**最も内側の ID を持つ要素**」が書いたものとして辿ります。出ていく向き（`dir: out`）は**その要素が直接書いた参照だけ**、入ってくる向き（`dir: in`）の相手は**その参照を直接書いた要素**です（A から出て X に着くなら、X へ入ってくる相手に A がいます）。
入れ子の要素（例: 画面の中の画面項目）が書いた参照は、外側の要素（画面）の参照ではありません。入れ子を辿りたいときは、入れ子の線 `edge: { contains: true }` を使います——その要素の**直下に入れ子になった ID を持つ要素**へ進みます（`dir: in` は外側の要素へ。
文書ノードとの間は、その文書にいちばん外側で書かれた要素）。`repeat` と組み合わせれば何段の入れ子でも辿れます。例「画面の配下のどの要素が書いた参照でも辿る」: `match: [{node: {entity: screen, bind: a}}, {edge: {contains: true, repeat: {min: 0}}}, {node: {kind: entity}}, {edge: {relation: uses}}, {node: {bind: t}}]`。
`contains` を書いた線に `relation` / `via` / `in` / `bind` / `row` は書けません。参照の本数（値の式 `refCount` の `dir: out`。多重度の `outMin` / `outMax`）も、その要素が直接書いた参照だけを数えます。
保有と所属（名前のある入れ子の線）は [ids.md](ids.md)。
- **`via`（参照が書かれた場所）**: 1語ならキー名（`via: actor`）、複数語なら**場所の末尾のキーの並び**です（`via: target.ref` は「`target` の下の `ref`」に書かれた参照だけ。配列の番号は無視します）。同じキー名の参照フィールドが別の場所にもあるときに、場所で区別できます。
- **何段でも辿る線（`repeat`）**: `edge: { relation: calls, repeat: true }` は、その線を**1回以上くり返して辿り着けるすべての要素**へ進みます（`repeat: { min: 0 }` は0回以上＝出発した要素そのものも含む）。
辿る計算はコードの専用アルゴリズム（辿り着ける要素の集まりを求める。必ず止まります）が行い、その先の判定（あること・ないこと・件数・値の比較）と文面・重大度は、今までどおり YAML で書きます。途中で通る要素は `node` の絞り込みを受けません（絞り込みは辿り着いた先にだけ効きます）。
見つけた道すじ（最短）は `message` の `{path}` に出せます。`repeat` を書いた線に `bind` は書けません。辿った範囲に相手の見つからない参照があれば、「流れが見つからない」という指摘は出しません（その参照が、探している流れかもしれないため）。
例——「途中が何段になるか決まらない対応付け」（処理が処理を呼ぶ）: `- edge: {relation: calls, repeat: {min: 0}}`／「循環が無いこと」: `match: [{node: {bind: a}}, {edge: {relation: depends-on, repeat: true}}, {node: {same: a}}]` ＋ `expect: absent`（`message: "…（{path}）"`）。
- **行を線とみなす（`row`）**: `edge: { row: { from: { relation: t-from }, to: { relation: t-to } } }` は、**同じ行（object）の直下に書かれた2つの参照**——`from` の相手から `to` の相手へ——を1本の線として辿ります（遷移の表のように、ID を持たない行に from と to が並ぶ書き方）。
`dir: in` は逆向き、`repeat` と組み合わせれば何段でも辿れます。例——「どの詳細画面からも、メイン画面へ辿り着けること」: `match: [{node: {entity: screen, bind: a}}, {edge: {row: {from: {relation: t-from}, to: {relation: t-to}}, repeat: true}}, {node: {id: SCR-MAIN}}]` ＋ `where: [{of: a, path: kind, equals: detail}]` ＋ `expect: exists`。
なお「どの流れを通っても最後は必ず着く」（すべての道についての性質）は、この書き方では判定できません。
- **すべての要素について（`forAll`）**: 起点とは参照でつながらない、**もう1つの集まり**を持ち込み、そのすべての要素について、起点からの流れに解があることを求めます（`expect` / `count` / `check` と排他。
`match` は起点の node 1つだけ）。`forAll: { node: {entity: environment, bind: env}, steps: [{edge: {dir: in, relation: value-of}}, {node: {entity: setting-value}}, {edge: {relation: for-environment}}, {node: {same: env}}] }`＝「設定項目（起点）のそれぞれについて、すべての環境に、その項目の設定値がある」。
解のなかった要素が不足で、`message` に `{count}`（不足の件数）と `{missing}`（不足の並び）を書けます。集まりが空なら判定しません。ある要素の解を探す途中で相手の見つからない参照に出会ったら、その要素は不足に数えません。
- **ノード一致 `same`**: `node: { same: 束縛名 }` は「先行して束縛済みのノード**そのもの**」への到達を要求します（他のキーと同居不可・先頭 node には書けません）。2経路が同一ノードで合流することの照合で、**型不一致の検出**が書けます——例:「カラム→実装する属性→業務型」と「カラム→業務型」が同じ型ノードに到達すること（`also: { from: c, steps: [{edge: {relation: dtype}}, {node: {same: t}}] }` ＋ `expect: exists`）。
値（表記）の比較ではなくノードの同一性で判定します。
- エンティティ型が未宣言のID・未解決参照・起点の母集団（`entity` / `id` / `where`）に入らないIDには黙ります（誤検知よりも見逃しを許容する方針）。さらに、解探索の途中で**未解決参照により候補が失われた**場合、「解の不足を理由とする違反」（`exists` の解なし・`count` の下限未達）は出しません——失われた候補が不足分だったかもしれないためで、未解決参照そのものは参照解決の検証が指摘します。`absent` の成立・`count` の上限超過は、見つかった解が実在する証拠のためそのまま指摘します。
- 検証パネル・CLI `validate`・変更セット適用・エージェントの提出ゲートに同じ判定が乗ります（`level: error` なら提出を塞げます）。
- **値の式**: `check` の左右には、値の読み出しだけでなく次の式を書けます——読み出し `{of: 束縛, in: {schemaId, fileGlob}, path: 相対パス}`（`in` は「どの文書に書かれた値を読むか」の指定。
省略すると同じ ID が書かれた全文書が候補）・決まった値（`10` や `approved` のように**そのまま書く**。定義のひな型で、渡されないかもしれない値を受けるときは `{value: 値}`——値が無ければ「得られない」扱い）・テンプレートの展開 `{format: 式, scopes: [{of: 束縛, in: 指定}], with: {穴の名前: 式}}`（式が返す文字列の `{パス}` を、scopes の要素の値で近い順に置き換える。
`with` は省略可で、計算した値を穴に差し込む＝どの入れ物よりも先に埋まる）・辞書での置き換え `{map: 式, using: {元: 先}}`・最初に得られた値 `{first: [式, ...]}`・文字数 `{length: 式}`・大文字と小文字の変換 `{upper: 式}` / `{lower: 式}`・数値の表記を揃える `{number: 式}`（`12.0` → `12`。桁区切り `12,000`・通貨記号 `¥` `円`・全角の数字・`▲` の負も数として読む。
数として読めなければ得られない）・日付の部分 `{year: 式}` / `{month: 式}` / `{day: 式}`（年・月・日の数）と `{yearMonth: 式}`（年月の文字 `2026-10`。月ごとに集計するときの鍵。日付 `YYYY-MM-DD` か日時として読めなければ得られない）・四則演算 `{add: [式, ...]}` / `{multiply: [式, ...]}`（2つ以上）と `{subtract: [式, 式]}` / `{divide: [式, 式]}`（どれかが数値として読めない・0 で割るときは得られない。
小数の誤差は持ち込みません＝`0.1 + 0.2` は `0.3`）・書かれた場所の数 `{occurrenceCount: {of: 束縛, schema: スキーマID または 並び, fileGlob: パターン, role: defining | detail}}`（その ID が書かれている場所のうち、指定に合うものの数。
`distinct: type` を添えると、宣言されたエンティティ型の種類の数）・参照の本数 `{refCount: {of: 束縛, dir: out | in, relation: 関係名, via: キー名}}`（その要素から出ていく／その要素へ入ってくる参照の本数。
同じ相手への参照が2本あれば2と数え、出ていく参照は相手が見つからないものも数えます）・集計 `{sum | min | max: 配列を返す式}` と `{count: 配列を返す式}`（配列を受け取る関数。`count` は件数・`length` は文字数。`min` / `max` の比べ方は読んだ項目の型で決まり、`type: number | date | time | datetime` を添えれば上書き。値が書かれていない・順序の種類として読めない要素が1つでもあれば得られません）・
集合から配列へ `{all: {of: 束縛, in: 指定, path: 相対パス}}`（同じ起点について見つかった**全ての解**にわたり、その束縛の要素（重複は1つ）の値を並べる。`path` を省くと ID の配列。値は指定に合う文書のうち定義した側を優先して1つから読む。
例 `{eq: [{number: {of: o, path: total}}, {sum: {all: {of: l, path: amount}}}]}`＝注文の合計は明細の金額の合計）と `{all: {from: 束縛, match: [...], where: [...], of, in, path}}`（`from` の束縛を起点に固定した照合の解から並べる。絞り方の違う合計を1つの検査に書ける）・
要素ごとの式 `{each: 配列を返す式, value: 式}`（各要素をいまの要素として `value` を当てた配列。例 `{sum: {each: {of: o, path: lines}, value: {multiply: [{path: price}, {path: qty}]}}}`）。
パスに `[*]` を書くと、その要素の**配列の全ての要素**の値を並べた配列になります（例 `{eq: [{of: t, path: lastUpdated}, {max: {all: {of: t, path: "comments[*].date"}}}]}`＝手書きの最終更新日は最新のコメントの日付と一致。
`date` の項目なので日付として比べます。項目の型が分からない値（決まった値・計算の結果）を日付として比べるなら `type: date` を添えます。`{count: {all: {of: t, path: "comments[*]"}}}` は配列の要素の数）。同じ式はビューの値の式の列（[views.md](views.md)）にも書けます。
制約の `count`（解の組の件数の範囲）と `all` の件数は数え方の単位が違います（制約の `count` は束縛の組・`all` は1つの束縛の要素）。
式は入れ子に書けます（例 `{lte: [{length: {of: item, path: name}}, 10]}`＝名称は10文字以内、`{eq: [{number: {of: line, path: total}}, {multiply: [{of: line, path: price}, {of: line, path: qty}]}]}`＝金額は単価×数量）。
指摘の文面には、何を計算したかが添えられます（`name の文字数: 14`・`「300」（= 100 × 3）`）。値が得られない組は評価せず（判定保留）、演算子を値として渡したいときは `{op: lte, left: 式, right: 式}` の形でも書けます。
`edge` にも `in: {schemaId, fileGlob}` を書けます（その参照が書かれた文書の指定）。同じ値の式は、項目の定義に `expression: true` の印を付けた項目（メタスキーマの `filePattern`＝新しい文書の置き場所など。
[schema.md](schema.md)「新しい文書の置き場所とひな型」）にも書けます——そこでは `of` を省略すると元の要素を読み、`{パス}` を含む文字列は `format` の省略形です。
- **文面・指摘の場所・エラー時の対応**: `message` は指摘の文面のひな型で、**どの判定にも**書けます（`{id}`＝起点の ID・`{束縛名.id}` `{束縛名.type}` `{束縛名.title}`＝見つかった解のノード・`{count}`＝解の件数・`{left}` `{right}`＝比べた値、`{left.raw}` `{right.raw}`＝計算前の元の値）。
`reportAt: {of: 束縛, in: 指定, path: 相対パス}` を書くと、指摘は起点を定義した場所ではなく**その値が書かれた場所**に出ます（値のある文書の検証で、要素ごとに報告）。`responses` はエラー時の対応の宣言で、`{jump: right.source, label: ...}`（値の出どころ——テンプレートなどが書かれた場所——へ移動）・`{jump: right.inputs, label: ...}`（テンプレートへ差し込んだ値の場所へ移動。
入力ごとに1件。ラベルに `{input.placeholder}` `{input.value}`）・`{jump: referenceSources, relation: 関係名, label: ...}`（起点の要素への参照を**書き足せそうな文書**を開く。
候補ごとに1件。ラベルに `{file}`。`check` がなくても書けます）・`{apply: right, label: ...}`（値を指摘の場所へ書き込む。値の場所の `reportAt` が必要）を、検証パネルのメニューに宣言の順で出します。
`{create: detailDocument, schemas: [スキーマID], label: ...}` は、起点の ID の詳細文書をそのスキーマの置き場所に作って開きます（スキーマごとに1件。ラベルに `{schema}`。文面の `{create.places}` には作り先のスキーマと置き場所が入ります）。
`note` を書くと、メニューでラベルの下に補足を添えます。
- **充足の状況の表示と、直せる場所への案内**: `status: ひな型` を書いた検査は、要素ごとの「検査の状況」の一覧（右パネルの出現タブ・ID 横ぐし・ビューの状態列・エージェントの `related`）に、満たしている・不足している・フェーズ未到達の別と、いまの値つきで出ます（例 `status: レビュー記録 {left} 件（必要 {right} 件）`）。
`fixSite: {schema: 書き足し先のスキーマ, message: 文面}` は、その検査の指摘が「別の文書へ書き足す」ことで直るときに使い、書き足し先のスキーマの文書の検証へ、指摘が出ている ID の一覧を案内（情報）として出します（`{count}`＝件数・`{ids}`＝ID の並び。
その文書に既に書かれている ID は載せません）。`levelFrom: definingUniqueness` のように書くと、関係レジストリの強制スイッチ（`enforcement`）が宣言されているときだけ、その重大度に切り替わります。
- **指摘の説明**: `absent`／`count` の違反は「該当の組: api=EAPI-001・tbl=TBL-MEMBER」のように**成立してしまった束縛の組**を列挙し、検証パネルのクリックメニューから各IDの定義へジャンプできます。定義出現が別文書にあるIDの詳細化文書にも指摘が届きます——**エラー級は同じ重大度（該当の組つき）**で、警告級は「報告先: 定義出現 <パス>」の INFO 案内で表示されます（全体集計ではエラー級の同一違反が出現数ぶん数えられます）。

## 検査の定義と語彙の定義（`functions` / `vocabulary`: 検査に名前を付けて使い回す）

検査の書き方は3段になっています。**下の段がベースで、上の段は検証の前に下の段へ展開されます**（展開結果は CLI `checks` で見られます）。

1. **基本の書き方**: スキーマの `constraints` に1件ずつ書く。プリミティブを直接書く（`match` ＋ `expect` / `count` / `check`）か、**定義を名前で使う**（`use` ＋ `with`）。
2. **関数のような定義**（`functions`）: 名前・受け取る値（`params`）・中身（`checks`＝基本の検査のひな型）。使われるたびに、渡された値がひな型の `$名前` へ差し込まれます。
3. **語彙の定義**（`vocabulary`）: 短く書くための書き方を作る。どこに書けるか（`in`）と、書かれた内容からどの定義をどの値で使うか（`uses`）を宣言します。

```yaml
# _schemas/my-checks.yaml —— 定義の置き場（kind: library）。どのスキーマ文書に書いても、ワークスペース全体で使えます
id: my-checks
kind: library
functions:
  - id: not-greater-than
    description: 指定スキーマの文書に書かれた値が、上限以下であること
    params: [schema, path, limit]
    checks:
      - match:
          - node: { schema: $schema, bind: item }
        check:
          - op: lte
            left: { of: item, in: { schemaId: $schema }, path: $path }
            right: $limit
        reportAt: { of: item, in: { schemaId: $schema }, path: $path }
        message: 「$path」の値「{left}」は上限「{right}」を超えています
        level: error
vocabulary:
  - word: limits
    in: limits[]                      # スキーマ直下の limits 配列の各要素に書ける
    uses:
      - use: not-greater-than
        with:
          schema: { schema: id }      # この語彙が書かれたスキーマのID
          path: { from: field }       # 書かれた内容から読む（default: / map: で既定値と読み替えも書ける）
          limit: { from: max }
```

```yaml
# 利用するスキーマ側
limits:                               # 語彙で短く書く
  - { field: size, max: 10 }
constraints:
  - use: not-greater-than             # 定義を名前で直接使う
    with: { schema: item, path: weight, limit: 5 }
```

- **差し込みの規則**: 文字列がちょうど `$名前` なら渡された値そのもの（数値・配列・マップも渡せる。渡されなければ「無い」）、文中の `$名前` は文字列として埋まります。`$` そのものは `$$`。ひな型が参照する名前は `params` に宣言が必要で、綴りの誤り・見つからない定義・宣言にない受け取る値は**スキーマの読み込みエラー**になります。ひな型の中に条件分岐や繰り返しは書けません（値の置き換えだけ）。
- **語彙の `uses`**: `when: キー`／`unless: キー` を書くと、そのキーが書かれている／いないときだけ有効になります（同じ語彙を、書かれ方に応じて別の定義へ対応させる）。キーの並びも書けます（`when: [cardinality.inMin, target]`＝すべて書かれているとき）。空の配列・空の object・空文字は「書かれていない」とみなします。`with` の `{from: パス, join: ", "}` は、配列の値を区切り文字でつないだ文字列にします（文面に並べて示すため）。
- **専用チェッカーを使う検査**: 何段でも辿った結果を要する計算のように、部品の組合せで書くと不自然になる検査は、コードで実装された専用チェッカーを名前で使います（すべてを YAML で書ける必要はありません）。`constraints` に `checker: 名前`・`args: {渡す値}`・`messages: {指摘の種類: 文面}` を書きます（`match` は書きません）。**書かなかった種類は指摘されません**。
用意されているチェッカー: `flow`（遷移検証。種類 `unreachable` / `deadEnd` / `undeclared`。`args` は `flow` の書き方と同じ `nodes` / `edges` / `start` / `terminal` / `usage`）。
文面には `{id}`・`{related}`（関連するノードの並び）・`{count}` を書けます。「何段でも辿る」だけで足りる検査（辿り着けること・循環が無いこと）は、専用チェッカーではなく、上の `edge` の `repeat` で YAML に書けます。
- **ひな型へ object を混ぜ込む（`$merge`）**: 関数のような定義のひな型で、object のキーに `$merge: $名前` と書くと、渡された object の中身をその object へ混ぜ込みます（例 `node: {$merge: $rows, bind: row}`＝渡された絞り込みに束縛名を足す）。同じキーは、ひな型に直接書いたほうが勝ちます。
- **語彙の書き方の形（最小）**: 語彙には `requires: [必ず書くキーのパス]`・`keys: [書けるキーの一覧]`（それ以外のキーは定義エラー＝綴りの誤りを見つける）と `removed: {廃止したキー: 案内}` を書けます。書き方が外れていれば、スキーマの読み込みエラーになります（黙って無視しません）。`with` の `{from: パス, format: "（{value}）"}` は、値があるときだけ文言を添えるのに使います。
- **特定のスキーマに属さない検査**: `kind: library` の文書に `constraints` を直接書くと、ワークスペースのどの文書に定義された要素にも効く検査になります（起点は `node: {typed: true}`＝型が宣言された要素、などで絞ります）。報告先は定義出現（なければ先頭の出現）です。
- **語彙は関係レジストリにも書けます**: `in: relations[]` とすると、関係の宣言の各要素に効く語彙になります（例: 関係の宣言に `mustHaveOwner: true` と書くと、参照先の要素に所有者の参照を要求する）。関係レジストリから展開された検査は特定のスキーマに属さず、ワークスペースのどの文書に定義された要素にも適用されます。語彙が要素から読むキーは、レジストリの検証で「定義されていない項目」と警告されません。関係レジストリに `constraints` を直接書くことはできません（検査は語彙を通して作ります）。
- **組込みの語彙も同じ仕組みです**: スキーマの `consistency`（整合ルール）・`coverage`（詳細文書の存在）・`matrix`（網羅マトリクス）・`flow`（遷移検証）と、関係の宣言の `cardinality`（多重度）・`source` / `target`（対象型）・`acyclic`（非循環）は、ツールに同梱された定義体（YAML）が作る語彙です。
エンティティの整合（浮遊詳細化・定義競合・型競合）も、同梱の定義体に直接書かれた検査です。組込みだけが使える特別な機能はありません——同じものを利用者が書けます。これで、検査の語彙はすべて定義体になりました。
- 利用者が定義した語彙のキーは、スキーマ文書の検証で「定義されていない項目」と警告されません（書き方の形の検証までは、まだ行いません）。

## 網羅マトリクス（`matrix`: 行×列の全組合せの検証）

「処理×試験観点のテスト項目」「テーブル×CRUDを担う機能」のような**2軸の全組合せ（セル）**に、行と列の両方を参照する**証人（witness）**が存在することを検証します。**`matrix` は組込みの定義体が作る語彙です**（後述「検査の定義と語彙の定義」）——検証の前に、検査の基本の書き方 `forAll`（すべての要素について）へ展開されます。展開結果は CLI `checks` で確認でき、同じ書き方で自分の「すべての組について」の検査を作れます。

```yaml
# 処理設計書のスキーマ: 各処理は全試験観点のテスト項目を持つこと
matrix:
  - id: proc-viewpoint-matrix
    description: 各処理は全試験観点の単体テスト項目を持つこと
    rows: { entity: process }              # 行の母集団（entity / schema / id で選択）
    columns: { entity: test-viewpoint }    # 列の母集団
    witness:                               # セルの証人: 行と列の両方を参照するエンティティ
      node: { entity: test-item }
      row: { relation: verifies }          # 証人 → 行 の参照 relation
      column: { relation: viewpoint }      # 証人 → 列 の参照 relation
    level: warning
```

- 不足セルは**行の定義出現**に「不足セルがあります（N 件）: VP-002（境界値）・…」と列挙で報告されます。
- **あえて試験しないセル**は、証人側に `excluded: true` の行として残します（証人が存在すればセルは充足。理由はデータとして記録され、網羅の判断がレビューに残ります）。
- 列の母集団が空のとき・行の母集団に入らないIDには黙ります（判定保留）。パターン制約と同様、検証パネル・CLI・提出ゲートに同じ判定が乗ります。

## 遷移検証（`flow`: 到達性・行き止まり・宣言外遷移）

画面遷移や状態遷移のような**エッジ一覧の文書**（1行に遷移元 ref と遷移先 ref が並ぶ形）を有向グラフとみなし、経路の長さによらない到達性を検証します。**`flow` は組込みの定義体が作る語彙です**（後述「検査の定義と語彙の定義」）——到達の計算そのものは、コードで実装された**専用チェッカー**（`checker: flow`）が行い、どの値を渡して使うか・指摘の種類ごとの文面・重大度は定義の側が宣言します。パターン制約（固定長の経路）では書けない「どこから何ホップでも」の判定を担います。

```yaml
# 画面一覧のスキーマ（ノードを定義する側）に宣言する
flow:
  - id: screen-flow
    description: 全画面は開始画面から到達でき、行き止まりは終端宣言があること
    nodes: { entity: screen }                  # ノード母集団（entity / schema / id で選択）
    edges: { from: { relation: transition-from }, to: { relation: transitions-to } }
    start: { relation: flow-start }            # 開始ノード（遷移文書のデータで宣言）
    terminal: { relation: flow-terminal }      # 出る遷移がなくてよいノード（例 完了画面）
    level: error
```

- **到達不能**: `start` で宣言した開始ノードから到達できないノードを、そのノードの**定義出現**に報告します（開始ノードへ relatedIds でジャンプ可）。`start` を宣言しない規則・開始データが空のときは判定しません（判定保留）。
- **行き止まり**: 出る遷移がなく `terminal` 宣言もないノードを報告します。
- **宣言外遷移**: `usage: {from: {relation}, to: {relation}}` を追加すると、そのエッジ集合が宣言エッジに含まれること（原本にない遷移の検出）を要求できます。
- エッジの from / to は**同じ行オブジェクトの直下**にあるスカラー参照の組だけがエッジになります。未解決参照でエッジ・開始・終端が失われたときは、解の不足系の判定（到達不能・行き止まり・宣言外）を黙らせます（未解決参照そのものは参照検証が指摘）。
- **状態遷移への応用**: 状態をID化（例 ST-RESERVED を状態台帳で定義）して遷移表を ref で書けば、同じ宣言が状態機械の検証（未定義遷移・到達不能状態）になります。

> 「設計に対してどんな機械的チェックが書けるか」のパターン一覧は [docs/DESIGN-CHECK-CATALOG.md](../DESIGN-CHECK-CATALOG.md)（設計チェックカタログ）にまとまっています。

## エンティティ操作（改名・統合・削除）とファイル移動

エンティティ（論理ID）のリファクタリング操作は、**全出現・全参照を1つの変更セットへ束ねて**生成し、通常の変更セット適用（オール・オア・ナッシング・適用後検証）で反映します。

- **改名（rename）**: 全出現のIDフィールドと全参照（スカラー参照・属性付き参照の `to`）を新IDへ書き換えます。新IDが既存IDと衝突する場合は生成段階で拒否（統合は merge を使用）、エンティティ型の `idPattern` から外れる場合は警告付きで生成します。
- **統合（merge）**: 統合元への全参照を統合先へ張り替えます。統合元の出現は「統合先のIDへ書き換えて詳細化として残す」（既定）か「要素ごと削除」を選べます。
- **削除（delete)**: 被参照が1件でもあれば参照元一覧つきで拒否します（黙って壊さない）。参照がなければ出現要素を削除します。
- 入口は**エンティティページの操作メニュー**（[views.md](views.md)。改名／別IDへ統合／削除を変更内容のプレビュー→適用で実行）、新CLI `workspace refactor rename-entity|merge-entity|delete-entity`（`--apply` なしは計画のプレビュー出力）、検索・コマンド（`Ctrl+K`）の「エンティティを改名…」です。GUI からの適用は1つのトランザクションとして記録され、**Ctrl+Z（Undo）1回で全変更が戻ります**。

ファイルの移動・改名も影響を見てから実行できます:

- ツリーの「名前を変更」ダイアログと新CLI `workspace refactor move-document <old> <new>` は、**パスIDの文書参照の書き換え**（`_document.id` 未宣言の文書が対象）と、**スキーマ `match` の当たりが変わる警告**・**ビュー定義の file / fileGlob が外れる警告**を実行前に表示します。参照の書き換えと移動は1つのトランザクションで適用されます。
- `_document.id` を宣言した文書は documentId が移動で変わらないため、書き換え不要の旨が表示されます。


## 整合ルール（宣言値と導出値の一致検証）

段階的詳細化で機械的に導出できる値（例: 値型の `maxLength` → `varchar(100)`）を下流文書に手書きしている場合、その値が**導出規則から計算した期待値と一致していること**をスキーマの `consistency:` で検証できます。ビューの値の式の列（[views.md](views.md)）と**同じ評価器・同じ解決**を使うため、ビューの「（導出）」列に見えている値と、検証が比較する期待値は常に一致します。

```yaml
# テーブル設計スキーマ側: カラムのDDL型は、値型参照を辿って型写像から導出した値と一致すること
consistency:
  - description: DDL型はDDL型写像から導出した値と一致すること
    idPattern: "FLD-*"          # 対象のID要素（省略時は全ID要素）
    path: type                  # ID要素からの相対パス（検査する値）
    expected:                   # 期待値の導出（lookup / source / path / values / map / default）
      lookup: { schemaId: concepts, via: type }
      source: { schemaId: ddl-mapping }
      path: to                  # 例: varchar({maxLength})
      values:
        - schemaId: concepts
    assert: equals              # equals（既定）/ lte（導出値以下）/ gte（導出値以上）
    level: warning              # warning（既定）/ error（エージェントの提出ゲートを塞ぐ）
    activeFrom: physical-design # フェーズ到達まで判定を保留（phases 宣言時）
```

`assert: lte` / `gte` は**適合（包含）判定**です（両辺を数値として比較。数値でなければ判定保留）。「画面入力の最大文字数は、参照する値型の最大文字数**以下**であること」のように、等値でなくてよい制約の流れを検証できます（例: 100文字の値型に50文字の入力欄は適合、200文字は「設定できない値を許してしまう」ため指摘）。sample-workspace の `_schemas/todo-screendef.yaml`（入力欄→値型）が実例です。

挙動の要点:

- 一致しない値には「値「Int」は導出値「String」と一致しません」の指摘が**検査した値の座標**に付きます（意図的な上書きを許す運用なら `warning`、禁止なら `error`）。
- **判定保留は沈黙**します: 検査する値が未記入（`required` の領分）・導出の元になる写像行がない（`detailIn` カバレッジの領分）・期待値のプレースホルダが未解決、の場合は指摘しません。
- **テンプレート健全性**: 整合ルールが導出元（`expected.source`）に選んでいる文書では、テンプレートに解決できないプレースホルダ（例: `{maxlen}` の書き間違い）を書くと、**その場（未保存でも）**テンプレートの座標に警告が出ます。
- 期待値の材料（他文書）は、画面上の検証では未保存の編集を優先して読みます（「見たまま判定」。CLI などのヘッドレス経路はディスク基準）。エージェントの変更セット・ステージングの検証では適用後のオーバーレイで判定されるため、提出ゲートにもそのまま乗ります。
- **整合ルールは組込みの定義体です**（後述「検査の定義と語彙の定義」）。`consistency` という書き方は、検証の前に「クエリ＋値の比較（`check`）」の基本の検査へ展開されて、他の検査と同じ規則で評価されます。展開結果は CLI `checks` で確認できます。
これに伴い次の2点が他の検査と揃いました: ①`source` / `values` の指定に合う文書が**複数あるときは、すべて調べて1つでも食い違えば指摘**します（以前は定義出現を優先して1つだけ読んでいました。1つの文書に絞れている書き方では結果は同じ）②`lookup.via` は**参照フィールド（`type: ref`）の場所**で、参照の線として辿ります（ref 型でないフィールドの値は辿りません。
1語ならキー名・`target.ref` のように書けば、その場所に書かれた参照だけ）。
- （ビューの値の式の列では）`in` の指定（`schemaId` / `fileGlob`）が**同一IDの複数の出現に一致する**場合は、**定義出現を優先**して1出現から読みます（定義出現がなければ索引順の先頭）。selector で1出現に絞れている通常の運用では意識する必要はありません。
- 判定は現在**等値**です（値の包含関係——maxLength 100 の入力は varchar(255) に適合する等——による適合判定は将来拡張）。

**明示的除外の規約**: 実装が導出元の全項目を持たないケース（エンティティが項目の部分集合だけ実装する等）では、黙って行を省くのではなく、**「あえて使わない」ことを行として残す**運用を推奨します。同一IDの出現なので完全性カバレッジ（`detailIn`）は充足し、値のフィールド（type 等）を書かないので整合検証は保留（沈黙）——つまり**黙った欠落だけが警告として残り、意図的な除外は理由つきのデータとして記録されます**。

```yaml
properties:
  - id: FLD-TASK-STAFF
    excluded: true        # あえて実装しない（スキーマに boolean フィールドとして宣言）
    note: 画面表示専用の項目のため、エンティティには持たせない
```

sample-workspace の `_schemas/todo-entity-design.yaml`・`_schemas/todo-table-design.yaml` が実例です（`excluded` フィールドの宣言を含む）。

なお、検証パネルの整合指摘は**クリックで選択メニュー**（エラー箇所へ／導出規則へ／入力値へ／**導出値を適用**）を出します。「導出値を適用」は未保存の編集として書き込むため、Undo・差分・保存がそのまま使えます。指摘のあるフィールドはフォーム上でも入力枠が色づきます（エラー=赤・警告=オレンジ）。また、カバレッジ（`detailIn`）の出現先になっている文書（写像文書など）には「不足しているID」の案内（INFO）が表示され、行を書いたその場（未保存でも）で消えます。


## 検証パネル

右パネルの「検証」に以下が表示されます。指摘のクリックで「何ができるか」の選択メニューが開き、「エラー箇所へ移動」（ファイル・パス表示つき）を先頭に、整合検証の指摘なら来歴のアクション（導出規則へ・入力値へ・導出値を適用）、関連IDつきなら各定義へのジャンプが並びます。

スコープは「**この文書／全体**」を切り替えられます。「全体」は索引対象の全文書を未保存の編集込み（「見たまま」）で検証し、ファイル別にまとめて表示します（ワークスペース全体のエラー0確認に使えます）。

- 必須項目の未設定（`required: true`）
- 型不一致（int / number / boolean / object / array / map）
- `enum` の選択肢外の値
- 非アクティブな case のキーの残存（`cases`。有効になる enum 値を案内。重大度は `unknownFields` に従う）
- `date` / `time` / `datetime` の形式逸脱（エラー）と、形式に合っても存在しない値（`2026-02-30` など。エラー）
- `id` / `string` / `text` の `pattern` 逸脱（IDフォーマットの強制を含む）
- 未解決の参照
- ID の重複（同一ファイル内。異なるファイルの同一IDは許容）
- カバレッジルールの不足（被参照数または詳細文書の出現数が `coverage` の要件に満たないID）
- スキーマファイルの構造、未知の型、フィールドキー重複、array/mapの子定義不足、未解決の `$ref`
- スキーマの型変更後の残留値は、フォーム側に修復UI（「値を消す／配列・スカラーに変換」）が出ます
