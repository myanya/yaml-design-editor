# 将来構想とロードマップ

本書はプロジェクトの中長期の方向性と開発計画を管理します。**実装済み**の機能は [FEATURES.md](FEATURES.md)、**現行**の設計は [ARCHITECTURE.md](ARCHITECTURE.md) が正であり、本書は「これから」だけを扱います。ロードマップ項目を実装したら、FEATURES.md に機能として登録し、本書の状態表を更新してください。

## 1. ビジョン

汎用YAMLエディタから、**ドキュメントベースの仕事を委託できる、サンドボックス型のAI実行環境**へ育てる。

> 構造化された文書の集まり（ワークスペース）を、人間とAIエージェントが**同じ操作系**で読み書きし、
> スキーマ検証と人間の承認をゲートとして仕事を進める実行環境。

- **仕事の対象** = ワークスペース内のYAML文書（スキーマ・ID・関係で構造化された「台帳」）
- **仕事の単位** = アクティビティ（スキーマ化された指示定義。対象・文脈・許可範囲・合格条件を持つ）
- **実行者** = 性格と権限を持つエージェント（レビュー担当・執筆担当など）
- **本ツールの役割** = ハーネス。文脈の段階的開示、部分パッチ、検証ゲート、差分レビュー、実行記録、ループ制御を提供する

```
人間 ─ 指示・起動 ─▶ アクティビティ ─▶ エージェント（性格・権限スコープ）
 ▲                                    │
 │                 ┌─── ツール使用ループ（提出か上限まで反復。§4.8）
 │                 │ 探索: カタログ → 骨子 → ノード全文、構造検索、関係トラバース
 │                 │ 編集: ステージングへの部分パッチ（複数文書・新規文書）
 │                 │ 検証: ステージング横断の検証 → NG なら自己修正
 │                 │ 対話: 人間への質問、前提・計画の明示
 │                 └──▶ 変更セットとして提出
 │                                    │
 └─ 差分レビュー・部分採用 ◀─ 検証ゲート ◀┘
        │ 承認
        ▼
   適用（Undo可・競合検出）＋ 実行記録（_runs）
```

## 4. 中核コンセプト

### 4.1 原本主義（YAML単一原本）

情報管理はYAMLに統一する。Excel・Markdown・Word等は**副次的な入出力形式**であり、インポートしてYAML化した時点からYAML側が原本。特別な指示がない限り、skillがExcelを読み書きしてもExcelを原本として扱わない。派生成果物は原本からいつでも再生成できる（＝派生側の手修正は原則しない）。

### 4.2 セルフホスティング（定義もYAML文書）

アクティビティ・エージェント・skill・実行記録は、`_schemas` と同様の予約ディレクトリ（`_activities` / `_agents` / `_skills` / `_runs`）に置く**スキーマ付きYAML文書**とする。つまり本ツール自身のフォーム編集・検証・差分・レビュー・AI生成が、エージェント運用の管理にもそのまま使える。エージェントによる自己改善（§6 P4）も「定義文書への変更セット提案」に帰着する。

### 4.3 サンドボックスと権限

エージェントが触れるのはワークスペース内のYAMLのみ、操作はツールが提供するAPI（検索・読取・パッチ・検証）のみ。生のファイルシステム・シェルには触れない。外界への作用（Web取得、外部ファイル変換など）はskill経由に限定し、明示的な許可制とする。アクティビティごとに書き込み可能なパス範囲（YPath／glob）を宣言する。

### 4.4 アクティビティ定義（指示の自動化）

```yaml
# _activities/review-requirements.yaml
id: review-requirements
name: 要求レビュー
agent: reviewer                        # _agents/reviewer.yaml を参照
target:
  match: "01_requirements/**/*.yaml"   # 対象文書の選択
instruction: |
  各要求の妥当性・一意性・検証可能性をレビューし、
  指摘を review_comments 配列に追記してください。
context:
  include: [refs, backlinks]           # 追加開示する関連情報のレシピ
allowedPaths: ["review_comments"]      # パッチを許可する範囲
tools: [explore, edit, validate, ask]  # 公開するツール分類（§4.8）
limits: { maxTurns: 24 }               # ループ上限（トークン・時間も指定可）
gates:
  validation: error-free               # 適用条件（検証エラー0）
approval: human                        # human（既定）/ auto
trigger: manual                        # manual / on-change / schedule / chain
```

### 4.5 エージェント定義（性格による色付け）

```yaml
# _agents/reviewer.yaml
id: reviewer
name: レビュー担当
persona: 慎重で、指摘には必ず対象IDと根拠を添える。
rubric: [妥当性, 一意性, 検証可能性, 用語整合]
permissions: { write: propose-only, scope: ["01_requirements/**"] }
model: { provider: anthropic, id: claude-opus-4-8 }
```

同じアクティビティでも、割り当てるエージェント（執筆担当・レビュー担当・校正担当…）によって出力の観点と文体が変わる。エージェントは複数ワークスペースで再利用できる汎用定義とし、ワークスペース側で上書き（カスタマイズ）できるようにする。

### 4.6 段階的開示（AIフレンドリーな検索）

エージェントには最初から全文を渡さず、①ワークスペースカタログ（`_document` の要約＋スキーマ一覧）→ ②文書の骨子（キー構造・ID一覧）→ ③必要なノードの全文、の順に**必要な分だけ**開示する。ID・参照・関係を辿る構造検索と、トークン予算を指定した文脈バンドル生成を提供する。これにより大規模ワークスペースでも文脈が破綻しない。

### 4.7 検証ゲートとループ

エージェントの提案は必ず検証を通す。スキーマ適合・参照解決に加えて、**カバレッジルール**（例:「全要求は1つ以上の設計項目から参照されること」）を導入し、段階的詳細化の充足を機械判定できるようにする。検証NGはエラー内容をフィードバックして再試行（最大回数・予算上限付き）。この「合格条件を機械化し、ループを設計する」ことがハーネスエンジニアリング／ループエンジニアリングの中身であり、良い検証ルールを書くこと自体が業務設計になる。

### 4.8 エージェントの実行モデル（ツール使用ループとステージング）

エージェントの実行は「1回の生成」ではなく、**LLMが自ら次の行動を選ぶマルチターンのツール使用ループ**とする。1ターン＝思考＋ツール呼び出しで、探索・編集・検証・対話を上限（ターン・トークン・時間）の範囲で繰り返す。エージェントに公開するツールはP1のAPIをそのまま包んだもので、アクティビティの権限スコープでフィルタされる。

| 分類 | ツール（例） | 内容 |
|---|---|---|
| 探索 | `list_documents` / `read_outline` / `read_node` / `search` / `related` | カタログ→骨子→ノード全文の段階的開示（§4.6）、構造検索、参照・被参照・同一IDの関係トラバース。**検索はエージェント自身の行動**であり、最初に全文を与えない |
| 編集 | `apply_patch` / `create_document` | ステージングへのYPathパッチと新規文書の作成。`allowedPaths` の範囲外は拒否される |
| 検証 | `validate` | ステージング全体の横断検証（結果を次ターンの入力として自己修正に使う） |
| 対話 | `ask_human` / `note` | 人間へのブロッキングな質問と、前提・判断の明示（実行記録に残る） |
| 管理 | `plan` / `submit_changeset` / `abort` | 作業計画（TODO）の宣言・更新、変更セットの提出、理由付きの中断 |

**ステージング（作業オーバーレイ）**: エージェントの編集は原本に直接触れず、ベースバージョンのスナップショットに対するオーバーレイに積む。**複数文書へのパッチ・新規文書もひとつの変更セット**にまとまり、検証とID・参照の解決はオーバーレイ上で行われる。これにより「用語を改名して参照元をすべて直す」ような文書横断の作業を、エージェント自身が整合を確認しながら進められる。提出時にはベースバージョンとの競合を検出する（R1-02）。

**終了条件**: ①`submit_changeset`（ゲート通過が前提）②`ask_human`（回答待ちで一時停止、再開可能）③`abort`（理由付き）④上限到達——のいずれか。上限到達時もステージングは**未提出ドラフト**として保存され、人間が中身を確認して引き継げる（作業の蒸発を防ぐ）。

### 4.9 二層モデル（文書×エンティティグラフ）

情報管理基盤の再定義（P20〜P23。方針承認 2026-08-10）。本ツールは既にプロパティグラフ——ノード＝論理ID（同一IDの複数出現＝多段定義）、エッジ＝型付き参照（`relation`）、ラベル＝出現スキーマ——を持つが、それはID索引の走査から導出される**副産物**であり、宣言層を持たない。文書側にはスキーマという宣言層があるのに関係側にはない非対称が、ノードの存在の曖昧さ（「最初の出現＝定義」ヒューリスティクス）・関係語彙の野放し（relation 自由文字列）・整合検証の片面性・照会機構の分裂（検索・トラバース・ビュー行・foreach 列挙・導出 lookup の5系統）の源である。これを解消するため、情報管理を2層で捉え直す:

- **物理層＝文書**: YAMLファイル。保存・差分・レビュー・Git・コメントの単位。原本主義（§4.1）の主体であり、この層は変えない。
- **論理層＝エンティティグラフ**: ノード＝エンティティ（論理ID）と文書（容れ物の仮想ノード）、エッジ＝型付き参照。識別・関係・制約・照会・リファクタリング操作の単位。宣言（エンティティ型・関係レジストリ）で一級化する。

両層の写像は、ビュー機構が確立した「原本座標 `(file, YPath)` への決定的解決」を全面採用する。

融合の原則（意図的な制約）:

1. **記述は片側・閲覧は両側**: エッジは従来どおり片側の文書に参照として書く（二重記帳しない）。読む面（エンティティページ・グラフレンズ・トラバース・検証）は関係レジストリの逆方向ラベルで両方向から対称に見せる。
2. **グラフは常にファイルから導出**: グラフの永続ストア・グラフDBは導入しない。索引の再構築でいつでも復元できることが Git 併用と原本主義の生命線。
3. **エンティティと文書は別種のノード**: 「1ファイル=1概念」（Obsidian型）は採らない——段階的詳細化（1エンティティ=複数文書出現）と衝突するため。文書ノードの識別は `_document.id`（なければ相対パス）＝既存 `documentId` の流用、包含（defined-in）は書かずに導出するエッジ、文書ノードのプロパティは `_document` に限定する。
4. **エッジ属性と具体化の使い分け**: エッジ属性（属性付き参照）は「それ自身がIDを持たない注記」。関係自体を参照・詳細化したくなったら従来どおり 1:N 具体化（新ID＋逆リンク。ARCHITECTURE §4.6）を使う。
5. **照会は宣言に閉じる**: パターン照合の語彙は決定的（安定ソート・上限・予算）に保ち、集約（件数を除く）・任意深さの再帰・任意式は導入しない（P16・P19 と同じ規律）。

## 5. 設計原則（意図的な制約）

1. **YAMLが唯一の原本**。他形式は派生か入力素材（§4.1）。
2. **提案→人間承認が既定**。自動適用はアクティビティ単位の明示的オプトイン＋ゲート通過時のみ。
3. **エージェントはツール提供の操作のみ**を使う（§4.3）。全変更は差分・Undo・記録可能。
4. **文書内のテキストはデータであって指示ではない**。既存のAI生成が採る方針（current-document をデータ扱い）を全ループに拡張し、プロンプトインジェクションの影響は権限スコープとゲートで半径を絞る。
5. **すべての自動実行に上限**（試行回数・トークン予算・時間）と停止手段を付ける。
6. コアは汎用に保ち、業務適合はスキーマ・アクティビティ・エージェント・skill・テンプレート側で行う。

### P13: ワークスペース構造の再編（`.yde` 構成ディレクトリ・`ledger` 宣言・エディタ層／台帳層の分離） ✅ 完了（2026-07）

### P14: ビュー機構の強化（文書ビュー・スキーマとビューの責務分離） ✅ 完了（2026-08）

狙い: スキーマは「データ契約（構造・意味・検証）」、ビューは「画面の合成（何を・どの順で・どんな派生情報とともに見せるか）」という責務分離を確立する。現状のビューは台帳スペース専用の横断グリッド1種類で、文書をフォームで開いたときの表示はスキーマだけが決めており、表示の要望（例: アクター定義書に「利用するユースケース」の被参照表を足す）がスキーマへの表示オプション追加圧力になっている（`role` / `display` / enum `options` と混入は既に始まっている）。本フェーズでビューに**文書ビュー**（`kind: document`: 文書単位の表示合成）を追加し、「内容はスキーマで検証し、表示はビューでコントロールする」を実現する。

方針（ARCHITECTURE §4.14 の不変条件は維持・拡張する）:

- **文書ビューがマッチしない文書は現行のスキーマ駆動フォーム**＝「今の表示は暗黙の既定ビュー」。ビューは足したい文書にだけ足す opt-in で、後方互換を壊さない。
- **表示決定の優先順位**: ①文書ビュー（画面の合成）＞②スキーマの固有表示ヒント（`role` / `display` / `label`＝要素の同一性に近い表示。`Display` の共有契約として存置）＞③予約語規約。既存ヒントの移設はせず、「今後、合成系のオプションはスキーマに足さない」を境界とする。
- **派生セクション（被参照表など）は読み取り専用＋原本座標へのジャンプ**。fields セクションの編集は既存の `FormCtx` / `Slot` 経路に委譲し、ビュー専用の書込経路を作らない。
- **人間とAIが同じ面を見る**: 文書ビューも `read_view` / CLI `view` で機械可読に解決できるようにする。

### P16: 値型と決定論的射影（値レベルの決定論的変換） 📋 構想

狙い: 段階的詳細化（概念データモデル→Javaエンティティ→テーブル定義など）には、機械的に置き換え可能な領域が一定数ある（例: 「ユーザ名: 4〜100文字の文字列」→ `String`＋`@Size(min=4, max=100)` → `varchar(100)`）。これをLLMではなく**宣言的・決定論的なルール**で導出し、導出元の変更が参照時に自動反映される状態を作る。アーキテクチャの先例は揃っている: 決定論的導出のパターンは派生スキーマ（R11-03: ロード時コンパイル・読み取り専用・`noteDiskChanges` での再導出）、参照時解決の器はビュー機構（ARCHITECTURE §4.14: データを持たない射影。バックリンク列＝派生表示列の先例）、写像語彙は `DeriveTypeRule` / skill列マッピング（path / map / default・`{パス}` プレースホルダ）。欠けているのは「値レベルの決定論的変換」の一級語彙と、導出の材料になる機械可読な制約の2点。

方針（検討済みの設計境界）:

- **導出結果は原則永続化しない**: 表示層の射影（計算列）とエクスポートで受ける。仮想派生文書（`derive:` の文書版）は、原本主義と索引・カタログの「ファイル実在」前提を崩すため採らない。
- **実体化する下流**（テーブル定義書のように手書き項目・意図的上書きが本質的にある文書）は「宣言値（原本）＞導出既定値」の**フィールド単位**合成とし、不一致はドリフト検証で可視化する（黙って書き換えない）。
- **変換は宣言に閉じる**: lookup（ref の前方トラバース）＋テンプレート（`{パス}` 置換）＋値辞書（map）＋default のみ。任意式・コード実行は導入しない（kind: run の明示許可制の境界を維持）。
- **命名変換（論理名→物理名）は計算しない**: 日本語→英語は決定論的でない（＝翻訳）ため、物理名は設計判断としてデータに書く（AI生成による一括起案は既存機能で可能）。
- **評価器は1実装に一元化**: 計算列・整合検証・スキャフォールド・決定論的アクティビティの全消費者で共有する（`Display` / `AiHttp` と同じ流儀）。

### P19: コンテキストエンジニアリングの一級化 ✅ 完了（方針承認 2026-08-09・全項目完了 2026-08-10）

狙い: エージェント実行の入力トークンが「ワークスペース規模 × ターン数 × 一括実行件数」の積で膨らむ構造問題の解消。実測（2026-08-09、software-template の elaborate-usecase 一括実行16件）では入力238万トークン・1送信あたり15.5〜19Kトークンで、大半は初期コンテキストへ全量展開したビュー（60行）の毎ターン再送だった。チャットAPIはステートレス（全履歴を毎ターン再送）のため、初期コンテキストに置いた宣言は**ターン数ぶん課金される**。一方でエージェントは渡されたビューに頼らず自力探索しており（対象IDが追加指示で来る一括実行ではビューはほぼ死荷重）、「多めの情報の機械的投入」はコストを払いながら精度にも寄与していなかった。中核コンセプトの段階的開示（§4.6）が唯一適用されていない場所が初期コンテキスト——`context.include` / `context.views` は「載せる／載せない」の二値しかない——であり、本フェーズで方針を「**コンテキストは利用者が設計・計測・チューニングする一級の宣言**」へ転換する（§4.2 セルフホスティングの流儀: レシピもアクティビティYAMLの一部）。

方針（承認済みの設計判断。2026-08-09）:

- **破壊的刷新**: 旧 `context.include` / `context.views` は廃止し、ロード時定義エラー（移行ヒント付き。`meta` かつ `approval: auto` の定義エラーと同じ流儀）。既存定義は全16件がリポジトリ内テンプレートのため互換維持で守る外部資産がなく、二重語彙の恒久化・全量ダンプ形式の温存・メタアクティビティ（improve-definitions が既存定義を手本にする）経由のレガシー伝播の方が高くつく。
- **空既定**: `context` 無指定は「指示＋権限＋ゲートのみ」。カタログすら明示宣言制とし、「コンテキストは利用者が設計する」を既定値の意味論に反映する（単発AI生成（R9-01）は既に初期文脈なしで運用実績あり）。
- **テンプレート同時移行**: 同梱テンプレート16定義を同一変更内で新形式へ移行し、重い6定義（ビュー全量宣言）は絞り込みレシピの実例（お手本）に仕立てる。
- **計測が先**: コンテキスト会計（R19-01）を最初に入れ、以降の各手の効果を数字で確認しながら進める。
- **語彙は宣言に閉じる**（P16 と同じ規律）: 絞り込み・予算・条件・経路パターンのみ。任意クエリ言語・任意式は導入しない。
- **評価器は1実装**: グラフトラバースはレシピ・エージェントツール・CLI の全消費者で共有する（`Display` / `AiHttp` / `Projection` の流儀）。

狙い: スキーマ定義の変更（フィールド改名・移動・順序変更など）に、既存文書と周辺の消費者（ビュー・宣言）を**1つの変更セット**で追随させる。方式は「操作ベース」——スキーマ差分からの推測（改名と削除＋追加が判別不能）は採らず、明示的なリファクタリング操作が生成器（`Plan` = 変更セット＋警告＋サマリ）を通って既存の `Workspace.apply` で適用される。ID改名（EntityOps。R21-02）・ファイル移動（DocMove。R21-03）と同型で、**新しい書込経路は作らない**。`_schemas` はエージェント書込不可のため本機能は人間専用。

**設計上の決定（2026-08-13 方針承認時）**:

- **決定的に書換**: 該当文書のデータキー（cases・フェーズ・`$ref`・派生スキーマを考慮したスキーマ誘導走査で列挙）、スキーマ自身（`fields[i].key`・`phases.key`）、ビューのパス（静的解決が一意な箇所: 通常列・計算列 path / lookup.via・newRow.path・文書ビューの sections / include / exclude・被参照表の列）。
- **警告のみ（自動書換しない）**: 自由テキスト（アクティビティ instruction 等）、解決が一意に定まらない参照（多義な列パス・skill 写像・アタッチ `at` など）。
- **拒否（安全側の既定）**: 改名・移動先キーが既存文書に存在する衝突は生成段階で拒否（ファイル一覧つき）。派生スキーマ（`derive` の導出フィールド）・組込みスキーマは対象外＝導出元文書を直す。配列・map の境界をまたぐ移動（1↔N で決定的に解決できない）・共有定義をまたぐ移動も拒否。
- **文書の順序整列（F2 の文書側）は独立コマンド**（align-order。スキーマは変更しない正規化）。マイグレーションスクリプトの蓄積はしない（閉世界＋変更セット原子適用＋Git履歴で足りる）。

| 台帳外へのスキーマ誤適用（広すぎる match）による検証ノイズ | 検証の集計は `ledger` 基準に限定し、台帳外は開いた文書の個別診断のみとする（P13 R13-03） |
| コンテキストの絞りすぎによる精度低下（探索ターン増で逆にコスト増） | コンテキスト会計（R19-01）で内訳を可視化し、評価セットのレシピA/B（R19-06）で「合格率×トークン」を計測してデータでチューニングする |
| クエリコアの語彙が肥大してDBエンジン化するスコープ暴走 | 「やらないこと」（集約は件数のみ・任意深さの再帰なし・任意式なし）を P22 の不変条件として着手前に明文化し、解禁は実例の需要で段階判断する（P16・P19 の規律） |
| 関係宣言・定義出現一意化の必須化による既存ワークスペースの移行コスト | lint 先行（P20 は警告のみ）・レジストリ自動推測（R20-02）・破壊はワークスペース単位の opt-in スイッチ（P21）で吸収する |

## 8. 本書の運用

- ロードマップ項目を実装したら、[FEATURES.md](FEATURES.md) に機能として登録し、§6 の状態表・該当項目を更新する（項目IDをコミットメッセージやFEATURESの行から参照してよい）。
- 方向性・優先度の変更は本書を更新する。他ドキュメントには将来構想の詳細を書かず、本書へリンクする。
- フェーズ着手時には、必要な設計を [ARCHITECTURE.md](ARCHITECTURE.md) に反映してから実装する（本書は設計書ではない）。
