## ビジョン

汎用 YAML エディタから、**ドキュメントベースの仕事を委託できる、サンドボックス型の AI 実行環境**へ育てる。
構造化された文書の集まり（ワークスペース）を、人間と AI エージェントが同じ操作系で読み書きし、スキーマ検証と人間の承認をゲートとして仕事を進める。

- **仕事の対象** = ワークスペース内の YAML 文書（スキーマ・ID・関係で構造化された台帳）
- **仕事の単位** = アクティビティ（対象・文脈・許可範囲・合格条件を持つ、スキーマ化された指示定義）
- **実行者** = 性格と権限を持つエージェント（レビュー担当・執筆担当など）
- **本ツールの役割** = ハーネス。文脈の段階的開示、部分パッチ、検証ゲート、差分レビュー、実行記録、ループ制御

```
人間 ─ 指示・起動 ─▶ アクティビティ ─▶ エージェント（性格・権限スコープ）
 ▲                                    │
 │                 ┌─── ツール使用ループ（提出か上限まで反復）
 │                 │ 探索: カタログ → 骨子 → ノード全文、構造検索、関係トラバース
 │                 │ 編集: ステージングへの部分パッチ（複数文書・新規文書）
 │                 │ 検証: ステージング横断の検証 → NG なら自己修正
 │                 │ 対話: 人間への質問、前提・計画の明示
 │                 └──▶ 変更セットとして提出
 │                                    │
 └─ 差分レビュー・部分採用 ◀─ 検証ゲート ◀┘
        │ 承認
        ▼
   適用（Undo可・競合検出）＋ 実行記録（_runs）
```

「文書にスキーマと検証がある」ことが、コードにおける型チェック・テストに相当する。AI の成果物を機械的に受け入れ判定できる点が最大の強み。

**本命のユースケース**はシステム開発の設計情報管理と設計の機械的検証（P28）。AI ネイティブ開発では設計情報の人間レビューが追いつかないため、「AI が書き、機械が検証し、人間は差分を承認する」ループの検証部を厚くする。

そのほかに向く業務: 執筆（世界観・用語・プロット・原稿）、汎用の台帳（顧客・資産・契約・ナレッジ）、定型業務（議事録・週報・チェックリスト）、翻訳、調査の構造化、監査・点検、FAQ 運用。
適性の基準は、①情報をスキーマで構造化できる ②成果を差分でレビューできる ③積み上げ型の作業である ④ID・参照によるトレーサビリティに価値がある。
単発の非構造文書作成や、リアルタイム共同編集が主体の業務には向かない。ユースケースはテンプレート（`templates/`）とサンプルとして提供し、コアは汎用に保つ。

## 中核コンセプト

詳しい仕組みは architecture/ の該当する主題に書く。ここには考え方だけを置く。

- **原本主義**: 情報管理は YAML に統一する。Excel・Markdown・Word は副次的な入出力形式で、インポートした時点から YAML が原本。派生成果物は原本からいつでも再生成できる。
- **セルフホスティング**: アクティビティ・エージェント・skill・実行記録も、予約ディレクトリに置くスキーマ付き YAML 文書。本ツール自身の編集・検証・差分・レビュー・AI 生成が、エージェント運用の管理にもそのまま使える。
- **サンドボックスと権限**: エージェントが触れるのはワークスペース内の YAML だけで、操作はツールが提供する API だけ。外界への作用は skill 経由の明示的な許可制。書込範囲はアクティビティごとに宣言する。
- **段階的開示**: 最初から全文を渡さず、カタログ → 文書の骨子 → 必要なノードの全文の順に、必要な分だけ開示する。
- **検証ゲートとループ**: 提案は必ず検証を通す。検証 NG はフィードバックして再試行（上限つき）。合格条件を機械化しループを設計することが、ハーネスエンジニアリングの中身であり業務設計そのもの。
- **実行モデル**: 1 回の生成ではなく、LLM が自ら次の行動を選ぶマルチターンのツール使用ループ。編集は原本に触れずステージング（オーバーレイ）に積み、複数文書の変更を 1 つの変更セットにまとめる。提出・質問・中断・上限到達のいずれかで終わり、上限到達時も未提出ドラフトとして残る。
- **二層モデル**: 物理層＝文書（保存・差分・レビュー・Git の単位）と、論理層＝エンティティグラフ（ID と型付き参照。識別・関係・制約・照会・リファクタリングの単位）。記述は片側・閲覧は両側、グラフは常にファイルから導出、エンティティと文書は別種のノード、照会は宣言に閉じる。

## 設計原則（意図的な制約）

1. **YAML が唯一の原本**。他形式は派生か入力素材。
2. **提案 → 人間承認が既定**。自動適用はアクティビティ単位の明示的オプトイン＋ゲート通過時のみ。
3. **エージェントはツール提供の操作のみ**を使う。全変更は差分・Undo・記録可能。
4. **文書内のテキストはデータであって指示ではない**。プロンプトインジェクションの影響は権限スコープとゲートで半径を絞る。
5. **すべての自動実行に上限**（試行回数・トークン予算・時間）と停止手段を付ける。
6. コアは汎用に保ち、業務適合はスキーマ・アクティビティ・エージェント・skill・テンプレート側で行う。

### P24: AI 生成の入口拡大

### P29: Core Calculus

- **目的**: YAML への計算を Term / Query / Expression / Predicate / Rewrite / Construct（＋Aggregate）の体系へ分解し、上位機能をその合成として説明できる状態にする。「機能ではなく直交プリミティブを増やす」を最上位原則とし、専用評価器の乱立を防ぐ。方針原本は [CORE-CALCULUS.md](CORE-CALCULUS.md)。
- **完了**: Phase 1 意味論の固定、Phase 2 既存機能のマッピングと語彙の刈り込み、Phase 3 評価部の共通化、Phase 4 Rewrite の形式化、Phase 5 規約化、Phase 6 定義層の実体化（検査の語彙はすべて定義体になった）。
- **残り**: OQ-03（文書分割）。「どの流れを通っても必ず着く」の検査（BACKLOG UX-110）と、遷移検証を YAML だけで書くのに足りない部品（UX-111）は、必要になったら実装する。
- **決めたこと**: 数え上げの評価器は統合しない。関係の多重度（参照の本数）と constraints の count（解の数）は意図的に単位が異なる。

### P30: YAML から YAML への変換の拡張と応用

- **位置づけ**: 変換は構造のスキーマの導出の土台として入れた（計算体系の 6 つ目の体系「組み立て」。CORE-CALCULUS「Construct Calculus」）。拡張と応用は個別の開発セクションとしてここで管理する。
- **狙い**: 変換を汎用の変換器の土台にする。ビューなど様々なところで使い、テンプレートエンジンを足して YAML から Markdown への変換器なども作る。検査と同じく「プリミティブな実装＋組込み定義＋ユーザ定義」の組合せにする。
- **いまあるもの**: 選ぶ（既存のクエリ）× 組み立てる（ひな型。`$copy` / `$format` / `$map` / `$first` / `$each` / `$eachEntry` / `$apply` / `$concat` / `$when`）× 規則を子に当てる。結果は新しい項と各値の出どころ。CLI `transform`。組込みの変換定義は `builtin-transforms/`。
- **守ること**: 出力は保存しない（原本へ書くなら Rewrite を通す）。クエリを ID の無い場所まで広げない。規則を当てるのは入力の木の子へ向かってだけ。出どころを結果の一部として持つ。置き場は semantic-core。組込みだけの特別な機能を作らない。式の中の条件分岐・キーの計算・利用者定義の再帰・任意のコード実行は入れない。

### P31: スキーマの値に式を書く

- **目的**: スキーマでの値の表現に式を使えるようにする。応用の 1 つ目は、詳細文書のファイル名に要素の項目の値を使えること。検査の `check` に書ける「値の式」を、検査の外（ひな型・表示・組み立て）でも使う。新しい式言語は作らない。
- **書き方**: 短い書き方（`{パス}` を含む文字列。`format` の省略形。予約の名前は `{id}` と `{title}`）と、完全な書き方（検査の値の式そのまま。`of` を省略するといまの要素。`format` に `with:` で名前を付けた値を差し込める）。どの項目が式を受け取るかは、項目の定義の印 `expression: true` だけが決める。
- **守ること**: 式は値 1 つを計算する純粋な計算で、非決定的な値（日付・乱数・連番）を入れない。語彙の予算に従う。検証・走査・検査は式を読まない。置き場は semantic-core。穴埋めの実装を増やさない（減らす）。
- **完了**: 値の式の評価器をクエリの外へ、ファイル名に式、ひな型の中身に元の要素の値、式を受け取る項目のメタ管理。
- **R31-04 その他の応用（一部完了）**: ビューの列 `value` は 2026-09-27 に完了（列に値の式を書く。あわせて値の式の集計にパスの `[*]`＝配列の要素にわたる集計と、順序の種類 `type: date` を足した。最終更新日＝コメントの日付の最大、が書ける）。同日に起点を固定した照合の件数を足し、続く P32 で `all` に寄せた（カテゴリ × 状態の集計表は `samples/todos`）。
  - 本質は「string で設定できる項目のうち、どの項目に `expression: true` の印を付けるか」で、残りの応用は後で考える。
  - 候補: 一覧の 1 行要約を式で、検査の文面に要素の値、派生スキーマと skill 取り込みの穴埋めを同じ評価器へ（取り込みは `build` と `target` のひな型を変換定義へ寄せた。列の対応表 `mapping` の `{列名}` は残る）、foreach の `as:` と文脈テンプレートで要素の値、newRow ダイアログで穴の値を入力、エージェントの `create_document` の作り先の提案。
  - 既存の `computed`（テンプレートの導出）は `value` へ寄せた（R30-03 の 1 つ目。`computed` は廃止）。

### P33: ユーザ定義の型（値型 → オブジェクト型）

- **目的**: 利用者がスキーマで型を定義し、項目に名前で使えるようにする。P27 段C で「必要になったら」と後回しにした「利用者が定義できる意味の型」（[記録](archive/roadmap-history.md) の SC-01・SC-06）の実現。組込みの型も同じ定義体にし、Kotlin が知る型を「基底の種類」だけに減らす（yaml-core は減らす方向）。
- **既知の技術との対応**: 値型は XSD の simpleType（基本型の restriction）・SQL の `CREATE DOMAIN`・TypeScript の型別名に当たる。オブジェクト型（第三弾）は XSD の complexType。
- **決めたこと（2026-10-01 オーナー）**: ①値型はエディタのスキーマの型（設計対象の台帳 DT-* とは別。橋渡しは後回し）②yaml-core の基本型は減らす ③第一弾は検証の決まり ④使う側は狭めるだけ ⑤組込みの型も同じ定義体 ⑥置き場は definitions ⑦オブジェクト型は ID を持たない部品も含む。
- **決めたこと（続き）**: ⑧綴りは `type: 名前` ⑨狭める規則の細部は下表 ⑩`date` を定義体へ移すとき、形式違反は警告からエラーになってよい。
- **確かめたこと（2026-10-01 実験）**: `definitions` ＋ `$ref` は今でも id・string・int・ref の名前付きの決まりとして検証に効き、2 段の継承（`社員メール ← メールアドレス ← string`）も解決される。
- **足りないもの**: `type: 名前` の綴り（未知の型エラー）・狭める規則（緩めても通る）・メタスキーマが `$ref` ＋制約キーを警告する・組込みの `text` / `date` が Kotlin の分岐。yaml-core の `text` は `string` と同じ処理、`date` は `string` ＋正規表現（警告）。

#### 設計

**型の 3 段**

| 段 | 実体 | 定義できるか |
|---|---|---|
| 基底の種類 | `string / int / number / boolean / enum / array / map / object / any` と、意味を持つ `id / ref`（Kotlin の `FieldType`） | できない。YAML の値の形と、索引・参照解決のようにコードが要る意味 |
| 組込みの型 | semantic-core の資源 YAML（`builtin-types`）。第一弾は `text`、第二弾で `date`、以後 `time` / `datetime` など | 組込み。UI・AI 生成・サンプル値は名前を知っていてよい |
| ユーザ型 | ワークスペースの `definitions`（`kind: library` が向く） | 利用者。ふるまいは組込みの型と同じ |

**書き方**: 型の定義は必ず `type:` を持ち、値は基底の種類か別の型名。連鎖の末端が基底の種類。

```yaml
# _schemas/common.yaml（kind: library）
definitions:
  金額:       { type: int, min: 0, display: grouped, description: 円単位 }
  画面ID:     { type: id, pattern: "^SCR-\\d{3}$" }
  メールアドレス: { type: string, maxLength: 100, pattern: "^[^@]+@[^@]+$" }
  社員メール:  { type: メールアドレス, pattern: "^[^@]+@example\\.com$", maxLength: 50 }   # 型から型へ。狭めるだけ
  業務データ型参照: { type: ref, idPattern: "DT-*", relation: dtype, scope: { schemaIds: [data-type-list] } }
  予約状態:   { type: enum, values: [RESERVED, CANCELED] }
  有効な状態: { type: 予約状態, values: [RESERVED] }                                           # 選択肢は部分集合
# 使う側（sysdev-template の entity-detail・table-design、kakeibo の 3 スキーマで重複していた定義が 1 つになる）
    - { key: amount, label: 金額, type: common#金額, required: true }
    - { key: dtype, label: 業務データ型, type: common#業務データ型参照, required: true }
```

**解決＝型の連鎖**: `type:` の値が基底の種類でなければ定義の名前として引く（順: 基底の種類 → 自分のモジュール → `モジュール#名前` → 組込みの型）。解決した項目は連鎖（例 `予約日 → date → string`）を持ち、`FieldType` は末端の基底の種類。使う側は `isA("date")` のように連鎖で判定し、`FieldType.DATE` のような分岐を増やさない。循環は定義エラー。`$ref` は同じ意味の別記法として残す（object の定義は今までどおり `$ref`）。

**狭める規則**: 使う側でも、型から型へでも同じ。緩めたら定義エラー。今の「使う側が勝つ」からの変更なので意図的差分に登録する。

| 決まり | 規則 |
|---|---|
| `minLength` / `min` | 定義以上 |
| `maxLength` / `max` | 定義以下 |
| `pattern` | 両方に一致（並べて持つ） |
| `values`（enum） | 部分集合 |
| `cases` | 定義に無いときだけ足せる |
| `required` / `requiredFrom` | 足すだけ |
| ref の `idPatterns` | 重ね合わせ（両方に合う ID だけ） |
| ref の `scope` | 共通部分 |
| ref の `relation` / `target` | 定義に無いときだけ。違えば定義エラー |
| `unknownFields` | 厳しくするだけ（allow → warning → error） |
| `label` / `description` / `display` / `default` | 決まりではない。今までどおり使う側が優先 |

文面の例: 「maxLength 200 は型「common#メールアドレス」の 100 より緩いため書けません（型は狭めるだけ）」。

**導出**: スカラーの連鎖は導出の前に解決し、基底の種類と合成した決まりを構造のスキーマへ写す（`$ref` のまま写すのは object / array / map の定義だけ＝再帰のため）。yaml-core に足すのは `pattern` を複数持てること（並べて全部に一致）だけで、型の名前は yaml-core に届かない。

**組込みの型のライブラリ**: 資源 `builtin-types/*.yaml`（`kind: library`・`id: builtin-types`）を、検査の組込み定義体と同じ流儀で読み、カタログの解決の最後に引く。第一弾で `text` を移す（検証の違いが無く、UI の複数行の判定を連鎖にする最初の例）。`date` は第二弾（入力欄の案内・サンプル値・順序のヒントが要る）。

**メタスキーマ**: 読み込み時に、ワークスペースと組込みの型の名前を `type` の選択肢へ足し、その `cases` に基底の種類の `cases` を写す（語彙のキーを足す `withVocabularyKeys` と同じ流儀）。`type: 名前` に書いた制約キーは、基底の種類と同じ扱いで検証される。`$ref` ＋制約キーの警告は残す（型は `type:` で書くのが正）。

**UI と道具**: 設計 UI の型の選択肢に型の名前を並べ、「型を追加」（スカラーの定義）を足し、定義カードに連鎖を出す。フォーム・AI 生成・サンプル・ビュー・走査は `resolve` を通るので、基底の種類で自動で効く。リファクタリングは `rename-definition` が `type:` の言及も書き換え、`extract-definition` は `type:` で書く。ID の採番の形は型の `pattern` から引ける（今と同じ経路）。

**置き場と計算体系**: 型は宣言で、6 体系のどれでもない。連鎖の解決は semantic-core の `schema`、狭める点検は workspace-core の `SchemaDefinitionChecks`、導出は `DerivedStructures` の変換定義、yaml-core は `pattern` の複数化だけ。新しい評価器・書込経路は作らない。

#### 第三弾（オブジェクト型）の設計（決定 2026-10-03 オーナー）

**一言で**: オブジェクト型 ＝ object の定義に ①同一性（`entity`）②表示（`label` と既存の `role`）③検査（`constraints`）を足し、使う側は `type: 名前` で使って「項目を足す・必須にする」だけができる。既知の技術との対応は XSD の complexType（extension＝足す・restriction＝狭める）・TypeScript の `interface B extends A`。

- **書き方**: object の定義（`definitions`）でも、その場の object（配列の要素など）でも `entity: { type, defines, aspect, owns }` を書ける（1 回しか使わない形のために型を定義しなくてよい）。名前付きの型では `entity.type` を省くと定義名。使う側は `type: 名前`（`$ref` は同義で残す）。
- **同一性の決め方**: 要素の object（解決した型）に `entity` があればそれ → 無ければ文書スキーマの `entity:`（ID の形で判別。今までどおり残す）。root を型で書き、その型が `entity` を持てばスキーマの `entity:` は省略できる。段階的詳細化（同じ ID を複数の文書に書く・側面の所有）はそのまま——オブジェクト型は要素の「形」を決め、側面をつなぐのは ID とエンティティ型の名前。
- **同じキーは狭める・新しいキーは足す**（熟練プログラマの直感＝サブインターフェースで同じ項目を書き直すと狭い型しか許されない）: 定義に無いキー→末尾に追加。定義にあるキー＋`required` / `requiredFrom`→必須にする（外せない）。定義にあるキー＋決まり→第一弾と同じ狭める規則。定義にあるキー＋`type`→省略が普通で、書くなら定義側の型を狭めた型だけ（基底の種類が変わる書き方は定義エラー）。
- 表示のヒント（`label` `description` `placeholder` `sample` `format` `display` `default` `role`）は使う側が勝つ。object / array / map の子（`fields` / `item` / `value`）には同じ規則を再帰的に当てる。`cases` は定義に無いときだけ。項目を外す・並べ替える・`entity.type` を変えるはできない。位置は同じキーなら定義の場所のまま。
- **検査は要素ごと**: 型の `constraints` は「その型の要素ごとに評価する検査」（文書をスキーマに沿って歩いて解決した型がその型の要素を見つけ、要素を「いまの要素」として既存の値の式の評価器で `where` と `check` を評価する。`of` を省けばその要素。指摘はその要素の場所）。ID の無い型でも書ける（明細の「単価 × 数量 ＝ 金額」など）。他の要素へ線を辿る検査（`match` の `edge`）は `entity` を持つ型にだけ書け、グラフの検査へ展開する。
- **表示**: 型の `label` / `description`。エンティティ型の表示名は関係レジストリ `entities:` → 型の `label` の順（レジストリはアスペクトの順序のために残す）。1 行要約は今までどおり `role`。
- **構造の検証への写し**: 追加の無い `type: 名前` は `$ref` のまま（再帰のため）。項目を足した使い方は合成した object を展開して写す。再帰する型への追加は定義エラー。
- **確かめ方**: labs/sysdev-template は domain-detail と screen-def だけ型へ書き換えて出力一致（ENT-* などの型付けが ID の形から要素の型に変わるだけ）。samples/todos は一覧の要素と個票を型にする。

### P41: 操作（型の操作とアクション）

- **目的**: Palantir の Action Types に当たる「モデルに対する操作の定義」を入れる。決まった手順の変更に名前を付け、人（画面・CLI）と AI エージェントが同じ名前で呼べるようにする。検査が「守る」側なら、操作は「正しく変える」側。

- **既知の技術との対応**: Palantir の Functions on Objects ≈ 型の操作、Action Types ≈ アクション。DDD のエンティティのメソッドとアプリケーションサービス。
- **決めたこと（2026-10-14 オーナー）①〜④**: アクションは「正しい変更の近道」で、手編集も Git もそのまま。二層＝型の `methods`（受け手の部分木に閉じる。型の `constraints` と対称）と横断の `actions`（Query・複数文書・`call`）。予約名 `create`（必須の初期値＋受け取った値か `build`）・配列の `insert`（採番 `id`・同じ明細 `key`。skill の綴り）・`delete`。イベント型のフックは入れない（予約名の結び付けと明示の `call` だけ。`auto` は例外）。

- **決めたこと（実装中）**: 受け手のキーは `target`（`on` は YAML が真偽値に読む）。受け取った値の一式が「いまの場所」で、要素は束縛名（受け手は `self`）。前提の文面は `{id}`＝起点・`$id`＝受け取った値。前提で参照した値が無ければ止める。配列が無ければ要素 1 つの配列を置く 1 つの操作にする。
- **最初の利用例**（labs/sysdev-template）: 「画面を追加する」（`add-screen`＝一覧の行・画面定義・遷移。到達性の検査が行き止まりを指摘する）と「ビジネスルールを廃止する」（`deprecate-rule`＝参照が残れば前提で止まる・型の操作 `deprecate` を呼ぶ）。

- **決めたこと⑥〜⑨**: ⑥壊れたまま保存を許し、その文書はテキスト文書（索引・検証の対象外）になる。保存は止めず、一般の文書はバナーとステータスで知らせ、スキーマ文書だけ確認を出す ⑦履歴は残す（カーネルに「テキストのまま保存して文書集合から外す」操作を足す）⑧区画エディタ（区画をまたぐ選択ができない）は採らない。大きな文書の上限は実測してマニュアルに書く ⑨下書きの寿命は未保存と同じ（閉じるときの確認）。
- **調べたこと**: Compose の標準の欄は全文を毎回配置し直すので 1 万行級では重い（開発元も 25 万字超は想定外と回答）。他の作者の対処は、標準の欄のまま上限を受け入れる（Nemo Editor）、見える行だけ自前で描く（KodeMirror・BigText）、Compose の欄を使わない（Fleet）の 3 つ。BigText は日本語の変換中の文字を扱う処理があり、将来の候補（Windows の日本語入力で試してから）。1 万行の実測: 解析 18ms・出力 21ms・色分け 5ms（問題なし）、行差分の旧実装 477ms（共通部分の切り落としで解消）。

### P46: チャートと、軸を値の式で広げるクロス集計

- **目的**: 数を扱う業務（注文管理の売上など）で、表を図で見る。チャートはフロー図と同じ「ビューの部品」（`kind: chart`）で、元の表（グリッドかクロス集計）の行を横軸の項目、数の列を系列にして描く。Excel の「表を作ってからグラフにする」と同じ形で、チャートに集計を書かない。あわせて、月の文書を置かずに「受付日の年月ごと」のような集計ができるよう、クロス集計の行と列を値の式で広げられるようにした。
- **決めたこと（2026-10-26 オーナー）**: ①ビューの種類として足す（グリッドの中には入らない。置き場は台帳のビュータブ・文書ビューの区画・ダッシュボードの区画）②第一弾の図は棒・積み上げ棒・折れ線・円 ③軸を式で広げるクロス集計も第一弾に含める ④日付から年・月を導く関数（`year` / `month` / `day` / `yearMonth`）を値の式に足す。

### P47: 開発を AI エージェントに向く形にする

- **目的**: 一貫性のある設計を保ったまま、AI エージェントによる開発の効率を上げる。規則を「読んで守る」から「破ると落ちる」へ、1 回に読む量と 1 ファイルの大きさを小さく、入口を 1 つに、画面の確認を自動にする。

## リスクと未解決課題

| リスク | 方針 |
|---|---|
| 人間の編集中文書へのエージェント変更の競合 | ベースバージョン付きパッチで検出し、既存の競合バナーの流儀で人間に選択させる |
| プロンプトインジェクション（文書内の指示文） | 文書内容は常にデータ扱い（設計原則 4）。加えて許可パッチ範囲・承認ゲートで被害半径を限定 |
| コスト・実行時間の暴走 | ターン・トークン・時間の上限をカーネルで必須にし、無人実行の方針で強化する |
| skill による任意コード実行 | 既定は宣言型変換のみ。コード実行 skill はサンドボックス外作用として明示許可制（人間の事前承認必須・定義変更で承認失効・エージェントからは起動不可） |
| 派生スキーマによる間接的な検証ルール変更 | 人間承認（既定）はゲートで足りる。自動適用だけは導出元文書への書込で承認待ちへ降格し、検証ルールが無人で変わる経路を塞いだ |
| 創作系（執筆）の品質評価が主観的 | 客観ゲートが弱い領域はルーブリック＋人間承認既定を維持し、自動適用を解禁しない |
| 大規模ワークスペースの性能 | 索引はファイル単位の増分更新に対応済み。エージェント実行時のオーバーレイ索引・ステージング検証は全再構築のままのため、遅延が目立てば次の最適化対象にする |
| GUI 常駐前提のアーキテクチャ | ヘッドレスコアを分離済み。以降の全テーマの前提 |
| 台帳外へのスキーマ誤適用（広すぎる match）による検証ノイズ | 検証の集計は `ledger` 基準に限定し、台帳外は開いた文書の個別診断のみとする |
| コンテキストの絞りすぎによる精度低下 | コンテキスト会計で内訳を可視化し、評価セットのレシピ A/B で「合格率 × トークン」を計測してデータでチューニングする |
| クエリコアの語彙が肥大して DB エンジン化するスコープ暴走 | 「やらないこと」（集約は件数のみ・任意深さの再帰なし・任意式なし）を不変条件として明文化し、解禁は実例の需要で段階判断する |
| 関係宣言・定義出現一意化の必須化による既存ワークスペースの移行コスト | lint 先行（警告のみ）・レジストリ自動推測・破壊はワークスペース単位の opt-in スイッチで吸収する |
