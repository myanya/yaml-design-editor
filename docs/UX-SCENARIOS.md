# UX試験シナリオ台帳

触り心地試験（[ROADMAP.md](ROADMAP.md) P17）のシナリオ（台本）を蓄積する台帳。機能追加の完了報告に添える「試し方」（[CONVENTIONS.md](CONVENTIONS.md) §7）を再利用可能な台本へ育て、定期的な通し試験で操作体験の劣化・取っ散らかりを検出する。

## 1. 運用

- **実施者**: プロダクトオーナー。開発側は台本の準備・試験環境の準備・指摘の記録（[BACKLOG.md](BACKLOG.md) への即時登録）を担う。
- **実施トリガ**: ①フェーズ（Px）完了ごと ②UIの骨格に触る変更（スペース・ナビゲーション・フォーム基盤）の後、に S1 を再実施する。目安として最低月1回。機能単位の「試し方」試験は従来どおり完了報告の都度（CONVENTIONS §7）。
- **記録**: 指摘は試験中に BACKLOG へ UX-nn として即時登録し、良かった点は所感メモへ残す。実施後、本書の該当シナリオの実施履歴へ1行追記する。優先度づけ・チューニングは R17-03（💬 の棚卸し）で行う。
- **台本の鮮度**: 機能の追加・変更で操作手順が変わったら、完了報告の「試し方」を該当シナリオの手順へ反映する。台本と現行UIのずれを見つけたら、台本を直すか BACKLOG へ登録する（ずれの放置は試験の信頼を損なう）。

### 未表示文書の Undo と保存

一時ワークスペースに `a.yaml` と `b.yaml` を作り、それぞれ `title: 最初` と `title: 二番目` を書く。
アプリで開き、文書フォームを開く前に台帳の一覧から両方を選択する。

1. 一括変更で `title` を `変更後` にして適用する。Undo ボタンで戻し、一覧と本文検索が元の値を示すことを確認する。
2. 未保存件数が 2 件になること、終了しようとすると確認が出ることを確認し、終了をキャンセルする。
3. `b.yaml` を開き、フォームとソースが `二番目`、差分の保存済み側が `変更後` になることを見る。ソースの行の差分印も確認する。
4. Redo で `変更後` に戻り未保存印が消えることを確認する。もう一度 Undo して「すべて保存」し、両ファイルが元の値で保存されることを見る。
5. 別の試行では手順 1 の後に文書を開かず「すべて保存」し、両方が保存されることを確認する。

見てほしい観点: どの画面から見ても値・未保存印・差分が一致し、文書を開いたことで Redo が消えないこと。
自動テスト: `HistoryConsistencyTest`。画面での試用は未実施。

### 横断 Undo の通知

一時ワークスペースに `a.yaml`（`title: A`）と `b.yaml`（`title: B`）を作り、アプリで開く。

1. B を編集し、A を表示して Ctrl+Z を押す。B の編集画面へ直接戻り、その場で値が戻ることを見る。Alt+←で A に戻り、Redo で再び B を表示して値が復元されることを確かめる。
2. B のソースを編集して別の画面へ移り、Undo する。解析待ちの有無にかかわらず B のソースタブへ戻ることを見る。同じ画面での Undo は入力の焦点を余計に移さないことを確かめる。
3. ビューのセルから編集し、原本のファイルを開いて Undo する。編集したビューへ戻ってセルの値が戻ることを見る。一覧の一括変更でも、元の一覧へ戻り全対象が戻ることを確かめる。
4. A と B を一括変更して Undo し、未保存件数が 2 件になることを見る。通知から A を開いて保存すると 1 件、「すべて保存」で 0 件になり、通知は残ることを確かめる。
5. 別フォルダーの同名ファイルを含めて 4 件以上を一括変更し、Undo する。対象一覧が相対パスで区別でき、スクロールして最後の対象も開けることを見る。
6. ライト・ダーク、狭いウィンドウ幅でも通知・長いパス・閉じる操作を確認する。壊れた下書きの確認をキャンセルした場合は画面も変わらないことを見る。

見てほしい観点: 編集した画面で変更が戻る感覚があるか、ビュー経由の操作が原本ファイルへ飛ばず元のビューで完結するか。
自動テスト: `HistoryNoticeTest`・`HistoryLocationTest`。実画面でのレイアウト・焦点・視認性の確認は未実施。

### 外部変更と保存

一時ワークスペースに `a.yaml`（`title: A`）と `b.yaml`（`title: B`）を作る。

1. 一覧で両方の title を一括変更し、Undo する。外部エディタで A を別の値に保存してから「すべて保存」する。
2. A の外部編集が残り、B だけ元の値で保存され、A の未保存印と保存失敗の通知が残ることを確認する。A を開くと競合バナーが出ることを見る。
3. 「次回保存で上書きを許可」を選ぶ。この時点ではディスクが変わらず、Ctrl+S で編集内容が保存されることを見る。
4. 別の試行では許可後にもう一度外部で編集してから保存する。再び停止することを確認し、「ディスク版を読み込む」で最新の外部編集へ切り替える。
5. ソースが `title: [` の状態や、外部でファイルを削除した場合にも、許可前の保存が停止することを見る。

見てほしい観点: 保存できた文書とできなかった文書、上書き許可と実際の保存の違いが分かること。
自動テスト: アプリ・workspace-core の `SaveConflictTest`。画面での試用は未実施。

### ソース入力直後の Undo と Redo

一時ワークスペースに `a.yaml`（`title: A`）と `b.yaml`（`title: B`）を作り、アプリで開く。

1. `a.yaml` のソースで値を入力し、間を置かず Ctrl+Z を押す。本文が元に戻り、少し待っても入力内容が復活しないことを見る。
2. Ctrl+Y で入力内容が戻ることを確認する。Undo/Redo ボタンでも同じ結果になることを見る。
3. `b.yaml` をフォームで変更し、`a.yaml` のソースへ戻って入力直後に Undo する。最初は A の入力が戻り、次の Undo で B が戻ることを確認する。
4. Undo の後に新しいソースを入力する。反映待ちの間は Redo ボタンが無効で、反映後も古い編集が復活しないことを見る。
5. 有効な編集をした後、ソースを `title: [` にして Undo する。確認をキャンセルすると下書きが残り、再操作して確認すると元に戻ることを見る。

見てほしい観点: 待ち時間の有無やボタンとキーで、戻る対象・通知・ソースの表示が変わらないこと。
`SourceHistoryTest` では遅れた解析結果と確認中の変更も待ち時間なしで再現する。画面での試用は未実施。

### フォーム入力の Undo と Redo

一時ワークスペースに `a.yaml`（`title: A`）と `b.yaml`（`title: B`）を作り、フォームで開く。

1. A の値を変更し、入力欄にカーソルを残して Ctrl+Z、Ctrl+Y、Ctrl+Z、Ctrl+Shift+Z を順に押す。値の取り消しと復元、未保存印、履歴通知がツールバーと一致することを見る。
2. A、B の順に変更し、A の入力欄へ戻って Ctrl+Z を押す。B の変更が戻り、通知から B を確認できることを見る。次の Ctrl+Z は A を戻す。
3. 数値・複数行・日付・ID・参照・ファイルパス、文書情報、表のセル、埋め込みフォーム、スキーマ設計の直接入力でも手順 1 を試す。
4. 検索欄、汎用フォームの追加キー／改名、スキーマの定義追加、操作パネルの値を入力して Ctrl+Z を押す。入力途中の文字列だけが戻り、文書の履歴と通知が変わらないことを見る。
5. フォームで日本語を変換中に Ctrl+Z を押し、変換終了後もキーを押し続ける。文書の履歴が戻らないことを確認し、キーを離して押し直すと通常の Undo になることを見る。
6. 履歴をすべて戻した状態でも Ctrl+Z を押す。欄だけが古い値へ戻ったり、Redo が失われたりしないことを見る。

自動テスト: `TextFieldHistoryTest`（キー判定・IME の一押し・文書との接続・横断履歴）。実際のキー配送と IME を含む画面での試用は未実施。

### Undo のまとまり

試験用コピーのワークスペースで、保存時の自動値を持たない文書の文字列項目を使う。画面の往復はできるだけ素早く行う。

1. 同じ欄へ続けて文字を入力し、Ctrl+Z で一まとまりとして戻ることを見る。1 秒より長く間を空けて追記した場合は、その追記から戻ることを確認する。
2. 入力後、差分タブへ切り替えてすぐ元のタブへ戻り、同じ欄へ追記する。Ctrl+Z で復帰後の追記だけが戻り、もう一度で移動前の入力が戻ることを見る。
3. 別文書・ビュー・実行スペースへの往復でも同様に試す。Alt+←／Alt+→による往復と、ビューで同じセルへ戻った場合も確認する。
4. ソースで有効な値を書き、解析を待たずに別画面へ移って戻り追記する。Undo は追記だけを戻し、移動前の入力を取りこぼさず、待っても値が復活しないことを見る。
5. 入力して Ctrl+S、すぐ同じ欄に追記して Undo する。保存した値へ戻って未保存印が消えること、もう一度 Undo すると保存前へ戻って未保存になることを見る。「すべて保存」でも試す。
6. Undo の後に編集せず画面を往復する。Redo が有効のままで、元の編集をやり直せることを確かめる。

観点: 保存や画面移動を区切りとして自然に感じるか、連続入力が細かく分かれすぎたり戻りすぎたりしないか。
自動テスト: アプリ・コアの `HistoryCoalescingTest`。
実施履歴: 2026-10-24、利用者から確認できたとの回答と「非常に良い」との評価。個別手順の実施範囲は未記録。

### 書式を含むソース編集の Undo と Redo

一時ワークスペースの `a.yaml` に `title: A` と `note: 維持 # コメント` の2行を書いて開く。

1. ソースを `title:    入力` と `note:    維持 # コメント` に変更し、カーソルを「維持」の前へ置く。Undo で title が A に戻り、note の空白・コメントとカーソル位置が保たれることを見る。
2. Redo と Undo を繰り返し、ソース・フォーム・差分の値が一致し、待っても取り消した値が復活しないことを見る。
3. 引用符つきの値、複数行文字列、`---` 区切りの後続文書でも試す。インデントを保つと値が変わる場合は書式調整の通知が出て、内部データと同じ内容が表示されることを見る。
4. 構文エラーのある下書きでは従来の破棄確認が出て、キャンセルした下書きが残ることを見る。

自動テスト: `SourceHistoryTest`・`SourceHistorySyncTest`。画面での試用は未実施。

### ソースの構文状態と詳細

1. 試験用ワークスペースの `_schemas` 内の文書を開き、「ソース」へ移る。緑の構文状態と保存状態が別々に表示されることを確認する。
2. 末尾に `test: [` を追加して入力を止める。確認中から赤い解析エラーへ変わっても、本文の開始位置が動かないことを見る。続けて文字を入力し、エラーの文面が変わっても位置が安定することを確認する。
3. 「詳細」を開き、長文をスクロール・選択・全文コピーできることを確認する。閉じる・Esc・外側クリックをそれぞれ試し、元のカーソルとスクロール位置で入力を再開できることを見る。
4. 詳細の「該当行へ移動」で問題の行へ移ることを見る。追加した行を消し、緑へ戻っても本文が動かないことを確認する。
5. ウィンドウを狭くし、状態文が省略されても「詳細」が押せること、上部の操作行を横にスクロールできることを確認する。ライト・ダークの両テーマと通常のYAML文書でも試す。
6. 試験用文書で解析できないまま保存し、スキーマの場合は確認に進む。赤い保存済み状態と詳細の説明を確認する。修復して保存し、通常の編集に戻ることを見る。

緑の構文状態はスキーマ検証の合格を意味しない。検証の指摘がある文書でも、その区別が読み取れるかを確認する。

## 3. S1: 全体通しシナリオ（ゼロから承認まで）

### 3.1 目的・前提

主要ワークフロー「スキーマ作成→文書記入→詳細化→ビュー→エージェント実行→承認」を、**空のワークスペースから通しで**触る。個別機能の正しさではなく、工程の継ぎ目（次に何をすべきか分かるか・行き来が自然か）を見る試験。

- 所要: 約80分（1回通し）。中断する場合は幕の区切りで保存すればディスクに残る。
- 前提: JDK 17+。AIのAPIキー（幕6で使用。環境変数 `ANTHROPIC_API_KEY` または `OPENAI_API_KEY` を**起動前に**設定するのが楽。接続ダイアログでの入力でも可＝メモリのみ保持）。
- ワークスペース: **毎回新しい空フォルダ**で行う（例 `C:\work\ux-s1-0808`。立ち上げ体験も試験対象のため使い回さない）。
- エージェント実行は実APIを使う（maxTurns 8 に制限済み。1回の実行で数万トークン程度を想定）。

**横断観点（全幕共通で気にする）**:

1. 4スペース（編集・台帳・実行・設計）の切替が「やりたいこと」の軸として機能しているか
2. 「検証に導かれて埋める」ループが工程の最初（スキーマ直後）から最後（エージェントのゲート）まで一貫しているか
3. 未保存編集の「見たまま判定」が全画面で一貫しているか（保存しないと反映されない画面が残っていないか）
4. 空状態・初回操作で「次の一歩」が画面から読み取れるか（人間向け段階的開示）
5. フォームを開き、左右ペインを両方閉じる／左だけ／右だけ／両方開くの各状態で幅を変える。入れ子の項目も展開し、項目名と入力欄の縦配置、ヘッダー操作の折り返し、表内の横スクロールで右端まで操作できるかを見る。
6. 列の多い配列・map の表でレコードを展開し、横スクロールしても編集フォームの左右が表示領域内に残り、見出しと各行の列位置が揃うことを見る。左右ペインの開閉・複数行の展開・表の入れ子・閲覧専用モードでも確認し、配列の並べ替えも試す。
7. 広いフォームで object・map・array を開き、内容が項目名の下から全幅を使うことを見る。単一値は左右配置、狭いペインでは縦配置になること、空の複合値・any・属性付き参照・汎用mapでも配置が自然なことを確認する。
8. 短い説明と長い Markdown 説明（段落・箇条書き・コード・リンク）を持つ項目で、項目名・ⓘへのホバーによる小さな予告を試す。項目名から入力欄までの空白・説明文・AIボタンでは表示されないことを見る。
   短文の幅が内容に合い、長文は約5行分と全文への案内に収まることを確かめる。ⓘをクリックして全文を固定し、スクロールとリンク操作、×・外側クリック・Escでの閉じ方を試す。
9. Tab でⓘへ移り Enter／Space で開く。閲覧専用・暗いテーマ・画面の右下でも説明が読めること、ホバーが入力の焦点を奪わないこと、折りたたみの保持・指摘からの自動展開・Undoが従来どおりなことを見る。

### フォーム入力の Esc

起動はリポジトリ直下で `GRADLE_USER_HOME` に既存の `.gradle` を指定して `gradlew.bat run --args="samples/todos"`。
文書ツリーから `todos/details/TODO-001.yaml` を開き、フォームで試す。試験用の変更は保存せず Undo で戻す。

1. 「ID」「期限」へ文字を入力して Esc。入力内容と未保存表示が保たれ、入力カーソルとフォーカス枠だけが消えることを見る。再クリックして編集を続け、空欄・不完全な日付でも同じか確認する。
2. 「文書情報」の概要へ複数行を入力して Esc。改行を含めて残り、選択中の文字も消えないことを見る。Esc 自体が Undo の一操作にならず、Ctrl+Z で入力変更を戻せるか確認する。
3. 日本語 IME で変換候補を出し Esc。変換の取消・候補の閉鎖を優先して入力欄に残り、変換終了後の別の Esc でのみフォーカスが外れることを見る。
4. ID の候補を開き Esc。候補だけが閉じて入力欄に戻り、押し続けてもフォーカス解除へ進まず、キーを離して再度押すと外れることを見る。参照・文書参照でも同じ操作を試す。
5. 「期限」のカレンダーを開き Esc。先にピッカーだけが閉じることを見る。時刻の「決定」前の選択が、Esc で勝手に適用されないことも確認する。
6. 数値の桁区切りや format を持つ欄で `1234` を入力して Esc。非フォーカスの表示へ戻り、再編集時は元の値になることを見る。不正値も消さず、書式切替だけで変更が増えないか確認する。
7. ファイルパス・表内セル・汎用フォームの新しいキー・スキーマ設計でも内容保持を確認する。キー追加・改名では Esc が確定にならず、入力途中の文字だけが残ることを見る。

## 6. S2: 自動化・連鎖シナリオ（無人運転と人間の関与）

### 6.1 目的・前提

エージェント運用を「見ている前提の手動実行」（S1 幕6〜7）から「**見ていない前提の自動実行**」へ広げたときの体験を通しで試す。対象は trigger（on-change / on-invalid / schedule）・直列キュー・受信箱・`approval: auto`・巻き戻し（revert）・連鎖（chain）・無人リトライ（retry）。エンジンの正しさは単体テスト済み（`AutomationTest`）のため、見るのは**無人動作を人間が信頼・制御・復元できるか**。

- 所要: 必須幕 約90分（任意プローブ込みで約110分）。実API実行は約8回（各 maxTurns 12 制限。初回実施の実測で 6 では不足＝11ターン。1回あたり数千〜数万トークン想定）。
- 前提: **S1 実施済みワークスペースをそのまま使う**（ISS-001〜007・詳細文書・スキーマ・ビュー・reviewer 定義が揃っている状態が出発点）。APIキーの設定は S1 幕0 と同じ。
- 待ち時間の設計: 付録の定義は debounce 10秒・schedule 1分に短縮してある（既定は30秒・分単位）。schedule は監視ONの間**毎分発火し続ける**ため、観察が済んだら都度監視をOFFにする（このON/OFF操作の煩わしさ自体も観察対象）。
- 「停止」ボタンはキュー消去＋実行中断で、監視もOFFに戻る。幕をまたぐときは監視状態を確認してから進む。

**横断観点（全幕共通で気にする）**:

1. **可観測性**: いま自動で何が起きた／起きようとしているかを、レール・ステータスバー・自動化タブ（キュー・履歴・ログ）・受信箱から追えるか
2. **制御感**: 止めたいときに止められるか（監視OFF・停止）。`approval: auto` の3条件（ゲート通過・スコープ内・対象が非編集中）が体感として腑に落ちるか
3. **復元可能性**: 自動適用→バックアップ→巻き戻しの安心感。CLI往復（revert / apply）の断絶がどの程度気になるか
4. **定義の敷居**: trigger / chain / retry / approval をフォーム（組込みスキーマ）で書き切れるか（BACKLOG UX-38 の再確認）

**事前仮説（狙って突く摩擦候補）**: ①revert がCLIのみ（GUIに欲しくなるか） ②受信箱の承認待ち・監視ON状態がアプリ再起動で消える（メモリのみ。変更セットのファイルは残る） ③debounce・分単位scheduleの「待ち」の体感（次の発火までの表示がない） ④無人ログを後から読む頻度が上がるため UX-39（ログ可読性）がより強く効く。

### 6.2 幕構成

#### 幕0: 準備（約10分）

1. S1 のワークスペースを開き、各文書の検証エラーが残っていないことを確認する（全体一覧はGUIに無いため、必要なら CLI `validate` を使う＝UX-44。`review_comments` の未知キー警告は残っていてよい——次で消す）。
2. **`review_comments` の正式フィールド化**（§5 拡張パスの前倒し）: 付録 B-1 のとおり共通定義ライブラリ `_schemas/_common.yaml`（`kind: library`）を新規作成し、`issue` と `issue-detail` の**ルート fields** へ `$ref` 参照のフィールドを追加する（設計UIでの追加とソース貼り付け、どちらでもよい）。保存後、未知キー警告が消えることを確認する。
3. APIキーを環境変数で設定して起動する（S1 幕0 と同じ）。

**見てほしい観点**: データが先・スキーマが後の「後付けフィールド化」の手数は妥当か。共通定義（library / `$ref`）の書き味。警告が消える瞬間の分かりやすさ。

#### 幕1: 自動化の入口（約5分）

1. 実行スペース「自動化」タブを一巡する: 監視トグル（「監視・自動実行 停止中」）・停止ボタン・空のキュー・履歴・ログ。
2. 監視をONにする。trigger 付きアクティビティがまだ無い状態で「有効にしたのに何も起きない」ことがどう見えるかを観察し、OFFへ戻す。

**見てほしい観点**: 「監視を有効にすると何が起こるか」が画面から読み取れるか。trigger 定義ゼロの空振り状態に案内はあるか。

#### 幕2: on-change トリアージ→受信箱（約15分）

1. 設計スペースで `_agents/triager.yaml`（付録 B-2）と `_activities/triage-issues.yaml`（付録 B-3）を作る。trigger / retry / gates は一度は**フォーム（組込みスキーマ）での入力**を試す（UX-38 の再確認）。
2. 自動化タブで監視ON。
3. 編集スペースで課題 ISS-006 を追加（件名「監視ログの保存先が散在している」・status: open・priority: high・期限と概要は**空のまま**・担当も未設定）→ 保存。
4. 自動化タブで debounce（10秒）→ キュー投入 → 実行開始の流れを観察する。実行中ログの読み味を手動実行タブと比べる。
5. 完了すると受信箱に変更セットが届く（レール・ステータスバーのバッジで気づけるか）。レビューして適用する。
6. 適用後、自動化タブで**再発火しない**こと（自己変更の抑止）を確認する。

**見てほしい観点**: 保存→発火→受信箱の一連が「見ていなくても分かる」導線になっているか。適用が再トリガしない安心感。

#### 幕3: on-invalid 穴埋めと直列キュー（約15分）

1. `_activities/complete-issues.yaml`（付録 B-4）を作る。監視ON。
2. 課題 ISS-007 を **id と件名だけ**で追加（件名「四半期報告の集計が手作業」）→ 必須の status / priority が欠けて検証エラーの状態のまま保存する。
3. 1回の保存で on-change（triage-issues）と on-invalid（complete-issues）の**両方**が発火し、キューに2件並ぶ → **直列に消化**される様子を観察する。
4. 受信箱に2件届く。先に穴埋め（complete-issues）の変更セットを適用する。
5. **意図的な競合プローブ**: 続けてトリアージ側の変更セットも適用してみる。両方とも同じ原本を基準にしているため、2件目は base 競合で拒否される想定。競合の見え方・リカバリ導線（却下して再実行など）を記録する（拒否され**ない**場合はそれ自体を記録）。
6. **逆プローブ**: エラーのない軽微な編集（概要の一字修正など）を保存し、キューに triage-issues **だけ**が積まれ complete-issues は発火しないことを確認 → 実行が始まる前後で「停止」を押し、キャンセル（キュー消去・実行中断）の挙動も見る。停止後は監視がOFFへ戻ることを確認する。

**見てほしい観点**: 「検証エラーのまま保存すると直しに来てくれる」体験は信頼できるか。多重発火・直列消化・競合が不安を生まないか。

#### 幕4: schedule 定期棚卸しと自動適用・巻き戻し（約20分）

1. `_activities/sweep-issues.yaml`（付録 B-5。`approval: auto`・everyMinutes: 1）を作る。担当未設定の課題が指摘対象になる——幕2〜3の適用で全課題に担当が付いていることがあるため、**無ければ手で用意する**（例: ISS-003 の assignee を空にして保存。この保存で triage-issues が発火したら、届いた変更セットは却下してよい）。
2. **降格プローブ**: `issues/00-issues.yaml` に未保存編集を残した状態（概要をどこか触って dirty のまま）で監視ON。約1分後の実行完了時、自動適用ではなく**受信箱へ降格**することを確認する（3条件の「対象が非編集中」を欠くため）。監視OFF。受信箱の変更セットは**却下**し、未保存編集は Undo で破棄する。
3. **自動適用**: 対象が clean の状態で監視ON。次の発火で受信箱を経ず自動適用まで走ることを確認する（履歴の自動適用記録・文書への指摘追記）。確認したらすぐ監視OFF（毎分発火し続けるため）。
4. 適用結果を編集スペースで開き、`_runs/` の実行記録（適用前バックアップを含む）を確認する。
5. **競合→巻き戻し**: 適用されたファイルへ軽微な編集を加えて保存し（適用後の変更を作る）、CLI で巻き戻す: `./gradlew runCli -q --args="revert <ワークスペース絶対パス> _runs/<実行記録>.yaml"` → **競合として拒否**されることを確認 → `--force` を付けて再実行 → 適用前の内容へ復元されることを確認する（自分の編集も消える点に注意）。
6. GUI側の追随: revert 直後、開いていた文書が外部変更としてどう見えるか（取込み・競合表示）を観察する。

**見てほしい観点**: 降格が「黙って失敗」ではなく理由つきで受信箱に現れるか。自動適用の履歴・バックアップで「勝手に書かれた」不安が拭えるか。revert がCLIのみである断絶の体感（GUIに欲しくなるか）。

#### 幕5: 連鎖（約15分）

1. `_activities/sweep-issues.yaml` の trigger を `{ type: manual }` へ変更する（毎分発火を止め、連鎖ターゲット専用にする）。
2. `_activities/triage-issues.yaml` へ chain を追記する（付録 B-3 末尾のコメント参照）。
3. 監視ON。どれかの課題の概要をあいまいな記述へ編集して保存 → triage-issues 発火 → 受信箱で**採用・適用** → **採否決定後**に連鎖で sweep-issues が起動することをキュー・履歴で確認する（sweep は `approval: auto`。追記すべき指摘が残っていなければ「変更なし」で終わってよい——連鎖実行そのものが履歴に載ることを見る）。
4. **（任意・+1実行分）逆プローブ**: もう一度 triage-issues を発火させ、今度は**全却下**する → changedFiles 条件を満たさず連鎖**しない**ことを確認する。
5. 監視OFF。

**見てほしい観点**: 「承認したら次が動く」の因果が履歴・キューから追えるか。連鎖起動の理由（どのルールに一致したか）は見えるか。

#### 幕6（任意）: 無人リトライと収束打ち切り（約15分）

リグ（意図的な失敗設定）でリトライ経路を観察する。試行1回が丸ごと1実行分のトークンを使うため任意。

1. `_activities/complete-issues.yaml` の allowedPaths を `["review_comments*"]` に**狭める**（instruction は必須補完のまま＝書きたい場所に書けない状態を作る）。`retry: { maxAttempts: 2 }` が付いていることを確認する。
2. 監視ON。ISS-008 を id と件名だけで保存 → on-invalid 発火 → エージェントは必須項目を書けず（スコープ拒否）、検証ゲートも通せない → **失敗** → 失敗理由がフィードバックされて**リトライ** → 同一失敗の繰り返しで**収束打ち切り**、を履歴・ログで観察する（triage-issues も同時発火する。受信箱へ届いた変更セットは却下してよい）。
3. 監視OFF。allowedPaths を元へ戻し、ISS-008 の必須項目は手で埋める（または行ごと削除する）。

**見てほしい観点**: 失敗の理由が履歴・ログから読み取れるか（スコープ拒否とゲート不通過の区別）。リトライと打ち切りの説明性。

#### 幕7: 耐久性・再起動と計測（約10分）

1. 承認待ちを1件仕込む: 課題の概要を軽く編集して保存 → triage-issues 発火 → 受信箱に変更セットが届いたら**適用せずに**アプリを終了する。
2. 再起動して同じワークスペースを開き、受信箱と監視状態を確認する（実装上は受信箱は空・監視はOFFへ戻る想定。「変更セットが消えたように見える」体験を記録する）。
3. `_runs/` に `*-changeset.yaml` が保存されていることをツリーで確認し、CLI で適用する: `./gradlew runCli -q --args="apply <ワークスペース絶対パス> _runs/<changesetファイル> --require-valid"` → 起動中のGUIに外部変更としてどう反映されるかを観察する。
4. 「計測・評価」タブで自動適用・巻き戻しの集計（幕4の実績）が載っていることを一瞥する。CLI の同一面確認は S5 で扱う。

**見てほしい観点**: 「アプリを閉じたら承認待ちがどうなるか」への不安と実際のギャップ。changeset ファイル→CLI apply の救済導線に気づけるか（画面に案内はあるか）。

## 8. S6: エンティティページとグラフレンズ（P23）

### 8.1 目的・前提

論理層の読み書き面（ROADMAP P23）を触る短時間の試験。「エンティティ全体像の閲覧→値の編集→関係の両方向確認→改名」が1画面で完結するか（R23-02 完了条件②）と、レンズの近傍表示→ページ着地（同④）を見る。

- 所要: 約30分。AIは使わない（read_entity の確認は CLI で代替）。
- ワークスペース: `sample-workspace/`（アスペクト宣言済み: `entity-model` / `table-design` 型・レジストリ `entities:` 節）。**todos はユーザーの実験場のため、編集は必ず Undo で戻すかコピーしたワークスペースで行う**。

### 8.2 手順

1. **一覧→ページ**: 台帳スペース「エンティティ」タブ → 左の一覧で ID の下にエンティティ型ラベル（例 TBL-TASK に「テーブル設計」）が出ることを確認 → TBL-TASK を選択。
2. **全体像**: ヘッダ（ID・型バッジ・タイトル・操作メニュー・「グラフで見る」）とアスペクト見出し（「テーブル設計（定義）」＋ファイル座標）を確認。「出現別フォームで表示」トグルで従来表示と往復する。
3. **編集**: 合成全体像のフォームで status を変更 → 未保存●・「すべて保存（1）」・Undo が通常どおり効くこと（編集は原本座標への通常編集）。Undo で戻す。
4. **関係パネル**: 「→ 由来する」（derives の label）に ENT-TASK が出ること・行クリックで ENT-TASK のページへ移動すること・ENT-TASK 側では「← 実装される」（inverseLabel）に TBL-TASK / TBL-TASK-HISTORY が出ること。矢印アイコンで参照座標（文書）へ飛べること。属性付き参照の注記（role: model）も見る。入れ子で書かれた要素があれば「◆ 保有:」「◇ 所属:」の節（関係名のラベル・子の役割・書かれた場所）も出ること。
5. **改名**: 操作メニュー「改名…」→ 改名先に `ENT-TASK2` 等を入力 → プレビュー（出現・参照の件数・対象ファイル）を確認して**キャンセル**（適用まで試すならコピーしたワークスペースで。適用後は参照元も書き換わり、ページが新IDへ切り替わる。B-1 以降、適用直後なら **Ctrl+Z 1回**で全ファイル戻せる＝戻した状態は未保存●・保存で確定）。
6. **レンズ**: ENT-TASK のページで「グラフで見る」→ レンズに起点近傍（深さ2）が放射配置（起点が中心）で出る。深さ1↔2の切替・右パネルの「型」「関係」タブの絞り込み（色の凡例もここ）・配置の切替（放射／階層／応力／力学）を確認 →ノードの箱をクリックしてエンティティページへ着地 → `Alt+←` で戻れること（履歴）。「起点を解除」で全体表示（応力配置）も見る。
   操作も試す: ホイールで拡大縮小（カーソル中心）・箱をドラッグして動かす（辺が追随する）・箱にホバーして隣だけ濃くなる・右クリックで「起点にする」「原本へ」「この型を隠す」・「PNG に保存」で画像を書き出す・縮小を戻して右下のミニマップで移動。
   保有（入れ子で書かれた要素。`labs/sysdev-template` なら画面→画面項目）は箱の入れ子で描かれ、畳んだ箱に「▸ 件数」が出て、押すと開くこと。関係のチェックに「（保有）」の印が付くこと。起点の近傍では起点の外側の箱が開いていること。
   「側面で分ける」を入れると箱が出現になり、SCR-RESERVE-INPUT が一覧・基本・物理の 3 つの箱に分かれて点線で結ばれ、基本の箱の中に SI、物理の箱の中に SPI が入ること。外側の箱をドラッグすると中の箱も動くこと。
   ツールバーの「型」で段を上げると、箱がエンティティ型（画面・画面項目・ユースケース…）になり、線が関係レジストリの関係、入れ子が保有の宣言（画面の中に画面項目）になること。箱を押すとその型を定義するスキーマ文書が開き、右クリック「この型の実体を見る」で実体の段に戻ってその型だけが見えること。
   `_views/lens.yaml`（`kind: lens`）で `arrow: reverse` にした関係（labs/sysdev-template なら derived-from）は、矢印が相手から参照を書いた側へ描かれ、文字が inverseLabel（「導出された成果物」）になること。設計スペースの「ビュー」にこの定義が並ぶこと。
7. **CLI同一面（任意）**: `./gradlew runCli -q --args="entity sample-workspace show TBL-TASK"` がページと同じ合成（アスペクト・座標・関係）を返すこと。

**見てほしい観点**:

- 全体像（アスペクト合成）は「複数文書に散らばる同一IDの情報」の把握を実際に楽にしているか。出現別フォームとの使い分けは自然か
- 関係パネルの両方向表示（label / inverseLabel）で「どちら向きの関係か」を迷わないか
- 操作メニューの改名・統合・削除は、プレビューだけで影響を信頼できるか
- レンズは「全件の一枚絵」より意思決定に使えるか（絞り込みの操作感・ラベルの可読性）

## 表示方式の固定とファイル指定

見てほしい観点は、現在の表示とファイル指定を区別できるか、固定と引き継ぎが予測どおりに働くか、アイコンと×で迷わず切り替えられるか。
