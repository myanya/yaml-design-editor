# ADR-0042: 業務モデルから 3 つの変換でソースコードまで作り、定義書と設計書を各段のモデルのビューにする

- 日付: 2026-11-25
- 状態: 方針合意（samples/todos-sysdev。体系の移行は進行中で、段階と進み具合は移行計画にある）

## 文脈

`samples/todos-sysdev` の変換定義 84 本と生成物を、ファイルの単位で調べた（[ファイル単位の生成グラフ](../../samples/todos-sysdev/docs/design-file-graph.html)）。次のことが分かった。

- 業務モデルに補正を当てて解き直したもの（補正後の業務モデル）が 3 段あり、その間にエンティティ定義書とアクション定義書が挟まっている。
- 詳細設計の導出 11 種が、基本設計ではなく、補正後の業務モデルを通して業務モデルの中身を読んでいる。
- 設計の情報とビューが分かれているのは、エンティティとテーブルだけである。残りの 20 種は、文書の形のファイルが情報を兼ねている。
- 各文書が同じ名前を業務モデルから別々に計算し、付け替えだけを表（4 枚）で伝えている。
- 人が書く入力は、補正・指定・追加・型対応・設定に分かれ、変換の前に効くものと後に効くものが混ざっている。

オーナーがもともと目指していた形は、LSI の論理合成・テクノロジマッピング・配置配線にならったものである。
業務モデルからアーキテクチャに写して抽象的なシステムのモデルを作り、技術スタックに写して具体的なモデルを作り、コードに写す。設計書は、各モデルをレビューしやすくするビューである。
この形を定式化し、補正の位置づけを単純にした。

## 決定

### 段と変換

```text
業務モデル
   ↓ アーキテクチャマッピング
抽象システムモデル（基本設計）      ビュー = 定義書
   ↓ 技術スタックマッピング
具体システムモデル（詳細設計）      ビュー = 設計書
   ↓ コードマッピング（前半）
プログラム設計（配置）
   ↓ コードマッピング（後半）
ソースコード
```

- **定義書**は基本設計の成果物、**設計書**は詳細設計の成果物と呼び分ける。どちらも、その段のモデルのビューで、ビューにしかない情報を持たない。
- 各段のモデルは**項目の形**で保存し、同じ段の項目を ID で指す。値を写さない。
- 各段の変換は、**1 つ前の段のモデルだけ**を読む。次の段を作るのに要る情報は、すべて前の段のモデルが運ぶ。
- ソースコードは、詳細設計かプログラム設計を読む。配置を決める必要がないもの（DDL・CSS）は詳細設計から直接出す。基本設計より前は読まない。

### 段の境

- **抽象と具体**: 技術スタックを替えても変わらないものが抽象である。確認画面・画面遷移・URL・二重確定を防ぐトークンは抽象、クラス名・型の名前・Mapper・SQL の型は具体とする。
- **詳細設計とプログラム設計**: 詳細設計は、技術スタックの言葉で「何を作るか」を書く（型の名前・クラス名・メソッド名）。
  プログラム設計は、「Java の文としてどう書くか」を書く（完全修飾名・アクセサ名・出力先のファイル）。Java の型対応表とテーマは、詳細設計に置く。

### 人が書くもの

人が書くのは、業務モデルと、各段の**判断**だけである。生成物は直さない。

| 場所 | 書くもの |
|---|---|
| 業務モデル | 業務の事実。業務として誤っている・足りないものは、ここを直す |
| 全体の判断 | 同じ種類のものすべてに当てる方針（認証の方式、型対応表、区分の定義 など） |
| 個別の判断 | 特定の要素だけの決定（区分の割当、索引の追加、名前の付け替え など） |

- 判断は段ごとに置き、**それを言える最初の段に 1 回だけ**書く。
- 判断は、対象より**下流のすべて**に届く。変換の前に効くか後に効くかは、書く人が選ばず、対象の ID から決まる。
- **変換の前に業務モデルを補正する層は置かない。** 業務モデルは自由に直せるものとする。業務モデルに本来要らない情報を足す必要が出たら、そのときに考え直す。
- 個別の判断を入れる前の結果（補正前）は、層ではなく**比較の相手**とする。確定したモデルとの差は、すべて個別の判断で説明できる。

### 項目の出どころ（2026-11-26 に追記）

システム化のために要る項目（業務モデルに無い項目）は、業務モデルに足さず、その段の判断として書く。項目の出どころは、次の 3 つである。

| 出どころ | 例 | 書く場所 |
|---|---|---|
| 業務の事実 | 期限、完了結果、作業項目 | 業務モデル |
| システム化のために、同じ種類すべてに要る | 更新者・更新日時、同時更新を検出する版、論理削除、ログイン利用者 | その段の全体の判断（方針） |
| システム化のために、特定の要素だけに要る | 特定のテーブルの索引、特定の画面だけの表示設定 | その段の個別の判断（追加） |

- 見分け方は 2 つの問いである。紙と台帳で業務をしていても、その項目はあるか（あるなら業務モデル）。アーキテクチャや技術スタックを替えたら、要らなくなるか（なるなら設計の判断）。
- システム化で足す項目は、項目だけを足しても動かない（だれが、いつ、何を書き込むかの規則が要る）。そのため、**方針と規則を組にして、全体の判断として書く**のを基本とする。各段の変換がそれを読み、対象の要素に項目を足す。
- 個別の追加は、下流がその種類を一般に扱えるもの（索引・セッションの属性など）に限る。
- 足した項目は、業務から来た項目と同じ形（同じ ID の体系）で、由来に「どの判断から来たか」を持つ。足した段から下流にだけ存在し、業務モデルには戻らない。
- どの段に書くかは「それを言える最初の段」に従う。技術を替えても要るもの（監査項目・同時更新の検出・論理削除）は抽象、技術の都合で要るもの（代理キー・並び順の列・外部キーの列・索引）は具体に書く。

### 抽象システムモデルの中身

要素の種類は、型・エンティティと項目・状態と遷移・データの決まり・操作・一覧の検索条件・画面・画面遷移・エラー・メッセージの 10 種とする。
状態と遷移・データの決まり・一覧の検索条件は、複数の箇所から読まれるので独立させ、操作や画面からは ID で指す。
ファイルは、業務モデルの 1 つの要素を直したときに Git の差分が 1 ファイルに収まるように分ける。

## 既存の決定との関係

- **ADR-0034**（段の項）の骨格を引き継ぐ。「補正の置き場は 3 つ（業務の事実は業務モデル、全体の方針、個別の例外）」は、業務モデル・全体の判断・個別の判断として残す。
  「詳細設計書が業務モデルを読んでもよい」は上書きする。各段は 1 つ前の段だけを読む。`.yde/stages/` の仕組みを使うかどうかは、この ADR では決めない。
- **ADR-0031** の「業務モデルの項に設計の規則を入れない」は残す。「設計書は業務モデルから生成する」は、基本設計までに限る。
- **ADR-0035・0036**（設計項目一覧とビュー、詳細設計項目一覧と型対応表）は維持し、エンティティとテーブル以外の種類にも広げる。
- **ADR-0038・0039** の「確定項目をビューと後段の生成で共有する」は維持する。
  導出・補正と指定・追加の分類は、全体の判断と個別の判断の 2 種類にまとめ直す。
  ADR-0039「明記と継承」の、共通型への補正を解き直して使う項目へ届ける処理は上書きする。共通型を直すときは、業務モデルを直す。
- **ADR-0041** の `design/basic/`・`design/detail/` の配置は維持する。プログラム設計（`application-*.yaml`）を詳細設計の確定項目に置いた点は上書きし、置き場所を分ける。
  `derived/` は補正前の比較用、`composed/` は検査記録の置き場として読み替える。
