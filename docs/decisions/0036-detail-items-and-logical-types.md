# ADR-0036: 詳細設計の項目一覧は詳細設計にだけ出るものを持ち、論理型は基本設計の設計項目、実装の型は型対応表で決める（区分は基本設計項目台帳・業務モデルのどの形もテーブルにする）

- 日付: 2026-11-16
- 状態: 承認済み（samples/todos-sysdev のテーブル設計書から）

## 文脈

ADR-0035 で、エンティティ定義書を「基本設計項目一覧（原本）＋補正一覧＋ビュー」にした。続いてテーブル設計書を同じ形で作る。オーナーの方針:

- 基本設計で定義した論理型から、SQL の型への対応を用意し、その対応に沿って変換する（論理型を設計項目にする）。
- 詳細設計と基本設計の重複した情報は管理しない。詳細設計にだけ出てくる項目を設計管理の対象にする。
- ビューは、基本設計書を詳細化したもの（要らない項目は落とす）にする。
- DDL に落とすテンプレートも用意し、DDL を作って情報の過不足を確かめる。
- 見直し（同じ日）: テーブル日本語名・カラム日本語名を足す。「名称」が役割の名称に見えないようにする。主キーには順がある。索引と外部キーは独立した表にし、参照先はカラムの一覧にも残す。初期値は無ければ「設定なし」と見せる。必須なのに NOT NULL が空に見える理由が分かるようにする。
  テーブル区分（マスタ・トランザクション）を足し、エンティティにも出す。業務モデルから導けなければ基本設計の項目で、人が書く基本設計項目台帳に置く（補正一覧とは別の、管理しやすい形）。
- 2 回目の見直し（同じ日）: 設計書体系を作っているので、今の todos に当てはまる形があるかではなく、設計書として書けるべきものが書けるか、業務モデルのどの形からも作れるかで判断する。複合の外部キー・複合の索引・消したときの動き（ON DELETE）を書けるようにし、業務モデルの形（入れ子の配列・マップ・object・入れ子のエンティティ 1 件）をすべてテーブルにする。業務モデルから導けない索引は人が書く。消したときの動きの既定は、入れ子で持つ親へは一緒に消す（CASCADE）・参照へは指定しない（オーナーの決定）。

## 決定

- **論理型は基本設計の設計項目**: 基本設計項目一覧（論理型）に、業務モデルの名前付きの型と、項目が直接使う組込みの型を `TYP-モジュール.型の名前` で持つ。値は業務モデルの型のまま（基底の種類・文字数・形・表示形式・選択肢・参照先）で、導出元は定義の索引の `yde-type`（`common#一行の文`）。行の型の項目は `FLD-モジュール.型の名前.キー`。業務モデルの項に `types` を足して、そこから作る。
- **項目は論理型を参照する**: エンティティの項目は `type`（論理型への参照）と、項目そのものの決まり（必須・初期値・自動で入る値・重ならない）だけを持つ。型の性質は項目ごとに写さず、ビューが論理型をたどって見せる。
- **型対応表は人が書く**: 論理型ごとの SQL の型の書き方（`VARCHAR({maxLength})` の穴は論理型の値で埋める）を、詳細設計の文書として人が決める。詳細設計にだけ出てくる型（並び順）もここに書く。
- **詳細設計項目一覧は詳細設計にだけ出るもの**: テーブル（`TBL-テーブル名`）・カラム（`COL-テーブル名.カラム名`）・索引（`IDX-索引名`）・外部キー（`FK-制約名`）の、テーブル名・カラム名・主キーの順・型対応への参照（`SQL-論理型`）・明細テーブルの親の ID と並び順・索引のカラム・外部キーのカラムだけを持つ。名称・必須・論理型・初期値・選択肢は、導出元の基本設計項目をたどって読む。型対応が無い論理型は参照切れで分かる。
  日本語名と NOT NULL も、基本設計に同じものが無いもの（明細テーブルの日本語名・親の ID と並び順のカラム）にだけ書く。ほかは導出元の名称と必須から決まり、ビューは NOT NULL の根拠（基本設計の必須か、詳細設計で足したカラムか）を並べて見せる。
- **業務モデルの形からテーブルへ（深さによらない）**: エンティティ型は主のテーブル。入れ子のエンティティは親の ID と、親の中の位置（配列なら並び順・マップならキー。1 件なら無く、親の ID が一意）を持つ。配列とマップの項目は明細テーブルで、主キーは親のキーに並び順かキーを足したもの。要素は参照なら `参照先_id`、スカラーなら値のカラム、object なら行の項目のカラム。行の中の配列・マップはさらに下の明細テーブルで、親のキーは親の明細テーブルの主キーの組（`todo_id`・`comments_seq`）。エンティティでない object は、名前の有無によらず埋め込み（`期間_開始日` → `period_from`）で、親の項目が必須でなければ、中の必須の項目も NOT NULL にしない。要素が名前の無い配列・マップの配列とマップ（配列の配列）と、要素がエンティティのマップはテーブルにできないので、対応の検査が指摘する（業務モデルで行の型に包む）。基本設計項目一覧も同じ形を写す: 名前の無い入れ物は論理型を持たず基底の種類を持ち、中の項目は入れ子の項目（`FLD-エンティティ型.キー.キー`）。
- **索引と外部キーは詳細設計項目**: 索引は詳細設計の規則で作る（配列の「同じものは 1 度だけ」から親のキーと要素・比べる項目の一意の索引、入れ子のエンティティの親の ID、外部キーのカラム。主キーの先頭のカラムは主キーの索引で足りるので除く）。索引のカラムは並び（昇順・降順）を持ち、索引はテーブルを `table` で指す（人が書く索引と同じ形）。外部キーは、入れ子で持つ親へ 1 つ（親のキーのカラムの組＝複合。消したときは一緒に消す）と、参照のカラムごとに 1 つ（消したときの動きは指定しない）。外部キーはカラムの並びと参照先のテーブルを持ち、どのカラムがどのカラムを指すかはカラムの参照先に書く（カラムの一覧にも参照先が残る）。主キーは制約名（`pk_テーブル名`）を持つ。
- **業務モデルから導けない詳細設計の項目は詳細設計項目台帳**: 画面の絞り込みや並びのための索引は、人が書く詳細設計項目台帳（`design/detail/ledger.yaml`）に、詳細設計項目一覧と同じ形と張る理由で足す。生成した項目の値の置き換えは補正一覧（詳細設計）で、当たり先に索引と外部キーも書ける（消したときの動きを変えるなど）。
- **テーブル設計書はビュー**: 詳細設計項目一覧と詳細設計項目台帳に補正一覧（詳細設計）を重ね、導出元と型対応表と台帳をたどって見せる（概要・カラム一覧・索引・外部キー）。複合の外部キーと索引のカラムは、並びの順に参照先をたどって見せる（値の式の `each` が参照の並びを辿る）。エンティティ定義書のうち、テーブルに要らない項目（項目の説明・CRUD）は落とす。初期値は無ければ「設定なし」と見せる。
- **区分は基本設計項目台帳**: マスタ・トランザクションの区分は業務モデルから導けない（ダッシュボードの「マスタ」の群は画面の並べ方で、データの区分の定義ではない）ので、基本設計の項目として、人が書く基本設計項目台帳（`design/basic/ledger.yaml`）に置く。
  生成物の値を置き換える補正一覧とは別の原本で、区分ごとに 1 行（`CLS-master`・意味の説明・入るエンティティの並び）。どのエンティティもちょうど 1 つの区分に入ることを検査が確かめ、エンティティが増えたときの書き忘れを指摘する。テーブルの区分は、導出元のエンティティ（明細テーブルは配列を持つエンティティ）の区分。
- **DDL はレポート**: テーブル設計書のビューの行を受け取り、ひな形で CREATE TABLE と CREATE INDEX を作る（主キーは主キーの順と制約名・複合の索引と並び）。外部キーはすべてのテーブルを作った後に ALTER TABLE で足す（テーブルの順と参照の輪に左右されない）。初期値は文字の値として書く（データベースが列の型に直す）。出力は派生物で、テストで H2 に流して確かめる。
- **入れ子をたどる生成は規則に値を渡す**: 深さによらない明細テーブルは、変換の規則を子へ当てて作る。規則は外側の名前を読めないので、親のテーブル名と親のキーの並びを `$with` で渡す（変換の本体に足した書き方。[transform.md](../architecture/transform.md)）。

## 既存の決定との関係

ADR-0035 の「設計項目一覧が原本・補正一覧・設計書はビュー」を、詳細設計にも広げる。詳細設計の段の項から作るテーブル設計書（生成物）は、この形に置き換えた。
ADR-0031 の「設計の規則は生成の定義に書く」のうち、型の対応（基底の種類から SQL の型への決め打ちの規則）は、型対応表（人が決める文書）に移す。
補正一覧（基本設計）の補正は、まだ詳細設計の生成に届かない（詳細設計項目一覧は業務モデルの段の項から作る）。
