# ADR-0030: Lifecycle の State の中の流れは、同じ ID の詳細化として別に書く

- 日付: 2026-11-14
- 状態: 承認済み

## 文脈

ADR-0029 で状態を Lifecycle を正にした。`samples/todos` の Lifecycle は 5 つの State を平らに並べ、「中止する」を未着手・対応中・中断の 3 か所から書いていた。
業務の話では「未完了のうちは中止できる」の 1 本で、未着手・対応中・中断は未完了の中の区別にすぎない。

状態を階層にする書き方には 2 通りある。
1 つは、親の State の下に子の流れを入れ子で書く形（UML の複合状態の書き方）。もう 1 つは、粗い流れはそのままにして、親の State の中の流れを同じ ID で別に書く形。
入れ子の形では、中を詳しくするたびに粗い流れの定義そのものが変わる。
YDE のモデル側の段階的な詳細化は、定義の出現と、同じ ID の詳細化の出現を分けて書く（一覧の行と個票）。将来モデル側にも状態の詳細化を入れるとき、同じ考え方にそろえたい。

## 決定

- **別に書く**: `kind: behavior` の `refinements` に、親の State の中の流れを書く（`state`・`states`・`entry`・`transitions`・`exits`）。粗い Lifecycle は書き換えない。
- **親は述語を書かない State**: 親は `states` に `predicate` を書かずに宣言する。値は子（葉）に保存し、親は「子のどれか」が真のとき真。述語は子から導く（子が同じ項目の enum から作った State のとき）。
- **粗い流れはそれだけで完結する**: 粗い Lifecycle の点検（入口・到達・行き止まり・終端）は親のまま行う。
- **入口は原因ごと**: 親へ入る遷移の原因ごとに、詳細化の `entry` に入る子を 1 つ書く。足りない原因と、親へ入らない原因の入口は誤り。
- **出口は狭めるだけ**: 親から出る遷移は、書かなければどの子からも出られる。`exits: [{by, from}]` で、その原因で出られる子を狭める。親から出ない原因の出口は誤り。新しい出口は作れない。
- **展開した流れを使う**: 操作の前提と書き込み・業務の流れの段と工程・業務シナリオ・照合は、親を子へ展開した Lifecycle を使う。展開した流れも同じ規則で点検する（中の流れの行き止まり・到達・enum の網羅）。
- 操作を断るときの「できるのは「…」のとき」は、子が全部そろった親の名前でまとめる（例「できるのは「未完了」のとき」）。
- 詳細化はさらに詳細化できる（子をまた親にする）。子の親は 1 つで、循環は誤り。終端の State の詳細化には遷移を書けない。

## 既存の決定との関係

ADR-0029 の「状態は Lifecycle を正にする」は変えない。正は粗い Lifecycle と詳細化の組で、操作と業務の流れは展開した 1 つの流れから導く。
状態の保存は今までどおり項目の値（葉）で、親の値は保存しない。

## 影響

親から出る遷移を 1 本で書けるので、「中止する」のような、未完了のどこからでもできる操作の定義が短くなる。
中を詳しくしても粗い流れの定義と、その点検の結果は変わらない。
③（Spring Boot）で状態と遷移の表を作るときは、展開した流れを使う。親は「子の値のどれか」の判定として作れる。
詳細は [schema.md「業務上の State / Lifecycle」](../architecture/schema.md) と [manual/schema.md](../manual/schema.md) の「State の中の流れを詳しく書く（詳細化）」に置く。
