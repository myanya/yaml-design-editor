# ADR-0003: YNodeは構文木・可変のまま・copy-on-write規律

- 日付: 2026-08-16
- 状態: 承認済み

## 文脈

`YNode` はYAML構文木で、コメント・表記スタイルを保持する。immutable化は既存実装との乖離が大きすぎる一方、snapshot意味論とは両立させる必要がある。

## 決定

- `YNode` は構文木に徹する。entity・refの意味グラフを埋め込まない。
- `YNode` は可変のまま維持する（immutable化は行わない）。
- そのうえで全層が次のcopy-on-write規律を守る（計画書§2.4）:
  1. YNode木の所有者は常に1つのworking文書。公開済みsnapshotの木は以後変更しない。
  2. 変更は「対象文書のdeep copy → `YamlOperation`適用 → 成功時に参照交換」。
  3. persisted状態は保存済みテキストで保持し、dirty判定はテキスト比較。
  4. semantic-coreは入力の木を変更せず、出力にYNode参照を保持しない（抽出値・`YPath`・座標のみ）。
  5. 将来のUI・AIも木を直接変更せず、操作／トランザクションを発行する。

## なぜコピーするか（可変ならin-placeでも良いのでは、への回答）

undoは逆操作・persistedはテキスト・semantic出力はノード参照なし、という他の決定のもとでは、in-place変更＋逆操作ロールバックでも論理的には成立する。それでも境界の1回のコピーを選ぶのは、コピーが可変性とは無関係に次の3つを買うからである。

1. **失敗時の無傷が構造で保証される。** in-place方式の復旧は「逆操作生成コードが完璧であること」に依存し、そのバグはエラー経路でworking状態を壊す。コピー方式は候補を捨てるだけで、working状態に触れていない。
2. **「検証してから確定」の順序が守れる。** トランザクションは候補の上で検証し、通った場合だけ交換する。in-placeでは「変更→検証→ロールバック」に反転する。
3. **取得済みsnapshotの (version, 内容) が安定する。** agent staging・AI提案のように「あるversionを基準に案を作り後で適用する」利用者が、保持中のsnapshotの内容書き換わりに晒されない。

これは新方式ではなく現行の透かし写しである。現行 `Workspace.apply` はディスクテキストを新しい木としてparseし、コピーにPatcherを当て、オーバーレイ索引で検証してから書き込む（失敗時はstagedを捨てる）。in-placeなのはUIフォーム編集の経路だけで、そのundo（`EditBuffer` の全文テキストsnapshot）はD-03で廃止される。コストも現行の毎編集フルダンプと同等。

「可変のまま」とCoWは補完関係にある: **境界で1回コピーし、候補の内側では可変性を活かしてin-placeに編集する**。immutable化すれば永続データ構造の書き直しが要り、コピーを省けば逆操作の完璧さが要る。その中間が最も安く安全である。

## 保証と機構の区別

本ADRが固定するのは**保証**であって機構ではない。

- 保証（不変）: 操作・トランザクションの失敗時にworking状態が変化しない／公開済みsnapshotの内容が変化しない。
- 機構（変更可）: 「対象文書deep copy→適用→交換」は現在の実装手段。Phase 11の計測でコピーがボトルネックになれば、保証を維持したままin-place＋逆操作ロールバック等へ最適化してよい。

## 帰結

- 可変な木のsnapshot間共有による破壊（1回のin-place編集がworking・persisted・候補を同時に書き換える事故）を規律で防ぐ。
- deep copyは変更対象の文書に限られ、全文書コピーは発生しない。
- レビュー時のチェック項目に本規律を含める。
- 規律4（出力にYNode参照を保持しない）の例外として**読み出しモデル族**を認める（2026-08-19追記）:
  エンティティ合成（EntityComposite）・仮想文書（計画書§17-6）のような「その場で消費し、snapshot状態と
  して保持しない導出結果」は、表示・編集座標のために値ノードの参照を持ってよい。入力の木は読み取り専用の
  まま、導出のたびに再構築し、鮮度は sourceVersion で判断する。
