# ADR-0034: 設計書は段の項から作り、横ぐしの方針と補正は段の規則・補正として項に重ねる

- 日付: 2026-11-15
- 状態: 承認済み

## 文脈

`samples/todos-sysdev` の設計書（基本設計書 10 本・詳細設計書 12 本）は、どれも業務モデルの項から直接作っていた（ADR-0031）。
生成の系譜（`generate --lineage`）で見ると、基本設計書を入力にする詳細設計書は 0 本だった。基本設計と詳細設計は、同じ ID と、生成の定義に書き写した同じ規則でそろえているだけである。確かめ方は 7 本、Mapper の名前は 7 本、URL は 5 本の定義に、同じ規則が書かれていた。

オーナーの方針:

- 詳細設計書が業務モデルを読んでもよい。ただし、基本設計で決めたことを踏まえて、詳細設計を補正できるようにする。
- 例として、業務モデルに無い更新者を基本設計で足し、詳細設計が引き継ぐ。テナント分離の変換規則を外付けすると、基本設計でテナント ID が付き、詳細設計で各処理がテナント ID を確かめる。
- 当たり前の横ぐしの設計を段階的に差し込める土台にする。
- Spring Boot は詳細設計を軸に、基本設計と業務モデルを補助に読む。

ADR-0031 は「手書きは別の文書に書いて同じ対象を指し、レビューはビューで両方を合わせて読む」としていた。この形では、手書きの補正は後ろの段の設計書と Spring Boot に届かない。

## 決定

- **段**: `.yde/workspace.yaml` の `stages:` に、段の並び（`id`・`name`・`description`）を書く。段の項は、前の段の項に、その段の規則と補正を当てたもので、最初の段の入力は業務モデルの項である（`Stages`）。形は業務モデルの項と同じで、生成の定義は段を変えても同じ書き方で読める。
- **生成は段を選ぶ**: 生成の定義に `stage` を書くと、その段の項を `model` として読む。書かなければ、今までどおり業務モデルの項を読む。段の項は業務モデルの中身をすべて持つので、前の段の事実も読める。
- **規則と補正**: 新しいゾーン `.yde/stages/` に、項の変更の文書を置く（メタスキーマ `builtin-stage`）。`kind: rule` は全体の方針で、条件で選んだ要素に当てる。`kind: patch` は個別の例外で、ID で選んだ要素に当てる。段の中では、規則を先に、補正を後に当てる（どちらも置き場の名前の順）。補正は、当たる要素が 1 つも無いと誤りになる。業務モデルの ID が変わったことに気づくためである。
- **専用の短い書き方**: 変更は「どの並びの、どの要素に（`each`・`where`）」と「置き換える（`set`）・中へ足す（`add`）・後ろへ足す（`after`）」で書き、入れ子の `changes` と要素の名前（`bind`）を持てる。値は変換のひな型で、いまの場所は選んだ要素、当てる前の項は `$of: model` で読む（`TermChanges`。semantic-core）。項の全体を変換で書き直す形にはしない。人が横ぐしの方針を読み書きしやすいことを優先する。
- **出どころ**: 足した要素（object）には `origin`（段・文書の ID と名前・種類）を付け、置き換えた場所は要素の `origins` に記録する。業務モデルから来たものには付かない。設計書はこれを写して、業務モデルに無い項目がなぜあるかを示す。段の項の頭には `stages`（当てた段と、段ごとの規則・補正の一覧）を足す。
- **補正の置き場は 3 つ**: 業務の事実は業務モデル、全体の方針は段の規則、個別の例外は段の補正に書く。生成物は直さない。

## 既存の決定との関係

ADR-0031 の「業務モデルの項に設計の規則を入れない」は残す。業務モデルの項は業務の事実だけを持ち、設計の判断は段の項に入る。
ADR-0031 の「手書きは別の文書に書いて同じ対象を指す」は、この ADR で上書きする。補正は設計書ではなく段の項に重ね、後ろの段の設計書と生成物のすべてに届くようにする。
生成の定義に書き写している設計の規則（名前・URL・確かめ方）は、詳細設計の段の事実へ移していく。
