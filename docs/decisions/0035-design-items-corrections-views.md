# ADR-0035: 設計の原本は設計項目一覧に持ち、個別の直しは補正一覧に書いて、設計書はビューで見る

- 日付: 2026-11-16
- 状態: 承認済み（samples/todos-sysdev のエンティティ定義書から）

## 文脈

ADR-0034 で、設計書を段の項から作り、横ぐしの方針と個別の例外を、段の規則と補正（`.yde/stages` の項の変更）として重ねる形にした。
オーナーのレビューで、次の違和感が出た。

- 補正を `.yde` の中の処理として定義すると、設計の生成に割り込んでいる感覚で、設計書を補正している感覚にならない。スキーマを決め、それに沿って文書を書きたい。
- 基本設計の項は CLI でしか見えず、何を見れば基本設計が分かるのかが無い。
- 設計書が 1 つの設計（エンティティ）になっておらず、レンズで依存が見えない。つながりが値（文字）で、リンクで飛べない。業務モデルと設計の ID を一致させたことが原因と考えた。
- 業務モデルの機械処理できる仕様（型・auto・選択肢・採番）を、日本語の文に言い換えてはいけない。目的はソースコードの生成である。

## 決定

- **設計項目一覧が原本**: 基本設計の中身を、設計項目の一覧（`design/basic/entities.yaml` など。生成物）として台帳に置く。設計項目は自分の ID（`ENT-todo`・`FLD-todo.title`・`OPS-todo.complete-todo`・`CRUD-todo.complete-todo.status`）を持ち、導出元（業務のエンティティ型・項目・操作）を参照で指す。業務の項目は定義の索引に `yde-field`（`型.キー`）として載せ、リンクで飛べるようにする。
- **値は業務モデルの書き方のまま**: 型の名前（`common#年月日`）・`auto`（`created`）・選択肢（value と label）・採番（接頭辞と桁）は、YDE の標準の書き方で持つ。人が読む言葉は説明（description）に書き、日本語の見せ方はビューやスキーマの側に置く。型の性質（表示形式など）は項目ごとに写さない。
- **補正一覧は人が書く文書**: 個別の直しは、補正のスキーマ（当たり先の参照・置き換える値・理由）に沿った台帳の文書に書く。設計項目一覧そのものは変えない。
- **設計書はビュー**: エンティティ定義書は、設計項目一覧に補正一覧を重ねて見せるビュー（ダッシュボード）にする。表のビューに「補正を重ねる」指定（`corrections`）を足し、重ねた値は読み取り専用で、補正と元の値へ移れる。
- 全体の方針（横ぐし）は、引き続き段のルール（`.yde/stages`）として、設計項目一覧を作る側に置く。

## 既存の決定との関係

ADR-0034 の「個別の例外は段の補正（`.yde/stages` の `kind: patch`）に書く」は、設計項目一覧を持つ設計書では、この ADR の補正一覧で置き換える（`kind: patch` の仕組みは残す）。段と段のルールはそのまま使う。
ADR-0031 の「設計書の ID は業務の ID そのもの（詳細化）」は、設計項目一覧を持つ設計書では、自分の ID と導出元の参照に置き換える。ほかの設計書は、一つずつ議論して同じ形へ移す。
詳細設計書が設計項目一覧と補正一覧を読む形（補正が詳細設計へ届く形）は、まだ作っていない。
