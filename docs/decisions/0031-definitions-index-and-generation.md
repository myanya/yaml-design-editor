# ADR-0031: 業務モデルの定義を索引に載せ、設計書は業務モデルから生成する

- 日付: 2026-11-15
- 状態: 承認済み

## 文脈

`samples/todos` の業務モデル（スキーマの操作・Lifecycle・エンティティ型）を要件定義として、Spring Boot のアプリの設計書体系（`samples/todos-sysdev`）を作る。
オーナーの方針は次のとおり。

- 業務モデルは設計の側に置き、正とする（設計書から業務の定義を指し、存在を確かめる）。
- 設計書の ID は、できるだけ業務の ID を使う。新しい ID が要るときは、業務モデルがシステム化に向いていないサインと考える。
- 設計書は YAML の計算でできるだけ生成する。生成したものは毎回作り直し、手書きは別の文書に書いて同じ対象を指す（生成したクラスを手書きが継承する、コード生成のやり方に近い）。レビューはビューで両方を合わせて読む。

これまで業務の定義（操作・State・Lifecycle）はスキーマのゾーンにあり、索引の外だった。State の多くは列挙型から作られ、ファイルにその ID の文字が無い。
また、操作の効果は do の手・Lifecycle（状態の値と履歴の行）・保存時に自動で入る値の 3 か所に分かれ、合わせた姿は操作の計画だけが知っていた。変換の評価器は入力の項を 1 つ受け取るだけで、作った項を文書として書く入口が無かった。

## 決定

- **定義の索引**: 業務の定義を、定義を書いた場所（スキーマの文書とその中のパス）の定義の出現として索引に載せる。種類はエンティティ型 `yde-action`（操作と型の操作）・`yde-state`・`yde-lifecycle`・`yde-entity`（エンティティ型）・`yde-require`（名前を付けた前提）。ID は業務の ID そのもの（前提は `操作ID.前提ID`）。組み立てた定義から作る（列挙型から作った State は `source` の宣言の場所）。利用者のスキーマは `yde-*` を定義として宣言できず、詳細化（`defines: false`）として書く。業務モデルから消えた定義を設計書が書き続けていれば、組込みの「浮いた詳細化」の検査が指摘する。
- **前提の名前**: 操作の前提に `id` を書ける（操作の中で 1 つ）。断りの種類の名前で、判定には使わない。
- **業務モデルの項**: スキーマに分けて書いた業務モデルを、生成が読める 1 つの項（`entities`・`actions`・`states`・`lifecycles`）に展開する（`BusinessModel`）。操作の効果は 3 か所を 1 列にまとめ、State は ID・名前・値の組、断りの文は操作の計画と同じ文にする。設計の規則（表や URL の決め方）はここに入れない。
- **生成**: 生成の定義を新しいゾーン `.yde/transforms/` に置く（`each`・`output`・`build`・`rules`。メタスキーマ `builtin-transform`）。業務モデルの項を入力に変換を当て、作った YAML を文書として書く。作った文書は生成物で、先頭の見出しのコメントで見分け、手で直さない。作り直すたびに、出力の場所にある同じ定義の生成物で作らなかったものは消す。書き込みはセッションの 1 トランザクションで、検証も保存も今までの経路。入口は CLI `generate`（`--apply`・`--check`・`--model`）。
- **変換の書き方の追加**: 名前の書き方をそろえる `$case`（camel・pascal・snake・kebab・constant。英語の文法は入れない）、呼び出し側が渡す名前の付いた場所（生成では `model` と `element`）、条件の比べる値に別の場所の値（`{$copy: パス, $of: 名前}`）。

## 既存の決定との関係

「変換の出力はワークスペースへ保存しない。原本へ書くなら変更セットと承認を通す」（architecture/transform.md）は、変換の評価器について変えない。生成は、評価器の結果を、生成物という派生した文書として、セッションの取引で書く別の入口である。生成物は原本ではなく、業務モデルと生成の定義が原本である。
レポート（YAML から文字へ。YAML には書かない）とも分けたままにする。
ADR-0029・ADR-0030 は変えない。業務モデルの項の Lifecycle は、詳細化を展開した流れである。
