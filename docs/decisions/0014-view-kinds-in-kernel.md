# ADR-0014: ビューの種類の差し込み口はカーネルに置き、拡張へ出すのは chart と flow にする

- 日付: 2026-10-28
- 状態: 承認済み
- 上書き対象: ADR-0013 の一部（`ViewKind` の置き場・拡張へ出すビューの種類・描画の登録簿の置き場・ビューの拡張が公開するもの）。それ以外の ADR-0013 の決定はそのまま

## 文脈

ADR-0013 は「app-core に `ViewKind` を置き、chart・lens・flow・matrix を拡張モジュールへ出す」と決めた。
着手のときに調べると、ビューの定義を読む処理（`ViewDefinitions`）はカーネルの workspace-core にあり、定義の型と行や図を作る処理（`VirtualViews`・`ChartViews`・`FlowViews`・`LensViews`）は semantic-core にあった。メタスキーマ（`builtin-schemas/view.yaml`）も workspace-core の資源である。
カーネルの中でも、変換の `$view` とレポートが grid（と matrix）の解決を使い、ファイルの改名の影響（`RefactoringImpact`）が flow の定義を直接読む。

種類ごとの性質も一様ではなかった。

- matrix は「列を広げた grid」として解決している（`lower`・`resolvePivot`）。チャートの元の表になり、変換とレポートも grid として読む。
- lens は行も図も作らない。グラフレンズの画面（中核の画面）で矢印の向きを決める設定で、読むのはその画面だけである。
- chart と flow は、中核の種類（文書ビューの区画・ダッシュボードの区画）に ID で埋め込まれるだけで、カーネルの計算からは使われない（flow は改名の影響の 1 か所を除く）。

## 決定

### 差し込み口はカーネルに置く

JDBC の `Driver` と同じ形にする。差し込み口は本体（カーネル）にあり、実装は別のモジュールにあり、使うものを入口が登録する。

- **`ViewKind`**（workspace-core）: 種類の ID と名前・定義の形の断片（資源の YAML）・`parse(raw)` で定義へ・カタログ全体での点検（`lint`）・文書ビューの区画に埋め込むときのキー・ダッシュボードの区画に置けるか。
- **定義と結果の共通部**（semantic-core）: `ExtensionViewDef`（拡張の種類の定義。中核の種類と同じ `VirtualViewDefinition` の仲間で、自分の解決と一覧の文を持つ）・`ExtensionViewResult`（解決した結果。件数・CLI の値・エージェントへの文）・`ViewContext`（解決に使う中核の表の窓口）。
- **登録簿**は app-core の `ExtensionRegistry` が持ち、入口が組み立てて渡す（ADR-0013 のまま）。カーネルは大域の登録簿を持たず、使う種類を引数（`kinds`）で受け取る。
- app-core の中で登録簿を持つ `app.ext` はカーネルだけを使うので、app-core の層の一番下に置く（ADR-0013 では tools と skill の間）。ビューを読む `app.core` が、登録した種類を引数に渡すため。
- 拡張は app-core とカーネルだけを使う（ADR-0013 のまま）。カーネルに差し込み口があっても、依存の向きは変わらない。

### 拡張へ出すのは chart と flow

grid・document・matrix・dashboard・lens は中核に残す。
matrix は grid の解決そのものなので、出すと grid が割れる。lens は中核の画面の設定なので、出しても画面が型を直接使い、外せない拡張になる。

### メタスキーマは断片を合成する

拡張の種類は、定義の形の断片（`src/main/resources/<名前>/schema.yaml`）を持つ。断片は次の 3 つだけを足す。

- `kind` の選択肢 1 つ
- ルートの項目（その種類だけが使うキー）
- 文書ビューの区画に埋め込むときのキー（`sections[].<キー>`）

合成は workspace-core（`ViewSchemaFragments`）が行い、項目の名前が中核や他の拡張とぶつかれば誤りにする。複数の種類が使う項目（`order` など）は中核に残す。

### 描画の登録簿は当面 desktop.ui に置く

ADR-0013 は描画の登録簿を `desktop.views` に置くとしたが、中核の描画（表・ダッシュボード・文書ビュー）が `desktop.ui` にあり、層の向き（規則 2）から登録簿もそこに置く。`desktop.views` への切り出しは、描画を view-*-ui へ出すときに合わせて考える。

### ビューの拡張が公開するもの

`ViewKind` の実装に加えて、描画が読む定義の型と解決の結果の型を公開する。描画は拡張の外（desktop か view-*-ui）にあるため。形式の拡張（format-*）は今までどおり実装 1 つだけを公開する。

### 書き方は変えない

`kind: chart` の文書も、文書ビューの `chart: {view}` の区画も、今のまま読める。入口が登録していない種類を書いた定義は、使える種類を並べた誤りになる（形式の差し込み口と同じ扱い）。

## 影響

- ADR-0013「移行の順」の 5 は、chart（1 段目。差し込み口・登録簿・断片の合成を含む）と flow（2 段目。改名の影響を差し込み口に足す）の 2 段で行う。
- 拡張を使わない入口やテストでは、chart と flow の定義は「使えない種類」になる。カーネルのテストは中核の種類だけで書き、chart と flow のテストはそれぞれの拡張モジュールに置く。

## 却下した案

- ADR-0013 どおり app-core に置く: ビューを読む処理をカーネルから上げることになるが、grid はカーネルの変換とレポートが使うので上げられず、読む処理が 2 か所に割れる。
- matrix を出す: grid の解決に matrix 用の差し込み口が要り、grid そのものが割れる。
- lens を出す: グラフレンズの画面が拡張の型を直接使うので、外せない拡張になる。画面ごと出すのは今の段階ではない。
- カーネルに大域の登録簿を置く: 引数を通す手間は減るが、カーネルの関数の結果が呼んだ時点の登録に左右され、テストでも追いにくい。
