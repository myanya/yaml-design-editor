# 意図的差分一覧

3層コア移行で**最初から意図して変える**既存挙動の台帳（計画書§2.3）。
新旧比較テストでこの表に該当する差分が出た場合、移植ミスとして扱わず、新旧それぞれの期待値を明記する。
ここに載っていない差分はすべて移植ミスの疑いとして調査する。

| ID | 現行挙動 | 新APIの挙動 | 関連ADR |
|---|---|---|---|
| D-01 | `Workspace.apply` が変更セットを検証してそのままファイルへ書く | `apply` はworking snapshotだけを更新し、`save` が別途ファイルへ書く | ADR-0005 |
| D-02 | UIの文書キャッシュ・ディスク索引・agent stagingが別々のoverlayを持つ | すべて `WorkspaceSnapshot` を入力とする共通semantic engineを使う | ADR-0004 |
| D-03 | `EditBuffer` が正規化text snapshotを履歴に持つ | 型付き `YamlOperation` とinverseを基本履歴にする | ADR-0005 / 0006 |
| D-04 | `AppState` や複数のcore機能が直接ファイルを書く | coreの書込を `DocumentStore` と `WorkspaceSession.save` へ集約する | ADR-0005 |
| D-05 | `Schema.kt` と `Validator.kt` が構造規則と意味規則を同時に扱う | structuralとsemanticのcompile/validationを分ける | ADR-0002 / 0004 |
| D-06 | `Path` がschema・index・coreへ広く渡る | `Path` はworkspace-coreのI/O境界に閉じ、下位層には `DocumentId` を渡す | ADR-0002 |
| D-07 | 単文書ごとのUndoスタック（EditBuffer単位） | Undoスタックはworkspace履歴のみ。単文書編集も文書1件の `ChangeRecord` | ADR-0006 |
| D-08 | ソース編集はパース不能テキスト状態（`rawText` / `parseError`）を保持しUndoできる | coreの履歴は型付き操作のみ。生テキスト編集のUndoは将来UI層の責務（core外） | ADR-0006 |
| D-09 | 文書移動（DocMove）は「物理移動成功→参照書き換え失敗」の継ぎ目がありうる（メッセージ案内） | 移動と参照書き換えを1トランザクションで適用し、失敗時は何も起きない。1回のUndoで移動ごと戻る | ADR-0005 |
| D-10 | リファクタリング（rename等）がビュー定義・アクティビティ等の言及を自動追随・警告スキャンする | カーネル経路（SemanticRefactor）は追随せず警告で案内する（ビューはUI層の産物でコアから見えない）。**B-1（RB-01）で解決**: GUI 経路はアプリ層（`core/RefactorImpact`）がカーネル計画にビュー追随・言及警告を補強＝旧挙動を回復。CLI（新CLI `workspace refactor`）は引き続き警告案内のみ | ADR-0002 |
| D-11 | 一括更新（bulkUpdate）はファイルごとに逐次書込（途中失敗で部分適用が残りうる・Undo不可）。保存は `Files.writeString` の直接書込 | 一括更新は**1トランザクション**として適用してから保存（1件でも適用できなければ何も書かない）。保存・一括更新の書込は `WorkspaceSession.save`＝`DocumentStore` 経由（一時ファイル→atomic move）。履歴一元化（A-3）後は一括更新が Undo 1回で戻る（**B-1 で発効**: 適用後に reload しない追随へ変更） | ADR-0005 / 0006 |
| D-12 | リファクタリング適用（エンティティ操作・スキーマ・リファクタリング）は `Workspace.apply`（baseハッシュ競合検出）でディスクへ書き、`reload()` で全再読込（履歴は文書単位のまま・操作自体は Undo 不可）。計画の生成はディスク索引（保存済み状態）が基準 | 適用は `session.applyRefactoring`＝**1トランザクション＋保存**（reload しない）——**リファクタリング全体が Undo 1回で戻る**。計画はセッションの working 状態＝「見たまま」基準（RA-02 の overlayIndex と同じ原則）で、古い計画は sourceVersion 不一致で適用拒否（baseハッシュに相当する競合検出）。適用→保存が未保存編集まで書かないよう、対象に dirty 文書があれば従来どおり拒否。複数ファイルの書込は `DocumentStore` 経由のファイル単位 atomic（旧ステージング一括と異なり、I/O 障害時にファイル単位の部分書込がありうる——working は常に一貫） | ADR-0005 / 0006 |

| D-13 | 文書内ID重複の指摘文言が UI 経路「ID「x」がこの**ファイル**内で重複しています」／カーネル経路「この**文書**内」の2種 | B-3（RB-06）の判定単一所有化でカーネル文言「この文書内で重複しています」へ統一（テスト・機械読取の参照なし。UI 表示のみの変化） | ADR-0002 |

| D-14 | 新経路 cli（workspace validate / catalog / entity / refactor / shell）は組込みスキーマ未注入＝`_schemas`・定義ゾーンの構造検証が効かない | C-4（RC-07）で `BuiltinSchemaResources.kernelSchemas` を注入——メタスキーマ・定義ゾーン検証がアプリと同じ面になる（定義不備が新たに構造エラーとして報告されうる＝検出強化の方向のみ） | ADR-0002 |

| D-15 | パターン制約（V-09）の `expect: exists`／`count` 下限は、解探索の途中で未解決参照により候補が失われていても「解なし＝違反」として発火する（沈黙が違反に化ける） | CALC-17（Core Calculus Phase 1 の決定 2026-09-05）: エッジ展開で参照の端をノードへ解決できない場合（OUT: 対象IDが索引に存在しない／IN: 参照の書き手をエンティティへ解決できない）を「候補の喪失（unknown-dropped）」として評価結果へ記録し、**解の不足を理由とする違反（exists の解なし・count の下限未達）は判定保留＝沈黙へ降格**する。解の実在を根拠とする違反（absent で解あり・count の上限超過）と、実在するノードの絞り込み（型・idPattern・where 不一致＝選択）は降格しない。未解決参照そのものは参照検証（§2）が従来どおり指摘する | ADR-0009 |

| D-16 | カバレッジの参照ベース `coverage.requiredBy`（被参照数の数え上げ）が宣言でき、参照が不足すると「参照が不足しています」を指摘する | Core Calculus Phase 2 の語彙刈り込み（MP-01・2026-09-19 オーナー承認・本運用前のため互換より正準優先）: **requiredBy を削除**。数え上げの正準は「1ホップ・無条件＝関係レジストリの cardinality／条件付き・多段＝constraints の count / exists」、coverage は出現ベース（detailIn＝詳細文書の存在）専用になる。`requiredBy` を書いたスキーマは移行案内つきの定義エラーになる（黙って無視しない）。**追補（R29-07・同日）**: スキーマID改名（`renameSchemaId`）の追随対象から、廃止語彙の子キー `fromSchemaIds` を外す（宣言できなくなったキーを書き換え対象に数えない。`schemaIds`＝detailIn 配下ほかの追随は不変） | ADR-0009 |
| D-17 | 期待値導出（consistency の expected・導出値を適用）の出現選択（lookup / source / values の selector 一致）は「索引挿入順の先頭」の先勝ち | Core Calculus Phase 2（MP-02・2026-09-19 オーナー承認）: 出現候補を**定義出現優先→索引順**に並べてから先勝ち（CALC-11 の代表出現と同じ規則＝σ 選択方針 CALC-19）。selector が1出現に絞れている既存運用では挙動不変。複数出現に一致する場合のみ、定義出現の値が採用されるようになる。**追補（R29-05・同日）**: テンプレート健全性検査（UX-12。導出元文書でプレースホルダの解決可否を静的に検査）の `values` の出現選択も同じ選択方針へ揃える（共有評価部 `SemanticExpression.select`。検査が実際の導出と別の出現を見る食い違いの解消） | ADR-0009 |
| D-18 | 文書の新規作成（新規 YAML・ビューの詳細文書／新規行ファイル・カバレッジ指摘からの詳細文書・スキーマ推論）はファイルへ直接書き、ワークスペース全体を読み直す（`reload`）。作成は Undo できず、読み直しでセッションが開き直されるため**それまでの Undo 履歴も失われる**。エージェント変更の適用で作成された文書を Undo しても、削除予約が保存されずファイルが残る | Core Calculus Phase 4 の RP-03（2026-09-19 オーナー承認「UI 挙動が変わってよい・当該領域も Undo 範囲へ」）: 作成はセッションの1トランザクション（`CreateDocument`）として適用→保存し、全体の読み直しをしない＝**Ctrl+Z で作成を取り消せる**（ファイルも消える）・それまでの履歴を保つ。**文書の作成・削除を含む履歴の Undo / Redo は、ファイルの有無までその場で確定する**（内容の編集の Undo が「未保存●」に留まるのと異なり、作成の取り消しを「保存」で確定させる手段が無いため）。セッションが文書として扱わないパス（隠しパス等）とセッション不在時は従来の直接書込のまま | ADR-0005 / 0006 / 0009 |
| D-19 | 整合検証（スキーマの `consistency`）は専用の検査プログラム（`SemanticConsistency`）が判定する。①期待値を読む文書は、指定（`source` / `values` / `lookup` の selector）に合うもののうち1つだけ（定義出現を優先。D-17）②`lookup.via` は、起点要素のそのパスに書かれた**値**を ID として読む（フィールドが ref 型でなくてもよい）③文面の末尾には `description` だけを付ける | Core Calculus Phase 6 第1段（2026-09-19 オーナー決定 DL-05「共通の規則に合わせる」）: 整合検証は**組込み定義体（YAML）**になり、プリミティブ（クエリ＋値の比較 `check`）へ展開されて、他の検査と同じ規則で評価される。①指定に合う文書が複数あれば**すべて調べ、1つでも食い違えば指摘する**（値の比較の共通規則。1つの文書に絞れている使い方では結果は同じ。ビューの計算列の出現選択は D-17 のまま）②`lookup` は**参照の線として辿る**——`via` は参照フィールド（`type: ref`）のキー名で、ref 型でないフィールドの値は辿らない（表記から意味を作らない。ADR-0008）。`lookup` の selector は「その参照が書かれた文書」の指定になる③文面の末尾は他の検査と同じく `description`（無ければ `id`）。指摘の場所（値が書かれた場所）・文面・「導出規則へ／入力値へ／導出値を適用」の対応は変わらない | ADR-0008 / 0009 |
| D-20 | 関係レジストリの多重度（`cardinality`）と対象型（`source` / `target`）は、カーネルの専用の検査プログラム（`SemanticGraphIntegrity`）が判定する。①指摘は意味解析の結果（snapshot）に含まれ、cli モジュールの `workspace validate`・対話 shell と、セッションの `requireValid` にも出る ②多重度の指摘は、エンティティを定義した場所（なければ先頭の出現）にだけ出る——同じ ID が書かれた他の文書には何も出ない ③参照元の型の不一致は、参照先が未解決の参照にも指摘する | Core Calculus Phase 6 第2段（2026-09-19 オーナー決定 DL-05「共通の規則に合わせる」）: 多重度と対象型は**組込み定義体（YAML）** `builtin-definitions/relations.yaml` になり、プリミティブ（クエリ＋参照の本数＋値の比較／ノードの条件の否定＋参照の場所への指摘）へ展開されて、スキーマの `constraints` と同じ規則・同じ経路で評価される。①評価はアプリ・通常の CLI `validate`・変更セット適用・エージェントの提出ゲート（constraints・整合検証と同じ経路）で行い、**カーネルの snapshot には出ない**（cli モジュールの `workspace validate` は constraints を元々評価しない＝既知の非同値。検査の実行をカーネルへ移す ROADMAP P27・D-4 で揃える）②多重度の指摘は他の検査と同じ配送規則に従う——同じ ID が書かれた他の文書にも案内が出る（警告級は INFO・エラー級は同格の ERROR。R28-05a）③参照先が未解決の参照と、自分自身への参照には、型の不一致を指摘しない（クエリは両端が解決できた参照だけを辿り、同じノードを二度通らない。未解決の参照そのものは参照解決の検証が ERROR で指摘する）。**文面・指摘の場所・重大度・被参照不足の「参照の追加先」は従来どおり**。出ていく参照の本数は、従来どおり相手が見つからない参照も数える（CALC-20）。非循環（`acyclic`）と宣言のない関係名（`enforcement.undeclaredRelation`）は従来どおりカーネルが判定する（非循環は第4段・宣言のない関係名は宣言の検査として残す） | ADR-0009 |

## 記入規則

- 新しい意図的差分が生じたら、実装より先にこの表へ行を足す（1行=1差分。関連ADRがなければ先にADRを書く）。
- 差分を廃止（旧挙動へ戻す）した場合は行を消さず、取り消し線と理由を残す。
