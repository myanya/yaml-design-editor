# ADR-0029: エンティティの状態は Lifecycle を正にし、操作と業務の流れを Lifecycle から導く

- 日付: 2026-11-14
- 状態: 承認済み

## 文脈

業務の State / Lifecycle（S-28〜S-34）は、状態の値の項目と操作をそのまま使い、その上に「どの状態からどこへ、何によって移るか」を宣言する形で入った。
宣言は点検（静的な点検・操作の確認の照合・業務シナリオ）に使う診断で、操作の適用は止めなかった。
そのため、1 つの移り方（例「着手で 未着手→対応中」）を、操作の前提（`require` の状態の条件）・操作の手（状態の値の `set` と履歴の行）・Lifecycle の遷移・ダッシュボードの業務の流れ（区画の `filter` と工程）に、別々に書いていた。
`samples/todos` では、状態の値が 11 ファイル・78 か所に現れた。業務の流れの線の書き忘れは、検証にもシナリオにも出なかった。

## 決定

- エンティティの状態は Lifecycle を正にする。状態の一覧は State（enum から作る）、移り方・入口・終わりは Lifecycle に書き、ほかの定義は Lifecycle から導く。
- **操作**: アクションに `lifecycle: ID`（か `{id, history}`）を書くと、計画器がその Lifecycle の遷移（`by: {action: この操作}`）から次の 3 つを作る。書いた操作は、状態の条件と状態の値の書き込みを自分で書かない（`do` を省ける）。
  - 前提: 受け手のいまの State（ちょうど 1 つ）から、この操作の遷移があること。無ければ「できるのは「…」のとき」を添えて止める。メニューの可否も同じ判定。
  - 書き込み: 行き先の State の値を、その State の項目（enum の `path`）を持つ出現へ書く。入口の操作は、同じ計画で作った対象の文書に初めの State を書く。
  - 記録: Lifecycle に `history: {path}` があれば、行（`date`・`action`・`from`・`to`）を足す。操作の `lifecycle.history` のひな型で値を足し、上書きできる（理由・日付など）。
- **業務の流れ**: ダッシュボードの `flow: {lifecycle, view, group}` は、段（State ごとの区画。filter は State の判定）・工程（操作による遷移）・入口・履歴を Lifecycle から作る。
- 読み込みの点検: Lifecycle を書いた操作に、その Lifecycle の入口か遷移があること・受け手の型が合うこと・同じ State から行き先が 1 つに決まること・行き先が enum から作った State であること。
- 書くかどうかは操作ごと・ダッシュボードごとに選ぶ。書かない操作と手書きの流れは、今までどおり（Lifecycle は点検だけ）。

## 既存の決定との関係

S-28〜S-34 の「Lifecycle は宣言であって、データの別の保存先・変更経路ではない」は維持する。状態は今までどおり項目の値として保存し、書き込みは操作の変更セット（ADR-0005 の適用の経路）を通る。
「宣言は診断で、操作の適用を止めない」は、`lifecycle` を書いた操作について上書きする（前提として止める）。
行き先が分かれる遷移（同じ状態・同じ操作で、結果により行き先が違う）は導けないので、その操作には `lifecycle` を書かず、手で状態を書く（照合は今までどおり）。

## 影響

`lifecycle` を書いた操作は、状態の前提・書き込み・記録を持たない短い定義になる。手書きの流れと Lifecycle の食い違いは、流れを Lifecycle から作れば起きない（手書きの流れは引き続き点検しない）。
外から起きる出来事（Event）による遷移は、操作の前提にも業務の流れの工程にも入れない（申告と照合だけ）。
③で状態と遷移の表から実装（例 Java の enum と遷移の判定）を作るときも、正は Lifecycle の 1 か所になる。
