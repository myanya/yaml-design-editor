# ADR-0033: ビューを定義の索引に載せ、業務モデルの項にダッシュボードからたどれる範囲を持たせる

- 日付: 2026-11-15
- 状態: 承認済み

## 文脈

`samples/todos-sysdev` の画面系の設計書（画面遷移定義書・画面定義書・画面遷移設計・セッション情報設計）を、業務モデルから計算で作る。
オーナーの方針は次のとおり。

- 画面は、ダッシュボードを起点に決める。業務モデルの操作は、基本的にダッシュボードを通じて行うため、ダッシュボードからたどれるビューと操作がアプリの画面の対象になる。
- アプリの範囲は、YDE の閲覧専用モードでできること（見る・操作する）。直接の編集は作らない。
- ダッシュボードからたどれないもの（カテゴリやタグを並べて見る道など）は、業務モデルの不足として業務モデルの側で直す。
- 今後、ダッシュボードの定義の自由度を上げ、いろいろな画面の構成に応えていく。

これまで、業務モデルの項（ADR-0031）はスキーマの定義だけを持ち、ビューとダッシュボードは持たなかった。ビューの文書は索引に載るが、種類（エンティティ型）を持たず、画面の設計書から業務の定義として指せなかった。

## 決定

- **ビューを定義の索引に載せる**: 組込みのメタスキーマ builtin-view に `entity: {type: yde-view, defines: true}` を宣言し、ビュー（ダッシュボード・表・集計・チャートなど）の文書のルートを、定義の出現 `yde-view` にする。画面の設計書は同じ ID の詳細化として書く。ダッシュボードかどうかは、定義の出現の文書の `kind` で絞る。利用者のスキーマは `yde-view` を定義として宣言できない（`yde-*` と同じ）。
- **業務モデルの項にビューとダッシュボード**: `views`（ID・名前・種類・行の型・列の見出しと読む項目・集計の数える要素の型）と `dashboards`（絞り込みの入力・上部の操作・区画）を足す（`BusinessModelViews`）。スコープを書いたときは、そのスコープのビューだけを読む。
- **ダッシュボードからたどれる範囲**: 各ダッシュボードと、その和に `reach` を足す。区画のビューの行と数える要素の型から、参照の項目の参照先をたどれるだけたどったエンティティ型（`entities`）、その中に入れ子で書かれた型（`nested`）、上部の操作と、たどれる型を受け手にする操作（`operations`）。YDE の閲覧専用モードでダッシュボードからたどれるものと同じ範囲で、業務の流れ（`flow`）の図は、いまは数えない。
- 画面の決め方（一覧画面・詳細画面・入力画面と確認画面・ボタンを出す状態・戻り先・URL）は、業務モデルの項には入れず、生成の定義（`samples/todos-sysdev/.yde/transforms/design/`）に書く。

## 既存の決定との関係

ADR-0031 の定義の索引に `yde-view` を足す。定義の索引の他の種類は、スキーマに書いた定義から `DefinitionIndex` が作るが、`yde-view` はビューの文書がもともと索引に載るため、メタスキーマの宣言で載せる（作り方が違うだけで、種類の役割は同じ）。
ADR-0032（スコープ）の範囲で、業務モデルのスコープのビューだけを読む。定義の索引と検査をスコープで絞る件（BACKLOG）は変えない。
