# YAML Design Editor

Kotlin + Compose for Desktop + Material 3 製の**スキーマ駆動・汎用 YAML エディタ**。
YAML で設計項目（要求・設計・課題など）を管理するためのツールです。

- 外部のスキーマ定義（`_schemas/*.yaml`）に沿って、YAML ファイルごとに適切なフォームビューを自動生成
- スキーマがないファイルも**汎用ビュー**（再帰的なツリーエディタ）で編集可能
- ワークスペース内の **ID を横断的に索引化**し、参照（ref）のリンクジャンプ・補完・未解決検出・バックリンク表示に対応
- フォーム／ソース／差分の3モード編集、スキーマ検証、ID検索
- 外部変更の自動検出、ファイル／ディレクトリ操作、リサイズ可能な左右ペイン
- `_schemas` 専用のスキーマ設計画面と、`definitions` / `$ref` による再帰定義
- **スキーマ工学**: 既存文書からの**スキーマ推測**、スキーマ文書自体を検証・フォーム編集する**メタスキーマ**、テーブル定義書などから検証スキーマを導出する**派生スキーマ**（`derive`）
- Undo/Redo、保存ショートカット、未保存終了確認、復元されるペインレイアウト
- ライト／ダークを切り替えられるMaterial 3テーマ（選択状態は次回起動時に復元）
- ワークスペース一覧・絞り込み・一括編集、**エンティティページ**（全出現のアスペクト合成・関係パネル・改名／統合／削除）、**グラフレンズ**（起点近傍・型／関係の絞り込み）、差分表示、コマンドパレット、最近開いたファイル
- **4スペースUI**: 左端のレールで「編集・台帳・実行・設計」を切替。人間の判断待ち（承認・質問・競合）は実行スペースの**受信箱**に集約され、右ペインは検証・関係・出現をまとめた**IDインスペクタ**
- 参照への**関係種別**（`relation`）付与と、「全要求は設計から参照される」等の**カバレッジルール**によるトレーサビリティ検証
- **AIによる作成支援**（OpenAI / Anthropic 連携）: フィールド単位・配列への候補追加・文書全体のたたき台生成。スキーマ準拠の構造化出力＋適用前プレビューと検証
- **エージェントによるアクティビティ実行**: `_agents`／`_activities` に定義した仕事（レビュー・改名・起票など）を、エージェントが探索→複数文書編集→自己検証のループで実行。提案は変更セットとして人間が部分採用
- **自動実行**: トリガ（ファイル更新・スケジュール・検証エラー）による自動起動、連鎖・リトライ、条件付き自動承認（適用前バックアップと巻き戻し付き）
- **自己改善**: 実行記録のメトリクス集計、評価セット（`_evals`）によるアクティビティの回帰評価とA/B比較、メタアクティビティによる定義改善の提案
- **skill（フォーマット適合）**: Excel / CSV / JSON / Markdown の宣言型インポート・エクスポート（YAMLが常に原本）、ユースケース別テンプレートパック（`init`）
- **ヘッドレスCLI**: GUIなしでカタログ・骨子・検索・部分パッチ（変更セット）・検証・エージェント実行・評価・入出力変換（エージェント連携の基盤）

## 1. ビルドと起動

要件: **JDK 17以上**。Gradle Wrapper（Gradle 9.3.0）を同梱しています。

```bash
cd yaml-design-editor
./gradlew run                                  # スタート画面から履歴・選択でワークスペースを開く
./gradlew run --args="/path/to/your/workspace" # 任意のワークスペースを指定して起動
```

配布物の作成:

```bash
./gradlew packageDistributionForCurrentOS # dmg / msi / deb
```

起動引数を省略すると**スタート画面**が表示され、最近開いたワークスペースの履歴（最大10件。アプリグローバルに保存）から選ぶか、「ワークスペースを開く…」でディレクトリを選択します（初回は `sample-workspace/` を開くボタンも表示されます）。開いた後もツールバーの「開く」やコマンドパレット（`Ctrl+K`）の「ワークスペースを切替」からいつでも切り替えられます（未保存の変更があれば確認ダイアログを挟みます）。

## 2. 画面構成

画面は左端の**アクティビティレール**で切り替える4つの**スペース**からなります。

```
┌──┬─────────────────────────────────────────────────────────────────────┐
│  │ 開く 再読込 ← → 履歴 │            検索・コマンド (Ctrl+K) 閲覧 Theme ◀▶ │
│編├─────────────┬──────────────────────────────────┬──────────────────────┤
│集│ ファイルツリー │ ファイル名 / スキーマ  Undo Redo 保存 すべて保存 │ 検証│関係│出現 │
│  │ 新規・改名    ├──────────────────────────────────┤ （IDインスペクタ）    │
│台│ 削除・展開    │ フォーム │ ソース │ 差分             │                      │
│帳│ ● 未保存      │ 構造化フォーム / YAML / 比較表示     │                      │
│  │             │                                  │                      │
│実│                                                                       │
│行│  台帳スペース: 一覧 │ ビュー │ レンズ │ エンティティ （ワークスペースの俯瞰） │
│  │  実行スペース: 受信箱 │ 手動実行 │ 自動化 │ 計測・評価 （エージェント運用）    │
│設│  設計スペース: スキーマ・ビュー・エージェント・アクティビティ・評価・連携の定義 │
│計├───────────────────────────────────────────────────────────────────────┤
│  │ ステータスバー: 状態 ／ 検証サマリ ／ 実行状態 ／ 判断待ちバッジ            │
└──┴─────────────────────────────────────────────────────────────────────┘
```

| スペース | 役割 |
|---|---|
| **編集** | ファイルツリー＋フォーム／ソース／差分で文書を1件ずつ編集する（従来のエディタ画面） |
| **台帳** | ワークスペース全体を俯瞰する。「一覧」「ビュー（ビューグリッド）」「レンズ（グラフレンズ）」「エンティティ（エンティティページ）」のタブ（§5） |
| **実行** | エージェント運用。**受信箱**（承認待ち・質問・競合）・手動実行・自動化・計測/評価のタブ（§12〜13）。定義が空でも常時表示され、`_agents`／`_activities` が無い間は空状態の案内が表示されます |
| **設計** | スキーマ・ビュー・エージェント・アクティビティ・評価・連携（skill）の定義を種類別に見渡し、新規作成・スキーマ推測の入口を提供する（§4・§14） |

- ファイル名横の `●` は未保存の編集を表します。ファイルを切り替えても編集内容はメモリ上に保持されます（「保存」「すべて保存」で書き出し）。
- 「フォーム」タブが構造化編集、「ソース」タブがテキスト編集です。ソースの編集は**入力のたびに解析され、成功時だけ内部のYAMLツリーへ自動反映**されます（フォームと相互に反映されます）。文書ヘッダーの「保存」はそのツリーをファイルへ書き出します。解析できない状態の間はツリー＝最後に解析できた状態が正で、保存もそれを書きます（エラーが画面に表示され、ソースタブの `Ctrl+S` は保存を拒否します）。
- `Ctrl+S` で現在のファイルを保存、`Ctrl+Shift+S` ですべて保存、`Ctrl+Z` / `Ctrl+Y` で編集を元に戻す／やり直すことができます。
- 右ペインは**IDインスペクタ**です。「検証」（エラー・警告・フェーズ進捗）、「関係」（この文書からの参照と被参照）、「出現」（文書ルートIDと同じ論理IDの全出現・カバレッジ充足。エンティティページへ展開）をタブで切り替えます。object、array、mapはフォーム内で折りたためます（既定ではルートから2階層までを展開し、より深い階層だけを折りたたみます。編集モード・閲覧専用モードで共通で、モード切替後も展開状態は保たれます）。畳んだ状態のヘッダには要素の要約（object は「ID タイトル（n項目）」、array は「n件: 先頭要素の要約, …」。§6 の表示解決）が表示され、開かなくても中身を判断できます。
- **配列・map のテーブル表示**: スカラー項目中心の object 配列（例: テーブル定義書のカラム一覧）や、値が object の map（例: 環境定義の `dev` / `staging` / `production`）は、フォーム内で自動的に**表形式**（列ヘッダ＋1要素1行。map は先頭にキー列）になります。適否は「列が2〜8個 かつ 要素の項目の過半がスカラー系」で自動判定され、スキーマの `display: table` / `display: list` で固定できます（§4）。セルはその場で編集でき、長文・ネスト・enum 連動項目など列にならない項目は行頭の ▶ で開く展開フォームで編集します。map のキー列は表では表示のみです（キーの追加は表の下の入力行、削除は行操作で行えます）。表が広いときは表の下の横スクロールバーで移動します。不適格な配列・map は従来どおり縦のリスト（各要素は畳み込み可）です。
- 参照ジャンプなどの移動は、実行・設計スペースにいても常に編集／台帳スペースへ着地します。スペースの切替自体も「戻る・進む」（`Alt+←` / `Alt+→`）の対象なので、ジャンプ後に戻れば元のスペースへ帰れます。
- **閲覧専用モード**: ツールバーの目のアイコンで切り替えます。入力欄がテキスト表示になり、追加・削除・AIボタンが消えて表示密度が上がります。参照ジャンプ・バックリンクは閲覧行為としてそのまま使えます。エンティティページの埋め込みフォームやビューグリッドにも同時に効き（操作メニューも非表示になります）、状態は次回起動時に復元されます。
- 左右ペインはドラッグでリサイズでき、開閉状態・幅・テーマ・閲覧専用モードは次回起動時に復元されます。
- ファイルペイン上部からYAML／ディレクトリの作成、名前変更、削除を実行できます。新規YAMLは配置先に適用されるスキーマから初期値を生成します。作成先は**ツリーで選択中の場所の配下**で、ダイアログに作成先パスが表示されます（「ワークスペース直下に作成する」への切替も可能。ツリーの空白をクリックすると選択が外れ、未選択時はルート直下が作成先になります）。名前の入力は Enter でも確定でき、同名ファイルが既にある等で作成できない場合は理由がダイアログ内に表示されます。
- ステータスバーの右側に、開いている文書の検証サマリ、実行中のアクティビティ、自動化の稼働状態、**判断待ちの件数**（クリックで受信箱へ）を常時表示します。
- ウィンドウ終了時とワークスペース切替時には未保存確認を表示します。

### 操作の役割

- **ライブ同期**（ソースタブ）: 入力のたびに解析し、成功時だけ内部YAMLツリーへ自動反映します。解析エラーの間は行・列つきのエラーが表示され、「編集を破棄」でツリーの状態に戻せます（エラーがなければ同じボタンが「整形」＝正規化テキストへの揃えになります）。
- **保存**（文書ヘッダー）: 内部YAMLツリーを現在のファイルへ書き込みます。コメント・キー順・引用符やフロー表記のスタイルは保持されます（詳細は「既知の制約」）。
- **ソース編集中の `Ctrl+S`**: 反映と保存を続けて実行します。
- **検索・置換**（ソースタブ）: 大文字小文字を無視した検索（件数表示）と「置換」「すべて置換」ができます。置換結果も自動で反映されます。
- **Tab キー**（ソースタブ）: フォーカス移動ではなくスペース2個を挿入します（YAMLはタブ文字を使えないため）。
- **構文ハイライト**（ソースタブ）: キー・文字列・数値・真偽値・コメント・`---` を色分け表示します。
- **Undo/Redo**: 履歴は**ワークスペース全体で1本**です（直前の変更が別のファイルのものなら、そのファイルが戻ります）。同じフィールドへの連続入力（1秒以内のタイプ）は1回の Undo でまとめて戻ります（フィールドを移る・時間を空ける・構造を変える操作が区切りになります）。実行するとステータスバーに「元に戻しました: <変更の内容>」と**戻ったファイルへのリンク**が表示され、戻した結果が未保存（●）になった場合は「保存で確定します」と案内します（この通知は次の編集・保存・✕で消えます）。ツールバーの Undo/Redo ボタンにマウスを載せると「次に何が戻るか」の予告が表示されます。**文書の新規作成**（新規 YAML・ビューからの詳細文書／新規行ファイル・検証指摘からの「詳細文書を作成」・スキーマ推測）も履歴に入り、`Ctrl+Z` で取り消せます——作成の取り消し／やり直しは**ファイルの有無までその場で反映**されます（内容の編集の Undo が未保存●に留まるのと違い、保存の操作は要りません）。作成しても、それまでの Undo 履歴は失われません。
- **キー名の変更**（汎用ビュー）: キー名横の鉛筆アイコンから、順序と値を保ったまま改名できます。
- **複数ドキュメント（`---` 区切り）**: フォームでは先頭ドキュメントを編集し、後続ドキュメントは保持されて保存時にそのまま再出力されます。全ドキュメントを編集したい場合はソースタブを使います。

### ショートカット

| キー | 操作 |
|---|---|
| `Ctrl+S` | 現在の文書を保存。ソース編集中は反映後に保存 |
| `Ctrl+Shift+S` | ソースを反映後、未保存文書をすべて保存 |
| `Ctrl+Z` | 元に戻す |
| `Ctrl+Y` / `Ctrl+Shift+Z` | やり直す |
| `Ctrl+K` | 検索・コマンド（ID・ファイル・本文・コマンドの統合パレット） |
| `Alt+←` | 戻る（ジャンプ・ファイル切替の履歴） |
| `Alt+→` | 進む |

## 3. ワークスペースの構成

任意のディレクトリを「ワークスペース」として開きます。

```
my-workspace/
├── _schemas/            # スキーマ定義（このディレクトリ名は固定）
│   ├── requirement.yaml
│   └── design-item.yaml
├── requirements/        # 以下は自由な構成。*.yaml / *.yml が対象
│   ├── req-001.yaml
│   └── req-002.yaml
├── designs/
│   └── dsn-001.yaml
└── notes/
    └── memo.yaml        # スキーマにマッチしない → 汎用ビュー
```

各 YAML ファイルには、`_schemas/` 内のスキーマのうち `match`（glob）がワークスペース相対パスに最初にマッチしたものが適用されます（ファイル名の昇順で評価）。どれにもマッチしなければ汎用ビューになります。

### `.yde` 構成（既存リポジトリとの共存・台帳範囲の宣言）

上記のレガシー構成（ルート直下の `_schemas` 等）に加えて、ツールの構成を隠しディレクトリ `.yde/` にまとめる**オプトイン構成**が使えます。既存のプロジェクトリポジトリ（他ツールのYAMLが混在する環境）へ後入れする場合はこちらを推奨します。

```
my-project/
├── .yde/                     # ツール構成（.git / .obsidian と同じ流儀）
│   ├── workspace.yaml        # ledger: 台帳ディレクトリの宣言
│   ├── schemas/              # 旧 _schemas（以下、アンダースコア無しの名前）
│   ├── views/  agents/  activities/  evals/  skills/  runs/
├── doc/                      # 台帳（ledger に宣言した範囲）
│   └── req-001.yaml
├── .github/workflows/        # 台帳外 → 索引・検証集計・エージェントの対象外
└── build/                    # 台帳外（エクスポート先などに自由に使える）
```

```yaml
# .yde/workspace.yaml
ledger: doc          # 文字列またはリスト（例: [doc, spec]）。未宣言なら全体が台帳
```

機能は2層に分かれます。**エディタ層**（ソース／スキーマフォーム編集・単文書検証など、1ファイルで完結する機能）は台帳外のYAMLにも効きます——スキーマの `match` は常にワークスペース相対で、台帳外にもマッチします。**台帳層**（ID索引・参照解決・カバレッジ・ビュー・エージェント・自動化・skill）は `ledger` 配下だけが対象です。台帳外の文書では未解決参照が情報レベルに降格され、ファイルツリーでは薄色・折りたたみで区別されます。

- `.yde/` が無いワークスペースは従来どおり動きます（設定不要）。
- レガシー構成からの移行は `./gradlew runCli -q --args="migrate <workspace> [--ledger doc]"`（予約ディレクトリの移動と構成ファイル作成のみ。スキーマ等の中身は書き換え不要）。
- `.git` などの隠しディレクトリは走査されません（`.yde` のみ例外）。

## 4. スキーマ定義リファレンス

`_schemas/*.yaml` に 1 ファイル 1 スキーマまたは共通定義ライブラリで配置します。

```yaml
id: requirement                       # 安定したスキーマID（省略時はスキーマファイル名）
name: 要求                             # 表示用のスキーマ名
kind: document                        # document（既定）/ library（共通定義のみ）
description: |                         # スキーマ全体の説明（任意・複数行）
  要求事項を管理するスキーマです。
  要求の状態と関連を一貫した形式で記録します。
match: "requirements/**/*.{yaml,yml}" # 適用対象の glob（**, *, ?, {a,b} に対応）
root:                                 # ルートのフィールド定義（通常 type: object）
  type: object
  fields:
    - key: id
      label: 要求ID
      type: id
      required: true
      description: 論理要素を識別するID（同一文書内で一意）
    - key: status
      type: enum
      values: [draft, review, approved, deprecated]
      default: draft
    - key: relates_to
      type: array
      item:
        type: ref
        idPattern: "REQ-*"            # 利用者定義のID体系で候補を限定
        scope:
          schemaIds: [requirement]    # 安定したスキーマIDで探索範囲を限定
```

トップレベルの `description` には、スキーマの目的や対象を説明する複数行の文を任意で指定できます。スキーマ設計画面では複数行テキスト欄として編集できます。

### フィールド定義のプロパティ

| プロパティ | 説明 |
|---|---|
| `key` | 親オブジェクト内のキー名（ルート・配列要素では不要） |
| `label` | フォームでの表示名（省略時は `key`） |
| `type` | 下表の型（省略時 `string`） |
| `required` | `true` で必須。未設定は検証エラー |
| `requiredFrom` | フェーズ機構（後述）: このフェーズ以降で必須。`required` と併用不可 |
| `values` | `enum` の選択肢。文字列、または `{value, label, description}` のリッチ選択肢（後述） |
| `role` | 表示役割 `title` / `subtitle`（後述の表示解決）。このフィールドの値を要素の要約タイトル／サブタイトルに使う |
| `cases` | `enum` の値ごとに、親オブジェクトへ追加される兄弟フィールドを定義（後述） |
| `item` | `array` の要素定義（フィールド定義を再帰的に記述） |
| `display` | `array` / `map` のフォーム表示形式。`table`＝表形式に固定（map はキー列つき）、`list`＝縦並びに固定。省略時は自動判定（要素（array は `item`、map は `value`）が object で、スカラー系の列が2〜8個 かつ 項目の過半を占めるとき表形式） |
| `value` | `map` の値定義（必須。フィールド定義を再帰的に記述） |
| `fields` | `object` の子フィールド定義のリスト |
| `unknownFields` | `object` のスキーマ外項目を `allow` / `warning` / `error` で扱う（省略時 `warning`） |
| `idPattern` / `idPatterns` | `ref` の参照先IDをglob（`*`, `?`）で限定。複数指定はOR |
| `scope.schemaIds` | 参照先を特定スキーマIDに限定。配列内はOR |
| `scope.documentIds` | 参照先を特定ドキュメントIDに限定。配列内はOR |
| `relation` | `ref` の関係種別（例 `implements` / `depends`）。解決可否には影響せず、表示とカバレッジ判定に使う |
| `minLength` / `maxLength` | `string` / `text` の文字数制約。違反は検証エラー。AI生成のJSON Schemaにも伝搬する |
| `pattern` | `string` / `text` / `id` の形式制約（正規表現。値の全体が一致すること）。例 `"^[a-z][a-z0-9_]*$"`。`id` に書くとIDフォーマットの強制になり（例 `TASK-\d{3}`）、自動採番の提案（フォームのID入力メニュー）のパターン源にもなる |
| `min` / `max` | `int` / `number` の範囲制約。違反は検証エラー |
| `default` | 「追加」「作成」時の初期値 |
| `description` | フォームに表示される説明文 |

### 型一覧

| type | フォーム表現 | 検証 |
|---|---|---|
| `string` | 1 行テキスト | required |
| `text` | 複数行テキスト | required |
| `int` | テキスト（整数変換） | 整数であること |
| `number` | テキスト（数値変換） | 数値であること |
| `boolean` | チェックボックス | 真偽値であること |
| `enum` | ドロップダウン | `values` に含まれること。`cases` で値ごとの追加フィールドを定義可能 |
| `date` | テキスト | `YYYY-MM-DD` 形式（警告） |
| `id` | テキスト＋重複警告＋被参照数 | 必須チェック、重複検出 |
| `ref` | テキスト＋候補ドロップダウン＋ジャンプボタン。解決済みの参照は入力欄の枠内右端に参照先タイトルを併記（IDと表示名を1つの領域で確認できる） | 参照解決 |
| `array` | 要素の追加・削除・並べ替え | 要素ごとに `item` を再帰検証 |
| `map` | 任意キーの追加・削除＋型付き値エディタ | 各キーの値を `value` で再帰検証 |
| `object` | 枠付きのネストフォーム | `fields` を再帰検証 |
| `any` | 汎用エディタ（値の形に合わせた編集） | 検証しない（必須チェックのみ）。単一の型で表せない値の明示に使う。AI生成では `map` と同様に構造化出力が無効化される |

`object` / `array` / `map` は任意の深さでネストできます（例: サブ項目の配列の中に `id` を持たせて、サブ項目単位で参照させることも可能）。

`object` にスキーマ外のキーがある場合、既定ではそのキーの位置に警告を1件表示します。`unknownFields: error` ならエラー、`allow` なら通知しません。未知キーの配下はスキーマ検証およびID・参照索引の対象外とし、配下の各要素へ同じ問題を重複表示しません。ルートの予約項目 `_document` はこの検査から除外されます。

### 任意キーのMap

任意の文字列キーを持つ連想配列は `map` で定義します。`value` は必須で、Map内のすべての値に同じフィールド定義が適用されます。

```yaml
root:
  type: object
  fields:
    - key: inputs
      label: 入力
      type: map
      value:
        type: string
```

上記のスキーマでは、次のようなデータをフォームから追加・編集でき、各値が `string` として検証されます。

```yaml
inputs:
  username: ユーザ名
  password: パスワード
  email: メールアドレス
```

`value` には `object`、`array`、`ref`、別の `map` など、すべての型を再帰的に指定できます。

フォームではMapの件数と各キーが表示されます。「キーを追加」で任意のキーを作成し、値は `value` で指定した型のエディタで編集します。キーの重複と空文字は追加できず、不要なキーは行ごとに削除できます。Mapフィールド自体が未作成の場合は「Mapを作成」から空のMapを作成します。

`value` を省略したスキーマはスキーマ定義エラーになります。また、データ側がYAMLマッピングでない場合や、Map内の値が `value` の型に一致しない場合は検証エラーになります。

値をオブジェクトにする場合は、次のように定義します。

```yaml
- key: environments
  type: map
  value:
    type: object
    fields:
      - key: endpoint
        type: string
        required: true
      - key: enabled
        type: boolean
```

```yaml
environments:
  development:
    endpoint: http://localhost:8080
    enabled: true
  production:
    endpoint: https://example.com
    enabled: false
```

ルート定義に `type: map` を指定することもできます。

### enum のリッチ選択肢（label / description）

`values` の要素は文字列のほか、`{value, label, description}` の形で表示ラベルと説明を付けられます（混在可・後方互換）。

```yaml
- key: status
  type: enum
  values:
    - open                                       # 文字列だけの選択肢（従来どおり）
    - { value: in-progress, label: 対応中 }
    - value: closed
      label: 完了
      description: 対応が終わり、確認も済んだ状態
```

- **データ・検証・`cases` のキー・AI生成の制約は常に `value`** を使います。ファイルに保存されるのも `value` です。
- フォームのドロップダウンは `label` を表示し、現在の選択値に ✓ を付け、`description` を選択肢と選択後の欄外に表示します。`label` と `value` が異なる場合は候補に値も併記します。
- スキーマ設計UIの「選択肢」欄からも値・ラベル・説明を編集できます（ラベル・説明を空にすると文字列形へ戻ります）。

**選択肢をワークスペースのデータで管理したい場合**（選択肢自体に説明文書や参照関係が必要な場合、選択肢を文書として増やしたい場合）は、enum ではなく `type: ref` ＋ `scope` を使ってください。選択肢を1文書（または1要素）＝1IDの台帳として持ち、`scope.schemaIds` / `idPatterns` で候補を台帳に限定すれば、「ドロップダウンから選ぶ」体験のまま、選択肢の追加・説明・被参照の追跡が原本側の編集として管理できます（§6 参照候補の絞り込み）。

### enum 値ごとの追加フィールド（cases）

「選択した値によって設定できる項目が変わる」構造（判別共用体）は、`enum` フィールドの `cases` で定義します。`cases` のキーは `values` のいずれかの値、値はフィールド定義のリストで、その enum 値が選択されているときだけ**親オブジェクトのフィールド**として有効になります。

```yaml
- key: type
  label: 入力種別
  type: enum
  values: [text, radio, checkbox, date]
  cases:
    radio:
      - key: options
        label: 選択肢
        type: array
        required: true
        item:
          type: string
    checkbox:
      - key: options
        label: 選択肢
        type: array
        item:
          type: string
```

上記のスキーマでは、`type: radio` の要素だけが `options` を持てます（`radio` のときは必須）。

挙動の要点:

- **フォーム**: case フィールドは判別フィールド（enum）の直後に行として表示され、enum の値を切り替えると表示が追随します。切り替えで不要になったキーのデータは削除されず、「現在の選択では使用しないキー」として案内つきで表示されます。
- **ネスト**: case から追加するフィールドをさらに `cases` つきの enum にできます。選択された case を順に展開し、追加フィールドはすべて同じ親オブジェクトの兄弟フィールドとして扱います。
- **検証**: アクティブな case のフィールドは通常のフィールドと同様に検証されます（`required` はその case が選択されているときのみ有効）。非アクティブな case のキーがデータに残っている場合は「「options」は「入力種別」が radio / checkbox のときのみ使用できます」のような案内になり、重大度はそのオブジェクトの `unknownFields` ポリシー（既定 warning）に従います。
- **ID・参照の索引**: アクティブな case フィールド配下の `type: id` / `type: ref` は通常どおり索引化されます。非アクティブな case のキー配下はスキーマ外サブツリーと同様に走査境界となります。
- **制約**: `cases` は `enum` 型でのみ使用できます。case のキーは共通フィールドや、同一オブジェクト内の別の enum の `cases` と重複できません（同じ enum の複数の case での重複は可。上例の `options`）。これらはメタスキーマ検証で検出されます。
- **`$ref`**: 名前付き定義の enum に `cases` を持たせて `$ref` で参照できます。

### 名前付き定義と再帰スキーマ

共通または再帰的な構造は `definitions` に置き、`$ref` で参照できます。同じスキーマ内は定義名だけ、別のスキーマ・ライブラリは `スキーマID#定義名` で参照します。名前付き定義はスキーマ内の再利用だけでなく、**ビュー定義からも参照できます**（グリッドの定義参照列・文書ビューの `fields.definition`。§5）。ビューから参照したいデータ構造は `definitions` に括り出すのがおすすめです。

```yaml
name: outline
match: "outlines/**/*.yaml"
definitions:
  node:
    type: object
    fields:
      - key: title
        type: string
        required: true
      - key: children
        type: array
        item:
          $ref: node
root:
  $ref: node
```

複数の工程別スキーマで共通する構造は、業務文書へ直接適用されない `kind: library` に切り出せます。library は `definitions` だけを持ち、`match` / `root` / `phases` / `coverage` は持ちません。

```yaml
# _schemas/_common.yaml
id: common
name: 共通フィールド
kind: library
definitions:
  column:
    type: object
    fields:
      - { key: name, type: string, required: true }
      - { key: dataType, type: enum, values: [string, number, boolean] }
```

```yaml
# _schemas/logical-table.yaml
id: logical-table
name: 論理テーブル
match: "tables/logical/**/*.yaml"
root:
  type: object
  fields:
    - key: columns
      type: array
      item:
        $ref: common#column
```

修飾参照した共通定義の内部で非修飾 `$ref` を使った場合、その参照は利用側ではなく共通定義を宣言したライブラリ内で解決されます。ライブラリIDの重複と未解決参照はロード時のスキーマ定義エラーになります。

`_schemas` 配下のファイルを開くと「スキーマ設計」タブが表示され、document / library の切替、名前付き定義、ローカル／横断参照を構造化UIで編集できます。document から library への変更では適用定義が削除されるため確認ダイアログが表示されます。

スキーマ設計画面には次の確認機能があります。

- **メタスキーマ検証**: 必須情報、フィールドキー重複、arrayの要素定義、enumの選択肢、`cases` の整合（enum型のみ・値の存在・キー衝突）、未解決の `$ref` を保存前に検出
- **プレビュー**: スキーマからサンプルYAMLを生成し、実際のフォームまたはYAMLとして確認
- **サンプル生成**: 生成したYAMLをクリップボードへコピー
- **適用対象**: `match` に一致するワークスペース内のファイルを一覧表示し、他スキーマとの競合も表示
- **フェーズ・カバレッジ**: スキーマ全体設定の `phases`（申告キー・フェーズ順序）と `coverage`（参照ベース／出現ベースの切替・重大度・判定開始フェーズ）も構造化UIで編集できます（後述のリファレンス参照）

スキーマファイルを保存すると、メタスキーマ検証結果は通常の右側「検証」パネルにも表示されます。

### スキーマ・リファクタリング（既存文書を追随させるスキーマ変更）

スキーマの `key` や構造を直接書き換えると、既存文書のキーが「スキーマ外項目」として残留します。スキーマ・リファクタリングは、スキーマ変更と既存文書・ビューの追随を**1つの計画**（プレビュー→適用。オール・オア・ナッシング）にまとめます。GUI からの適用は1つのトランザクションとして記録され、**Ctrl+Z（Undo）1回で全変更が戻ります**。

スキーマ設計画面からは次の操作が使えます（フィールド行のボタン。未保存の変更があるときは保存を促します）。

- **一括改名…**: スキーマ定義のキー（`$ref` で共有された定義のフィールドなら定義側＝全使用スキーマの文書が対象。ルート直下のフィールドが `phases` の申告キーなら `phases.key` も追随）＋全該当文書のデータキー（値・キー順・コメントを保った改名。`cases` 由来のキーは、その case が有効な文書だけが対象）＋ビューのパス（通常列・計算列・文書ビューなど、解決が一意に定まる場合のみ。多義な列は書き換えず警告）
- **一括削除…**: スキーマ定義と全該当文書のデータキーを削除。**値が入っている件数**をプレビューで明示します（ID型・フェーズ申告キーは拒否）
- **文書をスキーマ順へ整列…**（ルート定義の右上）: 全該当文書のキー順をスキーマのフィールド順へ正規化します（値・コメント保持。`_document` は先頭・スキーマ外キーは末尾に相対順で残る。スキーマは変更しません）

新CLI `workspace refactor`（§16）にはさらに次があります。フィールドパスはドット区切り（例 `details.priority`。配列・map は暗黙に降ります）。CLI 経路のビュー追随は行われず、言及箇所の警告のみです（自動追随は GUI 経路）。

- `move-field <schema-id> <field-path> <dest-path>`: フィールドの親子移動（`dest-path` は object のパス・ルートは `.`）。移動元と移動先が**同じ要素コンテキスト**にある場合のみ（配列・map の境界をまたぐ移動は1対Nの対応になるため拒否）。文書側は中間 object を生成し、空になった親 object は削除します（`--keep-empty` で残す）
- `rename-enum-value <schema-id> <field-path> <old> <new>`: enum 値の改名。`values`・`cases` のキー・`default`・（フェーズ申告フィールドなら）`phases.order` と `requiredFrom` / `activeFrom`・全該当文書の現在値が追随します
- `require-field <schema-id> <field-path> --default <値> [--from <フェーズ>]`: 必須化と同時に、値が無い（キー欠落・空）文書へ既定値を一括充填します（`--from` 指定時はそのフェーズに達している文書だけ）
- `convert-type <schema-id> <field-path> <型> [--values a,b,c]`: 決定的な型変換の一括版。スカラー→`array`（1要素に包む）・array→要素の型（1要素は引き継ぎ・空は削除・複数要素は拒否）・string→`enum`（逸脱値があれば一覧つき拒否）／`int`／`number`（解析検証つき）・enum／数値等→`string`
- `rename-definition <module-id> <name> <new>` / `extract-definition <schema-id> <field-path> <name>` / `inline-definition <schema-id> <field-path>`: 名前付き定義の改名（`$ref` を横断書換）・インライン構造の定義化・定義参照のインライン化（参照が残らない定義は削除）。文書は変わりません
- `rename-relation <old> <new>` / `rename-schema-id <old> <new>`: 関係名（レジストリ・スキーマの `relation:`・ビュー）とスキーマID（修飾 `$ref`・`schemaId` 系の参照）の横断改名

共通の安全規則: 改名・移動先のキーが既存文書に存在する等の衝突は**適用せずに中止**します（対象を提示）。アクティビティの指示文など自動書換できない参照は、言及箇所を**警告として列挙**するので適用後に確認してください。派生スキーマ（`derive`）のフィールドは対象外です（導出元文書を修正してください）。適用は保存を伴うため、対象に未保存の編集があるときは先に保存してください（未保存のまま適用しようとすると拒否されます）。

### カバレッジルール（詳細文書の必須化）

スキーマのルート直下に `coverage` を書くと、「指定スキーマの文書にも同じIDが出現する＝詳細文書があること」（出現ベース `detailIn`）を検証できます。一覧と詳細を同一ID（1:1の詳細化。§6）で運用するとき、詳細未作成のIDを機械検出できます。

```yaml
id: screen-list
match: "screens/index.yaml"
coverage:
  - idPattern: "SCR-*"            # 対象ID（省略時はこのスキーマの全ID）
    detailIn:
      schemaIds: [screen-detail]  # 出現先（詳細文書）のスキーマ（必須）
      minCount: 1                 # 必要な出現数（既定 1）
    level: warning                # warning（既定）/ error
    activeFrom: detail-design     # フェーズ機構（後述）: このフェーズに達するまで判定を保留（省略可）
    description: 全画面は画面定義（詳細文書）を持つこと
```

不足があると、IDを定義している文書の「検証」パネルに指摘が表示されます。画面上の判定は未保存の編集を含む「見たまま」で行われ、詳細文書を書いた時点で（保存前でも）反映されます（CLI・エージェントなどのヘッドレス経路はディスク基準）。充足状況はID横ぐしビュー・ビューグリッドの状態列でも確認できます。

**被参照数の要求**（「条件を満たす参照を一定数以上受けること」。旧 `requiredBy`）は、正準の綴りへ一本化しました——1ホップ・無条件なら関係レジストリの `cardinality`（`inMin` 等。§関係レジストリ）、参照元スキーマの限定など条件付き・多段なら `constraints`（`expect: exists` / `count`）で宣言してください。`requiredBy` を書いたスキーマは移行先を案内する定義エラーになります（使い分けの一覧は [docs/DESIGN-CHECK-CATALOG.md](docs/DESIGN-CHECK-CATALOG.md)）。

### フェーズ機構（工程に応じた検証の強弱）

要件定義→論理設計→物理設計のように、1つの論理要素（例: データモデルの1エンティティ）を複数の工程にまたがって記述していく運用では、後工程の項目を要件定義の時点で必須にすると検証エラーが大量発生してしまいます。`phases` を宣言すると、「この項目はこのフェーズ以降で必須」という**累積的な**必須化ができます。

```yaml
id: entity
match: "models/**/*.yaml"
phases:
  key: phase              # 現在フェーズを申告するルート直下のキー（省略時 phase）
  order: [requirements, logical-design, physical-design]
root:
  type: object
  fields:
    - key: phase
      type: enum
      values: [requirements, logical-design, physical-design]
      default: requirements
    - key: name
      type: string
      required: true       # 無条件必須（全フェーズで必須）
    - key: columns
      type: array
      requiredFrom: logical-design   # logical-design 以降で必須。requirements 段階の未記入はエラーにしない
      item: { type: object, fields: [ { key: name, type: string, required: true } ] }
    - key: physicalName
      type: string
      requiredFrom: physical-design  # 物理設計以降で必須
coverage:
  - detailIn: { schemaIds: [table-design] }
    activeFrom: physical-design      # 物理設計に達するまではカバレッジ判定を保留する
    level: error
```

挙動の要点:

- 文書はルート直下の申告キー（既定 `phase`）で現在フェーズを記載します。未申告・未知の値は**先頭フェーズ**（最も緩い判定）として扱われ、未知の値には警告が出ます。
- `requiredFrom` は「そのフェーズ**以降**で必須」（累積的）。現在フェーズより先の工程に属する項目の未記入はエラーにならず、代わりに「検証」パネルにフェーズ別の記入進捗（例: `logical-design: 1/2 記入`）として表示されます。フェーズが進むと、過去に必須化した項目は引き続き必須のままです。
- `required: true` と `requiredFrom` は併用できません（メタスキーマ検証でエラー）。
- カバレッジルールの `activeFrom` は「IDを**定義している文書**の現在フェーズがそのフェーズに達してから判定する」という保留を表します。未到達の間は「フェーズ未到達」として区別表示され、検証エラー・警告にはなりません（ID横ぐしビュー・ビューグリッドの状態列も同様に区別表示します）。
- 文書の物理的な分割単位（1文書で全工程を書くか、工程ごとにファイルを分けて段階的詳細化するか）はどちらでも成立します。工程ごとに分けた運用では、後工程のスキーマだけ `requiredFrom` を使わず素の `required` で書いても構いません。

CLI `validate` の出力にも、`phases` を宣言したスキーマの文書には `phaseProgress`（フェーズごとの記入済み／総数）が付与されます。

### 整合ルール（宣言値と導出値の一致検証）

段階的詳細化で機械的に導出できる値（例: 値型の `maxLength` → `varchar(100)`）を下流文書に手書きしている場合、その値が**導出規則から計算した期待値と一致していること**をスキーマの `consistency:` で検証できます。ビューの計算列（§ビューグリッド）と**同じ導出語彙・同じ解決**を使うため、ビューの「（導出）」列に見えている値と、検証が比較する期待値は常に一致します。

```yaml
# テーブル設計スキーマ側: カラムのDDL型は、値型参照を辿って型写像から導出した値と一致すること
consistency:
  - description: DDL型はDDL型写像から導出した値と一致すること
    idPattern: "FLD-*"          # 対象のID要素（省略時は全ID要素）
    path: type                  # ID要素からの相対パス（検査する値）
    expected:                   # 期待値の導出（計算列の computed と同じ語彙）
      lookup: { schemaId: concepts, via: type }
      source: { schemaId: ddl-mapping }
      path: to                  # 例: varchar({maxLength})
      values:
        - schemaId: concepts
    assert: equals              # equals（既定）/ lte（導出値以下）/ gte（導出値以上）
    level: warning              # warning（既定）/ error（エージェントの提出ゲートを塞ぐ）
    activeFrom: physical-design # フェーズ到達まで判定を保留（phases 宣言時）
```

`assert: lte` / `gte` は**適合（包含）判定**です（両辺を数値として比較。数値でなければ判定保留）。「画面入力の最大文字数は、参照する値型の最大文字数**以下**であること」のように、等値でなくてよい制約の流れを検証できます（例: 100文字の値型に50文字の入力欄は適合、200文字は「設定できない値を許してしまう」ため指摘）。sample-workspace の `_schemas/todo-screendef.yaml`（入力欄→値型）が実例です。

挙動の要点:

- 一致しない値には「値「Int」は導出値「String」と一致しません」の指摘が**検査した値の座標**に付きます（意図的な上書きを許す運用なら `warning`、禁止なら `error`）。
- **判定保留は沈黙**します: 検査する値が未記入（`required` の領分）・導出の元になる写像行がない（`detailIn` カバレッジの領分）・期待値のプレースホルダが未解決、の場合は指摘しません。
- **テンプレート健全性**: 整合ルールが導出元（`expected.source`）に選んでいる文書では、テンプレートに解決できないプレースホルダ（例: `{maxlen}` の書き間違い）を書くと、**その場（未保存でも）**テンプレートの座標に警告が出ます。
- 期待値の材料（他文書）は、画面上の検証では未保存の編集を優先して読みます（「見たまま判定」。CLI などのヘッドレス経路はディスク基準）。エージェントの変更セット・ステージングの検証では適用後のオーバーレイで判定されるため、提出ゲートにもそのまま乗ります。
- **整合ルールは組込みの定義体です**（後述「検査の定義と語彙の定義」）。`consistency` という書き方は、検証の前に「クエリ＋値の比較（`check`）」の基本の検査へ展開されて、他の検査と同じ規則で評価されます。展開結果は CLI `checks` で確認できます。これに伴い次の2点が他の検査と揃いました: ①`source` / `values` の指定に合う文書が**複数あるときは、すべて調べて1つでも食い違えば指摘**します（以前は定義出現を優先して1つだけ読んでいました。1つの文書に絞れている書き方では結果は同じ）②`lookup.via` は**参照フィールド（`type: ref`）のキー名**で、参照の線として辿ります（ref 型でないフィールドの値は辿りません）。
- （ビューの計算列 `computed` では）selector（`schemaId` / `fileGlob`）が**同一IDの複数の出現に一致する**場合は、**定義出現を優先**して1出現から読みます（定義出現がなければ索引順の先頭。R29-02）。selector で1出現に絞れている通常の運用では意識する必要はありません。
- 判定は現在**等値**です（値の包含関係——maxLength 100 の入力は varchar(255) に適合する等——による適合判定は将来拡張。ROADMAP R16-03b）。

**明示的除外の規約**: 実装が導出元の全項目を持たないケース（エンティティが項目の部分集合だけ実装する等）では、黙って行を省くのではなく、**「あえて使わない」ことを行として残す**運用を推奨します。同一IDの出現なので完全性カバレッジ（`detailIn`）は充足し、値のフィールド（type 等）を書かないので整合検証は保留（沈黙）——つまり**黙った欠落だけが警告として残り、意図的な除外は理由つきのデータとして記録されます**。

```yaml
properties:
  - id: FLD-TASK-STAFF
    excluded: true        # あえて実装しない（スキーマに boolean フィールドとして宣言）
    note: 画面表示専用の項目のため、エンティティには持たせない
```

sample-workspace の `_schemas/todo-entity-design.yaml`・`_schemas/todo-table-design.yaml` が実例です（`excluded` フィールドの宣言を含む）。

なお、検証パネルの整合指摘は**クリックで選択メニュー**（エラー箇所へ／導出規則へ／入力値へ／**導出値を適用**）を出します。「導出値を適用」は未保存の編集として書き込むため、Undo・差分・保存がそのまま使えます。指摘のあるフィールドはフォーム上でも入力枠が色づきます（エラー=赤・警告=オレンジ）。また、カバレッジ（`detailIn`）の出現先になっている文書（写像文書など）には「不足しているID」の案内（INFO）が表示され、行を書いたその場（未保存でも）で消えます。

### メタスキーマ（`_schemas` 文書の編集・検証・AI生成）

`_schemas/` 配下のスキーマ文書自体にも、組込みのメタスキーマ（ID `builtin-schema`）が適用されます。

- スキーマ文書を開くと「スキーマ設計」タブ（主要UX）に加えて「フォーム」タブが表示され、メタスキーマによる構造化フォームでも編集できます。文書ヘッダーの「AIで作成」でスキーマのドラフトをAI生成することもできます。
- 検証パネル・CLI `validate` はスキーマ文書をメタスキーマで検査します（例: `type` の値が選択肢外、`fields` は `type: object` のときのみ有効、`scope` のキー名間違い）。定義として読み込めない致命的な問題は従来どおりスキーマ読込エラーとして表示されます。
- 一般スキーマの `match` は `_schemas/` には適用されません（catch-all パターンの誤適用を防止）。メタスキーマを差し替えたい場合は、同じID（`builtin-schema`）のスキーマを `_schemas` に置くと上書きできます。
- エージェントの `_schemas` への書込禁止は従来どおりです（メタスキーマは編集・検証のためのもので、書込経路は増えません）。

### スキーマ推測（既存文書からのドラフト作成）

スキーマを書く前にYAML文書が既にある場合、既存文書からスキーマのドラフトを推測できます。

- **入口**: ファイルツリーで文書を選択して「スキーマ推測」ボタン（魔法の杖アイコン）、設計スペース「スキーマ」の「既存文書から推測…」、または CLI `infer-schema`。
- **推測の内容**: glob に一致する複数文書をマージし、①値の実例からの型推測（`int` / `number` / `boolean` / `date` / 長文は `text`）②参照の認識——命名規約（`ref` / `*_ref` / `refs` / `depends_on` 等。§6 の参照認識と同じ規約）に加え、全値がサンプル中の論理IDと一致するフィールドも `ref` と推測 ③小さく反復する値集合の `enum` 候補化（3件以上＋同じ値の反復が条件。IDらしい値＝既存IDと一致・`SCR-001` のようなID形式は enum にしません）④全文書に出現するキーの `required` 候補化 ⑤`id` キーの `type: id` 化 — を行います。構造が文書間で揺れるキーは `any` になります。
- **仕上げ**: 生成された `_schemas/<ID>.yaml` はドラフトです（先頭にその旨のコメントが付きます）。メタスキーマ検証・スキーマ設計画面で型や必須を確認・調整し、サンプルYAML生成（プレビュー）を逆方向の検算に使ってください。既存のスキーマファイルは上書きしません。

### 派生スキーマ（`derive`: 文書から検証スキーマを導出する）

テーブル定義書のような「実質スキーマの文書」がある場合、その文書を二重にスキーマへ書き写す代わりに、`derive:` を宣言したスキーマ（テンプレート）が導出元文書から検証スキーマを**ロード時にコンパイル**します。

```yaml
# _schemas/record-template.yaml
id: record-template
name: レコード検証
derive:
  from: "tables/**/*.{yaml,yml}"     # 導出元文書（テーブル定義書）の glob。予約ディレクトリは不可
  # each: entities                   # 1文書内の配列要素ごとに導出する場合は配列パスを指定（省略時は文書ルート）
  id: "record-{id}"                  # 導出スキーマのID。{パス} は導出元要素の値で置換される
  name: "{title} レコード"
  match: "records/{id}/**/*.{yaml,yml}"  # 導出スキーマの適用先（`,` を含む {a,b} は glob 構文として残る）
  fields:                            # 写像の語彙（path / map / default）は skill の列マッピング（§14）と同じ
    source: columns                  # フィールド一覧にする配列のパス
    key: name                        # 各要素のこの値 → フィールドのキー
    label: label                     # 任意: 表示ラベル
    description: note                # 任意: 説明
    required: required               # 任意: 必須（真偽値）
    type:                            # 任意: 型の写像（省略時はすべて string）
      path: dataType
      map: { varchar: string, bool: boolean, number: int }
      default: string
root:                                # 任意: 全導出スキーマ共通のフィールド（先頭に合成される）
  type: object
  fields:
    - { key: id, type: id, required: true }
```

- 上の例では `tables/tbl-task.yaml`（`id: TBL-TASK`、`columns` 配列）から、`records/TBL-TASK/**` に適用されるスキーマ `record-TBL-TASK` が導出されます。テーブル定義書に列を足して保存すると、レコード文書は**すぐに新しいルールで再検証**されます。
- `derive` を宣言したスキーマ自身はどの文書にもマッチしません（`match` は書けません）。導出スキーマはファイルとしては存在しない読み取り専用の成果物で、`coverage` / `phases` / `definitions` はテンプレートから引き継がれます。
- 導出できない要素（プレースホルダ値の欠落・フィールドキーの欠落・IDの重複・未知の型）は、理由付きでスキーマ読込エラーに報告されます（他の導出は継続します）。
- 導出元文書は通常の文書なので、エージェントの変更セットが（承認を経て）検証ルールを変えることがあります。このため**導出元文書への自動適用（`approval: auto`）は常に承認待ちへ降格**されます（§12）。

### エンティティ型宣言（`entity`: 出現の型と定義／詳細化の役割）

同一IDの複数文書出現（段階的詳細化。§6）では、「どの出現がそのIDの**定義（誕生）**か」をこれまで機械が知りませんでした。スキーマのルートに `entity:` を宣言すると、この文書群の出現にエンティティ型と役割が付きます。

```yaml
# 単一型（この文書群の全IDが1つの型）
entity:
  type: screen          # エンティティ型名（ワークスペース内で一意にする運用）
  idPattern: "SCR-*"    # この型のID命名規約（省略可。逸脱は検証が警告する）
  defines: true         # この文書群の出現が「定義（誕生）」。省略時 false = 詳細化

# 複数型（idPattern で判別。idPattern のない宣言は1つまで＝残り全部の受け皿）
entity:
  - { type: screen, idPattern: "SCR-*", defines: true }
  - { type: usecase, idPattern: "UC-*", defines: true }

# アスペクト宣言（省略可）: この出現がエンティティのどの「側面」を所有するか
entity:
  type: screen
  idPattern: "SCR-*"
  aspect: design          # 側面名（省略時はスキーマID）。レジストリの entities 節で表示名・順序を宣言できる
  owns: [layout, memo]    # この出現が所有するフィールドの限定（省略時は宣言フィールド全部。id は常に対象外）
```

宣言の効果（宣言のないスキーマは従来どおり＝**非破壊**）:

- **ジャンプ・表示が定義出現に安定**: 同一IDの複数出現があるとき、参照ジャンプ・タイトル解決は定義出現（`defines: true` の文書群の出現）を優先します（従来は「パス順で最初の出現」）。
- **エンティティ整合の検証（既定は警告）**: 定義出現がどこにもないID（浮遊詳細化）／定義出現が2文書以上にあるID（定義競合）／`idPattern` に一致しないID（命名逸脱）／同一IDが異なる型で出現（型競合）を、各出現のID要素の座標つきで指摘します。定義出現の一意性（浮遊詳細化・定義競合）は、関係レジストリ文書の `enforcement: { definingUniqueness: error }` でエラーへ昇格できます（「最初の出現＝定義」の暗黙運用をやめる opt-in スイッチ。後述）。
- **アスペクト（`aspect` / `owns`）＝エンティティ全体像の合成**: 各出現が「エンティティのどの側面（フィールド群）を所有するか」を宣言します。エンティティページ（§5）・エージェントの `read_entity`（§12）・CLI `entity show`（§16）は、全出現を「定義出現 → レジストリのアスペクト宣言順」に並べ、所有フィールドを座標つきでマージした**エンティティ全体像**として表示します。複数の出現が同じフィールドを所有していると検証が警告します（「同じ情報を重複記載しない」の機械化。誤検知を避けるため、双方に `entity` 宣言があり少なくとも一方が明示的な `owns` を持つ組だけを判定します）。
- sample-workspace の `_schemas/data-model.yaml`（`entity-model` 型）・`_schemas/table-design.yaml`（`table-design` 型）が実例です。

### 関係レジストリ（`kind: relations`: 関係語彙の宣言）

参照の関係種別（`type: ref` の `relation`）は自由な文字列で、これまで語彙の一覧も「逆方向から見たときの表示」もありませんでした。`_schemas` に `kind: relations` の文書を置くと、ワークスペースの関係語彙を宣言できます（`kind: library` と同様、この文書自体はどの文書にもマッチしません）。

```yaml
# _schemas/relations.yaml
id: workspace-relations
kind: relations
enforcement:                    # 強制スイッチ（後述。省略可＝従来の lint のまま）
  undeclaredRelation: error
  definingUniqueness: error
entities:                       # エンティティ型のレジストリ宣言（省略可）: 型の表示名とアスペクト順序
  - type: table-design
    label: テーブル設計          # エンティティページ・レンズ・read_entity で使う表示名
    aspects:                    # 全体像の合成でのアスペクト（entity.aspect）の並び順と表示名
      - { name: design, label: テーブル設計 }
relations:
  - name: derives               # スキーマの ref フィールドの relation と一致させる
    label: 由来する              # 参照方向（この要素からの参照）の表示ラベル
    inverseLabel: 実装される     # 被参照方向（この要素への参照）の表示ラベル
    source: [table-design]      # 参照を書く側のエンティティ型（宣言すると対象型・出次多重度の検証が効く）
    target: [entity-model]      # 参照先のエンティティ型（宣言すると対象型・入次多重度の検証が効く）
    cardinality: { inMin: 1 }   # in / out の下限上限（source / target の型宣言がある側にだけ効く）
    acyclic: true               # 非循環の宣言（違反は常にエラー）
    level: warning              # 対象型・多重度の指摘の重大度（warning / error。既定 warning）
    description: 1:N 詳細化の逆リンク
```

- **逆方向ラベル表示**: バックリンクを表示する全ての面（右パネルの関係タブ・ID横ぐし・ビューのバックリンク列・文書ビュー・グラフ・エージェントの `related`）で、relation 名の代わりに `label`（参照方向）／`inverseLabel`（被参照方向）が表示されます。未宣言の relation は従来どおり名前のまま表示されます。
- **グラフ整合検証**: レジストリの宣言は検証の制約になります（検証パネル・CLI `validate`・変更セット適用・エージェントの提出ゲートに同じ判定が乗ります）。
  - **対象型**: `source` / `target` を宣言した関係で、エッジ両端のエンティティ型が宣言と食い違う参照を、参照値の座標で指摘します（型宣言のないエンティティ・未解決参照には黙ります）。
  - **多重度**: `cardinality` の `outMin` / `outMax` は「そのエンティティが書く参照の合計」（複数出現に分けて書いても合算）、`inMin` / `inMax` は「そのエンティティへの被参照数」を検査します。判定対象は `source` / `target` の型宣言に一致する型つきエンティティだけです（「誰が満たすべきか」を推測しません）。座標は該当エンティティの定義出現です。被参照不足（`inMin`）の指摘は、クリックメニューに**「参照の追加先を開く: <文書>」**が出ます（追加先候補＝source 型を宣言するスキーマの文書のうち、対象IDのファイルと出現を共有するもの（同一IDの詳細化文書）か、台帳型スキーマの唯一の文書。機械が選べない場合は出ません）。
  - **非循環**: `acyclic: true` の関係で循環ができると、「循環経路（A → B → A）」を添えて循環を構成する参照値の座標へ**常にエラー**が出ます。
- **強制スイッチ（`enforcement:`）**: ワークスペース単位の opt-in で破壊的な強制を有効化します。各キーは3値（未宣言＝従来のまま／`warning`／`error`）です。
  - `undeclaredRelation`: レジストリにない relation を使う参照を、文書側でも参照値の座標で指摘します（未宣言時はスキーマ読込エラー一覧の lint のみ）。
  - `definingUniqueness`: `error` で浮遊詳細化・定義競合をエラーへ昇格します（エンティティ宣言のあるスキーマで定義出現の一意性を強制＝「最初の出現＝定義」ヒューリスティクスの廃止）。
  - 同一キーを複数のレジストリ文書で宣言するとロードエラーです。
- **未宣言 relation の lint**: レジストリを1つでも置くと、スキーマの ref フィールドがレジストリにない relation を使っている場合にスキーマ読込エラー一覧へ警告が出ます（レジストリがなければ何も出ません）。
- **自動推測**: CLI `infer-relations <workspace>` が、索引の参照実績（relation・キー名・参照元／先のエンティティ型）からレジストリのドラフトを生成します（`--apply` で `_schemas/` へ保存。`inverseLabel` は TODO コメント付きなので実際の語彙に書き換えてください）。
- レジストリ文書には専用のメタスキーマ（`builtin-relations`）が適用され、フォーム編集・検証がそのまま使えます。

### 属性付き参照（`{to, 属性...}`: エッジへの注記）

参照そのものに小さな注記（例: アクター参照の「役割」）を付けたい場合、`type: ref` のフィールドに `fields:`（属性の型宣言）を書くと、オブジェクト形式が使えるようになります。

```yaml
# スキーマ
- key: actors
  type: array
  item:
    type: ref
    relation: uses
    fields:                 # エッジ属性の型宣言（これがある場合だけオブジェクト形式を許可）
      - key: role
        type: string

# データ（スカラー形式とオブジェクト形式を混在できる）
actors:
  - ACT-USER                # 従来どおりのスカラー参照
  - to: ACT-ADMIN           # 予約キー to = 参照値（ジャンプ・パッチの座標は to の値）
    role: 承認者             # 兄弟キー = エッジ属性
```

- 参照の解決・検証・ジャンプは `to` の値に対して従来の ref と同じに働きます。属性は object として検証されます（未宣言キーは `unknownFields` ポリシー）。
- バックリンク・`related` の表示には属性が「（role: 承認者）」の括弧注記で添えられます（値はIDのままです）。
- フォームでは参照行の下に属性行が表示され、スカラー形式の値には「属性を追加」でオブジェクト形式へ変換できます。
- **使い分けの規約**: エッジ属性は「それ自身がIDを持たない注記」です。属性の中に `ref` / `id` は書けません（メタスキーマ検証でエラー）。関係自体を他から参照したい・詳細化したい場合は、従来どおり **1:N 具体化**（関係を表す新しいIDを持つ要素＋逆リンク。§6 の規約）を使ってください。
- `fields` 宣言のない ref にオブジェクトが来た場合は従来どおり型不一致です（ヒューリスティクス検出のスキーマなし文書にも適用されません）。

### 文書参照（`target: document`: 文書そのものへの参照）

参照先が「要素（論理ID）」ではなく「文書そのもの」の場合、ref フィールドに `target: document` を宣言します（既定は `entity`。値の形から推測はしません）。

```yaml
- key: spec
  type: ref
  target: document    # 参照先は文書ノード（documentId）
```

- 参照値は **documentId**（文書ルートに `_document: { id: ... }` があればその値、なければワークスペース相対パス）です。
- 解決・検証は文書の名前空間に対して行われ、エンティティIDには混ざりません（未解決は台帳内でエラー・台帳外の文書では情報レベル）。
- フォームの候補は documentId＋文書名（`_document.name`）で提示され、ジャンプは参照先の文書を開きます。参照された文書側では右パネルの関係タブに「この文書への参照」が表示されます。
- `_document.id` を宣言した文書への参照は、ファイルを移動しても壊れません（パス参照は後述の移動機能が書き換えます）。

### パターン制約（`constraints`: グラフパターンの存在／不在／件数／値比較の検証）

カバレッジルール（被参照数）よりも複雑なトレーサビリティ要件——「このパターンが存在すること（`exists`）／しないこと（`absent`）／解の件数が範囲内であること（`count`）／解ごとに束縛間の値比較が成り立つこと（`check`）」——を、グラフパターン照合（ビューのクエリ行と同じ語彙）で宣言できます。カバレッジの一般形で、既存の `coverage` を置き換えるものではありません。

```yaml
# ユースケースのスキーマ: どの画面からも到達できない孤立ユースケースを検出する
constraints:
  - id: reachable
    description: いずれかの画面から利用されること
    match:
      - node: { entity: usecase, bind: uc }   # 起点束縛（先頭 node。kind: entity 限定）
      - edge: { relation: uses, dir: in }     # 被参照を1段辿る
      - node: { entity: screen }
    expect: exists                            # exists = 解が1つ以上 / absent = 解がない
    level: warning                            # warning（既定）/ error
    # activeFrom: 設計                        # このフェーズに達するまで判定保留（coverage と同じ）
    # where: [...] / also: {...} / limit: n   # クエリ行と同じ語彙が使える
  - id: tested-twice
    description: テスト項目が2件以上あること
    match:
      - node: { entity: usecase, bind: uc }
      - edge: { relation: verifies, dir: in }
      - node: { entity: test-item, bind: item }  # 数えたい対象に bind を書く
    count: { min: 2 }                            # 解（束縛の組）の件数範囲。expect と排他。max も指定可
```

```yaml
# 画面項目のスキーマ: 項目の最大文字数が、参照する業務データ型の最大桁を超えないこと
constraints:
  - id: length-within-dtype
    description: 画面項目の最大文字数は業務データ型の最大桁以内であること
    match:
      - node: { entity: screen-item, bind: si }
      - edge: { relation: dtype }
      - node: { entity: data-type, bind: dt }
    check:                                       # 解ごとの判定述語（expect / count と排他・複数書けばすべて成立が期待）
      - lte: [{ of: si, path: max_length }, { of: dt, path: max_digits }]
    level: error
```

- 判定は「**起点束縛に一致する各エンティティ**について、残りのパターンに解があるか（`expect`）／解が何件あるか（`count`）／解ごとに値比較が成り立つか（`check`）」。`count` の件数はクエリ結果の行と同じ同一性（`bind` した列の組の distinct）で数えます。指摘の座標は起点の**定義出現**（なければ先頭出現）で、その出現を持つ文書の検証にだけ現れます。
- **束縛間の値比較 `check`**: 項目は `{lte|gte|lt|gt|eq|ne: [{of: 束縛, path: 相対パス}, {of: 束縛, path: 相対パス}]}`（複数書けばすべて成立が期待）。判定は解ごとに**出現の組**（同一IDの定義出現＋詳細化出現のどれから読むか）を走査し、**違反する組（反例）を1つでも発見したら違反**・値が読めない／順序比較で数値でない組しかなければ黙ります（判定保留）。1項目の中で同じ束縛を両辺に書いた場合は**同じ出現**から読みます（出現をまたいだ突合はしない）。違反メッセージには反例の値の組（例 `si=SI-001（max_length: 20） > dt=DT-003（max_digits: 10）`）が列挙され、各IDへジャンプできます。
- `where` の述語は `equals` / `notEquals` / `exists` のいずれか一つ。`notEquals` は「値が1つ以上あり、どの出現の値も指定値でない」ときに成立します（例 `{of: br, path: status, notEquals: approved}` で「承認済み**以外**」を捕まえる。値がなければ黙る）。
- **ノード一致 `same`**: `node: { same: 束縛名 }` は「先行して束縛済みのノード**そのもの**」への到達を要求します（他のキーと同居不可・先頭 node には書けません）。2経路が同一ノードで合流することの照合で、**型不一致の検出**が書けます——例:「カラム→実装する属性→業務型」と「カラム→業務型」が同じ型ノードに到達すること（`also: { from: c, steps: [{edge: {relation: dtype}}, {node: {same: t}}] }` ＋ `expect: exists`）。値（表記）の比較ではなくノードの同一性で判定します。
- エンティティ型が未宣言のID・未解決参照・起点の母集団（`entity` / `id` / `where`）に入らないIDには黙ります（誤検知よりも見逃しを許容する方針）。さらに、解探索の途中で**未解決参照により候補が失われた**場合、「解の不足を理由とする違反」（`exists` の解なし・`count` の下限未達）は出しません——失われた候補が不足分だったかもしれないためで、未解決参照そのものは参照解決の検証が指摘します。`absent` の成立・`count` の上限超過は、見つかった解が実在する証拠のためそのまま指摘します。
- 検証パネル・CLI `validate`・変更セット適用・エージェントの提出ゲートに同じ判定が乗ります（`level: error` なら提出を塞げます）。
- **値の式**: `check` の左右には、値の読み出しだけでなく次の式を書けます——読み出し `{of: 束縛, in: {schemaId, fileGlob}, path: 相対パス}`（`in` は「どの文書に書かれた値を読むか」の指定。省略すると同じ ID が書かれた全文書が候補）・決まった値 `{value: 値}`・テンプレートの展開 `{format: 式, scopes: [{of: 束縛, in: 指定}]}`（式が返す文字列の `{パス}` を、scopes の要素の値で近い順に置き換える）・辞書での置き換え `{map: 式, using: {元: 先}}`・最初に得られた値 `{first: [式, ...]}`。値が得られない組は評価せず（判定保留）、演算子を値として渡したいときは `{op: lte, left: 式, right: 式}` の形でも書けます。`edge` にも `in: {schemaId, fileGlob}` を書けます（その参照が書かれた文書の指定）。
- **文面・指摘の場所・エラー時の対応**（`check` の検査で使えます）: `message` は指摘の文面のひな型（`{left}` `{right}`＝比べた値、`{left.raw}` `{right.raw}`＝計算前の元の値）。`reportAt: {of: 束縛, in: 指定, path: 相対パス}` を書くと、指摘は起点を定義した場所ではなく**その値が書かれた場所**に出ます（値のある文書の検証で、要素ごとに報告）。`responses` はエラー時の対応の宣言で、`{jump: right.source, label: ...}`（値の出どころ——テンプレートなどが書かれた場所——へ移動）・`{jump: right.inputs, label: ...}`（テンプレートへ差し込んだ値の場所へ移動。入力ごとに1件。ラベルに `{input.placeholder}` `{input.value}`）・`{apply: right, label: ...}`（値を指摘の場所へ書き込む。`reportAt` が必要）を、検証パネルのメニューに宣言の順で出します。
- **指摘の説明**: `absent`／`count` の違反は「該当の組: api=EAPI-001・tbl=TBL-MEMBER」のように**成立してしまった束縛の組**を列挙し、検証パネルのクリックメニューから各IDの定義へジャンプできます。定義出現が別文書にあるIDの詳細化文書にも指摘が届きます——**エラー級は同じ重大度（該当の組つき）**で、警告級は「報告先: 定義出現 <パス>」の INFO 案内で表示されます（全体集計ではエラー級の同一違反が出現数ぶん数えられます）。

### 検査の定義と語彙の定義（`functions` / `vocabulary`: 検査に名前を付けて使い回す）

検査の書き方は3段になっています。**下の段がベースで、上の段は検証の前に下の段へ展開されます**（展開結果は CLI `checks` で見られます）。

1. **基本の書き方**: スキーマの `constraints` に1件ずつ書く。プリミティブを直接書く（`match` ＋ `expect` / `count` / `check`）か、**定義を名前で使う**（`use` ＋ `with`）。
2. **関数のような定義**（`functions`）: 名前・受け取る値（`params`）・中身（`checks`＝基本の検査のひな型）。使われるたびに、渡された値がひな型の `$名前` へ差し込まれます。
3. **語彙の定義**（`vocabulary`）: 短く書くための書き方を作る。どこに書けるか（`in`）と、書かれた内容からどの定義をどの値で使うか（`uses`）を宣言します。

```yaml
# _schemas/my-checks.yaml —— 定義の置き場（kind: library）。どのスキーマ文書に書いても、ワークスペース全体で使えます
id: my-checks
kind: library
functions:
  - id: not-greater-than
    description: 指定スキーマの文書に書かれた値が、上限以下であること
    params: [schema, path, limit]
    checks:
      - match:
          - node: { schema: $schema, bind: item }
        check:
          - op: lte
            left: { of: item, in: { schemaId: $schema }, path: $path }
            right: { value: $limit }
        reportAt: { of: item, in: { schemaId: $schema }, path: $path }
        message: 「$path」の値「{left}」は上限「{right}」を超えています
        level: error
vocabulary:
  - word: limits
    in: limits[]                      # スキーマ直下の limits 配列の各要素に書ける
    uses:
      - use: not-greater-than
        with:
          schema: { schema: id }      # この語彙が書かれたスキーマのID
          path: { from: field }       # 書かれた内容から読む（default: / map: で既定値と読み替えも書ける）
          limit: { from: max }
```

```yaml
# 利用するスキーマ側
limits:                               # 語彙で短く書く
  - { field: size, max: 10 }
constraints:
  - use: not-greater-than             # 定義を名前で直接使う
    with: { schema: item, path: weight, limit: 5 }
```

- **差し込みの規則**: 文字列がちょうど `$名前` なら渡された値そのもの（数値・配列・マップも渡せる。渡されなければ「無い」）、文中の `$名前` は文字列として埋まります。`$` そのものは `$$`。ひな型が参照する名前は `params` に宣言が必要で、綴りの誤り・見つからない定義・宣言にない受け取る値は**スキーマの読み込みエラー**になります。ひな型の中に条件分岐や繰り返しは書けません（値の置き換えだけ）。
- **語彙の `uses`**: `when: キー`／`unless: キー` を書くと、そのキーが書かれている／いないときだけ有効になります（同じ語彙を、書かれ方に応じて別の定義へ対応させる）。
- **組込みの語彙も同じ仕組みです**: スキーマの `consistency`（整合ルール）は、ツールに同梱された定義体（YAML。コードなし）が作る語彙です。組込みだけが使える特別な機能はありません——同じものを利用者が書けます。今後、多重度・詳細文書の存在・遷移検証・網羅マトリクスも順に定義体へ移ります（ROADMAP P29 Phase 6）。
- 利用者が定義した語彙のキーは、スキーマ文書の検証で「定義されていない項目」と警告されません（書き方の形の検証までは、まだ行いません）。

### 網羅マトリクス（`matrix`: 行×列の全組合せの検証）

「処理×試験観点のテスト項目」「テーブル×CRUDを担う機能」のような**2軸の全組合せ（セル）**に、行と列の両方を参照する**証人（witness）**が存在することを検証します。

```yaml
# 処理設計書のスキーマ: 各処理は全試験観点のテスト項目を持つこと
matrix:
  - id: proc-viewpoint-matrix
    description: 各処理は全試験観点の単体テスト項目を持つこと
    rows: { entity: process }              # 行の母集団（entity / schema / id で選択）
    columns: { entity: test-viewpoint }    # 列の母集団
    witness:                               # セルの証人: 行と列の両方を参照するエンティティ
      node: { entity: test-item }
      row: { relation: verifies }          # 証人 → 行 の参照 relation
      column: { relation: viewpoint }      # 証人 → 列 の参照 relation
    level: warning
```

- 不足セルは**行の定義出現**に「不足セルがあります（N 件）: VP-002（境界値）・…」と列挙で報告されます。
- **あえて試験しないセル**は、証人側に `excluded: true` の行として残します（証人が存在すればセルは充足。理由はデータとして記録され、網羅の判断がレビューに残ります）。
- 列の母集団が空のとき・行の母集団に入らないIDには黙ります（判定保留）。パターン制約と同様、検証パネル・CLI・提出ゲートに同じ判定が乗ります。

### 遷移検証（`flow`: 到達性・行き止まり・宣言外遷移）

画面遷移や状態遷移のような**エッジ一覧の文書**（1行に遷移元 ref と遷移先 ref が並ぶ形）を有向グラフとみなし、経路の長さによらない到達性を検証します。パターン制約（固定長の経路）では書けない「どこから何ホップでも」の判定を担います。

```yaml
# 画面一覧のスキーマ（ノードを定義する側）に宣言する
flow:
  - id: screen-flow
    description: 全画面は開始画面から到達でき、行き止まりは終端宣言があること
    nodes: { entity: screen }                  # ノード母集団（entity / schema / id で選択）
    edges: { from: { relation: transition-from }, to: { relation: transitions-to } }
    start: { relation: flow-start }            # 開始ノード（遷移文書のデータで宣言）
    terminal: { relation: flow-terminal }      # 出る遷移がなくてよいノード（例 完了画面）
    level: error
```

- **到達不能**: `start` で宣言した開始ノードから到達できないノードを、そのノードの**定義出現**に報告します（開始ノードへ relatedIds でジャンプ可）。`start` を宣言しない規則・開始データが空のときは判定しません（判定保留）。
- **行き止まり**: 出る遷移がなく `terminal` 宣言もないノードを報告します。
- **宣言外遷移**: `usage: {from: {relation}, to: {relation}}` を追加すると、そのエッジ集合が宣言エッジに含まれること（原本にない遷移の検出）を要求できます。
- エッジの from / to は**同じ行オブジェクトの直下**にあるスカラー参照の組だけがエッジになります。未解決参照でエッジ・開始・終端が失われたときは、解の不足系の判定（到達不能・行き止まり・宣言外）を黙らせます（未解決参照そのものは参照検証が指摘）。
- **状態遷移への応用**: 状態をID化（例 ST-RESERVED を状態台帳で定義）して遷移表を ref で書けば、同じ宣言が状態機械の検証（未定義遷移・到達不能状態）になります。

> 「設計に対してどんな機械的チェックが書けるか」のパターン一覧は [docs/DESIGN-CHECK-CATALOG.md](docs/DESIGN-CHECK-CATALOG.md)（設計チェックカタログ）にまとまっています。

### エンティティ操作（改名・統合・削除）とファイル移動

エンティティ（論理ID）のリファクタリング操作は、**全出現・全参照を1つの変更セットへ束ねて**生成し、通常の変更セット適用（オール・オア・ナッシング・適用後検証）で反映します。

- **改名（rename）**: 全出現のIDフィールドと全参照（スカラー参照・属性付き参照の `to`）を新IDへ書き換えます。新IDが既存IDと衝突する場合は生成段階で拒否（統合は merge を使用）、エンティティ型の `idPattern` から外れる場合は警告付きで生成します。
- **統合（merge）**: 統合元への全参照を統合先へ張り替えます。統合元の出現は「統合先のIDへ書き換えて詳細化として残す」（既定）か「要素ごと削除」を選べます。
- **削除（delete)**: 被参照が1件でもあれば参照元一覧つきで拒否します（黙って壊さない）。参照がなければ出現要素を削除します。
- 入口は**エンティティページの操作メニュー**（§5。改名／別IDへ統合／削除を変更内容のプレビュー→適用で実行）、新CLI `workspace refactor rename-entity|merge-entity|delete-entity`（`--apply` なしは計画のプレビュー出力）、検索・コマンド（`Ctrl+K`）の「エンティティを改名…」です。GUI からの適用は1つのトランザクションとして記録され、**Ctrl+Z（Undo）1回で全変更が戻ります**。

ファイルの移動・改名も影響を見てから実行できます:

- ツリーの「名前を変更」ダイアログと新CLI `workspace refactor move-document <old> <new>` は、**パスIDの文書参照の書き換え**（`_document.id` 未宣言の文書が対象）と、**スキーマ `match` の当たりが変わる警告**・**ビュー定義の file / fileGlob が外れる警告**を実行前に表示します。参照の書き換えと移動は1つのトランザクションで適用されます。
- `_document.id` を宣言した文書は documentId が移動で変わらないため、書き換え不要の旨が表示されます。

## 5. ワークスペース横断機能

台帳スペース（レールの「台帳」）のタブから、次の横断ビューを利用できます。

- **一覧ビュー**: ID、タイトル、状態、担当、種別、ファイルを表形式で表示し、文字列・種別・状態で絞り込み
- **一括編集**: 選択した複数ファイルのルート直下のスカラー項目を確認後に一括更新。対象キーはワークスペースの文書に現れるルート直下のスカラーキーから選択（`id`・`_document` などの予約キーと、配列・オブジェクト値の項目は対象外）
- **グラフレンズ**: エンティティグラフ（解決済みの参照の両端）を力学配置で描画します。エンティティページの「グラフで見る」で**起点の近傍**（深さ1〜2。起点の解除・深さ切替可）に絞れ、エンティティ型・関係（relation）のチェックボックスで部分グラフを切り出せます。ノードは型で色分け（凡例つき）・エッジには関係レジストリの `label` が表示され、ノードやエッジ一覧をクリックするとそのエンティティのページへ移動します。ドラッグでパン・「＋／－」でズーム
- **エンティティページ**: 同一論理IDの全出現を**エンティティ全体像**（アスペクト合成。§4 の `entity.aspect` / `owns`）として1画面に集約します。ヘッダにはID・エンティティ型・タイトルと**操作メニュー**（改名／別IDへ統合／削除。全出現・全参照を書き換える変更セットのプレビュー→適用）、本文にはアスペクト見出しつきの所有フィールド（その場で編集できます。編集は通常のフォームと同じ経路＝未保存●表示・Undo・保存がそのまま効きます）、**関係パネル**（関係ラベルでグループ化した両方向の参照。行クリックで相手エンティティのページへ・矢印で参照箇所へ）、カバレッジ充足を表示します。アスペクト宣言のないスキーマの出現も従来どおり出現フォームで編集でき、「出現別フォームで表示」トグルで従来表示に切り替えられます。ヘッダの「すべて保存」（未保存件数つき）で複数文書の編集をページを離れずに保存できます。台帳スペースの「エンティティ」タブ、右ペイン（インスペクタ）の「出現」タブ、検索・コマンド、ID出現候補ダイアログから開けます
- **ビューグリッド**: `_views/*.yaml` に定義した「行（論理ID）×列（各文書の項目）」の宣言的ビューを、**編集可能な一覧**として表示（後述）
- **差分**: 文書の「差分」タブで、ディスク上の保存済み内容と編集中内容を左右比較。変更行では行内の変わった箇所を文字単位で強調表示
- **最近開いたファイル**: ツールバーの履歴アイコンから直近12ファイルを再度開く。履歴はワークスペース単位で保存
- **検索・コマンド**: `Ctrl+K` で開く統合パレット。ID・タイトルでのジャンプ、ファイル検索、**本文検索**（2文字以上で発動。キー・値への部分一致。未保存の編集も対象＝「見たまま」で検索し、ヒットのクリックで該当箇所へジャンプ）、台帳ビューの切替、実行／設計スペースの表示、保存、エンティティの改名（全出現・全参照の一括書き換え。プレビュー→適用）、ワークスペースの切替（履歴からの選択・ディレクトリ選択）をキーボード中心で実行

一括編集は対象に未保存文書が含まれる場合は実行されません。実行前には確認ダイアログを表示し、変更後は索引と画面を再読込します。

### ビューグリッドとビュー定義（`_views`）

段階的詳細化（同一IDを複数文書で詳細化する運用）では、「機能一覧」と「機能ごとの詳細文書」のように情報が複数ファイルへ分かれます。ビューグリッドは、`_views/*.yaml` の**宣言的なビュー定義**に従って、それらを1つの一覧に結合して表示・編集する機能です。台帳スペースの「ビュー」タブから開きます。

- **行** = `rows.idPattern` に一致する**論理ID**。同じIDの出現が複数文書にあれば1行に結合されます。または `rows.match`（**クエリ行**。後述）でパターン照合の束縛行を行にできます（`idPattern` とは併用不可）
- **列** = 「どの出現（`schemaId` / `fileGlob` で選択）の、要素からの相対パス（`path`）」。`editable: true` の列はグリッド上で直接編集できます（文字列・数値・enum・参照などのスカラー値。配列・オブジェクトはクリックで該当文書へジャンプ）
- セルの編集は**元の文書への通常の編集**そのものです（未保存●表示・Undo・`Ctrl+S`／すべて保存・差分がそのまま使えます）。ビュー自体はデータを持ちません
- **詳細列**: `detail` に一致する出現があればリンク、なければ「作成」ボタンで `filePattern` の位置に**詳細文書をスキャフォールド**します（スキーマの必須初期値＋行のIDを設定）
- **新規行**: `newRow` を定義すると、グリッドから新しい行を作れます。2つのモードがあります（併用不可）
  - **配列モード**（`file` + `path`）: 一覧文書の配列へ新しい要素を追加します（IDを入力して保存するとグリッドの行になります）
  - **ファイルモード**（`filePattern`）: 一覧文書を持たず詳細文書だけでIDを運用するレイアウト向け。IDを入力すると `{id}` を置換したパスへ**詳細文書そのものをスキャフォールド**します（スキーマの必須初期値＋入力したIDを設定。ディスクへ書かれた時点で行が現れます）
- **バックリンク列**: 列に `path` の代わりに `backlinks` を書くと、行のIDへの**被参照**（参照元要素のID・タイトル）を一覧表示します。`relation`（参照の関係種別）と `schemaIds`（参照元スキーマ）で絞り込めます。1:N詳細化（§6）の「親から見た分裂先の一覧」に使います。派生表示のため編集はできません（クリックで参照元へジャンプ）
- **定義参照列**: 列に `label`／`path` の代わりに `definition: モジュール#定義名` を書くと、スキーマの**名前付き定義**（§4）のセル型フィールドが列に展開され、見出し・パスがスキーマから導出されます（ID型の項目は行のID列と重複するため除かれます）。`schemaId` を併記した場合は定義名だけでも書けます（例 `definition: screen`）。列の見出しをビューへ重複記載する必要がなくなり、スキーマの変更に自動で追随します。`editable: true` は展開された全列に適用されます
- **計算列**: 列に `path` の代わりに `computed` を書くと、他の出現に書かれた**テンプレート（元値）を参照時に評価した導出値**を表示します（読み取り専用の派生表示）。段階的詳細化で機械的に導出できる値（例: 値型の `maxLength` → `varchar(100)`）を、手で転記せずルールから表示するための機構です。導出元（テンプレート・入力値）を編集すると、**保存しなくても**評価値は自動で追随します（未保存のまま確認し、OKなら保存する流れで使えます）
  - `source`（必須）: 元値を読む対象IDの出現の選択（`schemaId`／`fileGlob`）。`path` でその要素からの相対パスを指定します
  - 元値の中の `{パス}` プレースホルダは「source の要素 → `values` で選んだ出現の要素 → `lookup` の起点要素」の順で解決されます（原本に書かれた値のみを参照する1段評価。解決できないものは `{...}` のまま表示されます）
  - `lookup`（任意）: 行の出現の参照フィールド（`via`）を1回だけ辿り、**参照先のID**を対象にします（例: 属性の値型参照を辿って型写像から導出）
  - `map`（評価後の値辞書）・`default`（元値が無いときの既定値）も指定できます
  - セルをクリックすると**導出の説明**（元値 → 評価結果）と行き先の選択が表示され、**導出規則**（テンプレート）と**各入力値**（プレースホルダを解決した値の位置）のどちらへもジャンプできます。値を変えたいときは規則か入力値を通常どおり編集します（`editable` とは併用できません）。エージェント（`read_view`）・CLI（`view` の `derivation` 節）にも同じ来歴が出ます
- **状態列**: カバレッジルール（§4）の充足状況を行ごとに表示します

```yaml
# _views/screen-catalog.yaml
id: screen-catalog
name: 画面カタログ
rows:
  idPattern: "SCR-*"                  # このIDパターンが行になる
order:
  fileGlob: todos/10-screens-list.yaml  # 一覧文書での出現順に並べる（省略時はID順）
columns:
  - label: 画面名
    fileGlob: todos/10-screens-list.yaml  # 値を取る出現（schemaId でも指定可）
    path: name                            # 出現要素からの相対パス
    editable: true
  - label: エリア
    fileGlob: "todos/screens/*.yaml"
    path: areas                           # 複合値は要約表示＋ジャンプ
  - label: 実装テーブル
    backlinks:                            # バックリンク列: この画面IDを参照している要素を一覧表示
      relation: derives                   # 参照の関係種別で絞る（省略可）
      schemaIds: [table-design]           # 参照元文書のスキーマで絞る（省略可）
detail:
  fileGlob: "todos/screens/*.yaml"        # この条件に一致する出現を「詳細」と見なす
  filePattern: "todos/screens/{id}.yaml"  # 「作成」ボタンの作成先（{id} が行のIDに置換）
newRow:
  file: todos/10-screens-list.yaml        # 「新規行」の追加先（一覧文書の配列）
  path: screens
```

一覧文書を持たないレイアウト（1詳細文書＝1ID）では、`newRow` をファイルモードにします:

```yaml
# _views/actor-list.yaml — 詳細文書だけでIDを運用する場合
id: actor-list
name: アクター一覧
rows:
  idPattern: "ACT-*"
columns:
  - label: アクター名
    schemaId: actor
    path: name
newRow:
  filePattern: "00-requirements/011-{id}.yaml"  # 「新規行」でIDを入力すると詳細文書を直接作成
```

**クエリ行**（`rows.match`）: 行を「1つのID」ではなく、**グラフパターン照合の束縛行**（結合の組）にします。「画面→uses→ユースケース」のような**多段結合の組を1行に**でき、結合先の値もセルとして表示・編集できます:

```yaml
# _views/entity-table-matrix.yaml（sample-workspace に同梱の実例）
id: entity-table-matrix
name: エンティティ×テーブル（結合）
rows:
  match:                                   # node / edge の交互連鎖（node で始まり node で終わる）
    - node: { entity: entity-model, bind: ent }   # 起点集合（entity: 型 / schema: 出現スキーマ / id: IDパターン）
    - edge: { relation: derives, dir: in }        # dir: out（参照を辿る。既定）/ in（被参照を辿る）。via（キー名）でも絞れる
    - node: { entity: table-design, bind: tbl }   # bind した束縛が結果の列になる
  # rowKey: ent                            # 行キーの束縛（省略時は先頭の bind。詳細列・状態列・新規行はこのIDに効く）
  # where:                                 # プロパティ述語（equals / exists のみ。値はいずれかの出現の該当パス）
  #   - { of: tbl, path: status, equals: draft }
  # limit: 100                             # 行数上限（既定 100）
columns:
  - { label: エンティティ名, path: name }              # of 省略 = 行キー束縛（ent）の値
  - { label: テーブル名, of: tbl, path: title, editable: true }  # of: 束縛名 = 結合先の値をセル化（編集は原本へ）
  - { label: 状態, of: tbl, path: status, editable: true }
```

- 結合により**同じIDの行が複数現れる**ことがあります（例: 1エンティティ×2テーブル = 2行）。セルの編集は従来どおり各原本文書への通常編集です
- `also:`（`{from: 束縛名, steps: [...]}`）で束縛済みノードからもう1本の連鎖を足せます（1段のみ・内部結合）。`kind: document` のノード（文書そのもの）も扱えます
- 行の並びはクエリの決定的順序（束縛名の辞書順に並べた値のID昇順）で、`order` とは併用できません。CLI `query`（§16）で同じパターンを試作できます

計算列の例（値型台帳の制約値で、型写像のテンプレートを評価して表示する）:

```yaml
# 行 = 属性ID（FLD-*）。属性の値型参照（type）を辿り、DDL型写像のテンプレートを評価する
columns:
  - label: DDL型（導出）
    computed:
      lookup: { schemaId: concepts, via: type }   # 行の出現の ref を1ホップ辿る（省略時は行のID自身）
      source: { schemaId: ddl-mapping }           # 元値（テンプレート）を読む出現
      path: to                                    # 例: varchar({maxLength})
      values:
        - schemaId: concepts                      # {maxLength} を値型定義の値で解決する
```

sample-workspace の `_views/field-traceability.yaml`（概念→実装→DDLの項目トレーサビリティ。手書きの宣言値と導出値を並置）と `_views/value-type-mappings.yaml` が実例です。

`_views` は予約ディレクトリで、組込みスキーマによりフォーム編集・検証できます。エージェントは同じビューを `read_view` ツールで参照でき（§12）、CLI では `view` コマンドで解決できます（§16）。

ビュー定義はロード時に**スキーマとの整合が検査されます**（リント）。存在しないスキーマIDへの参照、スキーマから解決できない列・セクションのパス、存在しない定義参照は「定義エラー」としてビューグリッドのバナー・`read_view`・CLI `view` の一覧に表示されます（指摘があってもビュー自体は従来どおり表示されます）。スキーマを変更したときに、それを参照しているビューが黙って壊れることを防ぎます。また、`_views` の定義文書を開いている間は**右ペインの検証タブにも同じ指摘が表示され**、編集中の内容で再判定されるため、保存する前に定義の誤りへ気づけます。

また、詳細文書をフォームで開くと、上部に**「他文書での定義」ストリップ**が表示され、同じIDの一覧側の情報（名前・種別など）を参照・ジャンプできます。一覧側にある情報を詳細文書へ重複記載する必要はありません。

### 文書ビュー（`kind: document`）— フォーム表示の合成

スキーマは「データの構造と検証」を、ビューは「画面の見せ方」を受け持ちます。**文書ビュー**は `_views` のビュー定義に `kind: document` を指定したもので、特定の文書をフォームで開いたときの表示を**セクションの並び**として合成します。「内容はスキーマでチェックし、表示はビューでコントロールする」ための機構です。

- **適用先**: `match`（ファイルglob）または `schemaId`（併記時は両方に一致）。マッチする文書ビューがない文書は、従来どおりスキーマ駆動フォームで表示されます（文書ビューは足したい文書にだけ足す上書きです）。複数の定義がマッチする場合は定義ファイル名順の先勝ちです
- **`sections`**: 上から順に描画されます。各セクションは次のどちらか一方を持ちます
  - **`fields`** — スキーマ駆動フォーム。`path` を省略すると文書全体、指定するとそのパスの項目だけを表示します。編集は通常のフォームと同じ（未保存●・Undo・保存がそのまま効きます）。`include: [キー...]`（列挙した順でそのキーだけを表示）／`exclude: [キー...]`（列挙したキーを除いて表示）で表示項目を選別でき、複数の fields セクションに分ければフォームをグループ分けできます。`definition: モジュール#定義名` を添えると「このセクションはこの名前付き定義（§4）の構造を表示している」という宣言になり、定義が存在しなければエラー、パス先のフィールドがその定義を参照しなくなればリントが指摘します（スキーマ変更への追随検出）
  - **`backlinks`** — 文書内のIDへの**被参照表**（読み取り専用）。`idPattern` で対象IDを絞り、`relation`・`schemaIds` で参照を絞り、`columns` で参照元要素の値を列表示できます。クリックで参照元へジャンプします
- **`attachments`（要素単位アタッチ）**: セクションが文書レベルの合成であるのに対し、アタッチは**フォーム中の要素の位置**へ被参照表を差し込みます。`at` に要素パスのパターン（YPath 構文＋`[*]`＝任意のインデックス。例 `actors[*]`）を書くと、一致する各要素の展開フォーム内（配列要素・ネスト・テーブルの行展開すべて）に、**その要素のIDへの被参照**だけを絞った表が現れます。被参照の条件（`relation`・`schemaIds`・`columns`）はセクションの `backlinks` と同じ語彙です。IDを持たない要素には差し込まれません

たとえば「アクター定義書に、そのアクターを利用するユースケースの一覧表を足したい」とき、スキーマにはアクター定義の本質だけを書き、被参照の表はビュー側に足します:

```yaml
# _views/actor-document.yaml
id: actor-document
name: アクター定義書
kind: document
match: "00-requirements/01-actors.yaml"   # schemaId: actors でも可
sections:
  - fields: {}                       # スキーマ駆動フォーム（従来表示そのもの）
  - label: 利用するユースケース
    backlinks:                       # 被参照表: この文書のアクターIDを参照している要素の一覧
      idPattern: "ACT-*"             # 文書内の対象ID（省略時は文書内の全ID）
      relation: uses                 # 参照の関係種別で絞る（省略可）
      schemaIds: [usecases]          # 参照元文書のスキーマで絞る（省略可）
      columns:                       # 参照元要素から表示する列（省略時はID・タイトルの要約のみ）
        - label: ユースケース名
          path: name
```

文書末尾の一覧表ではなく「各アクターの展開フォームの中に、そのアクターのユースケースだけを出したい」場合は、被参照表をアタッチとして書きます:

```yaml
sections:
  - fields: {}
attachments:
  - at: "actors[*]"                  # 各アクター要素の展開フォーム内に差し込む
    label: 利用するユースケース
    backlinks:
      relation: uses
      schemaIds: [usecases]
```

被参照は、画面上は未保存の編集を含む「見たまま」（オーバーレイ索引）、`read_view`・CLI はディスク索引に基づきます。文書ビューは台帳の文書のみが対象です（`ledger` 宣言時は台帳外に適用されません）。エージェントは `read_view` に `file` を渡して同じ被参照表を座標つきで読め、CLI では `view <view-id> [file]` で解決できます（適用対象が1文書だけなら `file` は省略可）。

## 6. ID とリンクの仕組み

### ID の索引化

ワークスペース内のYAMLをスキャンし、`id -> [(ファイル, パス, タイトル, schemaId, documentId)]` の索引を構築します。IDとして認識されるのは:

- スキーマで `type: id` と定義されたフィールドの値
- スキーマの有無に関わらず、キー名が **`id`** であるスカラー値（ネストした要素でも可）

同じIDは複数ドキュメントに定義できます。それらは段階的詳細化された同一論理要素の複数出現として索引化されます。同一ドキュメント内の重複だけが検証エラーです。ジャンプ時に複数出現がある場合は選択ダイアログを表示します。

スキーマの `id` は参照スコープに使う安定識別子、`name` は表示専用です。`id` を省略した場合はスキーマファイル名（拡張子なし）を使います。

ドキュメントIDは任意で次のように宣言できます。省略時はワークスペース相対パスを使います。

```yaml
_document:
  id: system-overview
  name: システム構想
  description: |
    システムの目的、利用者、主要な機能領域を定義する文書。
    後続の要求・設計文書が前提とする全体像を示す。
```

`name` は画面の文書ヘッダーに表示する任意の文書名です。省略時は従来どおりワークスペース相対パスを表示します。
`description` は、全文を読まずに文書の目的と内容を判断するための任意の概要です。フォーム先頭の「文書メタデータ」で文書名と概要を編集できます。これらは将来、LLMへ文書コンテキストを渡す際の要約情報としても利用できます。

### 表示解決（タイトル・要約の決まり方）

要素（IDを持つオブジェクトなど）を1行で見せる場面——畳み込みヘッダ・参照候補・バックリンク・ID横ぐしビュー・ビューグリッド・ID検索・エージェントの `related` 要約——は、すべて同じ**表示解決**の結果を使います（人間とAIが同じ要約を見ます）。タイトル・サブタイトルは次の優先順位で決まります。

1. **スキーマの `role` 指定**: `role: title` / `role: subtitle` を付けたフィールドの値（`$ref` 先の指定も合成され、library 共有にも乗ります）
2. **予約語**: タイトルは `title` → `name` → `label`、サブタイトルは `description` → `summary` の先勝ち
3. **id**: タイトルがなければ ID を表示
4. **キー数の要約**: どれもなければ「（n項目）」

つまり `name` や `title` という名前で項目を持つ文書はそのまま読みやすく表示され、独自の項目名（例 `件名`）をタイトルにしたい場合だけスキーマに `role: title` を1行足せば、参照候補から一覧・畳み込みヘッダまで**全画面に一括で**効きます。

補足:

- **タイトルの借用**: 要素自身にタイトルがなくても、同じ論理IDの他出現（定義側の文書）にタイトルがあれば画面上はそれを借りて表示します。id しか書かない写像行・詳細行の畳みヘッダでも「FLD-001 ユーザー名」のように読めます。
- **サブタイトルの併記**: 畳み込みヘッダは「ID タイトル — サブタイトル（n項目）」の形で、`role: subtitle`（または description / summary）も表示します。
- **親ノード情報**: エンティティページの各出現カードには、その出現がどの親要素（テーブル定義・一覧など）の配下にあるかが「親: …」として表示されます。

### 段階的詳細化の規約（1:1 の詳細化と 1:N の分裂）

工程をまたいで文書を詳細化していく運用では、次の2つの規約を使い分けます。

- **1:1 の詳細化 = 同一ID**: 同じ論理要素を別文書でさらに詳しく書くときは、**同じIDをそのまま使います**（例: 画面一覧の `SCR-LOGIN` と画面詳細文書の `SCR-LOGIN`）。出現はID横ぐしビュー・ビューグリッドで1行に結合され、詳細文書の存在は出現ベースのカバレッジルール（`detailIn`。§4）で機械検証できます。
- **1:N の分裂 = 新しいID＋親への参照**: 1つの要素が複数の要素へ分かれて実装されるときは（例: データモデルの1エンティティ→単票・明細の2テーブル）、分裂先に**新しいID**を与え、`type: ref`（`relation` で種別を宣言。例 `derives`）で**親へ逆リンク**します。親側のスキーマは被参照の制約（`constraints` の `dir: in` ＋ `expect: exists`、または関係レジストリの `cardinality: {inMin: 1}`）で「全エンティティが1つ以上のテーブルから実装されること」を検証でき、ビュー定義の**バックリンク列**（`backlinks`。§5）で親→分裂先の一覧を表示できます。

sample-workspace の `models/00-data-model.yaml`（エンティティ）と `tables/`（テーブル設計。`entity` 項目で親へ逆リンク）、ビュー定義 `_views/entity-tables.yaml` がこの規約の実例です。

スキーマに**エンティティ型宣言**（`entity:`。§4）を書くと、どの出現がそのIDの「定義（誕生）」かを機械が知り、参照ジャンプ・タイトル解決が定義出現に安定します。定義出現の欠落・競合は検証が警告します。

### 参照候補の絞り込み

`type: ref` ではID体系と探索範囲を独立して指定できます。

```yaml
type: ref
idPatterns: ["ACTOR-*", "ROLE-*"]
scope:
  schemaIds: [system-concepts, actor-detail]
  documentIds: [system-overview]
```

`idPatterns`、`schemaIds`、`documentIds`の各配列内はOR、異なる条件間はANDです。IDパターンは大文字・小文字を区別します。条件は候補表示だけでなく参照検証にも適用されます。ID自体が存在しても条件外なら検証エラーになります。条件を省略するとワークスペース全体が対象です。

### 参照（リンク）の認識

- スキーマで `type: ref` と定義された位置の値（配列要素含む）
- スキーマ外のキーに対する**命名規約ヒューリスティクス**:
  - キー名 `ref` または `*_ref` のスカラー値
  - キー名 `refs` / `*_refs` / `depends_on` / `relates_to` 配下のスカラー配列

### リンクの機能

- **ジャンプ**: ref フィールドの「→」ボタン（クリックで「定義へ移動（ファイル）／エンティティページで開く」を選択）、右パネル「関係」タブの参照クリックで定義元ファイルを開き、該当要素をハイライト表示＆自動スクロール
- **戻る・進む**: ジャンプやファイル切替のあと、ツールバーの「←」「→」ボタン（`Alt+←` / `Alt+→`）で移動前の位置へ戻る／やり直すことができます。文書はファイルとハイライト位置、ID横ぐしビュー・ビューグリッドから飛んだ場合はそのビューと選択中IDが復元されます。**レールでのスペース切替（編集・台帳・実行・設計）と台帳のタブ切替も履歴の対象**で、横ぐしビューでのID切替、ビューグリッドのビュー切替、検証パネルからのジャンプと同様に1段ずつ戻れます（同じ場所の再選択は積まれません。履歴は最大50件。ワークスペース切替でクリアされます）
- **補完**: ref フィールドのドロップダウンで、IDパターン、スコープ、入力文字列（ID・タイトル部分一致）により候補を選択
- **ID入力支援**: id フィールドのドロップダウンに「**採番**」（既存IDと `pattern` / entity 宣言から次の連番を提案。例 `TASK-003`）と既存IDの補完（選ぶと同一IDの出現＝別文書での詳細化・写像行の入力になる）が出ます
- **未解決検出**: 索引にも編集中ドキュメントにも存在しない ID への参照は、赤枠＋検証パネルにエラー表示
- **バックリンク**: 開いているファイルの ID を参照している箇所を「関係」タブの被参照に一覧表示。参照を書いた要素のID・タイトル（表示解決の結果）を主表示にし、クリックで参照元へジャンプ
- **出現**: 右パネル「出現」タブに、文書ルートIDと同じ論理IDの全出現（段階的詳細化の各文書）とカバレッジ充足を表示。「ID横ぐしビューで全出現を編集」で横ぐしビューへ展開
- **ID 検索**: 検索・コマンド（`Ctrl+K`）から ID・タイトルで横断検索してジャンプ

> **索引と「見たまま判定」**: 索引の正はディスク上のファイルで、ワークスペースを開く、再読込、保存、外部変更検出、一括編集のタイミングで更新されます。そのうえで**画面上の参照解決・被参照・カバレッジ・検証・ID検索は、未保存の編集を重ねたオーバーレイ索引（「見たまま判定」）で行われ、保存前でも追随します**。CLI・エージェントなどのヘッドレス経路はディスク索引基準のままです。

## 7. 検証

右パネルの「検証」に以下が表示されます。指摘のクリックで「何ができるか」の選択メニューが開き、「エラー箇所へ移動」（ファイル・パス表示つき）を先頭に、整合検証の指摘なら来歴のアクション（導出規則へ・入力値へ・導出値を適用）、関連IDつきなら各定義へのジャンプが並びます。

スコープは「**この文書／全体**」を切り替えられます。「全体」は索引対象の全文書を未保存の編集込み（「見たまま」）で検証し、ファイル別にまとめて表示します（ワークスペース全体のエラー0確認に使えます）。

- 必須項目の未設定（`required: true`）
- 型不一致（int / number / boolean / object / array / map）
- `enum` の選択肢外の値
- 非アクティブな case のキーの残存（`cases`。有効になる enum 値を案内。重大度は `unknownFields` に従う）
- `date` の形式逸脱（警告）
- `id` / `string` / `text` の `pattern` 逸脱（IDフォーマットの強制を含む）
- 未解決の参照
- ID の重複（同一ファイル内。異なるファイルの同一IDは許容）
- カバレッジルールの不足（被参照数または詳細文書の出現数が `coverage` の要件に満たないID）
- スキーマファイルの構造、未知の型、フィールドキー重複、array/mapの子定義不足、未解決の `$ref`
- スキーマの型変更後の残留値は、フォーム側に修復UI（「値を消す／配列・スカラーに変換」）が出ます

## 8. 外部変更・競合・安全性

- ワークスペース内のYAMLをOSのファイル監視（WatchService）で監視します。監視を開始できない環境では約1秒間隔のポーリングに自動フォールバックします。
- 未編集のファイルが外部変更された場合は自動的に再読込します。
- 未保存文書が外部変更された場合は自動上書きせず、競合バナーを表示します。
- 競合時は「ディスク版を読み込む」または「編集内容を維持」を選択できます。
- 未保存文書を含む名前変更・削除・一括編集は拒否されます。
- ファイル削除は確認ダイアログを経由します。

## 11. AIによる作成支援

スキーマが適用された文書では、OpenAI / Anthropic（Claude）/ Azure OpenAI（AI Foundry）の API を使って内容のたたき台を生成できます。入口は次のとおりです。

- **フィールド単位**: フォームの各フィールドラベル横の ✨ アイコン
- **配列への候補追加**: 配列エディタの「AIで候補追加」（既存項目を残して追加／配列全体を置き換えを選択可能）
- **文書全体**: 文書ヘッダーの「AIで作成」ボタン（`_document` メタデータは保持されます）
- **出現単位**: エンティティページのアスペクトカード・出現カードのヘッダ ✨「この出現をAIで作成」。そのアスペクトが所有するフィールドだけを生成し、生成しなかったキー・スキーマ外のキー・ID はそのまま保持されます（キー単位のマージ適用）
- **新規作成のたたき台**: ファイルツリーの「YAML ファイルを作成」とビューグリッドの「新規行」ダイアログの「作成後にAIでたたき台を生成」チェックボックス、グリッドの詳細「作成」ボタン横の ✨。ファイルを作成して開いた直後に、その文書を対象としたAI生成ダイアログが続けて開きます。生成はキー単位のマージで、作成時に設定されたID・`_document` は変更されません（スキーマが適用されないファイルでは通常の作成のみ行われ、ステータスバーで案内されます）

フィールド単位と配列への候補追加は、編集スペースのフォームだけでなく、**エンティティページ（台帳の「エンティティ」タブ）のアスペクトカード・出現フォームなど、同じフォーム部品を使う画面ならどこからでも**使えます。生成の対象と適用先は常に「ボタンを押したフォームの文書」で、適用結果はその文書の未保存編集として入ります（Undo可・保存は手動）。

流れは「指示を入力 → 生成 → プレビューで現在値と比較 → 適用」です。

- 生成結果は、対象フィールドのスキーマから変換した JSON Schema による構造化出力（Structured Outputs）で受け取るため、型・enum・必須キーがスキーマに準拠します（`map` 型を含む場合のみ構造化出力を無効化し、プロンプト指示によるJSON生成にフォールバック）。
- `cases` を持つ enum を1つ含むオブジェクトは、enum 値ごとの分岐（`anyOf`）に変換され、選択値と追加フィールドの組み合わせもスキーマで保証されます（`cases` を持つ enum が同一オブジェクトに複数ある場合は全 case フィールドの和集合で受けます）。
- `ref` 型フィールドは、`idPatterns`・`scope` で絞り込んだワークスペース内の既存IDを enum 制約として渡すため、存在しないIDへの参照が生成されにくくなります（候補が200件を超える場合は制約を省略し、プロンプト内の一覧のみ）。
- プレビューは現在値とAI提案の行単位差分表示で、提案を適用した場合のスキーマ検証結果（エラー・警告数）も表示します。適用は Undo 可能で、自動保存はされません。
- 生成中は「生成を中止」でキャンセルできます。
- **参考文書**: 同じスキーマが適用される他の文書を「書き方・粒度の手本」として一緒に送信できます。既定では更新日時の新しい順に最大3件が自動選択され、ダイアログのチェックボックスで選び直せます（候補の表示は関連文書とあわせて20件まで。1件あたり2万文字・合計12万文字を超える分は省略）。参考文書に未保存の編集がある場合は編集中の内容が送信されます。
- **関連文書**: エンティティページから開いた場合は、そのエンティティの出現・参照先・参照元の文書が「関連文書」として候補に並び、既定でこちらから最大3件が自動選択されます。関連文書は書き方の手本ではなく**内容の文脈**（事実関係の参照元）としてAIに渡され、生成内容が既存の記述と整合しやすくなります。文字数の合計上限（12万文字）は関連文書→参考文書の順に消費されます。
- モデルに送信されるのは、指示、現在の文書、対象フィールドのスキーマ、選択した関連文書・参考文書、ワークスペース内の既存ID（最大500件）です。
- 生成はエージェント実行と同じカーネル上で「1ターンで提出する特殊アクティビティ」として実行され、実行記録が `_runs/` に他のアクティビティと同じ形式で残ります（アクティビティID: `ai-generate`。適用自体は従来どおりダイアログのプレビュー→編集中文書への反映で、自動保存されません）。
- 実行記録にはデバッグ用に、実際に送信したシステム指示・プロンプト全文・応答スキーマとモデルの生出力が `exchange` 節として残り、`usage` には実測のトークン数が入ります。生成に失敗した場合も実行記録は書かれ（解析できない応答は生の本文ごと記録）、エラー表示に記録ファイルのパスが示されます。

接続設定:

- **プロバイダ**: OpenAI / Anthropic / Azure をダイアログで切り替えます。選択は端末の設定（Preferences）に保存されます。
- **APIキー**: ダイアログで入力するか、環境変数（`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `AZURE_OPENAI_API_KEY`）を設定します。キーはメモリ上にのみ保持され、ディスクには保存されません。
- **モデル**: 既定は OpenAI が `gpt-5.1`、Anthropic が `claude-opus-4-8`。Azure は**デプロイメント名**を指定します。変更はプロバイダごとに端末の設定へ保存されます。Structured Outputs 対応モデルが必要です。
- **Azure OpenAI / AI Foundry**: 「接続の詳細設定」でエンドポイント（例 `https://<リソース名>.openai.azure.com`）と APIバージョン（空なら v1 サーフェス）を設定します（環境変数 `AZURE_OPENAI_ENDPOINT` / `AZURE_OPENAI_API_VERSION` でも可）。認証は `api-key` ヘッダで行われます。
- **OpenAI互換エンドポイント**: OpenAI 選択時にベースURLを上書きすると、ollama / vLLM 等の互換エンドポイントも利用できます（環境変数 `OPENAI_BASE_URL` でも可）。
- **プロキシ**: 既定はシステム設定に従います。「接続の詳細設定」でプロキシなし／手動（ホスト・ポート）へ切り替えられ、Basic 認証（ID・パスワード）も指定できます。パスワードはAPIキー同様メモリのみ保持です。エンドポイント・プロキシ設定はフィールド生成とエージェント実行の両方に共通で効きます。
- **レート制限時の自動リトライ**: API がレート制限（429）や一時的なサーバーエラーを返した場合、待機して自動で再送します（プロバイダ指定の待機時間を尊重、最大3回・1回あたり最大60秒）。一括実行などで制限に達しても、実行が途中で失敗しにくくなります。リトライ中は進捗表示が一時的に止まって見えることがあります。それでも失敗する場合は、時間を置くか一括実行の `limit` を下げてください。

## 12. エージェントによるアクティビティ実行

定型化した仕事を「アクティビティ」として定義し、AIエージェントに委託できます。エージェントは探索（カタログ→骨子→本文）、複数文書への部分パッチ、横断検証を自律的に繰り返し、結果を**変更セット**として提出します。**原本は人間がレビューして採用するまで変更されません。**

### 定義の置き場所

| ディレクトリ | 内容 |
|---|---|
| `_agents/*.yaml` | エージェント定義: `id`・`persona`（性格・行動指針）・`rubric`（観点）・`model`（プロバイダ／モデルID）・`tools`（許可ツール分類） |
| `_activities/*.yaml` | アクティビティ定義: `id`・`agent`・`target.match`（対象glob）・`instruction`・`context.items`（コンテキストレシピ。§12）・`allowedFiles`／`allowedPaths`（書込許可）・`limits`（maxTurns等）・`gates.validation`・`trigger`／`chain`／`retry`／`approval`（自動実行）・`foreach`（一括実行。§12）・`meta`（§13） |
| `_evals/*.yaml` | 評価セット定義: ゴールデン入力と期待結果によるアクティビティの回帰評価（§13） |
| `_skills/*.yaml` | skill定義: 宣言型のインポート・エクスポート（§14） |
| `_views/*.yaml` | ビュー定義: 行×列の横断一覧（§5）。コンテキストレシピ（`context.items` の `kind: view`）でアクティビティの初期文脈にも開示できる |
| `_runs/` | 実行記録（自動生成。ターン・ツール呼び出し・質問・採否・トークン使用量・評価レポート）。デバッグ用の会話記録 `transcript` 節に、モデルへ送ったシステム指示・初期コンテキスト、モデルの本文テキスト、ツール呼び出しの引数と結果が全文で残る（1件2万字で打切り。委譲先エージェントの内部会話は対象外）。コンテキスト会計の `context` 節には、毎ターン再送される固定部（システム指示・ツール定義・指示・カタログ・ビュー等）の区分別の文字数・概算トークンと、送信ごとの入力トークン実測が残り、「どの宣言がいくらトークンを払わせたか」を確認できる（`usage.cachedInputTokens` はキャッシュ読取の内数） |

どちらも組込みスキーマ付きのYAML文書なので、本ツールのフォーム編集・検証がそのまま使えます（独自スキーマを `_schemas` に置けば上書き可能）。定義例:

```yaml
# _activities/review-concepts.yaml
id: review-concepts
name: システム構想レビュー
agent: reviewer                          # _agents/reviewer.yaml
target: { match: "01_requirements/**/*.{yaml,yml}" }
instruction: |
  actors / capabilities をレビューし、指摘を各文書の review_comments 配列に追記してください。
allowedFiles: ["01_requirements/**"]     # 書込を許可する範囲（省略時は全ファイル）
allowedPaths: ["review_comments*"]       # 書込を許可するパス（省略時は全パス）
limits: { maxTurns: 16 }
gates: { validation: error-free }        # 検証エラーが残る提出は拒否。点検系には no-new-errors
                                         # （既存エラーは許容し、この実行で増えたエラーだけ拒否）・none も選べる
```

### コンテキストレシピ（初期文脈の設計）

エージェントの入力トークンの大半は「毎ターン再送される初期コンテキスト」です。何をどれだけ最初に開示するかは、アクティビティ定義の `context.items` で**利用者が設計**します（**無指定の既定は開示なし**。カタログも明示宣言制）。項目は宣言順に開示され、実行記録のコンテキスト会計（`_runs` の `context` 節・レビュー画面の内訳）で「どの宣言がいくら払わせたか」を確認しながらチューニングできます。

```yaml
context:
  items:
    - kind: catalog                # 文書カタログ（match で対象を絞る）
      match: "00-requirements/*"
    - kind: related                # 対象IDの出現・参照・被参照の軽量なまとめ（related ツールと同形式）
      id: "{target}"
      when: has-target             # 対象の指定がある実行だけ開示
    - kind: entity                 # 対象エンティティの全体像（read_entity ツールと同形式。related の上位互換）
      id: "{target}"
      when: has-target
    - kind: sample                 # 同スキーマの既存文書N件（記述粒度の手本）
      schema: usecase
      count: 1
    - kind: view                   # 横断グリッドの解決結果
      view: usecase-list
      rows: "{target}"             # 行IDのパターンで絞る（プレースホルダ可）
      columns: [機能名, 機能説明]    # 列ラベルで絞る（省略時は全列）
      budgetChars: 4000            # 超過は決定的に打切り
    - kind: doc                    # 指定文書の全文（path で一部だけも可）
      file: todos/10-screens-list.yaml
    - kind: phase                  # 対象文書のフェーズ状態（段階的詳細化）
    - kind: graph                  # ID関係グラフの経路トラバース（多段）
      start: "{target}"
      steps:
        - emit: summary                            # 起点自身（責務定義書内の機能ノード等）
        - { follow: out, via: actor, emit: full }  # actor 参照を辿ってアクター定義の全文まで
```

- **graph（経路トラバース）**: `steps` は連鎖で、各ステップは前ステップの到達ノードから辿ります（`follow: out`＝参照を辿る／`in`＝被参照を辿る。`relation`・`via`・`schema` で絞り込み、`emit` で開示粒度を選択、`limitPerHop` 既定10）。エージェントも同じ語彙の `traverse` ツールを実行中に使えます。レシピに固定する前に CLI `traverse` で試せます（§16）
- **プレースホルダ**: `rows` / `file` / `path` / `id` / `start` には `{target}`（一括実行の対象ID等）・`{id}`・`{file}` などの対象値を書けます。値は `foreach`（§12）の各項目から供給され、解決できないプレースホルダが残る項目は開示されません（対象なしの実行で `{target}` 項目が黙って外れる、が意図した動きです）。
- **開示条件 `when`**: `always`（既定）／`has-target`（foreach の対象値または追加指示がある実行のみ）／`no-target`。「対象が指定された実行では全量ビューを載せない」を宣言で表現できます。
- **予算 `budgetChars`**: 項目ごとの文字数上限。超過は「…（予算 n 文字で打切り）」で決定的に切られます。全文系（doc / related / entity / sample）は無指定でも既定8,000字が掛かります。
- **旧語彙からの移行**: `context.include` / `context.views` は廃止されました（定義エラーになります）。`include: [catalog]` → `items: [{kind: catalog}]`、`views: [x]` → `items: [{kind: view, view: x}]` が等価な書き換えです。旧既定（カタログ自動開示）は引き継がれないため、カタログが必要なら明示してください。
- **prompt caching**: Anthropic 使用時は、システム指示・ツール定義・会話履歴の前方が自動でキャッシュされ（2ターン目以降はキャッシュ読取＝課金が大幅に下がる）、効果は実行記録の `usage.cachedInputTokens` で確認できます。

### プロバイダ・モデルの決まり方

実際に使われる接続先は **エージェント定義の `model:` が最優先**で、未指定の項目だけ「手動実行」タブの選択値で補われます。「AI接続」欄には常に**この実行で実際に使われる**プロバイダ・モデルが表示され、APIキーもそのプロバイダのものを入力します（例: エージェント定義が `provider: anthropic` を指定していれば、OpenAI を選んでいても Anthropic のキーが必要です）。

### 実行の流れ

1. レールの「実行」スペース →「手動実行」タブでアクティビティを選択（追加指示も可能）して「実行」
2. 実行中はターンごとの行動（探索・パッチ・検証）が流れ、エージェントからの**質問**には受信箱・実行タブのカードで回答できます（モーダルではないため、文書を確認しながら回答できます）。いつでもキャンセル可能。**実行中に他のスペースへ移動しても実行は継続**し、状態はステータスバーに表示されます
3. 終了すると**変更セットレビュー**画面になり、ファイル単位で採用／却下を選べます。採用の組み合わせを変えるたびに再検証され、参照整合の破れが警告されます
4. 「選択した変更を適用」で原本に書き込み（適用は Undo 不可ですが、適用前と同じ変更セットが `_runs/` の記録から辿れます）

### 安全性

- エージェントの読み書きはツール経由のみで、書込は `allowedFiles`／`allowedPaths` の範囲かつ予約ディレクトリ（`_schemas` `_agents` `_activities` `_evals` `_skills` `_views` `_runs`）以外に制限されます（定義ディレクトリはメタアクティビティ §13 でのみ提案可能）
- 探索ツールにはビュー参照（`read_view`）が含まれ、複数文書に散らばる同一IDの情報を、原本上の座標（file / path）つきの一覧として取得できます。`rows`（行IDパターン）・`columns`（列ラベル）で必要な行・列だけに絞れます。文書ビュー（`kind: document`。§5）は `file` で対象文書を指定して被参照表を取得できます（適用対象が1文書なら省略可）。コンテキストレシピ（`kind: view`。行・列の絞り込み可）で初期文脈として開示することもできます
- ID横断は2段構えです。`related` は隣接の軽量確認（主要フィールドの要約・フェーズ状態・参照・被参照を1回で。被参照は既定20件打切り＝`limit` 引数で拡張）、**`read_entity`** は対象を深く理解するための**エンティティ全体像**（エンティティページのAI版。アスペクト合成＝出現ごとの所有フィールドと原本座標（そのまま `apply_patch` の対象にできる）・両方向の関係ラベル・カバレッジ充足を1回で返す）です。`list_documents` のカタログにもフェーズ状態が付きます（`match` 引数で絞り込み可）。コンテキストレシピ（`kind: phase` / `kind: entity`）で、フェーズ状態や対象エンティティの全体像を最初から初期文脈に含めることもできます
- **参照の名前解決**: `read_node`（およびレシピの `doc` 項目）の出力末尾には「参照の解決」——そのノード配下の参照IDを `ID = 名前 [定義元ファイル]` で列挙したフッタ——が付き、ビューのセルでも参照値は `ID（名前）` と注記されます。「ACT-001 が誰か」を確かめるためだけの追加読取りが不要になります（未解決IDは（未解決）と明示）
- 提出には検証ゲート（既定: エラー0）があり、変更が壊す参照（改名の未修正参照元など）はステージング外のファイルでも検出されます
- ターン数・トークン・時間の上限があり、上限到達時も作業は未提出ドラフトとして保全され、レビュー画面から引き継げます
- 文書の内容はエージェントへの指示として扱われません（データとして扱う規範をシステムプロンプトで明示）

### 自動実行（トリガ・連鎖・自動承認）

実行スペースの「自動化」タブで監視を有効化すると、アクティビティ定義の `trigger` に従って自動起動します。実行は常に1件ずつ（直列）で、キュー・履歴・ログを同じタブで確認でき、「停止」でいつでも全消去・中断できます。承認待ちの変更セットは**受信箱**に届き、レール・ステータスバーのバッジで気づけます。

```yaml
trigger: { type: on-change, match: "requirements/**", debounceSeconds: 30 }
# type: manual（既定）… 手動起動のみ
#       on-change      … 対象ファイルの更新後、debounceSeconds 静止してから起動
#       on-invalid     … 更新されたファイルに検証エラーがあるときだけ起動
#       schedule       … everyMinutes ごとに起動
chain:                       # 実行後に連鎖起動（循環・深さ5は自動停止）
  rules:                     # 出力値による分岐（上から評価し、最初に一致した then へ。省略可）
  - when: { outcome: success, noteContains: 重複 }   # 条件はAND: outcome（success/failure/any）/
    then: dedupe-issues                              # changedFiles（採用変更のglob）/ minChangedFiles / noteContains
  onSuccess: file-issues     # どのルールにも一致しないときのフォールバック
  onFailure: notify
retry: { maxAttempts: 2 }    # 失敗時、理由をフィードバックして再実行（同一失敗の繰り返しは打ち切り）
approval: auto               # 自動適用（下記の条件つき）。既定は human（承認待ち）
```

- **`approval: auto` の安全条件**: 提出ゲート通過＋書込スコープ内＋対象がエディタで**編集中でない**こと。条件を欠くと自動でも「承認待ち」に降格します。人間の編集と自動実行が衝突しない排他がこれに当たります。派生スキーマ（§4）の**導出元文書**への変更を含む場合も、検証ルールが無人で変わることを防ぐため常に承認待ちへ降格します。
- **巻き戻し**: 自動適用は適用前の原文を実行記録（`_runs`）へバックアップし、`./gradlew runCli -q --args="revert <workspace> _runs/xxx.yaml"` で復元できます（適用後に更に変更されたファイルは競合として拒否。`--force` で上書き）。
- **承認待ちの耐久性**: 変更セットは `_runs/xxx-changeset.yaml` にも保存されるため、アプリを閉じても後から `apply` コマンドで適用できます。
- **自己変更では再発火しない**: エージェントが適用した変更で自分の on-change が再度発火することはありません。
- **エージェント同士の相談**: エージェントは `delegate` ツールで別のエージェント（例: レビュー担当）へ読み取り専用の相談ができ、ドラフト（ステージング）を見せて所見を受け取れます。編集・提出は依頼元だけが行います。

CLIからも実行できます: 単発は `agent`、常駐監視は `watch`（`--once` で1回だけ判定・消化）。`./gradlew runCli -q --args="watch <workspace>"`（定義一覧は `activities`。APIキーは環境変数から）。

### 一括実行（foreach: 同一アクティビティの連続実行）

「1実行=1文書」のアクティビティを対象違いで連続実行し、複数の文書を一気に整備できます。アクティビティ定義に `foreach`（対象の列挙）を宣言すると、手動実行タブに「一括実行（対象を選択）」ボタンが現れます。押すと対象の一覧が**チェックボックス付き**で表示され（既定は全選択。全選択／全解除も可能）、選択した対象だけが1件=1実行として自動化キューへ投入されます（自動化タブで「自動実行」を有効にすると直列に消化。項目の失敗は後続の項目を塞ぎません）。

```yaml
foreach:
  source: view             # 列挙元: view / issues / search / files / ids / query
  view: usecase-list       # source: view … ビューの行を対象にする
  where: detail-missing    # detail-missing（詳細文書が未作成の行のみ。既定）/ all（全行）
  as: "対象: {id}"          # 1件ごとの追加指示テンプレート（{id} {title} {file} {path} {message} 等）
  limit: 10                # 1回の投入で展開する上限（既定 20）
# source: issues … 検証の指摘ごと（severity: error / warning、match で対象ファイルを絞る）
# source: search … 検索ヒットごと（text / pathGlob / refTo / unresolved / schemaIds / match）
# source: files  … match（glob）に一致する文書ごと
# source: ids    … idPattern（× schemaIds）に一致する論理IDごと
# source: query  … グラフパターン照合（ビューのクエリ行と同じ語彙）の束縛行ごと。
#   query: { match: [...], where: [...] } を宣言し、as やコンテキストレシピから
#   束縛名で値を参照できる（{scr}=そのID・{scr_file}=定義出現のファイル。{id} 等は先頭束縛）
```

- 対象の列挙は起動時に1回だけ・`limit` 件まで。**「次の対象選び」はLLMではなく機械が行い**、各実行には対象を明示した追加指示が注入されます（アクティビティ本体の指示・権限・ゲートはそのまま）。
- `trigger: manual` のアクティビティ専用です（トリガ・連鎖など自動起動からの展開は不可）。
- 承認は通常どおり働きます: `approval: human`（既定）では項目ごとに承認待ちが受信箱へ届きます。
- CLI では `agent <workspace> <activity> --foreach` が同じ列挙を直列に一括実行します。`--apply` 併用時は1件ごとに適用するため、後続の実行から先行の成果が見えます（省略時は変更セットの表示のみ）。

## 13. 自己改善（メトリクス・評価セット・メタアクティビティ）

エージェント運用の品質を測定し、定義の改善をツール内で回すための機能群です。実行スペースの「計測・評価」タブで行います。

### 実行メトリクス

`_runs` の実行記録から、アクティビティ別に**提出率・採用率・却下ファイル率（部分採用で却下された割合＝人間による修正量の代理指標）・自動適用と巻き戻し・平均ターン・トークン**を集計します。実行のたびに追加の記録は不要で、過去の実行記録もそのまま集計対象です。CLI: `metrics <workspace> [--activity id]`。

### 評価セット（アクティビティの「テスト」）

`_evals/*.yaml` に**ゴールデン入力と期待結果**を定義すると、アクティビティを回帰評価できます。評価は**ワークスペースの一時コピー（サンドボックス）上で実行**されるため、原本は変更されません。レポートは `_runs/eval-*.yaml` に保存されます。

```yaml
# _evals/review-eval.yaml
id: review-eval
activity: review-concepts        # 評価対象のアクティビティ
variants:                        # 省略可: A/B比較（モデル・エージェント・追加指示・文脈レシピの差し替え）
- name: base
- name: strict
  instruction: 指摘は最大3件に絞ってください。
  # model: { provider: anthropic, id: claude-opus-4-8 } / agent: 別エージェントID も指定可
- name: lean-context             # 文脈レシピの差し替え（§12 と同じ items 書式。空 = 開示なし）
  context:
    items:
      - kind: catalog
cases:
- id: vague-actor-is-flagged
  setup:                         # ゴールデン入力: サンドボックスへ上書き・作成するファイル
  - file: 01_requirements/01-system-concepts.yaml
    content: |
      （意図的に曖昧な定義を含むYAML全文）
  expect:                        # 宣言的な期待結果（すべて満たせば合格）
    status: submitted            # submitted（既定）/ aborted / limit / error / any
    errorFree: true              # 終了時点の検証エラー0
    changedFiles: ["01_requirements/**"]   # 各globに1件以上の変更が必要
    unchangedFiles: ["03_designs/**"]      # マッチする変更があれば不合格
    content:                     # 結果（ステージング）の内容チェック
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, exists: true }
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, contains: ACTOR-USER }
```

期待結果を「出力文字列の完全一致」ではなく構造条件で書くのは意図的な設計です。モデルの揺らぎに対して壊れにくく、**良い合格条件を書くこと自体が業務設計（ハーネスエンジニアリング）** になります。CLI: `eval <workspace> <eval-id>`（引数なしで一覧）。

レポート（`_runs/eval-*.yaml`）には変異別の合格率・ターン・トークン（キャッシュ読取の内数込み）とケース別のトークンが記録されます。variants の `context` 差し替えと組み合わせると、**コンテキストレシピの絞り方を「合格率×トークン」のデータで選べます**（絞りすぎると探索ターンが増えて逆にコストが増える、といったトレードオフの検出。§12）。

### メタアクティビティ（定義の改善提案）

アクティビティ定義に `meta: true` を付けると、そのエージェントは `_agents` / `_activities` / `_evals` / `_skills` / `_views` の**定義文書そのものへの変更を提案**できます（例: 実行記録の傾向を踏まえた指示の改善、評価ケースの追加、エクスポート列の追加）。安全のための制約:

- **承認は human 固定**。`meta: true` かつ `approval: auto` は定義エラーになります（エージェントが自分の権限・挙動を変える変更は必ず人間が承認）
- `_schemas` と `_runs` への書込は meta でも**常に不可**
- ステージされた定義が**実際にパース可能であること**が提出ゲートに加わります（壊れた定義は提出できず、自己修正ループに入る）

「メタアクティビティで改善案を提案 → 評価セットで変異比較 → レビューで採用」という改善サイクルがツール内で完結します。

## 14. skill（インポート・エクスポート・テンプレート）

Excel・CSV等の現実の業務フォーマットと、YAML原本を接続する機能群です。設計スペースの「連携（skill）」から定義の一覧・作成と、取り込み・出力の実行を行います。変換は `_skills/*.yaml` に**宣言的に**定義します（例外は明示許可制のコード実行skill。後述）。

### インポート（表形式 → YAML原本）

xlsx / csv / json / markdown / docx（Word文書内の表）を、列マッピングでYAML文書群へ取り込みます。**取り込んだ時点からYAMLが原本**です。

```yaml
# _skills/import-issues.yaml
id: import-issues
kind: import
input: { format: xlsx, headerRow: 1 }        # xlsx / csv / json / markdown / docx
# docx は Word 文書内の表を読みます: input: { format: docx, table: 1 }（table = 何番目の表か。1始まり）
target: { file: "issues/{ID}.yaml" }         # {列名} が行の値で置換される（1行1文書）
mapping:
- { column: ID, path: id, required: true }
- { column: 件名, path: title, required: true }
- column: 状態
  path: status
  map: { 未着手: open, 対応中: in-progress, 完了: done }   # 値の変換辞書
- { column: 優先度, path: priority, type: int }            # 型変換（string/int/number/boolean/auto）
- { column: タグ, path: tags, split: "," }                 # 区切りで配列化
```

重要な性質:

- **既存文書はマップした項目だけ更新**されます（値が変わる場合のみ）。YAML側に追記した項目（レビューコメント等）は再インポートで消えません
- 適用前に**プレビュー**（作成／更新／変更なし／エラー）が出ます。適用は変更セット経由で、競合検出・検証ゲート・オール・オア・ナッシングが効きます
- エクスポートした帳票をそのまま再インポートすると**変更セットは空**になります（往復の無損失）

### エクスポート（YAML原本 → 派生成果物）

対象文書（glob）を行×列に展開し、xlsx / csv / markdown / json / html を再生成します（形式は出力ファイルの拡張子で決まります）。出力は**いつでも原本から作り直せる派生物**で、YAMLへの出力は定義段階で拒否されます。

```yaml
# _skills/export-issues.yaml
id: export-issues
kind: export
source: { match: "issues/**/*.{yaml,yml}" }  # rows: 配列パス を指定すると配列要素ごとに1行
output: { file: exports/issues.xlsx, sheet: 課題一覧 }
columns:
- { header: ID, path: id }
- { header: 件名, path: title }
- { header: タグ, path: tags, join: "," }
```

`source: { view: ビューID }` と書くと、`_views` のビュー定義（§5）を行×列の源にして「ビューで見えている表をそのまま帳票へ」出力できます（このとき `match` / `rows` / `columns` は書けません。1列目は行のID、バックリンク列は参照元IDの列挙になります）。

```yaml
# _skills/export-board.yaml
id: export-board
kind: export
source: { view: screen-catalog }
output: { file: exports/screens.html }
```

### コード実行skill（kind: run・明示許可制）

宣言型では書けない変換・定型手順のために、任意のコマンドを実行する skill を定義できます。**サンドボックス外への作用**のため、次の明示許可制が機械的に強制されます。

```yaml
# _skills/normalize.yaml
id: normalize
name: 正規化スクリプト
kind: run
run:
  command: [python, scripts/normalize.py]   # コマンドと引数
  workdir: .                                # ワークスペース相対（既定 "."）
  timeoutSeconds: 120
  writes: ["work/**"]                       # ワークスペース内への書込を宣言するglob
```

- **実行前に人間がコマンド内容と権限を承認**します（GUIは連携画面の承認ダイアログ、CLIは `--yes` フラグ）。承認なしに実行される経路はありません
- 承認は「承認した時点の定義内容」に紐づき、**定義が変わると失効**します（承認後の定義すり替え防止）
- エージェント・自動実行（トリガ）からは起動できません。メタアクティビティによる定義の**提案**は可能ですが、実行は常に人間の承認が必要です
- 実行後にワークスペース内の変更を検出し、`writes` 宣言外の変更を**警告**、予約ディレクトリ（`_schemas` 等）の変更を**重大な逸脱**として報告します（事後検査であり書込は防げないため、事前承認が前提です）

### テンプレートパック

`init` コマンドで、ユースケース別のスキーマ＋エージェント＋アクティビティ＋評価＋skill一式を新規ワークスペースへ展開できます（既存ファイルは上書きしません）。

```bash
./gradlew runCli -q --args="init my-workspace --template ledger"   # 課題台帳パック
./gradlew runCli -q --args="init my-workspace"                     # テンプレート一覧
```

`ledger` は「Excel台帳をインポート→YAML原本で運用（棚卸しアクティビティ・評価つき）→Excel帳票を再出力」の往復をそのまま体験できる雛形です。

## 15. 既知の制約

- **コメント・キー順・表記スタイルは「開く→編集→保存」の往復で保持されます**（引用符・リテラルブロック `|`・フロー表記 `[a, b]` を含む）。残る正規化は次のとおりです:
  - アンカー／エイリアス（`&x` / `*x`）は読み込み時に展開され、保存すると実体化します。
  - ブロックスタイルのインデントは 2 に正規化され、リストの `-` は親プロパティより一段深く配置されます。
  - リスト要素の**前の行**に書かれたコメントは、SnakeYAML エミッタの制約により初回保存時に `- # コメント` の形（`-` の後ろ）へ移動します。内容は失われず、以降の保存では安定します。
  - 編集で値を**置き換えた**箇所（AI適用・パッチなど）のコメントは可能な範囲で引き継がれますが、削除した項目のコメントは項目とともに消えます。
- 外部変更は OS のファイル監視（WatchService）で検出します。監視を開始できない環境（ネットワークドライブ等）では約1秒間隔のポーリングへ自動フォールバックします。未編集ファイルは自動反映され、未保存の編集がある場合は競合バナーからディスク版または編集中の内容を選択できます。
- 複数ドキュメント（`---` 区切り）の YAML は、フォーム編集・索引・検索が**先頭ドキュメント**を対象とします。後続ドキュメントは失われずに保持され、ソースタブで編集できます。
- 差分ビューは行単位の整列＋行内の文字単位強調です。Gitの履歴表示ではありません。
- 一覧ビューの一括編集はルート直下のスカラー項目のみが対象です（配列・オブジェクトの項目は選択しても上書きされません）。
- ビューグリッドの**行の増減**（新しいIDの出現）は索引基準のため保存まで反映されません（セルの値・編集は未保存でも即時反映されます）。セルの直接編集はスカラー値のみで、配列・オブジェクトはジャンプして個別フォームで編集します。

改善予定を含む実装状況の全体は [docs/FEATURES.md](docs/FEATURES.md) で管理しています。拡張方法（型の追加・横断ビュー・AIプロバイダの追加など）は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) の「拡張ポイント」を参照してください。

## 16. ヘッドレスCLI（エージェント向け基盤）

GUIを起動せずに、ワークスペースの探索・検索・部分変更・検証を実行できます。出力は機械可読なYAML（UTF-8）で、AIエージェントや自動化スクリプトからの利用を想定しています。

```bash
./gradlew runCli -q --args="catalog sample-workspace"                     # 文書カタログ（_document要約・スキーマ・ID数）
./gradlew runCli -q --args="outline sample-workspace path/to/doc.yaml"    # 骨子（キー構造・配列件数。長文は文字数表示）

./gradlew runCli -q --args="readiness sample-workspace --pending"         # 準備完了レポート（エンティティ単位にエラーを帰属。--pending で未完了のみ）
./gradlew runCli -q --args="checks sample-workspace --definitions"        # 展開後の検査の表示（語彙・定義の使用が、どんな基本の検査へ展開されたか。--definitions で定義と語彙の一覧も）
./gradlew runCli -q --args="hash sample-workspace path/to/doc.yaml"       # 変更セットの base に使う内容ハッシュ
./gradlew runCli -q --args="apply sample-workspace changeset.yaml --dry-run"  # 変更セットの適用（ドライラン）
./gradlew runCli -q --args="entity my-ws show SCR-001"                    # エンティティ全体像（アスペクト合成・関係・被参照。エンティティページ・read_entity と同じ合成）

# 変更系リファクタリング（エンティティ改名・統合・削除／ファイル移動／スキーマ・リファクタリング P25）は
# 新CLI（cli モジュール）へ移動しました（--apply なしは計画のプレビュー出力）:
./gradlew :cli:run -q --args="workspace refactor my-ws rename-entity SCR-001 SCR-100 --apply"

                                                                          # 他に merge-entity / delete-entity / move-field / align-order / rename-enum-value /

./gradlew runCli -q --args="revert sample-workspace _runs/xxx.yaml"       # 自動適用の巻き戻し
./gradlew runCli -q --args="metrics sample-workspace"                     # 実行記録の集計（提出率・採用率・コスト）

./gradlew runCli -q --args="migrate my-ws --ledger doc"                   # レガシー構成 → .yde 構成へ移行（README §3）
```

変更セット（changeset.yaml）は複数ファイルへの部分パッチの束です。`base` を指定すると、作成時点からディスクが変わっていた場合に適用を中止します（競合検出）。1件でも失敗すると全ファイル書き込みを行いません。`--require-valid` を付けると、適用後に検証エラーが残る場合も中止します。

```yaml
changes:
  - file: requirements/req-001.yaml
    base: 3f2a…                      # hash コマンドの値（省略可）
    ops:
      - { op: set,    path: title,        value: 新しいタイトル }
      - { op: insert, path: "tags[0]",    value: 重要 }        # 配列は挿入、マップは新規キー
      - { op: delete, path: obsolete }
      - { op: move,   from: "items[2]",   to: "items[0]" }
      - { op: rename, path: title,        to: name }           # キー改名（値・キー順・コメントを保持）
      - { op: reorder, path: details,     order: [id, name] }  # キー並べ替え（order を先頭に・残りは相対順。path 省略・空はルート）
```

パスは `items[2].title` 形式です。フロースタイル（`{ }`）内で `[` を含むパスは引用符で囲んでください。ルート（空パス）への操作はできません。
