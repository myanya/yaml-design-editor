# YAML Design Editor

Kotlin + Compose for Desktop + Material 3 製の**スキーマ駆動・汎用 YAML エディタ**。
YAML で設計項目（要求・設計・課題など）を管理するためのツールです。

- 外部のスキーマ定義（`_schemas/*.yaml`）に沿って、YAML ファイルごとに適切なフォームビューを自動生成
- スキーマがないファイルも**汎用ビュー**（再帰的なツリーエディタ）で編集可能
- ワークスペース内の **ID を横断的に索引化**し、参照（ref）のリンクジャンプ・補完・未解決検出・バックリンク表示に対応
- フォーム／ソース／差分の3モード編集、スキーマ検証、ID検索
- 外部変更の自動検出、ファイル／ディレクトリ操作、リサイズ可能な左右ペイン
- `_schemas` 専用のスキーマ設計画面と、`definitions` / `$ref` による再帰定義
- **スキーマ工学**: 既存文書からの**スキーマ推測**、スキーマ文書自体を検証・フォーム編集する**メタスキーマ**、テーブル定義書などから検証スキーマを導出する**派生スキーマ**（`derive`）
- Undo/Redo、保存ショートカット、未保存終了確認、復元されるペインレイアウト
- ライト／ダークを切り替えられるMaterial 3テーマ（選択状態は次回起動時に復元）
- ワークスペース一覧・絞り込み・一括編集、参照グラフ、**ID横ぐしビュー**、差分表示、コマンドパレット、最近開いたファイル
- 参照への**関係種別**（`relation`）付与と、「全要求は設計から参照される」等の**カバレッジルール**によるトレーサビリティ検証
- **AIによる作成支援**（OpenAI / Anthropic 連携）: フィールド単位・配列への候補追加・文書全体のたたき台生成。スキーマ準拠の構造化出力＋適用前プレビューと検証
- **エージェントによるアクティビティ実行**: `_agents`／`_activities` に定義した仕事（レビュー・改名・起票など）を、エージェントが探索→複数文書編集→自己検証のループで実行。提案は変更セットとして人間が部分採用
- **自動実行**: トリガ（ファイル更新・スケジュール・検証エラー）による自動起動、連鎖・リトライ、条件付き自動承認（適用前バックアップと巻き戻し付き）
- **自己改善**: 実行記録のメトリクス集計、評価セット（`_evals`）によるアクティビティの回帰評価とA/B比較、メタアクティビティによる定義改善の提案
- **skill（フォーマット適合）**: Excel / CSV / JSON / Markdown の宣言型インポート・エクスポート（YAMLが常に原本）、ユースケース別テンプレートパック（`init`）
- **ヘッドレスCLI**: GUIなしでカタログ・骨子・検索・部分パッチ（変更セット）・検証・エージェント実行・評価・入出力変換（エージェント連携の基盤）

## 1. ビルドと起動

要件: **JDK 17以上**。Gradle Wrapper（Gradle 9.3.0）を同梱しています。

```bash
cd yaml-design-editor
./gradlew run                                  # スタート画面から履歴・選択でワークスペースを開く
./gradlew run --args="/path/to/your/workspace" # 任意のワークスペースを指定して起動
```

配布物の作成:

```bash
./gradlew packageDistributionForCurrentOS # dmg / msi / deb
```

起動引数を省略すると**スタート画面**が表示され、最近開いたワークスペースの履歴（最大10件。アプリグローバルに保存）から選ぶか、「ワークスペースを開く…」でディレクトリを選択します（初回は `sample-workspace/` を開くボタンも表示されます）。開いた後もツールバーの「開く」やコマンドパレット（`Ctrl+K`）の「ワークスペースを切替」からいつでも切り替えられます（未保存の変更があれば確認ダイアログを挟みます）。

## 2. 画面構成

```
┌────────────────────────────────────────────────────────────────────────┐
│ 開く 再読込 │ 文書 一覧 グラフ 履歴 │ ID検索 Ctrl+K │ Theme │ ペイン切替 │
├─────────────┬──────────────────────────────────┬───────────────────────┤
│ ファイルツリー │ ファイル名 / スキーマ  Undo Redo 保存 すべて保存 │ 検証│参照│被参照 │
│ 新規・改名    ├──────────────────────────────────┤                       │
│ 削除・展開    │ フォーム │ ソース │ 差分             │                       │
│ ● 未保存      │ 構造化フォーム / YAML / 比較表示     │                       │
├─────────────┴──────────────────────────────────┴───────────────────────┤
│ ステータスバー                                                           │
└────────────────────────────────────────────────────────────────────────┘
```

- ファイル名横の `●` は未保存の編集を表します。ファイルを切り替えても編集内容はメモリ上に保持されます（「保存」「すべて保存」で書き出し）。
- 「フォーム」タブが構造化編集、「ソース」タブがテキスト編集です。ソース固有の「変更を反映」はテキストを内部のYAMLツリーへ取り込み、文書ヘッダーの「保存」はそのツリーをファイルへ書き出します。ソース編集中の `Ctrl+S` は反映と保存を続けて実行します。
- `Ctrl+S` で現在のファイルを保存、`Ctrl+Shift+S` ですべて保存、`Ctrl+Z` / `Ctrl+Y` で編集を元に戻す／やり直すことができます。
- 右ペインは「検証」「参照」「被参照」のタブで切り替えます。object、array、mapはフォーム内で折りたためます。畳んだ状態のヘッダには要素の要約（object は「ID タイトル（n項目）」、array は「n件: 先頭要素の要約, …」。§6 の表示解決）が表示され、開かなくても中身を判断できます。
- **閲覧専用モード**: ツールバーの目のアイコンで切り替えます。入力欄がテキスト表示になり、追加・削除・AIボタンが消えて表示密度が上がります（既定で折りたたみ＝拾い読み向き）。参照ジャンプ・バックリンクは閲覧行為としてそのまま使えます。ID横ぐしビューの埋め込みフォームやビューグリッドにも同時に効き、状態は次回起動時に復元されます。
- 左右ペインはドラッグでリサイズでき、開閉状態・幅・テーマ・閲覧専用モードは次回起動時に復元されます。
- ファイルペイン上部からYAML／ディレクトリの作成、名前変更、削除を実行できます。新規YAMLは配置先に適用されるスキーマから初期値を生成します。
- ウィンドウ終了時とワークスペース切替時には未保存確認を表示します。

### 操作の役割

- **変更を反映**（ソースタブ）: 編集中の文字列を解析して内部YAMLツリーへ取り込みます。
- **保存**（文書ヘッダー）: 内部YAMLツリーを現在のファイルへ書き込みます。コメント・キー順・引用符やフロー表記のスタイルは保持されます（詳細は「既知の制約」）。
- **ソース編集中の `Ctrl+S`**: 反映と保存を続けて実行します。
- **検索・置換**（ソースタブ）: 大文字小文字を無視した検索（件数表示）と「置換」「すべて置換」ができます。置換結果は「変更を反映」でツリーへ取り込みます。
- **構文ハイライト**（ソースタブ）: キー・文字列・数値・真偽値・コメント・`---` を色分け表示します。
- **Undo/Redo**: 内部YAMLツリーの編集履歴を最大100件保持します。
- **キー名の変更**（汎用ビュー）: キー名横の鉛筆アイコンから、順序と値を保ったまま改名できます。
- **複数ドキュメント（`---` 区切り）**: フォームでは先頭ドキュメントを編集し、後続ドキュメントは保持されて保存時にそのまま再出力されます。全ドキュメントを編集したい場合はソースタブを使います。

### ショートカット

| キー | 操作 |
|---|---|
| `Ctrl+S` | 現在の文書を保存。ソース編集中は反映後に保存 |
| `Ctrl+Shift+S` | ソースを反映後、未保存文書をすべて保存 |
| `Ctrl+Z` | 元に戻す |
| `Ctrl+Y` / `Ctrl+Shift+Z` | やり直す |
| `Ctrl+K` | コマンドパレット |
| `Alt+←` | 戻る（ジャンプ・ファイル切替の履歴） |
| `Alt+→` | 進む |

## 3. ワークスペースの構成

任意のディレクトリを「ワークスペース」として開きます。

```
my-workspace/
├── _schemas/            # スキーマ定義（このディレクトリ名は固定）
│   ├── requirement.yaml
│   └── design-item.yaml
├── requirements/        # 以下は自由な構成。*.yaml / *.yml が対象
│   ├── req-001.yaml
│   └── req-002.yaml
├── designs/
│   └── dsn-001.yaml
└── notes/
    └── memo.yaml        # スキーマにマッチしない → 汎用ビュー
```

各 YAML ファイルには、`_schemas/` 内のスキーマのうち `match`（glob）がワークスペース相対パスに最初にマッチしたものが適用されます（ファイル名の昇順で評価）。どれにもマッチしなければ汎用ビューになります。

## 4. スキーマ定義リファレンス

`_schemas/*.yaml` に 1 ファイル 1 スキーマまたは共通定義ライブラリで配置します。

```yaml
id: requirement                       # 安定したスキーマID（省略時はスキーマファイル名）
name: 要求                             # 表示用のスキーマ名
kind: document                        # document（既定）/ library（共通定義のみ）
description: |                         # スキーマ全体の説明（任意・複数行）
  要求事項を管理するスキーマです。
  要求の状態と関連を一貫した形式で記録します。
match: "requirements/**/*.{yaml,yml}" # 適用対象の glob（**, *, ?, {a,b} に対応）
root:                                 # ルートのフィールド定義（通常 type: object）
  type: object
  fields:
    - key: id
      label: 要求ID
      type: id
      required: true
      description: 論理要素を識別するID（同一文書内で一意）
    - key: status
      type: enum
      values: [draft, review, approved, deprecated]
      default: draft
    - key: relates_to
      type: array
      item:
        type: ref
        idPattern: "REQ-*"            # 利用者定義のID体系で候補を限定
        scope:
          schemaIds: [requirement]    # 安定したスキーマIDで探索範囲を限定
```

トップレベルの `description` には、スキーマの目的や対象を説明する複数行の文を任意で指定できます。スキーマ設計画面では複数行テキスト欄として編集できます。

### フィールド定義のプロパティ

| プロパティ | 説明 |
|---|---|
| `key` | 親オブジェクト内のキー名（ルート・配列要素では不要） |
| `label` | フォームでの表示名（省略時は `key`） |
| `type` | 下表の型（省略時 `string`） |
| `required` | `true` で必須。未設定は検証エラー |
| `requiredFrom` | フェーズ機構（後述）: このフェーズ以降で必須。`required` と併用不可 |
| `values` | `enum` の選択肢。文字列、または `{value, label, description}` のリッチ選択肢（後述） |
| `role` | 表示役割 `title` / `subtitle`（後述の表示解決）。このフィールドの値を要素の要約タイトル／サブタイトルに使う |
| `cases` | `enum` の値ごとに、親オブジェクトへ追加される兄弟フィールドを定義（後述） |
| `item` | `array` の要素定義（フィールド定義を再帰的に記述） |
| `value` | `map` の値定義（必須。フィールド定義を再帰的に記述） |
| `fields` | `object` の子フィールド定義のリスト |
| `unknownFields` | `object` のスキーマ外項目を `allow` / `warning` / `error` で扱う（省略時 `warning`） |
| `idPattern` / `idPatterns` | `ref` の参照先IDをglob（`*`, `?`）で限定。複数指定はOR |
| `scope.schemaIds` | 参照先を特定スキーマIDに限定。配列内はOR |
| `scope.documentIds` | 参照先を特定ドキュメントIDに限定。配列内はOR |
| `relation` | `ref` の関係種別（例 `implements` / `depends`）。解決可否には影響せず、表示とカバレッジ判定に使う |
| `default` | 「追加」「作成」時の初期値 |
| `description` | フォームに表示される説明文 |

### 型一覧

| type | フォーム表現 | 検証 |
|---|---|---|
| `string` | 1 行テキスト | required |
| `text` | 複数行テキスト | required |
| `int` | テキスト（整数変換） | 整数であること |
| `number` | テキスト（数値変換） | 数値であること |
| `boolean` | チェックボックス | 真偽値であること |
| `enum` | ドロップダウン | `values` に含まれること。`cases` で値ごとの追加フィールドを定義可能 |
| `date` | テキスト | `YYYY-MM-DD` 形式（警告） |
| `id` | テキスト＋重複警告＋被参照数 | 必須チェック、重複検出 |
| `ref` | テキスト＋候補ドロップダウン＋ジャンプボタン | 参照解決 |
| `array` | 要素の追加・削除・並べ替え | 要素ごとに `item` を再帰検証 |
| `map` | 任意キーの追加・削除＋型付き値エディタ | 各キーの値を `value` で再帰検証 |
| `object` | 枠付きのネストフォーム | `fields` を再帰検証 |
| `any` | 汎用エディタ（値の形に合わせた編集） | 検証しない（必須チェックのみ）。単一の型で表せない値の明示に使う。AI生成では `map` と同様に構造化出力が無効化される |

`object` / `array` / `map` は任意の深さでネストできます（例: サブ項目の配列の中に `id` を持たせて、サブ項目単位で参照させることも可能）。

`object` にスキーマ外のキーがある場合、既定ではそのキーの位置に警告を1件表示します。`unknownFields: error` ならエラー、`allow` なら通知しません。未知キーの配下はスキーマ検証およびID・参照索引の対象外とし、配下の各要素へ同じ問題を重複表示しません。ルートの予約項目 `_document` はこの検査から除外されます。

### 任意キーのMap

任意の文字列キーを持つ連想配列は `map` で定義します。`value` は必須で、Map内のすべての値に同じフィールド定義が適用されます。

```yaml
root:
  type: object
  fields:
    - key: inputs
      label: 入力
      type: map
      value:
        type: string
```

上記のスキーマでは、次のようなデータをフォームから追加・編集でき、各値が `string` として検証されます。

```yaml
inputs:
  username: ユーザ名
  password: パスワード
  email: メールアドレス
```

`value` には `object`、`array`、`ref`、別の `map` など、すべての型を再帰的に指定できます。

フォームではMapの件数と各キーが表示されます。「キーを追加」で任意のキーを作成し、値は `value` で指定した型のエディタで編集します。キーの重複と空文字は追加できず、不要なキーは行ごとに削除できます。Mapフィールド自体が未作成の場合は「Mapを作成」から空のMapを作成します。

`value` を省略したスキーマはスキーマ定義エラーになります。また、データ側がYAMLマッピングでない場合や、Map内の値が `value` の型に一致しない場合は検証エラーになります。

値をオブジェクトにする場合は、次のように定義します。

```yaml
- key: environments
  type: map
  value:
    type: object
    fields:
      - key: endpoint
        type: string
        required: true
      - key: enabled
        type: boolean
```

```yaml
environments:
  development:
    endpoint: http://localhost:8080
    enabled: true
  production:
    endpoint: https://example.com
    enabled: false
```

ルート定義に `type: map` を指定することもできます。

### enum のリッチ選択肢（label / description）

`values` の要素は文字列のほか、`{value, label, description}` の形で表示ラベルと説明を付けられます（混在可・後方互換）。

```yaml
- key: status
  type: enum
  values:
    - open                                       # 文字列だけの選択肢（従来どおり）
    - { value: in-progress, label: 対応中 }
    - value: closed
      label: 完了
      description: 対応が終わり、確認も済んだ状態
```

- **データ・検証・`cases` のキー・AI生成の制約は常に `value`** を使います。ファイルに保存されるのも `value` です。
- フォームのドロップダウンは `label` を表示し、現在の選択値に ✓ を付け、`description` を選択肢と選択後の欄外に表示します。`label` と `value` が異なる場合は候補に値も併記します。
- スキーマ設計UIの「選択肢」欄からも値・ラベル・説明を編集できます（ラベル・説明を空にすると文字列形へ戻ります）。

**選択肢をワークスペースのデータで管理したい場合**（選択肢自体に説明文書や参照関係が必要な場合、選択肢を文書として増やしたい場合）は、enum ではなく `type: ref` ＋ `scope` を使ってください。選択肢を1文書（または1要素）＝1IDの台帳として持ち、`scope.schemaIds` / `idPatterns` で候補を台帳に限定すれば、「ドロップダウンから選ぶ」体験のまま、選択肢の追加・説明・被参照の追跡が原本側の編集として管理できます（§6 参照候補の絞り込み）。

### enum 値ごとの追加フィールド（cases）

「選択した値によって設定できる項目が変わる」構造（判別共用体）は、`enum` フィールドの `cases` で定義します。`cases` のキーは `values` のいずれかの値、値はフィールド定義のリストで、その enum 値が選択されているときだけ**親オブジェクトのフィールド**として有効になります。

```yaml
- key: type
  label: 入力種別
  type: enum
  values: [text, radio, checkbox, date]
  cases:
    radio:
      - key: options
        label: 選択肢
        type: array
        required: true
        item:
          type: string
    checkbox:
      - key: options
        label: 選択肢
        type: array
        item:
          type: string
```

上記のスキーマでは、`type: radio` の要素だけが `options` を持てます（`radio` のときは必須）。

挙動の要点:

- **フォーム**: case フィールドは判別フィールド（enum）の直後に行として表示され、enum の値を切り替えると表示が追随します。切り替えで不要になったキーのデータは削除されず、「現在の選択では使用しないキー」として案内つきで表示されます。
- **ネスト**: case から追加するフィールドをさらに `cases` つきの enum にできます。選択された case を順に展開し、追加フィールドはすべて同じ親オブジェクトの兄弟フィールドとして扱います。
- **検証**: アクティブな case のフィールドは通常のフィールドと同様に検証されます（`required` はその case が選択されているときのみ有効）。非アクティブな case のキーがデータに残っている場合は「「options」は「入力種別」が radio / checkbox のときのみ使用できます」のような案内になり、重大度はそのオブジェクトの `unknownFields` ポリシー（既定 warning）に従います。
- **ID・参照の索引**: アクティブな case フィールド配下の `type: id` / `type: ref` は通常どおり索引化されます。非アクティブな case のキー配下はスキーマ外サブツリーと同様に走査境界となります。
- **制約**: `cases` は `enum` 型でのみ使用できます。case のキーは共通フィールドや、同一オブジェクト内の別の enum の `cases` と重複できません（同じ enum の複数の case での重複は可。上例の `options`）。これらはメタスキーマ検証で検出されます。
- **`$ref`**: 名前付き定義の enum に `cases` を持たせて `$ref` で参照できます。

### 名前付き定義と再帰スキーマ

共通または再帰的な構造は `definitions` に置き、`$ref` で参照できます。同じスキーマ内は定義名だけ、別のスキーマ・ライブラリは `スキーマID#定義名` で参照します。

```yaml
name: outline
match: "outlines/**/*.yaml"
definitions:
  node:
    type: object
    fields:
      - key: title
        type: string
        required: true
      - key: children
        type: array
        item:
          $ref: node
root:
  $ref: node
```

複数の工程別スキーマで共通する構造は、業務文書へ直接適用されない `kind: library` に切り出せます。library は `definitions` だけを持ち、`match` / `root` / `phases` / `coverage` は持ちません。

```yaml
# _schemas/_common.yaml
id: common
name: 共通フィールド
kind: library
definitions:
  column:
    type: object
    fields:
      - { key: name, type: string, required: true }
      - { key: dataType, type: enum, values: [string, number, boolean] }
```

```yaml
# _schemas/logical-table.yaml
id: logical-table
name: 論理テーブル
match: "tables/logical/**/*.yaml"
root:
  type: object
  fields:
    - key: columns
      type: array
      item:
        $ref: common#column
```

修飾参照した共通定義の内部で非修飾 `$ref` を使った場合、その参照は利用側ではなく共通定義を宣言したライブラリ内で解決されます。ライブラリIDの重複と未解決参照はロード時のスキーマ定義エラーになります。

`_schemas` 配下のファイルを開くと「スキーマ設計」タブが表示され、document / library の切替、名前付き定義、ローカル／横断参照を構造化UIで編集できます。document から library への変更では適用定義が削除されるため確認ダイアログが表示されます。

スキーマ設計画面には次の確認機能があります。

- **メタスキーマ検証**: 必須情報、フィールドキー重複、arrayの要素定義、enumの選択肢、`cases` の整合（enum型のみ・値の存在・キー衝突）、未解決の `$ref` を保存前に検出
- **プレビュー**: スキーマからサンプルYAMLを生成し、実際のフォームまたはYAMLとして確認
- **サンプル生成**: 生成したYAMLをクリップボードへコピー
- **適用対象**: `match` に一致するワークスペース内のファイルを一覧表示し、他スキーマとの競合も表示
- **フェーズ・カバレッジ**: スキーマ全体設定の `phases`（申告キー・フェーズ順序）と `coverage`（参照ベース／出現ベースの切替・重大度・判定開始フェーズ）も構造化UIで編集できます（後述のリファレンス参照）

スキーマファイルを保存すると、メタスキーマ検証結果は通常の右側「検証」パネルにも表示されます。

### カバレッジルール（被参照・詳細文書の必須化）

スキーマのルート直下に `coverage` を書くと、このスキーマが定義するIDへのトレーサビリティ要件を検証できます。ルールは2種類あります。

**参照ベース（`requiredBy`）**: 「条件を満たす参照を一定数以上受けること」。

```yaml
id: requirement
match: "requirements/**/*.yaml"
coverage:
  - idPattern: "REQ-???"        # 対象ID（省略時はこのスキーマの全ID）
    requiredBy:
      schemaIds: [design-item]  # 参照元文書のスキーマを限定（省略可）
      relation: implements      # 参照の関係種別を限定（省略可）
      minCount: 1               # 必要な参照数（既定 1）
    level: error                # warning（既定）/ error
    activeFrom: physical-design  # フェーズ機構（後述）: このフェーズに達するまで判定を保留（省略可）
    description: 全要求は設計項目から参照されること
root:
  ...
```

**出現ベース（`detailIn`）**: 「指定スキーマの文書にも同じIDが出現する＝詳細文書があること」。一覧と詳細を同一ID（1:1の詳細化。§6）で運用するとき、詳細未作成のIDを機械検出できます。

```yaml
id: screen-list
match: "screens/index.yaml"
coverage:
  - detailIn:
      schemaIds: [screen-detail]  # 出現先（詳細文書）のスキーマ（必須）
      minCount: 1                 # 必要な出現数（既定 1）
    level: warning
    description: 全画面は画面定義（詳細文書）を持つこと
```

1つのルールに `requiredBy` と `detailIn` は併用できません（メタスキーマ検証でエラー）。不足があると、IDを定義している文書の「検証」パネルに指摘が表示されます。判定は保存済みの索引に基づくため、参照・詳細文書を追加して保存すると反映されます。充足状況はID横ぐしビュー・ビューグリッドの状態列でも確認できます。

### フェーズ機構（工程に応じた検証の強弱）

要件定義→論理設計→物理設計のように、1つの論理要素（例: データモデルの1エンティティ）を複数の工程にまたがって記述していく運用では、後工程の項目を要件定義の時点で必須にすると検証エラーが大量発生してしまいます。`phases` を宣言すると、「この項目はこのフェーズ以降で必須」という**累積的な**必須化ができます。

```yaml
id: entity
match: "models/**/*.yaml"
phases:
  key: phase              # 現在フェーズを申告するルート直下のキー（省略時 phase）
  order: [requirements, logical-design, physical-design]
root:
  type: object
  fields:
    - key: phase
      type: enum
      values: [requirements, logical-design, physical-design]
      default: requirements
    - key: name
      type: string
      required: true       # 無条件必須（全フェーズで必須）
    - key: columns
      type: array
      requiredFrom: logical-design   # logical-design 以降で必須。requirements 段階の未記入はエラーにしない
      item: { type: object, fields: [ { key: name, type: string, required: true } ] }
    - key: physicalName
      type: string
      requiredFrom: physical-design  # 物理設計以降で必須
coverage:
  - requiredBy: { schemaIds: [table-design] }
    activeFrom: physical-design      # 物理設計に達するまではカバレッジ判定を保留する
    level: error
```

挙動の要点:

- 文書はルート直下の申告キー（既定 `phase`）で現在フェーズを記載します。未申告・未知の値は**先頭フェーズ**（最も緩い判定）として扱われ、未知の値には警告が出ます。
- `requiredFrom` は「そのフェーズ**以降**で必須」（累積的）。現在フェーズより先の工程に属する項目の未記入はエラーにならず、代わりに「検証」パネルにフェーズ別の記入進捗（例: `logical-design: 1/2 記入`）として表示されます。フェーズが進むと、過去に必須化した項目は引き続き必須のままです。
- `required: true` と `requiredFrom` は併用できません（メタスキーマ検証でエラー）。
- カバレッジルールの `activeFrom` は「IDを**定義している文書**の現在フェーズがそのフェーズに達してから判定する」という保留を表します。未到達の間は「フェーズ未到達」として区別表示され、検証エラー・警告にはなりません（ID横ぐしビュー・ビューグリッドの状態列も同様に区別表示します）。
- 文書の物理的な分割単位（1文書で全工程を書くか、工程ごとにファイルを分けて段階的詳細化するか）はどちらでも成立します。工程ごとに分けた運用では、後工程のスキーマだけ `requiredFrom` を使わず素の `required` で書いても構いません。

CLI `validate` の出力にも、`phases` を宣言したスキーマの文書には `phaseProgress`（フェーズごとの記入済み／総数）が付与されます。

### メタスキーマ（`_schemas` 文書の編集・検証・AI生成）

`_schemas/` 配下のスキーマ文書自体にも、組込みのメタスキーマ（ID `builtin-schema`）が適用されます。

- スキーマ文書を開くと「スキーマ設計」タブ（主要UX）に加えて「フォーム」タブが表示され、メタスキーマによる構造化フォームでも編集できます。文書ヘッダーの「AIで作成」でスキーマのドラフトをAI生成することもできます。
- 検証パネル・CLI `validate` はスキーマ文書をメタスキーマで検査します（例: `type` の値が選択肢外、`fields` は `type: object` のときのみ有効、`scope` のキー名間違い）。定義として読み込めない致命的な問題は従来どおりスキーマ読込エラーとして表示されます。
- 一般スキーマの `match` は `_schemas/` には適用されません（catch-all パターンの誤適用を防止）。メタスキーマを差し替えたい場合は、同じID（`builtin-schema`）のスキーマを `_schemas` に置くと上書きできます。
- エージェントの `_schemas` への書込禁止は従来どおりです（メタスキーマは編集・検証のためのもので、書込経路は増えません）。

### スキーマ推測（既存文書からのドラフト作成）

スキーマを書く前にYAML文書が既にある場合、既存文書からスキーマのドラフトを推測できます。

- **入口**: ファイルツリーで文書を選択して「スキーマ推測」ボタン（魔法の杖アイコン）、または CLI `infer-schema`。
- **推測の内容**: glob に一致する複数文書をマージし、①値の実例からの型推測（`int` / `number` / `boolean` / `date` / 長文は `text`）②参照の命名規約（`ref` / `*_ref` / `refs` / `depends_on` 等。§6 の参照認識と同じ規約）③小さく反復する値集合の `enum` 候補化 ④全文書に出現するキーの `required` 候補化 ⑤`id` キーの `type: id` 化 — を行います。構造が文書間で揺れるキーは `any` になります。
- **仕上げ**: 生成された `_schemas/<ID>.yaml` はドラフトです（先頭にその旨のコメントが付きます）。メタスキーマ検証・スキーマ設計画面で型や必須を確認・調整し、サンプルYAML生成（プレビュー）を逆方向の検算に使ってください。既存のスキーマファイルは上書きしません。

### 派生スキーマ（`derive`: 文書から検証スキーマを導出する）

テーブル定義書のような「実質スキーマの文書」がある場合、その文書を二重にスキーマへ書き写す代わりに、`derive:` を宣言したスキーマ（テンプレート）が導出元文書から検証スキーマを**ロード時にコンパイル**します。

```yaml
# _schemas/record-template.yaml
id: record-template
name: レコード検証
derive:
  from: "tables/**/*.{yaml,yml}"     # 導出元文書（テーブル定義書）の glob。予約ディレクトリは不可
  # each: entities                   # 1文書内の配列要素ごとに導出する場合は配列パスを指定（省略時は文書ルート）
  id: "record-{id}"                  # 導出スキーマのID。{パス} は導出元要素の値で置換される
  name: "{title} レコード"
  match: "records/{id}/**/*.{yaml,yml}"  # 導出スキーマの適用先（`,` を含む {a,b} は glob 構文として残る）
  fields:                            # 写像の語彙（path / map / default）は skill の列マッピング（§14）と同じ
    source: columns                  # フィールド一覧にする配列のパス
    key: name                        # 各要素のこの値 → フィールドのキー
    label: label                     # 任意: 表示ラベル
    description: note                # 任意: 説明
    required: required               # 任意: 必須（真偽値）
    type:                            # 任意: 型の写像（省略時はすべて string）
      path: dataType
      map: { varchar: string, bool: boolean, number: int }
      default: string
root:                                # 任意: 全導出スキーマ共通のフィールド（先頭に合成される）
  type: object
  fields:
    - { key: id, type: id, required: true }
```

- 上の例では `tables/tbl-task.yaml`（`id: TBL-TASK`、`columns` 配列）から、`records/TBL-TASK/**` に適用されるスキーマ `record-TBL-TASK` が導出されます。テーブル定義書に列を足して保存すると、レコード文書は**すぐに新しいルールで再検証**されます。
- `derive` を宣言したスキーマ自身はどの文書にもマッチしません（`match` は書けません）。導出スキーマはファイルとしては存在しない読み取り専用の成果物で、`coverage` / `phases` / `definitions` はテンプレートから引き継がれます。
- 導出できない要素（プレースホルダ値の欠落・フィールドキーの欠落・IDの重複・未知の型）は、理由付きでスキーマ読込エラーに報告されます（他の導出は継続します）。
- 導出元文書は通常の文書なので、エージェントの変更セットが（承認を経て）検証ルールを変えることがあります。このため**導出元文書への自動適用（`approval: auto`）は常に承認待ちへ降格**されます（§12）。

## 5. ワークスペース横断機能

ツールバーのビュー切替から、次の横断ビューを利用できます。

- **一覧ビュー**: ID、タイトル、状態、担当、種別、ファイルを表形式で表示し、文字列・種別・状態で絞り込み
- **一括編集**: 選択した複数ファイルのルート直下のスカラー項目を確認後に一括更新。対象キーはワークスペースの文書に現れるルート直下のスカラーキーから選択（`id`・`_document` などの予約キーと、配列・オブジェクト値の項目は対象外）
- **参照グラフ**: ワークスペース内の参照関係を力学配置（つながりの近いノードが寄る）で全件描画し、ドラッグでパン・「＋／－」でズームできます。参照先ID（ノードまたは一覧）をクリックすると定義へ移動します
- **ID横ぐしビュー**: 同一論理IDの全出現、その要素からの参照、被参照、カバレッジ充足を1画面に集約。各出現は`_views`定義を書かなくてもその場で編集できます（対象文書のスキーマに従ったフォーム。スキーマがない文書は汎用エディタ）。編集は通常のフォームと同じ経路（未保存●表示・Undo・保存がそのまま効きます）。ツールバーのハブアイコン、コマンドパレット、ID出現候補ダイアログの「横ぐしビューで表示」から開けます
- **ビューグリッド**: `_views/*.yaml` に定義した「行（論理ID）×列（各文書の項目）」の宣言的ビューを、**編集可能な一覧**として表示（後述）
- **差分**: 文書の「差分」タブで、ディスク上の保存済み内容と編集中内容を左右比較。変更行では行内の変わった箇所を文字単位で強調表示
- **最近開いたファイル**: ツールバーの履歴アイコンから直近12ファイルを再度開く。履歴はワークスペース単位で保存
- **コマンドパレット**: `Ctrl+K` で開き、ビュー切替、保存、ファイル検索、ID移動、ワークスペースの切替（履歴からの選択・ディレクトリ選択）をキーボード中心で実行

一括編集は対象に未保存文書が含まれる場合は実行されません。実行前には確認ダイアログを表示し、変更後は索引と画面を再読込します。

### ビューグリッドとビュー定義（`_views`）

段階的詳細化（同一IDを複数文書で詳細化する運用）では、「機能一覧」と「機能ごとの詳細文書」のように情報が複数ファイルへ分かれます。ビューグリッドは、`_views/*.yaml` の**宣言的なビュー定義**に従って、それらを1つの一覧に結合して表示・編集する機能です。ツールバーのグリッドアイコンから開きます。

- **行** = `rows.idPattern` に一致する**論理ID**。同じIDの出現が複数文書にあれば1行に結合されます
- **列** = 「どの出現（`schemaId` / `fileGlob` で選択）の、要素からの相対パス（`path`）」。`editable: true` の列はグリッド上で直接編集できます（文字列・数値・enum・参照などのスカラー値。配列・オブジェクトはクリックで該当文書へジャンプ）
- セルの編集は**元の文書への通常の編集**そのものです（未保存●表示・Undo・`Ctrl+S`／すべて保存・差分がそのまま使えます）。ビュー自体はデータを持ちません
- **詳細列**: `detail` に一致する出現があればリンク、なければ「作成」ボタンで `filePattern` の位置に**詳細文書をスキャフォールド**します（スキーマの必須初期値＋行のIDを設定）
- **新規行**: `newRow` を定義すると、一覧文書の配列へ新しい要素を追加できます（IDを入力して保存するとグリッドの行になります）
- **バックリンク列**: 列に `path` の代わりに `backlinks` を書くと、行のIDへの**被参照**（参照元要素のID・タイトル）を一覧表示します。`relation`（参照の関係種別）と `schemaIds`（参照元スキーマ）で絞り込めます。1:N詳細化（§6）の「親から見た分裂先の一覧」に使います。派生表示のため編集はできません（クリックで参照元へジャンプ）
- **状態列**: カバレッジルール（§4）の充足状況を行ごとに表示します

```yaml
# _views/screen-catalog.yaml
id: screen-catalog
name: 画面カタログ
rows:
  idPattern: "SCR-*"                  # このIDパターンが行になる
order:
  fileGlob: todos/10-screens-list.yaml  # 一覧文書での出現順に並べる（省略時はID順）
columns:
  - label: 画面名
    fileGlob: todos/10-screens-list.yaml  # 値を取る出現（schemaId でも指定可）
    path: name                            # 出現要素からの相対パス
    editable: true
  - label: エリア
    fileGlob: "todos/screens/*.yaml"
    path: areas                           # 複合値は要約表示＋ジャンプ
  - label: 実装テーブル
    backlinks:                            # バックリンク列: この画面IDを参照している要素を一覧表示
      relation: derives                   # 参照の関係種別で絞る（省略可）
      schemaIds: [table-design]           # 参照元文書のスキーマで絞る（省略可）
detail:
  fileGlob: "todos/screens/*.yaml"        # この条件に一致する出現を「詳細」と見なす
  filePattern: "todos/screens/{id}.yaml"  # 「作成」ボタンの作成先（{id} が行のIDに置換）
newRow:
  file: todos/10-screens-list.yaml        # 「新規行」の追加先（一覧文書の配列）
  path: screens
```

`_views` は予約ディレクトリで、組込みスキーマによりフォーム編集・検証できます。エージェントは同じビューを `read_view` ツールで参照でき（§12）、CLI では `view` コマンドで解決できます（§16）。

また、詳細文書をフォームで開くと、上部に**「他文書での定義」ストリップ**が表示され、同じIDの一覧側の情報（名前・種別など）を参照・ジャンプできます。一覧側にある情報を詳細文書へ重複記載する必要はありません。

## 6. ID とリンクの仕組み

### ID の索引化

ワークスペース内のYAMLをスキャンし、`id -> [(ファイル, パス, タイトル, schemaId, documentId)]` の索引を構築します。IDとして認識されるのは:

- スキーマで `type: id` と定義されたフィールドの値
- スキーマの有無に関わらず、キー名が **`id`** であるスカラー値（ネストした要素でも可）

同じIDは複数ドキュメントに定義できます。それらは段階的詳細化された同一論理要素の複数出現として索引化されます。同一ドキュメント内の重複だけが検証エラーです。ジャンプ時に複数出現がある場合は選択ダイアログを表示します。

スキーマの `id` は参照スコープに使う安定識別子、`name` は表示専用です。`id` を省略した場合はスキーマファイル名（拡張子なし）を使います。

ドキュメントIDは任意で次のように宣言できます。省略時はワークスペース相対パスを使います。

```yaml
_document:
  id: system-overview
  name: システム構想
  description: |
    システムの目的、利用者、主要な機能領域を定義する文書。
    後続の要求・設計文書が前提とする全体像を示す。
```

`name` は画面の文書ヘッダーに表示する任意の文書名です。省略時は従来どおりワークスペース相対パスを表示します。
`description` は、全文を読まずに文書の目的と内容を判断するための任意の概要です。フォーム先頭の「文書メタデータ」で文書名と概要を編集できます。これらは将来、LLMへ文書コンテキストを渡す際の要約情報としても利用できます。

### 表示解決（タイトル・要約の決まり方）

要素（IDを持つオブジェクトなど）を1行で見せる場面——畳み込みヘッダ・参照候補・バックリンク・ID横ぐしビュー・ビューグリッド・ID検索・エージェントの `related` 要約——は、すべて同じ**表示解決**の結果を使います（人間とAIが同じ要約を見ます）。タイトル・サブタイトルは次の優先順位で決まります。

1. **スキーマの `role` 指定**: `role: title` / `role: subtitle` を付けたフィールドの値（`$ref` 先の指定も合成され、library 共有にも乗ります）
2. **予約語**: タイトルは `title` → `name` → `label`、サブタイトルは `description` → `summary` の先勝ち
3. **id**: タイトルがなければ ID を表示
4. **キー数の要約**: どれもなければ「（n項目）」

つまり `name` や `title` という名前で項目を持つ文書はそのまま読みやすく表示され、独自の項目名（例 `件名`）をタイトルにしたい場合だけスキーマに `role: title` を1行足せば、参照候補から一覧・畳み込みヘッダまで**全画面に一括で**効きます。

### 段階的詳細化の規約（1:1 の詳細化と 1:N の分裂）

工程をまたいで文書を詳細化していく運用では、次の2つの規約を使い分けます。

- **1:1 の詳細化 = 同一ID**: 同じ論理要素を別文書でさらに詳しく書くときは、**同じIDをそのまま使います**（例: 画面一覧の `SCR-LOGIN` と画面詳細文書の `SCR-LOGIN`）。出現はID横ぐしビュー・ビューグリッドで1行に結合され、詳細文書の存在は出現ベースのカバレッジルール（`detailIn`。§4）で機械検証できます。
- **1:N の分裂 = 新しいID＋親への参照**: 1つの要素が複数の要素へ分かれて実装されるときは（例: データモデルの1エンティティ→単票・明細の2テーブル）、分裂先に**新しいID**を与え、`type: ref`（`relation` で種別を宣言。例 `derives`）で**親へ逆リンク**します。親側のスキーマは参照ベースのカバレッジルール（`requiredBy` の `relation` 限定）で「全エンティティが1つ以上のテーブルから実装されること」を検証でき、ビュー定義の**バックリンク列**（`backlinks`。§5）で親→分裂先の一覧を表示できます。

sample-workspace の `models/00-data-model.yaml`（エンティティ）と `tables/`（テーブル設計。`entity` 項目で親へ逆リンク）、ビュー定義 `_views/entity-tables.yaml` がこの規約の実例です。

### 参照候補の絞り込み

`type: ref` ではID体系と探索範囲を独立して指定できます。

```yaml
type: ref
idPatterns: ["ACTOR-*", "ROLE-*"]
scope:
  schemaIds: [system-concepts, actor-detail]
  documentIds: [system-overview]
```

`idPatterns`、`schemaIds`、`documentIds`の各配列内はOR、異なる条件間はANDです。IDパターンは大文字・小文字を区別します。条件は候補表示だけでなく参照検証にも適用されます。ID自体が存在しても条件外なら検証エラーになります。条件を省略するとワークスペース全体が対象です。

### 参照（リンク）の認識

- スキーマで `type: ref` と定義された位置の値（配列要素含む）
- スキーマ外のキーに対する**命名規約ヒューリスティクス**:
  - キー名 `ref` または `*_ref` のスカラー値
  - キー名 `refs` / `*_refs` / `depends_on` / `relates_to` 配下のスカラー配列

### リンクの機能

- **ジャンプ**: ref フィールドの「→」ボタン、右パネルの「参照」クリックで定義元ファイルを開き、該当要素をハイライト表示＆自動スクロール
- **戻る・進む**: ジャンプやファイル切替のあと、ツールバーの「←」「→」ボタン（`Alt+←` / `Alt+→`）で移動前の位置（ファイルとハイライト位置）へ戻る／やり直すことができます（履歴は最大50件。ワークスペース切替でクリアされます）
- **補完**: ref フィールドのドロップダウンで、IDパターン、スコープ、入力文字列（ID・タイトル部分一致）により候補を選択
- **未解決検出**: 索引にも編集中ドキュメントにも存在しない ID への参照は、赤枠＋検証パネルにエラー表示
- **バックリンク**: 開いているファイルの ID を参照している箇所を「被参照」に一覧表示。参照を書いた要素のID・タイトル（表示解決の結果）を主表示にし、クリックで参照元へジャンプ
- **ID 検索**: ツールバーの検索ボックスから ID・タイトルで横断検索してジャンプ

> **索引の更新タイミング**: 索引はディスク上のファイルに基づき、ワークスペースを開く、再読込、保存、外部変更検出、一括編集のタイミングで更新されます。未保存の編集は他ファイルからの解決・被参照にはまだ反映されませんが、編集中文書内のIDは保存前でも解決されます。

## 7. 検証

右パネルの「検証」に以下が表示され、クリックで該当箇所にジャンプします。

- 必須項目の未設定（`required: true`）
- 型不一致（int / number / boolean / object / array / map）
- `enum` の選択肢外の値
- 非アクティブな case のキーの残存（`cases`。有効になる enum 値を案内。重大度は `unknownFields` に従う）
- `date` の形式逸脱（警告）
- 未解決の参照
- ID の重複（同一ファイル内。異なるファイルの同一IDは許容）
- カバレッジルールの不足（被参照数または詳細文書の出現数が `coverage` の要件に満たないID）
- スキーマファイルの構造、未知の型、フィールドキー重複、array/mapの子定義不足、未解決の `$ref`

## 8. 外部変更・競合・安全性

- ワークスペース内のYAMLをOSのファイル監視（WatchService）で監視します。監視を開始できない環境では約1秒間隔のポーリングに自動フォールバックします。
- 未編集のファイルが外部変更された場合は自動的に再読込します。
- 未保存文書が外部変更された場合は自動上書きせず、競合バナーを表示します。
- 競合時は「ディスク版を読み込む」または「編集内容を維持」を選択できます。
- 未保存文書を含む名前変更・削除・一括編集は拒否されます。
- ファイル削除は確認ダイアログを経由します。

## 11. AIによる作成支援

スキーマが適用された文書では、OpenAI / Anthropic（Claude）/ Azure OpenAI（AI Foundry）の API を使って内容のたたき台を生成できます。入口は3か所です。

- **フィールド単位**: フォームの各フィールドラベル横の ✨ アイコン
- **配列への候補追加**: 配列エディタの「AIで候補追加」（既存項目を残して追加／配列全体を置き換えを選択可能）
- **文書全体**: 文書ヘッダーの「AIで作成」ボタン（`_document` メタデータは保持されます）

流れは「指示を入力 → 生成 → プレビューで現在値と比較 → 適用」です。

- 生成結果は、対象フィールドのスキーマから変換した JSON Schema による構造化出力（Structured Outputs）で受け取るため、型・enum・必須キーがスキーマに準拠します（`map` 型を含む場合のみ構造化出力を無効化し、プロンプト指示によるJSON生成にフォールバック）。
- `cases` を持つ enum を1つ含むオブジェクトは、enum 値ごとの分岐（`anyOf`）に変換され、選択値と追加フィールドの組み合わせもスキーマで保証されます（`cases` を持つ enum が同一オブジェクトに複数ある場合は全 case フィールドの和集合で受けます）。
- `ref` 型フィールドは、`idPatterns`・`scope` で絞り込んだワークスペース内の既存IDを enum 制約として渡すため、存在しないIDへの参照が生成されにくくなります（候補が200件を超える場合は制約を省略し、プロンプト内の一覧のみ）。
- プレビューは現在値とAI提案の行単位差分表示で、提案を適用した場合のスキーマ検証結果（エラー・警告数）も表示します。適用は Undo 可能で、自動保存はされません。
- 生成中は「生成を中止」でキャンセルできます。
- モデルに送信されるのは、指示、現在の文書、対象フィールドのスキーマ、ワークスペース内の既存ID（最大500件）です。
- 生成はエージェント実行と同じカーネル上で「1ターンで提出する特殊アクティビティ」として実行され、実行記録が `_runs/` に他のアクティビティと同じ形式で残ります（アクティビティID: `ai-generate`。適用自体は従来どおりダイアログのプレビュー→編集中文書への反映で、自動保存されません）。

接続設定:

- **プロバイダ**: OpenAI / Anthropic / Azure をダイアログで切り替えます。選択は端末の設定（Preferences）に保存されます。
- **APIキー**: ダイアログで入力するか、環境変数（`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `AZURE_OPENAI_API_KEY`）を設定します。キーはメモリ上にのみ保持され、ディスクには保存されません。
- **モデル**: 既定は OpenAI が `gpt-5.1`、Anthropic が `claude-opus-4-8`。Azure は**デプロイメント名**を指定します。変更はプロバイダごとに端末の設定へ保存されます。Structured Outputs 対応モデルが必要です。
- **Azure OpenAI / AI Foundry**: 「接続の詳細設定」でエンドポイント（例 `https://<リソース名>.openai.azure.com`）と APIバージョン（空なら v1 サーフェス）を設定します（環境変数 `AZURE_OPENAI_ENDPOINT` / `AZURE_OPENAI_API_VERSION` でも可）。認証は `api-key` ヘッダで行われます。
- **OpenAI互換エンドポイント**: OpenAI 選択時にベースURLを上書きすると、ollama / vLLM 等の互換エンドポイントも利用できます（環境変数 `OPENAI_BASE_URL` でも可）。
- **プロキシ**: 既定はシステム設定に従います。「接続の詳細設定」でプロキシなし／手動（ホスト・ポート）へ切り替えられ、Basic 認証（ID・パスワード）も指定できます。パスワードはAPIキー同様メモリのみ保持です。エンドポイント・プロキシ設定はフィールド生成とエージェント実行の両方に共通で効きます。

## 12. エージェントによるアクティビティ実行

定型化した仕事を「アクティビティ」として定義し、AIエージェントに委託できます。エージェントは探索（カタログ→骨子→本文）、複数文書への部分パッチ、横断検証を自律的に繰り返し、結果を**変更セット**として提出します。**原本は人間がレビューして採用するまで変更されません。**

### 定義の置き場所

| ディレクトリ | 内容 |
|---|---|
| `_agents/*.yaml` | エージェント定義: `id`・`persona`（性格・行動指針）・`rubric`（観点）・`model`（プロバイダ／モデルID）・`tools`（許可ツール分類） |
| `_activities/*.yaml` | アクティビティ定義: `id`・`agent`・`target.match`（対象glob）・`instruction`・`allowedFiles`／`allowedPaths`（書込許可）・`limits`（maxTurns等）・`gates.validation`・`trigger`／`chain`／`retry`／`approval`（自動実行）・`meta`（§13） |
| `_evals/*.yaml` | 評価セット定義: ゴールデン入力と期待結果によるアクティビティの回帰評価（§13） |
| `_skills/*.yaml` | skill定義: 宣言型のインポート・エクスポート（§14） |
| `_views/*.yaml` | ビュー定義: 行×列の横断一覧（§5）。`context.views` でアクティビティの初期文脈にも開示できる |
| `_runs/` | 実行記録（自動生成。ターン・ツール呼び出し・質問・採否・トークン使用量・評価レポート） |

どちらも組込みスキーマ付きのYAML文書なので、本ツールのフォーム編集・検証がそのまま使えます（独自スキーマを `_schemas` に置けば上書き可能）。定義例:

```yaml
# _activities/review-concepts.yaml
id: review-concepts
name: システム構想レビュー
agent: reviewer                          # _agents/reviewer.yaml
target: { match: "01_requirements/**/*.{yaml,yml}" }
instruction: |
  actors / capabilities をレビューし、指摘を各文書の review_comments 配列に追記してください。
allowedFiles: ["01_requirements/**"]     # 書込を許可する範囲（省略時は全ファイル）
allowedPaths: ["review_comments*"]       # 書込を許可するパス（省略時は全パス）
limits: { maxTurns: 16 }
gates: { validation: error-free }        # 検証エラーが残る提出は拒否
```

### プロバイダ・モデルの決まり方

実際に使われる接続先は **エージェント定義の `model:` が最優先**で、未指定の項目だけダイアログの選択値で補われます。ダイアログの「AI接続」には常に**この実行で実際に使われる**プロバイダ・モデルが表示され、APIキーもそのプロバイダのものを入力します（例: エージェント定義が `provider: anthropic` を指定していれば、OpenAI を選んでいても Anthropic のキーが必要です）。

### 実行の流れ

1. ツールバーのロボットアイコンからダイアログを開き、アクティビティを選択（追加指示も可能）
2. 実行中はターンごとの行動（探索・パッチ・検証）が流れ、エージェントからの**質問**には入力欄で回答できます。いつでもキャンセル可能
3. 終了すると**変更セットレビュー**画面になり、ファイル単位で採用／却下を選べます。採用の組み合わせを変えるたびに再検証され、参照整合の破れが警告されます
4. 「選択した変更を適用」で原本に書き込み（適用は Undo 不可ですが、適用前と同じ変更セットが `_runs/` の記録から辿れます）

### 安全性

- エージェントの読み書きはツール経由のみで、書込は `allowedFiles`／`allowedPaths` の範囲かつ予約ディレクトリ（`_schemas` `_agents` `_activities` `_evals` `_skills` `_views` `_runs`）以外に制限されます（定義ディレクトリはメタアクティビティ §13 でのみ提案可能）
- 探索ツールにはビュー参照（`read_view`）が含まれ、複数文書に散らばる同一IDの情報を、原本上の座標（file / path）つきの一覧として取得できます。アクティビティ定義の `context: { views: [ビューID] }` で初期文脈として開示することもできます
- ID横断（`related`）は出現ごとに `read_node` を呼ばずに済むよう、主要フィールドの要約と、`phases` 宣言スキーマなら現在フェーズ・記入進捗も1回の呼び出しで返します（ID横ぐしビューのAI版）。`list_documents` のカタログにも同様にフェーズ状態が付きます。アクティビティ定義の `context: { include: [catalog, phase] }` で、対象文書のフェーズ状態を最初から初期文脈に含めることもできます（段階的詳細化を前進させるアクティビティに使う）
- 提出には検証ゲート（既定: エラー0）があり、変更が壊す参照（改名の未修正参照元など）はステージング外のファイルでも検出されます
- ターン数・トークン・時間の上限があり、上限到達時も作業は未提出ドラフトとして保全され、レビュー画面から引き継げます
- 文書の内容はエージェントへの指示として扱われません（データとして扱う規範をシステムプロンプトで明示）

### 自動実行（トリガ・連鎖・自動承認）

ツールバーの回転矢印アイコンから**自動実行パネル**を開き、監視を有効化すると、アクティビティ定義の `trigger` に従って自動起動します。実行は常に1件ずつ（直列）で、パネルからキュー・承認待ち・履歴・ログを確認でき、「停止」でいつでも全消去・中断できます。

```yaml
trigger: { type: on-change, match: "requirements/**", debounceSeconds: 30 }
# type: manual（既定）… 手動起動のみ
#       on-change      … 対象ファイルの更新後、debounceSeconds 静止してから起動
#       on-invalid     … 更新されたファイルに検証エラーがあるときだけ起動
#       schedule       … everyMinutes ごとに起動
chain:                       # 実行後に連鎖起動（循環・深さ5は自動停止）
  rules:                     # 出力値による分岐（上から評価し、最初に一致した then へ。省略可）
  - when: { outcome: success, noteContains: 重複 }   # 条件はAND: outcome（success/failure/any）/
    then: dedupe-issues                              # changedFiles（採用変更のglob）/ minChangedFiles / noteContains
  onSuccess: file-issues     # どのルールにも一致しないときのフォールバック
  onFailure: notify
retry: { maxAttempts: 2 }    # 失敗時、理由をフィードバックして再実行（同一失敗の繰り返しは打ち切り）
approval: auto               # 自動適用（下記の条件つき）。既定は human（承認待ち）
```

- **`approval: auto` の安全条件**: 提出ゲート通過＋書込スコープ内＋対象がエディタで**編集中でない**こと。条件を欠くと自動でも「承認待ち」に降格します。人間の編集と自動実行が衝突しない排他がこれに当たります。派生スキーマ（§4）の**導出元文書**への変更を含む場合も、検証ルールが無人で変わることを防ぐため常に承認待ちへ降格します。
- **巻き戻し**: 自動適用は適用前の原文を実行記録（`_runs`）へバックアップし、`./gradlew runCli -q --args="revert <workspace> _runs/xxx.yaml"` で復元できます（適用後に更に変更されたファイルは競合として拒否。`--force` で上書き）。
- **承認待ちの耐久性**: 変更セットは `_runs/xxx-changeset.yaml` にも保存されるため、アプリを閉じても後から `apply` コマンドで適用できます。
- **自己変更では再発火しない**: エージェントが適用した変更で自分の on-change が再度発火することはありません。
- **エージェント同士の相談**: エージェントは `delegate` ツールで別のエージェント（例: レビュー担当）へ読み取り専用の相談ができ、ドラフト（ステージング）を見せて所見を受け取れます。編集・提出は依頼元だけが行います。

CLIからも実行できます: 単発は `agent`、常駐監視は `watch`（`--once` で1回だけ判定・消化）。`./gradlew runCli -q --args="watch <workspace>"`（定義一覧は `activities`。APIキーは環境変数から）。

## 13. 自己改善（メトリクス・評価セット・メタアクティビティ）

エージェント運用の品質を測定し、定義の改善をツール内で回すための機能群です。ツールバーのグラフアイコンから**自己改善パネル**を開きます。

### 実行メトリクス

`_runs` の実行記録から、アクティビティ別に**提出率・採用率・却下ファイル率（部分採用で却下された割合＝人間による修正量の代理指標）・自動適用と巻き戻し・平均ターン・トークン**を集計します。実行のたびに追加の記録は不要で、過去の実行記録もそのまま集計対象です。CLI: `metrics <workspace> [--activity id]`。

### 評価セット（アクティビティの「テスト」）

`_evals/*.yaml` に**ゴールデン入力と期待結果**を定義すると、アクティビティを回帰評価できます。評価は**ワークスペースの一時コピー（サンドボックス）上で実行**されるため、原本は変更されません。レポートは `_runs/eval-*.yaml` に保存されます。

```yaml
# _evals/review-eval.yaml
id: review-eval
activity: review-concepts        # 評価対象のアクティビティ
variants:                        # 省略可: A/B比較（モデル・エージェント・追加指示の差し替え）
- name: base
- name: strict
  instruction: 指摘は最大3件に絞ってください。
  # model: { provider: anthropic, id: claude-opus-4-8 } / agent: 別エージェントID も指定可
cases:
- id: vague-actor-is-flagged
  setup:                         # ゴールデン入力: サンドボックスへ上書き・作成するファイル
  - file: 01_requirements/01-system-concepts.yaml
    content: |
      （意図的に曖昧な定義を含むYAML全文）
  expect:                        # 宣言的な期待結果（すべて満たせば合格）
    status: submitted            # submitted（既定）/ aborted / limit / error / any
    errorFree: true              # 終了時点の検証エラー0
    changedFiles: ["01_requirements/**"]   # 各globに1件以上の変更が必要
    unchangedFiles: ["03_designs/**"]      # マッチする変更があれば不合格
    content:                     # 結果（ステージング）の内容チェック
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, exists: true }
    - { file: 01_requirements/01-system-concepts.yaml, path: review_comments, contains: ACTOR-USER }
```

期待結果を「出力文字列の完全一致」ではなく構造条件で書くのは意図的な設計です。モデルの揺らぎに対して壊れにくく、**良い合格条件を書くこと自体が業務設計（ハーネスエンジニアリング）** になります。CLI: `eval <workspace> <eval-id>`（引数なしで一覧）。

### メタアクティビティ（定義の改善提案）

アクティビティ定義に `meta: true` を付けると、そのエージェントは `_agents` / `_activities` / `_evals` / `_skills` / `_views` の**定義文書そのものへの変更を提案**できます（例: 実行記録の傾向を踏まえた指示の改善、評価ケースの追加、エクスポート列の追加）。安全のための制約:

- **承認は human 固定**。`meta: true` かつ `approval: auto` は定義エラーになります（エージェントが自分の権限・挙動を変える変更は必ず人間が承認）
- `_schemas` と `_runs` への書込は meta でも**常に不可**
- ステージされた定義が**実際にパース可能であること**が提出ゲートに加わります（壊れた定義は提出できず、自己修正ループに入る）

「メタアクティビティで改善案を提案 → 評価セットで変異比較 → レビューで採用」という改善サイクルがツール内で完結します。

## 14. skill（インポート・エクスポート・テンプレート）

Excel・CSV等の現実の業務フォーマットと、YAML原本を接続する機能群です。ツールバーの上下矢印アイコンから **skillパネル**を開きます。変換は `_skills/*.yaml` に**宣言的に**定義します（例外は明示許可制のコード実行skill。後述）。

### インポート（表形式 → YAML原本）

xlsx / csv / json / markdown / docx（Word文書内の表）を、列マッピングでYAML文書群へ取り込みます。**取り込んだ時点からYAMLが原本**です。

```yaml
# _skills/import-issues.yaml
id: import-issues
kind: import
input: { format: xlsx, headerRow: 1 }        # xlsx / csv / json / markdown / docx
# docx は Word 文書内の表を読みます: input: { format: docx, table: 1 }（table = 何番目の表か。1始まり）
target: { file: "issues/{ID}.yaml" }         # {列名} が行の値で置換される（1行1文書）
mapping:
- { column: ID, path: id, required: true }
- { column: 件名, path: title, required: true }
- column: 状態
  path: status
  map: { 未着手: open, 対応中: in-progress, 完了: done }   # 値の変換辞書
- { column: 優先度, path: priority, type: int }            # 型変換（string/int/number/boolean/auto）
- { column: タグ, path: tags, split: "," }                 # 区切りで配列化
```

重要な性質:

- **既存文書はマップした項目だけ更新**されます（値が変わる場合のみ）。YAML側に追記した項目（レビューコメント等）は再インポートで消えません
- 適用前に**プレビュー**（作成／更新／変更なし／エラー）が出ます。適用は変更セット経由で、競合検出・検証ゲート・オール・オア・ナッシングが効きます
- エクスポートした帳票をそのまま再インポートすると**変更セットは空**になります（往復の無損失）

### エクスポート（YAML原本 → 派生成果物）

対象文書（glob）を行×列に展開し、xlsx / csv / markdown / json / html を再生成します（形式は出力ファイルの拡張子で決まります）。出力は**いつでも原本から作り直せる派生物**で、YAMLへの出力は定義段階で拒否されます。

```yaml
# _skills/export-issues.yaml
id: export-issues
kind: export
source: { match: "issues/**/*.{yaml,yml}" }  # rows: 配列パス を指定すると配列要素ごとに1行
output: { file: exports/issues.xlsx, sheet: 課題一覧 }
columns:
- { header: ID, path: id }
- { header: 件名, path: title }
- { header: タグ, path: tags, join: "," }
```

`source: { view: ビューID }` と書くと、`_views` のビュー定義（§5）を行×列の源にして「ビューで見えている表をそのまま帳票へ」出力できます（このとき `match` / `rows` / `columns` は書けません。1列目は行のID、バックリンク列は参照元IDの列挙になります）。

```yaml
# _skills/export-board.yaml
id: export-board
kind: export
source: { view: screen-catalog }
output: { file: exports/screens.html }
```

### コード実行skill（kind: run・明示許可制）

宣言型では書けない変換・定型手順のために、任意のコマンドを実行する skill を定義できます。**サンドボックス外への作用**のため、次の明示許可制が機械的に強制されます。

```yaml
# _skills/normalize.yaml
id: normalize
name: 正規化スクリプト
kind: run
run:
  command: [python, scripts/normalize.py]   # コマンドと引数
  workdir: .                                # ワークスペース相対（既定 "."）
  timeoutSeconds: 120
  writes: ["work/**"]                       # ワークスペース内への書込を宣言するglob
```

- **実行前に人間がコマンド内容と権限を承認**します（skillパネルは承認ダイアログ、CLIは `--yes` フラグ）。承認なしに実行される経路はありません
- 承認は「承認した時点の定義内容」に紐づき、**定義が変わると失効**します（承認後の定義すり替え防止）
- エージェント・自動実行（トリガ）からは起動できません。メタアクティビティによる定義の**提案**は可能ですが、実行は常に人間の承認が必要です
- 実行後にワークスペース内の変更を検出し、`writes` 宣言外の変更を**警告**、予約ディレクトリ（`_schemas` 等）の変更を**重大な逸脱**として報告します（事後検査であり書込は防げないため、事前承認が前提です）

### テンプレートパック

`init` コマンドで、ユースケース別のスキーマ＋エージェント＋アクティビティ＋評価＋skill一式を新規ワークスペースへ展開できます（既存ファイルは上書きしません）。

```bash
./gradlew runCli -q --args="init my-workspace --template ledger"   # 課題台帳パック
./gradlew runCli -q --args="init my-workspace"                     # テンプレート一覧
```

`ledger` は「Excel台帳をインポート→YAML原本で運用（棚卸しアクティビティ・評価つき）→Excel帳票を再出力」の往復をそのまま体験できる雛形です。

## 15. 既知の制約

- **コメント・キー順・表記スタイルは「開く→編集→保存」の往復で保持されます**（引用符・リテラルブロック `|`・フロー表記 `[a, b]` を含む）。残る正規化は次のとおりです:
  - アンカー／エイリアス（`&x` / `*x`）は読み込み時に展開され、保存すると実体化します。
  - ブロックスタイルのインデントは 2 に正規化され、リストの `-` は親プロパティより一段深く配置されます。
  - リスト要素の**前の行**に書かれたコメントは、SnakeYAML エミッタの制約により初回保存時に `- # コメント` の形（`-` の後ろ）へ移動します。内容は失われず、以降の保存では安定します。
  - 編集で値を**置き換えた**箇所（AI適用・パッチなど）のコメントは可能な範囲で引き継がれますが、削除した項目のコメントは項目とともに消えます。
- 外部変更は OS のファイル監視（WatchService）で検出します。監視を開始できない環境（ネットワークドライブ等）では約1秒間隔のポーリングへ自動フォールバックします。未編集ファイルは自動反映され、未保存の編集がある場合は競合バナーからディスク版または編集中の内容を選択できます。
- 複数ドキュメント（`---` 区切り）の YAML は、フォーム編集・索引・検索が**先頭ドキュメント**を対象とします。後続ドキュメントは失われずに保持され、ソースタブで編集できます。
- 差分ビューは行単位の整列＋行内の文字単位強調です。Gitの履歴表示ではありません。
- 一覧ビューの一括編集はルート直下のスカラー項目のみが対象です（配列・オブジェクトの項目は選択しても上書きされません）。
- ビューグリッドの**行の増減**（新しいIDの出現）は索引基準のため保存まで反映されません（セルの値・編集は未保存でも即時反映されます）。セルの直接編集はスカラー値のみで、配列・オブジェクトはジャンプして個別フォームで編集します。

改善予定を含む実装状況の全体は [docs/FEATURES.md](docs/FEATURES.md) で管理しています。拡張方法（型の追加・横断ビュー・AIプロバイダの追加など）は [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) の「拡張ポイント」を参照してください。

## 16. ヘッドレスCLI（エージェント向け基盤）

GUIを起動せずに、ワークスペースの探索・検索・部分変更・検証を実行できます。出力は機械可読なYAML（UTF-8）で、AIエージェントや自動化スクリプトからの利用を想定しています。

```bash
./gradlew runCli -q --args="catalog sample-workspace"                     # 文書カタログ（_document要約・スキーマ・ID数）
./gradlew runCli -q --args="outline sample-workspace path/to/doc.yaml"    # 骨子（キー構造・配列件数。長文は文字数表示）
./gradlew runCli -q --args="read sample-workspace path/to/doc.yaml items[0]"  # 指定パス配下の全文
./gradlew runCli -q --args="bundle sample-workspace path/to/doc.yaml --budget 4000"  # 対象＋参照・被参照の文脈バンドル
./gradlew runCli -q --args="search sample-workspace --text ログイン --schema requirement"  # 本文検索
./gradlew runCli -q --args="search sample-workspace --ref-to REQ-001"     # 参照検索（--unresolved で未解決のみ）
./gradlew runCli -q --args="view sample-workspace screen-catalog"         # ビューの解決（引数なしで一覧。セルに原本座標つき）
./gradlew runCli -q --args="validate sample-workspace"                    # 全文書の検証（カバレッジ含む）
./gradlew runCli -q --args="hash sample-workspace path/to/doc.yaml"       # 変更セットの base に使う内容ハッシュ
./gradlew runCli -q --args="apply sample-workspace changeset.yaml --dry-run"  # 変更セットの適用（ドライラン）
./gradlew runCli -q --args="activities sample-workspace"                  # アクティビティ／エージェント定義の一覧
./gradlew runCli -q --args="agent sample-workspace review-concepts"       # アクティビティ実行（--apply で即適用）
./gradlew runCli -q --args="watch sample-workspace --once"                # 自動実行（トリガ判定→キュー消化を1回）
./gradlew runCli -q --args="revert sample-workspace _runs/xxx.yaml"       # 自動適用の巻き戻し
./gradlew runCli -q --args="metrics sample-workspace"                     # 実行記録の集計（提出率・採用率・コスト）
./gradlew runCli -q --args="eval sample-workspace review-eval"            # 評価セットの実行（引数なしで一覧）
./gradlew runCli -q --args="skills sample-workspace"                      # skill定義の一覧と検証
./gradlew runCli -q --args="import my-ws import-issues ledger.xlsx --apply"  # 表形式の取り込み（既定はプレビュー）
./gradlew runCli -q --args="export sample-workspace export-actors"        # 派生成果物の再生成
./gradlew runCli -q --args="run-skill my-ws normalize --yes"              # コード実行skill（--yes なしは内容表示のみ）
./gradlew runCli -q --args="init new-ws --template ledger"                # テンプレートで初期化
./gradlew runCli -q --args="infer-schema my-ws 'issues/**/*.yaml' --apply"  # 既存文書からスキーマ推測（--apply なしはプレビュー）
./gradlew runCli -q --args="bench bench-ws --docs 1000"                   # 索引性能の計測（空ディレクトリなら生成もする）
```

変更セット（changeset.yaml）は複数ファイルへの部分パッチの束です。`base` を指定すると、作成時点からディスクが変わっていた場合に適用を中止します（競合検出）。1件でも失敗すると全ファイル書き込みを行いません。`--require-valid` を付けると、適用後に検証エラーが残る場合も中止します。

```yaml
changes:
  - file: requirements/req-001.yaml
    base: 3f2a…                      # hash コマンドの値（省略可）
    ops:
      - { op: set,    path: title,        value: 新しいタイトル }
      - { op: insert, path: "tags[0]",    value: 重要 }        # 配列は挿入、マップは新規キー
      - { op: delete, path: obsolete }
      - { op: move,   from: "items[2]",   to: "items[0]" }
```

パスは `items[2].title` 形式です。フロースタイル（`{ }`）内で `[` を含むパスは引用符で囲んでください。ルート（空パス）への操作はできません。
