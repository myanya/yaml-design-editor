# 抽象システムモデル・具体システムモデルへの移行計画

業務モデルから 3 つの変換でソースコードまで作る形へ、いまの設計の体系を移す計画です。
2026-11-24・25 のオーナーとの議論の結果をまとめたもので、進捗は [ロードマップ](../../../docs/ROADMAP.md#p53-業務モデルから作る設計書体系とアプリ生成)の R53-12 で管理します。
決定は [ADR-0042](../../../docs/decisions/0042-system-models-and-views.md) にあります。この文書は、そこへ移す順序と、進み具合の確かめ方を持ちます。

> **進め方を見直す案があります（2026-11-27。オーナーの承認前）。** 種類ごとに横へ進めた結果、理想に無いファイルと、目指す形から外れている流れが減っていません。
> 系統ごとに縦へ通し、通すたびに古い仕組みを消す進め方と、全ファイルの扱いの一覧を [ファイル体系の全体と、いまのファイルをどうするか](file-system-plan.md) に書きました。
> 構造と進み具合は [移行の進み具合](design-progress.html) で見られます。

## 目指す形

```text
業務モデル
   ↓ アーキテクチャマッピング
抽象システムモデル（基本設計）      ビュー = 定義書
   ↓ 技術スタックマッピング
具体システムモデル（詳細設計）      ビュー = 設計書
   ↓ コードマッピング（前半）
プログラム設計（配置）
   ↓ コードマッピング（後半）
ソースコード
```

LSI の論理合成・テクノロジマッピング・配置配線にならった形です。
理想のファイルの種類と依存関係は [理想のファイル体系](design-ideal-graph.html)、いまの姿は [ファイル単位の生成グラフ](design-file-graph.html) にあります。

## 合意したこと

- **言葉**: 定義書は基本設計の成果物、設計書は詳細設計の成果物です。どちらも、それぞれのモデルのビューです。
- **人が書くもの**: 業務モデルと、各段の判断だけです。判断は「全体の判断（同じ種類すべてに当てる方針）」と「個別の判断（特定の要素だけの決定）」の 2 種類で、段ごとに分けて置きます。
- **業務モデルは直接直す**: 業務の事実の誤りは業務モデルを直します。変換の前に業務モデルを補正する層は置きません。
  業務モデルに本来要らない情報を足す必要が出たら、そのときに考え直します（いまは見つかっていません）。
- **判断の置き場**: 判断は、それを言える最初の段に 1 回だけ書きます。判断は、対象より下流のすべてに届きます。
- **補正前の結果**: 層ではなく、比較の相手です。「個別の判断が 0 件ならこうなる」を表し、確定したモデルとの差は、すべて個別の判断で説明できます。
- **プログラム設計**: `application-*.yaml` にあたるものを、詳細設計から分けます（置き場所も分ける）。

## 守る性質

図と検査で確かめられる形にしたものです。

1. 各段の変換は、1 つ前の段のモデルだけを読む。
2. 1 つ前の段のモデルだけで、次の段を作れる（要る情報は、すべて前の段が運ぶ）。
3. 抽象システムモデルには、技術スタックを替えると変わる語が現れない。
4. 各要素は、元になった前の段の要素を指す。
5. 判断は入力である。生成物は直さない。判断は ID で対象を指し、再生成のたびに当て直す。対象が消えたら止まる。
6. ビューは射影である。定義書・設計書にしかない情報はない。

## 体系について決めたこと（2026-11-25）

| 論点 | 決めたこと |
|---|---|
| 抽象システムモデルの要素の種類 | 10 種（型、エンティティと項目、状態と遷移、データの決まり、操作、一覧の検索条件、画面、画面遷移、エラー、メッセージ）。状態・データの決まり・検索条件は、複数の箇所から読まれるので独立させ、操作や画面からは ID で指す |
| ファイルの粒度 | 業務モデルの 1 つの要素を直したとき、Git の差分が 1 ファイルに収まるようにする。操作・処理の手順は操作ごと、画面・画面の部品と入力は画面ごと、エンティティと項目・テーブルへの読み書きはエンティティごと、ほかは 1 ファイル |
| 抽象と具体の境 | 技術スタックを替えても変わらないものが抽象。確認画面・画面遷移・URL・二重確定を防ぐトークンは抽象、クラス名・型の名前・Mapper・SQL の型は具体 |
| 詳細設計とプログラム設計の境 | 詳細設計は、技術スタックの言葉で「何を作るか」を書く（型の名前・クラス名・メソッド名）。プログラム設計は、「Java の文としてどう書くか」を書く（完全修飾名・アクセサ名・出力先のファイル）。Java の型対応表とテーマは、詳細設計の全体の判断に置く |
| ソースコードの作る元 | ソースコードは、詳細設計かプログラム設計を読む。配置を決める必要がないもの（DDL・CSS）は詳細設計から直接出す。基本設計より前は読まない。入力エラーの文は、詳細設計の「画面の部品と入力」を通す |

区分（マスタ・トランザクション）の定義は基本設計の全体の判断、エンティティへの割当は基本設計の個別の判断に置きます。

### 段階 3 の「操作」の進め方（2026-11-26 に合意）

操作の情報は、アクション定義書（文書の形）・それを重ねた補正後の業務モデル・エンティティ定義書の `OPS-` と `CRUD-` の 3 か所にあります。次の 3 歩で、項目の形の 1 か所にまとめます。

| 歩 | やること | 確かめること |
|---|---|---|
| 1. 項目の一覧を足す（済） | `design/basic/final/operations/<操作>.yaml` と、レビュー用のビューを足す | ほかの生成物が変わらない |
| 2. 詳細設計の 8 本を切り替える（済） | 項目を、読む側の形に戻したもの（解いた形）を 1 か所で作り、8 本がそれを読む。入力は基本設計の項目だけで、業務モデルを読まない | 生成物がバイト単位で同じ |
| 3. アクション定義書の文書と、補正後の業務モデルの操作をやめる（済） | 個別の判断を操作の項目へ直接当てる形にしたうえで、アクション定義書を項目のビューにし、アプリの入力・対応の検査・レビュー用のビュー・テストを項目へ向けた | 生成物の一覧から 14 本が減り、ほかとアプリは変わらない |

項目の形について決めたこと:

- 操作そのものの ID は `ACT-<操作>`。`OPS-` は「エンティティ × 操作」の行で、1 つの操作に 2 つ出ることがあるので、操作の ID には使わない。
- 入力 `PRM-`・前提 `PRE-`・効果 `EFF-`（操作の中の連番）に ID を振る。エンティティ・項目・型・遷移・データの決まりは ID で指し、条件と値の式は業務モデルのまま持つ。
- 指す向きは、操作からの 1 方向にする。`entities.yaml`（`OPS-`・`CRUD-`）と `states.yaml`（`TRN-`）の側から `ACT-` は指さない。操作の項目が、遷移（`transition`）と、エンティティから見た書込（`writes`）を指す。
- 効果 `EFF-` と `CRUD-` はどちらも残す。`CRUD-` を効果から導く形にするのは段階 5。
- 入力の値の定義は、型を指したうえで、その入力で効く決まり（必須・長さ・説明・参照先）も持つ。業務モデルが入力ごとに説明や長さを上書きできるので、型だけからは決まらない。エンティティの項目（`FLD-`）と同じ持ち方である。
- 基本設計の側の 9 本（画面・エラー・メッセージなど）は、アーキテクチャマッピングとして業務モデルを読むので、ここでは切り替えない。操作を ID で指す形にするのは、それぞれの種類を移すとき。
- 操作の項目は、業務モデルを直接は読まず、型と項目への補正を当てた後の業務モデル（2 段目）を読む。はじめは業務モデルを直接読む形にしたが、それでは型・項目への補正が詳細設計に届かなくなる（補正が 0 件のいまは生成物に差が出ないので、補正を入れて前後を比べて分かった）。

操作への個別の判断（2026-11-26 に合意）:

- 書き方は、エンティティの補正と同じ「対象の ID と `set`」。対象は操作 `ACT-` と入力 `PRM-` で、`kind`・`select`・`changes` は書かない。入力の決まりは、`PRM-` の直下に並べる（`FLD-` と同じ並び）。
- 置き換えられるのは、操作の名称・説明・入力の送り方と、入力の名称・決まり・はじめの値。識別する値（id・key・source・seq）と、振る舞い（対象・状態と遷移・前提・効果・確かめる決まり）は置き換えられない。振る舞いは業務の事実なので、業務モデルを直す。これは、アクション定義書の確定前検査が止めていた範囲と同じである。
- 補正前のファイルは作らない。当てた判断は、確定した項目の `decisions`（どの場所を、どの値に、どの判断で）に残す。
- 追加と指定は置かない。操作に入力を 1 つ足しても、それを使う規則が下流に無ければ何も起きないためである。システム化のために要る項目は、全体の判断から規則で足す（ADR-0042「項目の出どころ」。仕組みは次に作る）。
- 止める誤りは、対象が無い・操作と入力のほかを対象にした・書けないキー・識別する値・振る舞い・対象に合わないキー・別の段の入力に書いた、である。どれも書き込む前に止まり、前回の生成物が残る。

分かっている穴:

- **型より緩める指定を止めない。** エンティティの補正には、型が最大 100 字の項目を 150 字にする指定を止める検査があるが、操作の入力には無い。入力の決まりを型の決まりと比べる検査を、要るときに足す。
- **定義書の見え方は未レビュー。** アクション定義書は、操作のファイルの文書ビュー「操作の設計書（基本から詳細まで）」と、一覧・入力・効果の 3 枚の表になった。項目をそのまま並べているので、ID が多く、文書としては読みにくい。

### 段階 3 の「画面」の進め方（2026-11-27 に合意）

画面の情報は、画面定義書（文書の形。一覧・詳細・操作の 3 種）にあり、ボタンの名称と出す条件・区画の列・入力の決まり・断りの文を、操作や検索条件から写して持っていました。これを、ID で指す項目の形にまとめます。

項目の形について決めたこと:

- 1 画面 1 ファイル（`design/basic/final/screens/<画面>.yaml`）。操作の画面は、入力画面・確認画面・確定を操作ごとの 1 ファイルにまとめる。
- ID は、画面 `SCR-`（入力画面と確認画面は `SCR-<操作>.input`・`SCR-<操作>.confirm`）、絞り込み `FLT-`、区画と表 `SEC-`、ボタン `BTN-`。詳細画面に並べる値の項目は、ID を振らずに `FLD-` を並べる。
- 操作 `ACT-`・入力 `PRM-`・検索条件 `QRY-`・項目 `FLD-`・エンティティ `ENT-`・型 `TYP-`・遷移 `TRN-`・前提 `PRE-`・データの決まり `RUL-`・行き先の画面 `SCR-` は ID で指す。
- 指した先にある値は写さない。ボタンの名称と出す条件は操作から、区画の名称・行・列・条件は検索条件から、入力の決まりは操作の入力から、断りの文は前提とデータの決まりから決まる。
- 「どこから始まるか」（起点の画面）は持たない。ボタンの側から逆に引ける。
- たどれる範囲（業務モデルの `reach`）は、独立した項目にしない。画面の項目があるエンティティと操作が、たどれる範囲である。
- URL とリクエストは、画面の項目が持つ（抽象の側）。

画面への個別の判断:

- 書き方は、操作と同じ「対象の ID と `set`」（`design/basic/inputs/screens/corrections.yaml`）。対象は `SCR-`・`FLT-`・`SEC-`・`BTN-`。
- 置き換えられるのは、名称（`label`）・説明（`description`）・URL（`url`。一覧画面と詳細画面）・リクエスト（入力画面と確認画面の `request`、操作の画面の `executeRequest`・`backRequest`）。
- **入力の決まり（最大の長さなど）は、画面では変えられない。** 画面と Service で検査がずれないように、操作の入力（`PRM-`）への判断に書く。以前は、画面定義書への補正で画面だけを変えられた。
- ボタンの名称は、`BTN-` を対象にすると、その画面のそのボタンだけが変わる（操作の名称と、ほかの画面のボタンは変わらない）。
- ボタンが始める操作・区画の検索条件・見せる項目は、業務モデルから決まるので変えられない。対象が無い判断と、その対象では置き換えられない値は、書き込む前に止まる。
- 当てた判断は、確定した項目の `decisions` に残す。

まだ用意していないこと:

- **ボタン・区画・項目の並べ替えと、非表示。** 文書の形のときは、場所を指定した補正（`changes`）で何でも書き換えられたが、いまは名称・説明・URL・リクエストだけである。要るようになったら、置き換えられる値として足す。
- **画面への追加**（ボタンや区画を 1 つ足す）。文書の形のときの「追加」（`additions`）にあたるものは、画面の項目には置いていない。
- **画面を解いた形**（`basic-screens-resolved`）は、操作を解いた形と同じ途中経過で、読む側が項目を直接読むようになったら（段階 4）なくす。個別の判断を当てる前の URL（`originalRoutes`）を規則でもう一度組み立てているのも、ここだけである（読む側が、規則で組み立てた URL を確定した URL に置き換える仕組みを残しているため）。
- **起点の画面の場所の書き方が、形の上では変わった。** 解いた形の「どこから始まるか」（`starts`）は、ボタンのある表の名称から「表「…」の行のボタン」と書く。文書の形のときは、入れ子の要素の操作では要素の名称（作業項目）、番号で指す操作では並びの項目の名称から書いていた。このサンプルでは同じ文字になるので、生成物は変わっていない。
- **画面遷移定義書**は、まだ文書の形である。画面を指す欄（`source`）は `SCR-` の ID になったが、参照ではなく文字列で持っている（次の種類で項目の形にする）。
- **詳細設計は、ダッシュボードの構成（絞り込みの入力・区画・上部の操作）・ビューの列・エンティティの項目の並びを、まだ業務モデルから読んでいる**（画面設計書の一覧と詳細・一覧画面の画面遷移設計・テーブルアクセス設計書）。たどれる範囲は、画面を解いた形（`reach`）から読むようにした。ボタンと表の名称も、解いた形から引く。残りを画面と検索条件の項目から読む形にするのが、次の作業である。

### 方針から項目を足す仕組み（2026-11-26 に合意）

システム化のために要る項目は、全体の判断から規則で足す（ADR-0042「項目の出どころ」）。例として、同時更新を版で検出する方式を 2 歩で作る。

| 歩 | やること | 確かめること |
|---|---|---|
| 1. 項目と列まで（済） | 方式の指定（対象は区分）から、エンティティに項目「版」を足す。テーブルの列・DDL・行のクラスまで届く。値はまだ使わず、常に 0 | 指定を外すと項目も列も出ない。入れ子で持つ要素と、区分の違うエンティティには足されない。業務の画面には出ない |
| 2. 更新のたびに確かめて進める（済） | 更新する操作に、読んだときの版を運ぶ入力・版が同じという前提・版を 1 進める効果を足し、処理・Mapper・画面・断りの文まで通す | 古い画面からの更新が、確認か確定で断られる（Service と HTTP の検証テスト） |

書き方について決めたこと:

- 新しい書き方は作らず、既存の「方式と対象の指定」（`specifications`。`target`・`rule`・`settings`・`reason`）を使う。対象に区分（`CLS-`）を書くと、その区分のエンティティすべてに当たる。区分を対象にした指定が全体の判断、要素を対象にした指定が個別の判断になる。
- 方式の中身（何を足し、下流がどう使うか）は、変換定義の規則として書く。人が書くのは「どの方式を、どこに、どの設定で」だけである。
- 入れ子で持つ要素（親のあるエンティティ）には足さない。親の版で守る。
- 足した項目は、業務から来た項目と同じ形（`FLD-`）で、`addedBy` と根拠に指定の ID を持つ。

歩 2 で足した、定義の語彙（どれも方式が使うためのもので、業務モデルには書かない）:

- **画面が運ぶ入力**（操作の入力の `carried`）。人は入力せず、画面を出すときに受け手から読んで、hidden 項目で持ち回す。画面定義書の `carried` に読み元を持つ。
- **読んだ行の値と入力の比較**（前提の `equals: $入力名`）。処理設計書の「読んだ行で確かめる」手順として出る。
- **自動で入る版**（効果の `auto: revision`）。値の式は持たず、プログラム設計が「その項目の、次の値」にする。
- **親の行を読む手順と、親の行で確かめる検査**（処理設計書の `read-owner` と `checkMode: owner`）。受け手が入れ子の要素の操作で、親の値を条件にする前提に使う。このサンプルでは「作業項目を済にする」が、親の TODO のバージョンを確かめてインクリメントする。

歩 2 で残したこと:

- **確かめるのは、操作の画面を開いてから確定するまで。** 一覧を見てからボタンを押すまでの間の更新は、確認画面に最新の内容が出ることで気付く形にしている。確認の検査を持たない操作（コメントの追加など）は、確認では断らず、確定で断る。
- **アプリを複数動かす構成では足りない。** 読んだ行の版を比べる形は、操作を 1 つずつ順番に実行する仕組み（`writeConcurrency: local-serialized`）を前提にしている。その構成にするときは、更新の条件に版を入れ、0 件なら断る形に替える。

歩 1 と歩 2 のどちらも、生成したアプリ（`app/`）が変わる。`app/` の再生成は、Windows では `scripts/generate-app.ps1`、それ以外では `scripts/generate-app.py` で行う（同じ結果になる。GitHub Actions が両方の `-Check` / `--check` を実行する）。

## 段階ごとの確かめ方

- `python3 samples/todos-sysdev/scripts/design-map.py` で 4 枚を作り直し、「出発点」の表の数字を比べる。
- `generate samples/todos-sysdev` で生成物が最新であること（`TodosSysdevTest`）。
- `scripts/generate-app.ps1 -Check` で、アプリの再生成に差分が無いこと。意図して変えた所だけが差分に出ること。
- `scripts/verify-app.ps1`（`verify-app.sh`）で、アプリのテストと独立ビルドが通ること。
- 定義書・設計書の見え方は、機械の検査とは別に、オーナーがレビューする。

## 気を付けること

- **本体に足りない機能が見つかる可能性があります。** 確定の共通の仕組み（段階 5）と、項目から定義書を組み立てるビュー（段階 3・4）は、いまの YDE の変換とビューの語彙で書けるかを、最初の 1 種類で確かめてから広げます。
- **詳細設計は、段階 3 が終わるまで業務モデルを読み続けます。** 段階 2 で 3 種を移した後も、ダッシュボードの構成と、たどれる範囲を、詳細設計の 8 種が業務モデルから読んでいます。
  どちらも画面と画面遷移の情報なので、画面を項目の形にする段階 3 で移します（2026-11-26 に、段階 2 の完了の条件をこの形に直しました）。
- **足した 3 種は、条件と計算の式を業務モデルの式のまま持っています。** 設計の言葉（項目・比べ方・値の並び）に置き直すかどうかは、段階 3 で定義書の見え方と一緒に考えます。データの決まりが読む項目も、入れ子の項目を設計 ID へ対応付ける手段ができるまで、業務モデルの場所で持っています。
- **補正後業務モデルを作る変換定義は、段階 5 まで残ります。** この 7 本は、項目への個別の判断（たとえばタイトルを最大 60 字にする）を、画面・メッセージ・テーブルまで届ける実装でもあります。
  いまは各定義書が値を業務モデルから写しているので、先になくすと判断が届かなくなります。項目の形にして ID で指すようにした後（段階 3・4 の後）に、項目へ直接当てる形へ置き換えます。
  この仕組みを確かめるテストが 3 クラスあります（`TodosTypeCorrectionsTest`・`TodosFieldCorrectionsTest`・`TodosDesignTargetsTest`）。
- **共通型への補正は、段階 5 でやめます。** ADR-0042 で、共通型を直すときは業務モデルを直すと決めました。共通型への補正を確かめるテストは、そのときにオーナーと確かめてから外します。
- **段階 3・4 は大きい作業です。** 1 種類ずつ移し、移すたびにアプリが変わらないことを確かめます。途中は、文書の形と項目の形が混ざった状態になります。
- **TODO 管理に無い形は、まだ確かめていません。** いまの変換定義は業務モデルを一般的に読みますが、対応している式や構造は todos にあるものが中心です（[アプリの生成と独立ビルド](application-generation.md)・README「いま計算で作れないもの」）。段階 8 で確かめます。
