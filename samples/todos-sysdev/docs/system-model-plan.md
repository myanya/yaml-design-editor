# 抽象システムモデル・具体システムモデルへの移行計画

業務モデルから 3 つの変換でソースコードまで作る形へ、いまの設計の体系を移す計画です。
2026-11-24 のオーナーとの議論の結果をまとめたもので、進捗は [ロードマップ](../../../docs/ROADMAP.md#p53-業務モデルから作る設計書体系とアプリ生成)の R53-12 で管理します。
決定は、段階 0 で ADR にします。それまでは、この文書の「合意したこと」が方針です。

## 目指す形

```text
業務モデル
   ↓ アーキテクチャマッピング
抽象システムモデル（基本設計）      ビュー = 定義書
   ↓ 技術スタックマッピング
具体システムモデル（詳細設計）      ビュー = 設計書
   ↓ コードマッピング（前半）
プログラム設計（配置）
   ↓ コードマッピング（後半）
ソースコード
```

LSI の論理合成・テクノロジマッピング・配置配線にならった形です。
理想のファイルの種類と依存関係は [理想のファイル体系](design-ideal-graph.html)、いまの姿は [ファイル単位の生成グラフ](design-file-graph.html) にあります。

## 合意したこと

- **言葉**: 定義書は基本設計の成果物、設計書は詳細設計の成果物です。どちらも、それぞれのモデルのビューです。
- **人が書くもの**: 業務モデルと、各段の判断だけです。判断は「全体の判断（同じ種類すべてに当てる方針）」と「個別の判断（特定の要素だけの決定）」の 2 種類で、段ごとに分けて置きます。
- **業務モデルは直接直す**: 業務の事実の誤りは業務モデルを直します。変換の前に業務モデルを補正する層は置きません。
  業務モデルに本来要らない情報を足す必要が出たら、そのときに考え直します（いまは見つかっていません）。
- **判断の置き場**: 判断は、それを言える最初の段に 1 回だけ書きます。判断は、対象より下流のすべてに届きます。
- **補正前の結果**: 層ではなく、比較の相手です。「個別の判断が 0 件ならこうなる」を表し、確定したモデルとの差は、すべて個別の判断で説明できます。
- **プログラム設計**: `application-*.yaml` にあたるものを、詳細設計から分けます（置き場所も分ける）。

## 守る性質

図と検査で確かめられる形にしたものです。

1. 各段の変換は、1 つ前の段のモデルだけを読む。
2. 1 つ前の段のモデルだけで、次の段を作れる（要る情報は、すべて前の段が運ぶ）。
3. 抽象システムモデルには、技術スタックを替えると変わる語が現れない。
4. 各要素は、元になった前の段の要素を指す。
5. 判断は入力である。生成物は直さない。判断は ID で対象を指し、再生成のたびに当て直す。対象が消えたら止まる。
6. ビューは射影である。定義書・設計書にしかない情報はない。

## まだ決めていないこと

| 論点 | 仮の置き方（理想のファイル体系の図） |
|---|---|
| 抽象システムモデルの要素の種類 | 10 種（型、エンティティと項目、状態と遷移、データの決まり、操作、一覧の検索条件、画面、画面遷移、エラー、メッセージ） |
| ファイルの粒度 | 未定。操作と画面は単位ごとに分ける案 |
| 抽象と具体の境 | 「技術スタックを替えても変わらないものが抽象」。確認画面・画面遷移・URL は抽象、クラス名・Mapper・SQL の型は具体 |
| Java の型対応表とテーマの置き場 | 詳細設計の全体の判断 |
| DDL・CSS・入力エラーの文の出し方 | プログラム設計を通してソースにする（いまは設計書から直接出している） |

## 進め方

どの段階も、生成したアプリが変わらないことを確かめながら進めます（下の「段階ごとの確かめ方」）。
体系を組み替える作業なので、意図して変える所を除き、`app/` の中身は同じままのはずです。

| 段階 | やること | 完了の条件 |
|---|---|---|
| 0. 決定を残す | 合意したことを ADR にする。[目指す形への対応](design-target-map.html) の段を、この計画の段（補正後業務モデルを持たない形）に直す | ADR が承認され、3 枚目のページが新しい段で外れを数える |
| 1. 業務モデルを直して補正をなくす | TODO の ID の説明の食い違い（`COR-001`）を、samples/todos の業務モデルで直して写す。補正後業務モデルを作る途中経過の変換定義をなくす | 補正の変換定義がなくなり、`entities.yaml` の中身は説明以外変わらない |
| 2. 抽象システムモデルに 3 種を足す | 状態と遷移、データの決まり、一覧の検索条件を、項目の形で基本設計に置く。詳細設計の導出を、業務モデルではなくこれらを読む形に変える | 詳細設計の導出が業務モデルを読まない（段を飛ばして読む流れが 0） |
| 3. 基本設計を項目の形にする | 操作 → 画面 → 画面遷移 → エラー → メッセージの順に、文書の形から項目の形へ変える。定義書を、項目から組み立てるビューにする。ドメイン定義書はビューだけにする | 基本設計に文書の形のファイルが無い。定義書の見え方はオーナーがレビューする |
| 4. 詳細設計を項目の形にする | テーブルへの読み書き → 状態の型 → 処理の手順 → 画面の部品と入力 → URL と遷移 → セッション・エラーの扱いの順に変える。設計書をビューにする | 詳細設計に文書の形のファイルが無い |
| 5. 重複した仕組みをなくす | 項目が ID で互いを指すようにして、名前の付け替え表と、確定した定義書を重ねたモデルをなくす。確定の変換定義（20 本がほぼ同文）を共通の 1 つにする | 付け替え表が 0 枚。確定の仕組みが 1 つ |
| 6. 判断をまとめ直す | 人の入力を、段ごとの全体の判断と個別の判断に置き直す | 入力が、段ごとに 2 種類だけになる |
| 7. プログラム設計を分ける | `application-*.yaml` と検査記録を `design/program/` に移す。DDL・CSS・入力エラーの文を、プログラム設計を通して出す。詳細設計がプログラム設計を読む線をなくす | 後ろの段を読む流れと、段を飛ばして読む流れが 0 |
| 8. 別の業務モデルで確かめる | TODO 管理と形の違う業務モデルを 1 つ用意し、同じ変換定義で設計とアプリを作る | 変換定義を直さずに通る。直した所は、足りなかった形として記録する |

段階 1 と 2 は互いに独立です。段階 3 は 2 の後、段階 5 は 3 と 4 の後に行います。

## 段階ごとの確かめ方

- `python3 samples/todos-sysdev/scripts/design-map.py` で 4 枚を作り直し、「出発点」の表の数字を比べる。
- `generate samples/todos-sysdev` で生成物が最新であること（`TodosSysdevTest`）。
- `scripts/generate-app.ps1 -Check` で、アプリの再生成に差分が無いこと。意図して変えた所だけが差分に出ること。
- `scripts/verify-app.ps1`（`verify-app.sh`）で、アプリのテストと独立ビルドが通ること。
- 定義書・設計書の見え方は、機械の検査とは別に、オーナーがレビューする。

## 気を付けること

- **本体に足りない機能が見つかる可能性があります。** 確定の共通の仕組み（段階 5）と、項目から定義書を組み立てるビュー（段階 3・4）は、いまの YDE の変換とビューの語彙で書けるかを、最初の 1 種類で確かめてから広げます。
- **共通型を直したときの届き方が変わります。** いまは補正を当ててから型を解き直すので、共通型への補正が、それを使う全項目に届きます。段階 1 の後は、共通型を直すなら業務モデルを直します。
- **段階 3・4 は大きい作業です。** 1 種類ずつ移し、移すたびにアプリが変わらないことを確かめます。途中は、文書の形と項目の形が混ざった状態になります。
- **TODO 管理に無い形は、まだ確かめていません。** いまの変換定義は業務モデルを一般的に読みますが、対応している式や構造は todos にあるものが中心です（[アプリの生成と独立ビルド](application-generation.md)・README「いま計算で作れないもの」）。段階 8 で確かめます。
