# エンティティ定義書の見直し案

変換方針は [ADR-0039](../../../docs/decisions/0039-finalized-design-items.md)で合意済み。
以下の属性とビューの案はオーナー確認済み。実装済みの範囲と残る接続は、次の生成処理の文書で区別する。
保存する文書と生成処理への接続は、[保存構造と生成処理の案](entity-generation-contract.md)で具体化する。
エンティティ定義書とテーブル設計書のオーナーレビューは継続中。

既存の個別・横断・CRUD のビューとテーブル生成は、同じ確定項目を読む形へ切り替えた。
区分の追加・指定も合成し、未反映の補正や未対応の方式があれば確定前に停止する。
次の区切りは、実際のビューを使った内容のレビューと、区分以外の追加・方式を一つずつ接続することである。

## 見直し前に確認した問題

| 確認した箇所 | 現在の扱い | 見直す点 |
|---|---|---|
| `basic-type-list` の項目と論理型 | 基底・制約・参照先・要素の型などを保持 | 共通型と項目の情報を解決した共通の結果を用意する |
| `entity-definition-items` | 各列の式で項目固有の値と共通型の値を選択 | 確定項目の値を読む。フォームと同じ意味にする |
| `BusinessModel.fieldTerm` | 共通型と異なる制約を `overrides` に保持 | 共通型と同じ値を明記した場合も、その指定を保持する |
| `basic-entities` の項目の合成 | 同じキーをまとめ、多くの属性は最初の出現を採用 | 複数の出現にある指定と根拠を失わず、食い違いを検査する |
| `basic-types` の参照 | 主に参照先エンティティへ置き換える | 関係名・参照先を絞る条件・複数の対象を表せる形を検討する |
| 項目の入れ物 | 配列・マップとも `itemType` などへ写し、子項目は `fields` に配置 | 配列の要素・マップの値・object の子項目を区別し、任意の深さで保持する |
| 操作と C/U | 操作の `writes` と別の `crud` 表があり、ビューは `writes` 側の記録を読む | 操作と項目の関係を一つの正とし、表の並びはビューで作る |
| 区分 | 人が書く台帳からビューがたどる | 確定項目に区分への参照を含める |

この表は見直し前の問題を記したもの。現在の経路と検証結果は生成処理の文書にまとめる。

## エンティティ自体の属性案

| 情報 | 導出・指定の元 | 確定項目での扱い |
|---|---|---|
| 設計項目 ID・業務上のエンティティ名 | 業務モデルの同一性。追加は追加元の識別 | 補正の対象と後段の参照に使う。表示順と分ける |
| 名称・説明 | 業務モデル、補正、追加 | 確定した文字と出どころ |
| エンティティ区分 | 人の指定 | 区分の設計項目への参照 |
| 識別に使う項目 | 業務モデルの ID 定義 | 項目への参照。採番の有無とは分ける |
| 採番 | 業務モデルの採番、方式の指定 | 対象項目・接頭辞・桁などを YDE の値のまま保持 |
| 親との関係 | 保有するエンティティと項目、入れ物の構造 | 親への参照と保有する項目への参照。単純な参照関係と区別 |
| 適用するアーキテクチャ | 補正・指定項目一覧 | 方式・対象・利用する既存項目への参照 |
| 導出元と追加元 | 業務モデル、手書き追加、規則 | 一つの項目に関わる複数の根拠を保持 |

区分の定義そのものを新しく作ることは追加、既存エンティティに区分を割り当てることは指定、と分類する案。
現行の台帳は両者をまとめて持つため、移行時に情報を分ける必要がある。

## 項目の属性案

| 分類 | 保持する属性 | 注意点 |
|---|---|---|
| 識別と場所 | ID、所属エンティティ、キー、親の項目、項目の経路、順序 | 名前付き object の同じ子項目を別の場所で使う場合も区別できること |
| 説明 | 名称、説明 | 補正後の値と複数の導出元を保持 |
| 型 | 論理型への参照、基底の種類 | 名前の無い配列などは論理型への参照がなくても正常 |
| 必須 | 無条件の `required` | 単なる未指定と、条件付き・段階付きで判断が必要なものを区別 |
| 文字列 | `minLength`、`maxLength`、`pattern` | 型と項目の指定を合成。複数の正規表現を一つだけに減らさない |
| 数値 | `min`、`max` | `0` を値なしとして扱わない。実装言語や DB の型は詳細設計 |
| 選択肢 | `values` の `value` と `label` | コード生成は値を使う。表示名も失わない |
| 初期値 | `default` と、指定の有無 | `false`、`0`、空文字、空配列をそのまま保持 |
| 自動設定 | `auto` | `created`、`updated`、`revision` の意味を保持。適用される範囲も追えること |
| 表示上の性質 | `format`、`multiline` | 既存の値を保持。文字列の値の形式と、日付などの表示形式を混同しない |
| 参照 | 対象、関係名、ID や範囲の絞り込み | 一つのエンティティ名だけへ縮めない。型の継承で重なった条件も保持 |
| 配列 | `item`、`unique` | 配列自身と要素それぞれの型・制約・根拠を区別 |
| マップ | `value` | 配列の要素とマップの値を区別 |
| object | `fields`、必要ならエンティティへの参照 | 値の部品と、同一性を持つ入れ子のエンティティを区別 |
| 根拠と状態 | 導出・継承・補正・追加の元、解決状態 | 項目全体だけでなく、各属性の値を決めた根拠を追えること |

同じ項目の説明が複数の業務文書で異なる場合は、食い違いとして指摘し、補正で代表の説明を指定する。
例えば `todo.id` の一覧側の説明と個票側の説明を、定義側・ファイル順だけで選ばない。元の説明と導出元はすべて保持する。
`basic-targets` は説明を値ごとにまとめて全出現を残し、`basic-descriptions` は食い違いを指摘して補正を採用する。
現在は側面間の型・制約・入れ子の構造を比較し、食い違う場合は生成を止める。

参照や入れ子構造はエンティティ定義の情報として保持する。
テーブルへ変換できるかの判定は詳細設計で行い、基本設計で元の構造を落とす理由にしない。
再帰する型・エンティティへの参照は、無限に展開せず参照として保持する必要がある。
その場合の項目の経路と個別指定の表現は、保存スキーマを決める際に具体化する。

## 入れ物の表現案

YDE の構造と対応する `item`・`value`・`fields` を使う案を勧める。
次は現在の保存構造の説明例であり、ID と根拠の一部を省略している。

```yaml
id: FLD-todo.comments
key: comments
base: array
required: false
default: []
item:
  type: TYP-common.コメント
  base: object
  fields:
    - key: body
      type: TYP-text
      base: string
      required: true
      multiline: true
```

説明例は子項目の ID、ほかの子項目、根拠を省略している。
配列の中がさらに配列なら `item` の中にも `item` があり、マップなら `value` がある。
ビューが一行に展開するときには、対象エンティティと項目の経路を使って場所を示す。
既存の `itemType` などから移行済み。利用箇所の子は `FLD-todo.comments.item.body` のように入れ物を含む ID を持つ。

## 操作と C/U の案

操作 ID・名称・導出元と、「どの操作がどの項目を作成・更新するか」の関係を確定項目に持つ。
アーキテクチャが追加した項目への処理も、規則を根拠として同じ関係に含める。
操作一覧の書く項目と C/U 表は、この関係を別の並べ方で表示する。
書込のない項目も行として残す。空欄は、その操作による C/U の記録がないことを表し、R/D がないことを意味しない。

`auto` や採番があるだけで、すべての操作に C/U を推測して付けない。
適用される処理と範囲を根拠から特定する。既存の操作効果から確実に導出できる範囲を先に移す。
自動設定・アーキテクチャによる処理との関係は、操作の生成との接続時に確認する。

## ビューの構成案

| 区画 | 主に見せるもの |
|---|---|
| 概要 | 名称・説明・区分・識別項目・採番・親との関係・適用方式 |
| 項目一覧 | 経路・名称・論理型・基底・必須・初期値・自動設定 |
| 型と制約 | 文字数・数値範囲・正規表現・選択肢・表示形式 |
| 関係と入れ子 | 参照先と条件・保有関係・配列の要素・マップの値・object の子項目 |
| 操作と C/U | 操作と項目の関係。操作一覧と C/U 表は同じ関係から作る |
| 根拠と指摘 | 導出・継承・補正・追加の元、未解決と競合 |

保存する設計情報と、一覧の列は一対一にしない。属性は失わず、読む目的で表示を分ける。
個別表示は対象エンティティで絞り、横断表示は複数エンティティを並べる。同じ属性は同じ確定値を読む。
正規表現など適用対象の広い属性については、基底型と YDE の定義に従って適用の有無を判定する。

## 確認に使う具体例

| 入力・変更 | 期待する結果 |
|---|---|
| TODO のタイトル | 最大文字数 100 と改行の制限が、個別表示と横断表示で一致 |
| 共通型を最大 200 に補正。項目に個別指定なし | 項目の確定値は 200。詳細設計の入力も同じ値 |
| 共通型を最大 200 に補正。項目にも元から最大 100 と明記 | 項目の確定値は 100。明記された指定を根拠として残す |
| 共通型は最大 100。項目だけ最大 200 を指定 | 型を緩める指定として指摘 |
| 作業項目の `done` | 必須 `true` と初期値 `false` が別々に確認できる |
| TODO の `tasks`・`comments` | 初期値 `[]` と、初期値がない項目を区別 |
| TODO の `tags` | 配列自身の `unique` と、要素の参照先・関係名を確認できる |
| TODO の `comments` | 名前付き object の子項目の型・制約まで確認できる |
| 一覧と個票で同じ項目の指定が食い違う | 根拠を両方示す。最初の出現を選んで隠さない |
| 楽観ロックの規則を適用 | 必要な項目と処理の設計情報、生成規則の根拠がそろう |
| 楽観ロックに使う既存項目を指定 | 項目を重複追加せず、成立条件を検査 |
| 二つの規則の表示名が競合し、個別指定で名称を選択 | 名称は個別指定へ確定。各規則の成立条件は引き続き検査 |
| 規則を無効にして、その追加項目への補正が残る | 対象がなくなった補正を指摘 |
| 論理型の参照切れ | 「制限なし」へ置き換えず、解決できなかった理由を表示 |

確認例全体の完了を意味しない。型と個別補正・区分・C/U・DDL の照合は関連テストで扱い、楽観ロックなどの方式の展開は残る。
条件付き必須・項目間の業務規則・R/D の導出は保留する。
画面の配置や入力部品の指定は画面系、SQL・Java の具体的な型は詳細設計で扱う。
