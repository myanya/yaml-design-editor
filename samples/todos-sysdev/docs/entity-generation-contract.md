# エンティティ定義の保存構造と生成処理の案

[属性とビューの案](entity-definition-plan.md)はオーナー確認済み。
この文書は [ADR-0039](../../../docs/decisions/0039-finalized-design-items.md)を実装へつなぐための具体案。
保存構造と生成処理の方針はオーナー確認済み。以下の全体に移行済みという意味ではない。

最初の移行単位として、スキーマの項目と型に明記された属性を `declarations` に保持し、導出記録を生成するところまで実装した。
共通型と等しい値の明記・型の連鎖・原文の文書と場所・入れ子を保持する。`false`・`0`・空文字・空配列もキーの有無と区別する。
導出記録は `id: DRV-business` と `model` を持ち、`model` の中は業務モデルの項である。
記録内の識別子を通常の参照先にしないため、現在の保存スキーマでは `model` を `any` としている。入力と確定項目の詳細なスキーマは次の移行単位で整える。
補正・追加の合成、規則の競合検査、確定項目への切り替えは未実装であり、既存のビューと詳細生成は現在の経路を使っている。
宣言の場所を保持する対象はスキーマの `root`・`definitions` とその子で、操作の入力の原文の場所はまだ対象外。
業務モデルの既存の展開には深さの上限も残っている。次の移行単位では、再帰する型を参照として保持し、上限で省略された情報を確定した情報として扱わないようにする。

## 保存する文書

| 場所の案 | 内容 | 編集する側 |
|---|---|---|
| `design/basic/derived/model.yaml` | 業務モデルから取り出した宣言と導出元 | 生成 |
| `design/basic/corrections.yaml` | 方式・対象などの指定と、設計項目の補正 | 人 |
| `design/basic/additions.yaml` | 業務モデルからは導けない設計項目の追加 | 人 |
| `design/basic/expanded/changes.yaml` | 規則が作った追加・変更の候補と成立条件 | 生成 |
| `design/basic/entities.yaml` | 確定したエンティティ・項目・操作と C/U の関係 | 生成 |
| `design/basic/types.yaml` | 確定した論理型 | 生成 |

確定項目の配置と設計項目 ID は、可能な限り現在のものを引き継ぐ。
`basic` と `detail` は設計の段階であり、各段階の中の「準備・展開・確定」とは別である。
導出項目一覧には、アーキテクチャによる追加を混ぜず、業務モデル由来の宣言を記録する。
中間結果をすべて保存する必要はなく、準備の結果や規則間で渡す結果は生成計画の中で持てる。

## 生成対象の識別子と参照先を分ける

設計項目の ID（例 `FLD-todo.title`）を通常の索引に登録するのは確定項目だけとする案。
導出・追加・変更候補は、同じ文字を `designId` などの生成対象の識別子として持つが、確定項目の出現としては登録しない。
記録そのものへのリンクが必要なら、記録用の ID（例 `DRV-fields`・`ADD-001`）を別に持つ。
補正の対象は、引き続き設計項目の ID で指す。

通常の参照先と、生成中に対象を探す仕組みを分ける。
生成中の対象解決は、その段階でそろった導出・追加の集合を使い、ディスクに残った前回の確定項目へ頼らない。
新しい項目への補正も生成中に解決でき、消えた対象への補正は前回の生成物が残っていても指摘する必要がある。
最初の生成前に確定項目が存在しない場合も、入力の形の点検と、生成計画内の対象解決を分けて扱う。

### 小さなワークスペースで確かめた結果

導出値 100 と確定値 200 を別文書に置き、項目を直接読むビューと、その項目への参照をたどるビューを CLI で実行した。
両構成とも通常の検証はエラー・警告 0 件だった。

| 導出側の識別子 | 直接読むビュー | 参照をたどるビュー |
|---|---:|---:|
| 確定側と同じ値を `type: id` で登録 | 100 | 100 |
| 生成対象の識別子を `type: string` とし、確定側だけ ID として登録 | 200 | 200 |

同じ ID の複数文書出現は、YDE では段階的な詳細化として正当であり、重複エラーにはならない。
参照先の値は定義出現・索引順などに従って選ばれるため、保存しただけでは確定側を選ぶ保証にならない。
検証はこの識別方法に限ったものであり、100 から 200 への補正・型解決・確定生成を実行したものではない。

## 宣言と確定値の形

導出側には、解決前に明記されていた指定と、型への参照を残す。
共通型と同じ値であっても省略しない。原文でキーがあるかどうかを保持し、解決済みの値の比較から逆算しない。
`FieldDef` の値だけでは多くの属性で既定値と未指定が同じ形になるため、単に `overrides` の比較を変えるだけでは足りない。
型の定義と使う側の宣言を、元の場所まで追える `FieldDeclaration` として型解決側で保持し、業務モデルの項へ写す。

次は導出記録の説明例であり、現在の設計スキーマにそのまま書く形式ではない。

```yaml
id: DRV-fields
records:
  - designId: FLD-todo.title
    declarations:
      - schema: todo-list
        source: todo.title
        declared:
          type: TYP-common.一行の文
          required: true
          maxLength: 100
```

複数の文書から来る指定は `declarations` の複数の記録にする。
共通型の継承の連鎖も同じように保持し、途中の型で明記された制約を失わない。
この例の `declared.type` は生成中の型の識別子で、前回の確定型を参照して解決するものではない。
実際の宣言元の文書・場所は、共通の型の定義と利用箇所の両方まで追えるようにする。

共通型を 200 に補正しても、この項目は明記した制約により 100 となる。
確定側では、通常の表示と後段が読む属性を直接持つ。

```yaml
id: FLD-todo.title
key: title
label: タイトル
type: TYP-common.一行の文
base: string
required: true
maxLength: 100
```

この例は、ほかの制約・導出元・根拠の情報を省略している。
根拠は属性ごとに記録し、例えば最大文字数なら、共通型の補正後の値と、採用した個別の指定の両方へたどれるようにする。
「制限なし」「対象外」「解決できていない」は状態として区別し、`maxLength` の値へ文字を混ぜない。
初期値などの `false`・`0`・空文字・空配列は、キーの存在とは別にそのまま保持する。

## 補正・指定・追加の役割

補正・指定一覧は、同じ分類の中で次の二つを区別する案。

| 内容 | 読む時点 | 例 |
|---|---|---|
| 生成を左右する指定 | その規則の実行前 | TODO の区分、適用方式、楽観ロックに使う既存項目 |
| 生成した設計項目への補正 | 候補をそろえて合成するとき | 最大文字数、名称、生成した項目の初期値 |

規則が読む属性を宣言し、その属性への指定を事前に反映する。
最後の補正で規則の適用条件が変わるような定義は、そのまま通さず、依存関係と処理段階を見直す。
利用者がファイル名や手順番号を調整して適用順を作る形にはしない。

追加一覧では、項目自体の追加と、既存項目の属性の指定を区別する。
例えば区分 `CLS-transaction` の定義は追加、TODO をその区分に所属させることは指定である。
規則が作る追加も同じ設計項目の形を使い、作成元と変更理由を付ける。
候補の ID・キーの衝突、同じ属性への競合、対象の無い補正は、合成前後の検査対象にする。

## 既存の部品との接続

| 処理 | 利用する部品 | 必要な変更 |
|---|---|---|
| 宣言の取り出し | スキーマの読み取り・型の解決、`BusinessModel` | 未指定と明記を保持し、型の連鎖と原文の場所を残す |
| 入力の選択 | 既存の Query と生成計画の文書の重ね合わせ | 指定した入力と依存先の新しい結果を渡す。表示用ビューから設計値を再構成しない |
| 追加・変更候補の組み立て | `SemanticTransform` | 設計上の規則は YAML の変換定義として書く |
| 競合の判定 | 既存の判定と検査、Rewrite の競合という規律 | 候補を対象と属性でまとめ、優先順位と成立条件を区別する |
| 合意した変更の反映 | `TermChanges` などの項の変更 | 検査した候補から変更を組み立てる。現在の順番に上書きする処理だけでは競合検査にならない |
| 型と制約の解決 | `SchemaTree` の型の連鎖と狭める規則、定義の点検 | 設計項目を同じ意味の型定義へ対応付け、補正後の型を解決する。解決規則を複製しない |
| 規則の順序 | `Generators` の依存関係と循環検出 | 依存していない先行出力を暗黙に読まないよう、各段階へ渡す結果を限定する |
| 確定結果の反映 | 生成計画・既存の変更セットと保存 | 途中の結果を順次保存せず、検証した結果を既存の適用経路へ渡す |

現在の生成は `dependsOn` を持つが、入力の読み取りでは実行済みの出力全体を重ねている。
依存関係を宣言するだけでは、読む結果を依存先に限定したことにはならない。
また、現行の補正はファイルと位置の順で適用するため、合意した競合の解決を担う処理が別途必要である。

Core Calculus では、選択は Query、値と条件は Expression / Predicate、候補の組み立ては Construct、変更は Rewrite として扱う。
集合からの候補の収集・グループ化には既存のクエリと変換を使い、型の合成と検査は既存の意味を共有する。
専用の設計式エンジンは追加せず、不足する共通の処理だけを具体的な反例とともに検討する。

## 失敗時と再生成

競合・参照切れ・必要な成立条件の未解決があれば、確定した結果として後段へ渡さない。
判定できないものを、検証に指摘が出なかったという理由で充足にしない。
候補と理由はレビューできるようにし、保存済みの前回の結果があれば、その結果が今回の入力に対応していないことを示す必要がある。
生成の処理自体が成立しないものは計画の誤りとし、通常の検証エラーを許す指定で回避しない。

後段の生成は、同じ計画で作った新しい確定項目を読む。
保存した項目を読むレポートなどは、生成物の最新判定との接続も必要になる。
すべての入口で独自に補正や型解決をやり直す形にはしない。

## 移行の単位

1. **宣言を保持する**: 共通型と同じ値の明記、型の連鎖、複数文書の指定、原文の場所を業務モデルの項に残す。既存の導出結果との関係をテストする。
2. **入力と確定項目のスキーマを作る**: 記録の識別と設計項目の ID を分け、入れ子を `item`・`value`・`fields` で保持する。
3. **合成と確定の処理を作る**: 手書きの指定・追加と、規則による候補を合成し、競合・型・参照・成立条件を検査する。
4. **読む側を切り替える**: フォーム・項目一覧・操作一覧・C/U 表が同じ確定項目を読むようにする。影響するテーブル生成の入力も同時に接続する。
5. **出力を照合する**: 属性案の確認例に加え、前回の確定結果への依存、規則の順序、未解決の扱い、再生成で変更が増えないことを確かめる。

テーブルの設計内容のレビューは、エンティティ定義書のレビュー後に続ける。
既存のテーブル生成への接続確認は、今回の変更で補正後の値が届かなくなることを防ぐために行う。
段階ごとの途中実装を、設計書全体や確定処理全体の完了とは扱わない。
