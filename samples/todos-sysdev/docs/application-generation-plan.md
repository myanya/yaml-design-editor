# 設計の配置整理と Spring Boot アプリ生成の作業計画

基本設計と詳細設計をそれぞれ入力・導出・合成・確定に分け、確定項目から独立した Spring Boot プロジェクトを生成する。
配置とビルドの分離はオーナーと合意済み。配置の移行、アプリの基本構造、データアクセスの生成を接続し、業務処理の共通部分へ進めた。設計書の内容レビューは継続する。
決定は [ADR-0041](../../../docs/decisions/0041-design-layout-and-independent-app.md)、進捗は [ロードマップ](../../../docs/ROADMAP.md#p53-業務モデルから作る設計書体系とアプリ生成) で管理する。

## 到達点

- 業務モデルと手書き入力から設計の確定項目を再生成し、同じ確定値をビューとコード生成で読む。
- `app/` に Java・MyBatis XML・Thymeleaf・CSS・設定・ビルド定義をそろえる。
- `app/` を別の場所へコピーしても、Java 21 と通常の依存取得環境だけでテスト・ビルド・起動できる。
- ログインなしで、現行の業務モデルにある一覧・詳細・操作・確認画面と、実装対象にした入力検査・状態・前提・データの決まりを確認する。
- 同じ入力からの再生成に差分がなく、補正の変更が設計・コード・動作へ伝わる。
- YDE 本体のモジュール構成・ビルド・起動と競合しない。

コードに足りない内容は設計の入力か生成規則へ戻す。生成コードだけに手修正や TODO の仮実装を残して完了とはしない。
未対応の意味や構造は生成前に具体的な対象と理由を示し、対応するか対象外とするかを明示する。機械的な生成の成功とオーナーのレビュー完了を分ける。

## 移行後の配置

設計の配置は移行済み。`app/` は現在の確定設定から生成する。業務コードの生成は後続で追加する。

```text
todos-sysdev/
├─ .yde/                         形式・生成規則・ビュー・文字のひな形
├─ design/
│  ├─ basic/
│  │  ├─ inputs/                手書きの補正・指定・追加
│  │  ├─ derived/               導出項目
│  │  ├─ composed/              合成途中の候補・検査記録
│  │  └─ final/                 基本設計の確定項目
│  └─ detail/
│     ├─ inputs/                手書きの補正・指定・追加・型対応表
│     ├─ derived/               導出項目
│     ├─ composed/              合成途中の候補・検査記録
│     ├─ final/                 詳細設計の確定項目
│     └─ reports/               レビュー用の DDL など
└─ app/                          独立した Spring Boot プロジェクト
   ├─ README.md
   ├─ .gitignore
   ├─ settings.gradle.kts
   ├─ build.gradle.kts
   ├─ gradle.properties
   ├─ gradlew / gradlew.bat
   ├─ gradle/wrapper/
   └─ src/
      ├─ main/java/             Java パッケージごとのソース
      ├─ main/resources/        設定・SQL・Mapper XML・HTML・CSS・JS
      ├─ test/java/
      └─ test/resources/
```

`inputs/` などの中は、エンティティ・画面・テーブルなど対象ごとに分ける。
ほかの設計書の手書き入力は、対象の設計段階に応じて基本・詳細の `inputs/documents/` へ分けた。
補正・指定・追加の項目 ID と理由を保持し、分割する入力文書には重複しない文書 ID を割り当てる。別の段階の対象を誤って指定した場合は検査する。
確定文書は段階別の `final/` に置く。共通型は基本設計の確定項目を参照し、詳細設計へ複製しない。
全体の整合性検査は両段階を読み、基本設計が詳細設計の確定結果へ依存する経路を増やさない。

`.yde/schemas/design/`・`transforms/design/`・`views/design/` も基本・詳細と共用の定義を区別する。
生成処理用のビューとレビュー用のビューを分け、業務モデルの写しと定義 ID を保つ。共用は実際に両段階が使う形式や検査に限定する。
アプリを組み立てる文字のひな形は `.yde/reports/` に置き、生成後の `app/` から参照しない。

| 段階 | 設計書・項目 |
|---|---|
| 基本設計 | エンティティ・論理型・区分、アクション、ドメインと関連、画面定義と画面遷移定義、エラー定義、メッセージ定義 |
| 詳細設計 | テーブル、テーブルアクセス、処理と状態の判定、画面設計と Controller、画面のクラス対応、セッション、エラー設計 |

## YDE 本体との分離

| 対象 | 方針と確認方法 |
|---|---|
| Gradle のプロジェクト | YDE の `settings.gradle.kts` の `include`・`includeBuild` にアプリを加えず、両方の `projects` で対象を確認する |
| ビルド設定 | アプリは専用の settings・build・Wrapper・依存バージョンを持ち、YDE の `buildSrc`・版カタログ・`appVersion` に依存しない |
| 作業場所 | YDE はリポジトリのルート、アプリは `app/` を作業ディレクトリにして、その場所の Wrapper を起動する |
| 成果物 | アプリの `build/`・`.gradle/`・DB・ログをアプリ側に閉じ、Git と設計の入力から除く |
| YDE の検証対象 | `ledger: [design]` を維持し、アプリの設定・ソース・ビルド出力を設計 YAML として扱わない |
| サンプルを使うテスト | 設計用のコピーと入力収集からアプリを外し、コード生成のテストだけが対象ファイルを明示して読む |
| 実行資源 | 重い Gradle 検証は順番に実行し、既存キャッシュを使い、アプリの確認用ポートと一時 DB を分ける |
| 停止処理 | 起動した子プロセスだけを管理し、Java 全体の停止や他のビルドのデーモン停止を行わない |
| CI | YDE の通常の単体テストとアプリの生成・ビルド・動作確認を別ジョブに分ける |

現状、YDE のモジュールはルートの settings に明示され、ソース規則テストもそのモジュールを走査している。
サンプルの設計用テストは `.yde/` の定義と `design/` だけをコピーし、アプリと表示状態を除外する。
依存キャッシュの共有は可能だが、プロジェクトの設定・成果物・実行プロセスは共有しない。

## 作業の順序と完了条件

| 順序 | 作業 | 完了条件 |
|---|---|---|
| 1 | 設計の配置を移行する | パスと根拠の場所を除く確定値・ID・ビューの内容が移行前と一致し、再生成・検証・DDL が通る |
| 2 | コード生成の入力をそろえる | 各出力と確定項目の対応、型・初期値・方式の指定、未対応時の扱いが明示される |
| 3 | アプリの独立したビルドを用意する | 最小アプリが単独でビルド・起動でき、YDE のビルド対象と成果物が変わらない |
| 4 | 複数ファイルの生成と再生成を整える | 作成・更新・削除予定を確認でき、競合や生成エラーでは前の成果物を壊さない |
| 5 | データアクセスまで生成する | Java の型・モデル・Mapper・XML・DDL が一致し、H2 で実際の入出力が通る |
| 6 | 業務処理を生成する | 状態・前提・効果・トランザクション・エラーの成功時と失敗時を確認できる |
| 7 | 画面と画面遷移を生成する | 一覧・詳細・入力・確認・実行・エラー表示が接続し、Form とメッセージの制約が一致する |
| 8 | 全体の再生成と独立実行を確認する | 再生成の差分なし、補正の伝達、別の場所でのビルド・起動、YDE の全テストを確認する |

配置移行では既存の確定文書 80 件と代表ビュー 5 種類を比較し、パス以外の値と DDL を維持した。
アプリの方式設定、12 ファイルの基本構造、生成予定・競合検査・更新と削除の経路を実装した。
アプリだけを別の場所へコピーしたテスト・ビルド・起動も確認した。操作と対応範囲は [アプリの生成と独立ビルド](application-generation.md) にまとめる。
Java のスカラー型を Form と行モデルで共通化し、テーブル数に応じた行モデルの出力を接続した。
順序 5 の Mapper・XML・共通 DDL を接続し、48 メソッドの入出力を H2 で確認する検証を用意した。
順序 6 は、処理の機械的な指定と呼出先の照合、状態型・業務例外の生成を接続した。
Service の入力クラスと Mapper の引数・更新内容の照合、同時更新を順番に実行する共通実行部を生成する。
採番とトランザクションの完了まで順番を保つ方式は、一つのアプリ内で行う。共通実行部の H2 検証と、各操作本体の接続は分けて確認する。
順序 2 の Service の初期化式・入力検査との対応、順序 6 の操作本体・確認時の非更新・拒否時の取り消し、順序 7 以降は残っている。

業務処理の残りは、次の順で接続する。

1. 確定した処理設計の引数・式・対象列を対応付け、入力・現在値・基準日・採番・明細の順序から書く値を組み立てる。
2. 受け手と親を読み、状態・前提と更新後の値を検査する。確認用の処理は違反を返し、DB には書かない。
3. 共通実行部へ操作全体を接続し、書込み後の件数検査も含めて違反時に取り消す。採番と書込みを同じ操作内で実行する。
4. 全操作の成功・拒否・非更新・取り消しを H2 で確かめてから、Controller と画面へ接続する。

### 配置の移行

最初に旧パスと新パスの対応表を作り、設計書・入力・中間記録・定義・テストを振り分ける。
生成先、スキーマの `match`、入力ビュー、参照、根拠の文書パス、DDL、説明文とテストを同じ変更で更新する。
生成物を手で編集せず、作業用コピーで再生成し、旧パスに確定項目が重複して残らないことを確かめる。
保存先を変えたときに旧生成物が自動削除されるとは仮定せず、対応表と生成物の印で管理する。

ここでは設計内容の見直しと配置変更を混ぜない。既存の `TodosSysdevTest`・`TodosEntityFoundationTest`・`TodosSystemDocumentsTest` と生成の関連テストで比較する。
設計書別ダッシュボードと個別・横断ビュー、C/U、DDL の到達先を確認する。

### 生成の入力と未決事項

詳細設計の確定項目を主な入力とし、基本設計の確定項目への参照をたどる。
補正前の業務モデルから同じ設計判断を作り直したり、コードのひな形で型の継承や補正の優先順位を再計算したりしない。
アプリ名・Java パッケージ・依存版・DB・起動設定は詳細設計の入力から確定させる。
Java の型対応表には、必須と null、数・日付・参照・配列、初期値と文字のエスケープ、Bean Validation への対応を含める。
Form と行モデルは `final/java-types.yaml` の同じ対応を使う。整数は `Long`、真偽値は `Boolean`、配列は要素型をたどる。
行モデルの SQL 型との照合、初期値の値・出力方法、Mapper の入力と結果の型、文字のエスケープを接続した。数値の範囲・Bean Validation・Service の初期化式は後続で照合する。
テーブルアクセスの「同じ条件」は `whereFrom` によるメソッド ID 参照、「すべての列」は `{mode: all}` に正規化した。
取得結果の型・絞り込み・入れ子・更新条件を `application-access` で確定し、Mapper と XML を生成する。

| 確定した設計 | 主な出力 |
|---|---|
| エンティティ・論理型と物理項目 | Java のモデル・行の型・型変換、DDL |
| テーブルアクセス | Mapper インターフェースと XML |
| 処理・状態の判定 | Service、状態の型と判定、トランザクション |
| 画面遷移・セッション・エラー設計 | Controller、例外と応答、設定 |
| 画面設計・入力・メッセージ | Form、入力検査、Thymeleaf、messages.properties |
| 画面のクラス対応 | CSS と、必要な資源のビルド設定 |
| アプリの方式・依存・起動設定 | ビルド定義、起動クラス、application.properties、README |

レビュー用 DDL と `app/src/main/resources/schema.sql` は同じ確定値・同じ出力規則を使う。
ドメイン定義など、人が読むことを目的とする設計書には無理にコードの対応先を作らない。

現在の未対応範囲は [設計書の確定と全体レビュー](design-document-migration-plan.md) と [エンティティの生成処理](entity-generation-contract.md) を引き継ぐ。
Controller・Form の名前や画面構成の補正、選択肢の継承、配列の配列・エンティティのマップなどは、生成への影響を対応表で示す。
「手で書く」などの未実装表現や、式から Java・SQL・HTML への変換に不足があれば、その箇所を示して先に解決する。
条件付き必須や項目間の規則を新たに広げる判断は別に行い、現在実装対象とされている規則を黙って落とさない。

### アプリ生成の仕組み

レポートは値の組み立てと文字のひな形で一つの出力を作る。現在の基本構造は複数のレポートをまとめて実行し、全件の検査後に適用する。
生成ファイルの一覧とハッシュは `design/detail/reports/application-files.json` に保存し、アプリの通常のビルドでは読まない。
重複・手修正・同名の手書きファイルを検出したら止め、記録にあるファイルだけを更新・削除する。書込失敗時は、この処理による変更を復元する。
文書数に応じた出力単位とパラメータは `application-output-plan` で確定し、行モデルと Mapper・XML の可変個数の出力へ接続した。同じ DDL レポートをアプリにも出力する。

Wrapper の JAR や htmx などの固定資源は、文字の生成とは分けて版と取得元を固定する。
設定は既存の出力方式で扱える `application.properties` を使う。YAML 出力が必要になった場合は、現行のレポートが YAML を拒む規律と併せて別途設計する。
CSS の加工が必要な場合もアプリ側で依存と成果物を管理し、YDE の `web-ui` の Node やビルド設定を参照しない。

### 段階ごとの検証

1. 配置移行では、既存の確定値・ビュー・DDL・再生成の差分を比較する。
2. 最小アプリを別の場所へコピーし、YDE の親ディレクトリが無くてもアプリ自身の Wrapper でテスト・ビルドする。
3. データアクセスでは、実際の Mapper と H2 で参照・入れ子・採番・初期値・更新を確認する。
4. 業務処理では、成功時の更新、状態・前提違反時の非更新とメッセージを確認する。
5. 画面では、登録・変更・完了など業務モデルの操作と、入力エラーからの再表示、セッションと遷移を確認する。
6. 補正した型・物理名・メソッド名・URL・入力制約が、設計ビューと生成コードの両方へ届くことを確認する。
7. 再生成の一致、対象削除、名前変更、競合、途中失敗を確認し、YDE の全テストとアプリの検証を別々に通す。

YDE の通常の単体テストから別の Gradle ビルドやアプリを自動起動しない。
文字の生成・検査は既存の単体テストで確認し、依存取得・コンパイル・起動を伴う確認は明示的な結合検証と CI の別ジョブに置く。
重い検証は必要な段階で行い、変更のない結果を繰り返し確認しない。

## レビューの区切り

- 配置移行後: 同じ設計書を新配置とダッシュボードでたどれ、値が変わっていないことを確認する。
- データ・処理・画面の各段階: 生成元の設計項目、生成されたファイル、実際の動作を対応付けて確認する。
- 最後: 設計書全体とアプリをまとめてレビューし、対応範囲と残る制限を記録する。

設計判断が必要な不足は、具体的な入力・期待するコード・動作を添えて相談する。
ログイン、楽観ロックなど未合意の方式、H2 以外の実 DB への対応、別 Git リポジトリへの公開はこの計画の完了条件に含めない。
コミット・push・マージは、その都度のオーナーの指示に従う。
