# TODO のシステム開発の設計書

[todos](../todos/README.md) の業務モデルを要件定義として、Spring Boot のアプリを作るための設計書体系を置くサンプルです。
設計書は、業務モデルから YAML の計算（生成の定義）で作ります。YDE の業務モデルから設計書体系へ、どこまで計算で変換できるかを確かめる場でもあります。

いまは操作系（アクション定義書 → 処理設計書）・データ系（エンティティ定義書 → テーブル設計書 → テーブルアクセス設計書）・
画面系（画面遷移定義書 → 画面定義書 → 画面設計書・画面遷移設計・セッション情報設計と、一覧の読み出し）・
エラーとメッセージ系（エラー定義書・メッセージ定義書 → エラー設計書と、処理設計書のデータの決まりの手順）・
ドメイン（ドメイン定義書・ドメイン関連定義書。業務の概念を業務の言葉で書いた、人が読む文書）までです。

## レビューと次の作業

**エンティティ定義書・テーブル設計書を含め、設計書全体の内容をレビューする段階**です。生成や検査の成功を、オーナーのレビュー完了とは扱いません。
ほかの設計書も導出・補正と指定・追加から確定する経路へ移し、ダッシュボードの切替欄から「アクション定義書」「処理設計書」などの設計書を選んで確認できます。
「対象の設計書」で文書を選ぶと、概要と根拠・設計内容が切り替わります。「この設計書の一覧」には同じ種類の文書だけが並びます。全体の対応は「設計書の全体レビュー」で確認できます。
[設計書の確定と全体レビュー](docs/design-document-migration-plan.md)に、対象・受け渡し・入力例・試し方をまとめています。
計画と未決事項は [ロードマップ](../../docs/ROADMAP.md#p53-業務モデルから作る設計書体系とアプリ生成) にあります。
設計の配置を段階・役割ごとに整理し、独立した `app/` の行モデル・Mapper・XML・共通 DDL・状態型・業務例外・全操作の Service・入力検査付き Form と Service への接続を生成します。
サイバーパンクのデザイン台帳から CSS と確認用画面も生成します。型対応は Form・行モデル・Mapper・Service で共通です。
業務の 29 画面・14 操作、読出し・Controller・画面遷移も接続しました。テンプレートの場所と動作の試し方は [業務画面の生成と確認](docs/web-generation.md) を参照してください。
全体の順序は [作業計画](docs/application-generation-plan.md)、現在の出力範囲と操作は [アプリの生成と独立ビルド](docs/application-generation.md) を参照してください。
目指す設計の体系は [ADR-0042](../../docs/decisions/0042-system-models-and-views.md)、そこへ移す計画は [移行計画](docs/system-model-plan.md) にあります。いまの体系は移行前です。

導出・補正と指定・追加から確定項目一覧を作り、ビューと後段で共有する方針は [ADR-0039](../../docs/decisions/0039-finalized-design-items.md) に従います。
現在のエンティティ定義書はこの経路へ切り替えました。項目自身に解決した型・文字数・初期値を保存し、個別表示と横断表示はその値を読みます。テーブル生成も同じ確定項目を使います。

エンティティと型について人が書くのは `design/basic/inputs/entities/corrections.yaml` の補正と指定、`design/basic/inputs/entities/additions.yaml` の追加です。
ほかの設計書の入力は、基本・詳細それぞれの `inputs/documents/corrections.yaml`・`additions.yaml` です。物理設計は `design/detail/inputs/tables/` の入力を使います。
旧台帳の区分定義は追加へ、各エンティティの区分は `entity-class` の指定へ移しました。
エンティティと型の確定項目は `design/basic/final/` の `entities.yaml`・`types.yaml`・`classes.yaml` です。導出記録と合成の記録は各段階の `derived/`・`composed/` に残ります。
説明の食い違い、補正の競合、型・参照の誤り、未処理の指定があれば生成を止めます。業務モデルの説明の食い違いは、業務モデルを直します（TODO の ID の説明は 2026-11-25 にそろえ、補正 `COR-001` を無くしました）。

今回の到達点と残る作業は [生成処理と対応範囲](docs/entity-generation-contract.md) にまとめました。
区分以外の追加、楽観ロックなどの方式の展開、組込み型の補正、継承した選択肢の子の個別補正は残っています。未対応の入力を確定済みとは扱いません。
[エンティティ定義書の見直し案](docs/entity-definition-plan.md) は、レビューする属性と確認例の一覧です。

## 前提

- 要件定義は業務モデルそのもの（スコープ「業務モデル」＝`.yde/schemas/business/` と `.yde/views/business/`）です。機能要件が中心で、非機能要件は扱いません。
- アーキテクチャは決め打ちです: Thymeleaf・htmx・Java 21・Spring Boot 4・MyBatis（XML の Mapper に SQL を書く）・H2。Flyway は使いません。ログインはありません。
- 動きのある画面は htmx の部分更新（Controller が HTML の断片を返す）で作り、JSON の API は作りません。
- 型・桁・形式の入力検査は Controller（Bean Validation）、それ以外の前提は Service で確かめます。
- 画面は一般的な Thymeleaf の業務 Web です（SPA ではありません）。ダイアログではなく画面遷移で、登録なら 入力画面 → 確認画面 → 一覧画面へ戻る、です。
- アプリの範囲は、YDE の閲覧専用モードでできること（見る・操作する）です。直接の編集は作りません。

設計書は導出元として業務の ID を使い、確定項目は独自の設計 ID を持ちます。業務モデルから消えた操作やエンティティ型の設計書が残っていれば、「浮いた詳細化」として分かります。
前提（断りの種類）は `操作ID.前提ID`（`complete-todo.no-open-task`）、状態が合わない断りは `操作ID.state`、データの決まりの違反は `check.決まりID`（`check.closed-has-result`）です。

名前は業務の ID から機械的に作ります（`complete-todo` → `completeTodo`・`CompleteTodoForm`・`TodoController`）。英語の文法の規則（複数形など）は入れません。URL も業務の ID をそのまま使います（`POST /todo/{id}/complete-todo`）。

## 段（基本設計・詳細設計）

設計書は導出・合成・確定の経路を使います（ADR-0039）。基本設計と詳細設計を上位のディレクトリで分け、それぞれに入力・導出・合成・確定を置きます（ADR-0041）。
後段は `dependsOn` で宣言した今回の確定結果を読みます。従来の段の宣言（ADR-0034）は残っていますが、この経路へ段の補正を重ねません。

いまは、従来の段にルールはありません。確定項目の経路では、区分の追加とエンティティへの割当を反映し、「根拠」に追加・指定の記録を残します。

### 基本設計の確定項目と入力（エンティティ定義書）

- `design/basic/final/entities.yaml`・`types.yaml`・`classes.yaml` は、導出・補正・区分の追加と指定を合成し、検査した生成物です。通常の設計 ID と参照はここにあります。
- `corrections.yaml` の対象と `additions.yaml` の生成先 ID は文字として保存します。生成中の集合で対応を確かめ、前回の生成物へ頼りません。
- 個別のエンティティ定義書と横断の項目一覧は、同じ保存値を読みます。ビューで補正や型継承を重ねません。補正元と原文は「根拠」で確認します。
- ダッシュボード「エンティティ定義書」の「エンティティ一覧」で ID を押すと、そのエンティティの個票が開きます。個票は、概要・項目・操作と書く項目・項目 × 操作・子要素 × 操作を 1 枚に重ね、その下に子要素（並びの項目）ごとの表を並べた文書ビュー（`entity-definition-sheet`。`idPattern: "ENT-*"`）です。
- 子要素ごとの表は、コメント一覧・状態の履歴のように並びの中に項目を持つ子要素なら「項目」と「項目 × 操作」、作業項目のように子がエンティティなら、そのエンティティの「項目」と「項目 × 操作」です（区画の繰り返し `each`）。
- 子要素への作用は C＝足す・U＝変える・D＝消す で、業務モデルの操作の書き方から導きます。並びに足す（`insert`）は C、並びを丸ごと入れ替える（`set`）と消す（`delete`）は C・U・D、番号で指した 1 件の書き換え（`comments[$row].body` への `set`）は U、1 件の削除は D、子のエンティティの中への作用（作業項目を済にする）は親から見て U です。確定項目では、書込（`CRUD-*`）の `element` と `elementItems`（書く子の項目）に保存します。
- ダッシュボード「エンティティ定義書」の「レビュー」の区画（項目・入れ子の項目・操作と書く項目・項目 × 操作・子要素 × 操作）は、人が中身を読むための列だけにしています。型は名前、必須は ●、参照先と書く項目は名称で出します。経路・属性の状態・根拠・導出元は「確認用」の区画で見ます。
- 共通型への参照を保ちながら、各項目にも適用する制約を保存します。元から最大 100 と明記した項目は、共通型を 200 に補正しても 100 を保ちます。
- 区分は業務モデルから導かず人が追加します。エンティティへの割当は指定で行い、確定したエンティティの `entityClass` を両設計書で読みます。
- 操作と C/U の原本は `operations[].writes` 一つです。書込のない項目も CRUD の行に残します。R/D の導出は保留です。

### 詳細設計項目一覧と型対応表（テーブル設計書から。ADR-0036）

- 詳細設計項目一覧（`design/detail/final/tables.yaml`）は、詳細設計にだけ出てくるもの（テーブル名・カラム名・主キーの順と制約名・型対応への参照・親のキーと並び順・索引・外部キー）だけを持ちます。名称・必須・論理型・初期値・選択肢は、導出元（基本設計項目一覧）をたどって読みます。
  日本語名も、基本設計に同じものが無いもの（明細テーブル「TODOのタグ」・親の ID「TODOのID」・並び順・埋め込みのカラム「期間の開始日」）にだけ書き、ほかは導出元の名称です。NOT NULL も、詳細設計で足したカラム（親のキー・並び順・要素）と例外（埋め込みの object の中の必須の項目で、親の項目が必須でないもの＝false）にだけ書き、ほかは導出元の必須から決まります。そのため、一覧そのものでは日本語名・NOT NULL が空の行があります。
- 業務モデルの形は、深さによらずテーブルにします。todos に無い形も、テスト（`TodosSysdevTest`）が形の見本を足した写しで確かめています。
  - 配列とマップの項目は明細テーブルで、主キーは親のキーに並び順（配列）かキー（マップ）を足したものです。行の中の配列は、さらに下の明細テーブルで、親への外部キーは親の主キーの組（複合）です。
  - エンティティでない object は、名前の有無によらず、中の項目を `項目のキー_中のキー` のカラムに埋め込みます。
  - 入れ子のエンティティは親の ID を持ち、1 件で持つなら親の ID が一意です。
  - 配列・マップの要素が配列・マップである形と、エンティティのマップは、現変換では未対応として検査が指摘します。現在の案内は前者が行の型で包む、後者がエンティティの配列にする、です。SQL で表現できない意味ではなく、業務モデルの書き直しを求めるか設計側で対応するかはレビューで判断します。
- 索引は、配列の「同じものは 1 度だけ」から一意の索引（`ux_todo_tags_tag_id`＝親の ID と要素。object の配列なら比べる項目）を、外部キーのカラムから索引（`ix_todo_category`。主キーの先頭のカラムは除く）を作ります。索引のカラムは並び（昇順・降順）を持ちます。
  外部キーは、入れ子で持つ親へ 1 つ（親のキーの組。親の行を消したら一緒に消す）と、参照のカラムごとに 1 つ（消したときの動きは指定しない）です。どのカラムがどのカラムを指すかはカラムの参照先に書き、カラム一覧にも参照先が残ります。
- 業務モデルから導けない索引（画面の絞り込みや並びのため）は、詳細設計項目台帳（`design/detail/inputs/tables/ledger.yaml`）に人が書きます。いまは、ダッシュボードの「期限超過」で状態と期限で絞るための `ix_todo_status_due_on` です。生成した索引・外部キーの値を変えるとき（消したときの動きなど）は、補正一覧（詳細設計）に書きます。
- 型対応表（`design/detail/inputs/tables/sql-types.yaml`）は人が書きます。論理型ごとに SQL の型の書き方を決め、`VARCHAR({maxLength})` の穴は利用箇所の確定値で埋まります。論理型が増えて対応が無ければ、カラムの型対応への参照が切れて分かります。ビュー「型対応表（論理型 → SQL）」で、埋めた形と並べて見られます。
- テーブル設計書は、ダッシュボード「テーブル設計書」です（概要・カラム一覧・索引・外部キー）。補正一覧（詳細設計。`design/detail/inputs/tables/corrections.yaml`）を生成時に合成した確定値を表示します。テーブル名・カラム名の付け替え（UX-324）は、ここに書けます。
  概要はテーブル日本語名とテーブル区分（確定したエンティティの区分。明細テーブルは配列・マップを持つエンティティの区分）と主キーの制約名、カラム一覧はカラム日本語名・主キーの順・NOT NULL とその根拠（基本設計の必須か、詳細設計で足したカラムか）・初期値の設定（設定あり／設定なし）と値と出力方法・自動で入る値を出します。
  索引は台帳の索引も並べ（張る理由の列）、外部キーは複合のカラムと参照先のカラムを同じ順に並べます。
- DDL は、レポート `ddl`（`.yde/reports/design/`）がテーブル設計書のビューの行から作ります（`report samples/todos-sysdev ddl` で `design/detail/reports/ddl/schema.sql` に書く）。主キーは主キーの順と制約名で、索引は CREATE INDEX（降順は DESC）です。外部キーは、すべてのテーブルを作った後に ALTER TABLE で足します（テーブルの順に左右されない）。テストで H2 に流して確かめています。
- 初期値の出力方法は型対応表の `literal` で指定します。`string` は `'OPEN'`、`number` は `1`、`boolean` は `FALSE`、`date` は `DATE '2026-11-16'` の形です。文字列の引用符は二重にし、空文字は `''` にします。値の見た目では型を決めません。未設定と `false`・`0`・空文字・文字そのものの「設定なし」を区別します。
  `auto: created` などの自動値は Service が設定するもので、SQL の DEFAULT にはしません。
  Form と行モデルの Java 型は共通の対応表を使います。Service の初期化式の対応範囲は[アプリの生成](docs/application-generation.md)にまとめています。
テーブルは補正後の基本設計を入力にして、詳細設計の段の規則を当てます。`detail-tables` の `dependsOn` により、基本設計も同じ生成計画で先に作り直します。

## ドメインの決まり

ドメインは集約です（業務モデルの項の `aggregate`。入れ子の持ち主がいないエンティティ型と、その中に入れ子で書かれた型）。todos では TODO（作業項目を含む）・カテゴリ・タグの 3 つです。
ドメイン定義書は、説明・構成・情報（業務の型の名前と説明）・状態の流れ・提供する操作・データの決まり・ほかのドメインとの関係（出る向きと入る向き）を業務の言葉で書き、
テーブル・列・クラスのようなシステムの言葉は書きません。ドメイン関連定義書は、ドメインの一覧と関係（多重度・循環しない）と入れ子を 1 本にします。
関係の相手はドメイン定義書の ID で書くので、YDE の図でドメインの関係を見られます。ドメインの範囲を関係で決める仕組みは今後です（UX-332）。

## データ系の決まり

| 決まり | 例 |
|---|---|
| 業務モデルで 2 か所に書かれた項目（一覧の行と個票）は 1 テーブル | `todo`（タイトル・概要も状態・日付も） |
| テーブル名は型の名前のスネーク | `todo-task` → `todo_task` |
| 明細テーブルは「親のテーブル名_項目のキー」（ID の無い繰り返し・参照の並び） | `todo_comments`・`todo_history`・`todo_tags`（英語の単数・複数はそろえない） |
| カラム名は項目のキーのまま。SQL の予約語（H2）に当たれば末尾に `_` | 状態の履歴の `from_`・`to_` |
| 入れ子の型と明細テーブルは、親の ID と並び順の列を足す | `todo_id`・`seq` |
| 文字は上限があれば `VARCHAR(n)`、無ければ長さなしの `VARCHAR` | タイトルは `VARCHAR(100)`、番号・文章は `VARCHAR` |
| 選択肢は値の CHECK、参照は外部キー。形式（pattern）は DB では確かめない | `status` の CHECK・`category` → `category(id)` |
| 採番は Service が「使われている番号の次」を計算する | `TodoMapper.maxId` → `TODO-` と 3 桁 |
| 同じテーブルへの値の書き込みは、操作ごとに 1 つの update | 完了は `UPDATE todo SET completed_on, result, status, updated_on` |
| 前提のうち「受け手の中の要素の条件」は件数を数え、受け手の値の条件は読んだ行で確かめる | 完了の前提は `TodoTaskMapper.countCompleteTodoNoOpenTask`（0 件なら通す） |

エンティティ定義書の CRUD 表は、項目ごとに、どの操作がその項目を作る（C）・書き換える（U）かを並べます（列は操作の ID）。
配列の項目の「同じものは 1 度だけ」（`unique`）は、明細テーブルの「親の中で重ならない組」（`UNIQUE (todo_id, tag_id)`）になります。

## 画面系の決まり

画面は、ダッシュボードを起点に、業務モデルから計算で決めます（業務モデルの項の `reach`。ダッシュボードからたどれないものは、業務モデルの不足として業務モデルを直します）。

| 業務モデル | 画面 | 中身 |
|---|---|---|
| ダッシュボード | 一覧画面 | 絞り込みの欄（URL のパラメータ）・区画の表・上部の操作のボタン・行の右のボタン（行の型を受け手にする操作） |
| 区画の行の ID・参照の項目 | 詳細画面（エンティティ型ごと） | 項目・繰り返しと入れ子の型の表（入れ子の型の行の右に、その型の操作のボタン。繰り返しの行の右に、その並びの 1 件を番号で指す操作のボタン）・操作のボタン |
| 操作 | 入力画面 → 確認画面 | 受け取る値が無い操作は確認画面だけ（GET で開く）。並びの番号は行のボタンが運ぶので、受け取る値に数えない |
| 確定の後 | 起点の画面へリダイレクト | 完了の知らせを出す |
| 集計のセル | 一覧画面 | その行と列で絞る |

ボタンは Lifecycle の状態で出す・出さないを決めます（完了は対応中のときだけ）。前提（済んでいない作業項目が無い など）は確定のときに確かめ、断るときは確認画面に断りの文を出します。業務の流れの図（`flow`）は、いまは画面にしません。todos では 29 画面です（一覧 1・詳細 3・入力 11・確認 14）。

セキュリティの決まり: 状態を変えるのは POST だけ・確定でトークンを照合し、入力検査・状態・前提を確かめ直す・フォームは操作の受け取る値だけ・起点の画面は画面の ID で受け取る（URL は受け取らない）・確定の後はリダイレクト（PRG）。
セッションに置くのは、CSRF トークン（将来）・二重確定を防ぐトークン・完了の知らせの 3 つだけです。入力の値は確認画面の hidden 項目、絞り込みは URL のパラメータで持ちます（タブごとに独立）。

画面設計書は HTML のテンプレートではなく、HTML の手前の**部品の木**です。部品（page・notice・filters・section・facts・table・matrix・form・field・choices・rows・actions）は
どれも 1 つの意味のある HTML の要素（`main`・`section`・`dl`・`table`・`form`・`fieldset` など。div を並べない）に写し、物理パラメータ（欄の幅 `40ch`・
複数行の高さ・ボタンの強さ primary / secondary・寄せ・段組み・間隔）は決まった名前のクラス（`field control-date w-10ch`・`button-primary`）に写します。
クラスの中身は「画面のクラスの対応表」に通常の CSS の宣言で書きます。色・文字・余白は [画面デザイン台帳](docs/appearance-generation.md) の確定値を参照します。
台帳と部品の対応表から CSS と確認用画面を YDE のレポートで生成します。

| 決まり | 例 |
|---|---|
| 入力欄は業務の型から | 一行＝text（最長の文字数を幅に。上限 40ch）・複数行＝textarea・日付＝date・参照＝select（候補は参照先の一覧）・タグ＝チェックの並び |
| フォームの検査は業務の型から | 必須＝`@NotNull`・文字数＝`@Size`・形式＝`@Pattern`・重なり不可＝`@UniqueElements`。空の欄は未入力（null）として受け取る（前後の空白は落とさない） |
| 表示の形 | 日付は型の format（2026年11月15日）・選択肢は表示名・参照は名前と ID のリンク・文章は改行を保つ。表示は `th:text` だけ |
| 編集の入力 | 値を消すは効果からたどって欄の横にチェック・確認画面は変わる項目だけを今の値 → 新しい値で |
| 並びの 1 件を番号で指す操作 | 業務モデルの `comments[$row]` の番号は、アプリでは明細テーブルの並び順（`seq`）の値。詳細画面のその並びの表の行のボタンが URL のパラメータで運び、入力・確認の画面では hidden 項目で持ち回す（人は入力しない）。編集の初期値と確認画面の「対象の行」は、番号の指す行から読む。行が無ければ 404（`error.notFound.todo.comments`） |
| 一覧の読み出し | 区画ごとに Mapper の select と count（ビューの行の条件・区画の条件・列・並び）・集計は aggregate・詳細は findDetail・参照の候補は selectAll。読み出しの Service は画面ごと |
| ビューを SQL に写す規則 | 等しい・配列のどれか（明細テーブルの EXISTS）・State（値の IN）・値がある・日付の比べ（基準日）・入れ子の要素の件数・被参照の数。並びは番号の順か項目の順。写せない形は「手で書く」（todos では 0） |

## エラーとメッセージ系の決まり

業務モデルの項の操作の `checks`（その操作が書くと破れうるデータの決まり）から、どの操作でどの決まりを確かめるかが決まります。
書く項目と決まりが読む項目が重なり、書いた後の値が決まりの絞り込みに入りうるものだけです（状態を「中断」に書く操作は「完了した TODO には…」を確かめない）。

| 決まり | 例 |
|---|---|
| 要素ごとの決まり・循環の決まりは、書いた後の値を計算して、書く前に Java で確かめる | 完了は「完了日は作成日以降」「完了した TODO には結果」を確かめる |
| 入れ子の要素の決まりは、書いた後に同じトランザクションで件数を数え、違反なら例外で書いたものを取り消す | `TodoTaskMapper.countClosedHasNoOpenTask`（外側のテーブルをつないで、完了した TODO の済んでいない作業項目を数える） |
| 受け取る値が原因で破れうる決まりは、確認へでも確かめ（Service の `check操作`。書かない）、入力画面の欄の横に出す | 編集で期限を作成日より前にすると、期限の欄の横に出る |
| 確かめない決まりには理由を書く | 警告の決まりは断らない・書かれた場所の決まりは 1 テーブルなので起きない・参照の型は外部キー・1 列の参照は 2 つ入らない |
| 状態・前提・データの決まりの断りは、確定のときに確認画面に出す | `RefusedException` を確定のハンドラが受ける |
| ID を指定して見つからなければ見つからない画面（404）。絞り込みの結果が 0 件は正常 | `NotFoundException`・一覧の表の代わりに「該当するTODOはありません」 |
| 二重の確定・時間切れは、起点の画面へ戻して知らせ。想定外はエラー画面に受付番号だけ | `InvalidTokenException`・中身（スタックトレース・SQL）は画面に出さず、ログに残す |
| 文はメッセージのキーで書き、メッセージ定義書から messages.properties に写す | 状態の断りは Lifecycle の文・決まりは業務モデルの message・入力の誤りは検査の種類ごとの決まった文・完了の知らせは「TODOを完了しました（{id}）」 |

## 試し方

1. 業務モデルを展開した形（生成の入力）を見ます。

   ```bash
   ./gradlew runCli -q --args="generate samples/todos-sysdev --model --scope business"
   ```

   `actions` の `complete-todo` の `effects` に、do の手（完了日・結果）と、Lifecycle が書く状態の値と履歴の行と、保存時に自動で入る更新日が、1 列に並ぶことを確かめます。`entities` の `todo-task` に採番（`numbering`）と外側の型（`owner`）があることも見ます。
2. 生成物が最新かを確かめます。`upToDate: true` で、作る・作り直す・消す文書が無ければ最新です。

   ```bash
   ./gradlew runCli -q --args="generate samples/todos-sysdev"
   ```

3. 作業用コピーで、業務モデルを変えて作り直します。たとえばコピーの `.yde/schemas/business/operations.yaml` で完了の操作の `label` を変え、`generate <コピー> --apply` を実行します。該当箇所だけが作り直され、git の差分で変わった所を読めます。
4. 作業用コピーで、生成物を 1 つ消して検証します（`validate <コピー>`）。設計の対応の検査が「操作「complete-todo」に処理設計書がありません」「エンティティ型「todo」にテーブル設計書がありません」のように指摘します。
5. YDE で開き、次のビューを見ます。
   - `design/basic/final/actions/complete-todo.yaml` の「ビュー」タブの「操作の設計書（基本から詳細まで）」: アクション定義書と処理設計書が 1 つの画面に並び、この操作を扱う Controller と Mapper へ移れます。
   - 台帳のビュー「操作の設計の対応」「エンティティの設計の対応」: 操作・エンティティ型ごとに、どの設計書へ降りているかを一覧できます。
6. 画面系の生成物を読みます。
   - `design/basic/final/screens/transitions/todo-dashboard.yaml`: 29 の画面と、移り方（区画の行の ID → 詳細・ボタン → 入力 → 確認 → 起点の画面。コメントの編集と削除は、詳細画面の表「コメント一覧」の行のボタンから）。
   - `design/basic/final/screens/operations/complete-todo.yaml`: 起点の画面（期限超過とすべてのTODO の行のボタン・TODO詳細のボタン）・ボタンを出す状態（対応中）・入力の項目・確認・断りの種類。
   - `design/detail/final/controllers/todo.yaml` と `design/detail/final/session.yaml`: ハンドラごとの URL と、セッションに置く・読むキー。
7. 画面設計書と読み出しを読みます。
   - `design/detail/final/screen-designs/operations/complete-todo.yaml`: 入力画面と確認画面の部品の木と、`CompleteTodoForm` の検査（完了結果は `@NotNull` と `@Size(min = 1)`）。
   - `design/detail/final/screen-designs/operations/edit-todo.yaml`: カテゴリの欄の横の「値を消す」（`clear.category`）。
   - `design/detail/final/screen-designs/operations/edit-todo-comment.yaml` と `design/detail/final/screen-designs/details/todo.yaml`: コメント一覧の行のボタン（`row: {param: row, item: seq}`）と、番号を hidden で持ち回す入力画面・「対象の行」を見せる確認画面。
   - `design/detail/final/table-access/todo.yaml` の `selectTodoDashboardOverdue`: 期限超過の区画の条件（status が OPEN か IN_PROGRESS・期限がある・期限が基準日より前）。
   - YDE で `design/basic/final/screens/operations/complete-todo.yaml` のビュータブ「操作の画面の設計書（基本から詳細まで）」で、画面定義書と画面設計書が 1 つの画面に並ぶこと。

   ドメイン定義書の「ほかのドメインとの関係」の相手（`to`）は、ほかのドメインの ID への参照です。
9. エラーとメッセージ系の生成物を読みます。
   - `design/basic/final/errors.yaml`: 断りの種類と出す場所・データの決まりの扱い（確かめ方と、確かめない理由）・操作ごとの断り（入力の誤り・見つからない・状態・前提・データの決まり・二重の確定）。
   - `design/detail/final/processes/complete-todo.yaml`: 確認へで呼ぶ `checkCompleteTodo` と、データの決まりの手順（書く前に Java・書いた後に件数）。
   - `design/basic/final/messages.yaml` と `design/detail/final/error-handling.yaml`: キーと文・入力の誤りの文（フォームの項目ごと）・例外のクラスと受ける所・エラー画面・設定。
10. 作業用コピーで、業務モデルのダッシュボード（`.yde/views/business/todo-dashboard.yaml`）から区画「カテゴリ一覧」を消して作り直すと、カテゴリの詳細画面は TODO の参照からたどれるので残ります。上部のボタン「カテゴリを追加する」を消すと、その操作の画面とハンドラが消え、検証が「ダッシュボードからたどれず、画面がありません」「Controller のハンドラがありません」と警告します（設計書の側に案内として出ます）。
11. エンティティ定義書を見ます。YDE でダッシュボード「エンティティ定義書」を開き、エンティティに TODO を選びます。
    概要（ID形式・親エンティティ）・項目一覧（論理型・要素の論理型・導出元）・操作一覧（作成 C・更新 U）・CRUD の区画が出ます。論理型は `TYP-common.年月日` のような設計項目への参照、自動で入る値は `created` のような業務モデルの値です。導出元を押すと、業務モデルのスキーマのその項目へ飛べます。C/U 表は操作の書く項目を読み、書込の無い項目も行に残します。R/D の表示は未対応です。
    作業用コピーの `design/basic/inputs/entities/corrections.yaml` に補正（例 `target: FLD-todo.title`・`set: { maxLength: 60 }`）を加え、`generate <コピー> --apply` で再生成します。項目一覧の最大文字数が 60 になり、「根拠」に補正の記録が出ます。エンティティの指定を外した横断の項目一覧でも同じ値を確認できます。
12. テーブル設計書を見ます。YDE でダッシュボード「テーブル設計書」を開き、テーブルを選びます（最初は todo）。
    概要でテーブル日本語名と区分（TODO・トランザクション）を、カラム一覧でカラム日本語名・論理型・NOT NULL とその根拠は導出元から、SQL の型は型対応表から読んでいること（`title` は `VARCHAR(100)`）を確かめます。
    テーブルを todo_tags にすると、主キーの順（todo_id が 1・seq が 2）と、索引（一意の索引と外部キーの索引）・外部キーの区画（親への外部キーは一緒に消す）が見られます。todo の索引には、台帳の `ix_todo_status_due_on` と張る理由が出ます。詳細設計項目一覧そのものには、名称や必須が無いことも確かめます。
    DDL は `./gradlew runCli -q --args="report samples/todos-sysdev ddl --print"` で見られます。
    型対応表（論理型 → SQL）で `SQL-boolean` の出力方法が `boolean` であることを見ます。テーブルを todo_task にし、done の初期値が false・設定あり、DDL が `BOOLEAN DEFAULT FALSE` になっていることを確かめます。todo の status は文字列として `DEFAULT 'OPEN'`、初期値の無いカラムは「設定なし」です。

- 設計書の依存マップの線は 4 種類です: 内容を読む・補正後の業務モデル経由・名前の付け替えだけ・順序だけ（依存の宣言だけで、値は読まない）。
  箱の並べ方と、どの変換定義がどの箱を作るかは `scripts/design-map.json` に書きます。線と「数えたこと」は計算します。
- ファイル単位の生成グラフは、箱も線もすべて計算します。ビューが選ぶスキーマと ID の型を、いまあるファイルと突き合わせます。
  「上流をすべて」で箱を選ぶと、その箱より前に確定している必要があるものを確かめられます。
- 目指す形への対応は、目指す形（業務モデル → 抽象システムモデル → 具体システムモデル → プログラム設計。定義書と設計書は、それぞれのモデルのビュー。ADR-0042）の段と、
  各ファイルをどの段のどのまとまりに置くかを `scripts/design-map.json` の `target` に書きます。まとまりの間の流れと、目指す形から外れているかどうか（後ろの段を読む・段を飛ばして読む）は計算します。
- 理想のファイル体系は、まだ無い形なので、箱と線を `scripts/design-map.json` の `ideal` に人が書きます。
  業務モデル → 抽象システムモデル（基本設計） → 具体システムモデル（詳細設計） → プログラム設計 → ソースコードの段で、定義書と設計書はビューです。
  スクリプトは、線が決まり（作る元は決めた段だけ、指すのは同じ段だけ）を守っているかを確かめ、いまあって理想に無いファイルを計算します。

- 「読み取ったこと」「決まり」は設定の `notes`・`files.notes`・`target.notes`・`ideal.notes` に人が書くメモです。構成を変えたら、図と合っているかを見直します。
- ページの見た目は `scripts/design-*.template.html` を直します。

## 業務モデルの追従

業務モデルを直すときは、まず samples/todos を直し、一通り終えたら、todos の `.yde/schemas` と `.yde/views` を、それぞれこのサンプルの `business/` へ丸ごと写します（いまは指示があったときに手で写します）。
写したら `generate samples/todos-sysdev --apply` で作り直し、git の差分で設計書の変わった所を読みます。前回の設計との違いを見る専用の仕組みは、後の作業です。

## いま計算で作れないもの

- **エンティティ定義書のレビュー**: 基底・項目固有の制限・組込み型の性質を保持し、C/U は書込の値から表示します。項目と操作を別々に選ぶため、書込の無い項目も残ります。項目の値・補正・詳細生成・DDL をテストで照合しますが、オーナーのレビュー完了を意味しません。子要素（並びの要素）への作用は C・U・D で出します（コメントは追加＝C・編集＝U・削除＝D の 3 つの操作）。条件付き必須・項目間の規則と、エンティティそのものの R/D への拡張は後回しです。
- **SQL と Java の文字**: テーブルの DDL（schema.sql）はレポートで生成します。MyBatis の XML・Entity クラス・Thymeleaf のテンプレート・CSS の文字は③で、設計書の組み立て（テーブル・項目・値・条件・部品の木）から作ります。テーブルアクセス設計書の列は業務の項目のキーで書かれています。
- **詳細設計への補正の伝わり**: テーブル名・カラム名の付け替えは補正一覧（詳細設計）に書けますが、生成時に確定し、テーブル設計書・DDL・テーブルアクセス設計書で同じ値を使います（予約語の `_` の辞書は、詳細設計項目一覧の生成の定義にあります）。
- **補正の範囲**: 基本設計の補正は再生成時に反映し、検査した確定値をビューとテーブル生成で共有します。`TYP-*` は共通型、`FLD-*` は個別項目への補正です。対応する属性と残る作業は[生成処理と対応範囲](docs/entity-generation-contract.md)にあります。ほかの設計書の対応範囲は[設計書の確定と全体レビュー](docs/design-document-migration-plan.md)にあります。
- **番号と参照の文字数の上限**: 業務モデルに上限が無いので、長さなしの `VARCHAR` です（業務モデルの側の課題）。
- **前提の形**: 件数（受け手の中の要素の条件）と読んだ行（受け手の値の条件）のほかの形は、処理設計書に「手で書く」として出ます。todos の前提は、どちらかの形です。
- **要求の形の誤り**: URL のパラメータが読めない・決まっていない HTTP メソッドのような誤りは、いまは想定外（500）に入ります。
- **完了の知らせの文**: 操作の名前の末尾の「する」を「しました」にする決まりで、名前の付け方に頼っています（「する」で終わらなければ「「名前」が済みました」）。
- **物理パラメータの画面ごとの上書き**: 既定の表（生成の定義）だけで、画面ごとに変える手書きの文書はまだありません。
- **部品と物理パラメータの種類**: 色・文字・余白・幅は画面デザイン台帳に追加しました。狭い画面で隠す列など、画面ごとの指定は必要に応じて追加します。
