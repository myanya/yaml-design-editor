# samples/todos-sysdev で守ること

- `.yde/schemas/business/` と `.yde/views/business/` は samples/todos の写しです。ここを直さず、samples/todos を直してから丸ごと写します（オーナーの指示があったとき）。
- `design/basic/`・`design/detail/` の `inputs/` は手書き入力、`derived/`・`composed/`・`final/` は生成物です。生成物は手で直さず、入力か生成定義を直し、`generate samples/todos-sysdev --apply` で作り直します。生成物が最新かは `TodosSysdevTest` が確かめます。
- 設計項目一覧は独自の ID（ENT・FLD・TYP など）を持ち、業務モデルを導出元として参照します。確定項目への移行は ADR-0039 に従います。導出記録の中の識別子を、確定項目と同じ ID の出現として登録しません。ほかの設計書は `designId` を確定項目の ID とし、従来の `id` は導出元への参照として維持します。
- エンティティ・型の生成は ADR-0039 の経路を使います。導出 → 共通型の補正 → 利用箇所の補正 → 候補の統合 → `basic-final` の検査 → 確定項目の保存です。`stage` を再適用せず、`dependsOn` で今回の依存出力を読みます。
- 人が書く補正・指定は `design/basic/inputs/entities/corrections.yaml`、追加は `design/basic/inputs/entities/additions.yaml`。区分の定義と割当を分けます。生成中の対象は文字、確定項目だけが通常の設計 ID と参照です。
- `COR-001` はオーナーが選んだ TODO の ID の代表の説明です。検証用の写しで補正を増やすときも消しません。
- 未処理の補正・未対応の追加や方式は `basic-final` で生成を止めます。対応範囲は `docs/entity-generation-contract.md` を更新してください。中間結果を確定済みとして表示しません。
- 既存のエンティティ定義書・横断ビュー・C/U とテーブル生成は、保存した確定値を読みます。ビューへ基本設計の補正や型継承の計算を戻しません。
- 生成用ビューで確定項目を集めるときは、`rows.schemaIds` などで確定文書に限定します。`idPattern` だけだと、メタスキーマを注入しないカーネルのテストで、検索条件に書いた ID の文字まで対象になることがあります。
- ほかの設計書も導出・補正と指定・追加・確定の経路を使います。基本・詳細それぞれの `inputs/documents/corrections.yaml`・`additions.yaml` が手書き入力、`final/` が確定した出力です。別の段階の種類は入力検査で拒否します。全体の内容をまとめてレビューします。
- 設計書別のダッシュボードは `design-review-<kind>`。候補と各区画を同じ種類の確定文書に限定します。この接頭辞は設計書の閲覧用で、業務画面の生成との対応検査から外します。
- `basic-document-input-gate`・`detail-document-input-gate` と各候補の合成、`system-final` の検査を経て保存します。選択する補正は `select` でコレクションとキーを指定します。対応範囲と試し方は `docs/design-document-migration-plan.md` にあります。
- `.yde/` の設計の定義は基本・詳細・共用に分け、ビューは `input/` と `review/` を分けます。フォルダを定義 ID の名前空間にせず、既存 ID を維持します。
- 設計のテスト入力は `.yde/` の定義と `design/` に限定します。生成アプリの `app/` や、その `build/`・`.gradle/`、ワークスペースの表示状態をコピーしません。
- `app/` は独立した Gradle プロジェクトです。YDE 本体の settings に登録しません。生成方法・固定資源・検証は `docs/application-generation.md` に従います。生成済みファイルは `scripts/generate-app.ps1` から更新し、記録や競合検査を迂回して上書きしません。
- アプリの型・操作・画面が変わる変更（業務モデル・生成の定義・ひな形）では、`verification/` の検証テストも合わせて直し、`scripts/verify-app.ps1`（PowerShell が無ければ `scripts/verify-app.sh`）を手元で通します。この検証は `./gradlew test` に入れていません（毎回の待ちが長くなり開発が滞るので、意図して外に出しています。オーナーの判断 2026-11-24）。GitHub Actions の `todos-application` が push ごとに回すので、そこで失敗が見つかったら、そのとき直します。
- `app/data/` は実行時の保存データで、生成記録にも Git にも入れません。Java パッケージの `data/` は生成ソースとして登録します。コミット前は `scripts/export-app-index.ps1` で Git の登録内容を取り出し、その内容で再生成と独立ビルドを確認します。
- 画面入力を `screen-operation-candidates` で先に確定し、その同じ入力から Form とメッセージを生成します。表示文を埋める処理で入力を再合成しません。
- 詳細設計の台帳・型対応・補正は `detail-tables` で合成して保存します。ビューへ補正の適用を戻さず、DDL と Mapper は同じ物理名を読みます。
- 詳細設計項目一覧（`design/detail/final/tables.yaml`）には、詳細設計にだけ出てくるものだけを持たせます（基本設計の値は導出元をたどって読む）。SQL の型は型対応表（`design/detail/inputs/tables/sql-types.yaml`。人が書く）で決め、DDL はレポート `ddl` で作り直します（`TodosSysdevTest` が `design/detail/reports/ddl/schema.sql` が最新かを確かめます）。
- 業務モデルを読む生成には `scope: business` を書きます。確定前の検査は保存スキーマの原文を得るため `scope: design` を使い、業務の値は依存出力から読みます。設計の型は設計のスコープに置き、業務モデルから設計は使いません。
- 名前の決まり（ケバブからの機械的な変換だけ・URL は業務の ID のまま）と、データ系・画面系・エラーとメッセージ系の決まり（テーブル・カラムの名前・型の対応・採番・前提とデータの決まりの確かめ方・断りの出し方）は README の通りです。
- データの決まりの確かめ方（Java・SQL・対象外）は、エラー定義書・処理設計書・テーブルアクセス設計書・メッセージ定義書・Controller の生成の定義に同じ条件で書いています。1 つを直したら、ほかもそろえます（使うキーがメッセージ定義書にあるかは `TodosSysdevTest` が確かめます）。
- `docs/design-dependency-map.html`（設計書の依存マップ）・`docs/design-file-graph.html`（ファイル単位の生成グラフ）・`docs/design-target-map.html`（目指す形への対応）・`docs/design-ideal-graph.html`（理想のファイル体系）は生成物です。手で直さず、`scripts/design-map.py` で作り直します。変換定義を足す・消す・`dependsOn` や読むビューを変えたら、作り直して同じコミットに入れます（`--check` で最新かを確かめられます。GitHub Actions の `todos-application` の `design-maps` が push ごとに確かめるので、作り直し忘れはそこで止まります）。箱の並べ方と手書きのメモは `scripts/design-map.json`、見た目は `scripts/design-*.template.html` です。変換定義やビューを足したら、`design-map.json` の `target.groups` にも置き場所を書きます（書かないと「注意」に出ます）。
- 定義書は基本設計の成果物、設計書は詳細設計の成果物として使い分けます（オーナーの用語。2026-11-24）。目指す形は、業務モデル →（アーキテクチャマッピング）→ 抽象システムモデル（基本設計）→（技術スタックマッピング）→ 具体システムモデル（詳細設計）→（コードマッピング）→ ソースコードで、定義書と設計書はそれぞれのモデルのビューです。人が書くのは業務モデルと、各段の判断（全体・個別）だけで、業務の事実の誤りは業務モデルを直します（オーナーとの議論。2026-11-24・25。決めたことと段階は `docs/system-model-plan.md`、理想の箱と線は `design-map.json` の `ideal`）。`docs/design-target-map.html` は、この前の考え方（補正後業務モデルを段に持つ）のままです。
- labs の下のワークスペースは入力にしません。
