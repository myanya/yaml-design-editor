# samples/todos-sysdev で守ること

- `.yde/schemas/business/` と `.yde/views/business/` は samples/todos の写しです。ここを直さず、samples/todos を直してから丸ごと写します（オーナーの指示があったとき）。
- `design/basic/`・`design/detail/` の `inputs/` は手書き入力、`derived/`・`composed/`・`final/` は生成物です。生成物は手で直さず、入力か生成定義を直し、`generate samples/todos-sysdev --apply` で作り直します。生成物が最新かは `TodosSysdevTest` が確かめます。
- 設計項目一覧は独自の ID（ENT・FLD・TYP など）を持ち、業務モデルを導出元として参照します。確定項目への移行は ADR-0039 に従います。導出記録の中の識別子を、確定項目と同じ ID の出現として登録しません。ほかの設計書は `designId` を確定項目の ID とし、従来の `id` は導出元への参照として維持します。
- エンティティ・型の生成は ADR-0039 の経路を使います。導出 → 共通型の補正 → 利用箇所の補正 → 候補の統合 → `basic-final` の検査 → 確定項目の保存です。`stage` を再適用せず、`dependsOn` で今回の依存出力を読みます。
- 人が書く補正・指定は `design/basic/inputs/entities/corrections.yaml`、追加は `design/basic/inputs/entities/additions.yaml`。区分の定義と割当を分けます。生成中の対象は文字、確定項目だけが通常の設計 ID と参照です。
- 業務の事実の誤りや食い違いは、補正ではなく業務モデルを直します（ADR-0042）。TODO の ID の説明は、オーナーが選んだ代表の文に業務モデルの側でそろえ、補正 `COR-001` を無くしました。基本設計の補正は、いま 0 件です。
- 未処理の補正・未対応の追加や方式は `basic-final` で生成を止めます。対応範囲は `docs/entity-generation-contract.md` を更新してください。中間結果を確定済みとして表示しません。
- 既存のエンティティ定義書・横断ビュー・C/U とテーブル生成は、保存した確定値を読みます。ビューへ基本設計の補正や型継承の計算を戻しません。
- 生成用ビューで確定項目を集めるときは、`rows.schemaIds` などで確定文書に限定します。`idPattern` だけだと、メタスキーマを注入しないカーネルのテストで、検索条件に書いた ID の文字まで対象になることがあります。
- ほかの設計書も導出・補正と指定・追加・確定の経路を使います。基本・詳細それぞれの `inputs/documents/corrections.yaml`・`additions.yaml` が手書き入力、`final/` が確定した出力です。別の段階の種類は入力検査で拒否します。全体の内容をまとめてレビューします。
- 設計書別のダッシュボードは `design-review-<kind>`。候補と各区画を同じ種類の確定文書に限定します。この接頭辞は設計書の閲覧用で、業務画面の生成との対応検査から外します。
- `basic-document-input-gate`・`detail-document-input-gate` と各候補の合成、`system-final` の検査を経て保存します。選択する補正は `select` でコレクションとキーを指定します。対応範囲と試し方は `docs/design-document-migration-plan.md` にあります。
- `.yde/` の設計の定義は基本・詳細・共用に分け、ビューは `input/` と `review/` を分けます。フォルダを定義 ID の名前空間にせず、既存 ID を維持します。
- 設計のテスト入力は `.yde/` の定義と `design/` に限定します。生成アプリの `app/` や、その `build/`・`.gradle/`、ワークスペースの表示状態をコピーしません。
- `app/` は独立した Gradle プロジェクトです。YDE 本体の settings に登録しません。生成方法・固定資源・検証は `docs/application-generation.md` に従います。生成済みファイルは `scripts/generate-app.ps1` から更新し、記録や競合検査を迂回して上書きしません。
- アプリの型・操作・画面が変わる変更（業務モデル・生成の定義・ひな形）では、`verification/` の検証テストも合わせて直し、`scripts/verify-app.ps1`（PowerShell が無ければ `scripts/verify-app.sh`）を手元で通します。この検証は `./gradlew test` に入れていません（毎回の待ちが長くなり開発が滞るので、意図して外に出しています。オーナーの判断 2026-11-24）。GitHub Actions の `todos-application` が push ごとに回すので、そこで失敗が見つかったら、そのとき直します。
- `app/data/` は実行時の保存データで、生成記録にも Git にも入れません。Java パッケージの `data/` は生成ソースとして登録します。コミット前は `scripts/export-app-index.ps1` で Git の登録内容を取り出し、その内容で再生成と独立ビルドを確認します。
- 画面の入力は、操作の入力（`PRM-`）が持ちます。画面を解いた形（`basic-screens-resolved`）の入力から、Form とメッセージを生成します（画面だけの入力の決まりは持ちません）。
- 詳細設計の台帳・型対応・補正は `detail-tables` で合成して保存します。ビューへ補正の適用を戻さず、DDL と Mapper は同じ物理名を読みます。
- 詳細設計項目一覧（`design/detail/final/tables.yaml`）には、詳細設計にだけ出てくるものだけを持たせます（基本設計の値は導出元をたどって読む）。SQL の型は型対応表（`design/detail/inputs/tables/sql-types.yaml`。人が書く）で決め、DDL はレポート `ddl` で作り直します（`TodosSysdevTest` が `design/detail/reports/ddl/schema.sql` が最新かを確かめます）。
- 業務モデルを読む生成には `scope: business` を書きます。確定前の検査は保存スキーマの原文を得るため `scope: design` を使い、業務の値は依存出力から読みます。設計の型は設計のスコープに置き、業務モデルから設計は使いません。
- 名前の決まり（ケバブからの機械的な変換だけ・URL は業務の ID のまま）と、データ系・画面系・エラーとメッセージ系の決まり（テーブル・カラムの名前・型の対応・採番・前提とデータの決まりの確かめ方・断りの出し方）は README の通りです。
- データの決まりの確かめ方（Java・SQL・対象外）は、エラー定義書・処理設計書・テーブルアクセス設計書・メッセージ定義書・Controller の生成の定義に同じ条件で書いています。1 つを直したら、ほかもそろえます（使うキーがメッセージ定義書にあるかは `TodosSysdevTest` が確かめます）。
- `docs/design-dependency-map.html`（設計書の依存マップ）・`docs/design-file-graph.html`（ファイル単位の生成グラフ）・`docs/design-target-map.html`（目指す形への対応）・`docs/design-ideal-graph.html`（理想のファイル体系）・`docs/design-progress.html`（移行の進み具合）は生成物です。手で直さず、`scripts/design-map.py` で作り直します。変換定義を足す・消す・`dependsOn` や読むビューを変えたら、作り直して同じコミットに入れます（`--check` で最新かを確かめられます。GitHub Actions の `todos-application` の `design-maps` が push ごとに確かめるので、作り直し忘れはそこで止まります）。箱の並べ方と手書きのメモは `scripts/design-map.json`、見た目は `scripts/design-*.template.html` です。変換定義やビューを足したら、`design-map.json` の `target.groups` にも置き場所を書きます（書かないと「注意」に出ます）。
- 定義書は基本設計の成果物、設計書は詳細設計の成果物として使い分けます（オーナーの用語。2026-11-24）。目指す形は、業務モデル →（アーキテクチャマッピング）→ 抽象システムモデル（基本設計）→（技術スタックマッピング）→ 具体システムモデル（詳細設計）→（コードマッピング）→ ソースコードで、定義書と設計書はそれぞれのモデルのビューです。人が書くのは業務モデルと、各段の判断（全体・個別）だけで、業務の事実の誤りは業務モデルを直します（ADR-0042。移す順序は `docs/system-model-plan.md`、理想の箱と線は `design-map.json` の `ideal`）。いまの体系はまだ移行前なので、変換定義を直すときは、ADR-0042 の決まり（1 つ前の段だけを読む・項目の形で保存して ID で指す・定義書と設計書はビュー）に近づく向きに直します。
- `design/basic/final/states.yaml`（状態と遷移）・`rules.yaml`（データの決まり）・`queries.yaml`（一覧の検索条件）は、ADR-0042 の形で足した確定項目です。項目の形で、同じ段の項目（エンティティ・項目・操作・状態）を ID で指し、業務モデルを直接読んで作ります。詳細設計の「状態の判定」「処理設計書」「テーブルアクセス設計書」は、状態・決まり・読み出しを、業務モデルではなくここから読みます（処理設計書とテーブルアクセス設計書は、入力で `designRules`・`designQueries` として重ねて読む）。新しい種類を足すときは、これにならいます。条件や計算の式は、業務モデルの式のまま持っています。
- `design/basic/final/operations/<操作>.yaml`（操作）も項目の形の確定項目です（1 操作 1 ファイル）。操作 `ACT-`・入力 `PRM-`・前提 `PRE-`・効果 `EFF-` に ID を振り、エンティティ・項目・型・遷移・データの決まり・エンティティから見た書込（`CRUD-`）を ID で指します。指す向きは操作からの 1 方向です。アクション定義書の文書と、確定した操作を重ねた補正後の業務モデルは無くしました（アクション定義書は、操作のファイルの文書ビュー `action-design`）。
- 操作の項目は、型と項目への補正が入力の決まりに届くように、補正後の業務モデル（`system-model`）を読みます。操作への個別の判断は `design/basic/inputs/operations/corrections.yaml` に「対象の ID と `set`」で書き、`basic-operations` が項目へ直接当て、当てた判断を項目の `decisions` に残します。対象は `ACT-`（名称・説明・入力の送り方）と `PRM-`（名称・決まり・はじめの値）だけで、識別する値と振る舞い（状態・前提・効果・確かめる決まり）は入力の形（`basic-operation-corrections`）で止めます。置き換えられるキーを増やすときは、この形の `set` の項目に足します。型より緩める指定（型が最大 100 字の入力を 150 字にする）を止める検査は、まだありません。
- 操作を読む変換定義は、業務モデルの `actions` ではなく、項目を解いたもの（`design/basic/composed/operations-resolved.yaml`。変換定義 `basic-operations-resolved`）から読みます。詳細設計の 8 種は `designActions` として重ね、基本設計の画面定義書 4 種・ドメイン定義書・画面の入力項目を重ねたモデルは、モデルの `actions` を置き換えて読みます。解いた形は、ID で指した先を値に置き換えた途中経過で、入力を丸ごと写す読み手があるので、キーを業務モデルと同じ順に並べています。読む側が新しい属性を要るときは、まず操作の項目に持たせ、解いた形に足します。業務モデルが「なし」と書いた並び（入力・前提・確かめる決まり）は、空の並びのまま持ちます。
- `design/basic/final/screens/<画面>.yaml`（画面）も項目の形の確定項目です（1 画面 1 ファイル。操作の画面は、入力画面・確認画面・確定を操作ごとの 1 ファイル）。画面 `SCR-`・絞り込み `FLT-`・区画と表 `SEC-`・ボタン `BTN-` に ID を振り、操作・入力・検索条件・項目・行き先の画面を ID で指します。ボタンの名称と出す条件、区画の名称と列、入力の決まり、断りの文は写しません（指した先から決まります）。
- 画面への個別の判断は `design/basic/inputs/screens/corrections.yaml` に「対象の ID と `set`」で書き、`basic-screens` が項目へ直接当てます。置き換えられるのは名称・説明・URL・リクエストだけです。入力の決まりは画面では変えず、操作の入力（`PRM-`）への判断に書きます（画面と Service で検査がずれないようにするため）。
- 画面を読む変換定義は、項目を解いたもの（`design/basic/composed/screens-resolved.yaml`。変換定義 `basic-screens-resolved`。ビュー `basic-screens-resolved-lists`・`-details`・`-operations`）から読みます。解いた形の `record` は、以前の画面定義書と同じ形です。画面の項目に値を足すときは、解いた形の出し方も合わせます。
- ダッシュボードからたどれる範囲は、業務モデルの `reach` ではなく、画面を解いた形の `reach`（画面の項目があるダッシュボード・エンティティ・操作）から読みます。詳細設計の変換定義は、モデルに `designReach` として重ねて読みます（ビュー `basic-screens-resolved-input`）。画面設計書の一覧と詳細は、ボタンと表の名称を、重ねた解いた形（`screen`）から引きます。
- 入力画面と確認画面も `SCR-` の ID を持つので、ビュー `basic-model-screens` の行には、画面の項目（`kind` がある行）と、その中の入力画面・確認画面が混ざります。読む側は `kind` のある行だけを使います。
- 基本設計の項目を足す・読む元を変えるときは、補正が 0 件のときの一致だけでなく、補正を入れた状態でも前後の生成物が同じかを確かめます（補正が 0 件だと、判断が届かなくなる誤りが生成物に出ません）。
- システム化のために要る項目（業務モデルに無い項目）は、業務モデルに足さず、方式の指定（全体の判断）から規則で足します（ADR-0042「項目の出どころ」）。書き方は `design/basic/inputs/entities/corrections.yaml` の `specifications` で、対象に区分（`CLS-transaction`）を書くと、その区分のエンティティすべてに当たります。いまある方式は `optimistic-lock`（同時更新を版で検出する。項目「版」を足す）で、規則は `basic-final` の `policy-entities` にあります。足した項目は `addedBy` と根拠（`origins`）に指定の ID を持ち、基本設計の項目より下流（テーブルの列・行のクラス・Mapper）にだけ出ます。業務モデルを写したモデル（`system-model`）には入らないので、業務の画面の表示項目にはなりません。方式を足すときは、規則を書いたうえで、`basic-final` の未処理の検査（`finalization-gate` の `specifications`）から、その方式を外します（外さないと「未処理の入力」で止まります）。型の名前を持たない整数の列は、型対応表の `SQL-int` を使います。
- 楽観ロック（同時更新の検出）は、方式 `optimistic-lock` の指定から次のように組み立てます。
  - 基本設計の操作（`basic-operations`）に 3 つを足します。読んだときのバージョンを運ぶ入力（`carried: true`。初期値は受け手の `version`）、バージョンが一致するという前提（`<キー>-unchanged`）、バージョンをインクリメントする効果（`auto: revision`。値の式は持たない）です。
  - 対象は、受け手がバージョンを持つエンティティの操作と、受け手がその子（入れ子の要素）の操作です。子の操作では、入力の初期値を親から読み（`$of: owner`）、前提は親の行に対する条件（`of: owner`）、効果は親の項目に対するものになります。
  - 解いた形（`basic-operations-resolved`）は、運ぶ入力を `inputParams` から外して `carried`（キー）と `carriedValues`（読み元）に分けます。`auto: revision` の値は、受け手の項目なら `{$copy: <キー>, $of: next}`、親の項目なら `$of: ownerNext` として渡します。
  - 処理設計書（`processes-derived`）は、受け手の行に対する前提を「読んだ行で確かめる」検査（`checkMode: current`）に、親の行に対する前提を「親の行を読む手順（`read-owner`）＋親の行で確かめる検査（`checkMode: owner`）」にします。テーブルアクセス設計書は、親の行に対する前提を件数の検査にしません。
  - プログラム設計は、`application-service-bindings` が `next`・`owner`・`ownerNext` のシンボルを用意し、`application-service-programs` が前提の `equals: $入力名`（読んだ行の値と入力の比較）と `read-owner` を Java にします。
  - 画面の項目は、運ぶ入力を `hidden`（`PRM-` の並び）に持ちます。読み元は操作の入力が持ち、画面を解いた形で `carried` になります。画面設計書は入力画面と確認画面の `hidden` に入れます。Web の実行部（`.yde/reports/application/WebRuntime.java`・`WebPage.java`）は、入力画面では初期値と一緒に、入力画面の無い操作では確認画面を出すときに、運ぶ値を受け手（または親）から読みます。
  - 検査の範囲は、操作の画面を開いてから確定するまでです。比較と UPDATE はアトミックではないので、操作を直列に実行する現在の構成（`writeConcurrency: local-serialized`）が前提です。
- `app/` の再生成は、Windows では `scripts/generate-app.ps1`、それ以外では `scripts/generate-app.py` を使います（手順と安全確認は同じで、どちらで作り直しても同じ結果になります。GitHub Actions の `todos-application` が両方の `-Check` / `--check` を実行します）。片方の手順を変えたら、もう片方も合わせます。Service の引数や Form が変わったら、`verification/` の検証テストも直し、`verify-app.sh`（Windows は `verify-app.ps1`）で確かめます。
- 移行の進み具合（`docs/design-progress.html`）は、目標のファイル体系を「段 × 系統」に置き、箱ごとに済んだこと・残っていることを出します。目標の箱・箱の間の線（作る元・同じ段を指す・ビューが読む）・無くすもの・やることは `scripts/design-map.json` の `plan` に書き、済んだかどうかは、変換定義・ファイルがあるか・何を読んでいるか（`done` の条件）から `scripts/design-map.py` が計算します。「済」を手で書きません。やることを足す・変えるときは `plan.tasks` を直します。
- **作業の始め方（オーナーの指示。2026-11-27）。** 移行の作業（歩、またはその中のまとまり）を始める前に、次を説明して、オーナーの確認を取ってから着手します。
  - どこを実現するか（[移行の進み具合](docs/design-progress.html) のどの箱か）。
  - どのように実現するか（作る項目の形、読むもの、書く変換定義、変える読み手、消すもの、確かめ方）。
  - 中間ファイル（目標のファイル体系に無いファイル）が出るかどうか。出るなら、なぜ要るのか、いつ消すのか。出さずに済む方法があるなら、そちらを選びます。
- labs の下のワークスペースは入力にしません。
