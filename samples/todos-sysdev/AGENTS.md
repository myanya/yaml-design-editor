# samples/todos-sysdev で守ること

- `.yde/schemas/business/` と `.yde/views/business/` は samples/todos の写しです。ここを直さず、samples/todos を直してから丸ごと写します（オーナーの指示があったとき）。
- `design/basic/`・`design/detail/` の `inputs/` は手書き入力、`derived/`・`composed/`・`final/` は生成物です。生成物は手で直さず、入力か生成定義を直し、`generate samples/todos-sysdev --apply` で作り直します。生成物が最新かは `TodosSysdevTest` が確かめます。
- 設計項目一覧は独自の ID（ENT・FLD・TYP など）を持ち、業務モデルを導出元として参照します。確定項目への移行は ADR-0039 に従います。導出記録の中の識別子を、確定項目と同じ ID の出現として登録しません。ほかの設計書は `designId` を確定項目の ID とし、従来の `id` は導出元への参照として維持します。
- エンティティ・型の生成は ADR-0039 の経路を使います。導出 → 共通型の補正 → 利用箇所の補正 → 候補の統合 → `basic-final` の検査 → 確定項目の保存です。`stage` を再適用せず、`dependsOn` で今回の依存出力を読みます。
- 人が書く補正・指定は `design/basic/inputs/entities/corrections.yaml`、追加は `design/basic/inputs/entities/additions.yaml`。区分の定義と割当を分けます。生成中の対象は文字、確定項目だけが通常の設計 ID と参照です。
- 業務の事実の誤りや食い違いは、補正ではなく業務モデルを直します（ADR-0042）。TODO の ID の説明は、オーナーが選んだ代表の文に業務モデルの側でそろえ、補正 `COR-001` を無くしました。基本設計の補正は、いま 0 件です。
- 未処理の補正・未対応の追加や方式は `basic-final` で生成を止めます。対応範囲は `docs/entity-generation-contract.md` を更新してください。中間結果を確定済みとして表示しません。
- 既存のエンティティ定義書・横断ビュー・C/U とテーブル生成は、保存した確定値を読みます。ビューへ基本設計の補正や型継承の計算を戻しません。
- 生成用ビューで確定項目を集めるときは、`rows.schemaIds` などで確定文書に限定します。`idPattern` だけだと、メタスキーマを注入しないカーネルのテストで、検索条件に書いた ID の文字まで対象になることがあります。
- ほかの設計書も導出・補正と指定・追加・確定の経路を使います。基本・詳細それぞれの `inputs/documents/corrections.yaml`・`additions.yaml` が手書き入力、`final/` が確定した出力です。別の段階の種類は入力検査で拒否します。全体の内容をまとめてレビューします。
- 設計書別のダッシュボードは `design-review-<kind>`。候補と各区画を同じ種類の確定文書に限定します。この接頭辞は設計書の閲覧用で、業務画面の生成との対応検査から外します。
- `basic-document-input-gate`・`detail-document-input-gate` と各候補の合成、`system-final` の検査を経て保存します。選択する補正は `select` でコレクションとキーを指定します。対応範囲と試し方は `docs/design-document-migration-plan.md` にあります。
- `.yde/` の設計の定義は基本・詳細・共用に分け、ビューは `input/` と `review/` を分けます。フォルダを定義 ID の名前空間にせず、既存 ID を維持します。
- 設計のテスト入力は `.yde/` の定義と `design/` に限定します。生成アプリの `app/` や、その `build/`・`.gradle/`、ワークスペースの表示状態をコピーしません。
- `app/` は独立した Gradle プロジェクトです。YDE 本体の settings に登録しません。生成方法・固定資源・検証は `docs/application-generation.md` に従います。生成済みファイルは `scripts/generate-app.ps1` から更新し、記録や競合検査を迂回して上書きしません。
- アプリの型・操作・画面が変わる変更（業務モデル・生成の定義・ひな形）では、`verification/` の検証テストも合わせて直し、`scripts/verify-app.ps1`（PowerShell が無ければ `scripts/verify-app.sh`）を手元で通します。この検証は `./gradlew test` に入れていません（毎回の待ちが長くなり開発が滞るので、意図して外に出しています。オーナーの判断 2026-11-24）。GitHub Actions の `todos-application` が push ごとに回すので、そこで失敗が見つかったら、そのとき直します。
- `app/data/` は実行時の保存データで、生成記録にも Git にも入れません。Java パッケージの `data/` は生成ソースとして登録します。コミット前は `scripts/export-app-index.ps1` で Git の登録内容を取り出し、その内容で再生成と独立ビルドを確認します。
- 画面の入力は、操作の入力（`PRM-`）が持ちます。画面を解いた形（`basic-screens-resolved`）の入力から、Form とメッセージを生成します（画面だけの入力の決まりは持ちません）。
- テーブルの項目は、変換定義 `detail-tables` の 1 本で作ります（基本設計の項目からの導出と、台帳・型対応・補正の合成を 1 本で行い、補正前のファイルは作りません。当てた補正は `decisions` に残ります）。ビューへ補正の適用を戻さず、DDL と Mapper は同じ物理名を読みます。
- 詳細設計項目一覧（`design/detail/final/tables.yaml`）には、詳細設計にだけ出てくるものと、次の段が要るので運ぶもの（カラムの `base`・`maxLength`・`default`）を持たせます。行モデルのプログラム設計（`application-data-model`）はカラムの項目だけを読み、基本設計を読みません。名称・必須・選択肢は、テーブル設計書のビューが導出元をたどって読みます。SQL の型は型対応表（`design/detail/inputs/tables/sql-types.yaml`。人が書く）で決め、DDL はレポート `ddl` で作り直します（`TodosSysdevTest` が `design/detail/reports/ddl/schema.sql` が最新かを確かめます）。
- 業務モデルを読む生成には `scope: business` を書きます。確定前の検査は保存スキーマの原文を得るため `scope: design` を使い、業務の値は依存出力から読みます。設計の型は設計のスコープに置き、業務モデルから設計は使いません。
- 名前の決まり（ケバブからの機械的な変換だけ・URL は業務の ID のまま）と、データ系・画面系・エラーとメッセージ系の決まり（テーブル・カラムの名前・型の対応・採番・前提とデータの決まりの確かめ方・断りの出し方）は README の通りです。
- 「どの制約（データの決まり）を、操作の実行時にチェックするか」の条件は、エラー定義（`basic-errors`）・メッセージ定義（`basic-messages`）・処理設計書・テーブルへの読み書き・Controller の変換定義に、同じ条件で書いています。1 つを直したら、ほかもそろえます（参照しているメッセージキーが定義にあるかは `TodosSysdevTest` が検証します）。チェックの実装方式（アプリ側の判定か SQL か）は、基本設計のエラー定義には持たせず、処理設計書だけが持ちます。
- `design/basic/final/errors.yaml`（エラー定義）と `messages.yaml`（メッセージ定義）は、ID 付きレコードのリストです。変換定義は `basic-errors`・`basic-messages` の各 1 本で、入力は基本設計のレコード（操作・制約・一覧の検索条件・エンティティ・画面）だけです（業務モデルと中間ファイルは読まない）。
  - エラーケース `ERR-<操作>.<名前>` は、エラー種別 `ERK-`・操作 `ACT-`・原因（`ENT-`・`FLD-`・`TRN-`・`PRE-`・`RUL-`・`SCR-`）・メッセージ `MSG-` を ID で参照します。入力値が原因の制約違反は、その入力パラメータ `PRM-` も参照します。
  - メッセージ `MSG-<キー>` は、テキストの生成元を `source` で参照します。バリデーションメッセージ（`MSG-input.<操作>.<入力>.<チェック>`）は、キーを持たず、操作・入力パラメータ・チェックの種類で持ちます。メッセージキー（`validation.NotNull.addCategoryForm.name` のように Form クラス名と Bean Validation のコードを含む）は、Form のプログラム設計（`application-web-forms` の `validationMessages`）が組み立てます。
  - アプリに埋め込むメッセージカタログ（`web-model.json` の `messages`）は、Web のプログラム設計（`application-web`）がキーとテキストだけを出力します。
  - 基本設計のレコードへのオーバーライド（個別の判断）は `design/basic/inputs/decisions.yaml` の 1 ファイルに「対象の ID と `set`」で書きます（ID は `BDEC-`）。いまの対象はメッセージのテキスト（`text`）です。操作と画面へのオーバーライド（`inputs/operations/`・`inputs/screens/`）は、歩 6 でここへ移します。
- `design/detail/final/status/<状態の流れ>.yaml`（状態の型）は、詳細設計で最初に項目の形にした確定項目です。基本設計の「状態と遷移」の項目だけを読み（変換定義 `detail-status` の 1 本。導出と確定に分けない）、型 `ENM-`・定数 `ENC-`・判定 `ENG-` に ID を振り、各要素が作る元（`LCY-`・`STA-`・`STG-`・`TRN-`）を `source` で指します。同じファイルの中の定数は ID で指し、読む側（`application-runtime-model`・`detail-processes`）が定数の名前に解きます。
- `design/detail/final/table-access/<エンティティ>.yaml`（テーブルへの読み書き）も項目の形です。変換定義は `detail-table-access` の 1 本で、基本設計の項目（エンティティ・操作・データの決まり・一覧の検索条件・画面）と、同じ詳細設計のテーブルの項目だけを読みます（業務モデルも、解いた形も読まない）。エンティティ型ごとのまとまり `ACC-`（Mapper 1 つ）とメソッド `MTH-` に ID を振り、メソッドは作る元（`sources`。`ACT-`・`QRY-`・`SCR-`・`ENT-`）を指し、テーブルとカラムは ID（`TBL-`・`COL-`）で指します（名前を写さない）。前提・データの決まり・同じ条件のメソッドも ID（`PRE-`・`RUL-`・`MTH-`）です。Mapper のプログラム設計（`application-access`）は、入口の規則（`access-document`）で ID から名前を引いて読みます。
  - プログラム設計の Mapper の ID が `MAP-` なので、詳細設計の側は `ACC-` にしています（同じ ID は使えない）。
  - ID で 1 件読むメソッド（`findDetail`）と参照の候補（`selectAll`）は、詳細画面（画面の項目の `kind: detail`）があるエンティティに作ります。画面を解いた形の「たどれる範囲」ではなく、画面の項目を直接読みます。詳細画面の無いエンティティ（明細の形によっては、1 件読む読み出しをまだ作れない）には作りません。
  - 基本設計の項目を読む側の形に組む規則（`item-entity`・`item-action`）は、この定義の中に持っています。変換定義の規則は定義の間で共有できないためです（devtrack UX-384）。
- `design/detail/final/processes/<操作>.yaml`（処理の手順）も ID 付きレコードです。変換定義は `detail-processes` の 1 本で、入力は基本設計のレコード（操作・エンティティ・型・状態と遷移・制約）と、同じ詳細設計のレコード（テーブルへの読み書き・状態の型）だけです（業務モデル・中間ファイル「操作を解いた形」・Mapper の名前のマッピングテーブルは読まない）。
  - 処理 `PRC-<操作>`（Service のメソッド 1 つ）とステップ `STP-<操作>.<連番>` に ID を振ります。ステップは、呼ぶ Mapper のメソッド `MTH-`・事前条件 `PRE-`・状態エラーのエラーケース `ERR-<操作>.state`・制約 `RUL-`・メッセージ `MSG-`・エンティティ `ENT-`・状態の定数 `ENC-` を ID で参照します。メッセージのテキストと Mapper の呼び名はコピーしません。業務モデルの式（`rule` など）の中は変えません。
  - 操作のレコードが ID で参照している先の解決は、この変換定義の中のルール（`resolved-action` 以下）で行います。中間ファイル「操作を解いた形」（`basic-operations-resolved`）と同じルールで、画面の設計書（歩 4 の対象）がまだその中間ファイルを読んでいるため、いまは両方にあります。
  - 処理のレコードは、Service が受け取る入力パラメータの定義（`inputs`。基本設計の操作の入力を、参照先を解決したもの）も持ちます。Service の入力のプログラム設計（`application-service-inputs`）は、基本設計も中間ファイルも読まず、これを読みます。
  - オーバーライドは `decisions.yaml` に書きます（対象 `PRC-`。`serviceClass`・`serviceMethod`）。
  - 処理の手順を入力にする変換定義（`application-service-inputs`・`application-service-bindings`・`application-service-programs`・`application-process-gate`）は、入力アダプタ（`process-document` 以下のルール）で、ID から名前・テキスト・定数名を解決してから読みます。同じアダプタが 4 本にあります（ルールを変換定義の間で共有できないため。devtrack UX-384）。直すときは 4 本をそろえます。
- 詳細設計の方式の指定（全体の判断）は `design/detail/inputs/specifications.yaml` に「方式（`rule`）と対象」で書きます（ID は `DSPC-`。対象は基本設計のエンティティ `ENT-` か区分 `CLS-`）。規則が項目を足す・変えるもので、個別の項目の値を置き換える個別の判断（`decisions.yaml`）とは分けます。いまの方式は論理削除（`soft-delete`）です。
  - `detail-tables` が、対象のエンティティの主のテーブルに、削除の印のカラム（`deleted`。`role: deleted`・`addedBy` に指定の ID）を足します。対象が見つからない指定は、生成が止まります。
  - `detail-table-access` は、方式の指定を読まず、テーブルの項目（削除の印のカラムがあるか）から決めます。消すメソッドは印を立てる update（`softDelete: true`）に、読む・数える・集計のメソッドと、一緒に読む明細・件数の式には「削除されていない」の条件を足します。最大の値（番号と並び順の採番）と足すメソッドは変えません（消した行の番号を使い回さない）。
  - 操作の項目（効果は「消す」）・状態の遷移・処理の手順は変わりません。指定を外すと、行を消す（物理削除）に戻ります。
  - まだ対応していない所: 論理削除の型を「参照してくる要素」として数える集計（`via` の集計）と、つなぐテーブル（`join`）の側の条件。このサンプルの対象（作業項目）では出ません。
- 詳細設計の項目への個別の判断は `design/detail/inputs/decisions.yaml` の 1 ファイルに「対象の ID と `set`」で書きます（ID は `DDEC-`）。詳細設計の種類を項目の形にするたびに、対象と置き換えられる値を、スキーマ `detail-decisions` と、その種類の変換定義に足します。入力の検査は、既存の `detail-document-input-gate` に足します（検査の記録のファイルを増やさない）。
- 状態の型で置き換えられるのは、enum の名前と、判定のメソッドの名前だけです。遷移は業務の事実なので変えられません。定数の名前も変えられません（enum の定数の名前が、そのままテーブルに保存する値になるため。変えるなら、保存する値と定数の対応を持つ仕組みが先に要ります）。
- 変換の条件の `matches` は、正規表現が文字列の全体に合うときだけ成り立ちます。接頭辞で分けるときは `startsWith` を使います。
- **作業の始め方（オーナーの指示。2026-11-27）。** 移行の作業（歩、またはその中のまとまり）を始める前に、次を説明して、オーナーの確認を取ってから着手します。
  - どこを実現するか（[移行の進み具合](docs/design-progress.html) のどの箱か）。
  - どのように実現するか（作る項目の形、読むもの、書く変換定義、変える読み手、消すもの、確かめ方）。
  - 中間ファイル（目標のファイル体系に無いファイル）が出るかどうか。出るなら、なぜ要るのか、いつ消すのか。出さずに済む方法があるなら、そちらを選びます。
- labs の下のワークスペースは入力にしません。
