# TODO管理モデル

YDE（YAML Design Editor）上で実際に使える、個人向けのTODO管理ワークスペースです。
登録・着手・中断・再開・完了・中止・コメント追加・作業項目の追加と済・編集を操作として実行できます。閲覧専用モードでもTODOを管理でき、AI接続は不要です。
登録時のTODO番号と作成日、個票を変えたときの更新日、作業項目・カテゴリ・タグの番号は自動で入ります。状態を変える操作は、個票の「状態の履歴」に1行ずつ記録を残します。
TODOは、個票の中に作業項目（済んでいないものがあるうちは完了できない明細）を持ち、カテゴリ（1つまで）とタグ（いくつでも。多対多）で分類します。

`.yde/`の型・制約・操作・ビューがTODO管理のモデルで、`todos/`の文書がそのモデルで管理する具体的なデータです。
TODOの状態は、状態の流れ（`todo-behavior.yaml`の Lifecycle）を正にして管理します。どの状態からどの操作でどこへ移るかはここにだけ書き、操作の前提・状態の書き込み・状態の履歴・ダッシュボードの業務の流れは、ここから作られます。
`todos-sysdev-*`では、このTODO管理を専用アプリにした場合の設計を詳しくします。
[todos-sysdev-tablemodel](../todos-sysdev-tablemodel/README.md)は、この業務を概念・論理・物理モデルに具体化し、YDEでのSQL生成を検討するサンプルです。
担当者・共同編集・認証・通知・繰り返しタスクは扱いません。

## 配置と原本

| 場所 | 内容 |
|---|---|
| `todos/todo-list.yaml` | TODOのID・タイトル・概要・カテゴリ・タグ・元のTODOの原本 |
| `todos/details/<ID>.yaml` | 同じTODOの状態・日付・詳細・結果・作業項目・コメント・状態の履歴 |
| `todos/category-list.yaml` | カテゴリのIDと名前 |
| `todos/tag-list.yaml` | タグのIDと名前 |
| `.yde/schemas/todo-behavior.yaml` | 状態の流れの原本（状態・入口・移り方・終わり・状態の履歴） |
| `.yde/schemas/common.yaml` | 共通型と整合検査 |
| `.yde/schemas/todo-list.yaml`・`todo-detail.yaml`・`category-list.yaml`・`tag-list.yaml` | 型を文書に適用する定義（個票の作業項目の検査は `todo-detail.yaml`） |
| `.yde/schemas/operations.yaml` | TODOの登録・状態を変える操作・コメント追加・作業項目の追加・編集の実行定義 |
| `.yde/schemas/relations.yaml` | 関係レジストリ（カテゴリへの参照 `in-category`、タグへの参照 `tagged`、元のTODOへの参照 `follow-up-of`） |
| `.yde/views/` | TODOダッシュボード（業務の流れつき）・TODO管理・期限順・カテゴリ×ステータスとタグ×ステータスの集計 |
| `scenarios/lifecycle.yaml` | 状態の流れを確かめる業務シナリオ |

`.yde/workspace.yaml`で`todos`を台帳として指定しています。
スキーマとビューも同梱しているため、このディレクトリをコピーして単独で開けます。
一覧は定義出現、個票は同じIDの詳細化出現です。タイトルや概要を個票に転記しません。
`TODO-001`は具体的な作業の番号です。概念ERなどの設計IDはテーブルモデル側で扱います。

## 状態と移り方

| 保存する値 | 表示 | できる操作（移り先） |
|---|---|---|
| `OPEN` | 未着手 | 着手（対応中）・中止（中止） |
| `IN_PROGRESS` | 対応中 | 中断（中断）・完了（完了）・中止（中止） |
| `SUSPENDED` | 中断 | 再開（対応中）・中止（中止） |
| `CLOSED` | 完了 | なし（終わり） |
| `CANCELED` | 中止 | なし（終わり） |

- **中断**は一時的に止めることで、理由と再開予定日（決まっていれば）を状態の履歴に残します。再開すると対応中に戻ります。
- **完了**はやり終えたことで、完了日と結果を残します。完了するのは対応中からだけで、未着手からは直接完了できません。[作業項目](#作業項目で作業を小分けにする)に済んでいないものがあるうちも完了できません。完了したTODOは戻せません。
- **中止**はやらないと決めたことで、理由を結果欄と状態の履歴に残します。未着手・対応中・中断のどれからでも中止できます。
- 完了したTODOに追加の作業が要るときは、[続きのTODOを登録します](#続きのtodoを登録する)。

この表の移り方は `todo-behavior.yaml` に書いたものです。操作の定義には、状態の条件も状態の書き込みも書いていません。
状態の流れは 2 段で書いています。粗い流れは「未完了 → 完了／中止」だけで、未着手・対応中・中断は未完了の中の流れ（詳細化）として別に書きます。
中止は未完了から出る 1 本の移り方なので、未着手・対応中・中断のどれからでもでき、完了は未完了の出口を対応中に狭めています。
保存する値は未着手・対応中・中断のどれかで、「未完了」という値は持ちません。
移れない状態で操作を選ぶと、メニューが無効になり、「「TODO-005」は「未着手」なので、「TODOを完了する」はできません（できるのは「対応中」のとき）」のように理由が出ます。

## 操作を試す

業務の状況から始める場合は、先に [ダッシュボードを試す](#ダッシュボードを試す) を参照してください。

作業用にこのディレクトリをコピーし、YDEで開いてください。

1. `todos/todo-list.yaml`を開き、右ペインの「操作」またはコマンドパレット（Ctrl+K）で「TODOを登録する」を選びます。
2. タイトル・概要を入力します。カテゴリ・元のTODO・期限・詳細は任意で、番号と登録日の入力欄はありません。
3. 「確認」で一覧と個票の差分を見て「適用」を押します。両方が一度に保存され、番号に使われている番号の次（配布時のデータでは`TODO-009`）が入ること、状態が未着手で、作成日・更新日・状態の履歴の最初の行（登録）に本日が入ることを個票で確認します。
4. 「TODO管理」ビューの新しい行の「⋯」から「TODOに着手する」を選び、追加の入力なしで確認・適用すると「対応中」になることを確認します。
5. 同じ行で「TODOを中断する」を選び、中断日（本日）・理由・再開予定日を入力して適用すると「中断」になることを確認します。
6. 「TODOを再開する」を選び、再開日を確認して適用すると「対応中」に戻ることを確認します。
7. 「TODOを完了する」を選び、完了日に本日が入っていることを確認し、結果を入力して適用します。日付は修正できます。
8. 完了したTODOでは、着手・中断・再開・完了・中止がどれもメニューで無効になり、理由が出ることを確認します。
9. 個票の「状態の履歴」に、登録・着手・中断・再開・完了の行が古い順に並び、前の状態・後の状態・理由・再開予定日が残っていることを確認します。
10. 別のTODOで「TODOを中止する」を選び、理由を入力して確認・適用すると「中止」になり、結果欄と状態の履歴に理由が残ることを確認します。

中止理由や中断理由の空欄、再開予定日が中断日より前など、入力に依存する条件は確認時に検査します。
一覧フォームで行や子項目を選ぶと、右ペインの「選択中」にTODO番号が表示され、その対象で操作できます。スクロールや背後の選択で入力中の操作対象は変わりません。

操作は差分確認後に保存まで行います。未保存の編集がある場合は先に保存してください。
通常の編集モードではCtrl+Zで操作を取り消した後、保存してください。
作成日は`common.yaml`の`auto: created`で自動記入します。更新しても作成日は変わりません。
更新日は`auto: updated`で、個票の中身を変えて保存したとき（操作の適用を含む）に本日が入ります。
過去分の作成日は、登録後に「TODOを編集する」で修正できます。過去の期限も、同じ操作で作成日と整合する値に設定します。
完了日・中断日・再開日・コメントの記録日は、操作開始時の本日を初期表示します。隠して再表示しても日付と入力は保持されます。
状態の履歴の日付は、完了・中断・再開では入力した日付、登録・着手・中止では適用した日です。
番号は、一覧と個票で使われているTODO番号の最大の次を振ります。番号を選んで登録することはできません。
カテゴリが存在しない、期限が登録日より前などの場合は、通常の適用では一覧も個票も保存されません。
「検証エラーがあっても適用する」は演習では選ばないでください。

## 作業項目で作業を小分けにする

個票の「作業項目」は、TODOの作業を小分けにした明細です。番号はTODOの番号に続けて自動で振ります（`TODO-006-S01`）。
済んでいない作業項目があるうちは、TODOを完了できません。完了したTODOに済んでいない作業項目が残っていると、検証が指摘します。
TODO管理の「作業」の列に、済の数と全部の数（`1/3`）が出ます。作業項目の無いTODOは空です。

1. TODO管理の対応中の行（`TODO-004`）の「⋯」から「作業項目を追加する」を選び、作業を入力して確認・適用します。個票の作業項目に `TODO-004-S04` が足され、「作業」の列が `3/4` になることを確認します。
2. 同じ行で「TODOを完了する」を選び、確認で「TODO-004 には済んでいない作業項目があります」と止まることを確認します。
3. 個票を開き、作業項目の `TODO-004-S04` の行の「⋯」から「作業項目を済にする」を選んで確認・適用します。もう一度「TODOを完了する」を選ぶと、完了できることを確認します。
4. 完了・中止したTODOで「作業項目を追加する」を選ぶと、「完了か中止をしているので、作業項目を足せません」と出ることを確認します。

作業項目の追加は、個票のある未完了（未着手・対応中・中断）のTODOだけです。済にする操作は、作業項目の型の操作（`methods`）で、作業項目の中だけを書き換えます。
配布時のデータでは、完了の`TODO-002`と対応中の`TODO-004`の作業項目はすべて済、中断の`TODO-006`は3件のうち1件が済です。

## タグで分類する

カテゴリは1つまでですが、タグはいくつでも付けられます（多対多）。タグは`todos/tag-list.yaml`に置き、`TAG-001`の番号で参照します。
「TODOを登録する」と「TODOを編集する」でタグを選べ、TODO管理の「タグ」の列でも直接編集できます。タグの追加は「タグを追加する」です。
ダッシュボードの「タグ別の状況」は、行がタグ・列が状態のクロス集計です。1件のTODOが複数のタグの行に数えられるので、合計の行と列は出しません。

## 続きのTODOを登録する

完了したTODOは戻せないので、追加の作業が要るときは、新しいTODOを登録して「元のTODO」にその番号を選びます。
元のTODOへの参照には関係の名前 `follow-up-of` を付けていて、元のTODOの側からは「続きのTODO」（関係レジストリの被参照の表示名）として読めます。
自分自身は選べず、参照をたどって元へ戻る輪もできません。配布時のデータの`TODO-008`は、完了した`TODO-003`の続きです。

## ダッシュボードを試す

作業用コピーを開くと「TODOダッシュボード」から始まります。左端レール最上部からも戻れます。
画面の定義は `.yde/views/todo-dashboard.yaml` にあります。業務の流れは `todo-behavior.yaml` から作り、TODOのデータや操作の規則は既存のものを共有します。

1. 上部の「業務の流れ」に、未着手・対応中・中断・完了・中止の段と、着手・中断・再開・完了・中止の線が出ることを確認します。段の箱には件数が出ます（配布時は 2・1・1・3・1）。
   未着手・対応中・中断は「未完了 4 件」の枠に入り、中止の線は枠から 1 本、完了の線は対応中から出ます。
2. 段の「中断」を押すと、その一覧が下に出ます。枠の空いた所を押すと、未完了（未着手・対応中・中断）の一覧が出ます。「期限超過」「個票未作成」「すべてのTODO」「カテゴリ別の状況」「タグ別の状況」の件数も押し、対応する一覧が出ることを確認します。
3. 基準日を `2026-10-25` にして「反映」を押します。配布時のデータでは期限超過はTODO-004だけです（TODO-006 は期限を過ぎていますが中断中なので数えません）。個票未作成は0件です。
4. 線「TODOを完了する」（対応中から完了へ）を押し、対応中のTODOが「いま操作できる」に並ぶことを確認します。行のボタンから、その場で操作を始められます。
   枠から出る線「TODOを中止する」を押すと、未完了の4件がどれも「いま操作できる」に並びます。
5. 中断の一覧でTODO-006のIDを押します。業務詳細の上部の「流れの中の位置」に、いまいる段（「いま「未完了 › 中断」にいます」）・次にできること（再開・中止）・状態の履歴（新しい順。中断・着手・登録）が出ることを確認します。
6. 「この対象の操作」から「TODOを再開する」を選んで確認します。確認に「中断」から「対応中」へ移ることが出ることを確認して適用します。詳細は維持され、「一覧へ」で中断の件数が減ることを確認します。
7. Undoで元へ戻ることを確認します。通常の編集モードではUndo後に保存、閲覧専用では操作のUndoも保存まで行います。
8. 上部の「操作」からTODO登録・カテゴリ追加・タグ追加を始めます。閲覧専用でも入力・差分確認・適用ができます。
9. 詳細のカテゴリ参照からカテゴリへ進み、「戻る」でTODOへ戻ります。「原本を開く」だけが編集画面へ移ることを確認します。
10. 「一覧へ」で区画・基準日・スクロール位置が残ることを確認します。「一覧と並べる」では詳細が広く、狭幅では全幅へ切り替わります。

見てほしい点は、開いてすぐ作業を始められるか、流れ図から「いま何ができるか」が分かるか、詳細の広さが十分か、参照や操作の途中でファイル構造を意識せずに済むかです。
基準日は表示用で、完了日などの操作入力を変更しません。「本日」で当日の表示に戻ります。
期限超過は未着手と対応中だけで、期限が未記入のTODOも含めません。個票未作成を「未着手」と読み替えることもありません（[一覧から個票へ詳しくする](#一覧から個票へ詳しくする)）。
業務の流れの段（区画）と線と未完了の枠は、ダッシュボードの `flow: {lifecycle: todo-lifecycle}` が状態の流れ（粗い流れと未完了の詳細化）から作るので、ダッシュボードには書いていません。
一般の定義方法は [ダッシュボードのマニュアル](../../docs/manual/dashboards.md) を参照してください。

## コメントを追加する

「TODO管理」の行の「⋯」から「TODOにコメントを追加する」を選び、本日が入った記録日を確認し、本文を入力して確認・適用します。
既存のコメントを残して末尾へ追記します。どの状態でも追加でき、状態は変えません。
個票がなければ、先に「TODOを編集する」で個票を作成してください。

## 操作でTODOを編集する

閲覧専用モードでも、行の「⋯」から「TODOを編集する」を選べます。
一覧と個票の現在値を初期表示し、変更した項目だけを送る方式です。何も変えずに確認すると、個票があるTODOでは「変更はありません」と表示されます。

| 対象 | 編集できる項目 |
|---|---|
| 一覧 | タイトル・概要・カテゴリ・タグ |
| 個票 | 作成日・期限・詳細・結果・コメント一覧 |

状態と完了日は、この操作では変えません。状態は着手・中断・再開・完了・中止の操作だけが変え、そのたびに状態の履歴へ1行残します。
TODO番号は対象を識別するため固定です。変更していない項目はそのまま残します。詳細などを空文字にすることと、項目自体を消すことは区別します。
「値を消す」を展開してチェックすると、カテゴリ・タグ・期限・詳細・結果・コメントを消せます。同じ項目へ入力した値より消去が優先します。タグを入力した場合は全体を置き換えます。
作業項目は、この操作では変えません（「作業項目を追加する」と「作業項目を済にする」か、編集モードの個票で変えます）。
コメント一覧を入力した場合は全体を置き換えます。追記には「コメントを追加する」を使い、履歴を残したい場合は一覧を置き換えないでください。
コメントの全消去は空の配列にし、それ以外の消去対象は項目を外します。タイトル・概要・作成日は消去対象にできません。
個票のないTODOは同じ操作で個票を作成します。状態は未着手、作成日は本日になり、状態の履歴に「個票の作成」の行が入ります。

1. 閲覧専用モードでTODOを選び、「TODOを編集する」を開きます。
2. タイトルと期限を変更して確認・適用し、一覧と個票の両方が更新され、変更していない概要やコメントが残ることを確認します。
3. 「値を消す」の期限にチェックして適用し、期限未定に戻ることを確認します。
4. 作成日より前の期限や、存在しないカテゴリを指定し、通常の適用では変更が保存されないことを確認します。
5. 一覧の「追加」で作った個票の無いTODOで編集を実行し、個票を作成できることを確認します。
6. 入力を変更してから対象を切り替え、破棄確認のキャンセルで元の入力が残り、承認すると新しい対象の現在値に変わることを確認します。
7. パネルを隠して元のTODOを編集し、再表示して「確認」を押すと読み直しを求めることを確認します。「初期値を読み直す」で変更後の値が入ります。
8. 「確認」の後で入力を変更し、古い差分が消えてもう一度確認が必要になることを確認します。

更新後の一覧と個票をまとめて検証します。
状態を誤って変えたときは、状態を変える操作で正しい状態へ進めるか、編集モードのフォームかソースで直します。フォームやソースでの書き換えは状態の履歴に残りません。
操作での整合性確認を保つため、「検証エラーがあっても適用する」は選ばないでください。

## カテゴリを追加する

右ペインの「操作」またはコマンドパレットから「カテゴリを追加する」を選び、カテゴリ名を入力して確認・適用します。
`CAT-`に続く番号は既存IDの最大値の次を自動採番します。追加したカテゴリはTODOの参照候補に現れます。
カテゴリ名の重複は現段階では禁止していません。

TODO登録の途中で候補が足りない場合は、現在の機能で次のように操作します。

1. TODO登録のパネルを「いったん隠す」で閉じます。入力途中の値は保持されます。
2. 編集モードで`todos/category-list.yaml`を開き、カテゴリ一覧の「追加」を押します。
3. 自動採番されたIDの行へカテゴリ名を入力し、保存します。
4. 右ペインの作業中の操作からTODO登録パネルを開き直し、新しいカテゴリを選びます。

登録途中は別の「カテゴリを追加する」操作を開始せず、一覧フォームで追加してください。現在の操作作業は1件のため、別の操作を始めると置き換わります。
一覧の「追加」とアクションは、どちらも`category-list.yaml`の`methods.insert`による同じ採番規則を使います。

## 操作の定義

| 操作 | アクションID | 状態の流れとの関係 |
|---|---|---|
| TODOを登録する | `register-todo` | 入口（未着手） |
| TODOに着手する | `start-todo` | 未着手 → 対応中 |
| TODOを中断する | `suspend-todo` | 対応中 → 中断 |
| TODOを再開する | `resume-todo` | 中断 → 対応中 |
| TODOを完了する | `complete-todo` | 対応中 → 完了 |
| TODOを中止する | `cancel-todo` | 未着手・対応中・中断 → 中止 |
| TODOにコメントを追加する | `add-todo-comment` | 状態を変えない |
| 作業項目を追加する | `add-todo-task` | 状態を変えない（未完了のときだけ） |
| 作業項目を済にする | 型の操作 `finish`（作業項目の行の「⋯」） | 状態を変えない |
| TODOを編集する | `edit-todo` | 状態を変えない |
| カテゴリを追加する | `add-category` | ― |
| タグを追加する | `add-tag` | ― |

`.yde/schemas/operations.yaml`に、各操作の目的（`description`）、入力（`params`）、初期設定（`input`）、前提（`require`）、更新内容（`do`）を定義しています。
状態を変える操作は `lifecycle: todo-lifecycle` を書くだけで、どの状態からできるか・状態の値・状態の履歴の行は `todo-behavior.yaml` の遷移から決まります。
操作に書くのは、状態のほかに書く値（完了日・結果）と、履歴の行に足す値（`lifecycle.history`。理由・日付・再開予定日）だけです。
`input.initial`は既存のひな型で一覧・個票から値を読み、日付は`context.today`から読みます。編集だけは`input.submit: changed`で変更分を送ります。
登録は、`create`で個票を採番して作り（`bind: todo`で作った個票に名前を付ける）、その番号を一覧の行へ写します（`{$copy: id, $of: todo}`）。一覧の「追加」とビューの新規行は、`todo-list.yaml`の`methods.insert`で同じ規則の番号を振ります。
カテゴリとタグの追加操作と採番規則は`.yde/schemas/category-list.yaml`と`tag-list.yaml`に定義しています。
完了の操作の前提は2つです。状態（対応中から）は状態の流れから決まり、作業項目の条件（済んでいない作業項目が無い）は`require`に書いています。作業項目は個票が保有する要素なので、入れ子の線（`edge: {contains: true}`）で辿ります。
作業項目の追加の前提（未完了のとき）は、状態を変えない操作なので状態の流れからは導けず、`require`に状態の値（未着手・対応中・中断）を並べています。
保存するデータの整合条件は`common.yaml`の型の検査に定義します。操作と通常の編集で同じ検査を使います。

## 状態の流れを確かめる

`.yde/schemas/todo-behavior.yaml`は、TODOの状態の流れの原本です。状態は個票の`status`の値ごとに1つで、表示名は未着手・対応中・中断・完了・中止です。
入口は「TODOを登録する」（未着手へ）で、移り方は着手・中断・再開・完了・中止の操作ごとに書いています。終わりの状態は完了と中止です。
`history: {path: history}` で、移るたびに個票の状態の履歴へ1行足します。
外から起きる出来事（Event）は宣言していません。個人のTODOでは、状態を変える出来事はどれも本人の操作として記録するためです。

宣言の点検と業務シナリオは、リポジトリの根で次のように実行します。どちらも原本を変えません。

```bash
./gradlew runCli -q --args="behavior-audit samples/todos"
./gradlew runCli -q --args="behavior-scenarios samples/todos samples/todos/scenarios/lifecycle.yaml"
```

1. `behavior-audit`の`status`が`structurally-checked`（構造の問題が無い）で、状態ごとに入口・入る線・出る線が並ぶことを確認します。
2. `behavior-scenarios`で11件のケースがすべて`passed`になり、`coverage`の入口と移り方の8本すべてに、通したケースが付くことを確認します。
3. 画面で状態を変える操作の「確認」を押すと、「Lifecycle の照合: 1 件中、要確認 0 件」と、移り方が宣言されていることが出ることを確認します。

シナリオは保存済みの同じデータから1件ずつ評価し、ケースの間で変更を引き継ぎません。そのため、データに各状態のTODO（未着手TODO-005・対応中TODO-004・中断TODO-006・完了TODO-001・中止TODO-007）を置いています。
通ったシナリオは具体例の確認で、すべての条件で正しいことの証明ではありません。

## 一覧から個票へ詳しくする

フォームやビューの「新規行」で一覧だけを作る従来の経路も残しています。行の番号は、登録と同じ規則で自動で振られます。
この経路で作ったTODOには個票が無く、状態の流れに入る前の途中の状態です。ダッシュボードの「個票未作成」に出ます。
「TODOを編集する」で個票を作ると、状態は未着手になり、状態の履歴に「個票の作成」の行が入ります。「TODO管理」の詳細列の「作成」からも作れますが、その場合の履歴は空のままです。
作成日は個票を作った本日になります。一覧を作った日まで遡りたい場合は「TODOを編集する」で修正できます。
配布時のデータの`TODO-005`は、一覧だけで作ってから、編集で個票を作った例です。

個票がないまま状態を変える操作を選ぶと、「状態が決まっていません」で止まります。コメント追加も個票が必要です。閲覧専用モードでは「TODOを編集する」で個票を作成できます。
個票の無いTODOがある間は、一覧を書き換える操作（登録など）の確認の「Lifecycle の照合」に、そのTODOの要確認（State を1つに特定できない）が出ます。診断なので、適用は止めません。
この途中状態はYDEの段階的詳細化の教材です。テーブルモデルでは一覧と個票を一つのレコードにまとめるので、この状態はありません。

## 型とビュー

ID（TODO・作業項目・カテゴリ・タグ）・年月日・一行の文・文章・ステータスを`.yde/schemas/common.yaml`で共通化しています。
同じ型を一覧・個票・操作の入力で使い、ID形式・文字数・日付の書式をそろえます。
年月日はファイルでは`YYYY-MM-DD`、画面では日本語表記です。タイトルと概要は改行なし・100文字以内です。
共通型の検査では、期限・完了日・更新日が作成日以降、完了状態には完了日と結果が必要、完了以外には完了日を残さない、再開予定日は中断した日以降、元のTODOは自分以外、を確認します。
状態の履歴の行は、日付・操作・前の状態（登録と個票の作成の行には無い）・後の状態・理由（中止と中断、再開のメモ）・再開予定日（中断）です。
TODO管理は一覧と個票の項目を同じ行へ射影します。期限順は日付として並べ、期限未定を後ろに置きます。
カテゴリ×ステータスはクロス集計（`kind: matrix`）で、行がカテゴリ、列が状態、セルが件数です。合計の行と列は自動で付き、セルを押すと数えたTODOへ移動できます。
カテゴリを持たないTODOは、この表では数えません。
カテゴリ・タグ・元のTODOへの参照には関係の名前（`in-category`・`tagged`・`follow-up-of`）を付け、関係レジストリで表示名と、カテゴリと元のTODOは「1つまで」を宣言しています。タグは数を限りません。
同じタグを1件のTODOに2回付けることは、現段階では禁止していません。
作業項目はIDを持つ個票の中の要素で、エンティティ`todo-task`です。TODOが作業項目を保有する（入れ子の線）形で、関係レジストリには参照の関係として書きません。
TODO管理の更新日は個票の更新日（`auto: updated`）です。一覧の側（タイトル・概要・カテゴリ）だけを変えたときは変わりません。
状態・完了日・作成日はビューで直接編集する列にしていません。ただしフォーム・ソース編集は可能です。
操作を通した試用にはYDEの閲覧専用モードも使えます（操作は実行できます）。アクセス権限の仕組みではありません。
コメントは日付と本文で、並び順は任意です。

## テーブルモデルへ反映する

1. TODO管理の変更を、`.yde/`の型・制約・状態の流れ・操作・ビューに反映します。
2. 登録→着手→中断→再開→完了、中止の試用で、入力・状態・履歴の意味を確認します。
3. テーブルモデル側の概念・論理・物理設計へ対応づけ、SQLへの影響を確認します。
4. テーブル設計で見つかった業務上の不足は、こちらのTODO管理モデルで決め直します。

両ワークスペースの役割と定義の形式は異なり、自動同期はしません。型・制約・操作の意味が設計に反映されているかを確認します。
物理型・索引・DB固有制約はテーブルモデルだけで管理します。
