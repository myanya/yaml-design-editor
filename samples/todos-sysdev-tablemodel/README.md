# TODOのテーブルモデル

[todos](../todos/README.md)の業務を、概念・論理・物理へ段階的に詳しくする設計サンプルです。
まず設計書としての定義と対応を確認し、その上でYDEによるDDL・DML生成に必要な情報と機能を検討します。
外部ジェネレーターや実行環境のインストールは不要です。

## 構成

| 場所 | 役割 |
|---|---|
| `model/business.yaml` | 概念設計（業務概念・関連・多重度・TODO操作とカテゴリ追加の意味） |
| `model/20_logical/` | 論理設計（属性・業務型・識別子・他エンティティへの参照） |
| `model/30_physical/` | 物理設計（テーブル・カラム・SQLの型対応・キー・索引・DBで保証する条件） |
| `.yde/schemas/` | 設計文書のフォームと検証（側面の宣言・カバレッジ・関係レジストリ） |
| `.yde/views/` | 対応表・テーブル定義の表・物理テーブルの文書を開いたときの複合文書ビュー |
| `.yde/reports/` | テーブル定義書（Markdown）のレポート |
| [reference/schema.sql](reference/schema.sql) | 物理設計の主要部分をSQLで表した手書きの参考例 |
| [reference/sample-data.sql](reference/sample-data.sql) | データ投入を考えるための手書きのINSERT例 |
| [DDL-STUDY.md](DDL-STUDY.md) | 設計上の未決事項と、YDEでの生成に向けた検討 |

SQLの自動生成機能は含めていません。参考SQLは全制約を網羅せず、モデル変更にも自動追随しません。
差分を読んで「どの定義から、このSQLになるのか」を議論するための資料です。

## todosとの関係

`todos`では、`.yde/`の型・制約・操作・ビューによってTODO管理をモデル化しています。
こちらの`model/business.yaml`は、その意味を概念設計として記述する文書で、`.yde/schemas/business.yaml`はこの設計文書の形式を定義します。
`todos`のファイルのコピーではなく、専用システムの設計として管理します。別ワークスペースを実行時に読むことはありません。
変更時は`todos`の型・制約・操作を確認し、概念・論理・物理設計への影響を反映します。設計で見つかった業務上の不足は`todos`側にも反映します。
両者の自動同期はありません。操作の`action`は`todos`のアクションIDとの対応を示す文字列で、操作を実行する定義ではありません。

概念・論理・物理は、同じ`ENT-*`の3つの側面（別の文書に書いた同じIDの出現）です。
概念が名称と意味を、論理が属性・識別子・設計判断を、物理が物理名・カラム・キー・索引・条件を所有します。
属性`ATTR-*`も論理（名称・業務型・必須・元となる情報）と物理（カラムの物理名）の2つの側面を持ち、業務型`DT-*`は論理（基底型と制約）と物理（SQLの型）の2つの側面を持ちます。
つまりカラムは属性の物理の側面で、別のIDを持ちません。1属性対1カラム、1エンティティ対1テーブルが構造になります（「実装との境界」）。
具体的なTODOの番号`TODO-001`と、設計上の概念`ENT-TODO`は別の識別子です。
将来のUI・アプリケーション設計でも共通の設計IDを使う想定ですが、それらのサンプルはまだ含みません。

## 設計の要点

- TODO一覧と個票は同じ対象の側面なので、物理設計では`todos`にまとめます。
- コメントは繰り返す記録なので`comments`に分け、TODO番号とコメント番号の複合キーにします。
- カテゴリは独立した`categories`とし、未分類はTODOの外部キーをNULLにします。
- 必須・文字数・選択肢などは論理属性と業務型を原本にします。物理型は業務型の物理の側面（`types.yaml`）で決めます。
- 論理属性の`required: true`をNOT NULLに対応させます。この規則は型対応の方針に1か所だけ書きます。空文字とNULLの区別は別の設計論点です。
- 外部キーの削除・更新時の扱い、索引の目的、DBで保証する条件は物理定義へ明記します。
- SQLiteは具体的な型とDDLを議論するための仮置きです。アプリの採用DBを確定したものではありません。

関連の`target_min`などは業務データの多重度です。
YDEの関係レジストリが検査する設計要素の参照数とは区別します。
物理定義の`checks[].condition`は設計上の文章です。YDEで実行される検査式ではありません。

## YDEで見る

1. このディレクトリをYDEで開き、`model/30_physical/ENT-TODO.yaml`（物理テーブル）を開きます。複合文書ビュー「物理テーブル定義書」が、物理名・概念の意味（`business.yaml`）・カラム定義の表・論理の属性（`20_logical/ENT-TODO.yaml`）・キーと索引を1枚に合成します。概念や論理の区画を編集すると、その文書が未保存になります。
2. カラム定義の表で、物理名・論理名・SQL型・NULL可否・主キー・外部キー先を読みます。これらは論理属性・業務型・型対応から辿った値で、物理の文書には物理名しか書いていません。
3. 台帳のビューで「概念・論理・物理の対応」と「属性とカラムの対応」を開き、同じIDの側面が1行に並ぶことを確認します。「テーブル定義（カラム）」は上の欄にテーブルのIDを入れると絞れます。
4. エンティティページで`ATTR-TODO-CATEGORY`を開き、論理（名称・業務型・必須・参照先）と物理（category_id）が1枚で出ること、所属（`ENT-TODO`の属性とカラム）と被参照（外部キー・索引）が並ぶことを確認します。
5. レポート「テーブル定義書」をテーブルのID（例 `ENT-TODO`）で作り、Markdownの定義書を読みます。CLIなら `./gradlew runCli -q --args="report samples/todos-sysdev-tablemodel table-spec --param table=ENT-TODO --print"` です。
6. 参考SQLと比較し、YAMLに根拠がある部分と、まだ決める必要がある部分を確認します。

グラフレンズでは、関係レジストリの日本語のラベル（属性・カラム・主キー・外部キーの参照先など）で保有と参照を確認できます。
関連は独立した要素として表し、多重度はフォームで読みます。専用ER図の表記を実装するサンプルではありません。

## 確認の範囲

YDEでスキーマ・ID・参照を検証し、論理属性の欠落、属性の未実装（カラムの無い属性）、型対応の漏れを確認します。
未実装と対応漏れは、カバレッジ（論理の`ENT-*`と`ATTR-*`は物理に、`DT-*`は型対応に出現すること）が指摘します。
エラーがないことだけで設計が完成したとは判断せず、判定保留や設計上の未決事項も確認してください。
物理名の重複、キーの所属、FKの型の一致などは、どの検査を定義すべきかという検討事項に含めています。
参考SQLをDBで実行する検証や、業務型のすべての制約をSQLに写す検証は、このサンプルの確認手順には含めません。

業務操作は`todos`で登録→着手→完了→再開→中止を試します。
コメント追加と編集では、状態を保った追記と、一覧・個票をまとめた訂正を確認します。個票の作成も編集操作で行えます。
DBの状態制約と、操作時の前提・履歴記録・トランザクションの責務を分けてレビューしてください。
新しいサンプル専用のテストコードは追加せず、YDEの検証と以下の試用手順を使います。

## 変更演習

作業用コピーで試し、各演習後に変更を戻してください。

1. `DT-LINE.max_length`を100から80へ変更し、影響する属性・カラムと参考SQLの箇所を列挙します。「属性とカラムの対応」の業務型の列から辿れます。
2. `model/30_physical/ENT-CATEGORY.yaml`から名前のカラム（`ATTR-CATEGORY-NAME`）を外し、「論理属性はカラムとして実装されること」の指摘が論理の文書に出ることを確認します。
3. `model/30_physical/types.yaml`から一行外し、「業務データ型はSQLの型への対応を持つこと」の指摘が出ることを確認します。
4. 完了状態の条件を読み、DBで保証する条件と、再開操作で保証する条件を説明します。
5. [生成の検討](DDL-STUDY.md)に沿って、一つのカラム定義を作るために必要な情報と処理を確認します。

## 実装との境界

今は1エンティティ対1テーブル、1属性対1カラムを題材にし、それを「同じIDの側面」として構造に持たせています。汎用変換の制約を定めたものではありません。
分割・統合（1属性を複数のカラムに、複数のエンティティを1つのテーブルに）を扱うときは、カラムやテーブルに別のIDを与えて参照でつなぐ形へ戻すか、両方式を併用します。
複合外部キー、循環する参照、DB方言差、マイグレーションも後続の検討対象です。
検証は既存のQuery・Predicateと関係検査、ビューはQueryを利用します。
生成に使えるConstruct・Expressionの範囲は検討資料で整理し、SQL生成のためのYDE本体の拡張は行っていません。
