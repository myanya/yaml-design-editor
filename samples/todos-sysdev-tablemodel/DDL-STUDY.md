# DDL・DML生成の検討

目的は、設計情報をYDEで管理し、その定義からSQLを組み立てる際に必要なものを明らかにすることです。
生成機構の実装や、外部コードによる不足の補完はこの段階では行いません。
以下はリポジトリの変換・値の式・エクスポートの仕様と実装を読んだ整理です。生成を端から端まで試作した結果ではありません。

## 設計定義から読む情報

| SQLに必要な情報 | 原本 | 現在の扱い |
|---|---|---|
| テーブル名・カラム名・並び | 物理テーブルの`physical_name`・`columns` | 配列順をカラム順とする |
| SQL型 | カラム→論理属性の`dtype`→型対応表 | SQLiteのTEXT・INTEGERを仮置き |
| NULL可否 | 論理属性の`required` | trueをNOT NULL、falseをNULL許可とする |
| 主キー・列の順序 | 物理テーブルの`primary_key` | コメントは複合キー |
| 外部キー・削除／更新時の動作 | `foreign_keys` | 参照先を明記しRESTRICTを指定 |
| 索引と一意性 | `indexes` | カテゴリ別・期限順は非一意索引 |
| 値の制約 | 業務型の長さ・選択肢・形式・下限など | SQLへの写し方は未確定部分がある |
| 項目間の条件 | 物理テーブルの`checks` | 条件を文章で定義し、SQL化は手で検討する |
| 既定値・採番 | 各テーブルの`notes`と業務操作 | DB既定値に頼らず操作から渡す |

「名前・型・NULL可否・キー」が読めることと、すべての業務制約をDDLで保証できることは分けて考えます。
`checks[].condition`の自然文を機械的に実行できるとはみなしません。

## 参考SQLの範囲

[schema.sql](reference/schema.sql)は3テーブルの名前・型・NULL可否・PK・FK・索引と、代表的なCHECKを記述した手書き例です。
業務型のID形式、改行禁止、実在日付、空白文字の扱いまでを網羅した完成DDLではありません。
モデルを変えても参考SQLは変わらないので、レビューで対応を確認します。
[sample-data.sql](reference/sample-data.sql)も手書き例で、YDE上の実データを自動移送するものではありません。

## YDEの既存機能と確認点

TODO登録時の作成日はYDEの`auto: created`で補い、カテゴリ番号は配列の追加規則で採番します。
専用システムではアプリとDBのどちらがこれらを決定するか、日付の基準と同時登録時の採番も設計します。参考DDLに自動変換した定義はありません。

| 処理 | 既存の部品・確認した仕様 | 残る確認・不足 |
|---|---|---|
| 対象を選び、属性・型対応をたどる | Queryの参照追跡と束縛、ビューの結合 | 必要な値が欠落・重複した場合の生成中止条件を定義する |
| カラムごとの構造を組み立てる | Transformの`from`・`build`・`$each`・`$copy` | 複数文書を読むクエリとテーブル単位の組み立ての接続を試す |
| 型やNOT NULLの断片を作る | `$format`・`$map`・`$when`、値の式の`format` | 各断片を既存の式でどこまで書けるか小さな例で確認する |
| カラムや制約を区切って連結する | `$concat`は配列を連結する指示 | 可変長配列を区切り付き文字列へ変換する指示は確認できていない |
| 順序を保つ | 入力配列の順序とクエリの決定的な順序 | カラム順・複合キー順・テーブルの依存順は別に扱う |
| SQLの引用とエスケープ | 汎用の文字列穴埋め | SQL識別子・文字列リテラルを区別した引用処理は確認できていない |
| SQLファイルへ出力する | TransformはYAMLの項を返し、標準exportは表形式 | SQL／任意テキストの専用出力形式がない |
| 入力の問題を報告する | 検査の違反・保留、変換結果の出どころ | 値が得られない項目を落とす変換の仕様を、生成時にどう扱うか決める |

確認した主な資料は、リポジトリの`docs/architecture/transform.md`と`docs/architecture/agents.md`です。
実装では`semantic-core/schema/Transform.kt`・`ValueExpr.kt`、アプリの`skill/Skills.kt`の対応形式を参照しています。
ここで「確認できていない」とした処理を直ちに新機能と決めず、既存の組合せや制約を絞った定義で表せるか先に試します。
表エクスポートの配列セル用`join`と、変換結果全体をSQL文へ組み立てる処理は同じとは限りません。

## 設計上の未決事項

- 業務型の制約をどこまでDBに置くか。日付は保存形式の確認だけでなく、実在性の確認方法も必要。
- 文字列の空・空白・改行をどう定義するか。YDEの文字列検査とDBの文字関数の同等性は未確認。
- コメント番号の同時追加時の採番、衝突時の再試行、既存コメントの並べ替えをどう扱うか。
- TODOやコメントの削除を業務操作として認めるか。今の物理設計は参照がある削除を拒否する仮案。
- カテゴリ名を重複可能とするか。現在は重複禁止の業務要件がないため一意制約を設けていない。
- キーのカラムが同じテーブルに属すること、FKの型が一致すること、物理名が重複しないことを、どのYDE検査で表すか。

これらはこのサンプルの検討事項です。YDE本体の不具合や新機能要求として確定したものではありません。
本体や既存の未変更部分へ手を入れる必要が出た場合は、対象と変更案を列挙し、承認を得てから進めます。

## DMLで追加して決めること

初期データ用INSERTには、テーブル定義に加えて投入する行・値・NULL・省略値・投入順序の定義が必要です。
行の値を設計IDでカラムに結び付けるか、物理名で書くかも未決定です。
参考のINSERT例は「どのような出力が欲しいか」を示すだけで、入力データのスキーマはまだ設けません。
TODOの登録・状態変更・コメント追加・編集の業務SQLまで扱う場合は、操作の前提・更新対象・トランザクション・同時更新も別途設計します。

## 次に試す最小の範囲

1. 一つのカラムについて、物理名・型・NULL可否をYDEのクエリまたはビューでそろえる。
2. その情報からSQLの一行を作り、既存の式で可能な部分を確認する。
3. 複数カラムを一つのCREATE TABLEへまとめる段階で、順序・連結・引用の不足を切り分ける。
4. 画面やCLIで得た文字列をファイルへ出す方法を検討する。

まず1と2を議論・確認してから、必要な最小の部品と追加する場所を決めます。
選択はQuery、値の導出はExpression、構造の組み立てはConstructに寄せ、外部実装を先に作らない方針です。
