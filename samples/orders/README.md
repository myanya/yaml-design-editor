# 注文管理

YDE（YAML Design Editor）上でそのまま使える、注文管理のサンプルワークスペースです。
注文・顧客・会社・商品を別々のファイルで管理し、注文は顧客（窓口）を、法人の顧客は所属会社を、注文明細は商品を番号で参照します。
明細の金額と注文の合計は検査が確かめ、顧客別・商品別・月別の件数と金額はビューが注文から計算し、売上はチャートで見ます。AI 接続は不要です。

[TODO 管理サンプル](../todos/README.md)が 1 種類の情報の操作とダッシュボードを見せるのに対し、このサンプルは複数の種類の情報を参照でつなぐこと、入れ子で書いた明細を保有として扱うこと、金額の整合を検査で守ること、参照を辿って集計すること、集計を図にすることを見せます。
在庫、入金、返品、出荷済みの注文の取消は扱いません。

## 配置と原本

| 場所 | 内容 |
|---|---|
| `orders/ORD-<番号>.yaml` | 注文の原本です。1 件 1 ファイルで、明細は注文の中に入れ子で書きます |
| `customers/CUS-<番号>.yaml` | 顧客（注文の窓口。個人、または法人の部署・担当者）の原本です。1 件 1 ファイルです |
| `companies/COM-<番号>.yaml` | 会社の原本です。法人の顧客が所属会社として参照します。1 件 1 ファイルです |
| `products/PRD-<番号>.yaml` | 商品の原本です。1 件 1 ファイルです |
| `.yde/schemas/common.yaml` | 共通の型です。番号・金額・日付などの値の型と、注文・注文明細・顧客・会社・商品のオブジェクト型、金額と所属会社の検査を持ちます |
| `.yde/schemas/order.yaml`、`customer.yaml`、`company.yaml`、`product.yaml` | 型を文書に当てる定義です。注文には、明細番号の検査、販売を終えた商品の検査、4 つの操作があります |
| `.yde/schemas/relations.yaml` | 関係の語彙です。注文顧客、所属会社、注文商品、注文明細の表示名と多重度を宣言します |
| `.yde/views/` | 注文一覧、顧客一覧、会社一覧、商品一覧、月×状態の売上（クロス集計）、4 つのチャートと、入口になるダッシュボードです |

`.yde/workspace.yaml` で `orders`、`customers`、`companies`、`products` の 4 つを台帳として指定しています。
スキーマとビューも同梱しているため、このディレクトリをコピーして単独で開けます。
配布時のデータは、2025 年 11 月から 2026 年 10 月までの注文 109 件（出荷済み 95・取消済み 7・未処理 7）、顧客 22（個人 10・法人の窓口 12）、会社 10（ツキノワ製作所とそよかぜ学園には窓口が 2 つ）、商品 20（文具・オフィス機器・オフィス家具・消耗品・飲料・食品の 5 つの分野。2 つは販売終了）です。
会社名・人名・住所・電話番号・法人番号・メールアドレスはすべて架空です。会社名は同名の法人が見つからない造語、住所の番地は X-X-X、電話番号の中央 4 桁は 0000、法人番号は先頭が 0、メールは example.* のドメインにしています。日本の市内局番と携帯電話の番号は 0 で始まらず、法人番号の先頭（検査用数字）は 1〜9 なので、この形の番号は実在しません。

## 項目

| 注文（`orders/`） | 意味 |
|---|---|
| `orderId` | 注文番号。`ORD-001` の形で、ファイル名にもなります |
| `orderedAt` | 注文受付日。`YYYY-MM-DD` で書き、画面では日本語の日付で見せます |
| `status` | 注文状態。`pending`（未処理）、`shipped`（出荷済み）、`cancelled`（取消済み） |
| `customerId` | 注文顧客。顧客番号の参照です |
| `totalAmount` | 注文合計金額（円）。明細金額の合計と一致することを検査が確かめます |
| `lines[]` | 注文明細。`orderLineId`（明細番号 `ORD-001-01`）、`productId`（注文商品）、`quantity`（注文数量）、`unitPrice`（単価）、`amount`（明細金額） |

| 顧客（`customers/`） | 意味 |
|---|---|
| `customerId` | 顧客番号。`CUS-001` の形です |
| `kind` | 区分。`individual`（個人）か `corporate`（法人）。法人には所属会社が要り、個人には書きません（検査が確かめます） |
| `name` | 顧客名＝窓口の名前。法人なら部署と担当者（例「総務課 佐々木」）。会社名は会社の文書が持ちます |
| `companyId` | 所属会社。会社番号の参照で、個人は空です |
| `department` | 部署 |
| `email`、`phone` | メールアドレスと電話番号。形式を型で決めています |

| 会社（`companies/`） | 意味 |
|---|---|
| `companyId` | 会社番号。`COM-001` の形です |
| `name` | 会社名。一覧や参照先の名前に使います |
| `corporateNumber` | 法人番号（13 桁の数字） |
| `address`、`phone` | 所在地と代表電話 |

| 商品（`products/`） | 意味 |
|---|---|
| `productId` | 商品番号。`PRD-001` の形です |
| `name` | 商品名 |
| `unitPrice` | 現在の販売単価。注文明細の単価は注文したときの値なので、ここを変えても過去の注文は変わりません |
| `active` | 有効商品か否か。販売を終えたら `false` にします |

## 検査

| 名前 | 中身 | 書いてある場所 |
|---|---|---|
| `amount-is-unit-price-times-quantity` | 明細金額は単価 × 注文数量であること | `common.yaml` の型「注文明細」の `constraints`。明細の要素ごとに評価します |
| `total-is-sum-of-lines` | 注文合計金額は明細金額の合計であること | 型「注文」の `constraints`。`lines[*].amount` の `sum` と比べます |
| `has-lines` | 注文には明細が 1 件以上あること（警告） | 型「注文」の `constraints` |
| `line-id-starts-with-order-id` | 明細番号はその注文の番号で始まること | `order.yaml` の `constraints`。注文から明細へ保有の線を辿ります |
| `pending-order-has-no-inactive-product` | 未処理の注文に、販売を終えた商品が含まれていないこと（警告） | `order.yaml` の `constraints`。明細から商品へ参照を辿ります |
| `corporate-has-company` / `individual-has-no-company` | 法人の顧客には所属会社があり、個人には無いこと | `common.yaml` の型「顧客」の `constraints` |
| 参照の型と多重度 | 注文は顧客を 1 件、明細は商品を 1 件、顧客は会社を 1 つまで参照すること。会社には窓口が 1 つ以上あること（警告） | `relations.yaml` |

配布時のデータは、エラー 0・警告 0 です。

## ビューとダッシュボード

| 名前 | 中身 |
|---|---|
| 注文一覧（`order-grid`） | 受付日、注文月（受付日から `yearMonth` で導く計算列）、状態、顧客、合計金額、明細数。明細番号も `ORD-` で始まるので、行は ID の形ではなくエンティティ型 `order` のクエリ行で選びます |
| 顧客一覧（`customer-grid`） | 区分、顧客名、表示名（法人は「会社名 窓口名」、個人は顧客名。`format` と `via` の計算列）、所属会社、会社名、部署、連絡先と、この顧客の注文の件数と購入合計（取消済みは除きます）。「新規行」で顧客番号を入れると顧客のファイルができます |
| 会社一覧（`company-grid`） | 法人番号、所在地、窓口の数と、会社 ← 顧客 ← 注文 の 2 段で集めた注文の件数と購入合計。注文は会社を書かないので、顧客を経由して集めます |
| 商品一覧（`product-grid`） | 現在の販売単価、有効かどうか、受注数量の合計（取消済みの注文は除きます）。「新規行」で商品のファイルができます |
| 月×状態の売上（`month-by-status`） | クロス集計です。行は注文受付日の年月（`rows: {value: {yearMonth: …}}` で受付日から導くので、月の文書は置きません）、列は注文状態、セルは注文合計金額の合計。合計の行と列が付きます |
| 月別売上（`monthly-sales-chart`） | 月×状態の売上を積み上げ棒にしたチャートです。横軸＝年月、系列＝状態 |
| 売上の推移（`monthly-trend-chart`） | 同じ表の「合計」の列を折れ線にしたチャートです（合計の列は `series` に書いて選びます） |
| 顧客別の購入割合（`customer-share-chart`） | 顧客一覧の購入合計を、多い順（`order: {direction: desc}`）に円にしたチャートです。項目の文字は「表示名」の列（`x: 表示名`）なので、法人は会社名つきで出ます |
| 会社別の購入割合（`company-share-chart`） | 会社一覧の購入合計を多い順に円にしたチャートです。個人の注文は含みません |
| 注文ダッシュボード（`order-dashboard`） | 未処理、出荷済み、取消済み、すべての注文、顧客別、会社別、商品別、月別売上（図）、顧客別の割合（図）、会社別の割合（図）の 10 の区画（状況・内訳・図の 3 つの群）と、「注文を登録する」の入口です |

集計の列は、行の要素を起点に参照の線を辿って注文や明細を集め、`count` や `sum` で求めます。
セルを押すと集めた注文の一覧が出て、そこから原本へ移動できます。
チャートはデータを持たず、元の表（グリッドかクロス集計）の行を横軸の項目、数の列を系列にして描くだけです。図の種類は `chart: bar | stacked-bar | line | pie` で変えられます。

## 操作

| 操作 | アクション ID | 前提 |
|---|---|---|
| 注文を登録する | `register-order` | 注文番号が未使用であること。受付日は本日が初期値です。明細は商品・数量・単価を表で入れると、明細番号（注文番号-01、-02 …）と明細金額、注文合計金額が自動で入ります |
| 明細を足す | `add-order-line` | 未処理であること。商品・数量・単価を入れると、明細番号は配列の追加の決まりで採番され、明細金額と合計が更新されます |
| 注文を出荷する | `ship-order` | 未処理で、明細が 1 件以上あること |
| 注文を取り消す | `cancel-order` | 未処理であること。出荷済みの注文は取り消せません |

定義は `.yde/schemas/order.yaml` の `actions` にあります。前提を満たさない操作はメニューが無効になり、理由が表示されます。
登録の明細は、ひな型の `$each` と `$position`（1 始まりの番号）、`$number` の `$as: "00"`（0 詰め）、`$value`（単価 × 数量の計算と合計）で組み立てます。フォームの明細の表の「追加」で足した行は、配列の追加の決まり（`common.yaml` の `methods.insert`。接頭辞は親の注文番号を `$of: self` で読みます）で採番されます。
操作は差分を確認してから保存まで行い、`Ctrl+Z` 1 回で戻せます。閲覧専用モードでも実行できます。

## 試す

作業用にこのディレクトリをコピーし、YDE で開いてください。「注文ダッシュボード」から始まります。

1. 区画の件数を確かめます。配布時のデータでは、未処理 7（ORD-102・103・105〜109）、出荷済み 95、取消済み 7、すべての注文 109、顧客 22、会社 10、商品 20、月別売上 12 項目（2025-11〜2026-10）、顧客別の割合 22 項目、会社別の割合 10 項目です。区画は「状況」「内訳」「図」の 3 つの群に分かれ、群の見出し（▾）を押すと畳めます。窓を狭めると、横に 3 段以上になるところで左の縦一覧に切り替わります（`placement: auto`）。
2. 「未処理」の一覧で ORD-105 の番号を押します。業務詳細に、顧客の参照（CUS-013 設計部 春風＝合同会社カゼノミチ設計の窓口）と、明細の表が出ることを確認します。
3. 「この対象の操作」から「注文を出荷する」を選び、確認して適用します。「一覧へ」で戻ると、未処理 6・出荷済み 96 になります。`Ctrl+Z` で戻せます。
4. 出荷済みの注文（ORD-001 など）では「注文を取り消す」が無効になり、理由が表示されることを確認します。
5. 上部の「操作」から「注文を登録する」を選び、注文番号 `ORD-110`、受付日（本日が入っています）、注文顧客 `CUS-003` を入れ、注文明細の表に商品 `PRD-003`・数量 `2`・単価 `4800` の行を足して確認します。差分に明細番号 `ORD-110-01`、明細金額 `9600`、注文合計金額 `9600` が入っていることを見て適用します。明細を入れずに登録すると、合計 0 の注文ができて「明細がありません」の警告が出ます。
6. ORD-110 の業務詳細で「明細を足す」を選び、商品 `PRD-001`・数量 `3`・単価 `300` を入れて適用します。明細番号が `ORD-110-02` になり、合計が `10500` に更新されることを確認します。「原本を開く」で明細の表の「追加」から足した行も、同じ決まりで番号が付きます。
7. 検査を起こしてみます。明細金額を `9000` にすると「明細金額は単価 × 注文数量であること」のエラーが反例つきで出ます。明細番号を `ORD-111-01` にすると番号の検査が、注文商品を `PRD-004`（販売終了）にすると警告が出ます。直せば消えます。
8. 台帳スペースの「ビュー」で「顧客一覧」を開きます。注文件数と購入合計のセルを押すと、集めた注文から原本へ移動できます。「商品一覧」の受注数量も同じです。
9. 台帳スペースの「レンズ」で、実体の段に注文から顧客、明細から商品への線と、注文が明細を保有する入れ子が出ることを確認します。「型」の段に切り替えると、注文・注文明細・顧客・商品の 4 つの型の図になります。
10. ダッシュボードの「月別売上」を押します。2025-11 から 2026-10 の 12 本の積み上げ棒（未処理・出荷済み・取消済み）が出て、棒にマウスを載せると金額が見えることを確認します。2026-10 の「未処理」の部分を押すと、図の下に材料（10 月の未処理の注文 7 件、合計 60,700）が並び、「詳細」で注文の業務詳細へ、「原本」でファイルへ進めます（`drill: below`）。「元の表を開く」で月×状態の売上（クロス集計）へ移り、行が受付日の年月で、セルの来歴からも同じ注文へ辿れることを見ます。
11. 「顧客別の割合」は購入合計の多い顧客から並びます。扇形（または凡例の行）を押すと、その顧客の注文が図の右に並びます（`drill: right`）。「ビュー」タブの「売上の推移」（折れ線）では点を押すと浮いた一覧が出ます（既定の `popup`）。注文を 1 件登録したり受付日を変えたりすると、表と図が追随します（未保存の編集も映ります）。
12. 「会社別」を押します。株式会社ツキノワ製作所の窓口が 2（総務課・営業部）で、注文件数と購入合計が 2 つの窓口の注文を合わせた値になっていることを確認します。「会社別の割合」は会社ごとの円で、扇形を押すとその会社の注文が右に並びます。
13. 「顧客別」で法人の顧客（例 CUS-012 総務課 佐々木）の業務詳細を開き、所属会社の参照から会社のページへ、会社のページの関係パネル「所属する顧客（窓口）」から他の窓口へ進めることを見ます。個人の顧客に所属会社を書くと「個人の顧客に所属会社が書かれています」のエラーが、法人の顧客の所属会社を消すと「法人の顧客に所属会社がありません」のエラーが出ます。

見てほしい点は、参照の入力で候補と相手の名前が分かるか、明細の表で追加と金額の入力が自然にできるか、検査の反例の文面で直す場所が分かるか、1 件 1 ファイルの置き方で困る場面が無いか、図の見え方（棒の太さ・色・項目名の長さ）が業務の画面として十分か、です。

## 決めていること

- **明細の単価は注文したときの値です。** 商品の現在の販売単価を変えても、過去の注文の明細は変わりません。単価の違い（ORD-005 のまとめ買い）は、そういうものとして残します。
- **合計金額は原本に書き、検査で守ります。** 式で自動計算にせず、見えている値を原本に持たせ、「合計は明細の合計と一致すること」を検査します。
- **明細番号は自動で付きます。** 登録の操作ではひな型の `$position` で、明細の表の「追加」と「明細を足す」では配列の追加の決まり（親の注文番号を接頭辞に）で採番します。手で書いた番号も受け付け、「注文番号で始まること」を検査が確かめます。
- **取消済みの注文は、顧客別・商品別の集計に数えません。** 一覧には残ります。月×状態の売上では「取消済み」の列に出ます。
- **月の文書は置きません。** 月ごとの集計は、受付日から `yearMonth` で年月を導いて行にします（クロス集計の `rows.value`）。月をものとして持ちたくなったら（期首残高のような月の属性が要るとき）、家計簿の試作のように月の文書を足します。
- **顧客は注文の窓口で、法人の顧客は所属会社を参照します。** 会社は顧客と独立して存在し、同じ会社に複数の窓口（部署・担当者）が付くので、入れ子でなく参照にしました。顧客名は窓口の名前（部署と担当者）にし、会社名は会社の文書だけが持ちます（二重管理をしない）。一覧では会社名を参照から辿った列で補います。
- **`kind`（個人／法人）は残し、所属会社との整合を検査で守ります。** 所属会社の有無から導くこともできますが、個人事業主のような「会社は無いが法人扱い」も表せるように、区分は明示します。
- **注文は会社を書きません。** 会社別の集計は 会社 ← 顧客 ← 注文 の 2 段で集めます（クロス集計とビューの `all` で書けます）。
- **商品は 5 つの分野に分けてあります。** 文具・オフィス機器・オフィス家具・消耗品・飲料・食品で、いまは各商品ファイルのコメントに書いてあるだけです。商品カテゴリーの定義を足すときは、この分け方をカテゴリーの文書にして、商品から参照します。
- **データは配布時のものを手で直して使います。** 1 年分の注文は、まとめ買いの値引き（単価が現在の販売単価より安い明細）、販売終了の商品を含む過去の注文、取消済みの注文を含みます。
- **注文状態の遷移は、未処理から出荷済みか取消済みへの 1 段だけです。** 出荷済みの取消や返品は扱いません。

## 動かし方

```bash
./gradlew run --args="samples/orders"                              # GUI で開く（作業用のコピーで）
```
